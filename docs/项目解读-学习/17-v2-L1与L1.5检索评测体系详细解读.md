这份文档最重要的价值，不是“多加了一套 benchmark”，而是把 DevContext 的检索评测从：

> **搜索结果像不像答案相关内容？**

升级成了：

> **整条证据收集链，能不能可靠地把回答所需证据找齐，并正确判断自己是否已经找齐？**

这是一次非常关键的升级。因为你的生产链路现在已经不是普通 RAG，而是：

```text
用户问题
→ EvidencePlan
→ SearchAction
→ Retrieval
→ EvidencePool
→ ContextBuilder
→ CoverageChecker
→ 必要时第二轮搜索
→ EvidencePackage
```

所以如果还只看 `Recall@5`，实际上已经测不到产品真正运行的东西了。文档现在用 **L1 + Regression + L1.5** 三层把这个问题拆开测，这是整份设计的核心。

---

# 一、先建立最重要的整体认识：L1 和 L1.5 根本不是竞争关系

可以把它们想象成 Java 后端测试里的：

```text
L1
≈ Repository / Search Engine 单元测试

L1.5
≈ Retrieval Service 集成测试

L2
≈ 最终业务行为 / 用户体验测试
```

所以不是：

```text
有了 L1.5
→ L1 没用了
```

而是：

```text
L1：
底层搜索能力有没有退化？

L1.5：
这些搜索能力被 Agent 编排起来以后，
到底能不能把证据完整找回来？

L2：
证据找回来以后，
最后能不能解释清楚？
```

这三个问题完全不同。

---

# 二、为什么旧的 L1 仍然必须保留

L1 的输入是：

```text
固定原始 Query
```

然后分别跑：

```text
keyword
vector
hybrid
旧 routed
```

最后看：

```text
Top3
Top5
Top10
Top20
```

有没有人工标注的目标证据。

它的价值在于**变量非常少**。

假设你某天改了：

```text
Embedding 模型
RRF 权重
SQL 查询
Chunk 方式
关键词检索
vector 参数
```

然后发现：

```text
Recall@5
66% → 51%
```

你基本可以判断：

> 底层 Retriever 出问题了。

但如果直接跑完整 Agent：

```text
EvidencePlanner
↓
SearchActionPlanner
↓
Retriever
↓
CoverageChecker
```

最终效果变差，你完全不知道到底是哪一层的问题。

所以 L1 是一个非常重要的：

> **隔离底层检索变量的稳定回归测试。**

---

# 三、Full-case Success 为什么比 Recall 更接近真实问题

这是这一版评测中非常重要的改进。

假设某个问题需要 4 组证据：

```text
E1 ✅
E2 ✅
E3 ✅
E4 ❌
```

普通 Recall：

```text
3 / 4 = 75%
```

看起来挺好。

但用户如果问：

> “完整解释占座的一致性保证。”

而 E4 恰好是：

```text
失败后的补偿机制
```

那这个答案其实是不完整的。

所以新增：

```text
Full-case Success
```

它要求：

```text
E1 ✅
E2 ✅
E3 ✅
E4 ✅
```

才能记：

```text
Success = 1
```

只要缺一组：

```text
Success = 0
```

文档明确把它定义成：

> 一个案例中所有逻辑证据组全部命中，才算成功。

这就是为什么：

```text
routed Recall@5 = 66.67%
```

但：

```text
Full-case@5 = 58.33%
```

前者表示：

> 平均找到了约三分之二的证据。

后者才表示：

> 真正证据全部找齐的问题只有约 58%。

这两个数字不能混。

---

# 四、为什么 L1 已经不能代表当前产品

这是理解 L1.5 的关键。

L1 仍然是：

```text
原问题
↓
一次 Query
↓
TopK
```

但你的产品现在已经是：

```text
原问题
↓
EvidencePlanner
↓
ER1 ER2 ER3...
↓
每个 ER 生成自己的 SearchAction
↓
第一轮检索
↓
Coverage
↓
发现缺口
↓
第二轮 SearchAction
↓
EvidencePackage
```

所以 L1 看不到：

```text
Planner 有没有漏证据需求
Query 有没有生成偏
第二轮有没有利用真实 Symbol
EvidencePool 有没有公平保留各 ER
Context 有没有裁掉关键证据
Coverage 有没有误判
Package 有没有错误 READY
```

这些恰恰已经是现在系统最重要的逻辑。

因此 L1.5 出现不是“多一个指标”，而是：

> **测试对象变成当前真实生产 RetrievalController。**

---

# 五、L1.5 的设计其实非常漂亮：frozen 和 live 分开

这里是文档里我认为最值得保留的设计之一。

## frozen 模式

它把：

```text
EvidenceRequirement
Search Query
Coverage 判断
```

都人工冻结。

使用：

```text
FrozenEvidencePlanner
FrozenSearchActionPlanner
OracleCoverageChecker
```

但真正的：

```text
RetrievalPolicy
数据库
EvidencePool
ContextBuilder
```

仍然真实执行。

这意味着它主要测：

> 在“计划是正确的”前提下，检索链本身是否可靠？

如果 frozen 都失败了：

```text
就别怪 Planner。
```

问题一定更靠下游：

```text
召回
排序
组合
Context
```

---

## live 模式

live 才真正让：

```text
EvidencePlanner
SearchActionPlanner
CoverageChecker
```

全部用真实 LLM。

因此它测试：

> 整个真实产品工作流是否稳定。

但非常重要的一点是：

> **最终分数仍然用人工 Gold 判断，而不能相信模型自己的 SATISFIED。**

因为如果模型漏掉一个 Requirement：

```text
系统内部：
“所有我生成的 ER 都完成了！”
```

不能因此得：

```text
100 分
```

外部 Gold 仍然会说：

```text
你漏了一个 CORE。
```

这避免了最危险的：

> 考生自己出题、自己答题、自己判卷。



---

# 六、为什么需要 RetrievalObserver

这也是一个非常工程化的设计。

最终 `EvidencePackage` 只告诉你：

```text
最后有什么证据
```

但如果缺证据，你无法知道：

```text
到底从来没搜到？
```

还是：

```text
搜到了
但 EvidencePool 丢了？
```

还是：

```text
进入 Context 时被裁掉？
```

所以 Observer 会记录：

```text
每次 SearchAction 的完整候选
第一轮 Context
第二轮 Context
最终 Context
截断项
异常
```

而且 Observer 只能看，不能改 Query、候选或 Coverage。

这使评测第一次能回答：

> **证据到底丢在哪一步？**

这比一个孤零零的 Recall@5 强太多了。

---

# 七、六个关键指标要怎么理解

## 1. Full-case Success

问：

> 一个问题，所有应该找到的证据是不是全部找齐了？

它是“案例级”的。

例如：

```text
ER1 ✅
ER2 ✅
ER3 ❌
```

即使 Coverage 平均很高：

```text
Full-case = 0
```

因为对用户来说：

> 这个问题仍然缺一块。

---

## 2. CORE Requirement Coverage

问：

> 所有必须找到的核心证据中，找回来了多少？

公式：

```text
已完全满足的可满足 Gold CORE
/
所有可满足 Gold CORE
```

而且这里的分母是：

```text
人工 Gold CORE
```

不是模型生成多少就算多少。

这非常重要。

否则模型少生成几个难 Requirement：

```text
分母反而变小
得分反而更高
```

就会奖励坏 Planner。

---

## 3. All-core-satisfied Case Rate

它和 CORE Coverage 很像，但粒度不同。

比如两个 Case：

```text
Case A:
3 个 CORE
命中 2

Case B:
3 个 CORE
命中 2
```

整体 CORE Coverage：

```text
4 / 6 = 66.7%
```

但：

```text
真正所有 CORE 全齐的 Case
= 0 / 2
```

所以：

> Requirement Coverage 高，不代表很多问题已经完整可回答。

文档也正是用这个指标解释了：

```text
CORE Coverage = 83.33%
```

但：

```text
所有 CORE 全满足案例 = 77.78%
```



---

# 八、False READY 是整套评测里最重要的“安全指标”

定义：

```text
生产 Package = READY
```

但人工 Gold 表明：

```text
还有 CORE 没满足
```

就是：

```text
False READY
```



这比普通 Recall 低危险得多。

因为：

```text
证据不足
→ PARTIAL
```

最多让模型保守：

> “当前无法确认。”

但：

```text
证据不足
→ READY
```

会告诉 AnswerPlanner：

> “证据齐了，可以完整下结论。”

然后模型就更容易非常自信地讲错。

当前：

```text
false_ready_count = 0
```

说明你的系统目前最大的风险不是“乱自信”，而是“过于保守”。

---

# 九、为什么 False READY=0 还不能说系统很好

因为还有另一个指标：

```text
READY recall = 83.33%
```

也就是说：

很多人工判断已经足够 READY 的问题：

```text
系统仍然给 PARTIAL
```

这就像一个二分类器：

```text
Precision 很高
Recall 不够
```

当前系统性格是：

> **宁可少放行，也不要错放行。**

对于你这种 Grounded Project Understanding Agent，这是一个不错的初始偏好。

但长期还是要优化。

否则：

```text
用户明明问了一个完全能回答的问题
```

系统老说：

```text
“证据不足，无法确认。”
```

体验也会下降。

# 十、REG-002 特别重要，因为它暴露的是 Coverage 问题，不是 Retrieval 问题

文档说：

```text
REG-002 用户注册流程
```

结果是：

```text
Gold 证据已经完整进入 Context
Full-case 成功
CORE Coverage 成功

但是：
Package = PARTIAL
```



这个案例非常有诊断价值。

它说明：

```text
证据已经搜到了
↓
证据也没有被 Context 丢掉
↓
但系统仍然认为不足
```

所以不要去调：

```text
Embedding
TopK
RRF
```

应该查：

```text
Chunk → Requirement 归属
CoverageChecker 输入范围
success_criteria
Coverage 语义判断
最终 Package 状态计算
```

这就是新评测最大的价值：

> 能阻止你“修错地方”。

# 十一、Context Survival 92.31% 说明了什么

公式：

```text
最终完整进入 Context 的 Gold 证据
/
任意 SearchAction 曾找到的 Gold 证据
```

当前：

```text
36 / 39
= 92.31%
```



这个结果很重要。

因为之前你怀疑：

```text
是不是 Context 太小？
是不是 16000/28000 不够？
是不是 EvidencePool 组合有严重问题？
```

现在数据告诉你：

> **至少在当前 benchmark 上，它不是普遍性的首要问题，但已存在需要单独处理的失败案例。**

39 个已经搜到的 Gold 证据：

```text
丢了 3 个，其中 edge-01 的二轮目标已经进入候选，却没有完整进入最终 Context
```

所以目前：

```text
扩大 Context
```

不是第一优先级。

因为：

```text
Context Survival 总体达到 92.31%
```

继续把：

```text
28000 → 50000
```

很可能只是：

```text
模型输入更贵
```

却解决不了：

```text
Query 没搜到
Coverage 判错
```

文档因此明确说，下一步不应该盲目扩大 Context。

# 十二、修正后的 Second-round Rescue：75%，而不是 40%

这一项我认为就是你**下一阶段最应该盯的指标**。

旧报告把不可满足需求和仅仅来源相同、但属于其他 Requirement 的二轮动作也计入分母，得到：

```text
6 / 15 = 40%
```



修正口径后，只统计 `expected_satisfied=true`、第一轮未满足、且确实为同一 Requirement 执行了二轮搜索的 CORE：

```text
8 条真正 eligible
6 条成功补齐
2 条 no-gain
Rescue = 75%

另有 5 次不可满足需求的二轮搜索，
由 unanswerable_second_round_attempt_count 单独统计
```

这证明第二轮确实救回来 6 条，而且在真正有机会补齐的需求上多数有效。

因此不能再根据旧的 40% 得出“Query 改写普遍无效”的结论。现在应分别处理：

```text
flow-02：目标落在候选排名边界之外
edge-01：二轮已经找齐目标，但最终 Context 没有保留
5 次不可满足需求的无效二轮动作
```

这就告诉你：

> 动态查询机制值得保留；剩余问题同时涉及排名、Context Survival 和停止条件，不能统一归因于 Query。

# 十三、为什么第二轮可能 no-gain

文档给的原因很合理。

第一种：

```text
第一轮：
“购票占座 事务”

第二轮：
“当前购票占座中的事务实现”
```

虽然字变了：

```text
语义没真正变化
```

于是搜索回来还是同一批 Chunk。

---

第二种：

已经发现：

```text
PurchaseTicketTxService
doPurchaseInTransaction
```

但第二轮没有充分利用这些真实 Symbol。

本来应该：

```text
doPurchaseInTransaction Transactional rollback
```

却仍然问：

```text
购票占座事务如何保证一致性
```

太宽。

---

第三种：

`missing_criteria` 很适合判断：

```text
缺少什么
```

但未必是好 Search Query。

例如：

```text
missing_criteria:
缺少数据库层最终阻止重复状态更新的条件证据
```

这是非常好的 Coverage 描述。

但直接拿去做 embedding：

```text
未必是最佳检索表达
```

---

# 十四、这就是为什么你之前讨论的 Semantic-to-Symbol 会越来越重要

这份评测其实进一步支持了我们之前的判断。

现在系统已经能够：

```text
第一轮语义搜索
↓
发现真实类名 / 方法名
```

那么第二轮最有价值的升级不应该只是：

```text
LLM 再改写一个自然语言 Query
```

而应该逐渐变成：

```text
发现 Symbol
↓
围绕 Symbol 精确搜索
```

例如：

```text
第一轮发现：
PurchaseTicketTxService
doPurchaseInTransaction
```

第二轮：

```text
keyword / symbol-like exact search:
doPurchaseInTransaction
```

而不是继续做宽泛向量搜索。

文档当前还没有真正的 `symbol_search`。修正后的 75% Rescue 说明，精确复用真实 Symbol 仍值得研究，但不能仅凭 Rescue 指标断言必须新增 Symbol Search：

> **“根据第一轮发现的信息改变搜索方式”会比单纯改写句子更值得研究。**

这是基于文档数据进一步得到的工程推论。

# 十五、edge 为什么仍只有 50%，特别值得关注

当前切片：

| 类型 | Full-case |
|---|---:|
| locate | 100% |
| negative | 75% |
| flow | 85.71% |
| why | 71.43% |
| edge | 50% |



这个结果非常符合当前 Retriever 的能力结构。

定位题：

```text
“这个类在哪里？”
“这个方法做什么？”
```

通常只要：

```text
一个明确 Symbol / Chunk
```

所以容易。

但 edge：

```text
失败后怎么办？
超时怎么恢复？
Redis 掉了怎么办？
事务在哪些情况下回滚？
部分成功怎么办？
```

往往需要：

```text
正常路径
+
异常分支
+
状态变化
+
补偿
+
事务边界
```

一个 Case 可能需要 3～5 组彼此分散的证据。

因此只要漏一个：

```text
Full-case 就失败
```

这正是 Project Understanding Agent 真正困难的部分。

所以 edge 25% 是当前一个很重要的产品短板，而不是简单 benchmark 噪声。

# 十六、MIXED 为什么仍然重要

L1 的：

```text
MIXED Full-case@5 = 41.67%
```

而失败中：

```text
COMPOSITION_MISS = 7
```

是最多的。

这说明传统单 Query 检索中经常发生：

```text
代码找到了
文档没进去
```

或者：

```text
文档找到了
代码被挤掉
```

你现在的生产链已经专门针对这个问题做了：

```text
BOTH
↓
代码、文档分开搜
↓
交错合并
↓
EvidencePool 保留两个来源
```



所以未来不要只盯：

```text
旧 routed MIXED@5
```

更应该看：

```text
L1.5 BOTH Requirement satisfaction
```

因为那才是现在真实产品路径。

# 十七、EMPTY 有一个语义问题，后续最好修

这个地方文档指出得很好。

人工标注：

```text
EMPTY
```

可能表达：

> 没有能够直接回答用户问题的证据。

但生产系统的 `EMPTY` 当前定义是：

> 最终 Context 一条都没有。



于是可能出现：

```text
系统找到一些“相关但没用”的 Chunk
```

那么生产状态：

```text
PARTIAL
```

但人工认为：

```text
EMPTY
```

这其实是两个不同概念。

我建议未来最好拆成：

```text
NO_CONTEXT
```

与：

```text
NO_ANSWERABLE_EVIDENCE
```

或者至少重新定义 EMPTY。

否则以后看状态准确率时会一直混。

这是我基于文档这一现象给出的设计建议。

# 十八、现在系统最值得优化的已经非常明确

根据整份报告，优先级不是猜的，而是由指标直接推出来的。

### 第一优先：处理两个已经定位的 second-round no-gain

因为：

```text
Context Survival = 92.31%
```

说明总体存活率较高，但不能据此忽略具体裁剪失败。

同时：

```text
第二轮在 eligible CORE 中救回 75%
```

说明：

> 第二轮本身多数有效，剩余问题需要逐条归因。

逐条检查后已经确认：

```text
flow-02：候选排名边界
edge-01：Context Survival
```

诊断时仍然应该查看：

```text
第一轮 Query
第一轮候选
missing_criteria
发现的真实 Symbol
第二轮 Query
第二轮候选
Gold evidence
```

判断失败到底属于：

```text
Query 没变化
```

还是：

```text
Query 很好
但底层 Retriever 排不上来
```

这两种解决方案完全不同。

# 十九、第二优先：Gold 已经在 Context，但 Package 仍 PARTIAL

最典型：

```text
REG-002
```

这个要查 Coverage。

因为：

```text
Retrieval 成功
Context 成功
```

再继续优化 Search 是浪费时间。

重点检查：

```text
Requirement → Chunk 归属
Coverage 输入
success_criteria 是否过严
语义 Checker 是否保守
state 汇总逻辑
```

# 二十、第三优先：edge 类问题

不是简单“多加几个 Query”。

而是先分析：

> Requirement 本身是否过宽。

例如：

```text
ER：
确认异常情况下的数据一致性恢复机制
```

可能实际上同时要求：

```text
建单失败
支付失败
主动取消
超时关闭
补偿
```

一个 Requirement 太宽，导致：

```text
一个 Query 很难找齐

异常

```

机械目录。
