# 一、先说结论：这一阶段到底完成了什么

这一阶段完成的核心工作，不是“把检索分数调高”，而是建立了一套更可信、更严格、能够指导下一阶段优化的评测基础设施。

可以用一句话概括：

> 以前的评测主要回答“返回结果里有没有同名符号或目标文件”；现在的评测开始回答“返回的是不是指定文件、指定类、指定方法、指定签名、指定行号，或者指定 Markdown 标题层级下的那个 Chunk”。

当前已经形成下面这条完整链路：

```text
36 条分层 Benchmark
        │
        ├── CODE 12 条
        ├── DOC 12 条
        └── MIXED 12 条
        │
        ▼
加载前结构校验
        │
        ├── ID 是否重复
        ├── 类型与来源是否一致
        ├── CODE 定位字段是否齐全
        ├── DOCUMENT 标题路径是否齐全
        └── MIXED 是否同时具有 CODE 与 DOCUMENT 目标
        │
        ▼
Keyword / Vector / Hybrid 各运行 36 次
        │
        ▼
每次保留 Top 10、五段耗时和结构化失败原因
        │
        ▼
计算全局、分类、来源命中、排名、重复率和延迟指标
        │
        ▼
使用 Benchmark SHA-256 与已提交基线比较
        │
        ▼
输出 schema v2 JSON 报告和验收门槛结果
```

这次实现刻意没有修改：

- Keyword SQL 的查询条件和权重；
- Vector 查询方式；
- Hybrid 候选池大小；
- RRF 的 `k=60`；
- Keyword、Vector 的执行顺序；
- Embedding 查询缓存；
- 任何排序或重排算法。

因此，这次提交的价值是建立“测量仪器”和“当前基线”，而不是优化被测对象。

这也是为什么出现了一个表面上反直觉、实际上很健康的结果：

```text
旧版 legacy Hybrid Recall@5：1.0000
v2   legacy Hybrid Recall@5：0.5833
```

这并不表示检索算法突然退化，因为检索参数没有变化；主要变化是“什么才算命中”的标准变严格了。以前只要命中同名方法或同一个文档文件就可能得分，现在必须命中更精确的代码位置或文档标题层级。

# 三、36 条分层评测集是怎样设计的

## 1. 分布

当前数据集固定为：

| 类型 | 数量 | 主要验证目标 |
|---|---:|---|
| CODE | 12 | 能否定位指定 Java 类、方法或接口 |
| DOC | 12 | 能否定位指定 Markdown 章节 |
| MIXED | 12 | 同一个问题中能否同时定位代码与文档 |
| 合计 | 36 | 形成平衡的小型离线检索基准 |

其中 12 条带有：

```json
"legacy": true
```

这些是旧版 12 条问题经过 v2 精确标注后的兼容子集，用于观察老问题在严格判定下的表现。

这里的“legacy”不是继续沿用旧判定规则。它只是说明问题来自旧评测集；命中标准已经升级到 v2。

## 2. 为什么要保持 CODE、DOC、MIXED 各 12 条

如果 36 条中有 30 条都是精确方法名查询，Keyword 会天然占优势；如果大部分都是抽象设计问题，Vector 会天然占优势。

平衡分层至少能避免总指标被某一种问题类型完全支配，并且能够分别看出：

```text
代码定位能力
文档章节定位能力
代码与文档联合覆盖能力
```

## 3. `tags` 的作用

每个用例都必须有非空 `tags`，例如：

```json
"tags": ["purchase", "token-bucket", "same-name-method"]
```

目前 tags 主要承担两种作用：

1. 为以后按主题分析和筛选问题留下结构化维度；
2. 触发少量额外校验规则。

例如带有：

```text
same-name-method
```

的 CODE 目标必须提供 `signature`。原因是项目中可能同时存在接口、实现类、Controller 或多个重载的同名方法，仅凭 `symbol=login` 不能判断命中的是不是目标方法。

当前标签覆盖了：

- method、class、annotation；
- transaction、configuration；
- purchase、payment、order、timeout；
- token-bucket、bloom-filter；
- idempotency、compensation；
- same-name-method 等。

# 四、Ground truth v2：什么才算真正命中

Ground truth 可以理解为评测的“标准答案定位器”。

v2 的关键变化是：标准答案不再只是一个模糊名字，而是一组可以定位到具体 Chunk 的约束。

## 1. CODE 目标

一个 CODE 目标至少必须包含：

```text
source_type
path_contains
class_name
symbol
start_line
```

例如 `CODE-001` 的核心标注是：

```json
{
  "source_type": "CODE",
  "path_contains": "PurchaseTicketTxService.java",
  "class_name": "PurchaseTicketTxService",
  "symbol": "doPurchaseInTransaction",
  "signature": "public PurchaseReservationResult doPurchaseInTransaction(...)" ,
  "start_line": 69,
  "annotation_contains": "Transactional"
}
```

它表达的是：

```text
必须是 CODE
并且文件是 PurchaseTicketTxService.java
并且所属类是 PurchaseTicketTxService
并且符号是 doPurchaseInTransaction
并且完整签名一致
并且起始行为 69
并且注解中包含 Transactional
```

同一目标对象内部是 AND 关系。只要有一个条件不满足，这个 SearchResult 就不算命中。

这解决了旧版的典型问题：

```text
问题要求 UserLoginServiceImpl.login
旧版只检查 symbol=login
结果却可能命中接口 login 或 Controller.login
```

## 2. DOCUMENT 目标

一个 DOCUMENT 目标至少必须包含：

```text
source_type
path_contains
heading_path
```

例如：

```json
{
  "source_type": "DOCUMENT",
  "path_contains": "订单与支付模块.md",
  "heading_path": [
    "my12306 · 订单模块与支付模块 · 设计文档（自足版）",
    "四、订单模块：设计与实现",
    "4.4 超时关单双通道（详细）"
  ]
}
```

它要求命中的不是“这份 Markdown 文件中的任意一段”，而是：

```text
指定文件
+
指定完整标题层级
```

旧版只按文件路径判断时，同一文档中的“前言”“测试方法”“未来计划”等章节也可能被算作命中；v2 会把这些语义相近但定位不正确的章节区分开。

## 3. `any_of`：多个等价答案只算一个要求

有些问题确实存在多个等价答案。例如 `DOC-009`：

```text
Ticket 为什么预生成 orderSn，Order 又为什么仍需要唯一索引？
```

它接受两个章节中的任意一个：

```json
{
  "any_of": [
    {
      "path_contains": "2-订单支付-订单.md",
      "heading_path": ["五、订单创建里最重要的设计：`orderSn` 为什么由 Ticket 生成"]
    },
    {
      "path_contains": "2-订单支付-订单.md",
      "heading_path": ["九、那为什么还需要数据库唯一索引？"]
    }
  ]
}
```

这里要区分两个概念：

```text
组与组之间：是多个需要覆盖的要求
any_of 组内部：是同一个要求的多个替代答案
```

`any_of` 中命中任意一个目标，这一组就算完成，而且只计 1 分，不会因为两个替代答案都命中而重复得分。

同一个 `any_of` 中的所有替代项必须具有相同 `source_type`，不能把 CODE 和 DOCUMENT 混在一个替代组里。

## 4. MIXED 目标

MIXED 用例必须同时存在：

```text
至少一个 CODE 目标组
至少一个 DOCUMENT 目标组
```

例如 `MIXED-001`：

```text
问题：purchaseTickets 为什么先经过校验和令牌桶，相关代码与设计说明在哪里？
```

它有两个要求：

```text
要求 A：命中 PurchaseTicketServiceImpl.purchaseTickets
要求 B：命中责任链或令牌桶的指定设计章节之一
```

因此它的 Recall@5 只能是：

```text
0.0：代码和文档都没有命中
0.5：只命中其中一种来源
1.0：代码与文档都命中
```

这比旧版“只要代码或文档中有一个看起来相关就算成功”严格得多。

# 五、匹配时如何处理文本差异

v2 使用 `_normalize()` 统一处理大部分字符串：

```python
" ".join(value.split()).casefold()
```

它做了两件事：

1. 把连续空白压缩成一个空格；
2. 使用 `casefold()` 做不区分大小写比较。

例如：

```text
"public   void run()"
" PUBLIC void RUN() "
```

归一化后可以视为一致。

不同字段的匹配方式如下：

| 字段 | 匹配方式 |
|---|---|
| `source_type` | 归一化后完全相等 |
| `path_contains` | 归一化后进行路径子串匹配 |
| `class_name` | 完全相等 |
| `symbol` | 完全相等 |
| `signature` | 压缩空白后完全相等 |
| `start_line` | 整数完全相等 |
| `annotation_contains` | 在所有注解拼接文本中做子串匹配 |
| `title_contains` | 在当前标题中做子串匹配 |
| `heading_path` | 标题层级数组逐项完全相等 |

这里最严格的是：

```text
start_line
heading_path
signature
```

它们能显著减少误判，但也意味着源码插入几行、方法签名调整、Markdown 标题改名后，Benchmark 必须同步维护。

这不是实现错误，而是精确定位型 ground truth 的维护成本。

# 六、为什么要在调用百炼 API 之前校验 Benchmark

`load_cases()` 读取 JSONL 后立即调用 `validate_cases()`。

它会检查：

- Benchmark 不是空列表；
- 每条记录是对象；
- ID 非空且不重复；
- `type` 只能是 CODE、DOC、MIXED；
- question 非空；
- `legacy` 必须是布尔值；
- tags 必须是非空字符串列表；
- relevant 必须是非空列表；
- target 不允许出现未知字段；
- CODE 必需定位字段齐全；
- DOCUMENT 必需路径和标题层级；
- `start_line` 是正整数；
- `heading_path` 是非空字符串数组；
- `any_of` 不能与普通字段混写；
- `any_of` 替代项来源相同；
- 用例类型和相关目标来源一致；
- same-name-method 必须带 signature。

如果 JSONL 本身在某一行不是合法 JSON，还会报告具体行号，例如：

```text
Invalid benchmark JSON at line 17
```

执行顺序是：

```text
读取并校验 Benchmark
  ↓
计算 Benchmark hash
  ↓
创建 RetrievalService
  ↓
开始真实检索
```

所以错误数据会在昂贵的 Embedding 网络调用之前失败，避免：

- 浪费 API 请求；
- 跑了几十个查询后才发现第 30 条标注结构错误；
- 生成一份部分有效、部分无效的报告。

这叫 Fail Fast，即尽早失败。

# 七、`search_with_trace()` 是怎样做到兼容和计时的

## 1. 新旧接口关系

现在旧接口内部直接复用新接口：

```python
def search(...):
    return self.search_with_trace(...).results
```

因此只有一份真正的检索流程，避免出现：

```text
search() 用一套逻辑
search_with_trace() 又复制一套逻辑
两套代码以后行为不一致
```

## 2. 五段耗时

`SearchTimings` 包含：

```text
query_embedding_ms
keyword_sql_ms
vector_sql_ms
fusion_ms
total_ms
```

### `query_embedding_ms`

从创建百炼 Embedding 客户端到获得查询向量的耗时。

它包含客户端构造、HTTP 请求、网络等待和响应解析，不只是模型内部推理时间。

### `keyword_sql_ms`

执行 `keyword_search()` 的耗时，包括数据库连接、SQL 执行和结果读取。

### `vector_sql_ms`

执行 `vector_search()` 的耗时，包括数据库连接、pgvector 距离计算和结果读取。

### `fusion_ms`

对 Keyword 和 Vector 候选执行 RRF 融合的耗时。

### `total_ms`

从进入 `search_with_trace()` 到返回 SearchExecution 的总时间。

通常：

```text
total_ms >= 各阶段耗时之和
```

因为总时间还包含参数校验、对象创建、函数调用和阶段切换等少量开销。

## 3. 三种策略的阶段差异

### Keyword

```text
query_embedding_ms = 0
keyword_sql_ms      > 0
vector_sql_ms       = 0
fusion_ms           = 0
```

### Vector

```text
query_embedding_ms > 0
keyword_sql_ms     = 0
vector_sql_ms      > 0
fusion_ms          = 0
```

### Hybrid

```text
query_embedding_ms > 0
keyword_sql_ms     > 0
vector_sql_ms      > 0
fusion_ms          > 0
```

## 4. Hybrid 行为没有变化

流程仍然是：

```text
查询向量化
  ↓
Keyword SQL
  ↓
Vector SQL
  ↓
RRF
```

Keyword 和 Vector 仍然串行执行。

候选池仍然是：

```python
pool_size = max(20, top_k)
```

评测请求 `top_k=10`，所以两路各取 20 条候选，再使用：

```python
reciprocal_rank_fusion(..., k=60, top_k=10)
```

这保证本次新增计时不会改变被测检索结果。

# 八、单条用例如何生成诊断结果

评测器对每个策略、每个问题调用一次：

```python
service.search_with_trace(strategy, question, top_k=10)
```

36 条问题乘以 3 种策略：

```text
36 × 3 = 108 条策略/用例明细
```

每条明细保存：

- 用例 ID、类型、tags、legacy；
- 原始问题；
- Recall@3、Recall@5、RR；
- CODE/DOCUMENT 在 Top 3、Top 5 是否命中；
- MIXED 是否双来源命中；
- 首个相关 CODE/DOCUMENT 排名；
- 是否无结果；
- Top 5 逻辑重复率；
- 五段耗时；
- Top 5 未命中的目标；
- 结构化失败原因；
- 完整 Top 10 SearchResult。

旧版报告只保存 Top 5，正确答案在第 6～10 名时很难排查；v2 保存 Top 10 后，可以区分：

```text
答案只是排得不够靠前
还是候选池前 10 中完全没有答案
```

# 九、v2 指标应该怎样理解

## 1. Recall@3 / Recall@5

当前 Recall 计算的是“目标组覆盖率”：

```text
Recall@K = Top K 命中的 relevant 目标组数量 / relevant 目标组总数
```

CODE 和 DOC 通常只有一个目标组，因此单条用例的 Recall 是：

```text
0 或 1
```

MIXED 通常有两个目标组，因此单条用例的 Recall 是：

```text
0、0.5 或 1
```

这里不是在穷举“知识库中所有相关 Chunk”，所以它更接近需求覆盖率，而不是传统搜索引擎中的全量文档召回率。

## 2. MRR

MRR 是 Mean Reciprocal Rank，平均倒数排名。

单题 RR：

```text
第一个相关结果在第 1 名：1/1 = 1
第一个相关结果在第 2 名：1/2 = 0.5
第一个相关结果在第 5 名：1/5 = 0.2
Top 10 没有相关结果：0
```

评测只检索 Top 10，所以报告字段叫 `mrr`，严格来说更接近 `MRR@10`。

对 MIXED 要特别小心：只要代码或文档中的任意一个首先命中，RR 就会停止计算。它不能证明两种来源都找到，所以必须结合 `both_sources_hit@K`。

## 3. 分类指标 `by_type`

v2 会分别汇总：

```text
CODE
DOC
MIXED
```

每一类各有：

```text
case_count
recall_at_3
recall_at_5
mrr
```

这解决了旧版只有一个总分、无法看出问题来自代码还是文档的缺陷。

## 4. `code_hit@K`

它的分母不是 36 条，而是所有需要 CODE 的用例：

```text
12 条 CODE + 12 条 MIXED = 24 条
```

例如 Hybrid `code_hit@5 = 0.5417`，实际是：

```text
13 / 24 = 0.5417
```

其中包括：

- 8 条纯 CODE 用例在 Top 5 命中；
- 5 条 MIXED 用例的 CODE 目标在 Top 5 命中。

## 5. `doc_hit@K`

分母同样不是 36，而是：

```text
12 条 DOC + 12 条 MIXED = 24 条
```

Hybrid `doc_hit@5 = 0.3333`：

```text
8 / 24 = 0.3333
```

其中包括：

- 5 条纯 DOC 用例命中；
- 3 条 MIXED 用例的 DOCUMENT 目标命中。

## 6. `both_sources_hit@K`

这个指标只对 12 条 MIXED 用例计算：

```text
Top K 中 CODE 目标命中
并且
Top K 中 DOCUMENT 目标命中
```

当前 Hybrid `both_sources_hit@5 = 0.0`，意思不是 Hybrid 没有返回混合来源，而是：

> 12 条 MIXED 中，没有一条同时精确命中 v2 标注的 CODE 目标和 DOCUMENT 目标。

Top 5 里可能同时出现代码和文档，但如果其中一个不是 ground truth 指定的精确 Chunk，仍然不算双来源成功。

## 7. 首个相关结果平均排名

当前指标：

```text
mean_first_relevant_code_rank_at_5
mean_first_relevant_doc_rank_at_5
```

只会把“Top 5 已经命中的用例”加入平均值。

因此 Hybrid：

```text
首个相关 CODE 平均排名 = 1.6923
首个相关 DOC  平均排名 = 3.6250
```

应该解释为：

```text
在已经成功进入 Top 5 的 CODE 目标中，平均约排第 1.69；
在已经成功进入 Top 5 的 DOC 目标中，平均约排第 3.63。
```

它不包含完全没命中的用例，因此不能单独说明整体检索很好。这是一种条件平均值，存在“只看成功者”的偏差。

如果没有任何命中，当前实现返回 `0.0`，这不代表平均排第 0 名，而是表示没有可用于计算的排名数据。

## 8. 无结果率

```text
no_results_rate = 没有返回任何 SearchResult 的用例数 / 全部用例数
```

第二轮中：

- Keyword 为 `0.0556`，即 2/36 无结果；
- Vector 为 `0`；
- Hybrid 为 `0`。

Vector 在数据库有向量时通常总能返回“最相似”的结果，即使相关度不高，所以“有结果”不等于“结果正确”。

## 9. Top 5 重复结果率

公式：

```text
(Top 5 数量 - Top 5 逻辑唯一结果数量) / Top 5 数量
```

DOCUMENT 的逻辑唯一键是：

```text
source_type + file_path + heading_path + title
```

CODE 的逻辑唯一键是：

```text
source_type + file_path + chunk_type + class_name
+ signature 或 symbol + start_line
```

当前 Hybrid 重复率为 0，只说明没有出现完全相同逻辑定位的重复 Chunk。

它不代表没有语义冗余。例如下面这些结果在逻辑键上都不同：

```text
接口 purchaseTickets
实现类 purchaseTickets
Controller purchaseTickets
PurchaseTicketService 类 Chunk
PurchaseTicketServiceImpl 类 Chunk
```

但对最终上下文来说，它们仍可能高度重复。

# 十、五种结构化失败原因

## 1. `empty_results`

检索没有返回任何结果。

它只描述结果列表为空，不判断原因。可能是 Keyword SQL 没有任何候选，也可能是数据库或过滤条件导致。

## 2. `missing_code_source`

需要 CODE 目标，但 Top 5 没有命中精确 CODE ground truth。

需要注意，这个名称不等于“Top 5 完全没有代码”。Top 5 可以有很多 CODE Chunk，只要都不是目标代码，仍然会报告 `missing_code_source`。

## 3. `missing_document_source`

需要 DOCUMENT 目标，但 Top 5 没有命中精确 DOCUMENT ground truth。

同样，它不等于“Top 5 没有文档”。可能已经返回多个语义相关文档，但没有命中指定路径和完整标题层级。

## 4. `relevant_after_k`

某个 Top 5 未命中的目标，在第 6～10 名出现了。

它表示：

```text
候选召回到了答案
但排序不够靠前
```

这种问题通常更适合从排序、融合或来源配额角度处理，而不是先扩大候选池。

## 5. `target_not_in_top_10`

至少一个 Top 5 未命中的目标，在 Top 10 中也不存在。

它表示：

```text
目标没有进入当前诊断窗口
```

可能需要检查：

- Query 与目标 Chunk 的文本表达是否差异过大；
- embedding_text 是否缺少标题层级或代码身份；
- Keyword SQL 是否难以处理自然语言；
- 目标是否进入两路各 20 条 Hybrid 候选池；
- ground truth 是否过时或写错。

## 6. `duplicate_crowding`

当用例 Recall@5 不完整，并且 Top 5 存在逻辑重复结果时出现。

它表达的是：

```text
失败时同时观察到重复候选占位
```

这只是诊断线索，不等于已经证明“重复结果就是漏召回的唯一原因”。

## 7. 为什么一个用例可以有多个失败原因

例如 MIXED 用例：

```text
CODE 目标在第 8 名
DOCUMENT 目标 Top 10 完全没有
```

它会同时得到：

```text
missing_code_source
missing_document_source
relevant_after_k
target_not_in_top_10
```

所以失败原因的计数不能直接相加得到失败用例数。

本次 108 条策略/用例明细中共有 76 条 Recall@5 不完整：

| 策略 | Recall@5 不完整的用例数 |
|---|---:|
| Keyword | 30 |
| Vector | 23 |
| Hybrid | 23 |
| 合计 | 76 |

76 条全部保留了 Top 10 和至少一个结构化失败原因，因此当前框架已经做到“低分可追踪”。

# 十一、平均耗时与 P95 如何计算

## 1. 平均值

每个阶段对 36 条用例的耗时求算术平均。

例如：

```text
Hybrid query_embedding_ms 平均值
= 36 次 Hybrid 查询向量化耗时之和 / 36
```

## 2. P95

P95 表示大约 95% 的观测值不超过该数值，用于观察较慢请求，而不是只看平均值。

当前实现使用 nearest-rank 方式：

```python
index = ceil(0.95 * N) - 1
```

当 `N=36`：

```text
ceil(36 × 0.95) = ceil(34.2) = 35
```

也就是排序后第 35 个观测值，接近第二慢的请求。

当前 P95 不是插值百分位，而且每个问题只运行一次，所以它是本次真实运行的基线，不是严格的长期性能统计结论。

# 十二、Baseline 比较机制

## 1. 为什么先比较 Benchmark SHA-256

Benchmark 文件的原始字节会计算 SHA-256：

```text
b4275a82b8e4d4c6f01d32453adcf141e2bd9a53947964b978880b227702a23b
```

如果当前文件 hash 与基线不同，比较状态会变成：

```json
{
  "status": "incompatible",
  "reason": "benchmark_sha256 differs"
}
```

原因很简单：不能用不同的考试题直接比较分数。

如果增加题目、修改 ground truth、甚至只是改变文件字节，hash 都会变化。这样可以防止出现：

```text
旧版考 12 道简单题
新版考 36 道严格题
然后直接说 Recall 从 1.0 下降到 0.47
```

## 2. `comparable` 表示什么

第二轮报告识别为：

```text
status = comparable
```

只表示：

```text
当前评测和基线使用完全相同的 Benchmark 文件
```

然后框架把汇总对象中的数值字段扁平化，逐项计算：

```text
delta = current - baseline
```

本次所有召回、命中率、MRR 和排名指标差值都是 0，说明两轮检索质量结果一致；延迟存在真实运行波动。

## 3. 为什么基线记录的是旧 Git HEAD

基线中的：

```text
git_commit = 3670f79...
```

最终实现提交是：

```text
0b55290
```

原因是基线在提交前运行。当时工作区已经包含 v2 实现，但 `git rev-parse HEAD` 只能返回最近一次已提交的 commit，无法把未提交改动编码进 commit ID。

因此这个字段应该理解为：

```text
测量时仓库 HEAD
```

而不是：

```text
完整表示测量时所有工作区代码
```

Benchmark hash 能证明题目一致；Git HEAD 单独不能证明当时工作区完全干净。最终提交后工作区已验证干净，因此当前实现状态是清晰的，但这次基线的历史字段仍需按上述语义理解。

## 4. 基线比较目前比较什么

当前 `compare_baseline()` 比较汇总数值字段，包括：

- Recall、MRR；
- 分类指标；
- 来源命中率；
- 排名指标；
- 重复率、无结果率；
- 各阶段平均耗时与 P95。

基线虽然保存了逐用例 `case_status`，当前比较器并没有逐用例判断“某题退化、另一题提升后互相抵消”的情况。

所以：

```text
汇总 delta = 0
```

不能严格证明每一条用例都没有变化；本次报告中逐项检查确实一致，但以后若要自动化回归，建议再增加 per-case delta。

# 十三、Acceptance gates 和 `quality_passed`

当前验收门槛包括：

| Gate | 当前值 | 目标 | 状态 |
|---|---:|---:|---|
| 用例总数 | 36 | 36 | 通过 |
| 类型分布 | 12/12/12 | 12/12/12 | 通过 |
| legacy 用例数 | 12 | 12 | 通过 |
| legacy Hybrid Recall@5 | 0.5833 | 1.0000 | 未通过 |
| MIXED Hybrid both_sources_hit@5 | 0.0000 | 0.8000 | 未通过 |
| 全集 Hybrid Recall@5 相对基线 | 0.4722 | 不低于 0.4722 | 通过 |

`quality_passed` 的计算方式是：

```text
所有 passed 不是 null 的 gate 都必须为 true
```

因为两个质量门槛为 false，所以：

```json
"quality_passed": false
```

这并不表示本次开发失败，而是表示：

```text
评测框架建设完成
但被评测的当前检索质量还没有达到目标
```

需要区分两类“通过”：

### 结构建设通过

- 36 条数据存在且平衡；
- legacy 子集正确；
- 108 条明细完整；
- Top 10 与失败原因完整；
- 分阶段计时完整；
- 基线可比较；
- 自动化测试通过。

### 检索质量尚未通过

- legacy 严格 Recall@5 没达到 1.0；
- MIXED 双来源命中没有达到 0.8。

还有一个工程细节：当前 CLI 即使 `quality_passed=false`，只要评测过程没有抛出异常，进程仍返回退出码 0。也就是说它会在 JSON 中报告红灯，但暂时不会自动让 CI Job 失败。如果后续希望把质量门槛变成合并保护，需要显式增加非零退出码选项。

另外，两个质量阈值当前既写在基线 JSON 的 `thresholds` 中，也在 `_acceptance()` 代码中使用固定值。只修改基线 JSON 的阈值不会自动改变 Gate 逻辑；以后可以把阈值读取统一到一处。

# 十五、怎样从这些数字推导真实结论

## 1. Hybrid Recall@5 的 0.4722 是怎样来的

Hybrid 中：

```text
CODE：8 条完整命中，贡献 8 分
DOC：5 条完整命中，贡献 5 分
MIXED：没有完整命中，但 8 条各命中一半，贡献 4 分
```

所以：

```text
(8 + 5 + 4) / 36
= 17 / 36
= 0.4722
```

这说明总 Recall 不是“36 条里有 17 条成功”。实际完整 Recall@5 的用例是：

```text
8 条 CODE + 5 条 DOC + 0 条 MIXED = 13 条
```

另外 8 条 MIXED 只完成了一半目标。

## 2. Vector 和 Hybrid Recall@5 相同，不代表效果完全相同

两者都是：

```text
Recall@5 = 0.4722
```

但分类结构不同：

| 分类 | Vector Recall@5 | Hybrid Recall@5 |
|---|---:|---:|
| CODE | 0.4167 | 0.6667 |
| DOC | 0.5833 | 0.4167 |
| MIXED | 0.4167 | 0.3333 |

Hybrid 明显提升了精确代码目标，但牺牲了部分文档目标在 Top 5 中的位置。

这符合 RRF 的现状：Keyword 对精确代码标识符较强，融合后会把更多代码结果推到前面，也可能把 Vector 已经召回的文档挤到第 6～10 名。

因此下一阶段不能只优化一个总 Recall，需要同时观察分类和来源指标。

## 3. Keyword 的 DOC Recall 为 0 表示什么

它并不表示 Keyword 完全检索不到任何文档。

它表示在严格的：

```text
指定路径 + 完整 heading_path
```

规则下，12 条 DOC 的目标章节都没有进入 Top 5。

Keyword 仍可能返回同一文件中的其他章节或语义相关文档，但 v2 不把它们算作目标 Chunk。

## 4. `both_sources_hit@5 = 0` 是当前最重要的质量信号

Hybrid 的 MIXED 用例中：

- 一些只命中精确代码；
- 一些只命中精确文档；
- 没有一条在 Top 5 同时命中两者。

这说明当前 Hybrid 虽然混合了两路候选，却没有保证“一个需要两种证据的问题”得到完整证据组合。

这正是后续 Context Builder 之前必须解决的问题，否则大模型可能拿到：

```text
只有代码，没有设计依据
```

或者：

```text
只有文档，没有真实实现位置
```

## 5. RRF 几乎不是延迟瓶颈

Hybrid 平均总耗时：

```text
899.14 ms
```

RRF 平均只占：

```text
0.21 ms
```

比例大约是：

```text
0.21 / 899.14 ≈ 0.023%
```

真正耗时主要来自：

```text
查询向量化：382.35 ms
Keyword SQL：436.21 ms
Vector SQL：80.35 ms
```

所以如果下一阶段目标是降低延迟，优先调查 Embedding 网络调用和 Keyword SQL，而不是微优化 RRF 循环。

## 6. Keyword SQL 比 Vector SQL 慢

本次 Hybrid 中：

```text
Keyword SQL 平均 436.21 ms
Vector SQL  平均  80.35 ms
```

在只有 3112 个 Chunk 的规模下，Vector 精确扫描并不是主要瓶颈。相反，包含 `strpos`、`similarity` 和 token 子查询的 Keyword SQL 更值得用：

```sql
EXPLAIN (ANALYZE, BUFFERS)
```

检查执行计划和索引命中情况。

这也说明现阶段没有必要因为看到“向量检索”就立即增加 HNSW。

# 十七、为什么 legacy 从 1.0 变成 0.5833

legacy 12 条在 Hybrid v2 中的分数组成是：

```text
4 条 CODE：全部命中，贡献 4
4 条 DOC：只有 1 条严格命中，贡献 1
4 条 MIXED：每条只命中一半，贡献 4 × 0.5 = 2
```

所以：

```text
(4 + 1 + 2) / 12
= 7 / 12
= 0.5833
```

旧版可能这样判：

```text
同一个方法名 → 命中
同一个 Markdown 文件 → 命中
多个大致相关文档路径之一 → 命中
```

v2 则要求：

```text
指定类中的指定方法和签名
指定文件中的指定完整标题层级
MIXED 同时覆盖两个来源
```

因此正确说法是：

> v2 暴露了旧评测规则掩盖的定位精度问题。

不应说：

> Hybrid 排序从 1.0 退化到了 0.5833。

如果要证明排序真的退化，必须用完全相同的 Benchmark hash 和相同判定规则比较。这正是 baseline hash 机制存在的原因。

# 二十、下一阶段怎样根据数据优化，而不是盲目调参

现在已经可以正式进入检索优化，但应该按失败类型分流。

## 1. 第一类：目标在第 6～10 名

例如：

- DOC-001 的目标文档在第 8；
- MIXED-002 的目标文档在第 8；
- MIXED-003 的目标文档在第 10；
- CODE-011 的目标代码在第 8。

这类问题说明候选已经召回，优先研究：

- RRF 后的来源平衡；
- Keyword 与 Vector 的权重或融合策略；
- 文档标题层级是否进入 embedding_text；
- 是否需要在 MIXED 查询中保留 CODE/DOCUMENT 最小配额；
- 是否存在大量相近结果占据前五。

## 2. 第二类：目标不在 Top 10

例如：

- MIXED-010 的 AuthGlobalFilter.filter；
- MIXED-012 的库存校验 handler；
- CODE-007 等精确业务方法。

这类问题首先要检查：

- 目标是否进入 Keyword 前 20；
- 目标是否进入 Vector 前 20；
- embedding_text 是否充分表达类名、方法名、职责和注解；
- Query 中的自然语言与代码身份是否存在语义鸿沟；
- Keyword 是否只依赖问题中的显式标识符；
- ground truth 的行号和签名是否仍与当前索引一致。

如果两路前 20 都没有目标，只调整 RRF 不会有帮助，因为 RRF 不能融合不存在的候选。

## 3. 第三类：MIXED 只有一种来源命中

这是当前最明确的产品级问题。

可以先做最小、可评测的实验：

```text
识别 MIXED 查询
  ↓
分别保留若干 CODE 和 DOCUMENT 候选
  ↓
再在来源内部或整体做 RRF 排序
```

但任何策略都必须用现有 36 条基线验证：

- `both_sources_hit@5` 是否提高；
- CODE Recall 是否下降；
- DOC Recall 是否下降；
- MRR 是否明显退化；
- 延迟是否超出预算。

## 4. Keyword SQL 性能

平均 436 ms 是当前 Hybrid 最大的本地耗时项。

建议先用执行计划判断：

```sql
EXPLAIN (ANALYZE, BUFFERS)
```

不要直接猜测是 pg_trgm、数据库连接还是表达式导致。特别要检查 `lower`、`strpos`、`similarity` 和 `unnest` 是否使现有索引无法有效使用。

## 5. Embedding 查询延迟

平均 382 ms 来自外部查询向量化。

可以分别评估：

- HTTP 连接复用；
- 客户端生命周期；
- 短期查询向量缓存；
- 超时和重试对 P95 的影响。

但优化缓存时要明确：相同 Benchmark 重复执行会大量命中查询缓存，从而得到与真实首次查询不同的延迟。性能报告应区分 cache hit 和 cache miss。

# 二十一、当前实现还应注意的几个边界

## 1. Benchmark hash 只证明题目一致

它不证明：

- 数据库 Chunk 内容一致；
- Embedding 模型和维度一致；
- 外部源仓库 commit 一致；
- PostgreSQL 数据版本一致。

未来可在报告中增加：

```text
source_repository_commit
chunk_count
chunk_manifest_hash
embedding_model
embedding_dimensions
parser_version
```

这样基线可复现性会更强。

## 2. 精确 `start_line` 会随源码移动

即使方法内容完全没变，只在文件开头增加注释，方法起始行也会改变。

这会让旧 ground truth 失效。因此每次重新索引外部项目后，应有一个轻量校验工具检查标注目标是否仍能在数据库中唯一找到。

## 3. `heading_path` 完全相等会受标题改名影响

它提高了评测精度，但 Markdown 标题改名后需要同步更新 Benchmark。

如果未来需要兼容标题小改动，可以使用 `any_of` 明确记录新旧等价路径，而不建议悄悄改成宽松模糊匹配。

## 4. 重复率为 0 不代表上下文没有冗余

当前只识别相同逻辑定位。语义重复、接口与实现重复、相邻章节重复仍需要新的多样性指标或 Context Builder 去重策略。

## 5. 基线总分不退化不代表逐题不退化

一个问题从 1 变 0，另一个从 0 变 1，总分可以不变。

下一步可以利用基线已有的 `case_status`，生成：

```text
regressed_cases
improved_cases
unchanged_cases
```

## 6. 红灯被保留是正确行为

当前没有通过：

- 删除困难用例；
- 放宽 ground truth；
- 修改题目让它更容易命中；
- 调整算法直到当前数据“看起来全绿”。

这使 0.4722 和 0.0000 成为可信起点。一个诚实的红色基线，比宽松规则下的 1.0 更有工程价值。

# 二十三、最终总结

评测框架 v2 已经完成了从“能算几个总指标”到“可以作为检索优化依据”的升级。

最重要的成果不是某个分数，而是下面这些能力已经具备：

```text
题目分层
精确目标定位
等价答案建模
MIXED 双来源约束
数据加载前校验
分类与来源指标
Top 10 失败诊断
分阶段延迟
数据集 hash
可比较基线
明确的红色质量门槛
```

当前真实状态可以准确表述为：

> 评测基础设施已经完成并通过真实数据验证；现有检索算法在严格 v2 ground truth 下，代码目标优于文档目标，MIXED 问题还不能在 Top 5 同时提供精确代码与精确文档证据。下一阶段已经不需要凭感觉调参，可以根据 `relevant_after_k`、`target_not_in_top_10`、来源命中率和分阶段延迟，分别处理排序、候选召回、来源平衡与性能瓶颈。

这意味着 DevContext 已经跨过一个关键节点：

```text
以前：知道系统能检索
现在：知道系统具体在哪里检索得好、在哪里失败、失败发生在哪个阶段
```

而这正是正式进入检索优化阶段所需要的基础。
