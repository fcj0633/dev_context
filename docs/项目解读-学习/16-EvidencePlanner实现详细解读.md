## 0. 阅读说明：本文的证据规则

沿用本系列既有约定，每一处结论标注证据等级。

| 标记 | 含义 |
|---|---|
| 【实测】 | 从真实运行产物直接读到的事实 |
| 【代码可证】 | 直接从当前源码读出的行为 |
| 【测试可证】 | 由通过的自动化测试锁定的行为 |
| 【文档依据】 | 来自设计文档的意图 |
| 【推断】 | 由前几类证据推导，源码未直接证明 |
| 【无法确认】 | 仓库内没有足够证据，不猜测 |

# 一、这一部分在系统中的位置

## 1. 改动之前的链路

Question Planner V1 之后、Evidence Planner 之前：

```text
用户问题
   ↓
Question Planner                拆成若干子问题
   ↓
对每个子问题：
   QueryRouter.route(子问题)      ← 靠正则信号判断去哪种数据源
   RetrievalPolicy.search()       按判断结果检索
   ↓
证据合并 → Context → 充分性 → 回答
```

## 2. 改动之后的链路

```text
用户问题
   ↓
Question Planner                拆成若干子问题
   ↓
Evidence Planner                每个子问题 → 一条证据需求     ← 本轮新增
   ↓
对每个子问题：
   需求 → to_route_decision()    需求决定检索策略
   （规划失败时回退 QueryRouter）
   ↓
证据合并 → Context → 充分性 → 回答
```

## 3. 一句话概括

> 从"**让分类器猜这条子问题该去哪找**"，变成"**先声明这条子问题需要什么证据，再按需求去找**"。

# 二、为什么要把"证据需求"显式化

## 1. 上一轮留下的"暂时"

Phase 1 的设计文档在描述 `QueryRouter` 时用了"**暂时**由它承担"这个措辞：

> 子问题到证据类型的映射**暂时**由 `QueryRouter` 承担。

这个"暂时"不是客套。`QueryRouter` 的工作方式是**匹配正则信号**：问题里出现"在哪里"就倾向 CODE，出现"为什么"就倾向 DOCUMENT，两者都命中就是 MIXED。

## 2. 反推与声明，差在两处

用正则反推"这条子问题需要什么证据"有两个绕不过去的限制：

**粒度。** 它只能给一个来源标签。但一条子问题可能需要"某类实现 + 某份设计说明"这种组合——正则无法表达"需要 A 和 B 互相印证"。

**可解释性。** 它给出的理由是"命中了 code_locator 信号"。这个理由对排查问题几乎没有帮助——真正想知道的是"这条子问题要找的是什么"。

## 3. 与转型文档的关系

`01-项目开发方向转型.md` 的核心主张是：

> CODE / DOC 应该是**证据类型**，不是**用户问题类型**。

这一步分两阶段完成：Phase 1 把它从"用户问题类型"降级为"子问题级检索路由"，本轮再把它从"检索路由"升级为"显式证据需求"。至此，CODE / DOCUMENT 在 `ask` 主流程里已经完全不带"用户问题分类"的语义。

# 三、数据模型的设计

## 1. 两个结构

**EvidenceRequirement（证据需求）**：四个字段——需求标识、所属子问题标识、描述、偏好来源。

其中前两个字段**由程序赋值**，不由模型输出。这沿用项目在 Question Planner 阶段确立的原则：**结构和标识由程序决定，模型只填措辞**。模型只负责按给定子问题的顺序、为每条各给一条需求，程序校验数量相等后赋 `ER1`…`ERn` 与 `SQ1`…`SQn`。

这个设计有一个额外好处：**"每子问题一条"这个决策被固化成了校验规则**——数量不等即判失败，不需要另写检查逻辑。

**EvidencePlan（证据规划）**：需求元组 + 决策来源。

## 2. 一个刻意的命名选择：DOCUMENT 而不是 DOC

检索层的来源标识是 `"DOCUMENT"`，而 `QueryType` 里用的是 `"DOC"`。证据需求**直接采用检索层的写法**。

理由是避免在边界上做翻译：`preferred_sources` 里的值可以原样交给检索层使用。如果证据需求用 `DOC`，那么每次检索前都要做一次 `DOC → DOCUMENT` 的转换，多一层容易出错、且没有收益的映射。

**为什么用字符串常量而不是枚举。** 设计文档最初画的是 `EvidenceType` 枚举，但项目里 `source_type` 从数据库列到 `Citation` 字段到检索参数，从头到尾都是字符串。引入枚举会在检索边界多一层转换。因此实现改为用一个白名单常量 `EVIDENCE_SOURCES` 做校验，行为等价、边界干净。

# 四、Evidence Planner 的实现

## 1. LLM 契约

模型只输出一个严格 JSON 对象，里面是一个需求数组；每项包含"要找什么"和"偏好来源"。

模型**看不到也不需要输出**任何标识符——它只需要按顺序为每条子问题各给出一条。

## 2. 校验规则

解析函数逐条校验，任一条不满足即判定失败：

1. 响应非空、能被 JSON 解析
2. 顶层是对象，字段集合精确等于约定的那一个字段
3. 需求数组长度**恰好等于**子问题数量
4. 每项的字段集合精确等于约定的两个字段
5. 描述非空单行、不含代码围栏、不超过 300 字符
6. 来源是非空列表、每项属于白名单、不重复
7. 通过后由程序赋 `ER{i}` 与 `SQ{i}`

这套写法和项目在"证据充分性检查""定向查询改写""问题规划"三处已经确立的严格 JSON 风格完全一致。

## 3. 失败闭合：用空需求

任何一条校验不过，或模型调用出任何异常，都返回一个**空需求**的规划，决策来源标为回退。

工作流看到这个标记，就退回**逐子问题调用 `QueryRouter`**——也就是改动前的行为。

**为什么空需求比"保守地全要两类证据"更好。** 空需求 + 回退标记让回退路径与改动前**逐字节一致**，等价性是结构上保证的，不需要逐细节去对齐。如果改成"保守地全要两类证据"，回退就不再是回退，而是变成了一条新的、更贵的路径——它会让检索次数翻倍，而且行为与改动前不同。

这与 Question Planner 的失败闭合是同一个模式，也是本项目一贯的做法：**回退必须是结构等价，而不是语义相似**。

## 4. 提示词里的一个针对性约束

提示词明确要求：**只有在确实需要两类证据互相印证时才同时要 CODE 和 DOCUMENT。**

这一条是针对一个具体风险写的：MIXED 需求会触发两次向量检索，如果模型图省事对每条需求都要两类证据，检索次数会直接翻倍。把约束写在提示词里，比事后在代码里做限制更直接。

# 五、接入编排层

## 1. 接入点

编排层原本在这一步逐个调用 `QueryRouter`；现在改为先跑 Evidence Planner，再用需求决定每条子问题的检索策略。

回退时走原来的分支，因此 `QueryRouter` 依然是编排层的一个依赖——它没有从代码里消失，只是从主路径退到了兜底位置。

## 2. 需求到检索的映射

需求里的来源集合映射成检索层认识的三种路由：只要代码 → CODE，只要文档 → DOC，两者都要 → MIXED。

**这个映射函数刻意放在 `agentic/` 而不是 `planning/`。** 因为 `planning/` 包有一条硬约束：**不得依赖 `routing` 包、不得出现 `QueryType` 标识符**，由一条 AST 测试强制执行。把映射放在编排层，`planning/` 就能保持与三元分类完全无关——这正是"CODE/DOC 是证据类型而非用户问题类型"这条主张在代码结构上的体现。

## 3. 充分性判定完全没动

本轮**不碰** `sufficiency.py`。它仍然按各子问题路由的并集，判断"有没有 CODE 证据、有没有 DOCUMENT 证据"。

也就是说，本轮的重心是"**决定去哪找**"，而不是"**判断找够了没有**"。按需求逐条判定留给下一阶段。

# 六、可观测性

## 1. Trace 多了一块

证据规划整体写入 Trace（需求列表 + 决策来源），与问题规划、引用、节长统计并列。`--debug` 时可以直接看到每条需求及其来源。

一个实际价值：**Trace 里能直接读出"这条子问题的路由是从哪条需求来的"**——路由的 `reason` 字段记了需求编号与来源集合。排查"为什么这条走了文档"时不需要再猜。

## 2. `--plan-only` 一次输出两个规划

这个命令原本只输出问题规划。现在追加一个键，同时输出证据规划。

**为什么是追加键而不是嵌套结构。** 现有测试直接解析输出后断言问题规划的字段。改成嵌套会把已有契约打断；追加键既保住了契约，又能用**一次调用**同时审阅两个规划结果——这对人工检查证据规划质量是必要的，因为单独看证据规划不知道它对应哪些子问题。

# 七、实现效果

## 1. 测试规模

181 → **211 passed / 1 skipped**，新增 30 项。【测试可证】

新增的测试文件覆盖：解析、七条校验的失败集、回退、序列化；编排层的需求驱动路由、双来源映射、回退到 Router、问题规划回退时不调用证据规划器；CLI 的两个规划输出。

**包纯净性测试自动覆盖了新文件**——它遍历 `planning/` 下的所有 Python 文件，新增模块同样受"不得依赖 routing"管辖，不需要额外配置。这算是把约束做成测试的一个附带好处：新代码自动被约束住。

## 2. 它确实会区分问题类型【实测】

同一个命令、只换问题，来源分布完全不同：

| 问题 | 来源分布 |
|---|---|
| 订单超时以后系统怎么处理？ | CODE × 6，无 DOCUMENT |
| 简单解释用户注册的整个业务流程 | CODE × 6，无 DOCUMENT |
| 为什么订单关闭采用延迟队列而不是定时轮询 | CODE × 4，DOCUMENT × 4 |

"实现怎么做"只要代码；"为什么这样设计、取舍何在"要设计说明。

**这是本轮最想验证的一点**：此前由正则信号反推做不到这种区分——"为什么订单关闭采用延迟队列"这题同时含"为什么"和"延迟队列"这类具体名词，正则信号会倾向某一个标签，而规划器能逐条判断。看它的需求描述会更清楚：

```text
ER4 [DOCUMENT] 查找对订单关闭时效、可靠性与资源消耗提出的非功能要求、服务等级或容量规划说明。
ER5 [DOCUMENT] 查找延迟队列与定时轮询在架构耦合、扩展方式和维护成本方面的设计对比、取舍记录或演进说明。
```

这两条明确指向"设计对比与取舍记录"——正是这类问题真正需要的证据，而正则是表达不出这个意思的。

## 3. 端到端：路由确实来自需求【实测】

对"订单关闭为何这样设计"跑 `--debug`，Trace 显示：

```text
证据规划: 6 条需求
   ER1..ER5  CODE
   ER6       DOCUMENT

每子问题实际走的来源：
   SQ1..SQ5  CODE
   SQ6       DOC
```

SQ6 的原句是"订单关闭方式的选择受到哪些约束或目标驱动，与其他可选做法相比取舍何在"——**六个子问题里唯一问"取舍"的那条，也是唯一被规划为需要文档证据的**。

这条对应关系是本轮最有说服力的证据：路由不再是正则匹配的结果，而是逐条需求判断的结果。

## 4. 一个担心的风险没有发生

设计阶段列出的最大风险是"**需求普遍偏 MIXED 导致检索次数翻倍**"——MIXED 会做两次向量检索，若模型对每条需求都要两类证据，检索次数会直接翻倍。

实测结果是：多数需求是**单一来源**，只有设计取舍类问题才有 2/6 条需要两类证据。这个风险没有变成问题。

【推断】原因可能是提示词里写明了"只有在确实需要两类证据互相印证时才同时要两个"，也可能是模型本身倾向给明确的单来源答案。**具体是哪一个原因，当前无法确认**——没有做过对照实验。

## 5. L1 基准逐值未变【实测】

`evaluate` 的四种策略指标与改动前**完全一致**（keyword / vector / hybrid / routed 的 Recall@5 与 MRR 都相同），基准文件的 sha256 也未变。

这符合预期：L1 评测不经过 `ask`，而是直接用检索服务、`QueryRouter` 和检索策略驱动。本轮没有碰这三者，所以基准理应不变——**它也确实是检验"改造是否越界"的一道闸门**。

# 八、存在的问题

## 1. 中等：回退仍然是静默的

与 Question Planner 完全一样的问题：证据规划失败时，用户侧只看到"需求为空"，看不到原因。而失败原因（网络、截断、JSON 非法）在排查时是有意义的。

`--plan-only` 可以一次看到两个规划器的决策来源，但**需要主动去看**，没有任何提示。这个可观测性缺口在上一轮就被记录过，本轮没有改善。

## 2. 中等：需求质量没有评测

"这条证据需求定得对不对"目前只能人工判断。设计文档给出的两个指标（证据需求覆盖率、证据命中率）属于 L2 评测，本轮没有建。

这意味着：**规划器现在会区分问题类型，但没有量化手段回答"它区分得对不对"**。第 7 节的实测只能证明它会区分，不能证明它分得准确。

## 3. 中等：多了一次 LLM 调用

每次 `ask` 现在要调用两次规划（问题规划 + 证据规划），加上充分性检查和回答生成，一次提问的模型调用从 3 次变成 4 次。

成本增加是明确的，收益（更准的检索方向）目前只有定性证据。

## 4. 轻微：两个规划器的职责边界靠提示词维持

问题规划产出"要调查什么"，证据规划产出"要找什么证据"。两者容易写重——例如子问题写成"订单关闭的触发实现在哪里"，需求也写成"订单关闭的触发实现"。

实测中需求描述普遍写成"查找…的实现/说明"这种形式，与子问题没有重复。【实测】但这靠的是提示词，**没有任何机制阻止它们变重**。

## 5. 轻微：需求与子问题严格一对一

"每子问题一条需求"是设计决策，它让检索次数可控、校验规则简单。代价是**无法表达"一条子问题需要分头查两处不相干的证据"**。设计文档的示例里其实有这种情形（一条子问题下列出三条证据），本轮没有采纳。

## 6. 轻微：来源集合只有两种取值组合

`preferred_sources` 当前只有三种有意义的取值：只要代码、只要文档、两者都要。这实际上还是一个三分类，只是换了个名字。

真正摆脱三分类要等 Tool 层——那时的"来源"会变成具体工具（语义检索、符号检索、读源码），组合空间才真正打开。

# 九、可以做的优化

按投入产出比排序。

## 1. 按需求逐条判充分性（下一阶段的首选）

现在 `sufficiency` 仍按并集判"有没有 CODE、有没有 DOCUMENT"，而需求已经是逐条的。

改成逐条判定后，"缺什么"会从"缺少代码证据"这种笼统描述，变成"ER3 未满足：没找到订单关闭与相邻状态的衔接逻辑"这种可定位的清单。**这是当前编排层最明显的一处不匹配**——上游已经细到逐条，下游还在用并集。

## 2. 把需求质量做成可统计的指标

最小可行版本：统计每次运行的需求数、来源分布、单一来源比例、回退率。这些都不需要新建评测集，只需在现有 Trace 上做汇总。

再进一步才是设计文档说的 L2 指标（需求覆盖率、命中率），那需要人工标注 ground truth。

## 3. 给回退加一个可见信号

`ask` 的正常输出目前只显示 `Plan:`，不显示证据规划的决策来源。加一行（或在不回退时省略）就能让"这次没规划"变得可见，成本极低。

这与上一轮记录的"失败闭合让失败原因不可见"是同一个问题，可以一并解决。

## 4. 允许一条子问题拆多条需求

如果能表达"这条子问题需要分头查两处证据"，就能覆盖设计文档里的原始示例。代价是校验规则从"数量必须相等"变成"数量必须落在某范围内"，且检索次数上限需要重新设计。

**在"需求质量可统计"之前不建议做**——否则无法判断拆多条到底有没有改善。

## 5. 提示词层面的来源判定校准

第 7.4 节的实测留下了归因不明的部分：单一来源占多数，究竟是提示词起了作用还是模型本身的倾向。一个便宜的对照实验：去掉提示词里那句约束，看来源分布是否变化。

# 十、这一部分最应该掌握的十个问题

1. **为什么"反推"和"声明"是两回事？**
   反推给的是一个标签加一条正则理由；声明给的是"要找什么"加一个来源集合。前者只能回答"去哪找"，后者能表达"要两类证据互相印证"。

2. **为什么模型不输出需求的 id 和所属子问题？**
   沿用项目原则：结构和标识由程序决定，模型只填措辞。这同时让"每子问题一条"这个决策变成了"数量必须相等"这一条校验规则。

3. **为什么失败回退用"空需求"而不是"保守地全要两类证据"？**
   空需求让回退路径与改动前逐字节一致，等价性是结构上保证的。"保守地全要"会让检索翻倍且行为与改动前不同——那不是回退，是另一条路。

4. **为什么来源用 `DOCUMENT` 而不是 `DOC`？**
   检索层就用 `DOCUMENT`。对齐它可以让需求里的来源原样交给检索，不必在边界上做一次转换。

5. **为什么需求到路由的映射函数放在编排层而不是规划包？**
   规划包有一条硬约束：不得依赖 `routing`、不得出现 `QueryType`。把映射放在编排层，规划包就能保持与三元分类完全无关。

6. **为什么包纯净性测试能自动覆盖新文件？**
   它遍历 `planning/` 下所有 Python 文件。约束做成了测试，新代码就自动被约束住——这是把架构约束写成测试的一个附带好处。

7. **为什么提示词要专门写一句"只在确实需要两类证据时才同时要两个"？**
   因为 MIXED 需求会触发两次向量检索。模型图省事的话，检索次数会直接翻倍。这是把风险写进提示词，而不是事后在代码里拦。

8. **本轮为什么不动充分性判定？**
   本轮的重心是"决定去哪找"。逐条判充分性需要新的状态结构（每条需求的满足情况），与"决定去哪找"是两件事，混在一轮里会让失败无法归因。

9. **L1 基准为什么必然不变？**
   它不经过 `ask`，直接用检索服务、`QueryRouter` 和检索策略驱动。本轮没碰这三者。反过来说，**基准不变本身就是"改造没有越界"的证据**。

10. **"来源只有三种组合"算不算没摆脱三分类？**
    算。当前只是把三分类换了个名字。真正打开组合空间要等 Tool 层——那时的"来源"会变成具体工具而不是两种数据源。

---

# 十一、最终总结

本轮把"这个子问题需要什么证据"从**分类器反推**改成**规划器声明**：

```text
用户问题 → 子问题 → 每条子问题一条证据需求 → 需求决定检索
                        ↑
                    本轮新增
```

改动落到代码上是四件事：

1. 新增证据需求与证据规划两个数据结构，标识由程序赋值；
2. 新增证据规划器，严格 JSON、七条校验、失败时返回空需求以触发回退；
3. 编排层用需求推导检索策略，规划失败回退到 `QueryRouter`（回退路径与改动前逐字节一致）；
4. 证据规划写入 Trace，`--plan-only` 一次输出两个规划结果。

**实测结论**：它确实会区分问题类型（实现类问题全要代码，设计取舍类问题要文档），端到端验证中"唯一问取舍的那条子问题"正是唯一被规划为需要文档证据的；担心的"检索翻倍"风险没有发生；L1 基准逐值未变。

**但要说清楚两件事**：一是**需求质量没有量化评测**——实测只能证明它会区分，不能证明它分得准；二是**回退仍然是静默的**，失败时用户侧只看到需求为空。这两条与上一轮记录的问题同源，都没有在本轮解决。

下一步最该做的是**按需求逐条判充分性**——上游已经细到逐条需求，下游还在用并集判断，这是当前编排层最明显的一处不匹配。
