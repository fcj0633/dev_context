# Evidence Planner 实现详细解读

> 面向读者：已经了解 Question Planner、Chunk 和基础 RAG 检索，希望理解 Evidence Planner 为什么存在、怎样工作，以及目前效果如何。
>
> 本文解释当前仓库的实际实现，不展开复杂源码，也不把尚未评测的效果写成确定结论。

---

## 一、Evidence Planner 解决什么问题

一句话概括两个规划器的分工：

- **Question Planner** 决定“这个问题需要拆成哪些子问题”；
- **Evidence Planner** 决定“回答每个子问题，需要寻找什么证据”。

例如用户问：

> 为什么订单关闭使用延迟队列，而不是定时轮询？

Question Planner 可能把它拆成“订单关闭怎样触发”“延迟队列怎样参与处理”“与定时轮询相比有什么取舍”等子问题。但拆开还不够：实现过程要看源码，背景和取舍要看设计文档，有时还需要两类材料互相印证。

Evidence Planner 的作用，就是在真正检索之前把这些需求说清楚。

### 1. 改造前后的区别

| 对比项 | 改造前 | 改造后 |
|---|---|---|
| 决策依据 | 根据“在哪里”“为什么”等词语和规则推断来源 | 先说明要找什么证据，再选择来源 |
| 输出内容 | CODE、DOC 或 MIXED 标签 | 证据描述 + CODE、DOCUMENT 或两者 |
| 可解释性 | 能看到命中了哪条路由信号 | 能看到每个子问题具体缺什么证据 |
| 失败处理 | 使用原有 Query Router | Evidence Planner 失败时仍退回原有 Router |

原来的 Query Router 更像“分流器”：看到实现、类名、方法名等信号时倾向查代码，看到原因、设计、取舍时倾向查文档。规则不能确定时也可以借助模型分类，但最终仍只有来源标签，不能表达“究竟要找什么”。例如“为什么使用延迟队列”既需要设计理由，也可能需要代码确认设计是否落地。

因此，Evidence Planner 不是再做一次分类，而是把隐含判断变成明确的证据清单。这既能解释检索选择，也为以后逐条判断“证据是否找齐”打下基础。

## 二、它是怎样实现的

当前主流程可以简化为：

```text
用户问题
  ↓
Question Planner：拆成子问题
  ↓
Evidence Planner：为每个子问题声明证据需求
  ↓
按来源分别检索代码、文档或两者
  ↓
合并证据 → 检查充分性 → 生成答案
```

整个实现可以理解成六步。

### 第一步：先拆问题

Question Planner 先确定需要调查哪些方面。Evidence Planner 不重新拆题，也不直接回答问题，它只接收已经拆好的子问题。

前者关注“答案讲什么”，后者关注“这些内容凭什么”。

### 第二步：为每个子问题生成一条证据需求

Evidence Planner 按子问题顺序，为每一条生成对应的 `EvidenceRequirement`。一条需求包含两类核心信息：

- `description`：要找的具体内容，例如“订单关闭触发与执行过程的实现证据”；
- `preferred_sources`：优先从代码、文档还是两者中寻找。

当前版本规定一个子问题对应一条需求，关系清楚、检索次数可控，也容易发现遗漏。

### 第三步：组成完整证据计划

所有需求合在一起形成 `EvidencePlan`。计划里还保留 `decision_source`，用于说明本次结果来自模型正常规划，还是规划失败后的回退路径。

需求编号及其与子问题的对应关系由程序生成。模型只描述要找什么、选择来源，避免编号重复或错位。

### 第四步：校验模型输出

模型输出不能直接进入检索。程序会检查：输出能否解析、需求数量是否与子问题一致、描述是否有效、来源是否只包含允许的 CODE 和 DOCUMENT，以及同一来源是否重复。

任一关键条件不满足，规划就失败，避免残缺或错位的计划控制后续检索。

### 第五步：把证据来源转换成检索方式

校验通过后，每条需求会被转换成检索层可以执行的方式：

| 证据需求 | 实际检索方式 |
|---|---|
| 只需要 CODE | 只检索代码 |
| 只需要 DOCUMENT | 只检索项目文档 |
| 同时需要 CODE 和 DOCUMENT | 分别检索两类来源，再合并结果 |

仍以订单关闭问题为例：查找“关闭任务如何触发和执行”时主要需要代码；查找“为什么选择延迟队列”时需要设计文档；如果要核对设计是否真正落地，就需要代码和文档共同支持。

提示词要求能用一种来源说明时不要无条件选择两种，因为双来源检索会增加查询次数、延迟和上下文占用。

### 第六步：合并结果并继续原有问答链路

每个子问题完成检索后，结果会去重并合并，再交给现有的 Context Builder、充分性检查和答案生成流程。

Evidence Planner 到这里就完成了职责。它不是底层 Retriever，不负责计算相似度；也不是答案生成器，不负责组织最终回答。它做的是检索前的证据规划。

### 规划失败时怎么办

Evidence Planner 的失败不会让整次问答中断。模型不可用、返回空内容、格式错误或需求数量不一致时，系统会生成一份带有 `fallback` 标记的空计划，然后对每个子问题继续调用原有 Query Router。

新功能成功时使用证据需求，失败时恢复旧路由，因而不会成为单点故障。

调试 Trace 会记录证据计划、来源和实际路由；`--plan-only` 可同时查看问题规划与证据规划，便于定位“为什么查文档而没查代码”。

## 三、当前实现的效果如何

这里需要把“已经验证的事实”“可以从逻辑上确认的收益”和“目前还没有数据证明的效果”分开。

### 1. 已经验证的事实

完整测试结果：

```text
211 passed, 1 skipped
```

跳过的是需要显式开启并连接 PostgreSQL 的存储集成测试，不是 Evidence Planner 测试失败。相关测试已经覆盖：需求解析、非法输出回退、来源到检索方式的转换、双来源检索、主流程接入以及命令行规划输出。

运行记录表明，它会根据问题内容选择不同证据：

- “订单超时以后系统怎么处理”这类实现问题，需求主要指向 CODE；
- “为什么采用延迟队列而不是定时轮询”这类取舍问题，会要求 DOCUMENT，并在需要核对实现时同时要求 CODE；
- 在端到端调试信息中，询问实现的子问题走代码检索，询问约束和取舍的子问题走文档检索，实际路由与证据计划能够对应起来。

接入后，原有 L1 检索基准保持不变。这符合预期：改造只调整 `ask` 如何决定证据来源，没有修改底层检索和评分逻辑。

### 2. 从当前设计可以确认的收益

第一，检索决定更容易解释。系统不再只能说“这句话命中了文档信号”，而是能说明“这个子问题需要查设计取舍，因此检索文档”。

第二，复杂问题可以把实现证据和设计证据分开寻找。这样至少在逻辑上减少了只查一类材料、导致回答缺少另一半依据的风险。

第三，回退路径保留了旧能力。Evidence Planner 出错会降低为原来的规则路由，而不是让整个问答失败。

第四，结构化需求为以后记录“已满足、部分满足、未满足”提供了基础。

### 3. 目前还不能证明什么

项目还没有 Evidence Planner 专属的准确率、需求覆盖率或证据命中率评测。现有结果能证明它按设计工作、会区分来源，但不能证明所有规划都正确，更不能宣称整体召回率或答案准确率已经提高。

当前的充分性检查仍然看所有子问题合并后是否具备所需的代码或文档来源。例如整体计划需要两类证据，只要最终上下文中两类都存在，就可能通过来源检查；系统还不能逐条回答“ER1 找到了吗、ER2 找到了吗”。这也是当前实现最明显的下一步空间。

### 4. 需要承担的代价

- 每次正常 `ask` 增加一次模型规划调用，因此会增加一定延迟和调用成本；
- 规划失败虽然能够自动回退，但普通输出对失败原因展示得还不够明显；
- 一个子问题只能对应一条需求，暂时不能表达“同一子问题需要分别调查多项独立证据”。

因此，现阶段最准确的评价是：**机制已经落地，行为已经验证，质量收益仍需要评测。**

---

## 四、总结

Evidence Planner 的核心价值不是“再做一次 CODE、DOC、MIXED 分类”，而是在检索之前明确回答：**每个子问题究竟需要什么证据，以及应该从哪里寻找。**

```text
用户问题 → 子问题 → 证据需求 → 按来源检索
        → 汇总证据 → 检查充分性 → 生成答案
```

当前版本已经完成主流程接入、严格校验、安全回退和调试记录，并通过自动化测试及真实运行示例验证了基本行为。它让检索决策从“根据措辞猜来源”前进到“根据证据目标选来源”，但还没有量化证明最终检索或回答质量提升了多少。

下一步最有价值的工作不是继续增加更多标签，而是按每条证据需求检查是否真正满足，并建立证据需求覆盖率、证据命中率等质量指标。只有完成这一步，才能用数据回答 Evidence Planner 究竟让系统变好了多少。
