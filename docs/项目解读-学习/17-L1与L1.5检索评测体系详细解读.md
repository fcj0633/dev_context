# L1 与 L1.5 检索评测体系详细解读

## 1. 先说结论：当前检索质量究竟怎么样

DevContext 的检索已经不是“把用户原问题丢给向量库，取前几条结果”这么简单。当前主流程会先把问题转换成若干条可验证的证据需求，再为每条需求生成搜索动作，按来源执行底层检索，把候选证据公平地放入 Context，检查每条核心需求是否满足；如果第一轮仍有明确缺口，还会进行一次定向补检索。

因此，检索质量也不能再只用一个 Recall@5 衡量。当前项目保留了固定 Query 的 L1，同时新增了运行到 `EvidencePackage` 的 L1.5，并让 5 条关键 regression 真正执行完整检索工作流。

当前实际报告给出的总体判断是：

- 底层检索中，来源路由后的 `routed` 明显优于裸 `keyword`、`vector` 和 `hybrid`，说明“先确定去哪类知识中找”是有效的；
- L1 的 Top-20 明显好于 Top-5，说明相当一部分失败不是知识库里没有证据，而是目标证据排名不够靠前；
- MIXED 问题仍然是 L1 的主要弱项，经常只能找到代码或文档中的一边；
- L1.5 冻结链路的可满足 CORE 覆盖率为 **91.67%**，完整案例成功率为 **78.26%**；
- 候选证据进入最终 Context 后的存活率为 **92.31%**，说明总体保留效果较好，但已经出现“二轮找到了目标、最终被字符预算裁掉”的具体案例；
- 修正评测口径后，第二轮补检索救回 **6/8，75%**；另有 5 次搜索发生在人工已标记为不可满足的需求上，它们单独计为无效尝试，不再污染 Rescue 分母；
- `false_ready_count=0`，系统没有在缺少必要证据时错误宣称“证据已经齐全”；READY recall 为 **83.33%**，仍表现为偏保守。

一句话概括：**当前系统已经能安全地组织一轮或两轮证据检索，第二轮本身并非普遍无效；剩余问题已经可以进一步区分为候选排名边界、Context 存活、不可满足需求的无效补查和生产 Coverage 偏保守。**

## 2. 当前生产检索策略：从用户问题到 EvidencePackage

### 2.1 检索的目标已经从“找相关内容”变成“满足证据需求”

旧式 RAG 常见的处理方式是：

```text
用户问题 → 生成向量 → Top-K Chunk → 交给回答模型
```

它只能判断 Chunk 与问题是否相似，无法表达“回答这个问题需要哪几类事实”。例如用户问“为什么订单关闭使用延迟队列”，系统至少要区分：

1. 当前代码在哪里发出、消费和处理关闭事件；
2. 延迟关闭在业务上解决了什么问题；
3. 项目是否真的记录过与轮询方案的比较或设计依据。

只搜一次原问题，很可能找到实现却找不到设计依据，或者找到一篇设计文档却没有当前代码证明。当前系统因此先形成 `EvidencePlan`，其中每条 `EvidenceRequirement` 都描述：

- `target`：必须确认的项目事实；
- `success_criteria`：证据包含哪些内容才算找齐；
- `priority`：CORE 或 SUPPORTING；
- `temporal_scope`：当前、历史、未来或任意时间状态；
- `source_requirement`：必须来自代码、文档、两者或任一来源。

这一步只定义“要知道什么”，不提前固定回答章节，也不把回答深度混入检索预算。

### 2.2 完整执行链

```text
用户原问题
   ↓
EvidencePlanner
   生成 1～6 条 EvidenceRequirement
   ↓
SearchActionPlanner（第一轮）
   每条需求生成一个实际 Query
   ↓
RetrievalPolicy
   根据 source_scope 选择 CODE / DOCUMENT / BOTH / ANY 检索路径
   ↓
EvidencePool
   标注证据权威性、时间状态和所属 Requirement
   ↓
ContextBuilder
   公平选证据、去重、执行字符预算
   ↓
CoverageChecker
   先检查来源是否齐全，再判断语义是否满足 success_criteria
   ↓
未满足的 CORE 是否需要第二轮？
   ├─ 否：冻结结果
   └─ 是：利用缺失条件和已发现项目术语生成新 Query，再检索一次
   ↓
EvidencePackage：READY / PARTIAL / EMPTY
```

这条链路的边界很明确：`EvidencePackage` 一旦形成，检索阶段结束。后面的 AnswerPlanner 和回答生成器只能使用包中的证据，不能为了让回答更顺畅而临时再搜一次。

### 2.3 SearchAction 如何生成

第一轮 Query 不是简单复制用户问题。`SearchActionPlanner` 会同时读取：

- 用户原问题；
- 当前 Requirement 的 `target`；
- `success_criteria`；
- `source_requirement`。

它只允许为每条需求输出一个查询文本，不得回答问题、创建新需求或改变证据来源要求。若模型输出失败，程序会把原问题、证据目标和成功条件拼成确定性 Query，保证检索流程继续运行。

第二轮只处理第一轮状态为 `PARTIAL` 或 `MISSING` 的 CORE。新 Query 还会加入：

- 第一轮明确缺少的内容；
- 第一轮已经发现的类名、方法名、签名、文件名或文档标题；
- 已执行过的 Query。

程序要求第二轮 Query 与旧 Query 有实际差异，并优先使用已经出现过的真实项目符号，避免模型凭空编造类名。CORE 每次取 5 个结果，SUPPORTING 每次取 3 个结果；SUPPORTING 不执行第二轮。整次请求最多 12 个逻辑 SearchAction，防止工作流无限搜索。

### 2.4 来源要求如何变成实际检索策略

LLM 不直接决定使用 keyword、vector 还是 hybrid。模型只给出证据需要来自哪一类来源，程序再做确定性映射：

| `source_scope` | 当前实际执行方式 | 设计意图 |
|---|---|---|
| `CODE` | 仅过滤 CODE，执行 keyword + vector，再用 RRF 融合 | 类名、方法名可由关键词命中，语义描述可由向量命中 |
| `DOCUMENT` | 仅过滤 DOCUMENT，执行 vector | 文档问题通常是自然语言语义匹配 |
| `BOTH` | CODE 与 DOCUMENT 分别执行 vector；文档侧至少取 20 个候选，再提升一个标题/路径更匹配的文档锚点，最后交错合并 | 防止某一来源完全占满 Top-K |
| `ANY` | 不限制来源，执行 keyword + vector，并用 RRF 融合 | 来源不确定时在全库中寻找直接证据 |

这里有两个容易混淆的点。

第一，`hybrid` 不是“模型选择了混合检索”，而是程序同时取得关键词排名和向量排名，再用 Reciprocal Rank Fusion（RRF）合并。当前 RRF 的常量 `k=60`，同一个 Chunk 如果在两份排名中都靠前，融合分数会更高。

第二，`BOTH` 不是一次无过滤的 hybrid。它会分别检索代码和文档，然后交错组合结果。这是为了显式保证双来源机会，而不是让得分更高的一类来源把另一类完全挤掉。

### 2.5 EvidencePool 如何避免前面的需求吃掉全部名额

多条 Requirement 的候选结果不能简单按返回顺序拼接，否则前几个需求很容易占满 Top-K。`EvidencePool` 当前按以下顺序选证据：

1. 每条 CORE 先保留至少一个候选；
2. CORE 要求 `BOTH` 时，在候选可用的前提下尽量分别保留 CODE 和 DOCUMENT；
3. 每条 SUPPORTING 再保留至少一个候选；
4. 剩余名额按证据权威性和原检索顺序补充；
5. 相同 Chunk 只进入 Context 一次，但可以标记为同时支持多条 Requirement。

`SourcePolicy` 还会为证据附加权威性与时间状态：当前代码自动视为 `IMPLEMENTATION + CURRENT`，优先级为 100；文档则按路径规则标记为当前设计、验证材料、一般文档、历史计划等。当前问题优先使用 CURRENT 证据，历史或未来材料不会自然覆盖当前代码。

### 2.6 ContextBuilder 与字符预算

EvidencePool 先按 `top_k` 选出候选，`ContextBuilder` 再执行去重和字符预算。若同时存在代码、文档并且两条都能完整放入预算，会优先保留一个代码锚点和一个文档锚点。最后一条证据如果只放入了部分正文，会被标记为 `truncated`。

被截断的证据虽然可以出现在展示 Context 中，但不能用于证明 Requirement 已满足。这条规则避免模型只看到半段代码或半段文档，就误判关键条件已经出现。

Context 预算不再受回答深度控制，而由证据计划复杂度决定：

- `8000` 字符：只有一条非 BOTH 的 CORE；
- `16000` 字符：普通的 2～3 条需求，或存在一条 BOTH；
- `28000` 字符：4～6 条需求、至少两条 BOTH，或至少两条 CURRENT CORE；
- 用户显式提供 `context_budget_override` 时，以显式值为准。

因此同一个问题使用 brief 或 detailed 回答模式时，检索计划、检索预算和 EvidencePackage 应保持一致，区别只应出现在后续回答组织中。

### 2.7 CoverageChecker 与最终状态

CoverageChecker 分两层判断。

第一层由程序检查来源条件。例如 `BOTH` 必须同时具有未截断的 CODE 和 DOCUMENT，缺少任何一类都只能是 `PARTIAL` 或 `MISSING`。

第二层才由模型判断这些证据是否真正覆盖 `target` 和 `success_criteria`。相关但不能证明目标的材料只能判为 `PARTIAL`。检查模型连续失败时标记 `UNVERIFIED`，而不是伪装成“确实没有证据”。

最终状态为：

| 状态 | 判断规则 |
|---|---|
| `READY` | 最终 Context 非空，并且所有 CORE 都为 `SATISFIED` |
| `PARTIAL` | 有可用 Context，但至少一条 CORE 未满足或未完成验证 |
| `EMPTY` | 最终 Context 中没有任何证据项 |

注意：生产状态反映的是系统自己的 Requirement 与 Coverage 判断；评测时还必须用独立人工 Ground Truth 再检查一次，不能让系统既当考生又当裁判。

## 3. 原有测评为什么不够

原来的 L1 并非无效，它非常适合检查 Embedding、数据库查询、RRF 或路由规则修改后，固定目标有没有掉出 Top-K。问题在于，它测量的边界比当前产品链路窄得多。

### 3.1 平均 Recall 会掩盖“答案仍不可用”

假设一个问题必须同时找到代码实现和设计文档。系统只找到代码时，Recall 可以是 0.5，看起来不算完全失败；但回答“为什么这样设计”时，缺少设计依据仍然无法完整回答。

因此需要新增 Full-case Success：只有一个案例的所有逻辑证据组全部命中，才记为成功。

### 3.2 MRR 只关心第一条相关结果

MRR 衡量第一个相关结果排得多靠前，适合定位题。但一个复杂问题可能需要五条不同证据。第一条排第 1，不代表另外四条也存在。因此 MRR 必须与 Full-case Success、CORE Coverage 配合阅读。

### 3.3 固定原始 Query 测不到 RetrievalController

当前生产流程真正搜索的是 SearchAction Query，而不是始终搜索用户原话。固定 Query 的 L1 无法发现：

- EvidencePlanner 是否漏掉必要事实；
- SearchAction 是否把检索意图表达准确；
- 第二轮是否利用了第一轮发现的项目术语；
- 证据是否在 EvidencePool 或字符预算阶段被丢弃；
- CoverageChecker 是否把不充分证据误判为充分；
- EvidencePackage 是否错误输出 READY。

### 3.4 过去的 regression 只验证文件结构

5 条关键问题虽然存在于 regression 数据中，但过去只检查 JSON 是否合法，并没有实际通过检索控制器。这样的测试只能证明“评测样本还在”，不能证明这些关键问题仍然能够找到证据。

### 3.5 没有独立衡量第二轮到底有没有价值

系统增加第二轮会带来模型调用、Embedding 和数据库检索成本。如果不记录第一轮与第二轮的候选和 Context，就无法知道第二轮是在补齐证据，还是重复第一轮结果。Second-round Rescue 正是为这项成本收益判断而增加。

## 4. 优化后的三层评测边界

| 层级 | 输入 | 实际运行范围 | 主要回答的问题 |
|---|---|---|---|
| L1 | 冻结的原始 Query | keyword / vector / hybrid / 旧 routed 到 Top-K | 底层召回和排序是否退化 |
| Regression | 5 条关键业务问题 | EvidencePlan 到 EvidencePackage | 已知关键场景是否仍能获得应有状态和证据 |
| L1.5 | 18 条证据工作流问题 | Requirement、两轮 SearchAction、Context、Coverage、Package | 当前完整检索控制器是否找齐必要证据 |

L2 继续负责最终回答是否正确、清楚和自然。L1.5 到 `EvidencePackage` 为止，不生成回答，避免回答文风、篇幅和结构问题污染检索指标。

## 5. L1 具体如何测

### 5.1 数据与执行方式

L1 使用 `benchmark/cases.jsonl` 中冻结的 36 条案例，CODE、DOC、MIXED 各 12 条。每条案例保留固定问题和人工标注的逻辑证据组，分别执行四种策略：

- `keyword`：数据库关键词检索；
- `vector`：Query Embedding 与 Chunk 向量相似度检索；
- `hybrid`：关键词与向量候选经过 RRF 融合；
- `routed`：旧 QueryRouter 先判断 CODE、DOC 或 MIXED，再按 RetrievalPolicy 检索。

这里的 `routed` 是 L1 为历史可比性保留的旧来源路由，不等同于当前 EvidencePlan → SearchAction → Coverage 的 RetrievalController。

### 5.2 Ground Truth 不是单个文件名

每个案例可以包含多个“逻辑证据组”。一个证据组可指定来源类型、路径片段、类名、方法名、签名、行号或文档标题。若同一事实在多个位置都能被证明，可以用 `any_of` 表示等价候选，命中任意一个都算该组成功。

这种设计比只比对 Chunk ID 更稳定：重新切块导致 ID 改变时，只要语义位置仍然一致，就不会无故把正确结果判错。

### 5.3 L1 指标的含义

```text
Recall@K
= Top-K 命中的逻辑证据组数 / 该案例全部逻辑证据组数
```

```text
Full-case Success@K
= 该案例全部逻辑证据组是否都进入 Top-K
```

```text
MRR
= 1 / 第一条相关结果的排名
```

此外还报告：代码来源命中率、文档来源命中率、双来源同时命中率、重复结果率、无结果率、各检索阶段耗时，以及按 CODE、DOC、MIXED 和 legacy 子集的分组结果。

L1 还会把失败初步分成三类：

- `RETRIEVAL_MISS`：目标连对应来源的 Top-20 候选中都没有出现，偏向原始召回问题；
- `RANKING_MISS`：目标出现在较深候选或最终 Top-20，却没有进入 Top-5，偏向排序问题；
- `COMPOSITION_MISS`：代码和文档候选各自存在，但最终 Top-5 没有同时保留两边，偏向多来源组合问题。

这类归因不是最终根因诊断，但能指出下一步该查召回、排名还是组合策略。

## 6. L1.5 具体如何测

### 6.1 每条案例标注什么

L1.5 数据集有 18 条问题，并与 L2 的 `flow`、`why`、`edge`、`negative`、`locate` ID 对齐，但它不会直接拿 L2 的“回答必须覆盖什么”当检索真值。每条案例单独标注：

- 人工冻结的 EvidenceRequirement；
- 每条 Requirement 当前是否可满足；
- 必须命中的一个或多个逻辑证据组；
- 第一轮与第二轮冻结 Query；
- 期望 Package 状态 READY、PARTIAL 或 EMPTY。

Ground Truth 的确定顺序是先检查当前索引、源码和文档中是否真的有证据，再人工确认它能否满足 `success_criteria`。不能因为当前系统恰好搜到了某个 Chunk，就反过来把它标成正确答案。

### 6.2 frozen：稳定地测检索、组合和 Context

默认 frozen 模式使用：

- `FrozenEvidencePlanner`：读取人工 Requirement；
- `FrozenSearchActionPlanner`：读取人工冻结的两轮 Query；
- 真实 RetrievalPolicy、数据库检索、EvidencePool 与 ContextBuilder；
- `OracleCoverageChecker`：根据人工证据组是否进入 Context 做确定性判定。

它不调用规划和 Coverage LLM，所以同一版本重复运行不会因模型临时改变需求或措辞而漂移。frozen 主要测量：在相同证据目标和 Query 下，底层召回、证据组合、Context 选择和第二轮机制是否稳定。

### 6.3 live：测真实产品链路

live 模式使用真实 EvidencePlanner、SearchActionPlanner、CoverageChecker 和 RetrievalController。它能暴露 frozen 无法覆盖的问题，例如 Planner 漏需求、Query 生成偏题、Coverage 误判。

但最终得分仍由人工 Gold Requirement 计算，而不是直接相信模型自己的 `SATISFIED`。如果 live Planner 少生成一条关键需求，系统内部可能认为全部需求已完成，外部 Oracle 仍会按漏掉的 Gold CORE 扣分并检查 False READY。

live 支持重复 1～5 次，每次独立记分，用于观察模型输出的稳定性。不能把多次运行的结果拼在一起，伪装成一次检索成功。

### 6.4 为什么需要只读 RetrievalObserver

最终 `EvidencePackage` 只保存最终 Context，无法回答“证据是根本没搜到，还是搜到了却被裁掉”。评测运行器因此通过只读 Observer 记录：

- 每个 SearchAction 的完整候选；
- 候选属于哪个 Requirement 和哪一轮；
- 第一轮 Context；
- 第二轮 Context；
- 最终 Context 以及被截断的项；
- 检索异常类别。

Observer 只能复制快照，不能修改 Query、候选、EvidencePool、Coverage 或 Package，因此不会为了测量而改变正常检索行为。

### 6.5 L1.5 的六个关键指标

#### Full-case Success

一个案例中，所有 `expected_satisfied=true` 的 Requirement 都获得全部 Gold 证据组，才算完整成功。它比平均覆盖率更接近“当前已有证据是否真的找齐”。

#### CORE Requirement Coverage

```text
CORE Coverage
= 已完整满足的可满足 Gold CORE 数
  / 全部可满足 Gold CORE 数
```

分母使用人工 Gold CORE，而不是模型实际生成的 CORE。因此 live Planner 漏掉需求不会让分母随之缩小。

#### All-core-satisfied Case Rate

它按案例统计：一个问题的所有可满足 CORE 是否一次全部找齐。CORE Coverage 可能很高，但只要缺失分散在多个案例中，真正可以完整进入回答阶段的问题比例仍可能偏低。

#### False READY

```text
生产 Package = READY
但 Gold CORE 未全部满足，或该案例期望状态不是 READY
→ False READY
```

它衡量系统有没有“证据不够却自信地放行”。报告必须同时展示 predicted READY 数和 READY recall，防止系统靠永远输出 PARTIAL 获得虚假的零误报。

#### Context Survival

```text
Context Survival
= 候选中已找到、且完整进入最终 Context 的 Gold 证据组
  / 任意 SearchAction 候选中找到的 Gold 证据组
```

没有进入最终 Context、正文被截断、时间状态不符合 Requirement，都不算存活。它按逻辑证据组而不是原始 Chunk 数计算，避免重复命中同一 Chunk 造成虚高。

#### Second-round Rescue

只有 `expected_satisfied=true`、第一轮未满足，并且控制器确实为**同一个 Requirement** 执行了第二轮的 CORE 才进入分母。第二轮补齐全部 Gold 证据组才算 rescued；重复命中已有 Chunk 或仍不完整都算 no-gain。对 `expected_satisfied=false` 的需求执行第二轮不会进入 Rescue 分母，而是由 `unanswerable_second_round_attempt_count` 单独记录。

```text
Rescue Rate
= 第二轮成功补齐的 CORE 数
  / 实际进入第二轮的 CORE 数
```

当没有 eligible Requirement 时，指标为 `null`，不是 0。

## 7. 真实 L1 结果如何解读

以下数字来自当前 L1 报告，共 36 条案例：

| 策略 | Recall@5 | Full-case@5 | Recall@20 | Full-case@20 | 平均耗时 |
|---|---:|---:|---:|---:|---:|
| keyword | 22.22% | 16.67% | 29.17% | 22.22% | 约 588 ms |
| vector | 47.22% | 36.11% | 79.17% | 72.22% | 约 541 ms |
| hybrid | 47.22% | 36.11% | 75.00% | 63.89% | 约 1107 ms |
| routed | **66.67%** | **58.33%** | **86.11%** | **80.56%** | 约 663 ms |

### 7.1 来源路由确实有效

`routed` 的 Recall@5 比裸 vector/hybrid 高约 19.45 个百分点，Full-case@5 高约 22.22 个百分点。说明在当前数据集上，先限制代码、文档或双来源，可以显著减少无关来源竞争。

但这不能直接证明新 RetrievalController 的 Planner 很准确：L1 的 routed 使用旧 QueryRouter，而且当前 36 条问题的来源意图比较明确。报告中的路由准确率为 100%，更适合解释为“这批冻结样本上的路由规则没有出错”，不能外推成所有自然语言问题都能准确分类。

### 7.2 向量检索远好于纯关键词，但 hybrid 暂未体现整体增益

纯关键词对 CODE 尚有一定效果，但 DOC 的 Recall@5 为 0，说明中文自然语言文档很难只靠词面重合稳定召回。vector 显著改善了文档和语义表达不同的场景。

裸 hybrid 的 Recall@5 与 vector 同为 47.22%，Full-case@5 也同为 36.11%，但平均耗时约是 vector 的两倍；到 Top-20 时 hybrid 还略低于 vector。当前数据不支持“只要加关键词融合就一定更好”。更合理的判断是：RRF 能补充精确符号命中，但候选池、权重或排名融合仍需要针对数据继续调试。

### 7.3 Top-5 到 Top-20 的提升说明排序仍有空间

以 vector 为例，Recall 从 47.22% 升到 79.17%；routed 从 66.67% 升到 86.11%。这意味着不少正确证据已经被召回，但没有进入较小的最终窗口。

因此不能把所有 Top-5 失败都归咎于 Embedding。对这部分案例，优化重排、来源配额、查询表达或 Context 选择，可能比单纯扩大索引更有效。

### 7.4 MIXED 是最明显的薄弱点

routed 在 CODE 案例上的 Full-case@5 为 75%，DOC 为 58.33%，MIXED 只有 41.67%；MIXED 的双来源同时命中率同样只有 41.67%。当前 routed 失败共 15 条，其中：

- `RETRIEVAL_MISS` 3 条；
- `RANKING_MISS` 5 条；
- `COMPOSITION_MISS` 7 条。

数量最多的是组合失败。这说明“代码和文档都可能存在”不等于“最终窗口能同时保留二者”。这也是新 RetrievalController 为 BOTH 单独检索两类来源、EvidencePool 为双来源保留名额的直接原因。

### 7.5 L1 当前没有整体通过旧质量门槛

当前报告中，数据规模、类型分布、基线哈希和策略相对改进检查正常，hybrid Recall@5 也没有相对既有基线回退。但旧绝对门槛仍失败，例如 legacy hybrid Recall@5 只有 0.583，低于 1.0；MIXED hybrid 双来源命中率为 0，低于 0.8。因此 L1 报告的总体质量门槛仍为未通过。

这并不与 L1.5 的硬门槛通过冲突：两者测量边界不同。L1 说明底层固定 Query 的历史目标仍有明显缺口，L1.5 说明当前完整控制器没有执行错误和 False READY。

## 8. 真实 L1.5 与 Regression 结果如何解读

当前 frozen 全量报告包含 18 条 L1.5 和 5 条 regression，共 23 条案例：

| 指标 | 当前结果 |
|---|---:|
| 成功执行 | 23/23 |
| 执行错误 | **0** |
| Full-case Success | 18/23，**78.26%** |
| 可满足 CORE 覆盖 | 22/24，**91.67%** |
| 全部可满足 CORE 均找齐的案例 | 16/18，**88.89%** |
| predicted READY | 15 |
| False READY | **0** |
| READY recall | **83.33%** |
| 期望状态准确率 | 19/23，**82.61%** |
| Context Survival | 36/39，**92.31%** |
| Second-round Rescue | 6/8，**75.00%** |
| 第二轮 no-gain | 2/8 |
| 不可满足需求的二轮尝试 | 5 |
| 平均 SearchAction 数 | 2.35 |

### 8.1 硬门槛通过，但不能理解成检索已经优秀

第一阶段只设置两个硬门槛：`execution_error_count == 0` 和 `false_ready_count == 0`。当前二者都通过，说明评测链路能完整运行，并且系统没有把人工判断证据不足的问题错误放行为 READY。

但 Full-case 仍只有 78.26%，期望状态准确率为 82.61%。所以正确结论是“系统安全性门槛通过，并建立了可用基线”，不是“检索质量已经达标”。

### 8.2 91.67% CORE Coverage 与 78.26% Full-case 的差距

CORE Coverage 按需求平均，Full-case 按整个问题计算。22/24 条可满足 CORE 已找齐，看上去较高；但一个案例只要缺一条必要证据就不是完整成功，因此 Full-case 只有 18/23。

这正是新增 Full-case 的价值：它防止“多数需求都命中了”掩盖“最终仍有不少问题缺一块关键证据”。

### 8.3 False READY 为 0，系统目前偏保守

18 条期望 READY 的问题中，系统正确输出了 83.33% 的 READY，没有出现错误 READY。换言之，当前主要风险不是证据不足时过度自信，而是明明 Gold 证据已经出现，内部 Coverage 或证据归属仍把 Package 保留在 PARTIAL。

例如 REG-002 的 Gold CORE 已完整进入最终 Context，Full-case 和 CORE Coverage 都成功，但生产 Package 仍为 PARTIAL。这类案例说明召回本身没有失败，问题更可能发生在 Chunk 与 Requirement 的归属、内部 Coverage 语义判断或生产状态计算上。

### 8.4 Context Survival 92.31%，总体较高但不能忽略具体裁剪失败

39 个曾在任意 SearchAction 候选中出现的 Gold 证据组，有 36 个完整进入最终 Context，丢失 3 个。总体保留率仍较高，但 `edge-01` 已经证明：二轮候选中可以同时找到 `purchaseTickets` 和 `doPurchaseInTransaction`，它们仍可能因为 8000 字符预算和候选顺序没有完整存活到最终 Context。

因此下一步不应首先盲目扩大 Context。大 Context 会增加后续模型成本，却不一定解决没有召回、Query 偏题或 Coverage 误判。应先定位剩余需求是否根本没进入候选，以及为什么已进入 Context 的证据没有被正确判定。

### 8.5 修正口径后第二轮救回 75%，剩余失败不能都归咎于 Query

旧报告把所有执行过第二轮的 CORE 都放入分母，包括人工已经标记为 `expected_satisfied=false` 的需求，还会把同来源但属于其他 Requirement 的 SearchAction 错归过来，因此得到 6/15。修正后，真正可救援且为同一 Requirement 执行二轮的 CORE 有 8 条，其中 6 条补齐，Rescue 为 75%；另有 5 次不可满足需求二轮尝试被独立暴露。

剩余两条 no-gain 的原因已经不同：

- `flow-02`：`UserLoginServiceImpl#register` 位于候选边界之外，属于排名/候选窗口问题；
- `edge-01`：精简 Query 已在二轮 Top-5 找到两个目标方法，但最终 Context 没有完整保留，属于 Context Survival 问题。

把 CORE Top-K 从 5 临时提高到 6 的对照实验救回了 `flow-02`，却让 `negative-01` 从成功退化为失败；Full-case 仍是 18/23，Context Survival 从 92.31% 降到 90.00%。因此生产配置保持 Top-5，不能用全局扩大候选窗口解决局部排名问题。

这项指标第一次让“第二轮检索是否值得”可以被量化，而不再只能凭个别 Trace 判断。

### 8.6 不同问题类型差异很大

| 标签 | 案例数 | Full-case Success |
|---|---:|---:|
| locate | 3 | **100%** |
| negative | 4 | 75% |
| flow | 7 | 85.71% |
| why | 7 | 71.43% |
| edge | 4 | **50%** |

定位题通常具有明确的类名、方法名或职责词，当前检索最擅长这类问题。流程题和原因题需要组合多段证据，成功率处于中间水平。边界与异常题只有 25%，是最突出的短板：这类问题往往需要同时找到正常路径、失败分支、事务或补偿边界，任何一组缺失都会导致整题失败。

这里的标签可以重叠，所以各标签案例数相加会超过 23；它们用于切片观察，不是互斥分类。

### 8.7 READY、PARTIAL、EMPTY 的结果要分开理解

| 期望状态 | 案例数 | 状态准确率 | Full-case |
|---|---:|---:|---:|
| READY | 18 | 83.33% | 83.33% |
| PARTIAL | 4 | 100% | 50% |
| EMPTY | 1 | 0% | 100% |

PARTIAL 的状态判断全部正确，说明系统能较好地保留“不足以证明完整结论”的边界。

EMPTY 的 Full-case 100% 是一个容易误读的数字。该案例没有 `expected_satisfied=true` 的 Requirement，所以“所有可满足需求都找齐”在数学上是空集合成立，并不表示检索成功。生产系统实际返回 PARTIAL 而不是 EMPTY，是因为它仍找到了相关 Context；这暴露了一个状态语义差异：生产 `EMPTY` 表示 Context 完全为空，而人工 `EMPTY` 更强调没有直接可用于回答的证据。后续应明确两者是否需要统一，不能把这个 100% 当作优点。

### 8.8 5 条 Regression 的逐条结果

| 案例 | 期望 | 实际 | Full-case | 解读 |
|---|---|---|---|---|
| REG-001 订单关闭设计 | READY | READY | 成功 | 实现与设计依据均进入证据包 |

这些结果比过去的“JSON 结构合法”更有意义：它们真实运行了 EvidencePlan、SearchAction、Retrieval、Context 与 Coverage，可以发现关键问题是在召回、组合还是状态判断上退化。

## 9. 当前结果能够证明什么，不能证明什么

### 9.1 可以确认的事实

- L1 的固定 Query 检索中，当前 routed 明显优于其他三种裸策略；
- 裸关键词不适合当前中文文档检索；
- 很多目标存在于 Top-20，但没有进入 Top-5，排序和窗口组合仍有优化空间；
- MIXED 双来源组合是 L1 的主要失败类型；
- frozen L1.5 的执行错误和 False READY 都为 0；
- 当前 Context Survival 总体较高，但具体案例仍可能在最终字符预算阶段丢失二轮目标；
- 修正口径后第二轮补检索能救回 75% 的 eligible CORE；
- 当前仍有 5 次补检索浪费在人工已知不可满足的需求上；
- 简单定位题明显强于边界与异常题。

### 9.2 目前不能证明的结论

- frozen 模式冻结了 Requirement、Query 和 Oracle，不能证明真实 LLM 规划在多次运行中稳定；
- 18 条 L1.5 加 5 条 regression 仍是小规模、单项目数据，不能代表所有 Java 项目；
- 路由在 L1 上 100% 正确，不能证明开放式用户表达中的来源判断也有 100% 准确率；
- Context Survival 高，不代表 Context 中没有无关证据，它只衡量已找到的 Gold 是否被保留；
- Full-case 成功不等于最终回答优质，叙事组织、引用使用和过度结论仍需 L2 评测；
- 当前报告没有证明任何生产优化已经提升了准确率，因为这一轮首先完成的是测量体系与基线。

Ground Truth 也需要维护。源码、文档或切块规则变化后，路径、符号和等价证据位置可能改变，人工标注必须重新复核；否则评测会把“真值过期”误认为“检索退化”。

## 10. 根据结果，下一步最值得做什么

第一优先级已经从“分析 9 条 no-gain”推进为处理两个已定位问题：对 `flow-02` 研究局部重排或更精确的符号匹配，对 `edge-01` 研究按 Requirement 和轮次保留新增 Gold 候选。不能直接提高全局 Top-K，因为 Top-6 对照实验已经出现等量回退。

第二优先级是减少 5 次不可满足需求的无效二轮动作。评测现已单独输出 `unanswerable_second_round_attempt_count`，后续可研究控制器能否根据明确的不可满足信号提前停止；这项优化影响的是成本与延迟，不应通过把未知需求草率判成不可满足来换取。

第三优先级是检查“Gold 已进入 Context，但 Package 仍为 PARTIAL”的案例，尤其是 REG-002。这类问题不是扩大召回能够解决的，应重点检查 Requirement 归属、Coverage 的输入证据范围和语义判定。

第四优先级是为 edge 类问题补充更细的失败分析。它们通常不是单个 Chunk 定位失败，而是多个失败分支和保证边界没有组合完整。可以考虑将过宽的证据需求拆成更可检验的目标，但必须避免重新变成机械式问题列表。

第五优先级是继续改善 MIXED 的双来源组合。L1 已经表明它是底层主要缺口；L1.5 则可验证来源配额、候选池或排序调整后，代码与文档是否真的一起存活到最终 Context。

第六优先级才是运行多次 live L1.5，分别测量 Planner 漏需求、Query 漂移和 Coverage 误判。frozen 基线应继续作为稳定回归，live 结果不能覆盖或替代 frozen 基线。

上述方向都应以新指标验证：如果某项改动只让平均 Recall 上升，却没有改善 Full-case、CORE Coverage 或 Rescue，甚至增加 False READY，就不能认为它真正提高了当前检索工作流的质量。

## 11. 总结

这次评测优化的核心，不是多加几个百分比，而是把不同阶段的责任分开测量：

```text
L1：固定 Query 能不能召回并排好目标证据？

Regression：5 条关键问题经过真实工作流后有没有退化？

L1.5：证据需求经过两轮检索、组合、Context 与 Coverage 后，
      是否真的形成了可信的 EvidencePackage？
```

当前数据表明，来源路由和 Context 保留机制已经产生了明确价值，系统也没有出现 False READY。修正后的 Rescue 指标进一步证明，第二轮在真正可救援的需求上多数有效；当前应分别处理候选排名、Context 存活、无效补查和 Coverage 偏保守，而不是把所有失败统一归因于 Query 改写。新的评测体系能够指出证据究竟丢在候选召回、排名组合、Context 选择还是 Coverage 判断阶段，这比一个孤立的 Recall@5 更接近真实产品质量。
