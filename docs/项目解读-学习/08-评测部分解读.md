# 一、评测在这个项目里解决什么问题

当前项目已经能够完成三种检索：

```text
keyword：关键词检索
vector：向量检索
hybrid：关键词 + 向量的 RRF 混合检索
```

但“程序能返回结果”不等于“返回的是正确结果”。

评测要回答的是：

1. 用户提出一个问题后，正确的代码或文档有没有被检索出来？
2. 正确结果排在第几名？
3. Top 3、Top 5 里覆盖了多少预期内容？
4. keyword、vector、hybrid 哪种检索效果更好？
5. 一次检索需要多长时间？
6. 修改分块、Embedding 文本、SQL 或 RRF 后，效果是变好还是退化？

因此，当前评测属于：

> 离线检索评测，英文通常称为 Offline Retrieval Evaluation。

“离线”表示评测使用事先准备好的问题和标准答案，不依赖真实用户在线反馈。

当前评测链路可以概括为：

```text
benchmark/cases.jsonl
        │
        │ 读取问题与相关结果标注
        ▼
Evaluation Runner
        │
        ├── keyword search
        ├── vector search
        └── hybrid search
        │
        ▼
判断 Top K 中哪些结果命中标注
        │
        ▼
计算 Recall@3 / Recall@5 / MRR / 平均延迟
        │
        ▼
artifacts/evaluation-*.json
```

主要文件：

- 评测集：[cases.jsonl](D:/Java-learning/DevContext/benchmark/cases.jsonl)
- 评测执行器：[runner.py](D:/Java-learning/DevContext/src/devcontext/evaluation/runner.py:1)

# 二、评测集 Benchmark 是什么

## 1. Benchmark 的含义

Benchmark 可以理解为一套固定的“考试题”。

每一条评测用例包含：

- 问题是什么
- 问题属于哪一种类型
- 哪些代码或文档算正确结果
- 一些人工备注

例如代码问题：

```json
{
  "id": "CODE-001",
  "question": "PurchaseTicketTxService.doPurchaseInTransaction 的事务购票实现在哪里？",
  "type": "CODE",
  "relevant": [
    {
      "source_type": "CODE",
      "symbol": "doPurchaseInTransaction"
    }
  ],
  "notes": "定位本地数据库购票事务方法"
}
```

文档问题：

```json
{
  "id": "DOC-001",
  "question": "项目为什么使用余票令牌桶和 Lua，它与数据库真实余票是什么关系？",
  "type": "DOCUMENT",
  "relevant": [
    {
      "source_type": "DOCUMENT",
      "path_contains": "D2-设计分析-余票令牌桶与Lua.md"
    }
  ],
  "notes": "令牌桶设计文档"
}
```

混合问题：

```json
{
  "id": "MIXED-001",
  "question": "purchaseTickets 购票写链路为什么先经过校验和令牌桶，相关代码在哪里？",
  "type": "MIXED",
  "relevant": [
    {
      "source_type": "CODE",
      "symbol": "purchaseTickets"
    },
    {
      "source_type": "DOCUMENT",
      "path_contains_any": [
        "P1购票写链路代码阅读指导.md",
        "面试复习框架.md",
        "S2C-2-令牌桶与Lua详解.md",
        "D2-设计分析-余票令牌桶与Lua.md"
      ]
    }
  ],
  "notes": "购票主流程代码与等价说明"
}
```

## 2. JSONL 是什么

评测文件采用 JSONL，而不是普通 JSON 数组。

JSONL 是 JSON Lines 的缩写，格式是：

```text
一行一个独立 JSON 对象
```

例如：

```jsonl
{"id":"Q1","question":"问题一","relevant":[...]}
{"id":"Q2","question":"问题二","relevant":[...]}
{"id":"Q3","question":"问题三","relevant":[...]}
```

它的优点是：

- 可以逐行读取
- 添加一条用例比较方便
- 单条损坏时比较容易定位
- 适合流式处理
- Git diff 清晰
- 不需要把整个文件包装成一个大数组

项目中的 `load_cases()` 就是逐行读取：

```python
return [json.loads(line) for line in handle if line.strip()]
```

# 三、评测用例中的重要字段

## 1. `id`

例如：

```json
"id": "CODE-001"
```

这是用例的唯一标识。

目前使用前缀区分问题类型：

```text
CODE-xxx
DOC-xxx
MIXED-xxx
```

它主要用于：

- 定位失败用例
- 比较不同版本报告
- 输出逐题结果
- 追踪某一个查询长期是否退化

建议后续保持 ID 稳定。即使修改问题措辞，也不要随意更换 ID，否则不方便做版本对比。

---

## 2. `question`

这是实际发送给检索系统的用户问题。

例如：

```json
"question": "UserLoginServiceImpl.login 的登录实现在哪里？"
```

评测器不会对问题做特殊处理，而是直接调用：

```python
service.search(strategy, case["question"], top_k=10)
```

也就是说，Benchmark 中问题的写法会直接影响评测结果。

如果问题中包含非常精确的方法名：

```text
UserLoginServiceImpl.login
```

关键词检索天然占优势。

如果问题是纯自然语言：

```text
用户登录失败后，系统如何处理登录状态？
```

向量检索可能更有优势。

所以，Benchmark 中问题的分布会影响最终结论。一个主要由精确标识符组成的测试集，会偏向关键词检索；一个主要由概念性自然语言组成的测试集，会偏向向量检索。

---

## 3. `type`

当前有三种类型：

```text
CODE
DOCUMENT
MIXED
```

它们的含义是：

| 类型 | 目标 |
|---|---|
| CODE | 主要寻找 Java 代码 |
| DOCUMENT | 主要寻找 Markdown 文档 |
| MIXED | 同时寻找代码和文档 |

需要特别注意：

> 当前 `type` 字段并没有参与程序逻辑。

评测器只是读取了它，但没有按照 `type` 分组统计，也没有使用它改变检索策略。

当前报告只输出三种检索策略的整体指标：

```text
keyword
vector
hybrid
```

没有自动输出：

```text
CODE Recall@5
DOCUMENT Recall@5
MIXED Recall@5
```

所以 `type` 目前更像人工分类标签，而不是实际参与计算的字段。

---

## 4. `relevant`

`relevant` 表示哪些结果属于正确结果。

在信息检索领域，这种人工标注通常称为：

> Relevance Judgment，相关性判断。

如果把所有查询和相关结果标注独立保存，这套数据也经常被称为：

> qrels，query relevance judgments。

当前项目没有使用正式 qrels 文件，而是把相关性标注直接放在每条 Benchmark 用例中。

---

## 5. `notes`

`notes` 是给开发者看的人工备注。

例如：

```json
"notes": "定位本地数据库购票事务方法"
```

它不参与任何指标计算。

它的作用主要是：

- 解释为什么添加这道题
- 说明预期检索意图
- 帮助人工检查结果
- 记录用例对应的业务场景

# 四、当前项目如何判断“检索结果命中”

核心逻辑在 `_matches()`：

```python
def _matches(result, relevant):
    ...
```

它支持以下匹配条件：

- `source_type`
- `path_contains`
- `path_contains_any`
- `symbol`
- `title_contains`

---

## 1. `source_type`

例如：

```json
{
  "source_type": "CODE"
}
```

表示只有代码 Chunk 才能命中。

如果结果是 Markdown 文档，即使内容很相关，也不会被判定为这个目标的命中结果。

当前值主要是：

```text
CODE
DOCUMENT
```

---

## 2. `path_contains`

例如：

```json
{
  "path_contains": "D2-设计分析-余票令牌桶与Lua.md"
}
```

判断方式是：

```python
relevant["path_contains"].lower() in result.file_path.lower()
```

也就是不区分大小写的子串匹配。

假设数据库结果路径是：

```text
5-后续开发规划/D2-设计分析-余票令牌桶与Lua.md
```

只要它包含：

```text
D2-设计分析-余票令牌桶与Lua.md
```

就算命中。

### 这里存在一个重要问题

当前文档匹配通常只检查文件路径，不检查文档标题层级。

也就是说，只要某个 Chunk 来自目标 Markdown 文件，就算命中，即使它来自一个不相关章节。

例如问题是：

```text
Lua 如何保证令牌扣减原子性？
```

评测目标只要求文件为：

```text
D2-设计分析-余票令牌桶与Lua.md
```

那么这个文件中的以下章节都可能被判定为命中：

```text
项目背景
测试说明
未来规划
Lua 原子性说明
```

因此，当前文档评测判断的粒度是“文件级”，还不是“章节级”。

这可能导致指标偏高。

---

## 3. `path_contains_any`

例如：

```json
{
  "path_contains_any": [
    "D4-设计分析-Feign移出事务与支付通知异步化.md",
    "D4-开发计划.md",
    "模块4-优化故事.md"
  ]
}
```

它表示多个路径是等价答案。

只要结果路径包含其中任意一个字符串，就算该目标命中。

逻辑相当于：

```text
路径匹配 A
或
路径匹配 B
或
路径匹配 C
```

这是一个 OR 条件。

它适合解决一个问题在多份文档中都有正确说明的情况。

例如：

```text
为什么 Feign 调用要移出数据库事务？
```

可能在以下文档中都被合理解释：

- 设计分析文档
- 开发计划
- 优化故事
- 面试总结

如果只认可其中一个文件，系统召回另一个正确文档时就会被错误判定为失败。

---

## 4. `symbol`

例如：

```json
{
  "symbol": "scanTimeoutOrder"
}
```

它要求：

```python
relevant["symbol"].lower() == result.symbol_name.lower()
```

也就是方法名或符号名必须完全相同，只忽略大小写。

这比模糊匹配严格，但当前仍存在粒度问题。

例如：

```text
UserLoginServiceImpl.login
```

Benchmark 当前只写：

```json
{
  "symbol": "login"
}
```

那么以下结果都可能被判定为命中：

```text
UserLoginServiceImpl.login
UserLoginService.login
UserLoginController.login
其他类中的 login
```

因为评测器没有同时检查：

```text
class_name
file_path
signature
```

所以当前代码 ground truth 也是偏宽松的。

一个更准确的标注应该是：

```json
{
  "source_type": "CODE",
  "path_contains": "UserLoginServiceImpl.java",
  "symbol": "login"
}
```

或者进一步加入：

```json
{
  "source_type": "CODE",
  "class_name": "UserLoginServiceImpl",
  "symbol": "login",
  "signature": "login(UserLoginReqDTO)"
}
```

不过当前 `_matches()` 还不支持 `class_name` 和 `signature`，需要后续扩展。

---

## 5. `title_contains`

例如：

```json
{
  "title_contains": "事务处理"
}
```

只要 Markdown Chunk 的当前标题中包含该文本，就算匹配。

但是当前 Benchmark 里主要使用路径匹配，`title_contains` 使用得比较少。

而且当前 SearchResult 没有返回完整 `heading_path`，因此不能表达：

```text
系统设计 > 订单模块 > 事务处理
```

只能检查当前标题。

---

## 6. 同一个目标中的字段是 AND 关系

假设 relevant 是：

```json
{
  "source_type": "CODE",
  "path_contains": "UserLoginServiceImpl.java",
  "symbol": "login"
}
```

那么结果必须同时满足：

```text
source_type 是 CODE
并且
路径包含 UserLoginServiceImpl.java
并且
symbol 等于 login
```

才能命中。

也就是：

```text
source_type AND path AND symbol
```

---

## 7. `path_contains_any` 内部是 OR 关系

例如：

```json
{
  "source_type": "DOCUMENT",
  "path_contains_any": [
    "A.md",
    "B.md"
  ]
}
```

逻辑是：

```text
source_type == DOCUMENT
AND
(path 包含 A.md OR path 包含 B.md)
```

---

## 8. `relevant` 列表代表多个需要覆盖的目标

MIXED 用例通常是：

```json
"relevant": [
  {
    "source_type": "CODE",
    "symbol": "purchaseTickets"
  },
  {
    "source_type": "DOCUMENT",
    "path_contains_any": [...]
  }
]
```

这表示两个相关性要求：

1. 找到代码
2. 找到文档

Recall 要达到 1.0，两个要求都要覆盖。

注意它与 `path_contains_any` 不同：

- `relevant` 中的两个对象表示两个需要分别覆盖的目标。
- `path_contains_any` 表示同一个目标存在多个可接受替代答案。

可以把它理解为：

```text
relevant 列表：目标 A AND 目标 B 都要覆盖
path_contains_any：路径 A OR 路径 B 命中一个即可
```

# 五、完整评测执行过程

评测入口是：

```powershell
devcontext evaluate
```

CLI 调用：

```python
report = evaluate(settings)
```

## 第一步：读取 Benchmark

默认路径：

```text
benchmark/cases.jsonl
```

每个非空行被解析为一个 Python 字典。

---

## 第二步：依次运行三种策略

代码固定执行：

```python
for strategy in ("keyword", "vector", "hybrid"):
```

也就是：

```text
先跑全部 keyword
再跑全部 vector
最后跑全部 hybrid
```

不是同一道题交替执行三种策略。

---

## 第三步：每道题返回 Top 10

执行逻辑：

```python
results = service.search(
    strategy,
    case["question"],
    top_k=10
)
```

因此，每个策略、每道题都会检索最多 10 条结果。

虽然最终主要计算 Recall@3 和 Recall@5，但返回 10 条是为了让 MRR 能够继续观察第 6～10 名。

---

## 第四步：记录耗时

使用：

```python
started = time.perf_counter()
results = service.search(...)
latency_ms = (time.perf_counter() - started) * 1000
```

`time.perf_counter()` 是适合测量持续时间的高精度单调时钟。

“单调”表示系统时钟被手动修改时，它不会突然倒退，所以比普通当前时间更适合性能测量。

---

## 第五步：计算单题指标

每道题会计算：

```text
Recall@3
Recall@5
Reciprocal Rank
Latency
```

并保存前 5 条结果。

---

## 第六步：计算策略平均值

每种策略的整体指标是：

```text
所有用例指标之和 / 用例数
```

12 道题权重相同。

这叫：

> Macro Average，宏平均。

即每个问题贡献相同权重，不管它是代码问题、文档问题还是混合问题。

---

## 第七步：写入报告

报告写入：

```text
artifacts/evaluation-时间戳.json
```

例如：

- [evaluation-20260922-165124.json](D:/Java-learning/DevContext/artifacts/evaluation-20260922-165124.json)

报告包括：

```json
{
```

# 六、Recall@K 详细解释

## 1. Top K 是什么

检索系统会返回一个有顺序的结果列表：

```text
第 1 名
第 2 名
第 3 名
...
第 K 名
```

Top 3 表示前三名，Top 5 表示前五名。

在 RAG 系统中，Top K 很重要，因为后续通常只会把前 K 个 Chunk 放入大模型上下文。

如果正确结果排在第 20 名，但 Context Builder 只读取前 5 名，那么对最终回答来说，它相当于没有被召回。

---

## 2. Recall 的基本含义

Recall 中文通常翻译为：

> 召回率。

标准思想是：

```text
召回率 = 被检索到的相关内容数量 / 所有应该检索到的相关内容数量
```

当前项目中：

```python
hits = sum(
    any(_matches(result, target) for result in results[:k])
    for target in relevant
)

return hits / len(relevant)
```

更准确地说，它计算的是：

> 前 K 条结果覆盖了多少个 relevant 要求。

所以当前指标其实更接近：

```text
目标覆盖率@K
```

而不一定是传统意义上的“相关文档召回率”。

---

## 3. 单目标问题

假设某个 CODE 用例只有一个目标：

```json
"relevant": [
  {
    "symbol": "scanTimeoutOrder"
  }
]
```

检索 Top 3：

```text
1. OrderTimeoutCloseJob
2. scanTimeoutOrder
3. 某篇设计文档
```

因为 `scanTimeoutOrder` 在前三名：

```text
命中目标数 = 1
目标总数 = 1

Recall@3 = 1 / 1 = 1.0
```

如果它排在第 4 名：

```text
Recall@3 = 0.0
Recall@5 = 1.0
```

---

## 4. MIXED 问题

假设 MIXED 用例要求：

```text
目标 1：代码 purchaseTickets
目标 2：相关购票设计文档
```

关键词 Top 5 全是代码：

```text
1. purchaseTickets 方法
2. purchaseTickets 接口
3. purchaseTickets Controller
4. PurchaseTicketService 类
5. PurchaseTicketServiceImpl 类
```

那么：

```text
代码目标：命中
文档目标：未命中

Recall@5 = 1 / 2 = 0.5
```

如果 Top 5 中同时有代码和文档：

```text
代码目标：命中
文档目标：命中

Recall@5 = 2 / 2 = 1.0
```

这正是当前 `MIXED-001` 的实际情况：

- keyword Recall@5 = 0.5
- vector Recall@5 = 0.5
- hybrid Recall@5 = 1.0

关键词偏向代码，向量偏向文档，混合检索将两边组合起来。

---

## 5. 整体 Recall 是如何算出来的

Keyword 的 12 条用例中：

- 10 条 Recall@5 = 1.0
- 2 条 MIXED 用例 Recall@5 = 0.5

所以：

```text
总分 = 10 × 1.0 + 2 × 0.5
     = 11

平均 Recall@5 = 11 / 12
               = 0.9167
```

报告四舍五入后是：

```text
0.917
```

---

## 6. Recall@3 和 Recall@5 如何一起看

如果：

```text
Recall@3 = 0.60
Recall@5 = 0.90
```

说明大多数正确结果能进入 Top 5，但很多结果排在第 4 或第 5 名。

如果：

```text
Recall@3 = 0.90
Recall@5 = 0.92
```

说明正确结果通常已经排在前三名，增加到五条的收益不大。

当前 Hybrid：

```text
Recall@3 = 0.833
Recall@5 = 1.000
```

说明：

- 前五名覆盖非常好。
- 但仍有一部分目标只出现在第 4～5 名。
- 后续如果 Context Builder 取 Top 5，效果很好。
- 如果产品只展示前三名，还需要优化排序。

---

# 七、MRR 详细解释

## 1. MRR 是什么

MRR 是：

> Mean Reciprocal Rank，平均倒数排名。

它关注的是：

> 第一个相关结果排在第几名。

对于一条查询，先计算 Reciprocal Rank：

```text
RR = 1 / 第一个相关结果的排名
```

例如：

| 第一个相关结果排名 | RR |
|---:|---:|
| 1 | 1.0 |
| 2 | 0.5 |
| 3 | 0.3333 |
| 4 | 0.25 |
| 5 | 0.2 |
| 6 | 0.1667 |
| 没找到 | 0 |

然后对所有查询的 RR 求平均：

```text
MRR = 所有查询 RR 的平均值
```

---

## 2. 代码中的实现

```python
def reciprocal_rank(results, relevant):
    for rank, result in enumerate(results, start=1):
        if any(_matches(result, target) for target in relevant):
            return 1.0 / rank
    return 0.0
```

它从第一名开始检查：

```text
第 1 名相关？是 → 返回 1
第 1 名不相关，第 2 名相关？是 → 返回 1/2
...
都不相关 → 返回 0
```

---

## 3. 实际例子：CODE-001

问题：

```text
PurchaseTicketTxService.doPurchaseInTransaction 的事务购票实现在哪里？
```

Keyword 前两名是：

```text
1. PurchaseTicketTxService 类 Chunk
2. doPurchaseInTransaction 方法 Chunk
```

Benchmark 只接受：

```text
symbol = doPurchaseInTransaction
```

所以：

```text
第一个相关结果排名 = 2
RR = 1 / 2 = 0.5
```

虽然类 Chunk 可能也有帮助，但按照当前标注，它不算目标结果。

---

## 4. 实际例子：Vector CODE-001

向量检索中，正确方法排到第 6 名：

```text
第一个相关结果排名 = 6
RR = 1 / 6
   ≈ 0.1667
```

所以：

```text
Recall@3 = 0
Recall@5 = 0
RR = 0.1667
```

这说明虽然 Top 5 没找到，但 Top 10 中找到了。

---

## 5. 实际例子：Hybrid DOC-004

相关文档第一次出现在第 4 名：

```text
Recall@3 = 0
Recall@5 = 1
RR = 1 / 4 = 0.25
```

这个例子很好地体现了三个指标的区别：

- Recall@3：前三名有没有覆盖
- Recall@5：前五名有没有覆盖
- RR：第一个正确结果具体排在第几名

---

## 6. 当前 MRR 实际上是 MRR@10

评测器只请求：

```python
top_k=10
```

因此，如果正确结果排在第 11 名，程序根本看不到它，就会计算为：

```text
RR = 0
```

所以当前报告虽然字段名是：

```text
mrr
```

更精确的命名应当是：

```text
MRR@10
```

---

## 7. MRR 对 MIXED 问题不够好

这是当前评测中很重要的一个问题。

假设 MIXED 问题要求：

```text
代码 + 文档
```

返回结果：

```text
1. 正确代码
2. 其他代码
3. 其他代码
4. 其他代码
5. 其他代码
```

此时：

```text
代码目标命中
文档目标未命中

Recall@5 = 0.5
MRR = 1.0
```

因为 MRR 只关心“第一个相关结果”，第一名的代码已经相关，所以直接得到 1.0。

这会掩盖“文档没有召回”的问题。

当前 `MIXED-001` 和 `MIXED-002` 的 keyword 结果正是如此：

```text
Recall@5 = 0.5
RR = 1.0
```

因此：

> 当前 MRR 适合衡量单一目标的首个命中排名，但不适合单独评价 MIXED 查询的完整覆盖程度。

对 MIXED 查询，更应该关注：

```text
code_hit@K
document_hit@K
both_sources_hit@K
```

# 八、平均延迟详细解释

## 1. Latency 是什么

Latency 是一次请求从开始到结束的耗时。

单位是毫秒：

```text
ms，millisecond
```

当前测量范围是：

```python
started = time.perf_counter()
results = service.search(...)
latency_ms = ...
```

因此它测量的是一次 `RetrievalService.search()` 的端到端耗时。

---

## 2. Keyword 延迟包含什么

Keyword 检索大致包括：

```text
解析查询中的英文标识符
  ↓
连接 PostgreSQL
  ↓
执行关键词 SQL
  ↓
读取结果
  ↓
构造 SearchResult
```

当前平均约：

```text
397 ms
```

---

## 3. Vector 延迟包含什么

Vector 检索大致包括：

```text
创建 Embedding 客户端
  ↓
通过网络调用百炼 Embedding API
  ↓
得到 1024 维查询向量
  ↓
连接 PostgreSQL
  ↓
执行 pgvector 余弦检索
  ↓
构造 SearchResult
```

当前平均约：

```text
466 ms
```

这个数字不是单纯的 PostgreSQL 向量查询时间。

它包含外部 Embedding API 的网络延迟，所以不能看到 466 ms 就认为“pgvector 很慢”。

---

## 4. Hybrid 延迟包含什么

Hybrid 执行流程是：

```text
查询文本 Embedding
  ↓
关键词检索
  ↓
向量检索
  ↓
RRF 融合
```

当前代码中关键词 SQL 和向量 SQL 是顺序执行，不是并行执行。

平均约：

```text
932 ms
```

它大致包含：

```text
Embedding 网络调用
+ keyword SQL
+ vector SQL
+ RRF 融合
```

RRF 本身只是在几十条结果上做字典累加和排序，耗时通常很小；主要耗时一般来自网络和数据库。

---

## 5. 当前“平均耗时”有什么局限

当前只是：

```text
12 次查询耗时相加 / 12
```

这叫算术平均值。

它不能反映：

- 最快请求
- 最慢请求
- 中位数
- 长尾延迟
- 网络抖动
- 冷连接与热连接差异
- Embedding API 的偶发高延迟

生产系统通常还会看：

### P50

50% 的请求低于这个耗时，也就是中位数。

### P95

95% 的请求低于这个耗时。

P95 更能反映大部分用户遇到的较慢体验。

### P99

99% 的请求低于这个耗时，主要观察长尾问题。

例如：

```text
平均值：500 ms
P50：300 ms
P95：1200 ms
P99：3000 ms
```

这说明虽然大多数请求较快，但少部分请求非常慢。

当前只有 12 个样本，计算 P95、P99 也没有很强的统计意义，所以后续应该对每个查询重复多次。

---

# 九、RRF 混合检索是什么

## 1. 为什么不能直接相加原始分数

Keyword 的分数可能是：

```text
symbol 精确匹配 12 分
class 精确匹配 10 分
signature 包含 6 分
similarity 0～1 分
```

Vector 的分数通常是：

```text
余弦相似度，例如 0.71、0.83、0.91
```

两个分数量纲完全不同。

不能简单做：

```text
keyword_score + vector_score
```

否则 keyword 的 12 分会轻易压过 vector 的 0.8 分。

---

## 2. RRF 的基本思想

RRF 不关心原始分数，只关心排名。

公式是：

```text
RRF(document) = Σ 1 / (k + rank)
```

当前：

```text
k = 60
```

如果一个 Chunk 在 keyword 排名第 1：

```text
1 / (60 + 1)
= 1 / 61
≈ 0.01639
```

如果在 vector 排名第 3：

```text
1 / (60 + 3)
= 1 / 63
≈ 0.01587
```

两路都召回时：

```text
总 RRF 分数
= 1/61 + 1/63
≈ 0.03226
```

如果另一个 Chunk 只在 keyword 第 1：

```text
分数只有 1/61
≈ 0.01639
```

因此两路都认为相关的结果，通常会排得更靠前。

---

## 3. 为什么 `k=60`

RRF 中的 `k` 是一个平滑常数。

如果没有 `k`：

```text
第 1 名 = 1
第 2 名 = 0.5
第 3 名 = 0.333
```

头部排名差距非常大。

加上 60 后：

```text
第 1 名 = 1/61 = 0.01639
第 2 名 = 1/62 = 0.01613
第 3 名 = 1/63 = 0.01587
```

差距更加平缓。

这意味着：

- 不会让某一路的第一名过度支配结果。
- 更重视“是否被多路检索共同召回”。
- 对不同检索器的排名波动更稳定。

60 是 RRF 中常见的经验值，但不是绝对最优值。是否调整应通过评测验证。

---

## 4. 当前候选池大小

Hybrid 会让关键词和向量检索分别返回：

```python
pool_size = max(20, top_k)
```

评测时 `top_k=10`，因此：

```text
Keyword 候选：20 条
Vector 候选：20 条
```

然后对最多约 40 个候选进行融合。

相同数据库 Chunk 会根据 `id` 去重。

最后返回融合后的 Top 10。

---

## 5. RRF 的稳定排序

如果两个结果 RRF 分数完全相同，当前使用数据库 ID 升序决定顺序：

```python
sorted(scores, key=lambda item: (-scores[item], item))
```

这样做叫：

> Deterministic Tie-breaking，确定性同分排序。

它能保证相同输入下结果顺序稳定，避免测试随机失败。

但数据库 ID 可能在全量重建后变化，因此跨索引版本仍可能出现同分结果顺序变化。

更稳定的选择可以是：

```text
file_path + symbol_name + start_line
```

# 十、当前评测结果如何解读

最新结果为：

| 策略 | Recall@3 | Recall@5 | MRR | 平均耗时 |
|---|---:|---:|---:|---:|
| Keyword | 0.917 | 0.917 | 0.875 | 397 ms |
| Vector | 0.542 | 0.667 | 0.586 | 466 ms |
| Hybrid | 0.833 | 1.000 | 0.771 | 932 ms |

---

## 1. Keyword：精确定位能力强

Keyword 的特点：

```text
Recall@3 = 0.917
Recall@5 = 0.917
MRR = 0.875
```

说明：

- 正确结果通常很靠前。
- 从 Top 3 增加到 Top 5 基本没有新增收益。
- 对带有精确方法名、类名的问题尤其有效。
- 首个相关结果通常排在第一名附近。

CODE 用例中，它能很好地识别：

```text
doPurchaseInTransaction
takeToken
scanTimeoutOrder
login
```

但它在 MIXED 查询中容易只返回代码。

例如 `MIXED-001` 前五名都是代码：

```text
1. purchaseTickets
2. purchaseTickets
3. purchaseTickets
4. PurchaseTicketService
5. PurchaseTicketServiceImpl
```

所以：

```text
代码命中
文档未命中
Recall@5 = 0.5
```

---

## 2. Vector：语义能力强，但精确符号定位不稳定

Vector 的结果：

```text
Recall@3 = 0.542
Recall@5 = 0.667
MRR = 0.586
```

它在精确代码符号问题上不如关键词检索。

例如：

```text
doPurchaseInTransaction
```

正确方法排在第 6 名。

```text
scanTimeoutOrder
```

正确方法排在第 4 名。

```text
login
```

正确方法大约排在第 7 名。

这是因为向量检索比较的是整体语义，而不是字符串完全相等。

它可能认为下面这些内容也很接近：

- 所在类
- 接口定义
- Controller 方法
- 描述该流程的文档
- 类似业务方法

向量检索的强项不是“精确找到这个方法名”，而是：

```text
用户没有给出准确名字时，仍然理解大概语义
```

---

## 3. Vector 的分数可能被不完整 ground truth 低估

`DOC-001` 问的是：

```text
为什么使用余票令牌桶和 Lua，它与数据库真实余票是什么关系？
```

向量 Top 5 包括：

- 三个“余票”的区别
- 展示余票和令牌余量为什么是两个 Key
- 高并发和限流
- Lua 取令
- 令牌桶的项目整体说明

这些结果在语义上明显相关。

但 Benchmark 只认可路径：

```text
D2-设计分析-余票令牌桶与Lua.md
```

这个目标文件第一次可能出现在第 7 名，于是：

```text
Recall@5 = 0
RR = 1/7
```

这说明低分有两种可能：

1. 检索真的没有找到相关内容。
2. 检索找到了合理内容，但 Benchmark 没有把它标为可接受答案。

第二种情况叫：

> Ground Truth 不完整。

因此，评测失败不一定总是检索失败，也可能是标注失败。

---

## 4. Hybrid：Top 5 覆盖最好

Hybrid：

```text
Recall@3 = 0.833
Recall@5 = 1.000
MRR = 0.771
```

说明：

- 所有标注目标都能在 Top 5 范围内找到。
- Keyword 和 Vector 的互补确实发挥了作用。
- 但部分结果只是排到第 4～5 名。
- 首位排序不如 Keyword，因此 MRR 更低。
- 延迟明显更高。

Hybrid 对 RAG 上下文构造很适合，因为 RAG 通常需要多个候选 Chunk，而不是只需要第一名。

---

## 5. 为什么 Hybrid Recall@5 更高，但 MRR 更低

这是一个非常重要的现象：

```text
Keyword:
  Recall@5 = 0.917
  MRR = 0.875

Hybrid:
  Recall@5 = 1.000
  MRR = 0.771
```

它表示：

- Hybrid 找全内容的能力更强。
- Keyword 把第一个正确结果排在最前面的能力更强。

例如一个混合问题：

```text
Keyword:
1. 正确代码
2. 代码
3. 代码
4. 代码
5. 代码

Hybrid:
1. 正确代码
2. 代码
3. 代码
4. 正确文档
5. 代码
```

Keyword：

```text
MRR = 1
Recall@5 = 0.5
```

Hybrid：

```text
MRR = 1
Recall@5 = 1
```

另一个纯代码问题可能是：

```text
Keyword:
1. 正确方法

Hybrid:
1. 所在类
2. 正确方法
```

Keyword：

```text
RR = 1
```

Hybrid：

```text
RR = 0.5
```

这就可能导致 Hybrid 整体 MRR 下降，但混合覆盖提升。

选择哪个指标更重要，取决于产品用途：

- 如果用户只点击第一条搜索结果，MRR 很重要。
- 如果系统将 Top 5 交给大模型构造答案，Recall@5 更重要。
- 如果问题要求同时找到代码和文档，普通 MRR 不够，需要双来源覆盖指标。

# 十二、当前评测有哪些技术局限

## 1. 用例数量太少

当前只有 12 条：

```text
CODE：4
DOCUMENT：4
MIXED：4
```

一条用例就会明显改变总体指标。

对于单目标题：

```text
1 / 12 ≈ 0.0833
```

也就是说，只增加或减少一条成功用例，总体指标可能变化约 8.3 个百分点。

因此：

```text
Recall@5 = 1.0
```

只能说明当前 12 条题全部命中，不能说明面对真实用户问题也有接近 100% 的召回率。

---

## 2. 问题分布偏向精确标识符

很多 CODE 和 MIXED 问题直接包含：

```text
doPurchaseInTransaction
takeToken
scanTimeoutOrder
login
purchaseTickets
notifyPayResult
```

这对 Keyword 非常有利。

还缺少这些问题：

```text
购票时如何保证本地库存一致性？
系统在哪里关闭长期未支付的订单？
用户登录状态是怎样被校验的？
支付成功后如果通知订单服务失败怎么办？
```

这类问题没有准确方法名，更能验证语义检索价值。

---

## 3. 文档标注粒度太粗

当前通常只标文件路径，不标章节。

可能出现：

```text
命中了正确文件
但命中了错误章节
```

评测仍然认为正确。

这属于可能的“假阳性”。

### 假阳性 False Positive

系统实际上没有返回足够相关的 Chunk，但评测规则过宽，把它判成了命中。

---

## 4. 标注范围不完整

一份新文档可能同样能够正确回答问题，但没有加入 `path_contains_any`。

系统召回了它，评测仍然判错。

这属于可能的“假阴性”。

### 假阴性 False Negative

系统返回了实际相关结果，但评测标注没有认可它，因此被判为失败。

---

## 5. 代码标注没有限定所属类

例如：

```text
UserLoginServiceImpl.login
```

当前只标注：

```json
{"symbol":"login"}
```

接口、Controller 或其他类的 `login` 也可能被判定为正确。

建议至少使用：

```text
file_path + class_name + symbol_name
```

对于重载方法，再加入：

```text
signature
```

---

## 6. 报告只保存 Top 5

评测实际检索 Top 10：

```python
top_k=10
```

但报告只保存：

```python
results[:5]
```

这会产生一个审计问题。

例如：

```text
Recall@5 = 0
RR = 1/6
```

我们可以根据 RR 推断正确结果在第 6 名，但报告没有保存第 6 名的具体内容。

建议报告保存完整 Top 10，至少保存：

```text
rank
chunk id
file path
symbol/title
score
matched target
```

---

## 7. 没有保存各检索器的中间排名

Hybrid 结果只保存最终 RRF 分数，没有保存：

```text
keyword_rank
keyword_score
vector_rank
vector_similarity
rrf_score
```

因此看到某个 Hybrid 结果排在第 2 名时，很难知道：

- 它是关键词第 1、向量没召回？
- 关键词第 8、向量第 2？
- 两路都排在中间，但叠加后上升？
- 它为什么超过另一个结果？

这限制了可解释性和调参效率。

---

## 8. 没有无答案问题

当前每道题都有相关结果。

还缺少：

```text
这个项目使用 Kafka 处理订单了吗？
项目是否实现了 Elasticsearch？
系统中的退款审批工作流在哪里？
```

如果这些内容不存在，检索系统应该能够表现出低置信度，而不是始终返回看似相关的结果。

这种测试通常称为：

> Unanswerable Query，无法从当前知识库回答的问题。

虽然检索系统总会返回最相似项，但上层应根据分数或证据判断“知识库中没有足够答案”。

---

## 9. 没有重复运行

当前每个查询每种策略只运行一次。

对于外部 Embedding API，耗时可能受以下因素影响：

- 网络抖动
- DNS
- TLS 建连
- 服务端排队
- 连接复用
- API 限流
- 数据库冷缓存

单次结果不足以稳定衡量性能。

---

# 十三、为什么当前没有 Precision@K

## 1. Precision 的含义

Precision 中文通常称为：

> 准确率或查准率。

公式是：

```text
Precision@K =
Top K 中相关结果数量 / K
```

例如 Top 5 中有 3 个相关结果：

```text
Precision@5 = 3 / 5 = 0.6
```

Recall 关心“该找的是否找全”，Precision 关心“返回的结果有多少是真的相关”。

---

## 2. 当前为什么不适合直接计算 Precision

当前 ground truth 并没有穷举所有相关 Chunk。

例如问题：

```text
为什么使用余票令牌桶和 Lua？
```

数据库中可能有几十个相关章节，但 Benchmark 只标注了几个文件路径。

如果 Top 5 返回了五个实际相关 Chunk，只有一个在标注路径中，那么程序可能计算：

```text
Precision@5 = 1 / 5 = 0.2
```

但人工检查可能发现五个都相关。

所以，在 ground truth 不完整时，Precision 很容易低估系统。

要引入可靠的 Precision，需要：

- 对 Top K 候选进行更完整的人工相关性标注
- 或者使用固定候选池做人工判断
- 或者采用分级相关性评价

---

# 十四、后续值得增加的指标

## 1. Hit@K / Success@K

含义：

```text
Top K 中只要有一个相关结果，就是 1，否则为 0
```

公式：

```text
Hit@K =
1，如果 Top K 至少命中一个目标
0，否则
```

对单目标 CODE/DOCUMENT 问题，它和当前 Recall@K 常常相同。

---

## 2. All Targets Hit@K

对 MIXED 问题尤其重要：

```text
所有必需目标是否都在 Top K 中出现
```

例如代码和文档都出现：

```text
all_targets_hit@5 = 1
```

只出现代码：

```text
all_targets_hit@5 = 0
```

相比当前 0.5 的 Recall，它更直接表示“这个混合问题是否完整完成”。

---

## 3. Code Hit@K 和 Document Hit@K

对 MIXED 问题分别计算：

```text
code_hit@K
document_hit@K
```

例如：

```json
{
  "code_hit_at_5": true,
  "document_hit_at_5": false,
  "both_sources_hit_at_5": false
}
```

这样可以清楚判断是代码侧还是文档侧漏召回。

---

## 4. nDCG@K

nDCG 是：

> Normalized Discounted Cumulative Gain，归一化折损累计增益。

它适用于“相关性不是简单的正确/错误，而是有等级”的情况。

例如人工标注：

```text
3 分：直接回答问题的核心 Chunk
2 分：高度相关的辅助 Chunk
1 分：有一定关联
0 分：无关
```

nDCG 同时考虑：

- 结果是否相关
- 相关程度
- 排名位置

高相关结果排在前面得分更高。

它比二元 Recall 更适合评估：

```text
正确方法
所在类
接口定义
相关设计文档
外围说明
```

因为这些结果并不是简单的“都正确”或“都错误”。

---

## 5. MAP

MAP 是：

> Mean Average Precision，平均平均准确率。

它关心一条查询中多个相关结果在整个排名列表中的分布。

但它要求 ground truth 相对完整。当前项目暂时不适合直接使用，因为相关 Chunk 没有穷举。

---

## 6. Source Diversity

可以统计 Top K 来源多样性：

```text
Java Chunk 数量
Markdown Chunk 数量
不同文件数量
重复类数量
重复章节数量
```

这能发现：

```text
Top 5 全来自同一个类
Top 5 全来自同一个 Markdown 文件
Top 5 都是同一个方法的接口、实现和 Controller
```

对 Context Builder 来说，这种重复可能浪费上下文空间。

---

## 7. Duplicate Rate

例如 Top 5 中有：

```text
PurchaseTicketService.purchaseTickets
PurchaseTicketServiceImpl.purchaseTickets
TicketController.purchaseTickets
PurchaseTicketService 类
PurchaseTicketServiceImpl 类
```

虽然数据库 ID 不同，但语义可能高度重复。

可以定义：

```text
duplicate_rate@K
```

用于衡量上下文冗余。

---

## 8. P50/P95 延迟

建议至少增加：

```text
p50_latency_ms
p95_latency_ms
max_latency_ms
```

同时拆分：

```text
embedding_latency_ms
keyword_db_latency_ms
vector_db_latency_ms
fusion_latency_ms
total_latency_ms
```

# 十六、评测、单元测试和集成测试的区别

这三者不能相互替代。

## 1. 单元测试

例如：

```python
assert recall_at(results, relevant, 1) == 0.5
```

它验证：

- Recall 公式有没有写错
- 多目标是否正确计算
- 替代路径是否正确识别
- RRF 是否去重
- 同分排序是否稳定

单元测试回答：

> 评测程序本身是否按照设计工作？

它不回答检索质量是否好。

---

## 2. 集成测试

数据库集成测试验证：

- PostgreSQL 能连接
- Schema 正确
- Chunk 能写入
- Keyword SQL 能执行
- Vector SQL 能执行
- 事务能工作

它回答：

> 多个组件连接起来能否正常运行？

它也不直接回答结果是否符合真实用户需求。

---

## 3. Benchmark 评测

Benchmark 使用真实项目问题和真实索引数据。

它回答：

> 检索系统返回的内容质量怎么样？

所以：

```text
单元测试通过 ≠ 检索质量好
集成测试通过 ≠ 检索质量好
Benchmark 高分 ≠ 所有真实问题都表现好
```

三者分别保证不同层面。

---

# 十八、如何正确理解当前评测结论

当前结果能够支持以下结论：

1. 三种检索链路都已经正常运行。
2. Keyword 很适合精确 Java 标识符查询。
3. Vector 能提供语义召回，但精确方法定位不稳定。
4. Keyword 和 Vector 具有明显互补性。
5. Hybrid 在当前 12 条问题上实现了完整 Top 5 目标覆盖。
6. Hybrid 延迟高于单路检索。
7. MIXED 查询中，Keyword 容易偏代码，Vector 有时偏文档。
8. RRF 能有效整合两路结果。

当前结果不能支持以下结论：

1. 不能证明真实用户问题的 Recall@5 接近 100%。
2. 不能证明所有 Java 类、方法和文档都能正确检索。
3. 不能证明 Hybrid 在更大数据规模下仍保持同样延迟。
4. 不能证明 Vector 质量差，因为部分 ground truth 不完整。
5. 不能证明文档章节精确命中，因为当前主要是文件级匹配。
6. 不能证明回答质量，因为目前还没有 Context Builder 和 LLM 答案生成。
7. 不能证明引用准确性，因为评测尚未检查最终引用。

# 总结

当前项目的评测系统已经形成了一个完整的基础闭环：

```text
固定问题
  ↓
标注相关代码/文档
  ↓
运行三种检索
  ↓
检查 Top 3 / Top 5
  ↓
计算 Recall、MRR 和延迟
  ↓
保存逐题报告
```

几个最重要的概念可以这样记：

| 名词 | 简单理解 |
|---|---|
| Benchmark | 固定考试题集合 |
| Ground Truth | 人工定义的标准答案 |
| Relevant | 哪些检索结果算相关 |
| Top K | 只观察前 K 个结果 |
| Recall@K | 前 K 个结果覆盖了多少预期目标 |
| RR | 第一个正确结果排名的倒数 |
| MRR | 所有问题 RR 的平均值 |
| Latency | 一次检索的端到端耗时 |
| RRF | 根据多路排名融合结果，不直接混合原始分数 |
| Macro Average | 每道题权重相同后求平均 |
| False Positive | 实际不够相关，但评测判定命中 |
| False Negative | 实际相关，但评测标注没有认可 |
| qrels | 查询与相关结果的人工标注集合 |

当前最关键的认识是：

> Hybrid Recall@5 = 1.0 是一个很好的 MVP 信号，但它只是“当前 12 条、当前标注规则下全部命中”，不是系统检索质量已经达到 100%。

下一步最应该做的是：

> 扩大 Benchmark、提高 ground truth 粒度、增加 MIXED 双来源指标、保存完整检索排名和中间分数。

完成这些后，评测才会从“验证功能跑通”升级为“能够可靠指导检索算法开发”。
