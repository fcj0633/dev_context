# 第 3 章：Java 仓库如何被转换成 Symbol Graph

前两章我们解决了两个问题：

第一，为什么需要 Symbol Graph——因为普通 RAG 擅长文本相关性，却不擅长确定性的程序关系。

第二，Symbol Graph 要表示什么——用 `CLASS / INTERFACE / METHOD / CONSTRUCTOR` 作为程序实体，用 `EXTENDS / IMPLEMENTS / CALLS / CONSTRUCTS / OVERRIDES` 表示静态程序关系。

现在进入第三个问题：

> **我们已经知道“最终想要的图长什么样”，那怎么从几十上百个 Java 文件里可靠地构造出这张图？**

这一章最重要的不是 JavaParser API，而是理解三个设计思想：

```text
语法结构解析
        ↓
程序符号解析
        ↓
Repository 级两阶段分析
```

也就是：

> **AST 告诉我们代码“写成什么样”；SymbolSolver 告诉我们这些名字“究竟指向谁”；Two-Pass Analysis 再把整个仓库的实体和关系连接起来。**

---

# 一、为什么不能简单地“扫描源码字符串”

先看一个最简单的调用：

```java
public void create() {
    orderService.createOrder(request);
}
```

如果我们只做文本分析，可以看到：

```text
orderService
createOrder
request
```

于是可能想：

> 搜索仓库里所有叫 `createOrder` 的方法不就行了吗？

问题是，一个真实 Java 项目里可能存在：

```java
OrderService.createOrder(...)
OrderServiceImpl.createOrder(...)
MockOrderService.createOrder(...)
OrderController.createOrder(...)
```

还可能存在重载：

```java
createOrder(OrderRequest req)

createOrder(String orderSn)

createOrder(OrderRequest req, UserContext context)
```

单看：

```text
createOrder
```

根本无法知道这次调用的目标。

所以 Symbol Graph 不能建立在：

> **字符串匹配**

之上。

它需要理解 Java 语言本身。

---

# 二、第一层能力：AST 解决“代码的结构是什么”

这就是 JavaParser 首先发挥作用的地方。

源码：

```java
public class OrderServiceImpl {

    public void closeOrder(String orderSn) {
        releaseSeat(orderSn);
    }
}
```

对于人来说很简单，但程序首先需要把这段文本变成结构。

大致可以抽象成：

```text
CompilationUnit
│
└── ClassDeclaration
    │
    └── MethodDeclaration
        name = closeOrder
        │
        ├── Parameter
        │   └── String orderSn
        │
        └── MethodCallExpr
            ├── name = releaseSeat
            └── argument = orderSn
```

这就是：

```text
AST
Abstract Syntax Tree
抽象语法树
```

它把：

```text
一整段字符串
```

变成：

```text
有类型的程序节点。
```

---

# 三、为什么 AST 已经比文本搜索强很多

有 AST 后，我们至少知道：

```text
这是一个类

这是一个方法

这是一个构造器

这是一个方法调用

这是一个 new 表达式

这是 extends

这是 implements
```

例如：

```java
class OrderServiceImpl extends BaseService
        implements OrderService {
}
```

AST 可以直接告诉系统：

```text
ClassOrInterfaceDeclaration

extendedTypes:
BaseService

implementedTypes:
OrderService
```

所以：

```text
EXTENDS
IMPLEMENTS
```

这两类关系已经比文本匹配可靠很多。

但是问题还没有完全解决。

---

# 四、AST 最大的不足：它知道“名字”，却不一定知道“名字指向谁”

来看一个例子：

```java
public void createOrder(OrderRequest req) {
    service.save(req);
}
```

AST 能告诉你：

```text
MethodCallExpr
name = save

scope = service
argument = req
```

但它未必单独知道：

```text
service 是哪个类型？
```

更不知道：

```text
save 到底是哪一个具体声明？
```

可能仓库里同时有：

```java
OrderService.save(OrderRequest)

UserService.save(UserDTO)

CacheService.save(Object)

AbstractService.save(T)
```

所以：

```text
AST
```

主要解决：

> **语法结构。**

但 Symbol Graph 还需要解决：

> **语义身份。**

这就是 SymbolSolver 的作用。

---

# 五、SymbolSolver 解决的核心问题：名字绑定

可以把 SymbolSolver 理解成一个：

> **Java 名字解析器。**

例如：

```java
service.save(req);
```

它会结合：

```text
变量声明
import
package
继承关系
接口
方法重载
参数类型
泛型
```

最终尝试回答：

```text
这个 save
究竟对应哪个 Method Declaration？
```

如果成功，可能得到：

```text
edu.swu.xxx.OrderService
    #save(OrderRequest)
```

这时系统才真正有资格建立：

```text
CurrentMethod
    ↓ CALLS
OrderService#save(OrderRequest)
```

---

# 六、所以 JavaParser 和 SymbolSolver 的职责要分开理解

这是本章最重要的一组概念。

可以记成：

```text
JavaParser
解决：
“这是什么语法结构？”

SymbolSolver
解决：
“这个名字究竟指向哪个声明？”
```

例如：

```java
new ServiceException("error")
```

JavaParser 告诉你：

```text
这是 ObjectCreationExpr
```

SymbolSolver 告诉你：

```text
它对应的是：
ServiceException#<init>(String)
```

然后 Symbol Graph 才能建立：

```text
CurrentMethod
    ↓ CONSTRUCTS
ServiceException#<init>(String)
```

---

# 七、为什么 Symbol Graph 必须是 Repository-level Analysis

假设只有两个文件。

`OrderController.java`：

```java
public class OrderController {

    private OrderService orderService;

    public void create(OrderRequest req) {
        orderService.createOrder(req);
    }
}
```

`OrderService.java`：

```java
public interface OrderService {

    void createOrder(OrderRequest req);
}
```

如果只孤立解析：

```text
OrderController.java
```

那么里面出现：

```text
OrderService
OrderRequest
```

但这些类型定义可能根本不在这个文件。

要解析：

```text
orderService.createOrder(req)
```

系统必须能够看到：

```text
整个源码根目录。
```

所以不能：

```text
一份文件
↓
单独 JavaParser
↓
单独 Symbol Graph
```

而应该：

```text
整个 Repository
↓
建立统一类型解析环境
↓
解析所有 Java 文件
```

这就是：

> **Repository-level Analysis。**

---

# 八、多模块项目让这个问题更明显

像当前分析的 Java 项目通常不是：

```text
project/
└── src/main/java
```

而可能是：

```text
project/
├── order-service/
│   └── src/main/java
│
├── pay-service/
│   └── src/main/java
│
├── user-service/
│   └── src/main/java
│
└── common/
    └── src/main/java
```

于是类型可能跨模块引用：

```text
order-service
       ↓
common
```

如果 Analyzer 只知道：

```text
order-service/src/main/java
```

很多类型就解析不出来。

因此当前实现首先做的一个重要步骤是：

> **发现仓库里所有 `src/main/java` Source Root。**

然后把这些 Source Root 统一交给类型解析器。

---

# 九、Source Root 为什么重要

假设文件：

```text
order-service/src/main/java/
    edu/swu/order/service/OrderService.java
```

源码：

```java
package edu.swu.order.service;
```

Java 类型系统认为：

```text
edu.swu.order.service.OrderService
```

对应：

```text
Source Root
+
edu/swu/order/service/OrderService.java
```

所以类型解析器需要知道：

```text
order-service/src/main/java
```

是：

> 包结构开始的根。

它不能简单把整个 repository root 当 Source Root。

---

# 十、当前 Repository Type Environment 可以怎么理解

最终系统大致建立：

```text
CombinedTypeSolver
│
├── SourceRoot 1
│   └── JavaParserTypeSolver
│
├── SourceRoot 2
│   └── JavaParserTypeSolver
│
├── SourceRoot 3
│   └── JavaParserTypeSolver
│
└── ReflectionTypeSolver
```

这里不需要记 API，理解设计即可。

---

## JavaParserTypeSolver

负责：

```text
当前 Repository 自己的源码类型
```

比如：

```text
OrderService
PayService
OrderDO
BaseDO
```

---

## ReflectionTypeSolver

主要帮助解析：

```text
JDK 类型
```

比如：

```text
String
Object
List
RuntimeException
```

---

所以：

```text
CombinedTypeSolver
```

本质就是：

> **“如果遇到一个 Java 类型，我应该去哪里找它？”**

---

# 十一、为什么当前 V1 不追求完整 Maven Classpath

理论上，还可以加入：

```text
Spring JAR
MyBatis JAR
RocketMQ JAR
Lombok generated code
第三方 dependency
```

这样 SymbolSolver 能解析更多调用。

但是当前 V1 没有追求：

```text
100% Java Compiler 级别解析。
```

这是一个重要设计取舍。

因为 Symbol Graph 的目标不是：

> 完全替代 javac。

而是：

> **可靠地提取 Repository 内部最重要的结构关系。**

如果为了补齐所有第三方 dependency，系统马上会复杂很多：

```text
Maven dependency tree
版本冲突
generated sources
annotation processor
Lombok
module classpath
```

开发成本会迅速上升。

---

# 十二、因此当前设计选择“精度优先于召回”

假设：

```java
rocketMQTemplate.syncSend(...);
```

如果当前 TypeSolver 无法可靠解析：

```text
RocketMQTemplate.syncSend
```

系统不会：

```text
根据方法名猜一条 CALLS。
```

而是：

```text
记录 unresolved
不建 Edge
```

所以 Graph 可能：

```text
少一条边
```

但不会：

```text
多一条假的边。
```

这就是当前 Symbol Graph 很核心的设计哲学：

> **对于程序关系，错误事实比缺失事实更危险。**

因为缺失时系统还能说：

```text
证据不足。
```

但错误 Edge 会让系统非常自信地：

```text
沿着错误路径继续搜索。
```

---

# 十三、接下来进入第二个核心设计：为什么采用 Two-Pass Analysis

假设仓库：

```text
A.java
B.java
C.java
```

一种最简单的实现是：

```text
读 A
→ 建 A 的 Symbol
→ 建 A 的 Edge

读 B
→ 建 B 的 Symbol
→ 建 B 的 Edge

读 C
→ ...
```

这叫：

```text
Single-Pass
```

看起来最自然。

但是对于 Graph 构建并不理想。

---

# 十四、Single-Pass 最大的问题：关系目标可能还没有成为图节点

例如文件顺序：

```text
Controller.java
Service.java
ServiceImpl.java
```

先处理：

```text
Controller.java
```

发现：

```text
Controller#create
    CALLS
Service#create
```

SymbolSolver 也许已经能解析：

```text
Service#create
```

但是当前 Graph Registry 中：

```text
Service#create
```

可能还没正式登记为 Symbol。

于是系统面临一个问题：

> 我要不要创建这条 Edge？

如果直接创建：

```text
target 现在不存在。
```

如果先跳过：

```text
后面还要补边。
```

如果创建临时节点：

```text
系统复杂度增加。
```

---

# 十五、Two-Pass 的思想非常简单

把：

```text
发现实体
```

和：

```text
建立关系
```

分开。

第一阶段：

```text
Pass 1

扫描整个 Repository
        ↓
找到所有可可靠识别的 Symbol
        ↓
建立 Symbol Table
```

第二阶段：

```text
Pass 2

再次遍历 AST
        ↓
解析 Symbol 之间的关系
        ↓
建立 Edge
```

也就是：

```text
先问：
“图里有哪些节点？”

再问：
“这些节点之间有哪些边？”
```

---

# 十六、为什么这是一种非常常见的工程思想

其实很多系统都使用类似设计。

编译器：

```text
先收集声明
再做名称绑定 / 类型检查
```

数据库导入：

```text
先插实体
再建立 Foreign Key
```

知识图谱：

```text
先 Entity Resolution
再 Relation Resolution
```

当前 Symbol Graph 也是：

```text
Pass 1
Symbol Resolution

Pass 2
Relation Resolution
```

根本原因都一样：

> **关系依赖实体先存在。**

---

# 十七、Pass 1 的目标不是“解析所有 Java 代码”

这一点容易误解。

第一遍并不关心：

```text
A 调 B
B 调 C
```

它只需要解决：

> **当前 Repository 中有哪些稳定的程序实体？**

例如得到：

```text
T:OrderController

M:OrderController#create(...)

T:OrderService

M:OrderService#createOrder(...)

T:OrderServiceImpl

M:OrderServiceImpl#createOrder(...)
```

这些实体组成：

```text
Repository Symbol Table
```

后面所有 Edge 都必须引用其中的 Symbol。

---

# 十八、Symbol Table 的意义

可以把它理解成：

```text
symbol_key
        ↓
Symbol metadata
```

例如：

```text
M:xxx.OrderService#createOrder(Request)
        ↓
{
  kind: METHOD,
  owner: OrderService,
  chunk: ...,
  file: ...,
  lines: ...
}
```

所以后面得到一个目标声明：

```text
OrderService#createOrder(Request)
```

就能问：

```text
它是不是当前 Repository 内部 Symbol？
```

如果是：

```text
可以建 Edge。
```

如果不是：

```text
不进入内部 Graph。
```

---

# 十九、这一步还顺便定义了“Graph 的世界边界”

这是非常关键的。

假设代码：

```java
public void foo() {
    log.info("...");
}
```

SymbolSolver 成功解析：

```text
Logger.info(String)
```

但是：

```text
Logger
```

来自外部依赖。

它不在当前：

```text
Repository Symbol Table
```

所以不会建立：

```text
foo
 ↓ CALLS
Logger.info
```

---

为什么？

因为当前 Graph 的目标是：

> **Repository-internal graph**

不是：

> JVM 世界里所有能解析到的类型。

否则每个方法都会连出：

```text
String
List
Map
Logger
Objects
Collectors
Spring
...
```

图会迅速变成第三方 API 依赖图。

噪声巨大。

---

# 二十、所以“能 resolve”还不等于“应该入图”

这是本章非常重要的一句话。

SymbolSolver 回答：

> 这个调用目标是谁？

Graph Builder 还要再回答：

> **这个目标是不是当前 Repository 希望建模的内部 Symbol？**

完整判断大概是：

```text
Method Call
    ↓
能不能 resolve？
    │
    ├── 不能
    │     → unresolved
    │
    └── 能
          ↓
    是否 Repository 内部？
          │
          ├── 否
          │    → external，跳过
          │
          └── 是
                ↓
         是否已经建立 Symbol？
                │
                ├── 是 → Edge
                └── 否 → internal_target_not_indexed
```

这个流程非常值得记。

---

# 二十一、`internal_target_not_indexed` 为什么单独存在

例如当前 V1 不完整建模：

```text
record generated accessor
```

假设：

```java
record User(String name) {}
```

调用：

```java
user.name();
```

SymbolSolver 可能知道：

```text
User#name()
```

确实属于当前 Repository。

但 V1 的 Symbol Table 可能没有：

```text
M:User#name()
```

这个节点。

这时候不能记成：

```text
external
```

因为它明明是内部代码。

也不能记成：

```text
unresolved
```

因为 SymbolSolver 已经解析出来了。

所以单独：

```text
internal_target_not_indexed
```

表示：

> **程序关系解析成功，但当前 Graph Schema 没有为这个目标建节点。**

这个指标以后特别适合指导 V2：

> “是不是值得增加 Record / Enum / generated member 支持？”

---

# 二十二、Pass 2 才真正开始构建 Edge

现在 Symbol Table 已经完整。

第二阶段才遍历：

```text
extends

implements

method calls

new expressions

method hierarchy
```

生成：

```text
EXTENDS
IMPLEMENTS
CALLS
CONSTRUCTS
OVERRIDES
```

此时每条 Edge 都要求：

```text
source Symbol 已存在
target Symbol 已存在
```

所以 Graph 天然不会出现：

```text
悬空 Edge。
```

---

# 二十三、为什么 CALLS 需要 SymbolSolver，而 EXTENDS 看起来不太需要？

例如：

```java
class A extends B
```

AST 已经直接告诉：

```text
B
```

但仍然需要 SymbolSolver。

因为仓库里可能存在：

```text
com.foo.B

com.bar.B
```

源码通过：

```java
import com.foo.B;
```

决定具体继承谁。

AST 上的文字：

```text
B
```

不够。

所以即使：

```text
EXTENDS / IMPLEMENTS
```

看起来简单，

最终也应该解析成：

```text
Fully Qualified Type
```

而不是简单名称。

---

# 二十四、为什么 CALLS 更复杂

方法调用还涉及：

```text
方法重载
继承方法
泛型
变量静态类型
import
参数类型
```

例如：

```java
foo(null);
```

或者：

```java
service.execute(request);
```

单靠 AST 几乎不能稳定判断目标。

所以：

```text
CALLS
```

尤其依赖：

```text
SymbolSolver
```

的声明解析。

---

# 二十五、OVERRIDES 为什么是最复杂的一条 Edge

假设：

```java
interface Api<T> {
    T convert(T value);
}
```

然后：

```java
class StringApi implements Api<String> {

    public String convert(String value) {
        ...
    }
}
```

如果只比较源码：

```text
convert(T)

convert(String)
```

会发现：

```text
参数不一样。
```

但 Java 类型系统知道：

```text
Api<String>
```

里：

```text
T = String
```

所以这两个方法实际上：

```text
存在 override。
```

这就是为什么 `OVERRIDES` 不能靠：

```text
同名 + 参数数量
```

来判断。

---

# 二十六、这里才需要少量深入当前实现

当前 OVERRIDES 的设计大致是：

```text
拿到 child method

↓
获得它所有 ancestor types

↓
查看 ancestor 声明的方法

↓
应用 generic type substitution

↓
比较 subsignature

↓
检查 return type compatibility

↓
符合 Java override 规则

↓
建立 OVERRIDES
```

所以这里不是：

```text
文本关系抽取
```

而是真正开始接近：

> **Java 类型系统语义分析。**

---

# 二十七、为什么还要检查 private / static / package-private

因为不是：

```text
同名方法
```

就一定构成 Override。

例如：

```java
class A {
    private void foo() {}
}

class B extends A {
    void foo() {}
}
```

这里 B 的 `foo()`：

```text
不是 override A.private foo。
```

再例如：

```java
static
```

属于方法隐藏，而不是普通实例方法覆盖。

所以 Graph Builder 必须尊重：

```text
Java 访问控制和方法语义。
```

否则：

```text
OVERRIDES
```

就会变成大量假边。

---

# 二十八、到这里可以看出 SymbolSolver 的真正价值

SymbolSolver 并不是为了：

> “让 JavaParser 更高级一点。”

它提供的是 Symbol Graph 最重要的一层保障：

```text
Simple Name
   ↓
Resolved Declaration
   ↓
Canonical Program Identity
```

没有这一步：

```text
CALLS
OVERRIDES
IMPLEMENTS
```

都会很容易退化成：

```text
字符串猜测。
```

---

# 二十九、为什么最终 Graph 仍然不是“完全正确的 Java 调用图”

即使使用 SymbolSolver，也不要把当前 Graph 理解成：

> 完整运行时 Call Graph。

例如：

```java
OrderService service;
service.createOrder();
```

静态解析：

```text
OrderService#createOrder
```

但运行时具体可能：

```text
OrderServiceImpl
```

也可能是：

```text
Proxy
Mock
OtherImplementation
```

所以当前 Symbol Graph 表达的是：

> **Repository 内部可静态可靠证明的程序关系。**

不是：

> 完整运行时行为。

这是它的能力边界。

# 三十、这个边界实际上是优点

如果系统为了“看起来更完整”直接推断：

```text
→ 某 Implementation
```

马上会涉及：

```text
Bean 条件
@Primary
@Qualifier
Profile

```

如果没有真正分析这些规则，就不能说：


```text
Java 静态事实
```

和未来可能的：

```text
Framework semantics
```

严格分开。

这是一个很成熟的边界。

# 三十一、把这一章串成完整流程

现在不用看任何代码，也应该能理解 Repository Analyzer 的逻辑：

```text
Java Repository
       ↓
发现所有 Source Root
       ↓
建立统一 Type Resolution Environment
       ↓
JavaParser
       ↓
得到整个 Repository 的 AST
       ↓
───────────────────────────────
Pass 1：实体阶段
───────────────────────────────
找到稳定声明：
Class
Interface
Method
Constructor
       ↓
生成稳定 Symbol
       ↓
建立 Repository Symbol Table
       ↓
───────────────────────────────
Pass 2：关系阶段
───────────────────────────────
解析：
extends
implements
method call
new
override
       ↓
SymbolSolver 确认真实声明
       ↓
检查是否 Repository Internal
       ↓
检查 target Symbol 是否存在
       ↓
可靠事实 → Edge
不可靠 → Diagnostic
```

这就是整个：

> **Repository → Symbol Graph**

的构图过程。

# 三十二、为什么这一设计同时有“高精度”和“可解释性”

假设一条边：

```text
A
 ↓ CALLS
B
```

系统知道：

```text
为什么有这条边？
```

因为：

```text
A 方法体里存在某 MethodCallExpr
+
SymbolSolver 把它解析成 B 声明
+
B 是 Repository 内部 Symbol
```

而不是：

```text
A 和 B embedding similarity = 0.84
```

所以 Graph Relation 天然：

```text
可追溯
可验证
可复现
```

这也是 Graph 能承担后续 Tool Agent 确定性能力的原因。

# 三十三、本章最重要的五个设计思想

现在建议只记这五件事。

**第一：AST 和 Symbol Resolution 是两个层次。**

```text
AST
→ 代码结构是什么

SymbolSolver
→ 名字具体指向哪个声明
```

**第二：必须从单文件解析提升到 Repository-level Analysis。**

跨文件、跨模块关系不可能靠孤立文件可靠恢复。

**第三：采用 Two-Pass。**

```text
先实体
后关系
```

让所有 Edge 都建立在已经存在的 Symbol 上。

**第四：Graph 的世界边界是 Repository Internal。**

能解析到第三方 API，不等于应该进入内部 Graph。

**第五：Precision First。**

```text
确定 → 建边

不确定 → gap

不猜。
```
