# DevContext 当前实现设计文档

> 当前版本：`main @ 346a047`  
> 核心定位：**面向代码仓库与项目文档的 Evidence-driven Project Understanding Agent**  
> 当前默认回答模式：`teach`  
> 当前默认回答 Profile：`fast`  
> 当前核心架构：**Evidence-driven Retrieval + Fast/Full Teaching Answer Engine**

---

# 1. 项目定位

DevContext 最初是一个面向 Java 项目的代码与文档 RAG 系统：

```text
用户问题
→ 检索代码 / 文档
→ 拼接 Context
→ LLM 回答
```

当前版本已经明显超出了传统 RAG 的范围。

系统现在被拆成两个相对独立的核心子系统：

```text
                    User Question
                          │
                          ▼
              ┌─────────────────────┐
              │ Retrieval Controller│
              │  项目中什么是真的？  │
              └──────────┬──────────┘
                         │
                   EvidencePackage
                         │
                         ▼
              ┌─────────────────────┐
              │ Teaching Answer     │
              │ 怎样让用户理解它？   │
              └──────────┬──────────┘
                         │
                         ▼
                    Final Answer
```

因此现在更准确的定位是：

> DevContext 先通过 Evidence-driven Retrieval 对项目进行“证据调查”，再根据问题类型、用户理解目标和证据边界构建回答结构，最终生成可验证、可解释的教学型回答。

# 3. RequestPolicy：回答开始前的执行策略

文件：

```text
src/devcontext/answer_policy.py
```

这是当前版本新增的重要抽象。

以前一个问题进来后，基本直接进入：

```text
EvidencePlanner
```

现在回答引擎会先建立：

```text
RequestPolicy
```

包含：

```python
profile
reasoning_effort
primary_intent
secondary_intents
reader_assumption
latency_target_seconds
hard_timeout_seconds
```

---

## 3.1 RequestPolicy 不调用 LLM

当前意图判断是规则实现：

```text
为什么 / 为何 / why
→ WHY

如何 / 怎么 / 流程
→ HOW

比较 / 区别 / vs
→ COMPARE

报错 / 排查 / debug
→ DEBUG

在哪里 / 哪个文件
→ LOCATE

是什么 / 定义
→ WHAT

其它
→ GENERAL
```

目的不是追求复杂 Intent Classification，而是：

> 用非常低的成本，在整个请求最开始确定“用户要完成什么理解任务”。

# 4. 当前问题类型

统一支持：

```text
WHAT
WHY
HOW
COMPARE
DEBUG
LOCATE
GENERAL
```

不同 Intent 对应不同的理解任务。

## WHAT

```text
定义与用途
→ 关键关系
→ 例子
→ 边界
```

## WHY

```text
原方案能力
→ 当前设计改变的条件
→ 为什么有效
→ 代价和前提
```

## HOW

```text
起始状态
→ 动作
→ 结果
→ 依赖
→ 故障分支
→ 边界
```

## COMPARE

```text
共同问题
→ 相同维度
→ 差异
→ 协作关系
→ 选择条件
```

## DEBUG

```text
预期
→ 实际现象
→ 候选原因
→ 排查顺序
→ 修复
→ 验证
```

## LOCATE

```text
代码位置
→ 职责
→ 必要调用关系
```

## GENERAL

不强行分类，而是：

```text
先回答问题
→ 再按真正理解所需组织内容
```

# 5. 不再使用 Answer Depth

旧版本存在：

```text
brief
standard
detailed
deep
```

当前已经完全移除。

CLI 如果传：

```bash
--depth detailed
```

会直接报错。

当前设计原则是：

> **回答的展开程度不应该由一个四档参数决定，而应该由问题真正需要建立多少关系来决定。**

例如：

```text
“UserInfoController 在哪里？”
```

可以只需要一个 Section。

而：

```text
“为什么 Redis Token Bucket 不能单独保证不超卖？”
```

自然需要：

```text
问题
→ 两层模型
→ 正常流程
→ 失败场景
→ 边界
```

用户仍然可以说：

```text
简单解释
详细解释
只给重点
```

但这些现在属于：

```text
自然语言偏好
```

而不是：

```text
固定的系统深度档位
```

# 6. 检索模块总览

当前 Retrieval Controller 的目标已经不是：

> 找和 Query 最相关的 Top-K Chunk。

而是：

> 回答这个问题之前，必须证明哪些事实？这些事实是否已经被当前项目证据满足？

整体流程：

```text
User Query
    │
    ▼
EvidencePlanner
    │
    ▼
EvidenceRequirement[]
    │
    ▼
SearchActionPlanner
    │
    ▼
SearchAction[]
    │
    ▼
Retrieval
    │
    ▼
EvidenceWorkspace
    │
    ▼
CoverageChecker
    │
    ├── SATISFIED
    ├── PARTIAL
    └── MISSING
    │
    ▼
缺 CORE？
    │
   YES
    ▼
Second-round Search
    │
    ▼
Coverage
    │
    ▼
EvidencePackage
```

# 7. EvidencePlanner

EvidencePlanner 负责回答：

> 为了回答用户问题，必须确认哪些项目事实？

生成：

```text
EvidenceRequirement
```

每项包括：

```text
target
success_criteria
priority
temporal_scope
source_requirement
```

例如用户问：

```text
为什么不能只靠 Redis 防止超卖？
```

可能拆为：

```text
ER1 CORE
确认 Redis 余票桶在购票链路中的实际职责

ER2 CORE
确认数据库最终状态保护逻辑

ER3 SUPPORTING
确认设计文档如何描述 Redis 与 DB 的职责
```

# 8. Fast Retrieval Planner

当前 Fast Profile 对检索链路也进行了优化。

文件：

```text
src/devcontext/agentic/fast.py
```

旧链路：

```text
EvidencePlanner
↓ LLM

SearchActionPlanner
↓ LLM
```

Fast 会将两次规划合并：

```text
FastRetrievalPlanner
```

一次 LLM 同时输出：

```text
primary_intent
subjects
requirements
queries
```

也就是说：

```text
Evidence Planning
+
Round0 Search Action Planning
```

合成一次调用。

目的：

```text
减少一次 LLM RTT
```

同时保持：

```text
Requirement
```

仍然作为 Retrieval Controller 的核心数据结构。

# 9. Stage-aware CODE Retrieval

这是最新 main 已经正式采用的检索策略。

旧实现：

```text
CODE
→ Hybrid
```

现在 Evidence Controller 的 CODE SearchAction 会先：

```text
code_strategy_for()
```

判断当前有没有代码 Symbol。

---

## 9.1 无 Symbol

例如：

```text
“购票事务最终状态更新”
```

没有：

```text
class_name
method_name
signature
```

则：

```text
CODE
→ Vector
```

原因：

> 这时检索目标仍然是业务语义，把 Keyword 混入 Hybrid 容易产生不必要的排名噪声。

---

## 9.2 有 Symbol

例如：

```text
PurchaseTicketTxService
doPurchaseInTransaction
```

则：

```text
CODE
→ Keyword
```

利用：

```text
class_name
symbol_name
signature
```

的强匹配能力。

---

# 10. Stage-aware 的实质

当前检索设计已经从：

```text
Source-aware Retrieval
```

演进到：

```text
Information-state-aware Retrieval
```

即：

```text
“搜索的是代码”
```

还不足以决定搜索算法。

还需要看：

```text
系统当前掌握了多少信息？
```

所以：

```text
Semantic state
→ Vector

Symbol state
→ Keyword
```

# 11. EvidenceWorkspace

检索到的候选会进入：

```text
EvidenceWorkspace
```

Workspace 是当前整个项目非常重要的基础抽象。

它保存：

```text
Retriever 真正找到过的完整证据集合
```

而不是只保存：

```text
最终 Prompt 放得下的证据
```

每个 Evidence 保存：

```text
evidence_id
citation
requirement_ids
source_role
temporal_status
authority_priority
first_seen_round
retrieval_rank
retrieval_score
content
```

# 12. 稳定 Evidence ID

当前 teach 路径使用：

```text
E1
E2
E3
...
```

而不是传统：

```text
C1
C2
```

区别在于：

```text
C1
= 某一个 Context 中第一个 Chunk

E1
= Workspace 中这个 Evidence 的稳定身份
```

所以：

```text
Planner
Writer
Section
Reviewer
```

看到同一条 Evidence 时 ID 不会变化。

这为：

```text
多阶段回答
```

提供了稳定引用基础。

---

# 13. Coverage Checker

Coverage 判断：

```text
Requirement 是否已经被证据满足
```

而不是：

```text
有没有搜索结果
```

首先执行确定性来源检查：

```text
CODE Requirement
但没有 CODE
→ MISSING

BOTH Requirement
只有 CODE
→ PARTIAL
```

然后必要时调用 LLM 做：

```text
语义充分性判断
```

产生：

```text
SATISFIED
PARTIAL
MISSING
UNVERIFIED
```

---

# 14. Fast Coverage

Fast Profile 会优先使用规则判断。

核心逻辑类似：

```text
有结果
+
来源满足
+
目标 Subject 出现在 Evidence
→ UNVERIFIED，可继续回答
```

只有不确定的 Requirement 才进一步调用：

```text
Semantic CoverageChecker
```

而且最多使用一次语义检查。

目的：

> 避免每一轮都额外调用 Coverage LLM。

因此 Fast 更关注：

```text
快速得到“足够可解释”的证据
```

而 Full 更关注：

```text
尽可能严格确认事实覆盖。
```

# 15. EvidencePackage

检索冻结后的核心对象是：

```text
EvidencePackage
```

包含：

```text
original_query
evidence_plan
context_bundle
requirement_coverage
unresolved_requirements
retrieval_state
search_history
coverage_rounds
evidence_catalog
evidence_workspace
```

这是检索系统与回答系统之间的边界。

从这一刻开始：

> 回答模块不应该再决定“项目事实是真是假”，只应该决定“这些事实怎么解释”。

Fast 是默认 Profile。


# 18. MicroExplanationPlanner

Fast 没有使用旧的完整 ExplanationPlan。

而是生成：

```text
MicroSectionPlan
```

包括：

```text
direct_answer
core_mental_model
question_kind
sections[]
```

Section：

```text
id
title
teaching_goal
key_points
evidence_labels
target_tokens
```

例如：

```text
S1
title:
Redis 在购票中的真实职责

goal:
先纠正“Redis 是最终库存”的误解

evidence:
E1 E3
```

Fast Planner 的目标是：

> 保留最核心的认知规划，但不构建非常复杂的教学蓝图。

---

# 19. Fast 的核心心智模型仍然存在

虽然 Planner 简化了，但：

```text
core_mental_model
```

仍然保留。

例如：

```text
Redis = 前置准入状态
数据库 = 最终事实状态
```

Writer 后续所有 Section 仍然需要围绕这个模型展开。

所以 Fast 并不是：

```text
取消规划
```

而是：

```text
压缩规划复杂度
```

---

# 20. Fast 不再逐 Section 调 LLM

这是相较上一版文档非常大的变化。

旧 Multi-pass：

```text
S1 → LLM
S2 → LLM
S3 → LLM
S4 → LLM
```

如果 8 个章节：

```text
至少 8 次 Writer Call
```

当前 Fast：

```text
一个 Streaming Writer Call
```

一次输出：

```text
S1
S2
S3
...
```

但通过特殊协议：

```text
<<<SECTION:S1>>>
## 标题
正文
<<<END_SECTION:S1>>>
```

让程序能够：

```text
边接收
边识别完整 Section
边验证
边发布
```

所以：

```text
Single LLM Call
≠
无法做 Section Control
```

---

# 21. Section Streaming Protocol

Writer 输出：

```text
<<<SECTION:S1>>>
## Redis 的作用
...
<<<END_SECTION:S1>>>

<<<SECTION:S2>>>
## 数据库为什么仍然需要
...
<<<END_SECTION:S2>>>
```

`SectionParser` 持续消费 Token Stream。

一旦看到：

```text
<<<END_SECTION:S1>>>
```

就立刻：

```text
完成 S1
→ 校验 S1
→ 发布 S1
```

不需要等整个回答生成结束。

---

# 22. Section 级校验

每个 Section 在发布前都会检查：

```text
标题是否与计划一致

Section 顺序是否正确

正文是否为空

Citation 格式是否合法

Citation 是否存在

Citation 是否属于该 Section allowlist
```

例如 S2 允许：

```text
E2 E5
```

Writer 如果生成：

```text
[E9]
```

严格模式下：

```text
整个 Section 拒绝。
```

在新 Answer Engine 的 permissive 模式中，也可以：

```text
移除非法 Citation
+
记录 warning
```

而不是错误传播到最终用户。

# 23. Fast 的核心设计思想

Fast 并不是简单减少内容，而是：

> 尽量压缩 LLM 调用次数，同时保留 Evidence Binding、Mental Model、Section Contract 和流式验证。

旧：

```text
Planner
+
N × Writer
+
Composer
+
Reviewer
```

新 Fast：

```text
Combined Retrieval Plan
+
Micro Explanation Plan
+
1 × Streaming Writer
```

显著减少了：

```text
串行 LLM RTT
```

# 26. Learning Goal

Planner 首先确定：

```text
用户回答完这个问题后应该能够做到什么？
```

例如：

```text
能解释 Redis Token Bucket 与数据库最终一致性保护之间的职责关系。
```

这比：

```text
“讲一下 Redis Token Bucket”
```

更具体。

---

# 27. Goal Capabilities

一个 Learning Goal 可以进一步拆成：

```text
G1
能区分 Redis 准入与 DB 最终状态

G2
能解释为什么两者同时存在

G3
能说明 Redis 成功、DB 失败时系统的边界
```

后续 Answer Structure 必须覆盖所有：

```text
applicable goal
```

避免：

```text
Planner 想了一个学习目标
但最终章节没有真正讲到。
```

---

# 28. Claims 是整个 Full Blueprint 的事实核心

Full V3 中：

```text
Claim
```

成为回答结构的基础节点。

每个 Claim 包含：

```text
id
statement
claim_type
status
evidence_labels
preconditions
reason
owner_section
```

Claim Type 仍然遵循：

```text
PROJECT_FACT
PROJECT_INFERENCE
GENERAL_CONCEPT
ILLUSTRATIVE_EXAMPLE
```

但现在进一步加入：

```text
status
```

例如：

```text
CONFIRMED
INFERENCE
UNKNOWN
```

---

# 29. Knowledge Boundary

Blueprint 可以从 Claim 自动得到：

```text
confirmed
inference
unknown
```

形成：

```text
Knowledge Boundary
```

例如：

```text
Confirmed:
Redis Token Bucket 在数据库事务前调用

Inference:
它承担前置准入职责

Unknown:
某极端异常是否存在专门补偿
```

这相当于：

> 在正式写答案前，先明确“知道什么、推断什么、不知道什么”。

这是防止项目型问答幻觉的重要边界。

---

# 30. Claim Ownership

每个 Claim 有且只有一个：

```text
owner_section
```

表示：

> 这条结论在哪个章节第一次完整建立。

其它 Section 如果需要：

```text
只允许 reference
```

而不应该：

```text
重复完整解释
```

这是为了解决长回答中：

```text
同一观点在多个章节反复出现
```

的问题。

---

# 31. Core Mental Model 已升级为关系图

旧版本：

```text
core_mental_model
= 一个字符串
```

例如：

```text
Redis 是准入层，DB 是最终状态层。
```

Full V3：

```text
core_mental_model[]
```

每个模型节点包括：

```text
statement
relation
roles
claim_ids
```

因此已经更接近：

```text
Claim Relationship Map
```

而不是简单一句总结。

---

# 32. Critical Distinctions

Blueprint 显式规划：

```text
容易混淆但必须区分的概念
```

例如：

```text
准入资格
≠
最终库存

Redis 成功
≠
购票事务成功

减少数据库压力
≠
保证绝对一致性
```

这类信息对于教学型回答非常重要。

因为很多用户“没听懂”并不是信息不足，而是：

> 两个相似概念没有被明确拆开。

---

# 33. WHY Spine

如果问题类型是：

```text
WHY
```

Full V3 要求构建固定的逻辑槽位：

```text
constraint

alternative

alternative_limit

chosen_design

changed_condition

causal_explanation

tradeoff_boundary
```

对应：

```text
原来面临什么约束？

有哪些可选方案？

原方案为什么不够？

当前选了什么？

它改变了哪个条件？

为什么改变后问题得到解决？

代价和边界是什么？
```

这比以前：

```text
WHY → PROBLEM_SOLUTION
```

更加形式化。

---

# 34. HOW Spine

HOW 不再只是：

```text
Step1
Step2
Step3
```

而是每一步包含：

```text
state_before
problem
action
state_after
preconditions
guarantee_claim_ids
links
path
```

并区分：

```text
NORMAL

FAILURE
```

Failure Step 还必须有：

```text
BRANCH_FROM
```

明确说明：

> 从哪个正常状态开始分叉。

所以 Full 对流程问题建立的是：

```text
State Transition + Dependency Graph
```

而不是简单时间顺序列表。

---

# 35. 通用 Explanation Units

对于：

```text
WHAT
COMPARE
DEBUG
LOCATE
GENERAL
```

使用更通用：

```text
explanation_units
```

每个 Unit 表达：

```text
problem
action
state_result
preconditions
remaining_boundary
claim_ids
links
```

不同 Unit 之间可以：

```text
PRECEDES
DEPENDS_ON
JOINT_CONSTRAINT
BOUNDARY_EXTENSION
BRANCH_FROM
```

建立显式关系。

---

# 36. Learning Delta

Full Blueprint 的每一个 Section 都必须声明：

```text
learning_delta
```

包括：

```text
before_kind

before

after
```

例如：

```text
before:
只知道 Redis 减少请求数量

after:
理解 Redis 只是前置准入，并不能替代 DB 最终状态检查
```

因此：

> 每一节必须真正改变用户认知。

如果一节只是重复上一节：

```text
不会产生有效 Learning Delta。
```

---

# 37. Scenario

Full 可以根据问题设计：

```text
NONE

RELATION_EXAMPLE

STATE_TRACE

COUNTERFACTUAL
```

并包含：

```text
actors
assumptions
checkpoints
```

例如并发问题：

```text
Request A
Request B
Redis
Database
```

然后使用 Checkpoint 表示：

```text
状态前
→ 动作
→ 状态后
```

---

# 38. Comprehension Checks

Blueprint 甚至允许规划：

```text
comprehension_checks
```

用于检查：

> 如果用户真正理解了这段回答，他应该能回答什么问题？

例如：

```text
为什么 Redis Token Bucket 成功并不能推出数据库事务一定成功？
```

当前这部分主要用于 Blueprint 完整性，而不是强制输出为考试题。

---

# 39. Blueprint Validation

Full Planner 的输出不会直接信任。

系统会验证：

```text
Claim ID 是否有效

Owner Section 是否存在

Evidence Label 是否存在

Learning Goal 是否被章节覆盖

Mental Model 是否绑定 Claim

Section Learning Delta 是否真实变化

WHY 是否满足 7 个 reasoning slot

HOW Failure 是否存在 Branch Origin

UNKNOWN Claim 是否被错误当成 established guarantee

Unit 链接是否引用真实节点
```

只要结构错误：

```text
Planner Output Reject
```

---

# 40. Planner Recovery

Full Planner 最多允许：

```text
2 次尝试
```

如果第一次 Blueprint 校验失败：

```text
LLM 输出
↓
Validator
↓
具体 Issues
↓
把错误反馈给 Planner
↓
重新输出完整 Blueprint
```

这是：

```text
Structured Self-repair
```

但它不是无限循环。

如果：

```text
第二次仍失败
```

或者：

```text
剩余时间不足
```

则退出 Planner。

---

# 41. Evidence Reconciliation

即使 Blueprint 逻辑上有效，也可能存在：

```text
Planner 想用 E7
但 E7 内容被截断
```

因此 Writer 前还有：

```text
reconcile_evidence()
```

它会重新检查：

```text
PROJECT_FACT
PROJECT_INFERENCE
```

所依赖 Evidence 是否真正可用。

如果 Evidence 不可用：

```text
Claim
→ UNKNOWN

Evidence Labels
→ 移除无效引用
```

也就是说：

> 回答计划的事实保证会根据真实 Evidence 再次收缩。

而不是：

```text
Planner 已经说 CONFIRMED
→ 后面无条件相信。
```

---

# 42. WriterEvidencePack

接下来：

```text
build_writer_evidence_pack()
```

会把 Blueprint 转为 Writer 真正需要的执行结构。

每个 Writer Section 有：

```text
id
title
evidence_labels
contract
```

其中 Contract 包含：

```text
owned_claims

may_reference

dependency_claims

spine

checkpoints

critical_distinctions

required_labels

allowed_labels

support_labels

prior_context_claim_ids
```

因此 Full Writer 收到的并不是：

```text
“第 3 节，请写一下 Redis”
```

而是一份非常严格的：

```text
Section Execution Contract
```

---

# 43. Full 不会裁掉必要证明链

构建 Evidence Pack 时：

```text
Required Evidence
```

优先于：

```text
Optional Evidence
```

如果 Required Evidence 超出预算：

```text
EvidencePackUnavailable
```

而不是：

```text
偷偷把 Required Evidence 截掉
再让 Writer 根据不完整证据写。
```

这个设计很重要。

原则是：

> 宁可降级回答，也不破坏核心证明链。

---

# 44. Full Writer 仍然使用 Single Stream

这是相较早期 V3 很大的优化。

虽然 Full Blueprint 非常复杂，但写正文时仍然是：

```text
一次 Streaming LLM Call
```

而不是：

```text
每个 Section 一次 Call。
```

完整：

```text
Blueprint
+
WriterEvidencePack
+
Evidence
↓
TeachingWriterV3
↓
Single Stream
↓
S1
S2
S3
...
```

所以当前架构成功地保留了：

```text
复杂规划
```

同时减少：

```text
Writer 串行 RTT。
```

---

# 45. Full Section Validation

每一个流式完成的 Section 都要经过：

```text
validate_section()
```

然后根据 Contract 做：

```text
Citation 检查

Evidence Allowlist 检查

Grounding Rule 检查

Claim Boundary 检查
```

完成后才：

```text
on_section(section)
```

发布给 CLI。

所以用户看到的不是：

```text
未经验证的 token stream
```

而是：

```text
已完成 + 已通过 Section Validation 的块级流式结果。
```

---

# 46. First Section Ready

系统现在专门记录：

```text
first_content_token_ms
first_section_ready_ms
```

二者不同。

```text
first_content_token
```

表示：

> 模型开始输出。

而：

```text
first_section_ready
```

表示：

> 第一节完整生成并通过校验，可以安全展示。

后者才是真正的：

```text
用户可用 TTFR
```

---

# 47. Full Writer Retry

如果整个 Stream 在第一节发布前发生可恢复错误：

```text
network error
protocol error
abnormal finish
```

可以：

```text
再次完整尝试
```

但如果已经成功发布 Section：

```text
不会简单从头生成一遍
```

避免用户看到重复内容。

---

# 48. Full Direct Fallback

这是最新版本一个非常重要的可靠性设计。

如果：

```text
Blueprint Planner 最终失败
```

或者：

```text
Evidence Pack 无法构建
```

系统不一定直接返回：

```text
“生成失败”
```

而可以进入：

```text
full_direct_fallback
```

流程：

```text
现有 Evidence
↓
移除 Blueprint 专属 Prompt
↓
Direct Teaching Writer
↓
普通 Markdown
↓
Citation 清理
↓
Final Answer
```

也就是说：

> Full 的规划系统失败，不代表整个回答必须失败。

---

# 49. Fallback 不是编造

Direct Fallback 仍然：

```text
只使用真实 Evidence
```

并且：

```text
非法 E Citation
→ 移除
→ Warning
```

它失去的是：

```text
复杂 Blueprint 教学规划
```

而不是：

```text
Grounding 边界。
```

---

# 50. 当前回答系统的三层降级

现在实际上已经形成：

```text
Full Blueprint Pipeline
      │
      │ Planner / Pack Recoverable Failure
      ▼
Full Direct Fallback
```

Fast 则：

```text
Micro Plan
↓
Single Stream
```

而旧：

```text
multi_pass
```

仍然保留作为兼容实现。

所以系统不再只有：

```text
成功
/
失败
```

而是具备：

```text
高质量结构化回答
→ 简化回答
→ 明确失败
```

的可控降级路径。

---

# 51. 旧 Multi-pass 现在是什么地位

上一版文档的主要回答链：

```text
ExplanationPlanner
→ Section Writer × N
→ Composer
→ Reviewer
→ Targeted Revision
```

代码仍存在。

通过：

```bash
--teaching-generation-mode multi_pass
```

仍然可以使用。

因此它不是被删除。

但它现在更应该理解为：

> 历史兼容 / 实验对照路径。

而不是：

> 当前默认生产回答架构。

---

# 52. Composer / Reviewer 的地位变化

这也是上一版文档最需要纠正的地方之一。

以前主路径：

```text
Section Writer
↓
Composer
↓
TeachingReviewer
↓
Targeted Revision
```

当前 Fast / Full 新引擎的核心思路变成：

```text
在生成前提高 Plan / Contract 强度
+
在流式 Section 完成时立即验证
```

也就是说：

```text
Post-generation Repair
```

的重要性下降。

系统更加偏向：

```text
Pre-generation Constraint
+
During-generation Validation
```

这是一个明显的架构方向变化。

---

# 53. 为什么从 Reviewer-heavy 转向 Contract-heavy

旧思路：

```text
先生成
↓
Reviewer 判断哪里有问题
↓
再修改
```

问题：

```text
慢
成本高
结果波动
Reviewer 本身也可能错
```

当前 Full：

```text
Planner 先定义 Claim
↓
Claim Owner
↓
Evidence
↓
Reasoning Spine
↓
Section Contract
↓
Writer 只能按 Contract 写
```

所以目标是：

> 尽量让错误根本没有机会生成，而不是生成完再纠错。

# 54. 当前 Fast 与 Full 的区别

可以总结为：

| 维度 | Fast | Full |
|---|---|---|
| 默认 | ✅ | 手动 |
| Retrieval Planner | 合并版 | 完整 |
| Answer Planner | Micro Plan | Teaching Blueprint |
| Mental Model | 简化字符串 | Claim Relationship Map |
| Claim Planning | 轻量 | 完整 |
| Reasoning Spine | 隐式/简化 | 显式 |
| Learning Goal | 简化 | 完整 |
| Learning Delta | 无严格要求 | 显式 |
| Evidence Pack | Bound Bundle | WriterEvidencePack |
| Writer | Single Streaming | Controlled Streaming V3 |
| Writer Calls | 1 | 1 |
| Section Validate | ✅ | ✅ 更严格 |
| Planner Retry | 简单 | 最多 1 次修正 |

# 55. Fast 并不是“低质量模式”

Fast 的设计目标不是：

```text
少写一点
```

而是：

```text
用更少的 LLM 调用
完成大部分普通项目问答
```

它仍然保留：

```text
Evidence Plan
Mental Model
Section Plan
Evidence Binding
Streaming Protocol
Citation Validation
```

只是去掉：

```text
复杂 Claim Graph
WHY/HOW Spine
Learning Delta
Scenario Checkpoints
复杂 Evidence Pack
```

---

# 56. Full 也不是“详细模式”

Full 不应该理解为旧：

```text
deep
```

Full 的差别不是：

```text
写得更多
```

而是：

```text
在写之前进行更完整的认知建模和证据契约设计。
```

因此一个复杂 WHY 问题值得使用 Full。

一个简单 LOCATE 问题即使要求：

```text
“详细一点”
```

也没有必要构建十几个复杂结构。

> 我做了一个 RAG，然后加了 Planner 和 Reviewer。

更合适的是：

> 我把项目问答拆成 Evidence Investigation 和 Teaching Explanation 两个独立阶段。检索阶段不是直接 Top-K，而是先规划需要证明的事实，通过 Evidence Requirement、Stage-aware Retrieval、Coverage 和二轮 Rescue 建立 EvidencePackage。回答阶段进一步分成 Fast 和 Full 两套执行 Profile：Fast 使用 Micro Plan + 单次流式 Writer 降低时延；Full 使用 Teaching Blueprint，对 Claim Ownership、Knowledge Boundary、Mental Model、WHY/HOW Reasoning Spine、Learning Delta 和 Evidence Pack 建立严格契约，然后一次流式生成各章节，并在章节发布前进行 Citation 和 Contract 校验。系统把能够确定性验证的规则从 LLM 中拿出来，同时保留 Planner 处理语义与教学结构，从而兼顾 Grounding、解释质量和性能。

# 69. 当前仍然存在的问题

当前架构已经比较完整，但还没有“做完”。

## 69.1 Symbol Router 仍可继续收紧

当前：

```text
symbols_in_text()
```

主要依据：

```text
CamelCase
qualified name
annotation
.java
```

判断。

仍存在：

```text
技术名词误识别
```

以及：

```text
纯小写 method 无法识别
```

的问题。

未来更合理：

```text
Query Symbol
∩
Repository Symbol Index
```

后再进入 Keyword。

---

## 69.2 Fast 的 Micro Plan 仍是 LLM

Fast 的延迟和质量依然部分取决于：

```text
MicroExplanationPlanner
```

如果它：

```text
章节划分过多
Evidence Binding 不理想
```

依然会影响最终回答。

---

## 69.3 Full Blueprint 很复杂

Full 的强约束提升了回答结构质量，但也增加：

```text
Planner Token
Validation Complexity
Planner Retry
```

因此 Full 的真正价值需要继续通过：

```text
L2 Blind Evaluation
```

验证，而不能仅凭 Blueprint 复杂度证明质量更好。

---

## 69.4 Claim-Evidence Entailment 仍不是形式化证明

目前系统能保证：

```text
E5 存在
E5 被允许用于 S3
```

但：

```text
某一句自然语言是否真的被 E5 完整蕴含
```

仍不能由纯规则完全判断。

---

## 69.5 Fast / Full 的路由还比较简单

当前：

```text
默认 fast
用户 --profile full
```

未来可以考虑：

```text
根据问题复杂度
+
Evidence Complexity
+
用户要求
```

自动决定：

```text
Fast or Full
```

但在没有足够 benchmark 之前，不应该过早自动化。
