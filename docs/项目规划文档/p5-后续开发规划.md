## 总体结论

当前项目已经完成了一个可运行、可验证的“代码与文档混合检索 MVP”。

如果以当前生效的精简范围为标准，开发进度可以判断为：

> Java/Markdown 解析 → Chunk 统一建模 → Embedding → PostgreSQL/pgvector 存储 → 关键词/向量/混合检索 → 小规模评测，这条主链路已经打通。

当前最主要的问题已经不是“功能跑不起来”，而是：

1. 评测集太小，暂时不足以证明检索质量稳定。
2. 检索结果还没有正式构造成可供大模型消费的上下文。
3. 引用定位信息不够完整。
4. 解析、缓存和数据库链路仍然偏 MVP，实现了主流程，但生产级健壮性不足。
5. 当前 Docker 引擎没有运行，因此本次分析没有重新执行数据库集成测试；运行结果主要依据 2026-09-22 的验证记录和当前代码静态检查。

因此，建议下一阶段不要急着引入 LangChain、LangGraph 或 Agent，而是先完成：

> 强化评测基线 → Context Builder → 精确引用 → 有评测支撑的检索优化

## 3. Markdown 文档解析

```markdown

生成的 Markdown Chunk 会包含类似：

```text
title = 支付流程

```text

Markdown Chunk 2363
总 Chunk        2901
```

Markdown 约占总 Chunk 的 81.5%，代码约占 18.5%。

### 当前不足

当前 Markdown 解析采用正则和行扫描，不是完整的 CommonMark AST，因此存在一些边界风险：

1. 代码块中的伪标题可能被误判。

例如：

````markdown
```text
# 这其实是代码内容
```
````

如果解析器没有维护 fenced code block 状态，就可能把这一行误认为正文标题。

2. 缺少表格、列表、引用块等结构语义。

3. Chunk 之间没有重叠窗口，跨段落语义可能被截断。

4. `heading_path` 虽然被解析和存储，但目前没有充分参与 Embedding 文本和检索结果输出。

5. 超长内容最后采用字符硬切时，可能在语句中间断开。

当前实现足以完成基础文档索引，但下一阶段应优先把它改成“代码围栏感知”的解析器。

  ↓

  ↓
统一排序
  ↓

```

### `content`、`keyword_text` 和 `embedding_text`

三者并不是同一个字段的重复副本。

#### `content`

原始内容，用于最终展示和构造上下文。

Java 方法 Chunk 的 `content` 通常是原始方法源码；Markdown Chunk 的 `content` 是章节正文。

#### `keyword_text`

为关键词匹配准备的文本。

它通常由适合精确检索的结构字段组成，例如：

```text
类名
方法名
方法签名
文档标题
原文内容
```

适合搜索：

- `purchaseTickets`
- `TxService`
- `@Transactional`
- 精确方法名
- 精确类名
- 文档中的特定术语

#### `embedding_text`

真正发给 Embedding 模型的语义文本。

它不仅需要包含原始内容，还要给模型补充 Chunk 的身份信息。例如代码 Chunk 可以近似构造为：

```text
Type: METHOD
Class: TxService
Symbol: purchaseTickets
Signature: purchaseTickets(...)
Content:
...
```

文档 Chunk可以近似构造为：

```text
Type: DOC_SECTION
Title: 分布式事务设计
Content:
...
```

`keyword_text` 面向字符、词项和标识符匹配；`embedding_text` 面向语义向量计算。

## 5. Embedding 与缓存链路

当前 Embedding 实现已经包含比较完整的基础能力：

- 百炼 `text-embedding-v4`
- 1024 维向量
- 批量请求
- 单批默认控制在 10 条左右
- OpenAI 兼容客户端
- curl 兼容路径
- 请求失败重试
- 返回数量检查
- 向量维度检查
- 非有限值检查
- 本地 JSONL 缓存

主要代码包括：

- Embedding 客户端
- Embedding pipeline
- Embedding cache
- 维度和批处理相关测试

缓存键的核心思想是：

```text
模型 + 维度 + embedding_text 内容指纹
```

而不是简单使用 Chunk ID。

这样，当源文件位置发生变化但实际送给模型的文本没有变化时，理论上仍然可以复用向量；当模型、维度或文本变化时，旧缓存自然失效。

### 现有缓存状态

当前缓存文件约 67 MB：

- 有效记录约 3089 条
- 唯一缓存键约 3011 个
- 当前 Chunk 数量为 2901

说明缓存已经被实际使用过，但也说明它是追加式缓存：

- 存在过期条目
- 存在少量重复键
- 没有自动压缩
- 没有缓存垃圾回收

### 当前不足

1. 缓存是追加式 JSONL，不适合持续增长的长期运行环境。
2. 缺少并发写锁。
3. 缺少原子压缩和损坏恢复策略。
4. 查询向量没有独立的短期缓存。
5. 缓存统计没有直接暴露到 ingest 报告。
6. 数据库中的 `embedding_model` 虽然保存了，但查询时没有严格校验所有记录是否来自当前模型。
7. 模型或维度变化后，缺少明确的“必须重建索引”提示。

对于当前 2901 个 Chunk，JSONL 完全够用；只有当项目频繁导入或规模增大时，才需要换 SQLite 等缓存实现。

## 6. PostgreSQL / pgvector 存储

数据库使用：

- PostgreSQL 18
- pgvector 0.8.6
- pg_trgm 1.6

Schema 位于：

- [schema.sql](D:/Java-learning/DevContext/src/devcontext/db/schema.sql)

当前采用单表存储：

```text
knowledge_chunk
```

Java 和 Markdown Chunk 都写入这张表，通过以下字段区分：

```text
source_type = JAVA / MARKDOWN
chunk_type  = CLASS / METHOD / DOC_SECTION / ...
```

主要能力包括：

- 创建 vector 扩展
- 创建 pg_trgm 扩展
- 存储 1024 维 embedding
- repository 索引
- source_type 索引
- chunk_type 索引
- file_path 索引
- keyword_text trigram 索引
- 事务式删除并重建某个仓库数据
- 关键词检索
- 向量余弦检索

### 全量重建的事务语义

当前导入采用：

```text
BEGIN
  删除指定 repository 的旧数据
  插入新 Chunk
COMMIT
```

如果写入失败：

```text
ROLLBACK
```

因此不会出现“旧数据已经删掉，新数据只写入一半”的正常事务中间状态。

这是当前数据链路中比较重要且正确的设计。

### 当前不足

#### 1. 向量检索还是精确扫描

当前使用 pgvector 的余弦距离：

```sql
embedding <=> query_vector
```

但没有 HNSW 或 IVFFlat 索引。

2901 条数据下完全可以接受，而且精确扫描不会引入 ANN 召回损失。现在不应该为了“用了 pgvector 就必须建 HNSW”而提前优化。

只有以下情况出现时才值得引入 HNSW：

- Chunk 达到数万甚至数十万
- 向量 SQL 延迟明显成为瓶颈
- `EXPLAIN ANALYZE` 证明扫描成本不可接受
- 已经有足够完整的评测集验证 ANN 参数不会损害召回

#### 2. `pg_trgm` 索引是否真正命中需要验证

关键词 SQL 中包含：

- `lower(...)`
- `strpos(...)`
- `similarity(...)`

但建立的 GIN trigram 索引不一定能够被当前表达式有效使用。

需要通过：

```sql
EXPLAIN (ANALYZE, BUFFERS)
```

确认真实执行计划，而不能仅根据“建了索引”判断它已经发挥作用。

#### 3. 缺少索引版本

目前数据库能够保存内容和向量，但缺少：

- parser version
- chunk schema version
- embedding text template version
- ingestion run ID
- indexed_at
- source file checksum

这些信息在以后升级解析规则或 Embedding 模板时非常重要。

#### 4. 全量重建够简单，但还没有增量索引

当前每次 ingest 都是仓库级重建。对于 2901 个 Chunk 很合理；后续规模增加后，才需要基于文件 hash 做增量更新。

- 没有 query type 分类。

## 8. 向量检索

向量检索流程已经打通：

```text
用户问题
  ↓
调用 Embedding API
  ↓
得到 1024 维查询向量
  ↓
PostgreSQL pgvector 余弦距离
  ↓
返回最相似 Chunk
```

向量检索特别适合：

- 用户没有说出准确方法名
- 文档标题和问题措辞不同
- 需要按含义召回
- 中英文术语表达不完全一致

当前评测：

- Recall@3：0.542
- Recall@5：0.667
- MRR：0.586

这明显低于关键词检索，但并不意味着向量链路实现错误。

原因是当前评测中包含很多精确符号问题。对以下问题，关键词天然有优势：

```text
login 方法在哪里？
scanTimeout 的实现是什么？
doPurchaseInTransaction 在哪里？
```

向量检索不应该被要求在精确标识符问题上全面击败关键词检索。它的主要价值是补充模糊语义召回。

### 观察到的具体问题

在现有评测结果中：

- `doPurchaseInTransaction` 的正确方法大约落到第 6 名。
- `scanTimeout` 的正确方法大约落到第 4 名。
- `login` 的正确方法大约落到第 7 名。
- 某些文档问题检索出了语义正确但不在评测标注路径中的新文档。

这说明有两类问题同时存在：

1. Embedding 对精确符号定位不够稳定。
2. 评测 ground truth 没有及时覆盖新增的等价文档。

## 9. 混合检索

混合检索采用 RRF，也就是 Reciprocal Rank Fusion。

基本公式可以理解为：

```text
RRF 分数 = 1 / (k + keyword_rank)
         + 1 / (k + vector_rank)
```

当前 `k` 为 60，并且关键词和向量候选池都会至少取 20 条左右，再执行融合。

这种方法的优点是：

- 不需要把关键词分数和向量距离直接归一化到同一量纲。
- 对不同检索器的原始分数分布不敏感。
- 一个结果在两路都排名靠前时，会自然得到更高融合排名。
- 单路漏召回时，可以由另一路补充。

当前混合检索指标：

- Recall@3：0.833
- Recall@5：1.000
- MRR：0.771

这是当前项目最重要的成果：

> 12 条评测用例中，混合检索在 Top 5 范围实现了全部目标召回。

不过不能只看 1.000：

- 评测只有 12 条。
- 测试集覆盖不够广。
- 部分 ground truth 已经落后于当前文档内容。
- Hybrid 的 MRR 低于关键词检索，说明正确结果虽然能进入 Top 5，但不一定总在第一名。
- DOC-004 的相关结果在第 4 名，说明 Top 3 仍有改进空间。

## 10. 评测系统

评测已经支持：

- JSONL benchmark
- keyword/vector/hybrid 三种模式
- Recall@3
- Recall@5
- MRR
- 平均延迟
- 逐条结果输出
- 结果保存到 artifacts

主要文件：

- [runner.py](D:/Java-learning/DevContext/src/devcontext/evaluation/runner.py)
- [benchmark.jsonl](D:/Java-learning/DevContext/evaluation/benchmark.jsonl)

当前评测集共有 12 条：

- CODE：4 条
- DOC：4 条
- MIXED：4 条

验证结果：

| 模式 | Recall@3 | Recall@5 | MRR | 平均耗时 |
|---|---:|---:|---:|---:|
| keyword | 0.917 | 0.917 | 0.875 | 约 397 ms |
| vector | 0.542 | 0.667 | 0.586 | 约 466 ms |
| hybrid | 0.833 | 1.000 | 0.771 | 约 932 ms |

### 如何解读这些指标

- Keyword 的首位排序最好，MRR 最高。
- Vector 单独作为默认检索器不合适。
- Hybrid 的 Top 5 召回最好。
- Hybrid 延迟最大，因为它同时执行关键词和向量链路，而且向量链路包含外部查询 Embedding。
- 当前延迟是端到端延迟，不是单纯数据库 SQL 延迟。

从当前数据看，默认策略使用 Hybrid 是合理的，因为后续 Context Builder 通常需要多个相关 Chunk，而不是只依赖第一名。

# 三、当前项目已经达到什么程度

可以把当前项目分为三个层次理解。

## 第一层：检索技术验证

这一层已经完成。

已经证明：

- JavaParser 能稳定解析目标仓库。
- Markdown 能拆分成可检索章节。
- Java 和 Markdown 可以统一成为 Chunk。
- Chunk 可以生成 Embedding。
- Embedding 可以缓存。
- Chunk 和向量可以写入 PostgreSQL。
- 三种检索模式可以工作。
- 混合检索能够在小规模测试中提升 Top 5 召回。

这一层完成了主体，但尚需加固。

还需要：

- 更大评测集

- 更完整失败报告
- 更完善测试
- 查询过滤
- 版本管理
- 检索可观测性
- 缓存维护
- 索引执行计划验证

  ↓

  ↓

所以，当前项目不是“完整的 RAG 问答产品”，而是“已经完成检索底座的 RAG 原型”。

# 四、当前最值得关注的问题

## 1. 评测集只有 12 条

这是现在最大的质量风险。

Hybrid Recall@5 达到 1.0 很好，但 12 条样本不足以证明：

- 新增代码后仍然稳定
- 更多中文问题下仍然稳定
- 同名方法能够正确区分
- 跨模块查询能够正确召回
- 文档标题变化后仍然稳定
- 混合问题始终能同时召回代码和文档

此外，现有评测已经出现 ground truth 漂移：

- 向量检索找到了语义相关的新设计文档。
- 但 benchmark 只认可旧路径。
- 于是“检索结果实际合理”，评测却判定为错误。

这说明下一阶段如果直接调整 RRF、Embedding 模板或数据库权重，可能会被不完整的评测数据误导。

---

## 2. MIXED 问题需要专门指标

当前混合问题通常期待：

```text
至少一个代码 Chunk
+
至少一个文档 Chunk
```

现有评测里已经观察到：

- 关键词检索在部分 MIXED 查询中 Top 5 全是代码。
- 向量检索在部分 MIXED 查询中 Top 5 全是文档。
- Hybrid 才将两侧结果合并起来。

当前普通 Recall 能反映一部分情况，但不够直观。

建议增加：

```text
code_hit@k
doc_hit@k
both_sources_hit@k
```

例如：

```text
MIXED-001:
  code_hit@5 = true
  doc_hit@5 = true
  both_sources_hit@5 = true
```

这比单一 Recall 更能反映混合检索是否达成产品目标。

---

## 3. SearchResult 缺少构造引用所需的完整信息

当前检索结果主要包含：

- ID
- 路径
- symbol
- title
- start/end line
- content
- score

但是后续引用还需要更多信息：

- `heading_path`
- `class_name`
- `signature`
- `module`
- `package_name`
- `annotations`
- `javadoc`
- `embedding_model`
- keyword 原始排名
- vector 原始排名
- RRF 最终分数

尤其是 Markdown 引用，如果只有文件路径和标题，不带完整标题层级，就很难生成这种稳定引用：

```text
docs/design.md > 系统设计 > 订单模块 > 事务处理
```

因此，Context Builder 之前应先扩展检索结果契约。

---

## 4. 缺少可解释的检索跟踪信息

当前用户看到的主要是最终分数，但很难知道：

```text
这个结果是关键词召回的？
是向量召回的？
两路都召回了吗？
它在关键词结果中第几名？
它在向量结果中第几名？
最终为什么排到这里？
```

建议 Hybrid 结果至少保留：

```json
{
  "keyword_rank": 1,
  "keyword_score": 18.42,
  "vector_rank": 7,
  "vector_similarity": 0.73,
  "rrf_score": 0.0311
}
```

这对后续调整检索器非常重要。

---

## 5. 测试数量偏少

当前 Python 测试约 11 条，Java 侧有一个核心 JUnit 测试类。

现有测试覆盖了：

- Java 21 语法基础
- CRLF 行号
- interface
- method
- constructor
- annotation
- Markdown 基础解析
- Chunk 模型
- Embedding 批处理
- 错误向量维度
- Hybrid 基础逻辑
- Evaluation 基础逻辑
- 数据库集成流程

但是缺少：

- Markdown fenced code block 测试
- enum/record 测试
- Embedding 超时和重试测试
- 429/5xx 测试
- 缓存重复、损坏、并发测试
- 数据库回滚测试
- 模型维度不一致测试
- repository 隔离测试
- keyword SQL 排序测试
- vector SQL 排序测试
- Hybrid 同分稳定排序测试
- 路径与中文字符测试

# 五、下一步开发建议

## 第一优先级：先强化评测，不要马上改检索算法

建议先把评测集从 12 条扩展到至少 30～50 条。

推荐分布：

| 类型 | 建议数量 | 重点 |
|---|---:|---|
| CODE | 10～15 | 类、方法、注解、事务、异常、同名方法 |
| DOC | 10～15 | 设计、流程、部署、配置、术语同义表达 |
| MIXED | 10～20 | 同时要求代码和设计说明 |
| 总计 | 30～50 | 能支撑基础回归判断 |

### CODE ground truth

不要只写：

```json
{
  "symbol": "purchaseTickets"
}
```

建议至少写：

```json
{
  "source_type": "JAVA",
  "path_contains": "TxService.java",
  "class_name": "TxService",
  "symbol": "purchaseTickets",
  "start_line": 120
}
```

对于重载方法，还应加入 signature。

### DOC ground truth

不要只依赖文件路径，建议加入标题层级：

```json
{
  "source_type": "MARKDOWN",
  "path_contains": "design.md",
  "heading_path": [
    "系统设计",
    "订单模块",
    "事务处理"
  ]
}
```

### 允许多个等价答案

如果新旧文档都能够正确回答问题，应允许：

```json
{
  "any_of": [
    {
      "path_contains": "2-系统设计.md",
      "title_contains": "事务"
    },
    {
      "path_contains": "7-模块设计文档.md",
      "title_contains": "事务"
    }
  ]
}
```

否则评测会把合理结果误判为失败。

### 增加分类指标

建议增加：

- CODE Recall@k
- DOC Recall@k
- MIXED Recall@k
- `code_hit@k`
- `doc_hit@k`
- `both_sources_hit@k`
- 无结果率
- 重复结果率
- 首个相关 CODE 排名
- 首个相关 DOC 排名

### 拆分延迟

当前平均延迟是端到端时间，建议拆分：

```text
query_embedding_ms
keyword_sql_ms
vector_sql_ms
fusion_ms
total_ms
```

这样才能知道 Hybrid 的约 932 ms 到底花在哪里。

### 这一阶段的验收条件

建议设为：

- benchmark 不少于 30 条
- 每一类不少于 10 条
- Hybrid Recall@5 不低于当前基线
- MIXED `both_sources_hit@5` 达到明确目标
- 所有失败用例都能输出排名和失败原因
- 每次改检索策略前后都有对比报告

---

## 第二优先级：实现 Context Builder 和引用

这是下一项最值得增加的产品能力。

当前检索输出还是“若干数据库记录”，下一步需要将其转换成结构清晰、长度受控、可引用的上下文。

建议流程：

```text
SearchResult[]
  ↓
按 Chunk ID 去重
  ↓
代码/文档结果适度平衡
  ↓
合并相邻或重叠 Chunk
  ↓
按字符/token 预算截断
  ↓
生成引用标签
  ↓
输出 ContextBundle
```

### 建议的数据结构

```python
@dataclass
class Citation:
    citation_id: str
    source_type: str
    file_path: str
    start_line: int | None
    end_line: int | None
    heading_path: list[str] | None
    symbol_name: str | None
    signature: str | None


@dataclass
class ContextItem:
    citation: Citation
    content: str
    retrieval_mode: str
    score: float
    keyword_rank: int | None
    vector_rank: int | None


@dataclass
class ContextBundle:
    query: str
    items: list[ContextItem]
    rendered_text: str
```

### Java 上下文模板

```text
[C1] Java source
File: src/main/java/.../TxService.java
Symbol: TxService.purchaseTickets(...)
Lines: 120-168

<source code>
```

### Markdown 上下文模板

```text
[C2] Documentation
File: docs/design.md
Section: 系统设计 > 订单模块 > 事务处理

<document content>
```

### Context Builder 应该负责

- 去重
- token/字符预算
- 引用编号
- 文件路径格式化
- Java 行号引用
- Markdown 标题路径引用
- 控制代码和文档比例
- 保留检索来源和排序依据
- 避免将同一个类和其中多个高度重叠的方法全部重复放入上下文

### 不建议 Context Builder 负责

- 调用 LLM
- 生成最终答案
- 判断答案真假
- 解析自然语言意图
- 执行 Agent 工具调用

保持 Context Builder 独立后，可以先人工检查上下文质量，再决定接入哪一种大模型。

### 建议增加 CLI

例如：

```powershell
devcontext context "购票事务是如何实现的？" --top-k 5
```

输出：

```text
Query: 购票事务是如何实现的？

[C1] TxService.java:120-168
...

[C2] docs/design.md > 订单模块 > 事务处理
...
```

### 这一阶段的验收条件

- 每个 ContextItem 都有稳定引用。
- Java 引用包含文件和行号。
- Markdown 引用包含文件和标题路径。
- 不出现重复 Chunk。
- 总长度不超过配置预算。
- MIXED 查询能够同时保留代码和文档。
- Context Builder 不依赖具体 LLM SDK。
- 至少有 10 条单元测试覆盖去重、预算、引用和混合来源。

---

## 第三优先级：在评测保护下优化检索

评测和 Context Builder 就绪后，再优化检索。

### 1. 为混合查询做来源平衡

现有数据已经显示：

```text
Keyword 容易只返回代码
Vector 容易只返回文档
Hybrid 才能把两者拼起来
```

可以考虑简单的来源配额：

```text
Top 5:
  至少 1～2 个 Java Chunk
  至少 1～2 个 Markdown Chunk
  其余按 RRF 分数填充
```

但这个策略不应该对所有问题强制使用。

例如纯代码问题：

```text
login 方法在哪里？
```

强制插入两个文档结果反而会降低上下文质量。

因此建议先使用一个简单的 query intent：

```text
CODE
DOC
MIXED
UNKNOWN
```

或者只对 benchmark 明确标记为 MIXED 的查询实验来源平衡，不需要马上引入复杂模型。

---

### 2. 改进 Markdown 的 embedding_text

当前可以 A/B 测试把完整标题路径加入 Embedding 文本：

```text
Document section
Path: 系统设计 > 订单模块 > 事务处理
Title: 事务处理

Content:
...
```

而不是只放当前标题和正文。

原因是标题路径提供了非常重要的语义上下文。例如正文只写“本模块采用……”，如果没有上级标题，Embedding 模型并不知道“本模块”是订单模块还是支付模块。

注意：这应该通过评测验证，不要直接假设一定提升所有场景。

---

### 3. 对代码查询保留关键词优先特性

当前关键词检索的 MRR 高于 Hybrid：

```text
keyword MRR = 0.875
hybrid MRR  = 0.771
```

说明精确代码问题中，关键词排序经常比融合排序更好。

可以考虑：

```text
如果问题包含明显的 Java 标识符：
  提高 keyword RRF 权重
否则：
  使用默认平衡权重
```

明显标识符可能包括：

- 驼峰名称
- 全大写常量
- 带括号的方法形式
- 完整包名
- `.java`
- 注解名

但仍然应该先在扩展评测集上验证。

---

### 4. 增加过滤条件

建议 search 支持：

```text
--repository
--source-type
--chunk-type
--module
--package
--path-prefix
```

例如：

```powershell
devcontext search "事务处理" `
  --mode hybrid `
  --source-type JAVA `
  --module ticket-service
```

这能够显著降低不必要的候选竞争，也为以后 Web API 提供稳定查询契约。

---

### 5. 增强检索可解释性

返回结果增加：

```text
keyword_rank
keyword_score
vector_rank
vector_similarity
rrf_score
matched_identifiers
```

同时让评测报告能够输出：

```text
为什么这个结果排在第一？
正确答案在哪一路被召回？
在哪个阶段掉出了 Top 5？
```

## 第四优先级：增强解析和导入可靠性

### Java 解析

建议按以下顺序补充：

1. enum
2. record
3. annotation type
4. 字段
5. 完全限定符号名
6. 重载方法唯一标识
7. SymbolSolver
8. 调用关系

前四项成本较低，可以尽早完善 Chunk 类型覆盖。

  ↓
代码块中的 # 不作为标题
  ↓
遇到关闭 fence
  ↓
恢复标题识别
```

然后再考虑：

- 列表与表格完整性
- 章节之间少量 overlap
- 超长段落的句子级切分
- Markdown AST 库

### 导入报告

建议每次 ingest 生成结构化报告：

```json
{
  "run_id": "...",
  "started_at": "...",
  "repository": "...",
  "java_files_scanned": 218,

}
```

这样比终端日志更适合作为可复现验收证据。

## 第五优先级：缓存与索引工程化

### 缓存压缩

当前 JSONL 缓存可以增加：

```text
devcontext cache compact
```

行为：

1. 读取全部有效记录。
2. 按 key 保留最后一条。
3. 写入临时文件。
4. 校验临时文件。
5. 原子替换原缓存。

### 缓存并发安全

增加：

- 文件锁
- 临时文件
- 原子 rename
- 损坏行统计
- 模型维度隔离

### 索引版本

建议增加一个 ingestion/index manifest，例如：

```json
{
  "schema_version": 1,
  "parser_version": "0.2.0",
  "chunk_template_version": "java-v2",
  "embedding_model": "text-embedding-v4",
  "embedding_dimensions": 1024,
  "indexed_at": "2026-09-23T..."
}
```

它可以保存在数据库表或 artifacts 中。

当 `embedding_text` 模板改变时，即使源码没有变，向量也必须重建。版本信息可以防止新旧索引混用。

# 六、现阶段不建议优先做的事情

## 1. 不建议马上上 LangChain 或 LangGraph

当前流程很线性：

```text
parse → chunk → embed → store → retrieve
```

没有复杂工具编排、循环执行或多 Agent 协作需求。

现在引入框架会增加：

- 抽象层
- 调试难度
- 依赖
- 数据模型转换
- 隐藏的默认行为

等到出现这些需求时再考虑：

- 多轮工具调用
- Query Rewrite
- 检索失败自动回退
- 代码关系查询
- 多步骤规划
- 多仓库路由

---

## 2. 不建议马上做 HNSW

当前只有 2901 个 Chunk，精确向量扫描简单且结果确定。

现在的约 466 ms 向量检索延迟包含外部 Embedding 请求，不等于数据库向量扫描用了 466 ms。

应该先把延迟拆开。如果数据库部分只有几毫秒到几十毫秒，HNSW 不会解决真正瓶颈。

---

## 3. 不建议马上接入 LLM 生成答案

如果现在直接接 LLM，会遇到：

- 引用信息不完整
- 上下文可能重复
- Java 和文档比例不可控
- 超长上下文没有预算管理
- 无法判断错误来自检索还是生成
- 评测集不足以验证改动

更合理的顺序是：

```text
检索质量稳定
  ↓
Context Builder 可人工检查
  ↓
引用格式稳定
  ↓
再接入 LLM
```

---

## 4. 不建议马上实现完整调用图

调用图需要：

- SymbolSolver
- Maven 依赖解析
- 重载解析
- 接口动态绑定
- 可能的反射处理
- Spring Bean 关系
- 跨模块类型解析

成本很高，而且当前检索 MVP 还没有评测证明这是最急需的能力。

先收集真实问题。如果大量问题都属于：

```text
这个 Controller 最后调用了哪个 Mapper？
这个接口的实现类是哪一个？
这个方法被谁调用？
```

再把 SymbolSolver 和调用图提到前面。

# 七、推荐的开发路线

## 里程碑 A：检索质量基线

目标：让当前检索指标可信。

工作内容：

- 扩展到 30～50 条 benchmark
- 更新过期 ground truth
- 支持代码路径、类、方法、签名、行号匹配
- 支持文档 heading path 匹配
- 支持多个等价答案
- 增加 CODE/DOC/MIXED 分类指标
- 增加 mixed 双来源命中指标
- 拆分 Embedding、SQL、融合耗时
- 输出逐条失败分析

完成标准：

```text
任何一次检索修改，都可以明确回答：
改进了哪些问题？
退化了哪些问题？
为什么？
```

---

## 里程碑 B：Context Builder 与 Citation

目标：把检索结果转换成稳定、可读、可引用的上下文。

工作内容：

- 扩展 SearchResult 字段
- Java 文件与行号引用
- Markdown 文件与标题路径引用
- Chunk 去重
- 相邻 Chunk 合并
- token/字符预算
- Java/Markdown 来源平衡
- 新增 `context` CLI
- 增加 Context Builder 单元测试

完成标准：

```text
不调用 LLM，也能从 CLI 输出一份结构化、
无重复、长度可控、引用完整的上下文包。
```

---

## 里程碑 C：有评测支撑的检索优化

目标：提升 Top 3 排序和混合问题覆盖率。

工作内容：

- A/B 测试完整 heading path 的 Embedding 文本
- 试验来源平衡
- 对代码标识符查询提高关键词权重
- 增加搜索过滤
- 暴露各路 rank 和 score
- 使用 `EXPLAIN ANALYZE` 检查关键词 SQL
- 增加 `embedding_model` 一致性检查

完成标准：

- Recall@5 不下降
- Hybrid Recall@3 明显提升或至少不退化
- MIXED 双来源命中率达到目标
- 延迟增长有明确上限
- 所有排序变化都有评测证据

---

## 里程碑 D：答案生成

只有完成前三个里程碑后，再加入：

```text
Question
  ↓
Hybrid Retrieval
  ↓
Context Builder
  ↓
Prompt Builder
  ↓
LLM
  ↓
Answer + Citations
```

第一版甚至不需要 Agent，只需要一个简单的 Answer Generator：

- 强制仅根据上下文回答
- 每个结论带引用
- 上下文不足时明确说明
- 不允许生成不存在的文件和行号
- 答案引用必须能够映射回 ContextItem

# 八、建议的最近一个开发迭代

如果只选择一个短迭代，我建议按下面顺序做。

## 第 1 步：增强评测数据模型

修改 benchmark 和 matcher，使它支持：

```text
class_name
signature
heading_path
start_line
any_of
```

同时把 benchmark 扩展到至少 30 条。

## 第 2 步：扩展 SearchResult

至少增加：

```text
heading_path
class_name
signature
module
package_name
annotations
javadoc
keyword_rank
vector_rank
```

## 第 3 步：实现 Context Builder

支持：

```text
去重
引用
预算
Java/Markdown 模板
混合来源保留
```

## 第 4 步：新增 context CLI

例如：

```powershell
devcontext context "购票操作为什么需要事务？" --top-k 5
```

## 第 5 步：用 benchmark 验证 Context

除了 Recall，还可以开始加入：

- 引用完整率
- 重复上下文率
- 混合来源覆盖率
- 上下文总长度
- 相关 Chunk 在预算内保留率

这会形成下一阶段最关键的闭环：

```text
解析质量
  ↓
检索质量
  ↓
上下文质量
  ↓
以后才是答案质量
```

# 九、最终判断

当前项目的真实状态可以概括为：

> 检索 MVP 已经完成，并且有真实仓库数据、数据库存储、Embedding 调用和小规模评测支撑；它不是空壳，也不只是设计文档。

目前已经实现：

- 218 个 Java 文件成功解析
- 57 个 Markdown 文件成功解析
- 538 个 Java Chunk
- 2363 个文档 Chunk
- 总计 2901 个 Chunk
- 1024 维 Embedding
- 本地 Embedding 缓存
- PostgreSQL/pgvector 统一存储
- keyword/vector/hybrid 三路检索
- 12 条基础 benchmark
- Hybrid Recall@5 达到 1.0
- Python 和 Java 基础测试通过
- Git 工作区干净，已有初始功能提交

但距离“完整知识助手”还缺少：

- 足够可信的评测集
- Context Builder
- 稳定引用
- 上下文预算
- 答案生成
- API/UI
- 更强的工程可靠性

最推荐的下一条主线是：

> 先把评测从“能跑”提升到“可信”，然后实现 Context Builder 与引用；之后再通过评测决定是否调整检索策略，最后才接入 LLM。

这是当前项目从“技术原型”走向“可用系统”最稳妥、收益最高的路径。
