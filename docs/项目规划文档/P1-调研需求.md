你现在作为 **DevContext-Java 项目的技术调研 Agent** 工作。

你的任务不是开发 DevContext，也不是完整学习或总结开源项目，而是在正式开发前，对 **Continue、JavaParser、RAGFlow** 三个项目进行一次**问题驱动、范围受控、面向工程决策的定向调研**。

最终需要产出：

`开源项目调研.md`

这份文档将作为 DevContext 后续架构设计、模块设计、编码和 AI 辅助开发的重要上层参考。

后续其他 AI Agent 会阅读这份调研文档，因此要求：

* 结论准确；
* 能追溯到真实源码/官方文档；
* 明确区分“开源项目怎么做”和“DevContext 最终决定怎么做”；
* 不为了模仿开源项目而增加无必要复杂度；
* 所有调研必须服务于 DevContext 10～15 天 MVP。

项目暂定名称：

`DevContext-Java`

项目不是 Cursor、Codex、Claude Code 等 Coding Agent 的替代品。

* 写代码；
* 修改代码；

> **面向 Java 项目的代码与设计知识混合 Context Retrieval 系统。**

重点研究：


> **如何为 LLM / Agent 找到正确、完整、可验证的项目 Context。**

因此项目核心不是“模型多强”，而是：

`Context Engineering`

# 五、核心 Research Questions

## Q1

一个代码 Repository 应该如何建立可检索 Index？

需要回答：

* Repository 到 Searchable Context 中间有哪些阶段？
* 是否应该存在独立 Chunk 层？
* Chunk 是否应该和 Vector DB 解耦？
* 一个 Repository 为什么可能需要多种 Index？

---

## Q2

为什么代码不能简单使用普通文本固定长度切分？

需要研究：

* 成熟 Code Indexing 系统如何考虑语法结构；
* Function / Class / Method 等代码结构是否应该成为 Chunk 边界；
* 结构化 Chunk 应保留哪些 metadata。

---

## Q3

为什么 Coding Agent / Code RAG 不应该只依赖 Vector Search？

重点研究：

```text
Keyword Search
vs
Semantic Search
```

分别适合：

* Symbol；
* Class；
* Method；
* Framework API；
* 自然语言问题；

中的哪些场景。

---

## Q4

是否应该同时建立：

```text
Full-text Index
+
Vector Index
```

如果应该：

需要解释：

* 两者解决的不同问题；
* 是否共享同一 Chunk 数据源；
* 如何在 DevContext 中简化实现。

---

## Q5

Markdown 和 Java 是否应该采用不同 Chunk 策略？

重点比较：

```text
Markdown
→ Heading-aware / Structure-aware

Java
→ AST-aware
```

不要默认存在一种万能 Chunk Strategy。

---

## Q6

多个 Retriever 的结果应该如何融合？

需要理解：

```text
Vector Ranking
+
Keyword Ranking
```

为什么不能简单直接比较原始 score。

重点研究：

`Reciprocal Rank Fusion / RRF`

但不要求复杂数学推导。

---

## Q7

Repository 代码发生变化后，索引应该如何更新？

重点研究：

* Full reindex；
* Incremental index；
* file hash；
* content hash；
* changed file detection；

等设计。

注意：

DevContext V1 可以暂时全量重建。

本次研究主要判断：

> 增量索引是否应该作为 P1 演进方向。

---

## Q8

Retrieval 是否应该独立于 LLM Generation 进行 Evaluation？

需要分析：

* 为什么不能只通过最终聊天回答判断 RAG 效果；
* Retrieval Test 应该测试什么；
* DevContext 应该如何建立自己的 Benchmark。

# 三十二、建议最终得到一个 Decision Table

例如：

```text
| Decision | Choice | Reason | Source | Phase |
|---|---|---|---|---|
| Java parsing | JavaParser | Java-only，AST结构足够 | JavaParser | P0 |
| Code Chunk | Method/Class | 保留代码语义边界 | Continue + JavaParser | P0 |
| Document Chunk | Heading-aware | 保留文档章节结构 | RAGFlow | P0 |
| Keyword | PostgreSQL FTS | 减少基础设施 | Continue/RAGFlow启发 | P0 |
| Vector | pgvector | 与Postgres统一 | RAGFlow启发 | P0 |
| Fusion | RRF | 避免异构score直接比较 | Retrieval Research | P0 |
| Rerank | Cross Encoder | 提升TopK精排 | RAGFlow | P1 |
| Incremental | content hash | 避免全Repo重建 | Continue | P1 |
| Symbol | SymbolSolver | 精确reference能力 | JavaParser | P2 |
```

表中的具体结果必须根据真实研究确认。

不能直接照抄示例。

# 三十三、时间限制

这项调研应控制在：

```text
0.5 ～ 1 Day
```

不要为了完整理解三个项目无限扩展。

停止条件：

当能够清楚解释下面这条链路时：

```text
Java Repository

↓

JavaParser / Markdown Parser

↓

CodeChunk / DocChunk

↓

PostgreSQL

├── Full Text Search
│
└── pgvector

↓

Keyword + Vector Retrieval

↓

RRF

↓

Top-K Context

↓

LangGraph

↓

LLM
```

并能够回答：

```text
为什么代码不能普通固定Chunk？

为什么使用JavaParser？

为什么不用Tree-sitter？

为什么同时需要Keyword和Vector？

为什么不直接照搬Continue？

RAGFlow给Retrieval设计什么启发？

为什么SymbolSolver不进入V1？

为什么Incremental Index可以晚做？

为什么Retrieval必须独立Evaluation？
```

则立即停止调研。

不要继续扩大参考项目范围。
