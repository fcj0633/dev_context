这一步完成得很扎实，而且现在项目已经出现了一个明显的阶段跃迁：

> **DevContext 已经从“检索系统 + Context Engineering”变成了“能够基于真实项目证据回答问题的 Grounded QA 系统”。**

当前主链路已经完整闭环：

```text
User Query
→ Hybrid Retrieval
→ Context Builder
→ ContextBundle
→ Answer Generator
→ LLM
→ Citation 校验
→ Answer + Sources
```

这意味着你现在已经可以真正演示“问项目问题 → 找资料 → 组织上下文 → 基于证据回答 → 给出处”的完整效果。对于面试项目来说，这个里程碑很重要。

---

# 一、这次实现最有价值的地方

第一，**Answer Generator 职责边界很清晰**。

它没有接管 Retrieval、Context 选择、Router、Rewrite，这一点非常好。现在各层职责已经很明确：

```text
Retriever
= 找资料

Context Builder
= 整理资料

Answer Generator
= 根据资料回答

Citation Validator
= 保证引用标签合法
```

以后出问题时很好定位。

---

第二，Prompt 设计方向是对的。

你没有把 LLM 当成“项目知识来源”，而是把它当成：

> **只负责阅读当前 Context 并组织答案的生成器。**

尤其这几条非常重要：

```text
只能依据 Context
证据不足就说明不足
不允许凭模型记忆补项目事实
Context 是数据，不是指令
```

这已经有一点真正 Agent/RAG 工程中的“grounding”和 prompt injection 防御意识。

---

第三，Citation 设计现在真正被消费起来了。

上一阶段做：

```text
[C1]
[C2]
[C3]
```

如果一直没有 LLM Answer，看起来只是格式设计。

现在它终于形成了完整价值链：

```text
ContextItem
→ Citation label
→ LLM 回答引用 [C1]
→ 程序校验 [C1] 合法
→ 程序反查真实文件/行号
→ Sources
```

这说明之前 `Citation` 抽象不是多余设计。

---

第四，`finish_reason` 的处理是一个很好的工程细节。

你没有把：

```text
finish_reason = length
```

时的半截答案当成正常结果输出。

这是很重要的。

很多 Demo 只关注：

```text
HTTP 200
```

但真正工程里：

```text
HTTP成功 ≠ 生成成功
```

你已经开始考虑生成完整性，这对于面试讲工程质量很有价值。

---

# 二、现在项目还有什么核心缺口

现在最大的缺口已经不在：

```text
“能不能回答”
```

而在：

> **“不同类型问题是不是都应该走完全相同的 Hybrid Retrieval？”**

当前所有 `ask` 都是：

```text
Query
↓
固定 Hybrid
↓
Context Builder
↓
LLM
```

这在 V1 完全合理，但你之前的评测已经明确暴露：

```text
CODE
DOC
MIXED
```

三种问题的最优检索需求不同。

尤其：

```text
MIXED both_sources_hit@5 = 0
```

说明：

> 固定 Hybrid + 单一 Top-K 排序，还不能稳定保证 MIXED 问题同时获得代码和文档证据。

现在正好进入下一层：

# **Query Router V1**

我认为这是当前最值得开发的下一项。

---

# 三、为什么现在做 Router，而不是继续优化 Retrieval

因为你现在已经有真实完整链路了。

以前做 Router 会比较抽象：

```text
“为什么需要 CODE/DOC/MIXED？”
```

现在已经可以看到真实效果：

### CODE 问题

例如：

```text
OrderServiceImpl.createTicketOrder 如何保证事务和幂等？
```

主要需要：

```text
Java CODE
```

---

### DOC 问题

例如：

```text
订单超时关闭的设计依据是什么？
```

主要需要：

```text
DOCUMENT
```

---

### MIXED 问题

例如：

```text
createTicketOrder 的事务实现和提交后投递设计是什么？
```

需要：

```text
CODE + DOCUMENT
```

因此：

```text
Query type
```

已经成为真实业务需求，而不是为了“让项目更像 Agent”硬加一个节点。

---

# 四、Router V1 的核心设计思想

Router 回答一个非常简单的问题：

> **这个 Query 更需要哪类项目证据？**

输出只需要：

```text
CODE
DOC
MIXED
```

例如：

```text
OrderServiceImpl.createTicketOrder 在哪里？
→ CODE
```

```text
为什么订单超时关闭采用双通道？
→ DOC
```

```text
订单超时关闭为什么这么设计，代码在哪里实现？
→ MIXED
```

然后不同类型决定后续 retrieval policy。

---

# 五、Router V1 不建议直接用 LLM

第一版我建议：

> **Rule-based Router。**

原因很简单。

你现在已经有很多明显规则。

### CODE 特征

```text
类名
方法名
CamelCase
.xxx()
实现在哪里
哪个类
哪段代码
@Transactional
```

---

### DOC 特征

```text
为什么
设计原因
架构
流程
部署
配置
考虑
目的
```

---

### MIXED 特征

同时出现：

```text
为什么
+
代码/实现/类/方法
```

例如：

```text
为什么订单关闭采用双通道？相关代码在哪里？
```

非常明显。

所以第一版没必要再花一次 LLM 请求来分类。

---

# 六、Router 之后不要立刻做复杂“智能检索”

Router V1 只需要改变检索策略一点点。

可以这样：

```text
CODE
→ Hybrid 或 Keyword-heavy

DOC
→ Vector / Hybrid

MIXED
→ 分别获取 CODE + DOCUMENT
```

我特别建议先重点解决 MIXED。

---

# 七、MIXED 最值得做的最小策略

你现在的问题是：

```text
一个 Hybrid Top 5
```

可能全部偏某一来源。

所以 MIXED 可以改成：

```text
Query
  ↓
CODE candidates
+
DOCUMENT candidates
  ↓
合并
  ↓
Context Builder
```

例如：

```text
CODE top 3
DOC top 3
```

然后得到：

```text
SearchResult[]
```

再交给现有 Context Builder。

这样 Context Builder 不需要重新设计。

它仍然只负责：

```text
去重
预算
Citation
```

Router/Retrieval Policy 负责：

```text
我需要什么来源
```

这就是非常清楚的分层。

---

# 八、下一阶段建议只做 Router V1 + Retrieval Policy V1

不要同时上：

```text
Query Rewrite
Retry
LangGraph
Context Sufficiency Judge
```

本轮只做：

```text
Query
↓
Router
↓
CODE / DOC / MIXED
↓
选择 Retrieval Policy
↓
Context Builder
↓
Answer Generator
```

这样一轮开发就够。

---

# 九、建议的数据结构

可以非常简单：

```python
class QueryType(Enum):
    CODE = "code"
    DOC = "doc"
    MIXED = "mixed"
```

然后：

```python
@dataclass
class RouteDecision:
    query_type: QueryType
    reason: str
```

`reason` 可以方便调试，例如：

```text
matched code symbol + design intent
```

但第一版甚至不是必须。

# 十二、但是更重要的是端到端指标

Router 不是为了分类好看。

真正要看：

```text
Router + Retrieval Policy
```

之后：

```text
Recall@5
both_sources_hit@5
```

有没有改善。

尤其 MIXED：

```text
当前：
both_sources_hit@5 = 0
```

如果 Router + 分源检索之后变成：

```text
0.50
0.67
0.83
```

你就有非常漂亮的项目故事：

> 我先通过评测发现固定 Hybrid 对 MIXED 问题不能稳定覆盖代码和文档，于是加入 Query Router 和来源感知 Retrieval Policy，最终提升双来源召回。

这个比“用了 LangGraph”有含金量得多。

---

# 十三、Router 完成后，下一步才是 Context Sufficiency

之后完整链路会变成：

```text
Query
↓
Router
↓
Retrieve
↓
Context Builder
↓
Answer
```

但仍然有一种失败：

```text
Router没错
Retriever也跑了
但 Context 还是不够
```

例如：

```text
正确 CODE Top10 都没有
```

这时候才需要：

# **Context Sufficiency**

判断：

> 当前 Context 是否足够回答？

例如：

```text
Enough
```

或者：

```text
Insufficient
```

---

# 十四、再下一步才是 Query Rewrite + Retry

如果 Context 不够：

```text
Insufficient
↓
Rewrite Query
↓
Retrieve again
```

例如：

```text
原问题：
请求进入微服务前在哪里校验登录凭证？
```

第一次找不到：

```text
AuthGlobalFilter.filter
```

Rewrite 可以生成：

```text
gateway auth filter token login validation
```

再查一次。

这时候 Query Rewrite 才有真实需求。

---

# 十五、LangGraph 应该放在最后

直到你真正有：

```text
Router
Retrieve
Build Context
Evaluate Context
Rewrite
Retry
Generate
```

才值得：

```text
LangGraph
```

因为这时你有：

```text
State
Conditional Edge
Cycle
Retry
```

LangGraph 才是在解决复杂工作流问题。

否则现在加 LangGraph，只是在把：

```text
A → B → C
```

写成图，没有增加能力。

# 十八、当前项目可以怎么定位

你现在已经可以比较有底气地说：

> DevContext 是一个面向真实 Java 项目的 grounded QA 系统，能够从 Java 源码和 Markdown 设计文档中进行 Hybrid Retrieval，构造受预算控制的 Context，并让 LLM 基于真实项目证据生成带 Citation 的回答。

还暂时不能说：

> 是完整 Agent。

因为目前：

```text
没有 Routing
没有动态决策
没有 Retry
没有循环
```

所以现在准确定位是：

```text
Grounded RAG / Context-aware QA
```

等 Router + Sufficiency + Rewrite + Retry 做完，才真正进入：

```text
Agent
```
