# 4. P0 核心开发原则

整个开发阶段遵循五条原则。

## 4.1 先做 Retrieval，再做 Agent

顺序：

```text
Parsing
↓
Chunking
↓
Storage
↓
Retrieval
↓
Evaluation
↓
Generation
↓
Agentic Routing
```

不要：

```text
LangGraph
↓
Agent
↓
再回来补 Retriever
```

否则后期出了问题，很难判断到底是：

```text
Parser
Chunk
Retriever
Router
Prompt
LLM
```

哪一层出错。

---

## 4.2 每完成一层，都必须能单独运行

例如：

```text
Java Parser
```

必须可以独立运行：

```bash
java-parser --file TicketServiceImpl.java
```

输出：

```json
[
  {
    "chunkType": "METHOD",
    "className": "TicketServiceImpl",
    "methodName": "purchaseTicket"
  }
]
```

而不是必须启动整个 DevContext 才知道 Parser 是否正常。

同样：

```text
Retriever
```

必须能够直接：

```text
query
↓
Top-K chunks
```

不经过 LLM。

# 17. Method Content 获取方式

禁止：

```java
method.toString()
```

V1 使用：

```text
Method Range
+
原始文件内容
```

按：

```text
startLine
endLine
```

直接切片。

例如：

```text
120 ～ 188
```

就直接从原文件读取：

```text
第 120～188 行
```

这样保证：

```text
content
```

和：

```text
Citation
```

完全一致。

这一选择已经由 JavaParser 调研确认。

# 18. CLASS Chunk

CLASS 不保存整个 Java 类。

例如不要：

```text
800 行 TicketServiceImpl
→ 一个 Chunk
```

而生成：

```java
@Service
public class TicketServiceImpl implements TicketService {

    purchaseTicket(...);

    cancelTicket(...);

    refundTicket(...);
}
```

即：

```text
Class Annotation
+
Class Declaration
+
extends / implements
+
Method Signature List
```

这样 CLASS Chunk 负责回答：

```text
这个类负责什么？
有哪些主要方法？
实现了什么接口？
```

而 METHOD Chunk 负责回答：

```text
某个功能具体怎么实现？
```

JavaParser 调研对 V1 的建议正是：

```text
METHOD 主体
+
CLASS Summary 辅助
```

# 49. Recall@K

回答：

```text
正确 Chunk 是否出现在前 K？
```

```text

```


# 50. MRR

回答：

```text
正确 Chunk 排得靠不靠前？
```

如果正确答案总是：

```text
第 1
```

显然比：

```text
第 5
```

更好。

---

# 51. 评测时不要过滤低分结果

Evaluation：

```text
threshold = 0
```

拿完整 Ranking。

然后再：

```text
Top 3
Top 5
```

计算指标。

不要让：

```text
similarity threshold
```

提前把正确 Chunk 删除。

RAGFlow 的离线 benchmark 也是使用零阈值取得完整排名再做评测。


