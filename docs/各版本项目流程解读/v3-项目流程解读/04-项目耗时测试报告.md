这是这次 profiling 最有意义的结论之一。

# 五、当前真正的 P0：Section 数量失控

这是我认为这次测试**最重要的结果**。

同一个问题、同样的参数：

```text
flow-01

471.1s → 11 sections
113.7s → 3 sections
435.9s → 8 sections
```

完全相同输入：

```text
最大相差 4.1 倍
```

另一个：

```text
teach-token-bucket

397.3s → 10 sections
353.2s → 11 sections
132.0s → 3 sections
```

而统计结果：

```text
sections       ↔ latency   +0.94
LLM call count ↔ latency   +0.98
output tokens  ↔ latency   +0.98
```

这说明现在的链路实际上是：

```text
ExplanationPlanner
        ↓
决定 section 数
        ↓
每个 section 一次 LLM
        ↓
section 越多
        ↓
LLM calls 越多
        ↓
output tokens 越多
        ↓
耗时越高
```

所以当前的核心函数近似可以理解为：

```text
Total Latency
≈
LLM 调用次数 × 单次 LLM 延迟
```

而：

```text
LLM 调用次数
≈
基础规划调用
+
Section 数
+
Review
+
Revision
+
Composer
```

因此：

> **“节数”不是单纯回答格式问题，它现在实际上是一个性能参数。**

# 六、这说明 ExplanationPlanner 不只是 P1，它实际上有“双重性能影响”

报告按照直接耗时将：

```text
P0 Teaching Draft
P1 Explanation Planner
```

这个排序按“直接 wall-clock”是对的。

但是从**系统杠杆**上看，我甚至认为 ExplanationPlanner 和 Section Writer 应该并列看作第一优先级。

因为 ExplanationPlanner 自己已经：

```text
平均 39.9s
最大 75.3s
占总时间 20.1%
```

这已经非常慢。

但它还有一个更严重的**间接影响**：

```text
ExplanationPlanner
       ↓
产生 3 sections
       ↓
后续可能 100s

或者

产生 11 sections
       ↓
后续可能 400s+
```

所以它同时控制：

```text
直接成本：Planner 自己要 40 秒

间接成本：决定后面生成多少次
```

这就是典型的：

> **高杠杆节点。**

# 八、而且 Planner 的随机性已经开始影响系统架构行为

更严重的问题不是单纯：

```text
Planner = 40s
```

而是：

```text
同一个 Query
↓
Planner 第一次规划 11 sections
第二次规划 3 sections
第三次规划 8 sections
```

这意味着 Planner 不只是“内容稍有随机”。

```text

Reviewer 是否触发

```

也就是说：

> **Planner 的非确定性已经被放大成系统级非确定性。**

这是当前架构比“慢”更加值得处理的问题。

用户问同一句：

```text

可能 471 秒
```

产品体验会非常不可预测。

# 十一、Section 并行现在已经有非常强的数据依据

之前说“可以并行 Section”还属于架构推断。

现在已经有数据支持。

因为各 Section：

```text
共享：
core_mental_model

各自拥有：
section plan
section evidence
section context
```

生成过程中不存在：

```text
S2 必须读取 S1 的文本
S3 必须读取 S2 的输出
```

也就是说它天然是：

```text
               ┌→ S1
               ├→ S2
Plan + Evidence├→ S3
               ├→ S4
               └→ S5
                   ↓
                  Join
```

现在却实现成：

```text
S1 → S2 → S3 → S4 → S5
```

这是非常典型的可以从：

> **Sequential Pipeline → Fan-out/Fan-in**

进行优化的地方。

而且这会是一个很好讲的面试工程点。

# 十二、Composer 比原来想象得严重很多

这个结果也很重要：

```text
Composer

调用：21 次
平均：32.9s / call
总计：690.4s
```

而单个 Section：

```text
13.5～13.7s
```

Composer 一次大约等于：

```text
2～3 个 Section 的生成成本
```

为什么？

因为它拿到：

```text
S1 全文
S2 全文
S3 全文
...
```

然后让 LLM：

> 再把整篇文章重新生成一次。

所以现在实际上可能发生：

```text

先生成 S3
先生成 S4
先生成 S5

        ↓

Composer 再生成一遍完整答案
```

这其实是非常明显的 Token 重复计算。

# 十四、但这里要特别注意一个统计问题：Composer 和 P0 不能直接相加

报告中：

```text
Teaching Draft 37.7%
Composer       13.2%
```

不能理解成：

```text
37.7 + 13.2 = 50.9%
```

因为 Composer 是：

```text
Teaching Draft
    ├── S1
    ├── S2
    ├── ...
    └── Composer
```

或者第二次：

```text
Teaching Revision
    ├── revision section
    └── Composer
```

所以 Composer 是**子阶段**。

同理：

```text
Wasted LLM latency ≈ 13%
```

也是和现有阶段重叠的。

正确理解是：

> Teaching Draft 是顶层 wall-clock 成本；Composer 是告诉你 Teaching Draft/Revision 内部哪一部分在耗时。

这个区分后面计算“预计能快多少”时非常重要，否则会重复计算收益。

```text
→ Coverage 变化很小
```

那才值得改触发逻辑。

这和你之前分析过的 Second-round No-gain 正好可以衔接起来。

# 二十三、简单问题为什么也要 25～65 秒？

这个数据非常值得单独看。

Locate 问题虽然：

```text
没有 multi-pass
没有 Reviewer
没有 Revision
```

仍然有：

```text
5 次 LLM 调用
```

大致仍是：

```text
Evidence Planner
↓
SearchAction Planner
↓
Coverage
↓
Explanation Planner
↓
Writer
```

所以 Fast Path 目前只解决了：

> “最终怎么写。”

却没有真正解决：

> “简单问题是否需要经过完整 Agent Pipeline。”

这意味着现在的 Fast Path 其实还不够“Fast”。

真正的 Fast Path 应该考虑：

```text
LOCATE / 简短事实问题
        ↓
轻量 Query 分类
        ↓
Retrieval
        ↓
Direct Answer
```

而不是仍然先经历几轮复杂规划。

# 二十四、报告本身有两个统计表达需要修正

不影响整体结论，但建议后面把文档修一下。

### 第一个：`--repeat 3` 的描述存在矛盾

基线报告开头写：

> 样本之间是独立 Python 进程。

但当前 `cli.py::_run_ask()` 明确是：

```python
for index in range(repeats):
    result = run_once()
```

也就是：

> `--repeat 3` 是**同一个 Python 解释器里的三次运行**。

只是每次：

```python
_planned_workflow(...)
```

会重新构造 Workflow，所以不共享 Workflow 的可变状态。

因此准确描述应该是：

```text
同进程
+
每次重建 Workflow
+
不应称为 warm cache
```

这不影响当前 latency 结论，但报告里的环境说明应修正。

# 二十五、第二个：Case 表里的 `sections/path` 容易误导

比如：

```text
flow-01
```

表里写：

```text
path = multi_pass
sections = 11
```

但三次其实是：

```text
11 → multi-pass
3  → fast
8  → multi-pass
```

所以 Case 级表最好改成：

```text
planned_sections
11 / 3 / 8

path
multi / fast / multi
```

否则和后面“同题路径会变化”的结论冲突。

另外：

```text
summary.sections
```

代码里实际上统计的是：

```python
SectionExecutionTrace
```

因此 Fast Path 会显示：

```text
sections = 0
```

即使 ExplanationPlan 实际规划了 1～3 个 Sections。

所以后续分析必须优先使用：

```text
planned_section_count
```

而不是：

```text
summary.sections
```

来研究 Planner 行为。

# 二十七、下一轮实验应该分成两套 Benchmark

当前这 27 次非常适合作为：

> **Natural / Real-world Baseline**

因为没有强制 depth，反映实际默认体验。

但优化阶段最好再增加一个：

|---|---|

| Controlled Suite | 性能因果分析 |

# 二十八、我会重新定义当前优化优先级

如果只是按照“当前直接耗时”排序，报告里的排序基本正确。

但如果按照**工程杠杆 + 性能收益 + 风险**，我建议下一轮按这个顺序：

1. **ExplanationPlanner 稳定化 + 节数约束**：它自己占 20.1%，同时还决定后面要生成多少 Section，是最大的“放大器”。先让相同问题不要随机产生 3/8/11 节，并根据 brief/standard/detailed 建立明确 section 上限。

2. **Section 并行生成**：这是最大直接 wall-clock 项。不要改变 Section 内容逻辑，只把串行 fan-out 改成有界并发，这是风险相对低、收益很直接的一项。

3. **Composer 消融实验**：它平均 32.9 秒，而 `_deterministic_join()` 已经存在。先 A/B 测质量，再决定是取消、轻量化还是只在 deep 模式开启。

4. **Reviewer 超时与预算重构**：不能直接删 Reviewer，因为 11 次中 7 次触发 Revision；但“等 120 秒然后直接 accepted”必须解决。Reviewer 的 JSON 输出也没有理由预留 32768 tokens，应根据真实 output token p95 配预算。

5. **Wasted Latency 定位和清理**：先把那 25 次 wasted 按 stage/reason 聚合。平均 25.7 秒/request 是非常大的可回收空间。

6. **第二轮检索 Cost/Benefit**：重点分析 Round 1 到底救回多少 Coverage，而不是继续优化 pgvector。只有确认 no-gain 比例高，才改触发条件。

7. **Embedding 重复调用**：最后做。因为整个 Retrieval 只有 2%，即使完全消灭也不会改变用户体验。

# 二十九、如果把这次结果压缩成一句“面试级结论”

这个项目现在已经不再是：

> “我的 RAG 回答比较慢，我去优化一下向量检索。”

而可以变成：

> **我们通过调用级 tracing 建立了 Agentic RAG 的端到端延迟模型，发现性能瓶颈并不在 Retrieval，而在 LLM orchestration：复杂请求最高形成 23 层串行 LLM Critical Path；Explanation Planner 的不稳定 section planning 会将相同请求的延迟放大 4.1 倍；Section 串行生成占 37.7%，Planner 占 20.1%，而实际 Retrieval 只有 2%。因此后续优化方向从数据库优化转向 Plan 稳定化、fan-out/fan-in 并发、LLM 调用压缩、stage-specific budget 与 conditional review。**

这其实比“把接口从 4 秒优化到 2 秒”更有项目价值。

# 三十、这次测试后，我对当前项目问题的最终判断

现在的 DevContext **检索已经不是主要矛盾**。

真正的问题已经从：

```text
RAG 能不能找到内容？
```

演变成：

```text
找到内容之后，
Agent 为了“把问题讲清楚”
到底需要多少次模型调用？
```

当前设计在回答质量方向走得比较远：

```text
Evidence Planning
Coverage
Explanation Planning
Section Writing
Composer
Reviewer
Revision
```

每一层单独看都有合理性。

但组合以后出现了典型 Agent 系统问题：

```text
每个节点都有价值
+
每个节点都调用一次 LLM
+
部分节点还是 N 次 LLM
+
全部串行
=
3～8 分钟
```

所以后面的目标不应该是删除“智能”。

而应该变成：

> **用更少的 Sequential LLM Calls，实现现在接近的回答质量。**

我建议下一步正式进入 **`Latency Optimization V1`**。第一轮不要同时改五六个地方，最好先做 **Planner 稳定化/节数预算 + Section 有界并行 + Composer A/B 消融** 三件事，然后用现在这套 profiler 原样复测。这样能非常清楚地得到“优化前 192.5s → 优化后多少秒，同时回答质量是否下降”的结果。
