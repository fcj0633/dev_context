这三步其实构成 V3 的**回答层核心闭环**：

> **④ 先规划“怎么讲” → ⑤ 按计划、按证据逐节生成 → ⑥ 检查“有没有讲错、讲偏、讲不清”，必要时只修有问题的章节。**

它们和前面的 `EvidenceWorkspace + Coverage` 分工非常清楚：

```text
前半段：
“项目里到底有什么证据、什么是真的？”

EvidenceWorkspace
        ↓
Coverage
        ↓
EvidencePackage

================ 分界线 ================

后半段：
“这些真实信息应该怎样让用户理解？”

ExplanationPlanner
        ↓
TeachingWriter / Section View
        ↓
Composer
        ↓
Grounding + TeachingReviewer
        ↓
Final Answer
```

下面把这三个流程拆开讲。

---

# 一、④ ExplanationPlanner：从“证据顺序”变成“理解顺序”

这是 V3 和 V2 很核心的区别。

前面的 `EvidencePlanner` 已经完成：

```text
ER1：需要证明什么
ER2：需要证明什么
ER3：需要证明什么
```

比如用户问：

> 为什么项目使用责任链校验？

EvidencePlanner 可能得到：

```text
ER1：证明项目确实存在责任链实现
ER2：找到实际业务入口
ER3：找到采用责任链的原因
ER4：找到 Handler 如何排序
ER5：找到扩展机制
```

但这只是：

> **调查顺序。**

如果直接拿这些 ER 当文章目录，很容易写成：

```text
1. 责任链代码在哪
2. 调用入口在哪
3. 文档怎么说
4. order 怎么写
5. Handler 怎么扩展
```

事实很多，但是读者仍然不知道：

> “所以为什么项目需要它？”

---

## 1. ExplanationPlanner 输入什么

当前 V3 中，它接收的核心输入是：

```text
UserRequest
+
EvidencePackage
```

也就是说，它工作时：

```text
检索已经完成
EvidenceWorkspace 已经冻结
Coverage 已经知道哪些 Requirement 满足、哪些不满足
```

它不是再去搜索。

它只负责：

> **根据已经找到的事实，设计一条解释路线。**

可以理解成：

```text
EvidencePlanner：
“我要调查什么？”

ExplanationPlanner：
“调查结果应该以什么认知顺序告诉用户？”
```

---

# 二、ExplanationPlanner 最重要的输出：ExplanationPlan

它不是直接生成正文，而是先生成一个结构化对象：

```text
ExplanationPlan
```

当前里面比较关键的是：

```text
answer_goal
direct_answer
audience_model
core_mental_model

primary_strategy
secondary_strategies

prerequisite_concepts
likely_misconceptions

sections

unresolved_gaps
conflicts

answer_depth
```

这实际上就是：

> **回答的“施工图”。**

---

# 三、`core_mental_model`：先决定全文到底想让用户记住什么

这是 V3 很重要的设计。

比如责任链问题，一个好的核心模型不是：

```text
AbstractChainHandler 有 mark、order、handler。
```

因为这是代码事实。

更好的 mental model 是：

> **责任链不是为了“能够校验”，而是为了把持续增长、有顺序、成本不同的校验规则，从稳定的主业务流程中拆出去。**

于是全文所有章节都应该围绕这个模型展开。

后面讲：

```text
mark
order
Handler
Spring 自动收集
提前失败
```

都不是孤立知识点。

它们分别回答：

```text
mark
→ 怎么把不同业务链隔离？

order
→ 怎么表达先后和成本优先级？

Handler
→ 怎么让规则独立扩展？

自动收集
→ 为什么新增规则可以不改主流程？
```

这就是：

```text
事实
↓
围绕一个核心模型形成解释
```

。

---

# 四、Explanation Strategy：决定采用什么讲解策略

当前 Planner 不只是输出章节。

还会选择：

```text
primary_strategy
secondary_strategies
```

例如责任链问题可能是：

```text
primary:
PROBLEM_SOLUTION

secondary:
CONCEPT_BUILDUP
TRADEOFF
FAILURE_ANALYSIS
```

意思是全文不是简单：

```text
定义
→ 类名
→ 方法
```

而是：

```text
先讲问题
↓
再建立概念
↓
解释为什么这样设计
↓
再讲它的代价和失败情形
```

不同问题可以不同。

比如：

```text
“这个方法在哪里？”
```

可能：

```text
LOCATION_ONLY
```

只需要很短。

而：

```text
“为什么这个设计能保证一致性？”
```

可能更适合：

```text
MECHANISM
+
FAILURE_ANALYSIS
+
TRADEOFF
```

所以 V3 不再强制所有问题套一个“万能八段式”。

---

# 五、Planner 接下来生成 Sections

例如责任链最终可能设计成：

```text
S1：先说问题是什么
section_type = PROBLEM_SETUP

S2：责任链的核心理解
section_type = MENTAL_MODEL

S3：项目中到底怎么实现
section_type = MECHANISM

S4：为什么 order 很重要
section_type = DESIGN_REASON

S5：不用责任链会发生什么
section_type = COMPARISON

S6：失败和边界
section_type = BOUNDARY

S7：总结
section_type = SUMMARY
```

注意：

```text
ER1 / ER2 / ER3 / ER4
```

不会机械变成：

```text
S1 / S2 / S3 / S4
```

这就是：

> **Investigation Order ≠ Explanation Order。**

---

# 六、每个 Section 里还有 ClaimPlan

Planner 不只是说：

> “S3 讲实现。”

还进一步规划这一节允许出现哪些类型的内容。

当前有四种 Claim：

```text
PROJECT_FACT
PROJECT_INFERENCE
GENERAL_CONCEPT
ILLUSTRATIVE_EXAMPLE
```

例如 S4：

> 为什么参数非空检查应该排在数据库查询之前？

可能规划：

```text
Claim A
PROJECT_FACT
“项目中 order 控制 Handler 顺序。”
Evidence: E3

Claim B
PROJECT_INFERENCE
“这说明顺序本身承担优先级语义。”
Evidence: E3

Claim C
GENERAL_CONCEPT
“便宜的纯参数校验通常应该在昂贵 I/O 前执行。”

Claim D
ILLUSTRATIVE_EXAMPLE
“假设用户名为空，如果先查数据库就会浪费一次 I/O。”
conditional = true
```

这一步非常重要。

因为它提前规定：

> **哪些是项目事实，哪些是推导，哪些只是教学知识，哪些只是例子。**

---

# 七、Planner 本身还有一层严格校验

模型不是输出什么都接受。

例如当前代码会检查：

```text
必须有 core_mental_model

LOCATION_ONLY
不能规划大量章节

NEGATIVE_CORRECTION
必须有 MISCONCEPTION 章节

PROJECT_FACT
必须绑定 Evidence

ILLUSTRATIVE_EXAMPLE
必须 conditional=true
并且必须写 assumptions

conditional Claim
不能标记成 CONFIRMED

Citation label
必须真实存在于 EvidencePackage
```

所以实际流程不是：

```text
LLM → ExplanationPlan
```

而是：

```text
LLM
↓
JSON Plan
↓
结构校验
↓
业务合法性校验
↓
ExplanationPlan
```

如果失败：

```text
fallback_explanation_plan()
```

会生成一个更保守的确定性计划。

你上一轮责任链的 Teach 输出中：

```text
Mental Model:
按证据逐条说明，不额外推断
```

其实就是 fallback plan 的典型表现。

---

# 八、④ 最终完成的事情

所以 ExplanationPlanner 可以浓缩成：

```text
EvidencePackage
        ↓
分析用户真正想理解什么
        ↓
建立 core mental model
        ↓
选择 explanation strategy
        ↓
设计章节顺序
        ↓
为每节绑定 Evidence
        ↓
为每条 Claim 标记语义类型
        ↓
ExplanationPlan
```

一句话：

> **它不负责写答案，它负责把“调查结果”翻译成“教学设计”。**

---

---
# 二、⑤ 教学生成：Section View + TeachingWriter + Composer

有了 ExplanationPlan，才真正进入写正文。

这里最关键的变化是：

> **不是把整个 EvidenceWorkspace 一次塞给模型写全文。**

而是：

```text
Plan
↓
每一节需要什么 Evidence
↓
建立自己的 Section View
↓
单独生成这一节
```

---

# 九、首先决定 Fast Path 还是 Deep/Multi-pass Path

当前会根据：

```text
answer_depth
+
section count
```

决定。

简单问题：

```text
brief
或者章节很少
```

可以：

```text
一次 Writer
↓
完整回答
```

也就是：

```text
Fast Path
```

复杂问题，比如：

```text
detailed
deep
章节 > 3
```

进入：

```text
Multi-pass
```

也就是：

```text
S1 → Writer

S2 → Writer

S3 → Writer

S4 → Writer

...
```

最后再 Composer。

---

# 十、为什么复杂问题不能一次把所有 Evidence 全塞给 Writer

假设：

```text
Workspace = 25 个 Chunk
```

完整答案有：

```text
8 个 Section
```

如果一次性：

```text
25 Evidence
+
8 Section Plan
+
Question
+
各种 Claim
↓
一个 LLM Prompt
```

容易出现三个问题。

第一：

```text
模型忘记前面章节的目标
```

第二：

```text
Citation 到底支持哪一节
变得模糊
```

第三：

```text
大量无关 Evidence 干扰当前论证
```

所以 V3 改成：

```text
Workspace
↓
按 Section Evidence Labels 切片
```

。

---

# 十一、Section View 到底是什么

假设 ExplanationPlan：

```text
S1 evidence:
E1 E3

S2 evidence:
E2 E5 E7

S3 evidence:
E4 E6
```

那么真正生成 S2 时：

```text
EvidenceWorkspace
        ↓
by_citation(E2,E5,E7)
        ↓
PromptContextView
        ↓
ContextBundle
```

Writer 只看到：

```text
E2
E5
E7
```

它不会看到：

```text
E1
E3
E4
E6
```

。

---

# 十二、Section View 还负责预算

不是：

```text
Section 要 3 条证据
→ 全部无脑塞进去
```

。

而是：

```text
Model Context Window
        -
System Prompt
        -
Question
        -
ExplanationPlan
        -
Output Reserve
        -
Safety Margin
        =
Evidence Context Budget
```

然后 `build_context_view()` 决定：

```text
哪些 Evidence 可以放进去
哪些被截断
哪些完全被省略
```

所以：

```text
EvidenceWorkspace
```

负责：

> 保持全部证据。

而：

```text
Section View
```

负责：

> 当前这一次模型调用能看到多少。

这个分层非常重要。

---

# 十三、TeachingWriter：根据 Section Type 用不同方式写

现在不是简单 Prompt：

> “请详细解释。”

Writer 会看到：

```text
Question
Core Mental Model

Current Section:
  title
  section_type
  teaching_goal
  key_points
  teaching_devices
  evidence_state
  claim plans

Available Citations

Section Context
```

然后不同类型有不同写法。

例如：

### `PROBLEM_SETUP`

要求：

```text
先制造问题
↓
说明为什么需要这个机制
```

### `EXECUTION_FLOW`

要求：

```text
按时序
↓
每一步职责
↓
为什么进入下一步
```

### `FAILURE_SCENARIO`

要求：

```text
正常状态
↓
故障发生
↓
状态变化
↓
系统如何恢复
```

### `TRADEOFF`

要求：

```text
方案 A
vs
方案 B
↓
为什么选择当前方案
↓
代价是什么
```

所以不是每一节都写成：

```text
定义
→ 代码
→ 优点
```

。

---

# 十四、Writer 必须遵守四层 Claim 边界

Writer Prompt 里明确区分：

```text
A 项目事实

B 基于项目事实推导

C 通用技术知识

D 假设案例
```

例如：

### 有 Evidence

可以：

> `AbstractChainContext` 会根据 `order` 排序处理器 [E3]。

### 推导

可以：

> 从这种排序机制可以看出，校验顺序已经从主流程代码位置中抽离出来。

### 通用知识

可以：

> 在一般工程实践中，低成本参数校验通常应该优先于数据库或 RPC 操作。

### 假设

可以：

> 假设未来增加一个风控规则，可以新增独立 Handler……

但不能：

> 项目当前已经存在风控 Handler。

除非有真实 Evidence。

---

# 十五、Section-scoped Citation Validation

这是 TeachingWriter 非常关键的一层。

假设：

```text
S2 permitted:
E2 E5 E7
```

Writer 返回：

```text
... [E2]
... [E9]
```

系统提取 Citation：

```text
E2 → allowed
E9 → invalid
```

所以：

```text
used_citations = E2

invalid_citations = E9
```

即使：

```text
E9
```

真的存在于 Workspace，

也不代表它可以支撑 S2。

所以 V3 的约束是：

> **“这个 Citation 存在”还不够，还必须是 Planner 为当前 Section 分配的 Evidence。**

这就是 Section-level Grounding。

---

# 十六、所有 Section 写完之后进入 Composer

现在可能有：

```text
Draft S1
Draft S2
Draft S3
Draft S4
Draft S5
```

如果直接：

```text
拼接
```

容易出现：

```text
重复
跳跃
术语不统一
章节过渡生硬
```

所以增加：

```text
SectionComposer
```

。

---

# 十七、Composer 的职责很窄

Composer 可以：

```text
重新组织过渡
减少重复
统一术语
改善开头结尾
调整章节顺序
```

但是禁止：

```text
新增 Project Fact
新增 Citation
新增类名 / Symbol
```

也就是说：

> Writer 负责“内容事实”，Composer 只负责“文章编辑”。

这是非常重要的职责隔离。

---

# 十八、Composer 还有一个确定性安全阀

假设各 Section 只使用：

```text
E1 E2 E5
```

Composer 最后突然输出：

```text
[E7]
```

那么：

```text
E7 ∉ drafts.used_citations
```

系统不会：

```text
把 E7 删除继续用 Composer 结果
```

而是：

```text
Composer output
↓
整体丢弃
↓
_deteministic_join(section drafts)
```

直接回退到：

```text
## S1
原 Draft

## S2
原 Draft

...
```

为什么？

因为：

> **如果 Composer 已经违反最重要的 Evidence 规则，那么同一输出中其它改写也不值得继续信任。**

这个设计很稳。

---

# 十九、⑤ 最终完成什么

整个教学生成就是：

```text
ExplanationPlan
        ↓
判断 Fast / Multi-pass
        ↓
每节提取 Evidence Labels
        ↓
Section View
        ↓
Token Budget
        ↓
TeachingWriter
        ↓
Section Citation Validation
        ↓
DraftSection[]
        ↓
SectionComposer
        ↓
TeachingDraft
```

一句话：

> **它把一篇复杂回答拆成若干“有独立教学目标、有独立证据边界”的小回答，再把它们编排成全文。**

---

---
# 三、⑥ 质量控制：Grounding + TeachingReviewer

回答写出来以后还不能直接结束。

V3 主要有两层质量控制：

```text
Grounding
=
确定性规则检查

TeachingReviewer
=
LLM 语义审稿
```

两者不是重复关系。

---

# 二十、为什么先要 Grounding

有些错误完全不需要 LLM 判断。

例如 Planner 已经说：

```text
Claim:
ILLUSTRATIVE_EXAMPLE
```

正文却：

```text
项目当前会产生 100 个并发请求……
```

没有：

```text
假设
例如
```

这已经可以通过字符串规则发现。

没必要花一次 LLM。

所以：

```text
Grounding
```

负责：

> **便宜、确定、必须守住的底线。**

---

# 二十一、当前 Grounding 主要检查四类问题

## 1. PROJECT_FACT_WITHOUT_EVIDENCE

Plan 说：

```text
PROJECT_FACT
```

但当前 Section：

```text
没有 evidence_labels
```

直接报：

```text
PROJECT_FACT_WITHOUT_EVIDENCE
```

---

## 2. CONDITIONAL_NOT_MARKED

Planner：

```text
conditional = true
```

例如：

> 如果 Lua 脚本确实做了原子检查，那么……

但 Writer 写成：

> Lua 脚本完成了原子检查。

正文里没有：

```text
如果
假设
```

就报错。

---

## 3. EXAMPLE_NOT_LABELLED

Planner：

```text
ILLUSTRATIVE_EXAMPLE
```

但是正文把例子当项目事实。

没有：

```text
例如
假设
可以想象
```

就报错。

---

## 4. UNVERIFIED_WRITTEN_AS_FACT

如果：

```text
Section evidence_state = UNVERIFIED
```

说明系统本身没有确认这些 Evidence 足够。

正文应该写：

```text
当前证据无法确认……
```

而不能：

```text
项目就是这样实现的。
```

否则 Grounding 报：

```text
UNVERIFIED_WRITTEN_AS_FACT
```

。

---

# 二十二、Grounding 的特点

它最大的优点是：

```text
不调用 LLM
```

所以：

```text
稳定
便宜
不会 hallucinate
```

但缺点也明显：

> 它只能检查非常结构化、非常明显的问题。

比如：

```text
E3
到底能不能支持
“责任链一定避免了循环依赖”
```

这种语义问题，Grounding 很难通过字符串判断。

所以需要第二层：

```text
TeachingReviewer
```

。

---

# 二十三、TeachingReviewer 审什么

TeachingReviewer 主要看两大类：

```text
事实 / Grounding

+

教学质量
```

。

---

# 二十四、事实层问题

例如：

```text
UNSUPPORTED_CLAIM
```

没有足够支持。

```text
FACT_INFERENCE_CONFUSION
```

把“推导”写成了“证据本身”。

```text
GENERAL_KNOWLEDGE_AS_PROJECT_FACT
```

把通用知识写成：

> 本项目就是这样。

```text
SECTION_EVIDENCE_MISMATCH
```

这个 Section 的结论和它使用的 Evidence 对不上。

---

# 二十五、教学层问题

例如：

```text
MISSING_MENTAL_MODEL
```

全文只有很多事实，没有一条主线。

```text
MISSING_WHY
```

只讲：

> 怎么实现。

没有讲：

> 为什么这样实现。

```text
POOR_SCAFFOLDING
```

直接从复杂细节开讲，没有逐层展开。

```text
ABRUPT_TRANSITION
```

章节之间跳跃。

```text
MISLABELED_EXAMPLE
```

假设案例被说成真实行为。

```text
UNHELPFUL_DETAIL
```

堆了很多对理解没帮助的源码细节。

---

# 二十六、Reviewer 不是每次都运行

为了控制成本，现在是三档门控。

### brief / LOCATION_ONLY

只做：

```text
Deterministic Grounding
```

不调用 LLM Reviewer。

因为一句：

> `takeToken()` 位于 xxx 类中 [E3]。

没必要再花一次完整 Reviewer。

---

### standard

只有出现：

```text
Grounding Issues
```

或者：

```text
Plan Conflict
```

才调用 Reviewer。

---

### detailed / deep

一定调用：

```text
TeachingReviewer
```

因为复杂长回答更容易：

```text
事实漂移
结构失衡
重复
漏 why
```

。

---

# 二十七、Reviewer 返回的不是一篇“新版全文”

这是非常重要的。

它返回类似：

```json id="4bu9cj"
{
  "accepted": false,
  "global_issues": [],
  "section_issues": [
    {
      "section_id": "S3",
      "issue_type": "MISSING_WHY",
      "description": "只说明 order 如何工作，没有解释为什么顺序本身重要"
    }
  ],
  "revision_required": ["S3"]
}
```

也就是说 Reviewer 的职责是：

> **诊断。**

而不是：

> **重写。**

# 二十八、为什么不让 Reviewer 重写整篇

因为假设：

```text
S1 正确
S2 正确
S3 不好
S4 正确
S5 正确
```

如果把全文交给 Reviewer：

```text
请重写
```

它可能：

```text
S3 修好了
但 S2 新增幻觉
S4 Citation 改错
```

。

所以 V3：

```text
Reviewer
↓
指出 S3
↓
Writer 重新写 S3
```

而：

```text
S1
S2
S4
S5
```

全部保留。

这叫：

> **Targeted Revision。**

# 二十九、定向重写时会发生什么

例如 Reviewer：

```text
revision_required = ["S3"]
```

Workflow：

```text
找到 ExplanationPlan.S3
↓
重新构造 S3 Section View
↓
仍然只给 S3 原来的 Evidence
↓
把 reviewer notes 加给 Writer
↓
TeachingWriter.write_section(...)
```

比如 Writer 会收到：

```text
revision_notes:
MISSING_WHY:
需要解释 order 为什么代表成本优先级
```

然后只重写：

```text
S3
```

。

之后：

```text
新的 S3
+
原 S1 S2 S4 S5
↓
重新 Composer
```

。

# 三十、最多只修一次

当前：

```text
MAX_REVISION_ROUNDS = 1
```

因此：

```text
Generate
↓
Review
↓
Revision
↓
Compose
↓
End
```

不会：

```text
Review
→ Rewrite
→ Review
→ Rewrite
→ Review
...
```

。

这是控制：

```text
cost
latency
agent instability
```

的重要设计。

# 三十一、Reviewer 自己失败怎么办

当前设计是：

```text
Reviewer API failure
JSON malformed
```

不会让整条回答失败。

而是：

```text
accepted = true
decision_source = fallback
error = ...
```

然后保留原回答。

也就是：

> **Review 是质量增强步骤，不是 Answer Availability 的强依赖。**

这属于：

```text
fail-open
```

策略。

优点：

```text
Reviewer 挂了，用户仍然有回答。
```

缺点：

```text
这一次回答其实没有真正通过 Review。
```

所以 Debug Trace 中必须保存：

```text
decision_source
error
```

才能区分。

# 三十二、把三个阶段放到一个完整例子里

用户问：

> 为什么项目使用责任链校验？

前面的 Retrieval 已经得到：

```text
E1 设计文档：if-else 会不断增长

E2 AbstractChainHandler

E3 AbstractChainContext：
按 mark 分组，order 排序

E4 注册 Handler

E5 车票查询责任链设计
```

然后进入④。

---

## ④ ExplanationPlanner

得到：

```text
Mental Model：

责任链不是为了让系统“能校验”，
而是为了把持续增长、有顺序、有不同成本的规则
从稳定主流程中拆出去。
```

设计：

```text
S1 为什么普通 if 会出问题
E1 E5

S2 责任链的核心模型
E1 E3

S3 当前项目怎么实现
E2 E3 E4

S4 order 为什么重要
E3 E5

S5 扩展性与代价
E1 E4 E5
```

---

## ⑤ Teaching Generation

生成 S3：

```text
Section View
=
E2 E3 E4
```

Writer 写：

> 项目使用 `AbstractChainHandler` 统一定义节点……[E2]

> `AbstractChainContext` 按 mark 收集并按 order 排序……[E3]

> 注册校验节点通过具体 Handler 接入……[E4]

如果 Writer 写：

```text
Lua 脚本保证责任链执行原子性 [E9]
```

但 S3 没有 E9：

```text
invalid citation
```

。

全部 S1～S5 完成后：

```text
Composer
```

组织成完整回答。

## ⑥ Quality Control

Grounding 检查：

```text
有没有无 Evidence Project Fact？
有没有假设说成事实？
有没有 UNVERIFIED 写成确定结论？
```

然后 Detailed：

```text
TeachingReviewer
```

发现：

```text
S4 只讲了 order 如何排序
没有讲为什么便宜的校验应该更早
```

返回：

```text
MISSING_WHY
revision_required = S4
```

系统只：

```text
重新生成 S4
```

然后重新 Composer。

最终回答完成。

# 三十三、最简记忆方式

你可以把这三阶段记成三个问题：

```text
④ ExplanationPlanner
回答：
“应该讲什么、先讲什么、用什么核心模型讲？”

        ↓

⑤ Teaching Generation
回答：
“每一节应该看哪些证据，并怎样把这一节写清楚？”

        ↓

⑥ Quality Control
回答：
“这篇答案有没有超出证据？有没有虽然正确但没讲清楚？”
```

再压缩成三个词：

```text
Planning
↓
Writing
↓
Review
```

但 DevContext V3 与普通：

```text
Plan → Write → Review
```

真正不同的地方在于中间始终带着：

```text
Evidence Identity
Claim Type
Section Scope
Coverage State
```

所以完整本质应该理解成：

> **Evidence-aware Planning → Evidence-scoped Writing → Grounded Teaching Review。**

这才是这三个模块组合起来真正解决的问题。
