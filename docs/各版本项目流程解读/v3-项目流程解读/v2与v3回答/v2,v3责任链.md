## 问题是什么

这个模块真正要解决的问题，不是"要不要校验参数"，而是"校验逻辑一旦不止一步、而且还会不断长出新步骤时，代码该挂在哪里"。历史设计文档把车票查询读链路的流程分成三类：接口 1、2 是"校验 → 查缓存 → 未命中回源 → 返回"的简单字典类，接口 3 是"校验 → 直接查库 → 排序返回"的单对象类，只有接口 4 组合类写成了"责任链校验 → 四 层组装 → 返回" [E1]。这个对比本身就把问题定位出来了：前面几个接口的前置校验是单点式的，而组合类查询的前置校验需要被单独组织成一条链，才值得在流程概览里用一 个不同的词去描述 [E1]。

那么这条链要处理的是什么？按文档描述，被校验的是车次查询的入参，链条按"先非空 → 再基础 → 再存在性"分成三段，每一段是独立处理器、有明确顺序 [E2]。三段职责被 拆得很清楚：非空段回答"缺什么"，基础段回答"规则是否合理"，存在性段回答"数据里有没有" [E2]。这三件事的性质完全不同——前两段是纯参数判断，第三段要访问数据源， 是三类里"重"的一类 [E2]。把它们混在一起，就会出现 文档点名的那个坑：把存在性校验写进基础校验段，导致每个请求都要先访问数据源、再报参数错误 [E2]。换句话说， 问题不是校验本 身难写，而是**校验项的成本差异与顺序关系**没有载体去表达。

第二个压力来自演进。文档明确写着车次查询的校验会持续演进，未来可能加预售期校验、城市兼容校验、风控校验 [E2]。如果这些逻 辑堆成一串 if，每加一条都要回到主流 程里改判断顺序，"新增校验只加一段，不改主流程"这个性质就保不住 [E2]。所以引入责任链是在应对一个具体约束：**校验点数量会增长，而主流程不该跟着增长**。文档同 时说明，用户模块已经实现并验证过同一套责任链容器，P0 直接复用其设计形态、复制其实现模式 [E2]——这说明选择责任链不只是模式上的偏好，还有现成可复制的实现作为前提。

从证据链的时间线上看，这个决定的"必要性"本身也经历了一次判定。用户模块 v1 的实现指导里，方案已确认的一栏明确写着"不做分 布式锁、布隆过滤器、Redis、责任链（ 列为 v2）" [E4]，也就是在 v1 阶段，责任链被判断为可以不做。到了 v2，情况变了：新增一 项注册校验只需要新增一个实现 `AbstractChainHandler` 的处理器，`mark()` 返回 `USER_REGISTER_FILTER`、`getOrder()` 指定位 置，容器启动时自动收集排序，业务代码零改动 [E3]；同一份代码阅读指导里，`common` 包也被描述为容纳"Result、异常、JWT、UserContext、责任链、常量、工具"的通用件集合 [E5]。也就是说，责任链在用户模块里从"列为 v2"变成了"已落地的通用容器" [E4][E3][E5]，车票模块正是站在这个结果上决定复用 [E2]。这共同构成了"为什么要用"的实际理由：不是因为模式好看，而是因为已经存在一个可复用、按 mark/order 自动装配的容器形态。

## 一句话回答：责任链是项目用来治理“会不断加规则的前置校验”的骨架

本项目选用责任链，根本原因不是"这是一个经典设计模式"，而是这个项目里存在一类会持续增长的东西——进入业务主流程之前（以及其中）的顺序校验规则；责任链就是给这类增长提供的一个"新增规则不用动主流程"的挂载骨架。这是全文的主线：后文每一节都围绕"规则会变多"这个变化点展开，而不是复述模式定义。

这个骨架由三个部件咬合而成。抽象层是 `AbstractChainHandler`，它只要求实现类回答三个问题：属于哪条链（`mark`）、排在第几位（`order`）、拿到请求参数后做什么（`handler`）[E1][E2]。容器层是 `AbstractChainContext`，它在启动后按 `mark` 收集所有 Handler、组内按 `order` 排序，业务侧只需调用 `handler(mark, requestParam)`，容器就把该组的处理器按序跑一遍 [E3][E4][E5]。业务层因此被压缩成"在正确的时机调用一次 handler(mark, ...)"——从调用顺序看，它承担的是请求进入业务主流程前/中的顺序处理骨架；这一步是推导而非代码直接写明，它的前提是 `mark` 对应的处理器集合确实是在进入主流程的时机被调用的 [E3]。

顺序在这个骨架里不是装饰，而是纪律。抽象接口把 `order` 提升为必须声明的方法 [E1][E2]，容器在启动期就完成排序 [E3][E4]，说明执行次序在项目里被当作代码化的约 定而非代码行号的偶然结果。当前代码中已经能看到这条约定落地：注册链的第一个处理器是参数非空校验，`order=0`，也就是最先执行 [E13]。

项目设计文档把这个选择的原因写得更直白：校验规则会持续演进（新增预售期、城市兼容、风控等），因此需要"每一段是独立处理器、有明确顺序，新增校验只加一段、不改 主流程"的形态 [E11]；购票前置资格校验一节同样把责任链定位为对"一长串 if 会迅速恶化"的答案——主流程臃肿、每加规则都要动主流程、顺序藏在行号里、单条规则难以独 立测试 [E7]。需要提醒的是，E7 与 E11 均出自历史设计文档，属于当时的方案描述，应与当前代码交叉验证；可以直接确认的是，上述抽象与容器在当前代码中确实存在 [E1][E2][E3][E4][E5]。

代价同样被明说了：跳转不直观，点进"校验链"看不到具体有哪几条规则，得靠 `mark` 反查实现类；排错时要知道"现在跑到哪一段"，通常靠异常消息反推；并且按文档所述，责任链中任意一段抛异常就立刻中断，后面的规则不再执行，于是 `order` 小的必须更基础 [E7]。换句话说，这个骨架解决的是"规则数量增长"，同时把成本转移到了"跳转可 见性"和"顺序纪律"上——这两笔账后文会分别展开。

## 先把问题摆出来：一堆 if 在项目里会坏在哪

项目在设计责任链之前，先把自己否定的那个方案摆出来了：在购票方法开头写十几个 `if`，每个条件不满足就抛异常 [E7]。需要先说清楚材料的性质——这两份都是历史设计文档里的对照分析，讲的是当时被比较的写法，并不能据此断言当前代码里一定还长这样；至于今天实现形态如何，从这两条证据无法确认。

规则只有三五条时，这种写法没有任何问题：十几个 `if` 从上往下读，比一堆类名加一个容器直观得多，调试时也不用猜"现在跑到哪一段了"。真正让方案失效的不是写法难看，而是"规则会变多"这个前提。文档把恶化路径拆成四条 [E7]：主流程方法膨胀到 200 行，业务逻辑被淹没在参数检查里；每加一条规则都要动主流程，回归风险高；规则之间的先后顺序藏在代码行号里，没人说得清"为什么这条必须排在前面"；想单独测试某条规则，只能构造整个购票请求去打主流程。

这四条各自对应一种具体的维护代价，而不是风格偏好。前两条讲的是改动半径：一条新规则的成本被挂在主流程这个所有人共享的文件上，动它就得重新验证整条链路。第三条讲的是顺序不可表达——顺序本身是真实存在的语义，它决定先报哪个错、后报哪个错——但它只以行号形式存在，读者无法从代码结构中读出意图。第四条讲的是可测性：规则无法作为独立单元被驱动，只能走整体入口。

而这个项目里，规则集恰恰是开放的。车票查询链路的设计文档直接把"校验会持续演进"写成不用一堆 `if` 的理由，并点名了未来的可能成员：预售期校验、城市兼容校验、风控校验 [E11]。这句话是整节的支点：如果校验集合是封闭的，一串 `if` 就是更省事的选择；正因为它是开放的，才需要一种"新增规则不必触碰既有代码"的结构。从两份文档的取舍叙述看，项目真正想避免的正是"新增校验必须修改主流程"这一耦合 [E7][E11]。

这与本项目的责任链形态是同一件事的两面：主流程只留一行"执行购票校验链" [E7]，新规则以组件类形式加入，由容器在启动期按 mark 收集、按 order 排序。链式结构之所以值得，前提是先承认规则数量会增长；如果规则永远只有三条，链路本身就是更贵的方案。

可以想象这个对照有多具体：假设下一步要加"预售期校验"，在 `if` 串里意味着打开主流程、找一个语义正确的位置插入、确认它不会打乱已有的报错顺序、再跑一遍整体回归；在链式结构里则是一段新处理器加一个 order 值，前提是这个 order 摆得对。查询链路的三段划分恰好说明 order 是有语义的：先保证参数齐全，再做业务规则判断，最后 做较重的存在性查询 [E11]；文档也点出了反例——把存在性校验写进基础校验段，会让每个请求先访问数据源再报参数错误 [E11]。这种"为什么必须这个顺序"的知识，在行号里是无处安放的；一旦它迁移到显式声明的 order 上，它就从隐含直觉变成了需要人遵守的纪律——这也是这套结构要付的第一笔代价。

## 核心模型：一条按 mark 分组、按 order 排序、启动期自动装配的处理器队列

本项目里的“责任链”并不是教科书里那种“每个节点持有 next 指针”的链表，而更像一份按 mark 分组的处理器队列：分组与顺序由容器统一维护，调用方只报出一个 mark，其 余全部由容器接管。

先看链上的“节点”长什么样。AbstractChainHandler 只暴露三个方法：mark() 声明它属于哪条链，order() 声明它在这条链里的位置，handler(T requestParam) 是真正处理请求的入口 [E1][E2]——两个服务里的同名接口定义完全一致。这里有一个容易被忽略的细节：接口里没有 next、没有 setNext，也没有任何指向后继者的字段。也就是说，从接口契约看，处理器彼此之间没有链接手段 [E1][E2]；“串成链”这件事不可能发生在处理器内部，只能发生在容器一侧。反过来推：业务代码只能靠 mark 和 order 这两个“声明式”信息告诉容器“我是谁、我排第几”，而无法主动控制自己被谁调用。

容器这一侧，AbstractChainContext 同时实现 ApplicationContextAware 与 CommandLineRunner，内部持有 `Map<String, List<AbstractChainHandler>> container`，注释写明它的职责是“启动后按 mark 收集所有 Handler 并按 order 排序”，对外只暴露一个 handler(mark, param) 入口 [E3][E4]。类名、字段类型、方法签名都可以确认；但证据 强度需要分清楚：run(String... args) 的方法体不在本轮证据范围内，因此“怎么收集、怎么排序”目前只能说是类注释所声称的行为，而不是被实现代码逐行证实的流程。

那为什么把装配放在“启动期”，而不是构造注入？E4 的注释给出了理由：用 CommandLineRunner + ApplicationContext 收集（而非构造注入），是为了避免 Handler 反向依赖 Service 造成的构造循环 [E4]。这解释了时间点选择的必要性——如果容器在自身构造阶段就要求所有 Handler 就位，而某些 Handler 又要反向依赖 Service，Spring 的构造 注入就容易打结；把收集推迟到容器启动完成后的回调里，装配与依赖注入就被拆成了两个阶段。这里同样按注释所述来理解，实现体未验证。

运行期的行为则有方法体可查，E5 写得很直白：`container.get(mark)` 取出该 mark 下的列表，非空就 `handlers.forEach(handler -> handler.handler(requestParam))` [E5]。换句话说，以 mark 为唯一检索键、按列表的当前顺序逐个调用；列表的顺序就是执行顺序。因此“链的先后”完全取决于容器维护的那份 List，处理器无法改变自己在链中的位置。

把两段合起来看：

```
启动期（注释所述，实现体未见）
  ApplicationContext 中的 AbstractChainHandler 实现
        │  按 mark() 分桶
        ▼
  container: mark → List<Handler>，每个 List 内按 order() 排序
        │
运行期（[E5] 方法体）
  handler(mark, param) → container.get(mark) → 非空 → forEach 依次 handler(param)
```

所以可以把这个结构读成“注册表 + 有序列表”，而不是节点互指的双向或单向链表。由此还带出两个贯穿全文的特征。其一，调用点是完全扁平的：业务侧只写 handler(mark, param)，不 new 具体处理器、也不感知链上有几个节点 [E3][E5]，代价是跳转不直观——读代码时看不到分支，要知道谁被执行必须回到 container 的装配结果。其二，顺序是 一项需要全体实现类共同遵守的纪律：既然位置由 order() 声明、由容器在启动期排定，任何新增处理器都必须认真填写 order，否则执行次序可能与预期不符。需要说明的是 ，“链的串接完全由容器负责”这一判断依赖一个前提：所示 AbstractChainContext 是该责任链的唯一装配入口；在该前提下，处理器之间不存在 next 链 [E3][E5]。若项目另 有一处也在装配同批处理器，这个结论就要重新审视。同样，“新增一条规则只需新增一个实现类并声明 mark 与 order”是这套结构的自然推论，但收集的具体范围（是扫描全部 Bean 还是按类型过滤）无法从本轮证据确认。

一句话收束本节的核心模型：本项目的链 = 按 mark 分组、按 order 排序、启动期由容器自动装配的处理器队列；调用方交出 mark，容器交出顺序。

## 一次请求进来，链是怎么跑起来的

一次请求进来，链的跑法可以压成一条主线：**触发只认 mark，执行只认 List 里的顺序，而这个顺序是启动期就定下来的**。也就是说，运行时的"按 order 执行"其实是启动期"按 order 排序"的延迟兑现——两者是同一件事的前后两半。

**第一段：启动期，容器把组和顺序准备好。** `AbstractChainContext` 的类声明是 `implements ApplicationContextAware, CommandLineRunner`，内部持有 `Map<String, List<AbstractChainHandler>> container` [E3][E4]。类注释声称它的行为是"启动后按 mark 收集所有 Handler 并按 order 排序" [E3][E4]。这里要分清证据层级：`CommandLineRunner` 接口和 `run(String... args)` 方法签名是代码事实 [E3][E4]，说明收集动作发生在容器启动完成之后、由容器回调触发；但"按 mark 分组、组内按 order 升序"这句是注释里的声明（设计文档同样把它当作既定约定 [E7]），本节证据看不到 `run` 方法体，所以用什么比较器、order 缺失怎么兜底、重复 order 如何处置，都无法确认。E4 还给出了这个收集方式的一个直接理由：用 `CommandLineRunner + ApplicationContext` 而不是构造注入，是为了避免 Handler 反向依赖 Service 造成的构造循环 [E4]——这解释了为什么"编链"这一步必须推迟到启动期，而不能在构造阶段完成。

**第二段：请求到达，业务侧只递出 mark。** 调用点是 `handler(String mark, Object requestParam)` [E3][E4]。业务代码不知道链里有哪些规则，它只提供一个分组键 mark 和一个参数对象。这就是核心模型的第一层含义：**mark 是链的地址，order 是链内的位置**。

**第三段：查表取组。** `container.get(mark)` 拿到该组处理器列表 [E5]。注意紧接着的判断：`if (handlers != null)` ——如果这个 mark 没有任何实现类注册，方法直接什么都不做就返回了 [E5]。这不是"报错"，而是"静默通过"，属于代码级可确认的行为，也是排错时容易被忽略的一点。

**第四段：顺序执行。** 拿到列表后是 `handlers.forEach(handler -> handler.handler(requestParam))` [E5]：串行、同步、无返回值、按 List 的迭代顺序。因此执行顺 序就等于启动期排好的顺序。反过来推导：如果某条规则因为排序环节的问题没被排进去或者顺序错了，运行时不会给出任何提示，只会少跑一段或乱序跑——因为这里没有任何一致性校验。

**第五段：异常即断。** 设计文档明确约定"责任链中任意一段抛异常就立刻中断，后面的规则不会执行" [E7]。这份文档是历史设计规划，本节证据里看不到容器对异常的显式处理；但从 [E5] 的写法推断，`forEach` 内部没有 try/catch，某一段 `handler` 抛出的异常会直接穿出 `handler()` 方法，后续元素自然不再迭代——这个结果与文档说的" 中断"一致。

把上面五段画成时序：

```
启动   CommandLineRunner.run()
          ↓  按 mark 收集、组内按 order 升序（注释/文档声明 [E3][E4][E7]）
       Map<mark, List<Handler>>

请求   service → handler(mark, param)                [E5]
          ↓
       container.get(mark)
          ├─ null → 静默返回，什么都不执行              [E5]
          └─ List → forEach 顺序执行                   [E5]
                 H(order=0) → H(order=1) → H(order=2) → …
                      ↓ 任一段抛异常
                 异常穿出 handler()，后续不再执行        [E7]
```

**顺序纪律从哪来。** 因为中断是不可逆的，order 小的规则就必须承担更基础的职责。注册链给出了一个具体样本：`UserRegisterParamNotNullChainHandler` 的注释写明它是"注册责任链 1/3：参数非空校验（order=0，最先执行）" [E13]。也就是说，在用户注册这条链上，非空判断是第一个被执行的那一环，它通过之后，后面的规则才拿得到"字段确实存在"这个前提。

**失败情形长什么样。** 假设某条规则被排在空值校验之前，而它自身没有独立的 null 保护，那么参数缺失时它就会对 null 做运算——这是有前提的条件判断，本节证据无法 确认真实项目的 order 分配是否出现过这种情况。如果发生，链会在这一环抛出空指针之类的技术异常，用户看到的是"系统错误"而不是"参数错误" [E7]，这恰恰是"order 小 的必须更基础"这条纪律存在的理由。

**代价，就在这条时序里。** 在 IDE 里点"购票校验链"看不到具体有哪几条规则，你必须用 mark 去反查哪些类实现了这个接口；排错时也要靠异常消息反推"现在跑到哪一段 了" [E7]。也就是说，链把"新增规则不改主流程"的好处，换成了"读代码时要多跳一层"的成本——这正好呼应了它被选中的根本原因：规则会持续增长，而跳转不直观是一次性的阅读成本。

## 装配机制：为什么用 CommandLineRunner 而不是构造注入

装配这件事在本项目里被拆成两个时间点：先拿到容器，等容器就绪后再一次性收集。

AbstractChainContext 同时实现 ApplicationContextAware 与 CommandLineRunner [E3][E4]，这两个接口正好对应上面两个时间点。setApplicationContext 由 Spring 在 Bean 创建之后回调，把容器引用存进 applicationContext 字段；此刻 container 那个 Map<String, List<AbstractChainHandler>> 还是空的 [E3][E4]。真正的填充发生在 CommandLineRunner.run(String... args) 里：这是 Spring Boot 在所有单例 Bean 都初始化完成之后才触发的回调，代码在这个时点按 mark 分组、按 order 排序，把处理器写 进 container [E3][E4]。此后业务侧调用 handler(mark, param)，本质上只是一次 Map 查表加顺序遍历 [E3][E4]；注意该签名返回 void，说明它是执行入口，而不是返回队 列的查询接口。

那为什么不干脆把这些 Handler 构造注入进来？用户服务那份实现把理由写在了注释里：用 CommandLineRunner + ApplicationContext 收集（而非构造注入），避免 Handler 反向依赖 Service 造成的构造循环 [E4]。把它展开就是：如果抽象链上下文自己以构造参数形式持有 List<AbstractChainHandler>，Spring 必须先把所有 Handler 建出来才 能构造它；一旦 Handler 又需要 Service，而 Service 侧同样牵连到链上下文，环就闭合了，构造注入无法解开它。这是通用的生命周期约束——构造注入要求依赖在实例创建那一刻就可解析，字段注入与回调式注入则把解析推迟到创建之后。

所以"启动后统一收集"不是风格偏好，而是把装配从构造期搬到启动完成期，用时序差切断环。

这里要标出不确定的部分：Handler 实现类确实注入了 Service 层对象这一点，无法从现有证据确认，注释只表明存在这种风险或设计意图 [E4]。更准确的说法是条件式的：如果某个 Handler 注入了 Service，那么在构造注入下就会形成环，而当前写法让链上下文等所有 Handler 就绪之后才去读它们，环被时间差化解。另外，这段说明性注释出现在可见的 [E4] 片段里，票务服务那一份 [E3] 的片段中没有这句。

从机制上看，收益是注册表式的：启动期付出一次 O(处理器数) 的收集开销，运行期查表定位 mark；新增规则只需新增一个 Handler 并申报 mark/order，不必改动上下文本身。这正是"校验规则会持续增长"这一选型动因在装配层面的落点。代价也恰好在这里：收集发生在运行期，mark 写错不会有编译错误，只有在查不到处理器时才暴露；执行顺序 也完全依赖各 Handler 自己申报的 order，顺序纪律落在约定上，而不是类型系统里。可以看出这两个服务各自持有自己的 AbstractChainContext [E3][E4]，即装配是按模块 各做一遍，而不是一个全局单例——这是从文件分布推导出的判断，不是证据直接陈述的结论。

## 逐条对账：项目从责任链拿到的四类收益

这一节要回答的不是"责任链有什么好处"，而是一个更窄的问题：项目在"一长串 if"和"责任链"之间做选择时，究竟押注在哪个约束上。约束很具体——校验规则只增不减。P1 设计文档描述朴素写法"在规则少的时候没问题，但会迅速恶化"，并列出四条恶化路径 [E7]；P0 文档同样把理由落在"车次查询的校验会持续演进（未来可能加预售期校验、城市 兼容校验、风控校验）"上 [E11]。所以这里的取舍标准不是代码美观，而是**新增一条规则的成本落点**。因此"解耦"这个说法在本项目里必须被拆成可逐条核对的收益，否则 它只是口号。

| 增长带来的具体问题 | 责任链给出的答案（P1 设计文档表述 [E7]） | 落到哪一段结构上 |
| --- | --- | --- |
| 主流程臃肿，业务逻辑被淹没在参数检查里 | 主流程只有一行"执行购票校验链"，具体规则在各自的类里 | 容器对外只暴露一次 `handler(mark, requestParam)` 调用 [E3] |
| 每加一条规则都要动主流程，回归风险高 | 新增一个组件类即可自动挂上，主流程不动 | 启动期由容器自动收集 Handler [E3][E4] |
| 规则先后顺序藏在代码行号里 | 每条规则显式声明自己的 order | 容器按 order 排序后顺序执行 [E3] |
| 想测单条规则只能打整个购票请求 | 每个校验类都可以单独构造输入去测 | 每条规则是一个独立类，而非主流程中的一段 if |

逐条看，它们各自成立的条件并不一样。

**主流程瘦身**。文档的说法是"只有一行"，这个行数无法从本节证据核实；能核实的是形态：容器只提供 `handler(mark, requestParam)` 这一个入口 [E3]，业务侧调用它时不需要知道链上有哪些规则。从调用顺序看，这说明校验的"调度"被从业务方法里移走了，业务方法保留的只是"我要触发哪条链"这个决定——瘦身瘦掉的是规则清单，不是判断本身。

**开闭**。这条收益依赖收集方式。用户服务的容器注释明确写了"用 CommandLineRunner + ApplicationContext 收集（而非构造注入），避免 Handler 反向依赖 Service 造 成的构造循环" [E4]。这解释了为什么"新增一个类即可挂上"能成立：容器不是靠逐个注入来认识 Handler 的，而是在启动完成后按 mark 扫描收集 [E3][E4]。代价是容器与 Handler 之间是隐式关联，编译期看不出谁属于哪条链——这正是下面要说的取舍。

**顺序显式**。这里有两处证据必须配对读：规则侧"显式声明自己的 order" [E7]，容器侧"按 mark 收集所有 Handler 并按 order 排序" [E3]。声明与排序是同一件事的两端，缺一端顺序就仍然要靠阅读顺序猜。这条收益是四条里最"硬"的，因为它把顺序从注释和行号变成了可被容器执行的字段。

**可单测**。三个服务各自一个校验类，理论上可以绕开主流程单独构造输入 [E7]。但这是条件判断：如果某个校验类自身依赖了数据源或外部组件，那么"单独测"仍需要替身 对象，收益会打折。P0 文档提到的常见坑正好相反——"把存在性校验写进'基础校验'段，导致每个请求都要访问数据源后再报参数错误" [E11]，说明分段本身也决定了测试的轻 重分布：越靠前的段越应该无依赖。

还有一条不算新设计收益、但确实降低了本项目采用成本的：用户模块已经实现并验证过同一套责任链容器，P0 直接复用其设计形态（服务内自包含，复制其实现模式）[E11]。两份 `AbstractChainContext` 在车票服务与用户服务中各存一份，类签名、容器字段 `Map<String, List<AbstractChainHandler>>` 与三个方法完全同构 [E3][E4]，这与"复 制实现模式"的描述一致；但是否逐行等价、是否存在细节分叉，本节证据不足以确认，需要两份文件交叉比对。

把四条收益并排看，结论才是 core model 那句话：项目不是因为"责任链更优雅"而选它，而是因为变化点固定在"校验规则数量"上，责任链把新增规则的成本从"改主流程"降到"加一个类"。同一枚硬币的背面也必须记在账上：在 IDE 里点"购票校验链"看不到有哪几条规则，排错要靠异常消息反推跑到哪一段 [E7]。所以这是一次用可读性换可扩展性的交易，接受它的前提是规则数量确实会持续增长——如果校验永远只有三条且不再变，那些跳转成本就白白付出了。

## 代价与纪律：责任链不是白拿的

责任链把"加一条规则就要动主流程"的代价，换成了两类新的代价，并且把一部分正确性从编译器手里移交给了写代码的人。[E7] 记录了这笔交换的账单，这里逐项拆开。

**账单第一项：调用点看不到规则。** 业务侧的入口是一个 `handler(mark, requestParam)` 调用，容器按 mark 取出处理器列表后顺序执行 [E5][E3]。这意味着"购票校验链"在调用点只是一个字符串——在 IDE 里点进去，看到的是容器的 `forEach`，而不是具体有哪几条规则；要弄清链上有谁，只能反查哪些类实现了该 mark 对应的处理器，再由容器在启动时按 order 收集起来 [E3][E4]。值得注意的是，这并非"从差变好"，而是代价换了个位置：朴素写法把规则顺序藏在代码行号里 [E7]，责任链把顺序显式成了 order 字段，却把"有哪几条规则"从显式变成了隐式。

**账单第二项：排错靠异常反推。** 容器对外只提供两种结局——执行到底，或者抛异常；中间没有"当前跑到第几段"这类返回值 [E5]。所以排查线上问题时，通常只能靠异常消息反推是哪一段断的 [E7]。需要说明的是，这条来自历史设计文档的记述 [E7]，当前代码 [E3][E4][E5] 只能证明容器与执行机制存在，并不能证明团队今天的排障习惯仍然如此。

**最关键的一项不是代价，而是纪律。** handler 的实现就是一个 `forEach` [E5]，没有 try/catch。因此任一段抛异常，异常会直接向外传播，后面的处理器不再执行——这与文档里"任意一段抛异常就立刻中断"的表述一致 [E7]。中断语义本身是中性的，但它给靠后的规则制造了一个隐含前提：它们可以假设前面的规则已经把非法输入挡住了 [E7]。于是就有了 order 纪律，而违反它不会编译报错，只会在运行时改变用户看到的错误性质。

| 纪律 | 依赖的前提 | 违反后的表现 |
| --- | --- | --- |
| 空值检查 order 排第一位 | 无，它必须是最外层前提 | 后面的规则对 null 做运算，抛出空指针之类的技术异常，用户看到"系统错误"而不是"参数错误" [E7] |
| order 小 = 更基础 | 前面的段已经把非法输入挡住 | 报错语义错位：问题其实出在参数上，却表现为另一条规则失败 [E7]（由此推导） |
| 顺序即优先级 | 链严格按 order 顺序执行 [E3][E4][E5] | 排序依据失去意义，纪律退化回"顺序藏在行号里"的状态 [E7]（推导） |

**为什么这份纪律必须由人来扛？** 因为容器只做两件事：启动时按 mark 收集并排序 [E3][E4]，运行期按序执行 [E5]。它不知道哪条规则"更基础"——这个语义只有写规则的 人知道。所以框架能保证执行顺序是稳定的，却不能保证执行顺序是合理的，这是从当前实现里能直接看出的分工。由此还可以推导出一条更可操作的排序梯度：如果以"更基础"为判据，顺序大体应是参数完整性检查 → 业务规则判断 → 代价更重的检查（例如存在性查询）。把重查询放后面，是因为它成本更高，只在前面都通过时才值得付出。这个梯度只有两端在 [E7] 里有依据（空值检查排第一、总原则是 order 小的更基础），中间分层属于据此推导，而非文档明文。

**这笔代价什么时候不划算？** 文档自己承认，朴素的一长串 if "在规则少的时候没问题"，恶化是规则迅速增长之后才发生的 [E7]。也就是说，责任链的收益与校验规则的数量成正比，而它带来的三项负担——跳转不直观、排错靠异常反推、顺序纪律——是固定成本 [E7]。规则只有两三条时，一串 if 反而更直白；只有在规则会持续增长、且增长速度 快到"新增规则要改主流程"成为常态的场景下，这笔交换才划算。本项目选择责任链，正是站在后一种处境上做的判断。

## 顺序写错会怎样：两种文档点名的翻车方式

正常状态下的链是这样的：容器在启动期按 mark 收集同一组的处理器，并按各自的 order 升序排列，执行时非空段先跑——注册链里的 `UserRegisterParamNotNullChainHandler` 就明确标着 order=0、"最先执行" [E13]——接着才是基础规则判断，最后才是要访问数据源的存在性查询 [E11]。这条顺序里藏着一条硬语义：链上任意一段抛异常就立刻中 断，后面的处理器不会再执行 [E7]。正因如此，"谁先跑"直接决定了"用户最终看到哪种错误"，顺序因此不是风格偏好，而是行为约束。

反例一：把空值检查挪出第一位。文档把这条列为"最关键的一条约定"——order 小的必须更基础，空值检查永远排第一位；一旦不这样，后面的规则会对 null 做运算，抛出莫名其妙的技术异常（比如空指针），于是用户看到的是"系统错误"而不是"参数错误" [E7]。沿着中断语义往下推，故障的传播路径是清晰的：null 进入第一条规则 → 该规则没拦 住（它本来就不是干这个的）→ 运算时抛出技术异常 → 链在这里中断 → 排在它后面的字段校验、存在性校验一条都不会跑 [E7]。状态变化的关键不在于"报了错"，而在于错误 的类型变了：用户提交的明明是一个可归因于自己的缺参，系统却回给他一个看起来像服务端 bug 的异常。这类错误还会污染排错路径，因为 E7 同时指出，链的跳转本身就不 直观，排错时通常要靠异常消息反推"现在跑到哪一段了" [E7]。

需要说明的是，E7 属于历史设计文档，描述的是当时的设计分析 [E7]；至于某条具体新规则会不会踩这个坑，只能写成条件判断——如果一条新规则自身没做独立的空值保护，而它的 order 又排在空值校验之前，或者空值校验被整体后移到了它后面，那么这个风险在实际运行中就会成立。

反例二和反例三是同一个病根的两种表现。文档点名的另一种翻车方式是把存在性校验写进"基础校验"段，后果是每个请求都要先访问数据源，然后才报出参数错误；另一种是三段顺序整体颠倒，先查库后验空参，后果同样是浪费且错误提示不准确 [E11]。把这两种写法和正常态对照，代价就能算清楚：正常态下参数本身不合法时，非空段和基础段就足以拒绝请求，根本不需要触碰数据源 [E11]；而顺序颠倒之后，一个连必填字段都没填的请求，也会先付一次依赖查询的成本，再得到一个本该更早、更便宜就能给出的结论。更糟的是提示语义被稀释了——用户拿到的是"这条记录不存在"，而他真正的问题是"你没传够参数"，两句话指向的修复动作完全不同 [E11]。

恢复动作在两种情形下都不复杂，但必须改对地方。对反例一，是把非空校验放回 order 最小的位置——当前实现里注册链就是这么落地的，非空处理器 order=0、最先执行 [E13]——或者给那条插在前面的规则补上自己的空值保护。对反例二、三，是把存在性段还原到链条末尾，让"先保证参数齐全，再做业务规则判断，最后做重一点的依赖查询"这个次 序成立 [E11]。修复之所以只是调 order 值，恰恰是核心模型决定的：处理器由容器按 order 自动收集排序，你无法靠阅读调用处看出真实执行次序，order 值就是唯一可读的优先级声明 [E7][E13]。也因此，这类故障在代码审查里几乎看不出来，只会在运行期以"错误类型不对"或"多余的数据源访问"的形式暴露。

最后标一句证据边界：以上关于错误类型变化与数据源浪费的判断，来自两份 HISTORICAL 设计文档的设计分析 [E7][E11]；当前代码侧只能确认注册链存在 order=0 的非空处 理器 [E13]，其他链是否完全同形、实际线上是否出现过这些翻车，从这三条证据无法确认。

## 证据边界：哪些说法只能停在文档层

把核心模型拆开来看会更清楚：这条链由三个属性组成——按 mark 分组、按 order 排序、启动期由容器自动收集。恰恰是这三个属性，证据强度并不齐平。"按 mark 分组"有代 码级依据，"启动期收集"只证实了钩子的存在、没证实钩子内部做了什么，"按 order 排序"则完全落在注释与历史文档一侧。本节要划的就是这条线。

| 说法 | 能停在哪一层 | 依据 |
| --- | --- | --- |
| 存在处理器抽象与容器类（implements ApplicationContextAware, CommandLineRunner） | 代码已证实 | [E3][E4] |
| 容器字段 `Map<String, List<AbstractChainHandler>> container` 按 mark 存放 | 代码已证实 | [E3][E4] |
| 业务侧以 `handler(mark, requestParam)` 触发 | 代码已证实 | [E3][E4]，方法体见 [E5] |
| handler 体内按 mark 取列表、非 null 则逐个 `handler(requestParam)` | 代码已证实 | [E5] |
| 用 CommandLineRunner + ApplicationContext 收集，动机是避免构造循环 | 结构已证实，动机来自同文件注释 | [E4]（[E3] 无该段注释） |
| "启动后按 mark 收集所有 Handler 并按 order 排序" | 注释所述；`run(String... args)` 的实现体不在本轮证据内 | [E3][E4] 类注释 |
| 任意一段抛异常即中断整条链 | 仅文档所述 | [E7] |
| order 小的必须更基础、空值检查永远第一 | 仅文档所述 | [E7] |
| 朴素 if 的四条弊端、跳转不直观与靠异常消息反推位置 | 仅历史设计文档 | [E7] |
| 车票查询三段链（非空→基础→存在性）、复用用户模块设计形态 | 仅历史设计文档 | [E11] |
| 某个处理器注册时的具体 order 取值 | 本轮可用证据中没有对应片段 | — |
| 是否比较过规则引擎、策略模式等备选 | 无法确认 | — |

代码已证实的那几行撑住的是模型骨架：容器持有按 mark 索引的列表 [E3][E4]，执行入口是 `handler(mark, Object)` [E5]，链路遍历发生在 `forEach` 里 [E5]。而"排序"和"中断"这两个语义没有任何一段可引用的代码，只能写成"文档这样描述"。这不是学究式区分：前者可以直接陈述为项目事实，后者如果写成"本项目按 order 排序执行"就是 在把历史计划当成当前实现。

注释的位置尤其暧昧。类注释写了"按 order 收集并排序" [E3][E4]，但注释是对行为的声明而非行为本身，而被声明的那个 `run(String... args)` 方法体不在证据里。所以 更准确的边界是：容器暴露了 `run(String... args)` 这个启动钩子 [E3][E4]，至于它内部是否真的做了排序、按什么比较器排、order 缺失时如何兜底，本轮无法确认。条件句可以这样写：如果后续检索到 `run` 的实现且确实按 order 排序，那么"按 order 排序"就从文档层升到代码层；在那之前，它只是注释所声称的行为。

中断那条同样要小心。[E7] 把"任意一段抛异常就立刻中断，后面规则不再执行"称为最关键的一条约定，并由此推出 order 纪律。但 [E5] 的循环体既没有 try/catch，也没有任何显式短路——从这段代码看不出中断是特意实现的。由此可以做一个标注清楚的推导：正因为 [E5] 里没有捕获，按 Java 的常规语义，某段抛异常会自然向上冒泡并终止 `forEach`，效果上与 [E7] 的描述一致。这是基于通用语义的推论，不是本项目显式实现的中断逻辑；文档所说的"约定"到底靠机制保证还是靠默认语义顺带满足，现有证据分不出来。

动机层面的证据还有一处不对称，值得单独指出。"用 CommandLineRunner + ApplicationContext 收集（而非构造注入），避免 Handler 反向依赖 Service 造成的构造循环"这句话只出现在 [E4] 的注释里，[E3] 对应的类注释没有这一段。因此"避免构造循环"目前只能限定在 user-services 一侧有注释支撑；把它推广成"本项目所有模块都出于这个 动机"，属于超出证据的推广。同样，[E11] 说车票查询"直接复用其设计形态（服务内自包含，复制其实现模式）"，而我们在两个模块看到同名的容器类 [E3][E4]，这与"复制"的说法相符——但"相符"是推导，不排除两份实现各自演化的可能。

有一条证据必须明确挡在门外。[E12] 虽然标注为当前设计，但它的标题是"5.1.1 缓存三防 + 多级缓存（D3）"，讲的是被放弃的缓存方案，与责任链的选型没有任何交集。拿 它来支撑"为什么用责任链"，等于用另一条决策串上的证据去证明这一条。本节的边界由此包含一条禁令：任何把 [E12] 并入责任链选型论证的写法都不成立。

最后是备选方案的边界。[E7] 与 [E11] 给出的对照物都只有"一长串 if"这一种，而这两份本身都是历史文档；是否曾评估过规则引擎、策略模式或其他编排方式，现有证据完 全无法确认。可以写成条件判断：如果将来检索到设计讨论文档中提及这些备选，那么关于"为什么是责任链而不是别的"的结论就会变；在此之前，只能说文档层确立的对照物是朴素 if，不能说本项目比较过并否决了其他模式。

所以本节划定的范围是：哪些话该说成"代码里就是这样"（mark 分组、容器字段、`handler(mark, param)` 触发方式 [E3][E4][E5]），哪些话必须降级为"文档/注释这样说"（排序、异常中断、顺序纪律、与 if 的对照 [E3][E4][E7][E11]），哪条证据与本题无关（[E12]），哪些问题没有答案（备选方案比较、order 具体取值）。它不解决的是"排序究竟怎么实现""中断是否显式编写"这类实现细节——那需要回到 `run(String... args)` 的实体和 `AbstractChainHandler` 的契约去看，而不是继续在文档层推演。

项目使用责任链校验，核心原因是校验项会持续增加，而把这些校验继续堆在业务主流程里会迅速恶化。以用户服务 v1 → v2 注册校验为例，注册校验项从“参数非空 → 用户名 可用 → 证件黑名单 → 未来实名核验/风控”不断增加；如果用 if-else 堆叠，会出现顺序难以控制与复用、新增校验要改 Service 方法体从而违反开闭原则、校验逻辑与业务逻辑耦合导致难单测等问题。责任链的价值就在于把“每一步校验”拆成独立 Handler，按 mark 分组、按 order 排序、顺序执行，最终做到“新增规则=新增一个 Handler，不动既 有代码”。

车票查询读链路也是同样逻辑：车次查询的校验会持续演进，未来可能加预售期校验、城市兼容校验、风控校验；因此项目采用“先非空 → 再基础 → 再存在性”的分段责任链，每一段是独立处理器、有明确顺序，新增校验只加一段，不改主流程。购票场景中，购票校验项也会不断增加，如果全部堆在主流程里，购票方法会变成几十个 if；责任链把不同 校验拆成独立 Handler，并通过顺序控制执行，新加校验时不需要修改购票主流程。

从设计收益看，P1 购票与选座文档总结了朴素 if 写法的问题：主流程方法可能变成 200 行，业务逻辑被淹没在参数检查里；每加一条规则都要动主流程，回归风险高；规则之间的先后顺序藏在代码行号里；想单独测试某条规则，只能构造整个购票请求去打主流程。责任链对应的解决方式是：主流程只有一行“执行购票校验链”，具体规则在各自类里；新增一个组件类即可自动挂上，主流程不动；每条规则显式声明自己的 order，顺序是写在代码里的约定；每个校验类都可以单独构造输入去测。

顺序控制是责任链被采用的关键原因之一。责任链中任意一段抛异常就会立刻中断，后面的规则不会执行，因此必须遵守“order 小的必须更基础，空值检查永远排第一位”的纪律；否则后面的规则会对 null 做运算而抛出莫名其妙的技术异常，用户看到的就是“系统错误”而不是“参数错误”。这也是为什么参数非空要排最前：它是最便宜的纯参数检查，如果连参数都不合法，就没有必要做数据库、Redis 或远程调用。车票查询中同样强调“顺序即优先级”：先保证参数齐全，再做业务规则判断，最后做更重的依赖查询；三段各有明确职责，非空负责“缺什么”，基础负责“规则是否合理”，存在性负责“数据里有没有”。常见坑包括把存在性校验写进“基础校验”段，导致每个请求都要访问数据源后再报参数错误；或者三段顺序颠倒，先查库后验空参，浪费且错误提示不准确。

责任链还带来扩展性与复用性。用户模块新增一项注册校验时，比如实名核验，只需新增一个实现 `AbstractChainHandler` 的 Handler，让 `mark()` 返回 `USER_REGISTER_FILTER`、`getOrder()` 指定位置，容器启动自动收集排序，业务代码零改动。车票查询的设计也直接复用用户模块已经实现并验证过的同一套责任链容器设计形态，采用服务内自包含、复制其实现模式的方式。这说明项目使用责任链不仅是为了解决单个方法的 if 膨胀，也是为了在不同模块之间复用一套可扩展、可排序、可插拔的校验框架。

当然，Context 也指出了责任链的代价：跳转不直观，在 IDE 里点“购票校验链”看不到具体有哪几条规则，需要靠 mark 去找有哪些类实现了这个链的接口；排错时要知道“现在跑到哪一段了”，通常靠异常消息反推。但项目仍然采用它，是因为校验规则持续增长所带来的维护、扩展、测试和顺序控制问题，比责任链的跳转与排错成本更关键。

综上，项目使用责任链校验，是为了把不断增长的校验规则从主流程中解耦出来，变成按 mark 分组、按 order 排序、顺序执行、可单独测试、可自动收集、新增时无需改主流 程的独立 Handler；同时通过异常中断和 order 约定强制校验顺序，先做便宜且基础的参数检查，再做更重的业务规则与依赖查询。
