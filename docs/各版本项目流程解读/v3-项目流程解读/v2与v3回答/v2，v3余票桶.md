## 为什么不是一串 if-else

根据现有说明文档，采用责任链的动因可以拆成三点。第一是解耦：每种校验拆成独立 Handler，各自只关心自己的判断。第二是顺序可控：Handler 通过 order 声明执行次序 ，容器据此排序调用，因此“先做哪一步、后做哪一步”由元数据决定，而非散落在主流程代码里 。第三是扩展成本低：新增校验时不需要修改购票主流程。文档还解释了排序原 则——参数非空要排最前，因为它是最便宜的纯参数检查，如果连参数都不合法，就没有必要做数据库、Redis 或远程调用。这说明责任链在本项目中同时承担提前失败的职责：越早、越便宜的检查越靠前，后续昂贵操作才有机会被挡掉。该动因来自说明材料，不是由当前代码直接证明的主观决策；代码只能证明顺序控制与插件式处理器结构确实存在。

## 链式结构在当前代码中的落地

当前实现不是只有文档描述，代码中有抽象与容器。AbstractChainHandler 定义统一契约：mark 表示链分组，order 表示执行顺序，handler 表示具体处理逻辑，其中 handler 是接收请求参数的抽象方法。AbstractChainContext 实现 ApplicationContextAware 与 CommandLineRunner，内部维护 Map<String, List<AbstractChainHandler>> 容器，在 run 阶段按 mark 收集所有 Handler 并按 order 排 序，业务侧通过 handler(mark, param) 顺序执行。一个实现取舍是：容器用 CommandLineRunner + ApplicationContext 收集，而不是构造注入，注释说明这是为了避免 Handler 反向依赖 Service 造成构造循环。此外，注册链通过 UserRegisterCreateChainFilter 继 承抽象处理器，统一 mark 为 USER_REGISTER_FILTER，说明每条业务链可以用专属接口约束分组，而不是让各处理器自由声明。

## 校验链覆盖的业务场景：注册、购票与查询

责任链校验已落在具体业务流程中。用户注册场景中，UserRegisterParamNotNullChainHandler 实现注册创建链过滤器，order=0 最先 执行，依次校验用户名、密码、真实姓名、证件类型、证件号码、手机号、邮箱是否为空，任一为空即抛出 ServiceException。购票场 景中，TrainPurchaseTicketParamNotNullChainFilter 是购票流程过滤器之一， 负责参数必填校验。查询车票场景中，TrainTicketQueryParamBaseVerifyChainFilter 是查询流程过滤器之二，负责校验日期、出发地与目的地等业务规则。不同业务链通过 mark 分组，容器按 mark 维护各自的处理器列表，因此注册、购票、查询可以各自独立组织校验顺序。

## 设计动因与实现取舍

把责任链与集中式 if-else 对比，本项目的取舍可以归纳为：用“独立的处理器 + 顺序元数据 + 统一容器”换取主流程稳定。处理器以 Spring 组件形式存在，例如注册参数非 空处理器与购票参数必填过滤器均标注 @Component，容器启动后自动收集，新增规则因此具备可插拔基础。执行语义上，order 排序决定先后，注册非空校验在 order=0 时最先执行并在失败时抛异常，从而形成提前失败：一旦某个 节点抛出异常，后续节点不会继续。这里仍需区分证据性质：直接解释“为何采用责任链”的 是说明/面试准备材料，只能 作为设计动因参考；而抽象、容器收集与排序、具体处理器这些结构，由代码证据 支撑，属于当前实现事实。

## 问题是什么

这个模块真正要解决的问题，不是"要不要校验参数"，而是"校验逻辑一旦不止一步、而且还会不断长出新步骤时，代码该挂在哪里"。历史设计文档把车票查询读链路的流程分成三类：接口 1、2 是"校验 → 查缓存 → 未命中回源 → 返回"的简单字典类，接口 3 是"校验 → 直接查库 → 排序返回"的单对象类，只有接口 4 组合类写成了"责任链校验 → 四 层组装 → 返回" [E1]。这个对比本身就把问题定位出来了：前面几个接口的前置校验是单点式的，而组合类查询的前置校验需要被单独组织成一条链，才值得在流程概览里用一 个不同的词去描述 [E1]。

那么这条链要处理的是什么？按文档描述，被校验的是车次查询的入参，链条按"先非空 → 再基础 → 再存在性"分成三段，每一段是独立处理器、有明确顺序 [E2]。三段职责被 拆得很清楚：非空段回答"缺什么"，基础段回答"规则是否合理"，存在性段回答"数据里有没有" [E2]。这三件事的性质完全不同——前两段是纯参数判断，第三段要访问数据源， 是三类里"重"的一类 [E2]。把它们混在一起，就会出现 文档点名的那个坑：把存在性校验写进基础校验段，导致每个请求都要先访问数据源、再报参数错误 [E2]。换句话说， 问题不是校验本 身难写，而是**校验项的成本差异与顺序关系**没有载体去表达。

第二个压力来自演进。文档明确写着车次查询的校验会持续演进，未来可能加预售期校验、城市兼容校验、风控校验 [E2]。如果这些逻 辑堆成一串 if，每加一条都要回到主流 程里改判断顺序，"新增校验只加一段，不改主流程"这个性质就保不住 [E2]。所以引入责任链是在应对一个具体约束：**校验点数量会增长，而主流程不该跟着增长**。文档同 时说明，用户模块已经实现并验证过同一套责任链容器，P0 直接复用其设计形态、复制其实现模式 [E2]——这说明选择责任链不只是模式上的偏好，还有现成可复制的实现作为前提。

从证据链的时间线上看，这个决定的"必要性"本身也经历了一次判定。用户模块 v1 的实现指导里，方案已确认的一栏明确写着"不做分 布式锁、布隆过滤器、Redis、责任链（ 列为 v2）" [E4]，也就是在 v1 阶段，责任链被判断为可以不做。到了 v2，情况变了：新增一 项注册校验只需要新增一个实现 `AbstractChainHandler` 的处理器，`mark()` 返回 `USER_REGISTER_FILTER`、`getOrder()` 指定位 置，容器启动时自动收集排序，业务代码零改动 [E3]；同一份代码阅读指导里，`common` 包也被描述为容纳"Result、异常、JWT、UserContext、责任链、常量、工具"的通用件集合 [E5]。也就是说，责任链在用户模块里从"列为 v2"变成了"已落地的通用容器" [E4][E3][E5]，车票模块正是站在这个结果上决定复用 [E2]。这共同构成了"为什么要用"的实际理由：不是因为模式好看，而是因为已经存在一个可复用、按 mark/order 自动装配的容器形态。

## 实现机制

本节只按证据能覆盖的层次描述机制，证据未写明的实现细节不补。能确认的机制骨架是：处理器自描述（`mark` 与 `order`）+ 容器 启动收集排序 + 按段顺序执行；它落在 组合类接口的校验路径上，而不是全模块统一入口。

车票查询侧，三类流程里只有组合类接口 4 写成“责任链校验 → 四层组装 → 返回”，简单字典类接口 1、2 和单对象类接口 3 仍写的是“校验”后的缓存/查库路径 [E1]。因此触发点首先是接口 4 的业务入口，而不是所有读接口的公共前置。进入责任链后，被校验对象是 该组合查询的请求条件；校验分成三段：非空（缺什么）、基础（规则是否合理）、存在性（数据里有没有）[E2]。顺序固定为“先非空 → 再基础 → 再存在性”，设计含义是“先保证参数齐全，再做业务规则判断，最后做重一点的依赖查询（存在性）” [E2]。 校验通过后才 进入四层组装并返回 [E1]。证据没有展开失败时由谁中断、返回什么结构；但 E2 把“把存在性校验写进基础校验段”列为常见坑，并指 出其代价是“每个请求都要访问数据源后再报参数错误”，这说明链在设计意图上要让前段失败阻断后段，否则“先验空参再查库”的收益不成立——这是从设计含义推导出的条件判断，不是证据对短路实现的 直接描述 [E2]。

## 收束

这一节把前面几节收回到证据本身：项目里对责任链校验的记录，落在具体模块和具体链路上，而不是停留在通用模式介绍。

余票桶是一道放在 Redis 里的购票准入闸门——Hash 结构按「车次+区间」分桶、按席别记数，扣减/归还走 Lua，缺失时在锁内从数据库聚合装载并带 TTL；它只负责放行或挡住请求，不负责记账，真正的库存裁决始终在 MySQL。下面按“定位—链路位置—结构—装载—取令还令—归还方—并发—降级—权衡—回收”的顺序展开。

## 先给结论：它是一道闸门，不是一本账

余票桶不是一本库存账本，而是一道放在 Redis 里的购票准入闸门：它只回答"这次请求放不放行"，真正的库存事实留在 MySQL 那边——这一句定位来自类注释本身，注释明确写着"Redis 余票令牌桶只负责购票准入，不是库存事实源。异常时始终降级放行，最终是否能占座仍由 MySQL 条件更新决定" [E4]。

这道闸门的形状是一个 Redis Hash。key 由 `TRAIN_STATION_TOKEN_BUCKET` 前缀加上 `CacheUtil.buildKey(trainId, departure, arrival)` 拼成 [E12]，也就是"车次+出发站+到达站"唯一确定一个区间桶；field 是席别、value 是该席别的可售数——装载时正是把 `seatType` 与 `count` 都以字符串形式塞进同一个 Hash [E2]。所以一次闸门判断 的语义很窄：某个车次、某个区间、某个席别，还允不允许请求通过。

接口形状印证了这个窄职责。`takeToken` 返回 boolean，内部只区分三种 Redis 返回值：`TAKE_SUCCESS=1`、`TAKE_REJECTED=0`、`BUCKET_MISSING=-1` [E4]；拿到 1 就放 行、拿到 0 就挡住、拿到 -1 说明桶还没装载 [E5]。对外它不承诺任何"扣了多少、还剩多少"——那不是闸门该回答的问题。扣减与归还则分别走两条 Lua 脚本：`TAKE_TOKEN_SCRIPT` 在取令路径执行 [E5]，`RETURN_TOKEN_SCRIPT` 在归还路径执行 [E1]，两个脚本都是启动时通过 `loadScript` 加载的 `DefaultRedisScript<Long>` [E4]。从通用实 现惯例看，用脚本的意义在于把"读多个 field、比较、扣减"合成一次原子执行，避免并发下的中间态；就本项目代码本身能够确认的，只是扣减和归还都经由 Lua 而非普通命 令 [E4]。

为什么说它是闸门而不是账本，最关键的一点在失败方向。`takeToken` 在开关关闭、请求席别计数为空时直接返回 true [E5]；在捕获到任何异常时同样返回 true，并给 `my12306.token.degrade` 打一个降级计数 [E5]。`returnToken` 也一样，异常时只 warn 并打降级计数，日志里写明"保留偏松降级并等待 TTL 自愈" [E1]。这说明异常路径被有 意统一成"松"：宁愿多放一些请求去 MySQL 撞一遍条件更新，也不因为 Redis 抖动而误伤本该成功的购票。一个会在故障时主动失效的组件，本质上不可能承担事实源的职责。
TTL 是同一逻辑的另一个侧面。桶的过期时间由 `expireMinutes` 控制，默认 10 分钟 [E4]，装载时用 `hPutAllWithTtl` 写入 [E2]。一个会自己过期的准入判断，只能视为 对数据库当前状态的一份有时限的近似——它的数值来自装载时刻的聚合快照 [E2]，此后随着取令、归还、TTL 到期不断漂移。因此这里的双层定位可以这样记：Redis 桶是准入 层，它可能偏松、可能与数据库真实可售数存在偏差、可能整桶消失并需要重装；MySQL 是事实层，负责最终裁决。沿着这个定位往下看，后面关于装载时机、装载锁、Lua 返回码和降级计数的所有细节，讨论的都是"闸门怎么开合"，而不是"账本怎么记账"。

## 一句话模型：Hash 桶 + 分层真相

余票桶在脑中最省力的记法是一台"席别计数器"：它以「车次+出发站+到达站」为粒度落在 Redis 里，形状是一个 Hash，只回答"这单能不能继续往下走"，不回答"这张票到底 归谁"[E4]。

先看它的形状。桶本身就是一个 Hash，field 是席别的字符串形式，value 是可售数量的字符串形式——这一层在装载逻辑里看得很清楚：聚合结果 `availableBySeatType` 是 `Map<Integer, Long>`，写进桶时被逐项转成 `String.valueOf(seatType)` 与 `String.valueOf(...)`[E2]。装载方式是取一个区间的 `seat_status = AVAILABLE` 座位行，按 `seat_type` 做 `group by` 计数，一次查询拿到各席别的真实可售数[E2]；随后按车型支持的全部席别补齐，缺失的记 0，然后整体带 TTL 写入[E2]。这里有两个容易被忽略的设计含义：补 0 意味着"席别在桶里存在但计数为 0"与"席别不在桶里"是两种不同状态，前者是真实售完，后者才触发重装[E2]；TTL 意味着这个桶是一份有保鲜期的快照， 而不是永久账本[E2]。

再看桶里不装什么。座位级的明细——车厢号、座位号、乘客标识、出发到达站、席别——属于 `t_ticket` 这张购票事实表[E3]，桶里一个都不存。桶只保存按席别聚合后的计数[E2][E3]。这说明两者是不同坐标系的对象：数据库行是"某一排某一座在某区间被谁占了"，桶是"这个区间这个席别还剩几个"[E3][E2]。从调用顺序看，业务先拿到席别这个粗粒度坐标去做准入判断，真正落座时才回到明细粒度，因此桶的粒度天然比库存事实粗一层[E2][E3]。

于是就有了分层真相。桶负责快速放行或拦截：类注释直接写明"Redis 余票令牌桶只负责购票准入，不是库存事实源"，并且异常时始终降级放行，最终能否占座仍由 MySQL 条 件更新决定[E4]。换言之，桶说"可以"，只是允许请求继续前进；桶说"不行"，只是提前挡掉大概率无望的请求[E4]。真正的那次裁决发生在数据库的条件更新上，桶的结论对它没有约束力[E4]。

```
请求(车次, 区间, 席别×张数)
        │
        ▼
  Redis Hash 桶  field=席别  value=可售数   ← 准入闸门，快照 + TTL
        │
   ┌────┴─────┐
   ▼          ▼
 放行        拦截 ──► 直接失败，不必去压 MySQL
   │
   ▼
 MySQL 条件更新  ← 唯一的库存裁决处
   │
   ├─ 成功 → 真正占座
   └─ 失败 → 桶的"放行"被推翻，属正常路径
```

理解了这张图，"桶的数值短期内允许与真实库存不一致"就不再像缺陷，而是这套设计的必要前提：桶是装载时刻的聚合快照，装载之后数据库里可能又有别的事务在扣减或归还[E2][E3]，而桶并不实时跟踪这些变化——它只保证"不会因为桶过期而永久挡住一个本来有票的请求"（补 0 与 TTL 都在服务这个目标）[E2]。也正因为如此，"异常降级放行"才站得住：既然桶只是闸门而不是账本，它出故障时把请求放进去交给 MySQL 判断，代价只是少挡一些请求，而不是卖错票[E4]。反过来说，这个结论有一个前提——那条 MySQL 条件更新确实仍在下游执行；如果某条链路绕过了它，桶就从"宽松的闸门"变成了"唯一的判断"，前提失效[E4]。

## 它被插在购票链路的哪一步

一个购票请求刚到达服务端时，最先要回答的并不是"还有哪个座位空着"，而是一个更便宜的问题：这个请求值不值得往下走。原因是再往后那一步很贵——`reserveLocally` 会 先拿用户锁，再对 `seatTypeCounts` 里的每个席别逐个加锁，然后才调用 `doPurchaseInTransaction` 进入本地事务 [E11]。如果所有请求不加区分地都走到这里，那些注定 无票的请求会同样参与抢锁、持锁、开事务，把最稀缺的临界区资源消耗在必然失败的流程上。

所以需要一个前置闸门。但从 `purchaseTickets` 的实际代码形态看，这道闸门并没有插在方法最开头，而是插在几道便宜判断之后 [E7]。按调用顺序展开，同一个请求经历的次序是：先跑一遍 `TRAIN_PURCHASE_TICKET_FILTER` 过滤链；接着校验 `userId`/`username` 是否为空，空则抛"请先登录后再购票"；再校验 `requestParam.getPassengers().size() > 5` 则抛"单笔订单乘车人不能超过 5 位"；然后把请求折叠成 `seatTypeCounts` 这份"席别→张数"的 Map，紧接着调用 `tokenBucket.takeToken(trainId, departure, arrival, seatTypeCounts)` [E7]。

理解这道闸门的位置，关键要看清楚"取令前"和"取令后"分别发生了什么。取令之前只有参数与身份层面的判断：过滤链、登录态、乘车人数量上限——这些都不需要访问库存，代价极低 [E7]。而乘客归属校验（`loadPassengers`，注释明确写着它要"在请求占用任何一把分布式锁之前"拒绝非法乘客）发生在取令成功之后；至于加锁与事务，更是在 `reserveLocally` 内部才展开 [E7][E11]。也就是说，闸门被放在了"零成本校验做完了、昂贵校验还没开始"的那个位置：取令前是请求本身的合法性，取令后才是业务资源。

这一位置的语义是硬的，不是软的。`takeToken` 返回 `false` 时，代码直接 `throw new ServiceException("列车站点已无余票")`，方法就此退出，后面的 `loadPassengers`、`reserveLocally`、Redisson 加锁、事务提交一步都不会发生 [E7]。这里没有"先放进来、后面再兜底"的降级路径。与之对称的是反向动作：如果取了令、但请求最终没有 走到本地事务提交（`!reservationCommitted`），`finally` 块会调用 `returnToken` 把额度还回去；而注释指出一旦本地事务提交，归还的责任就归 `cancelCallback` 单独承担 [E7]。取令因此是一次"预定准入额度"的动作，有借有还，且归还责任在两条路径上是明确划分的。

回到那三行 `takeToken` 本身还能读出一个边界：它是针对整个 `seatTypeCounts` 的一次调用，返回的是单个布尔值 [E7]，而这份 Map 会一路带到后面的加锁与事务阶段使 用 [E7][E11]——闸门与后续扣减共享同一份席别数量口径。但至于它是全部席别都放行才返回真、还是部分放行也算通过，本节证据只到调用点为止，看不到实现，无法确认。

把准入判断前移到内存层、让明显无票的请求止步于重路径之外，这是高并发系统里的通用手法：判断越便宜、位置越靠前，被挡下的请求就越不必支付后续代价。不过就本项目而言，证据只能说明它这样做了、结构上确实把取令排在了加锁与事务之前；从调用顺序看，桶的作用就是把明显无票的请求挡在这两段之外，但到底避免了多大比例的无用请求、省下了多少锁与事务开销，这两段代码里没有任何度量可以支撑，属于无法确认的部分。

最后要分清这道闸门的职责边界：取令成功并不意味着有票。它只表示这个请求获得了继续参与竞争的资格，座位能否真正占住，仍要由 `reserveLocally` 里那把用户锁、那些席别锁以及其内部的事务来裁决 [E11]——闸门只负责放行或挡住，不负责记账。

## 桶里到底存了哪些字段，缺字段意味着什么

余票桶在 Redis 里是一个 Hash：key 由车次与上下车站区间拼成 [E12]，桶里的每一个 field 是一种席别编码的字符串，对应的 value 是该席别可售数量的字符串 [E2]。也 就是说，key 回答"哪趟车的哪一段"，field 回答"哪种席别"，value 回答"这道闸门认为还剩多少"。三者合起来才是闸门做出"放行还是挡住"所需的完整刻度。桶本身不记账，它只是把 MySQL 聚合出来的数字搬过来当准入阈值，所以字段一旦缺失，它的含义不是"库存为零"，而是"这道闸门对这个席别压根没有刻度可用"——这两件事在后续判断里会被 区别对待。

按 [E2] 的装载逻辑，桶装好之后大致是下面这个形状（**下表所有车次、站名、编码与数字均为虚构，仅用于说明结构**）：

| 层次 | 存放内容 | 示例（虚构） |
| --- | --- | --- |
| key | 车次 + 出发站 + 到达站 | `某前缀:1001_甲站_乙站` |
| field | 席别编码的字符串 | `"1"`、`"2"`、`"3"` |
| value | 该席别可售数量的字符串 | `"12"`、`"0"`、`"7"` |

这里最关键的设计是"补 0"。装载时的聚合查询只统计 `seat_status` 为可售、且区间匹配的记录，并按 `seat_type` 分组 [E2]，因此一个已经卖光的席别在结果里根本不会 出现行；代码再按车型支持的全部席别遍历，用 `getOrDefault(seatType, 0L)` 把没有记录的席别写成 `"0"` [E2]。假设某个车型支持席别编码 1、2、3，而聚合结果里只有 1 和 2 有可售记录，那么装载后 field `"3"` 仍会以 `"0"` 落进桶里。**如果不做这步补 0**，这个席别就永远没有 field，于是每次针对它的请求都会被判为"字段缺失"， 进而触发一次完整的桶重装——取锁、跑聚合 SQL、`hPutAllWithTtl` 写回 [E2]。补 0 的作用就是把"永远缺失"变成"稳定的 0"，让闸门能干脆地回答"满了"，而不是反复去做 无意义的装载。

由此可以推出判定字段完整性的规则：它不是一个"key 在不在"的问题。装载入口在拿到锁之后，先用本次请求涉及的席别去 `hMultiGet`，再要求结果全部非空才会直接返回 [E2]。从调用顺序看 [E5]，只有 Lua 返回 `BUCKET_MISSING` 才会走到装载，而装载在锁内还要再验一次 [E2]——这说明"Key 已存在"与"本次要查的席别都在"是两件独立的事：Hash 的 key 存在，并不意味着里面的字段集合满足当前这次请求。

请求侧的席别数量在进入这个判断之前会先过一遍 `normalize`，如果归一化后为空，`takeToken` 直接返回放行、连桶都不查 [E5]。归一化本身的具体规则不在本节证据范围 内，能确认的只是它之后的效果：当没有任何席别需要校验时，闸门选择放行而不是拦截。另外，这里有一个基于代码结构的推导需要标明——如果请求里的某个席别不属于该车型支持的席别集合，那么按 [E2] 的装载循环它不会被补进桶，完整性判定会对它持续失败；这是从循环范围推断出的条件性结论，不是已确认的运行现象。

回到核心模型：桶是一道闸门，它只有"放行"和"挡住"两种输出，而 field 与 value 就是它做这个判断的全部依据。判断"0"和判断"缺失"对闸门的意义完全不同——前者是"查过，确实没有可售"，后者是"不知道"；补 0 把前者固化下来，避免后者被误当成"库存信息没拿到"而反复重装。真正的库存裁决始终在 MySQL 那边，桶里的数字只是让闸门能更 快说"不"。

## 分桶维度与装载时机：懒加载出来的桶

把余票桶理解成一道 Redis 侧的准入闸门，那这一节讲的不是闸门怎么开合，而是闸门本身什么时候出现。它不是一个预先铺满全库的静态结构，而是被第一个请求"撞"出来的 。

一次完整的诞生时序大致是这样：

```
takeToken(车次, 出发站, 到达站, 席别→张数)
   │  buildBucketKey → 「固定前缀 + 车次 + 出发 + 到达」      [E12]
   ├─ Lua 取令 → 1 放行 / 0 拦截
   └─ Lua 取令 → -1（桶缺失）                                [E4][E5]
          └─ loadBucket
                ├─ executeWithLock(车次+区间锁)                [E2]
                ├─ 本次涉及的席别字段全在？→ 直接返回
                ├─ 分组聚合 SQL → 各席别可售数                 [E2]
                ├─ 校验车次存在、车型有席别 → 否则抛错         [E2]
                ├─ 车型全部席别补 0 → hPutAllWithTtl           [E2]
                └─ 退出锁
          └─ 再取一次令 → 1 / 0 / 其他一律降级放行             [E5]
```

**起点：已经有一个确定的 key，但还不确定 Redis 里有没有东西。** 桶的 key 由 `buildBucketKey` 拼出，形式是固定前缀加 `CacheUtil.buildKey(trainId, departure, arrival)` [E12]，所以桶的粒度是「车次 + 出发站 + 到达站」这一区间。这直接决定了装载 SQL 的过滤条件也落在同样的三个字段上：`train_id`、`start_station`、`end_station` [E2]。同一趟车卖北京→上海和卖南京→上海，落在两个不同的桶里，各自装载、各自计数。

**第二步：取令先于装载。** `takeToken` 先做开关与参数的空值短路，再做 `normalize`，然后构建 key 并执行取令 Lua [E5]。这里的设计选择是"先问再装"：不装载也能 走一次 Lua，成本比一次聚合 SQL 低得多，而绝大多数请求遇到的桶其实已经存在。只有当 Lua 返回 `BUCKET_MISSING`（即 -1，来自常量定义）[E4] 时，才值得付出装载代 价——这就是懒加载的触发点。

**第三步：进锁，而不是直接装载。** `loadBucket` 先由车次与区间拼出 `keySuffix`，再用 `LOCK_TRAIN_STATION_TOKEN_BUCKET` 格式化出 `lockKey`，把整个装载过程包 在 `executeWithLock(lockKey)` 里 [E2]。为什么必须进锁：一个桶刚过期的瞬间，落在这条区间上的并发请求会几乎同时拿到 -1，如果不互斥，就会同时发起聚合 SQL 并互 相覆盖写回。锁的粒度特意选成「车次 + 区间」而不是全局锁，这样不同线路的装载互不阻塞。

**第四步：锁内先做字段完整性判断，而不是判断 key 是否存在。** 进入临界区后，代码把本次请求涉及的席别转成字段名，`hMultiGet` 一次取出并交给 `allNonNull` 判断，齐全就直接返回 [E2]。这里有个容易忽略的点：Key 存在并不代表字段完整，所以只要本次请求涉及的任一席别缺失，就会重新装载完整桶 [E2]。这段判断同时承担了双重检查的职责——如果前一个持锁线程已经把桶装好，后一个线程在这里就回头了，不会重复查库。

**第五步：一条分组聚合 SQL 拿到全部真实可售数。** 判定不通过才真正查库：`select("seat_type", "COUNT(*) AS cnt")`，按 `seat_type` 分组，条件是票在可售状态且 未逻辑删除（`seat_status=AVAILABLE`、`del_flag=0`），结果逐行塞进一个按席别编号索引的 Map [E2]。注释里写明了目的：一次聚合查询取得区间各席别的真实可售数，减少装载阶段的 SQL 往返 [E2]。换句话说，桶的所有席别是一次性凑齐的，而不是每个席别查一次、缺哪个补哪个。

**第六步：校验，失败就抛错而不是写半截桶。** 聚合结果拿到后，代码还会 `trainMapper.selectById(trainId)`，为空则抛 `IllegalStateException`；再用 `VehicleTypeEnum.findSeatTypesByCode(train.getTrainType())` 取车型支持的席别，为空同样抛错 [E2]。这两步的意义是：桶的字段集合必须由"车型支持哪些席别"决定，而不能由"数据库里恰好有哪些席别"决定。

**第七步：补齐零值，再整体带 TTL 写回。** 组装时遍历车型支持的全部席别，用 `availableBySeatType.getOrDefault(seatType, 0L)` 取值，取不到就补 0 [E2]——注释解 释了原因：避免售完席别永久触发"字段缺失"重装。这是一个很实际的细节：某席别卖光后，聚合 SQL 的 `group by` 结果里根本没有这一行，如果不补 0，下一次携带该席别 的请求就会永远认为字段缺失，反复进锁重装。最后用 `hPutAllWithTtl(bucketKey, bucket, expireMinutes, TimeUnit.MINUTES)` 一次性写入整个 Hash 并附上过期时间 [E2]，`expireMinutes` 来自配置项，默认 10 [E4]。装载次数由 `my12306.token.load` 计数器记录 [E2]，可以用来观测懒加载频率。

**第八步：出锁后重试一次取令，并接受三种收尾。** 装载返回后，`takeToken` 对同一个 key 再执行一次取令 Lua [E5]。返回 1 则 `my12306.token.pass` 计数并放行；返回 0 则 `my12306.token.reject` 计数并拦截；其余情况（包括装载后仍缺席别）记 `my12306.token.degrade` 并降级放行，异常路径同样记降级并放行 [E5]。这一步是核心 模型最直白的体现：桶只是闸门，闸门失灵时的默认动作是放行，真正拦不拦得住由后续的 MySQL 条件更新裁决 [E4]。

**最后一点关于"桶怎么跟库存重新对齐"。** 写回带 TTL 意味着桶不会永久存在；而购票与取消路径上被主动删除的，是另一个前缀 `TRAIN_STATION_REMAINING_TICKET` 构成的**余票查询缓存** key [E8][E10]，跟桶 key 不是同一个东西。由此可以推断：桶内数值除了取令与归还这两条 Lua 路径，主要靠 TTL 过期后重新装载来与数据库库存收敛 。需要说明的是，这个推断依赖一个前提——假定代码库中不存在其他主动刷新余票桶 key 的入口；如果存在这样的入口，结论就不成立。

## 取令与还令：三个返回值串起来的动作

取令与还令不是两个独立的功能，而是同一把钥匙的两次使用：两次都先用 `buildBucketKey(trainId, departure, arrival)` 拼出同一个 Redis key，再分别把 `TAKE_TOKEN_SCRIPT` 与 `RETURN_TOKEN_SCRIPT` 打向它 [E4][E5][E1]。正是因为 key 的构造方式一致，扣减和归还在数据上落在同一个桶里，一取一还才能构成配平关系。下面用伪代码 把这两条路径的走向画出来，随后再解释每一步为什么这么走。

```
takeToken(trainId, dep, arr, seatTypeCountMap):
    if (!enabled || map == null || map.isEmpty()) return true      // 闸门关闭=直接放行
    requested = normalize(seatTypeCountMap); if (requested.isEmpty()) return true
    key = buildBucketKey(trainId, dep, arr)
    try:
        r = execute(TAKE_TOKEN_SCRIPT, key, requested)
        if (r == BUCKET_MISSING /*-1*/):                            // 桶不存在
            loadBucket(key, trainId, dep, arr, requested 的席别集合)
            r = execute(TAKE_TOKEN_SCRIPT, key, requested)          // 装载后重试
        if (r == TAKE_SUCCESS /*1*/):  pass++;    return true
        if (r == TAKE_REJECTED /*0*/): reject++;  return false
        degrade++; return true                                      // 装载后仍无法归类
    catch (ex):
        degrade++; return true                                      // 异常也放行

returnToken(trainId, dep, arr, seatTypeCountMap):
    if (!enabled || map == null || map.isEmpty()) return
    returned = normalize(seatTypeCountMap); if (returned.isEmpty()) return
    key = buildBucketKey(trainId, dep, arr)                         // 与取令同一个 key
    try: execute(RETURN_TOKEN_SCRIPT, key, returned)
    catch (ex): warn + degrade++                                    // 不外抛，仅告警计数
```

三个返回值其实是在编码三种「闸门状态」：`1` 是有桶且有量、`0` 是有桶但该次请求量过不去、`-1` 是这道闸门此刻根本不存在 [E4][E5]。前两者是可以直接裁决的，所以调用方立刻分流：返回 `1` 计 `my12306.token.pass` 并返回 `true`；返回 `0` 计 `my12306.token.reject` 并返回 `false` [E5]。`-1` 不可裁决，因为桶没装载过，任何 「有票/无票」的判断都无从谈起，于是走 `loadBucket` 从数据库把该车次区间的席别量聚合进 Redis，然后**再调一次同一个脚本**——注意是重试而不是自己算，判定权始终 留在脚本里 [E5][E4]。

`0` 这条分支的后果值得单独看：`takeToken` 本身只返回 `false`，真正把它变成用户可见结果的是上层。在 `PurchaseTicketServiceImpl#purchaseTickets` 里，取令调用 发生在 `loadPassengers`、`reserveLocally`、`createOrder` 之前，一旦 `tokenTaken` 为假就抛 `ServiceException("列车站点已无余票")` [E7]。因此这个 `0` 的含义是「在触达任何占座与下单动作之前，请求就到此为止」——这正是准入闸门该站的位置。这里要说明的是，脚本在什么条件下才返回 `0`，不在本次证据范围内；例如可以假设脚本在该席别余量不足以覆盖本次请求量时返回 `0`，那拒绝也就发生在座位被占之前，但这只是流程示意，不是对脚本内部逻辑的断言 [E4]。

`-1` 之后的第二次执行如果仍然给出 `1` 或 `0`，就按上面的分流正常处理；如果给出任何归不进这两类的值（包括再次 `-1`），代码会打一行「令牌桶装载后仍缺少席别， 降级放行」的告警、计 `my12306.token.degrade`，然后返回 `true` [E5]。异常路径同理，只是换了一条日志。值得留意的是判定写法用的是 `Long.valueOf(BUCKET_MISSING).equals(result)` 而不是直接比较数值，这意味着结果为 `null` 时不会走到「桶缺失」分支，而是落到最后的降级放行——从写法上看，所有「说不清」的情况都被收敛到同一 个出口 [E5]。

还令这条路径短得多，但取向和取令一致。它同样先做 enable/空值/归一的短路，再用同一个 key 调 `RETURN_TOKEN_SCRIPT`；区别在于整个执行被 try 包住，异常只记一条 warn 和 `my12306.token.degrade`，不向外抛 [E1]。为什么必须吞掉异常：从 `purchaseTickets` 的调用位置看，`returnToken` 是在 `finally` 里、`reservationCommitted` 为假时被调用的 [E7]，归还若抛出，就会顶掉主流程正在冒泡的那个失败原因。日志里那句「保留偏松降级并等待 TTL 自愈」也点明了兜底手段——归还失败意味着桶里的计 数偏多（偏松），而桶本身带过期配置（`expire-minutes` 默认 10 [E4]），所以这个偏松状态有明确的时间上界，不需要额外的对账或补偿来收敛 [E1][E4]。

把两条路径合起来看，它们共同维护的是一致的方向性：取令在装载后仍无法归类时放行、在脚本异常时放行 [E5]，还令在失败时不阻塞、不抛出 [E1]，这与类注释「异常时始终降级放行」是同一取向 [E4]。代价就是在故障窗口内可能出现「放行了但其实无票」的请求——这不是问题，因为桶只决定放行与否，能否占座最终仍由 MySQL 的条件更新裁决 [E4]。反过来说，`0` 这条唯一真正拦人的分支也必须站在 MySQL 判定之前，才能起到拦截无效请求、保护后续链路的作用 [E7]。至于两个 Lua 脚本内部的比较与增减规则，本次证据只能确认脚本被调用、以及调用方如何处理三个返回值，脚本内部逻辑无法确认。

## 谁负责把令牌还回去：单一归还方的设计

令牌是要被"还"的，但只能还一次——这是这一节所有设计取舍的起点。余票桶的存在意义是当闸门：桶里有数才放请求过去，桶里没数就直接拒绝 [E7]。因此桶内计数的准确性 只有两个方向会坏：少了，闸门会把真实有票的请求挡在门外；多了，闸门会把超出座位数的请求放进数据库，让本该在 Redis 层面完成的粗筛失效，压力全部落到 MySQL 的库存裁决上。既然桶是按「车次+区间+席别」记数的准入名额 [E7]，那么"同一笔名额被归还两次"就不是无害的重复动作，而是直接把闸门调松。

在这个约束下，最自然的直觉做法是"每条可能释放座位的路径都顺手把令牌还回去"，但这样做必须为每条路径配一套幂等去重，否则同一个占座既被主流程的异常分支归还、又被回调归还。项目没有走去重路线，而是走"所有权转移"路线：主流程 `purchaseTickets` 的 `finally` 块里，归还动作被 `reservationCommitted` 这个布尔量守住，只有本地占座未提交成功时才调用 `returnToken`；代码注释直接写明，本地事务提交之后，取消回调是唯一的令牌归还方 [E7]。也就是说，`reservationCommitted = true` 这个赋 值点就是归还责任的分界线：分界线之前，主流程拥有令牌；分界线之后，主流程主动放弃归还权，改由回调侧接管。用状态位做一次性的所有权交接，比让两侧都还、再去重要简单——代价是把"不会重复"的保证，建立在对这条分界线的严格执行上。

分界线的另一侧，也就是回调侧，处理的是时机问题。`returnTokensAfterCommit` 并没有立刻调 `tokenBucket.returnToken`，而是把它包成一个 `Runnable`，先判断当前是 否存在活动的事务同步：不存在就立即执行，存在就注册到事务同步的 `afterCommit` 上 [E6]。这解释了本节要回答的后半问：为什么不能在释放座位的事务里同步还令牌。座位释放本身是一个数据库事务，事务在提交之前是可能回滚的；如果归还动作和事务内的释放动作同步发生，就等于在座位还没真正回到可售状态时，先把准入名额还进了桶。从注册位置的选择可以看出，这样安排正是为了避免"座位尚未真正释放就先还令"，否则桶内数值会先一步虚高。顺带一个细节也指向同一意图：`releasedBySeatType` 在注册前 被 `Map.copyOf` 复制成不可变快照 [E6]，因为回调是延迟执行的，若直接引用可变 Map，注册之后发生的修改会污染这次延迟归还的数值。

把两条路径拼起来看，这套设计其实是在回答"令牌归还该由谁负责"，而不是"该在哪里归还"：主流程只负责一件事——发现自己没走到提交那一步，就把令牌原样退回；一旦提交成功，它就不再碰令牌，剩下的交给在事务提交后才触发的回调 [E6][E7]。这样做的收益是归还路径单一、时机与事务状态绑定；它的代价也很明确：提交之后主流程完全弃权 ，归还的达成依赖回调链路被真正触发。如果某个取消动作最终没有走到 `returnTokensAfterCommit`，那么按这套分工，令牌不会被任何人归还，桶里的可用数会低于真实余票——这属于该设计的已知薄弱面，因为项目当前证据只能确认"谁负责还"，不能确认"回调一定不会丢"。同样，当本地占座已提交、但订单侧拒绝而走补偿释放座位时，令牌归还也应经由回调那一侧完成，这一点由注释中的"唯一归还方"可以推知，但具体补偿链是否确实调用到该回调，无法从当前证据确认。

## 并发下的三层保护，别把它们看成一件事

三处“锁”经常被读成同一件事的三次重复，但从证据看，它们的互斥对象、key 构成和加锁位置都不一样，各自守的是流程里的不同一段：有的守“桶怎么被造出来”，有的守“计 数怎么被改写”，有的守“本地占座事务怎么被串起来”。把它们叠在一起看，余票桶仍然只是那道准入闸门——`TicketAvailabilityTokenBucket` 的类注释写得很直白：它只负责 购票准入，不是库存事实源，异常时始终降级放行，最终能否占座由 MySQL 条件更新决定 [E4]。三层保护要放在这个前提下理解：它们让闸门自身不出错，但都不改变“裁决权 在数据库”这件事。

第一层是装载锁，发生在桶尚不存在或字段不完整的时候。`loadBucket` 先用 `trainId`、`departure`、`arrival` 拼出 `keySuffix`，再套进 `LOCK_TRAIN_STATION_TOKEN_BUCKET` 模板得到 `lockKey`，然后把整段装载逻辑交给 `redisCacheHelper.executeWithLock(lockKey, ...)` 包裹 [E2]。注意锁内的第一件事不是查库，而是 `hMultiGet`  检查本次请求涉及的席别字段是否齐全，齐全就直接返回 [E2]。这说明装载锁要防的不是“读不到”，而是“同时有多个请求都判定读不到、于是各自去聚合一遍并各自写回”。锁 真正罩住的是那段聚合 SQL 加两次映射表读取、再补零、再 `hPutAllWithTtl` 的完整区间 [E2]，所以同一区间同一时刻只有一次真实装载；`my12306.token.load` 计数器写 在 lambda 内部，因此它统计的是实际发生的装载次数，而不是尝试次数——这是从计数器位置推出的结论，不是独立事实 [E2]。锁随 lambda 结束退出，具体的释放实现不在本 节证据范围内，这里不做断言。

第二层不是 Redisson 锁，而是两条 Lua 脚本：类里静态加载了 `lua/take_token_from_bucket.lua` 和 `lua/return_token_to_bucket.lua`，统一的 `execute` 入口接收脚 本、`bucketKey` 和席别计数映射，返回值被三个常量解释为成功（1）、拒绝（0）和桶缺失（-1） [E4]。为什么非得是脚本而不是“先 GET 再 SET”：扣减和归还本质都是读改写，如果拆成两次往返，两个并发请求可能读到同一个旧值、各自减一、再各自写回，结果只减了一次。Lua 在 Redis 服务端把整个读改写当成一个不可分割的执行单元，互斥 范围落在单个 `bucketKey` 上——这是数据层面的原子性，不需要显式加解锁 [E4]。也正因为它是数据层面的，它管不到数据库：脚本成功只意味着“闸门放行了一个名额”，不意味着那个名额真的被扣到了库存行上。

第三层才是购票期间的业务锁，出现在 `reserveLocally` 里，加锁顺序是固定的：先按 `username` 加 `trainId` 拼出用户锁并 `lock()`，再遍历本次请求的 `seatTypeCounts.keySet()`，逐个按 `trainId` 加 `seatType` 拼出席别锁并 `lock()`，全部拿到之后才调用 `doPurchaseInTransaction` [E11]。退出路径严格逆序：`finally` 里先停止临界区计时（并把计时上报失败吞成一条 warn，注释明确写着可观测性不得改变预占或令牌归属的语义），再从后往前释放席别锁，最后释放用户锁 [E11]。为什么要先用户后 席别、释放时反过来：同时购买多个席别的事务会持有不止一把席别锁，如果不同请求按不同顺序抢这些锁，就会互相等成环；固定顺序让所有竞争者排成同一条队列。而用户锁的粒度比席别锁细得多——它只串行化“同一个用户在同一车次”的重复提交，真正的跨用户争抢发生在席别锁上。这一层锁保护的是本地事务的临界区，它的作用范围到事务返回为止，不延伸到库存判定。

| 层次 | 互斥对象 | key / 作用域 | 加锁位置 | 退出方式 | 能保证 | 管不到 |
|---|---|---|---|---|---|---|
| 桶装载锁 | 同一车次+区间的桶构建 | `LOCK_TRAIN_STATION_TOKEN_BUCKET` + (trainId, departure, arrival) [E2] | `loadBucket` 内，`executeWithLock` 包住装载全 程 [E2] | 随 lambda 结束退出，释放细节本节不做断言 | 字段缺失时只有一次真实装载与写回 [E2] | 不参与准入判定，也不保证桶与库存一致 |
| Lua 扣减/归还 | 单个 `bucketKey` 上的读改写 | `bucketKey` 本身，数据层原子性，非 Redisson 锁 [E4] | Redis 服务端脚本执行中 | 脚本返回即完成，无显式解锁 | 单次成功/拒绝/缺失的判定与计数更新不丢失 [E4] | 不触达数据库，不跨 key，也不串行化整个购票流程 |
| 用户锁 / 席别锁 | 同一用户同车次的本地占座；同一车次同一席别 | `LOCK_PURCHASE_TICKETS_USER`(username, trainId)；`LOCK_PURCHASE_TICKETS_SEAT_TYPE`(trainId, seatType) [E11] | `reserveLocally` 中，进入 `doPurchaseInTransaction` 之前 [E11] | `finally` 中席别锁逆序、用户锁最后 [E11] | 固定加锁顺序、逆序释放，收窄 本地事务临界区 [E11] | 不决定库存成败，成败由 MySQL 条件更新裁决 [E4] |

从 key 的构成和加锁位置就能看出这三层无法合并：装载锁的 key 带区间、只在桶不完整时被触碰；Lua 的互斥范围是一个 Redis key 的数据操作；用户锁与席别锁的 key 分别是“用户+车次”和“车次+席别”，且它们在业务事务边界内成对出现 [E2][E4][E11]。这也解释了为什么加了这么多锁，桶仍然不能当账本：锁保证的是各自那一段操作不被打乱，而桶的值来自某一次聚合查询加上 TTL 装载 [E2]，`expireMinutes` 默认十分钟 [E4]——也就是说桶是一个会过期、会重建的派生视图。假设某个区间已经卖空，桶把对应席 别减到 0；此时即使三层锁全部正常工作，也只是让“0 会稳定地拒绝请求”这件事成立，而如果数据库侧的行因为释放订单等原因重新可售，桶不会因此自动知道，要等重新装载或 TTL 到期。这就是为什么类注释把降级放行和 MySQL 条件更新写在一起 [E4]：前者说明闸门失效时宁可放行，后者说明放行的请求最终仍要在数据库那里过一遍条件更新。 三层保护是闸门自身的工程质量，不是库存一致性的来源。

## 桶出错的时候：降级、放行、等 TTL 自愈

正常运行的时候，取令就是一次 Lua 调用：返回 1 放行、返回 0 拒绝，返回 -1 说明桶根本不在，于是先在锁内装载再从数据库聚合一遍，然后重试一次 [E5][E2]。这是桶唯一"有意见"的时刻。一旦这套判断本身出问题，代码的选择是不再判断。

第一类故障出在 execute 抛异常，Redis 连不上或脚本执行失败都算。takeToken 的 try 块包住了从 execute 到 loadBucket 重试的整段逻辑，所以异常直接落到 catch：打 一条 warn「余票令牌桶取令异常，降级放行」，degrade 计数器加一，然后 return true [E5]。返回的是 true，不是"没判断"，而是"判断为放行"。有个容易漏掉的细节：loadBucket 是在同一个 try 里被调用的 [E5]，而它内部会抛 IllegalStateException——车次不存在、车型查不到席别都会触发 [E2]——所以装载阶段的异常和取令阶段的异常走的 是同一条降级路径，不需要各自处理。

第二类更隐蔽：execute 正常返回了，但返回的值既不是 1 也不是 0。比如装载完成之后某个席别的 field 仍然缺失。此时 takeToken 的末段兜底先 warn「令牌桶装载后仍缺少席别，降级放行」，同样记 degrade、同样 return true [E5]。这条分支值得停一下：装载流程本身已经做了「只要本次涉及的任一席别缺失就重新装载完整桶」的检查，并 且会按车型支持的全部席别补 0 [E2]，而兜底分支依然存在，说明代码不假设装载一定补得齐——它给"补不齐"也留了出路。

还令的情况性质不同。returnToken 同样包了 try/catch，异常时只打 warn「余票令牌归还异常，保留偏松降级并等待 TTL 自愈」并记 degrade [E1]。它是 void 方法，没有 返回值可以决定放不放行，所以这里的容错是另一层含义：不让归还失败向上冒泡、打断已经走到一半的取消或回滚流程。代价要说清楚：归还失败意味着桶里的数没有加回去，因此在一个 TTL 周期内，桶的可用数可能低于数据库里的真实可售数 [E1]，这段时间里本可成功的请求会被 Lua 正常地返回 0 挡掉——这不是异常路径，降级放行接不住它。这是"偏松"取向下覆盖不到的一角，也是 TTL 存在的直接理由。

恢复不靠主动修复，靠过期重建。装载时用 hPutAllWithTtl 写入，过期时间来自 @Value 注入的 expire-minutes，注解给的默认值是 10 分钟 [E2][E4]。到点后整个 key 消 失，下一次取令的 Lua 返回 -1 [E5]，于是重新触发 loadBucket，在锁内从 MySQL 聚合真实可售数再写一遍 [E2]。所以桶不是被"修好"的，而是被"作废重建"的，每一次重装都会重新设定 TTL。这把上面所有漂移——异常期间的放行、归还失败的漏加、装载失败留下的空桶——都压缩在最长一个 TTL 的窗口内，而不是永久累积。具体是 10 分钟还是别 的值取决于部署配置，类里给出的只是注解默认值 [E4]。

把这几条并起来，异常下的取向就很直白：取令能返回就按返回值判断，返回不了或返回不认识，就放行；还令失败就放弃，等 TTL 重来。类注释把这条取向写死了——「异常时 始终降级放行，最终是否能占座仍由 MySQL 条件更新决定」[E4]。这正是闸门与账本的分工：闸门误开，最坏是多放几个请求到下游，MySQL 的条件更新会自己裁决；闸门误关 ，则是把本该成功的购票挡在门外，用户只看到一次没有解释的失败。

一个反例可以把方向钉住。假设把 takeToken 的 catch 改成 return false，也就是 Redis 一抖就拒绝：桶本身不持有库存事实 [E4]，用缓存的可用性去否决数据库本可以给 出的正确判断，等于故障期间全线误拦，而真正承担裁决的 MySQL 其实毫发无伤。反过来放行，代价只是那段时间多了一些请求打到下游，以及超出桶余量的部分靠条件更新筛 掉。两边代价不对称,「宁可放过多、不可错拦」就是从这里来的。

同样的思路在余票查询缓存上复现了一次。PurchaseTicketServiceImpl 的 evictRemainingTicketCacheSafely 把 delete 包在 try/catch 里，失败时只 warn「本地占座已提 交，但余票缓存删除失败，等待缓存过期」[E10]。这句话的顺序很关键：占座已提交在前、删缓存失败在后，因此不能因为删缓存失败就回滚占座——缓存是读加速，删不掉就等 它自然过期，最坏是短时间内读到偏旧的余票数，而不是已售出的座位被吐回去。TicketCallbackServiceImpl 的 evictRemainingTicketCache 做的是同类失效动作，是一句直 接的 delete [E8]；两处指向同一个缓存 key 的构造方式，但从这段代码本身看不出它是否也带等价的异常包装。

最后要认下偏松的代价。异常期间被放行的请求会集中进入下游，如果 MySQL 恰好也在承压，压力是叠加的；而归还失败造成的桶数偏低会在一个 TTL 窗口内产生误拦。项目选择接受这两项，理由是它们都有明确的时间上界（TTL），且都不会破坏以 MySQL 为准的最终一致性——这也是为什么 TTL 在这个设计里不是可选的清理策略，而是整个容错方案 的收口。

## 这套设计换到了什么，代价是什么

评价这套余票桶设计，关键不是问“桶里的数字准不准”，而是问“它替系统换掉了什么，又把什么责任明确地推给了别人”。只有把它当成一道闸门而非一本账，才能同时解释它为什么敢在异常时放行，也解释它为什么不能充当权威库存——这层定位在类注释里写得很直白：Redis 余票令牌桶只负责购票准入，不是库存事实源，异常时始终降级放行，最终是否能占座仍由 MySQL 条件更新决定 [E4]。

换到的第一样东西，是入口处的轻量拦截。takeToken 在购票入口只发起一次 Redis 脚本调用，拿到成功、拒绝或“桶缺失”三种结果之一就返回布尔值；桶缺失时先在锁内装载 、再重试一次，仍拿不到有效结果就记一笔降级计数并放行 [E5]。也就是说这条链路上没有任何会阻塞购票的强依赖——桶挂了、桶不完整、脚本抛异常，代价只是少挡了一层请 求，而不是让购票失败。

第二样是原子化的计数变更。扣减与归还分别由类级静态脚本 TAKE_TOKEN_SCRIPT、RETURN_TOKEN_SCRIPT 承担 [E4]。高频路径上因此没有“先读再写”的竞态，也不需要为每次 扣减去抢分布式锁——从调用结构看，锁只在装载桶时出现 [E2]，属于低频路径。这说明设计上是刻意把并发控制下沉到脚本、把互斥留在装载阶段的。

第三样是懒加载加 TTL 带来的运维简单性，这一点最容易被低估。桶不是预先为所有车次区间生成的，而是某次请求真正需要、又发现桶缺失时，在锁内用一条 group by 聚合 查询把该区间各席别的可售数一次取回再整体写入 [E2]；写入时还按车型支持的全部席别补 0，用来避免“售完的席别永久触发字段缺失重装” [E2]；整桶带 expireMinutes（默认 10 分钟）过期 [E4]。由此可以推导：项目不需要全量预热任务、不需要独立的桶清理作业，也不需要为每次库存变更维护一条精确同步通道，过期即自愈、缺失即重装，维 护成本被压到很低。

代价同样清楚，而且正是上述收益的另一面：既然桶靠 TTL 而不是靠与 MySQL 的逐步同步来保持新鲜，那么在一个 TTL 窗口内，桶里的值就只是某个时刻的数据库快照叠加此 后的扣减与归还，可能与真实可售数发生偏离。方向只能是偏松——takeToken 在异常、以及在装载后字段仍然缺失时都返回 true [E5]。这是有意为之：如果反过来在异常时拒绝，桶就从“少挡一层”变成“误杀正常购票”的故障源，而它本来就没有能力判断自己是否可信。

边界也随之划定。桶不提供座位分配能力，它的数据形态只是按席别记的整数计数 [E2]；它也不承担余票查询数据源的角色。查询侧走的是另一套 key：前缀为 TRAIN_STATION_REMAINING_TICKET 的缓存，在本地占座提交后被删除（删除失败则记警告并等待过期）[E10]，在回调流程中同样被删除 [E8]。这与桶自身由 TRAIN_STATION_TOKEN_BUCKET 前 缀拼接车次区间构成的 key [E12] 是完全独立的两条缓存路径。项目确实对外提供余票分页查询接口 [E9]，但其实现不在本次证据范围内，因此无法确认它是否读取桶；不过从两套 key 前缀彼此独立、且所有删除动作都只针对 remaining-ticket 缓存这一点看，把桶当查询数据源缺乏证据支持。

所以对这套设计的评价应当落在“责权是否对齐”上：它用准确性换取入口效率，用偏松换取不断购，用懒加载与 TTL 换取运维上的轻量，而把准确性、否决权与座位分配全部留 给 MySQL。判断它好不好，不该看桶里的数字像不像真库存，而要看漏放和错放的请求是否在下一层被稳稳兜住。真正危险的从来不是这套交换本身，而是有人把闸门误读成账本——一旦把桶当作查询数据源，就会得出“查到的余票是权威库存”这种与设计意图相反的结论。

## 要点回收

把整个余票桶压缩成一句可复述的模型：它是挂在 Redis 上的一道**购票准入闸门**——Hash 结构按「车次+区间」分桶、按席别记数，取令与还令都走 Lua，桶缺失时在锁内从 数据库聚合装载并带 TTL；它只回答「这次请求能不能继续往下走」，从不回答「还剩几张票」，真正的库存裁决始终在 MySQL [E4]。

回看**结构**：桶的 key 由车次、出发站、到达站拼成 [E12]，field 是席别、value 是可售计数；装载时不是只写本次请求涉及的席别，而是按车型支持的全部席别补 0 [E2]。这一笔补齐有实际含义——「售完」被记成计数 0，是一个可以正常扣减失败的数值；「字段不存在」才是需要重装桶的信号，两者不能混为一谈。

回看**流程**：请求先 takeToken 走 Lua 扣减，Lua 返回桶缺失时就地进入 loadBucket，在锁内先 hMultiGet 校验本次涉及的席别字段，只要缺任一席别才用一次 groupBy  聚合查询取回真实可售数，再 hPutAllWithTtl 写回并重试取令 [E5][E2]；反向路径由取消回调在事务提交后调用 returnToken 走 Lua 归还 [E6]，而购票主流程只在本地预留未提交的 finally 分支里自行归还 [E7]，两条归还路径互不重叠。

由此收束出三条设计取向：**准入而非记账**——桶的存在只为分流，不承担库存事实源的角色 [E4]；**原子而非同步**——取令与还令各自以一次 Lua 执行为单位完成，不靠应用层加锁拼凑中间状态 [E5][E1]；**降级而非拒绝**——取令异常、或装载后仍缺席别时一律放行 [E5]，归还异常则保留偏松状态等待 TTL 自愈 [E1]。最坏结果是多放若干请求去 MySQL 上竞争，而不是把一个本可成交的购票请求挡在门外。
