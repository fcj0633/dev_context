当前 `ask` 实际上可以走 **4 条可直接执行的回答链路**。

需要先区分两个概念：

> `--answer-mode` 本身只有 **3 个值：`legacy / explain / teach`**。  
> 另外还有一个独立开关 `--no-plan`，它会绕开当前的新 Evidence 检索链路，执行更早期的 `AgenticRetrievalWorkflow`。

所以从“用户现在能跑出几种回答”来看，是 **4 种**。

---

# 一、总览

| 调用方式 | 定位 | 检索链路 | 回答链路 |
|---|---|---|---|
| `--no-plan` | 最早保留版本 | 旧 Agentic Retrieval | 直接 AnswerGenerator |
| `--answer-mode legacy` | 新检索 + 老回答 | 当前 Evidence Retrieval | 直接 AnswerGenerator |
| `--answer-mode explain` | V2 | 当前 Evidence Retrieval | AnswerPlanner → Grounded Draft → Reviewer |
| `--answer-mode teach` | V3 | 当前 Evidence Retrieval | ExplanationPlanner → Section Writer → Composer → TeachingReviewer |

默认：

```bash
uv run devcontext ask "问题"
```

等价于：

```bash
uv run devcontext ask "问题" --answer-mode legacy
```

---

# 二、模式 1：`--no-plan`

命令：

```bash
uv run devcontext ask "问题" --no-plan
```

这是目前还能直接调用的**最早完整回答链路**。

整体流程：

```text
User Query
   ↓
QueryRouter
   ↓
判断 CODE / DOC / MIXED
   ↓
RetrievalPolicy
   ↓
Hybrid Retrieval
   ↓
ContextBuilder
   ↓
ContextBundle
   ↓
ContextSufficiencyChecker
   ↓
够不够？
   │
   ├── enough
   │      ↓
   │  AnswerGenerator
   │
   └── insufficient
          ↓
     QueryRewriter
          ↓
       再检索
          ↓
     最多继续若干轮
          ↓
     AnswerGenerator
```

## 它的核心特点

它不会先问：

> “回答这个问题需要哪些 Evidence？”

而是直接：

```text
原始问题
→ 路由
→ 搜索
```

例如：

> 为什么项目使用责任链？

它可能直接判断：

```text
Route = DOC
```

然后搜索整个问题。

---

## 它判断的是“整个 Context 够不够”

即：

```text
ContextBundle
↓
Sufficiency
```

而不是现在这种：

```text
ER1 SATISFIED
ER2 PARTIAL
ER3 MISSING
```

所以它属于比较早期的：

> **Query → Context → Answer**

模式。

---

# 三、模式 2：`legacy`

命令：

```bash
uv run devcontext ask "问题" --answer-mode legacy
```

这是最容易误解的模式。

它虽然叫：

```text
legacy
```

但**不是整条老链路**。

它实际使用的是：

> **当前最新 Evidence Retrieval + 旧式直接回答。**

---

## Legacy 的完整流程

```text
User Query
   ↓
EvidencePlanner
   ↓
Evidence Requirements
   ↓
SearchActionPlanner
   ↓
RetrievalController
   ↓
EvidencePool
   ↓
EvidenceWorkspace
   ↓
CoverageChecker
   ↓
必要时第二轮 Retrieval
   ↓
EvidencePackage
   ↓
ContextBundle
   ↓
AnswerGenerator
   ↓
Final Answer
```

前半部分已经是当前新的检索系统。

---

# 四、Legacy 前半段具体做了什么

假设问题：

> 为什么项目使用责任链？

首先：

```text
EvidencePlanner
```

可能得到：

```text
ER1：证明项目真实存在责任链
ER2：找到实际业务场景
ER3：找到设计原因
ER4：找到排序机制
ER5：找到扩展方式
```

然后：

```text
SearchActionPlanner
```

决定：

```text
ER1 → CODE
ER2 → CODE
ER3 → DOCUMENT / MIXED
ER4 → CODE
ER5 → CODE
```

执行检索后放进：

```text
EvidenceWorkspace
```

再通过：

```text
CoverageChecker
```

得到：

```text
ER1 SATISFIED
ER2 PARTIAL
ER3 SATISFIED
...
```

必要时补检索。

---

# 五、但 Legacy 回答阶段非常简单

得到 `EvidencePackage` 之后：

如果证据足够：

```text
ContextBundle
↓
AnswerGenerator.generate()
```

证据不够：

```text
ContextBundle
+
Missing Gaps
↓
AnswerGenerator.generate_partial()
```

结束。

它没有：

```text
AnswerPlanner
ExplanationPlanner
Composer
TeachingReviewer
```

所以可以把 Legacy 理解成：

> **“新检索系统到底带来了什么效果”的基础回答模式。**

非常适合作为后续 Answer V2/V3 的 baseline。

---

# 六、模式 3：`explain`

命令：

```bash
uv run devcontext ask "问题" \
  --answer-mode explain \
  --depth detailed
```

这是你之前的 **V2 Answer Quality**。

检索部分和 Legacy 基本一致：

```text
User Query
↓
EvidencePlanner
↓
SearchActionPlanner
↓
RetrievalController
↓
EvidenceWorkspace
↓
Coverage
↓
EvidencePackage
```

真正不同从回答阶段开始。

---

# 七、Explain 的回答流程

```text
EvidencePackage
      ↓
AnswerPlanner
      ↓
AnswerPlan
      ↓
Grounded Draft
      ↓
AnswerReviewer
      ↓
Final Answer
```

---

## 1. AnswerPlanner

先决定：

```text
直接结论是什么？
回答深度是什么？
应该有哪些章节？
Evidence 怎么组织？
有什么冲突？
有什么证据缺口？
```

得到：

```text
AnswerPlan
```

例如：

```text
直接结论

## 为什么不用 if-else
## 项目如何实现
## 应用场景
## 设计取舍
## 证据边界
```

---

## 2. Grounded Draft

然后：

```text
AnswerPlan
+
ContextBundle
↓
AnswerGenerator
```

一次生成完整回答。

这是 V2 很关键的特点：

> **通常仍是 Whole-answer Generation。**

也就是整个文章一次生成。

---

## 3. AnswerReviewer

对详细回答或者出现：

```text
Citation 问题
Conflict
Fallback Plan
结构问题
```

时调用 Reviewer。

Reviewer 可以对整篇回答进行修正。

所以 V2 可以概括为：

> **先规划文章，再一次写完，再整体审稿。**

---

# 八、模式 4：`teach`

命令：

```bash
uv run devcontext ask "问题" \
  --answer-mode teach \
  --depth detailed
```

或者：

```bash
--depth deep
```

这是当前 **V3**。

检索前半部分依然共享：

```text
EvidencePlanner
↓
SearchActionPlanner
↓
RetrievalController
↓
EvidenceWorkspace
↓
Coverage
↓
EvidencePackage
```

但是 Answer Pipeline 完全升级。

---

# 九、Teach / V3 的完整流程

```text
EvidencePackage
      ↓
ExplanationPlanner
      ↓
ExplanationPlan
      │
      ├─ core mental model
      ├─ explanation strategy
      ├─ section types
      ├─ claim types
      └─ evidence bindings
      ↓
判断 Fast / Multi-pass
      ↓
Section View
      ↓
TeachingWriter
      ↓
DraftSection
      ↓
重复 N 个 Section
      ↓
Grounding Check
      ↓
SectionComposer
      ↓
TeachingReviewer
      ↓
需要修改？
      │
      ├─ no → Final Answer
      │
      └─ yes
             ↓
       Targeted Revision
             ↓
       只重写问题 Section
             ↓
          Composer
             ↓
         Final Answer
```

---

# 十、V3 的第一步：ExplanationPlanner

和 V2 的：

```text
AnswerPlanner
```

不同。

V2 问的是：

> “这篇答案怎么组织？”

V3 问的是：

> “用户怎样才能真正理解？”

所以它会额外产生：

```text
core_mental_model
```

例如：

> 责任链不是为了“能校验”，而是为了把不断增长、有顺序、有不同成本的校验规则从稳定主流程中拆出去。

然后决定讲解策略：

```text
PROBLEM_SOLUTION
MECHANISM
COMPARISON
FAILURE_ANALYSIS
TRADEOFF
...
```

再规划章节。

---

# 十一、V3 不直接一次写全文

例如 Planner 得到：

```text
S1：问题是什么
S2：核心模型
S3：项目怎么实现
S4：为什么 order 重要
S5：边界与代价
```

每个 Section 都有自己的：

```text
Evidence Labels
```

例如：

```text
S1 → E1 E4
S2 → E1 E3
S3 → E2 E3 E5
S4 → E3 E6
```

---

# 十二、Section View

生成 S3 时：

```text
EvidenceWorkspace
↓
只选 E2 E3 E5
↓
Section Context View
```

TeachingWriter 只看到这些证据。

这和 Explain 最大区别之一就是：

```text
Explain：
一整个 ContextBundle
→ 一次生成全文

Teach：
Workspace
→ 每节自己的 Context
→ 分节生成
```

---

# 十三、TeachingWriter

Writer 不只是知道：

```text
“请写 S3”
```

它还知道：

```text
Core Mental Model
Section Type
Teaching Goal
Claim Types
Evidence State
Allowed Citation
```

Claim 又区分：

```text
PROJECT_FACT
PROJECT_INFERENCE
GENERAL_CONCEPT
ILLUSTRATIVE_EXAMPLE
```

从而让模型知道：

> 哪些能当项目事实说，哪些只是推导，哪些是通用知识，哪些是假设案例。

---

# 十四、Grounding

每一节写完之后会进行一些确定性检查。

例如：

```text
PROJECT_FACT
但没有证据
```

或者：

```text
假设案例
却写成项目真实实现
```

或者：

```text
UNVERIFIED
却使用非常确定的语气
```

这些不需要再调 LLM。

---

# 十五、Composer

所有 Section 写完：

```text
S1 Draft
S2 Draft
S3 Draft
S4 Draft
```

再交给：

```text
SectionComposer
```

负责：

```text
统一术语
减少重复
增加过渡
让全文连贯
```

但不允许随意新增：

```text
项目事实
Citation
Symbol
```

。

---

# 十六、TeachingReviewer

然后进入教学质量审查。

它不只是检查：

```text
有没有 hallucination
```

还检查：

```text
有没有 mental model
有没有解释 why
是否由浅入深
章节是否跳跃
有没有没标记的假设
是否堆了无意义源码细节
```

如果：

```text
S1 OK
S2 OK
S3 有问题
S4 OK
```

它返回：

```text
revision_required = S3
```

然后只重新生成：

```text
S3
```

不会把全文重新写一遍。

这就是：

```text
Targeted Revision
```

。

# 十八、四者真正的演进关系

可以记成：

```text
V0 / --no-plan
“直接搜这个问题”
        ↓

V1 / legacy
“先搞清楚需要什么证据，再搜”
        ↓

V2 / explain
“证据找完后，先规划文章，再回答”
        ↓

V3 / teach
“证据找完后，先规划人的理解路径，
再按章节、按证据生成和审查”
```

所以不是：

```text
4 个完全独立的系统
```

而是越来越多能力叠加。

其中 **Legacy / Explain / Teach 三者共享当前最新的 Evidence Retrieval**，主要差异发生在回答阶段；只有 `--no-plan` 还走较早的整套检索链路。

另外，仓库里的旧 `PlannedRetrievalWorkflow / QuestionPlan` 属于 V0 和当前 Evidence-driven Retrieval 之间的一代历史实现，源码还在，但**当前 `ask` CLI 没有直接模式去调用它的完整回答链路**。
