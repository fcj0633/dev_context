可以把 `EvidenceWorkspace + Coverage` 看成 V3 检索层最关键的一次重构：

> **V2 是“先把检索结果压成一个 Context，再判断证据够不够”；V3 是“先完整保存检索证据，再独立判断每个 Evidence Requirement 是否满足，最后才决定回答时给模型看哪些 Context”。**

也就是把：

```text
“检索到了什么”
```

和：

```text
“这次 Prompt 能放下什么”
```

彻底分开了。

---

# 一、先看 V2 的流程

V2 的大致链路是：

```text
EvidencePlanner
      ↓
SearchActionPlanner
      ↓
Retrieval
      ↓
EvidencePool
      ↓
pool.select(..., top_k)
      ↓
ContextBuilder(max_chars)
      ↓
ContextBundle
      ↓
CoverageChecker
      ↓
EvidencePackage
      ↓
AnswerPlanner
      ↓
Explain Answer
```

这里最大的结构问题是：

```text
EvidencePool
      ↓
Top-K 筛选
      ↓
字符预算截断
      ↓
Coverage
```

也就是说 Coverage 判断的不是：

> “检索系统实际上找到的所有证据够不够？”

而是：

> “最终塞进 Answer Context 的证据够不够？”

这两个概念被混在一起了。

---

# 二、举一个最简单的例子

假设 EvidencePlanner 得到：

```text
ER1：找到责任链抽象结构
ER2：找到实际调用入口
ER3：找到为什么采用责任链的设计依据
ER4：找到 Handler 排序方式
```

检索实际上找到了：

```text
EvidencePool

ER1 → A、B
ER2 → C
ER3 → D、E
ER4 → F
```

总共 6 个 Chunk。

但是 ContextBuilder 只有：

```text
max_chars = 8000
```

于是可能最终只装进去：

```text
A
B
D
E
```

而：

```text
C
F
```

由于预算不够，被丢掉。

---

# 三、V2 的 Coverage 就会产生错误判断

V2 看到的是：

```text
ContextBundle

A
B
D
E
```

于是它可能判断：

```text
ER1 SATISFIED
ER2 MISSING
ER3 SATISFIED
ER4 MISSING
```

但实际上：

```text
ER2 的 C 已经检索到了
ER4 的 F 也已经检索到了
```

它们只是：

> **没有进入这一份 ContextBundle。**

所以：

```text
MISSING
```

其实不是 Retrieval Missing，

而是：

```text
Presentation Context Missing
```

。

这是 V2 非常重要的语义错误。

---

# 四、V3 加入 EvidenceWorkspace

现在链路变成：

```text
EvidencePlanner
      ↓
SearchActionPlanner
      ↓
RetrievalController
      ↓
EvidencePool
      ↓
EvidenceWorkspace   ← 新增
      │
      ├── CoverageView
      │       ↓
      │   CoverageChecker
      │
      └── ContextBuilder
              ↓
         legacy ContextBundle
```

核心变化就是：

> **EvidencePool 检索完之后，不再先经过 Top-K / ContextBuilder 才交给后面的系统，而是先完整复制/冻结到 EvidenceWorkspace。**

---

# 五、EvidenceWorkspace 到底是什么

你可以把它理解为：

> **“当前这次用户请求的完整证据仓库”。**

例如这次检索真正找到：

```text
20 个 Chunk
```

那么：

```text
EvidenceWorkspace
```

就保存这 20 个。

而不是因为 Answer Prompt 最后只能装：

```text
8 个
```

就把剩下 12 个当不存在。

结构上，每条 Evidence 会变成：

```text
EvidenceRef
├── chunk_id
├── evidence_id
├── citation
├── requirement_ids
├── source_role
├── temporal_status
├── authority_priority
├── first_seen_round
├── retrieval_rank
├── retrieval_score
└── content
```

注意一个设计：

```text
EvidenceRef
```

没有：

```text
truncated
```

。

因为：

> 一条 Evidence 本身没有“被截断”。

真正会截断的是：

```text
某一次 PromptContextView
```

。

这就是 V3 非常重要的一次概念分离：

```text
Evidence
≠
Prompt Context
```

---

# 六、EvidenceWorkspace 在什么时候建立

当前 `RetrievalController` 中，一次 `retrieve()` 开始时创建：

```python
workspace = EvidenceWorkspace(request.original_query)
```

然后第一轮检索：

```text
Round 0
↓
_execute(...)
↓
EvidencePool.add(...)
↓
workspace.ingest(...)
```

比如第一轮找到了：

```text
E1
E2
E3
E4
```

Workspace：

```text
[E1, E2, E3, E4]
```

---

# 七、为什么不能只在最后创建 Workspace

因为还有第二轮 Retrieval。

假设：

```text
Round 0
↓
ER3 PARTIAL
```

系统可能继续：

```text
Round 1
```

找：

```text
E5
E6
```

那么同一个 Workspace 会继续：

```text
Round 0:
E1 E2 E3 E4

Round 1:
E5 E6
```

最终：

```text
Workspace:
E1 E2 E3 E4 E5 E6
```

。

不是每一轮重新建一个 Workspace。

---

# 八、CitationRegistry 在这里一起解决了证据身份问题

以前 ContextBuilder 的 Citation 是：

```text
C1
C2
C3
```

它表达的是：

> 当前 Context 中第几个。

例如：

```text
Context A:
chunk 123 → C1

Context B:
chunk 123 → C7
```

同一证据身份会变化。

V3 Workspace 建立时通过：

```text
CitationRegistry
```

获得：

```text
chunk 123 → E3
```

以后无论：

```text
Coverage View
Planner View
Section View
```

都还是：

```text
E3
```

。

因此：

```text
E3
```

现在是：

> **Evidence Identity**

而不是：

> Context Position。

---

# 九、接下来进入 Coverage

V3 不会直接：

```text
CoverageChecker(workspace 所有 20 条 evidence)
```

。

因为每个 Requirement 应该只看自己的 Evidence。

比如：

```text
ER1：责任链抽象结构

workspace:
E1 AbstractChainHandler
E2 AbstractChainContext
E3 余票桶
E4 订单服务
E5 责任链设计文档
```

Coverage 判断 ER1 时，不应该把 E3、E4 都给它。

所以引入：

```text
WorkspaceCoverageView
```

。

---

# 十、CoverageView 做什么

假设：

```text
ER1:
E1 E2

ER2:
E4 E7

ER3:
E5 E8 E9
```

那么：

```python
view.items_for("ER1")
```

只返回：

```text
E1
E2
```

。

```python
view.items_for("ER3")
```

只返回：

```text
E5
E8
E9
```

。

所以现在变成：

```text
完整 EvidenceWorkspace
        ↓
按 Requirement 投影
        ↓
CoverageView
```

。

---

# 十一、这里和 V2 最大的不同：CoverageView 没有 Answer Context Budget

这是关键。

V2：

```text
Evidence
↓
Context max_chars=16000
↓
Coverage
```

V3：

```text
EvidenceWorkspace
↓
CoverageView
↓
Coverage
```

CoverageView 的职责明确是：

> **不能因为 Answer Prompt 长度限制而丢掉检索证据。**

所以：

```text
Coverage
```

和：

```text
Answer Context
```

现在完全解耦。

---

# 十二、CoverageChecker 接下来做两层判断

当前 Coverage 大致分：

```text
第一层：确定性 Source Gate
第二层：LLM Semantic Coverage
```

---

## 第一层：来源是否满足要求

假设：

```text
ER1:
source_requirement = CODE
```

结果只有：

```text
DOCUMENT
```

那甚至不需要 LLM。

可以直接判断：

```text
PARTIAL
```

并记录：

```text
缺少直接相关 CODE 证据
```

。

再例如：

```text
ER2:
source_requirement = BOTH
```

当前只有：

```text
CODE
```

那么：

```text
PARTIAL
```

。

---

# 十三、第二层才让 LLM 判断语义够不够

如果来源已经满足：

```text
ER3
target:
说明为什么项目选择责任链

success_criteria:
需要项目设计依据或能支撑该设计动因的直接证据

Evidence:
E5
E8
```

CoverageChecker 才把：

```text
Requirement
+
属于该 Requirement 的 Evidence
```

送给模型。

模型返回：

```text
SATISFIED
PARTIAL
MISSING
```

。

另外系统自己还有：

```text
UNVERIFIED
```

表示：

> 不是证据缺失，而是 Coverage 检查自己失败了。

比如：

```text
LLM 调用失败
JSON 解析失败
输出被截断
```

。

这和 V2 早期经常把：

```text
checker failure
```

误报成：

```text
evidence missing
```

相比，也是一个重要修复。

---

# 十四、一个非常重要的实现细节：Coverage 仍然只调用一次 LLM

这点很容易误解。

现在虽然：

```text
每个 Requirement 有独立 Evidence View
```

但不是：

```text
ER1 → LLM
ER2 → LLM
ER3 → LLM
ER4 → LLM
```

。

而是：

```text
ER1 → 自己的 Evidence
ER2 → 自己的 Evidence
ER3 → 自己的 Evidence

        ↓

组成一个 batch payload

        ↓

一次 Coverage LLM
```

所以：

> **Requirement-scoped Evidence ≠ Requirement-scoped LLM call。**

这样同时保证：

```text
证据不会串 Requirement
+
成本不会乘 5～6 倍
```

。

---

# 十五、第一轮 Coverage 后决定是否补检索

得到：

```text
ER1 SATISFIED
ER2 PARTIAL
ER3 MISSING
ER4 SATISFIED
```

之后：

```text
RetrievalController
```

只重点看：

```text
CORE Requirement
```

。

比如：

```text
ER2 CORE PARTIAL
ER3 CORE MISSING
```

那么才进入：

```text
Round 1
```

。

---

# 十六、第二轮检索也和 V2 有一个重要变化

以前第二轮 Query Rewrite / 补检索用来发现新关键词的材料来自：

```text
ContextBundle
```

问题还是一样：

```text
某条证据其实已经找到
↓
但没进入 Context
↓
第二轮 Planner 根本看不到它
```

。

V3：

```text
discovered_terms
```

来自：

```text
EvidenceWorkspace
```

。

所以第二轮可以利用：

> **第一轮真实找到的完整 Evidence。**

不是只利用被 ContextBuilder 留下的那一小部分。

---

# 十七、第二轮结束后再做一次 Coverage

流程：

```text
Round 0
↓
Workspace = E1 E2 E3 E4
↓
Coverage
↓
ER3 PARTIAL

Round 1
↓
新增 E5 E6
↓
Workspace = E1 E2 E3 E4 E5 E6
↓
Coverage again
```

这里第二轮 Coverage 能看到：

```text
Round 0 + Round 1
```

的累计证据。

不能只看 Round 1。

---

# 十八、为什么 `for_round()` 是“累计”语义

当前设计：

```text
for_round(0)
→ 第一轮证据

for_round(1)
→ 第一轮 + 第二轮证据
```

而不是：

```text
for_round(1)
→ 只有第二轮
```

。

因为第二轮 Coverage 判断的是：

> 经过两轮调查后，现在证据够不够？

自然应该看累计结果。

但是反过来：

```text
Round 0 Coverage
```

绝不能看到：

```text
Round 1
```

未来才找到的 Evidence。

这叫：

```text
不向前泄漏
```

。

---

# 十九、Coverage 完成后形成 EvidencePackage

最终得到：

```text
EvidencePackage
```

现在里面不仅有：

```text
ContextBundle
```

还会有：

```text
EvidenceWorkspace
EvidenceCatalog
Coverage
SearchHistory
RetrievalState
```

。

所以 V3 中：

```text
EvidencePackage
```

真正变成了：

> **检索阶段和回答阶段之间的稳定边界。**

---

# 二十、这里还有一个很重要的 V2 → V3 改动：RetrievalState

V2 很容易出现：

```text
ContextBundle empty
↓
EMPTY
```

。

但 V3 出现一个新情况：

```text
Workspace:
有 15 条 Evidence

ContextBundle:
因为预算等原因 0 条
```

这时候：

```text
EMPTY
```

就明显是错的。

所以现在 Teach 模式判断“有没有 Evidence”时，看：

```text
Workspace
```

而不是：

```text
Legacy ContextBundle
```

。

---

# 二十一、但是为了兼容 V2，系统没有把所有模式都强制切到 Workspace

这是一个非常好的兼容设计。

现在：

```text
legacy / explain
→ evidence_source = bundle

teach
→ evidence_source = workspace
```

。

也就是说：

```text
V2 explain
```

仍然保持旧行为，方便做：

```text
explain vs teach A/B
```

。

如果直接把 Explain 也改成 Workspace：

```text
V2 baseline
```

就被你顺手改掉了。

那后面根本没法公平比较。

---

# 二十二、所以 V2 和 V3 的根本差别可以总结成这张表

| 问题 | V2 | V3 |
|---|---|---|
| 完整 Evidence 是否长期保存 | ❌ | ✅ Workspace |
| Coverage 输入 | ContextBundle | WorkspaceCoverageView |
| Coverage 是否受 Answer Context 长度影响 | ✅ 会 | ❌ 基本解耦 |
| Evidence 身份 | `C1/C2`，依 Context 位置 | `E1/E2`，稳定身份 |
| 第二轮发现词来源 | 被截断 Context | 完整 Workspace |
| Answer 与 Retrieval 是否共享同一 Evidence 表示 | 基本共享 | 分离 |
| EMPTY 判断 | 主要看 Context | Teach 看 Workspace |
| Section 可以重新取 Evidence | ❌ | ✅ |
| 后续多 Context View | 很困难 | 天然支持 |

---

# 二十三、最重要的一点：为什么一定要先做 Workspace，再做 Teach

因为 Teach 后面要：

```text
Section 1
只看 E1 E3 E5

Section 2
只看 E6 E8

Section 3
只看 E2 E7
```

如果 V2 时代只有：

```text
一个被截断的 ContextBundle
```

那很多 Evidence 在回答开始之前已经彻底丢了。

根本无法做到：

```text
Section-specific retrieval view
```

。

所以：

```text
EvidenceWorkspace
```

其实是：

```text
ExplanationPlanner
Section View
Section Citation
Teaching Writer
```

这些 V3 能力的共同地基。

# 二十四、用一个完整例子串起来

还是：

> “详细解释项目为何要使用责任链校验”

### 第一步：EvidencePlanner

得到：

```text
ER1 证明项目存在责任链
ER2 找实际业务场景
ER3 找为什么采用
ER4 找节点顺序
ER5 找扩展机制
```

---

### 第二步：Round 0 Retrieval

找到：

```text
ER1 → E1 E2
ER2 → E3
ER3 → E4 E5
ER4 → E6
ER5 → E7
```

Workspace：

```text
E1 E2 E3 E4 E5 E6 E7
```

---

### 第三步：CoverageView

分别：

```text
ER1 View:
E1 E2

ER2 View:
E3

ER3 View:
E4 E5
...
```

---

### 第四步：Coverage

得到：

```text
ER1 SATISFIED
ER2 PARTIAL
ER3 SATISFIED
ER4 SATISFIED
ER5 PARTIAL
```

---

### 第五步：Round 1

只针对：

```text
ER2 / ER5
```

继续搜索。

找到：

```text
E8
E9
```

Workspace：

```text
E1 ... E9
```

。

---

### 第六步：再次 Coverage

可能变成：

```text
ER1 SATISFIED
ER2 SATISFIED
ER3 SATISFIED
ER4 SATISFIED
ER5 SATISFIED
```

。

---

### 第七步：冻结

```text
Workspace.freeze()
↓
EvidenceCatalog
```

之后不能再偷偷：

```text
register new evidence
```

。

检索阶段结束。

# 二十五、你可以用一句非常适合面试的话描述这次重构

> V2 的 Coverage 直接基于最终 ContextBundle，因此 Retrieval correctness 和 Prompt budget 耦合：证据可能已经被搜到，只是因为 Top-K 或字符预算没进入 Context，就被错误判为 Missing。V3 增加了 request-scoped EvidenceWorkspace，在任何有损筛选前保存完整检索结果，并通过 Requirement-scoped CoverageView 进行覆盖判断；Answer Context 则变成 Workspace 的一个有预算视图。这样“是否找到证据”和“这一轮 Prompt 能看到多少证据”被彻底分离，同时也为后续 Section-scoped Context 和稳定 Citation 提供了基础。

这一段基本就是 **EvidenceWorkspace + Coverage** 最核心的设计思想。
