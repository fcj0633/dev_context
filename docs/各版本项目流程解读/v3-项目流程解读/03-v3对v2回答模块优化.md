可以把 **V2 → 当前 V3 链路**理解成一次从“**把证据组织成回答**”升级到“**把证据组织成可理解、可约束、可审查的解释**”。

最核心的变化不是“多了几个 Prompt”，而是整个回答架构从：

```text
V2：
Evidence
→ 一个 Context
→ AnswerPlan
→ 一次生成
→ Reviewer
```

升级成：

```text
V3：
EvidenceWorkspace
→ Coverage
→ ExplanationPlan
→ Section View
→ 分节生成
→ Composer
→ Grounding
→ TeachingReviewer
→ 定向修订
```

你可以先记住一句话：

> **V2 重点解决“基于证据正确回答”；V3 进一步解决“如何围绕正确证据，把复杂问题真正讲懂”。**

---

# 一、先看 V2 的完整链路

V2，也就是现在的：

```bash
--answer-mode explain
```

大致是：

```text
用户问题
  ↓
EvidencePlanner
  ↓
SearchActionPlanner
  ↓
RetrievalController
  ↓
EvidencePool
  ↓
ContextBuilder
  ↓
ContextBundle
  ↓
Coverage
  ↓
EvidencePackage
  ↓
AnswerPlanner
  ↓
Grounded Draft
  ↓
AnswerReviewer
  ↓
最终回答
```

它已经不是普通 RAG。

V2 已经解决了很多问题：

```text
问题应该需要哪些证据？
证据是否充分？
哪些是代码证据？
哪些是文档证据？
是否存在历史文档与当前代码冲突？
回答应该组织成哪些章节？
引用是否合法？
```

所以 V3 并不是推翻 V2。

而是在 V2 的基础上继续解决：

> **“回答虽然正确，但为什么还是像源码说明书，而不像真正的教学解释？”**

你上传的 V2 `explain` 输出就很典型：已经会讲“为什么不是 if-else”“设计动因与实现取舍”“扩展方式与证据边界”，说明 V2 已经具备较强的 Grounded Explanation 能力。不同版本回答

---

# 二、V3 第一个重要优化：Evidence 和 Context 解耦

这是底层最重要的变化之一。

## V2

大体逻辑：

```text
检索结果
↓
EvidencePool
↓
Top-K
↓
ContextBuilder(max_chars)
↓
ContextBundle
↓
Coverage
↓
Answer
```

这里存在一个问题：

> Coverage 和 Answer 都依赖同一个已经被裁剪过的 `ContextBundle`。

假设系统实际上找到：

```text
ER1 → A
ER2 → B
ER3 → C
ER4 → D
```

但 Context 只能装：

```text
A
B
C
```

那么：

```text
D
```

虽然已经检索到了，

Coverage 却可能认为：

```text
ER4 MISSING
```

---

# 三、V3 增加 EvidenceWorkspace

现在：

```text
检索
↓
EvidencePool
↓
EvidenceWorkspace
     │
     ├→ Coverage
     │
     └→ 各种 Prompt View
```

也就是说：

```text
EvidenceWorkspace
=
这次请求实际找到的完整证据集
```

而：

```text
Context View
=
某一次 LLM 调用允许看到的证据子集
```

于是：

```text
检索事实
≠
Prompt 容量
```

被真正分开。

这是一个架构级优化。

---

# 四、V2 和 V3 的 Coverage 也不同

V2 更接近：

```text
ContextBundle
↓
Coverage
```

V3：

```text
EvidenceWorkspace
↓
WorkspaceCoverageView
↓
Coverage
```

所以 V3 判断的是：

> “我们到底找到证据了吗？”

而不是：

> “这次回答 Prompt 里有没有装进去？”

这使 Coverage 更真实。

---

# 五、第二个优化：Citation 从“位置”升级成“身份”

V2 Context Citation 主要是：

```text
C1
C2
C3
```

它表示：

> 当前 Context 中第几个 chunk。

所以同一 Chunk：

```text
Context A → C1
Context B → C7
```

身份不稳定。

---

V3 增加：

```text
CitationRegistry
```

变成：

```text
chunk 123 → E3
```

整个 request 生命周期中都保持：

```text
E3
```

于是：

```text
Planner
Section 1
Section 5
Reviewer
```

看到的还是同一个 Evidence。

这为后面的：

```text
Section-scoped Citation
```

打下基础。

---

# 六、第三个重大变化：AnswerPlanner → ExplanationPlanner

这是回答层最核心的一次升级。

V2 使用：

```text
AnswerPlanner
```

它更关注：

```text
回答目标是什么？
回答分几节？
哪些 Evidence 应该写进去？
哪些冲突需要说明？
```

可以理解成：

> **“怎么把证据组织成一篇合理答案。”**

---

V3 使用：

```text
ExplanationPlanner
```

它关注的是：

```text
用户最需要理解的核心模型是什么？

应该先讲问题还是先讲代码？

有没有容易产生的误解？

应该使用：
问题-解决？
机制解释？
失败场景？
取舍比较？

每一节承担什么认知作用？
```

也就是说：

> V2 做的是 **Answer Structure**。

> V3 做的是 **Teaching Structure**。

---

# 七、V3 新增 `core_mental_model`

这是 V2 没有真正强化的概念。

比如：

> 为什么使用责任链？

V2 可能组织为：

```text
责任链实现
调用场景
设计原因
扩展机制
```

这些都没错。

但 V3 会先试图得到：

```text
core_mental_model
```

比如：

> 责任链的价值不是“能够校验”，而是把持续增长、具有顺序和不同执行成本的校验规则，从稳定主流程中拆出去。

然后后面的：

```text
mark
order
Handler
Spring 收集
提前失败
```

全部围绕这个模型解释。

于是回答从：

```text
一组正确事实
```

升级成：

```text
围绕一个核心概念组织的知识结构
```

。

---

# 八、第四个优化：Evidence Requirement 不再直接变成文章章节

V2 已经比很早版本强很多。

但整体上还是比较容易出现：

```text
ER1
↓
Section 1

ER2
↓
Section 2

ER3
↓
Section 3
```

回答结构和调查结构距离较近。

---

V3 明确区分：

```text
Investigation Order
```

和：

```text
Explanation Order
```

比如检索：

```text
ER1 找代码结构
ER2 找业务入口
ER3 找设计原因
ER4 找排序机制
```

但最终讲解可能是：

```text
① 为什么出现这个问题
② 核心心智模型
③ 责任链如何解决
④ 项目具体怎么实现
⑤ 为什么顺序重要
⑥ 它的边界和代价
```

这明显更符合人的理解顺序。

---

# 九、第五个优化：增加 Section Type

V2 的章节更多是：

```text
标题 + 内容目标
```

V3 给每节增加了明确的认知类型：

```text
PROBLEM_SETUP
MENTAL_MODEL
EXECUTION_FLOW
MECHANISM
DESIGN_REASON
COMPARISON
FAILURE_SCENARIO
TRADEOFF
BOUNDARY
MISCONCEPTION
SUMMARY
...
```

然后不同 Section Type 使用不同写法。

例如：

```text
FAILURE_SCENARIO
```

要求：

```text
正常状态
→ 故障
→ 状态怎么变化
→ 如何恢复
```

而：

```text
TRADEOFF
```

要求：

```text
方案 A
→ 方案 B
→ 为什么选现在方案
→ 付出了什么代价
```

所以 V3 不再只是：

> “每节都详细解释。”

而是：

> **每种章节承担不同的教学任务。**

---

# 十、第六个优化：引入 Claim 语义分类

V2 的核心约束大致还是：

```text
有 Citation
→ 可以说
```

虽然已经有 Reviewer 和 Evidence Conflict，但对“证据之外能不能解释”比较保守。

---

V3 显式区分：

```text
PROJECT_FACT
PROJECT_INFERENCE
GENERAL_CONCEPT
ILLUSTRATIVE_EXAMPLE
```

这非常重要。

### PROJECT_FACT

```text
本项目代码确实这样做
```

必须 Evidence。

### PROJECT_INFERENCE

```text
从项目代码可以推导出……
```

允许推理，但必须明确是推导。

### GENERAL_CONCEPT

```text
通用工程知识
```

可以帮助理解，但不能冒充项目事实。

### ILLUSTRATIVE_EXAMPLE

```text
假设 / 示例
```

可以自由教学，但必须标记是假设。

---

# 十一、这个优化解决了 V2 的一个矛盾

V2 很容易陷入：

```text
为了不 hallucinate
↓
严格要求只根据 Context
↓
模型越来越像“源码复述器”
```

而 V3 改成：

```text
不是禁止证据之外的任何内容

而是：
证据之外的内容必须说明
“它是什么性质”
```

于是允许：

```text
项目事实
+
合理推导
+
通用原理
+
假设案例
```

共同组成真正的解释。

这是 V3 教学能力提升的重要来源。

---

# 十二、第七个优化：全文生成 → 分节生成

V2：

```text
AnswerPlan
+
整个 ContextBundle
↓
一次 Grounded Draft
```

复杂问题仍然主要是一轮生成。

---

V3 对复杂问题：

```text
ExplanationPlan
↓
S1
S2
S3
S4
...
```

分别执行：

```text
Section Evidence View
↓
TeachingWriter
↓
DraftSection
```

例如：

```text
S1 只看 E1 E3

S2 只看 E2 E4

S3 只看 E5 E8
```

所以：

> 模型写 S2 时，不需要处理整个 Repository Evidence。

---

# 十三、这样做的三个收益

## 1. 降低 Context 噪声

不相关 Evidence 不进入当前 Section。

## 2. 更容易维持章节目标

Writer 这一轮只负责：

```text
“为什么 order 很重要”
```

而不是同时考虑：

```text
8 个章节
20 个 Evidence
```

。

## 3. Citation 约束变强

这一节只能引用：

```text
它绑定的 E ID
```

。

---

# 十四、第八个优化：从全文 Citation 合法升级为 Section Citation 合法

V2：

```text
只要 C3 存在于整个 Context
```

基本上就可以引用。

---

V3：

假设：

```text
S2 allowed:
E2 E4 E7
```

模型写：

```text
[E9]
```

即使：

```text
E9
```

存在于整个 Workspace，

也被认为：

```text
invalid_citation
```

。

这说明 V3 从：

```text
“Citation 存在吗？”
```

升级成：

```text
“这个 Citation 有资格支撑这一节吗？”
```

。

Grounding 粒度明显更细。

---

# 十五、第九个优化：增加 Composer

V2 通常：

```text
一次生成整篇
```

所以天然有全文连贯性。

---

V3 分节生成后出现新问题：

```text
每一节单独都很好
↓
但拼起来可能很生硬
```

所以增加：

```text
SectionComposer
```

负责：

```text
章节衔接
术语统一
删除重复
改善开头结尾
```

但禁止新增事实。

也就是说：

```text
Writer
=
内容生产

Composer
=
全文编辑
```

。

这是 V3 为 Multi-pass 引入的配套机制。

---

# 十六、第十个优化：Reviewer 从“全文重写”转向“问题定位 + 定向修订”

V2 Reviewer 更接近：

```text
Draft
↓
Review
↓
返回 final_answer
```

也就是说 Reviewer 有较大的全文改写能力。

---

V3 的 TeachingReviewer：

```text
S1 OK
S2 OK
S3 有问题
S4 OK
```

返回：

```text
revision_required = ["S3"]
```

然后：

```text
只重新生成 S3
```

。

这样避免：

> 为了修 S3，把原本正确的 S1/S2/S4 又改坏。

这个是很明显的稳定性优化。

---

# 十七、第十一个优化：增加确定性 Grounding 层

V2 主要依赖 LLM Reviewer 做语义审查。

V3 在 Reviewer 前增加：

```text
Deterministic Grounding
```

直接用程序检查：

```text
PROJECT_FACT 没证据

conditional 没写成条件句

example 没标“假设”

UNVERIFIED 却写成确定事实
```

。

这些错误不需要再调用 LLM。

因此：

```text
确定性规则
负责硬约束

LLM Reviewer
负责软语义
```

。

这样比全部交给 LLM 更可靠。

---

# 十八、第十二个优化：Reviewer 不再只检查正确性，还检查“教学质量”

V2 Reviewer 更关注：

```text
unsupported claim
citation
overclaim
conflict
```

。

V3 TeachingReviewer 又增加：

```text
MISSING_MENTAL_MODEL

MISSING_WHY

POOR_SCAFFOLDING

ABRUPT_TRANSITION

UNHELPFUL_DETAIL

GENERAL_KNOWLEDGE_AS_PROJECT_FACT

FACT_INFERENCE_CONFUSION
```

也就是说质量标准从：

> **“回答有没有错？”**

升级成：

> **“回答有没有错，而且用户能不能真正理解？”**

---

# 十九、第十三个优化：固定字符预算 → Model-aware Token Budget

V2 很多地方还是：

```text
8000 chars
16000 chars
28000 chars
```

这样的字符预算。

问题是：

```text
28000 中文字符
```

和：

```text
28000 英文字符
```

消耗 Token 完全不同。

---

V3 增加：

```text
ModelCapabilities

TokenBudgetPolicy

TokenEstimator
```

大体：

```text
Model Context Window
-
Fixed Prompt
-
Output Reserve
-
Safety Margin
=
Evidence Budget
```

然后再决定 Section View 能装多少。

这比固定字符预算更接近真实模型约束。

---

# 二十、第十四个优化：回答长度策略改变

V2 `detailed` 有很明显的：

```text
2200–5000 chars
```

目标。

这也导致复杂问题有时候：

> 证据很多，但为了卡长度压缩掉了关键解释。

---

V3 特别是：

```text
deep
```

不再设旧的固定字符上限。

回答长度主要由：

```text
ExplanationPlan complexity
+
section count
+
ModelCapabilities
```

决定。

所以余票桶曾实际生成：

```text
9K
18K
18K+
```

字符。

目标从：

```text
“必须落在 5000 内”
```

改成：

```text
“复杂度决定需要多少内容”
```

。

---

# 二十一、第十五个优化：Trace 更完整

V2 Trace 主要关注：

```text
Evidence Plan
Search
Coverage
Answer Plan
Review
```

。

V3 又增加：

```text
Explanation Strategy

Core Mental Model

Workspace Evidence Count

Bound Evidence Count

Per-section View Size

Section Drafts

Section Citation

Section Confidence

Revision Trace

Output Budget
```

。

所以以后 Debug 时可以直接回答：

> 为什么这次答案这么长？

> 为什么只生成三节？

> S4 用了哪些 Evidence？

> Reviewer 到底要求改了哪一节？

可观测性明显更强。

# 二十二、用同一个问题看差距最清楚

假设用户问：

> 为什么项目使用责任链？

---

## V2 的思路

```text
Evidence：
找到责任链代码
找到设计文档
找到业务场景

↓
AnswerPlanner：

直接回答
为什么不是 if-else
代码如何实现
应用场景
设计取舍
证据边界

↓
一次 Grounded Draft
↓
Reviewer
```

已经很好。

---

## V3 的思路

```text
EvidenceWorkspace
↓
Coverage

↓
ExplanationPlanner：

用户真正应该理解：

“责任链不是为了能校验，
而是为了解决规则持续增长、
有顺序、有成本差异的问题。”

↓
设计认知顺序：

问题是什么
↓
核心模型
↓
项目机制
↓
顺序为什么重要
↓
扩展为什么容易
↓
代价和边界

↓
每节绑定 Evidence

↓
每节单独生成

↓
Composer

↓
Grounding

↓
TeachingReviewer

↓
只修改有问题章节
```

V3 多出的其实不是：

```text
更多内容
```

而是：

```text
更清晰的认知控制
+
更细的 Evidence 控制
+
更稳的质量控制
```

。

# 二十三、可以总结成 5 个核心升级

如果面试时不能讲这么长，可以直接说：

### 1. Evidence 层

```text
V2：
Evidence → Context

V3：
Evidence → Workspace → 多种 View
```

解决：

> Evidence 和 Prompt Budget 耦合。

---

### 2. Planning 层

```text
V2：
AnswerPlanner
“答案怎么组织？”

V3：
ExplanationPlanner
“用户怎么才能理解？”
```

增加：

```text
mental model
strategy
misconception
section type
claim type
```

---

### 3. Generation 层

```text
V2：
全文一次生成

V3：
Section-scoped Multi-pass
```

解决：

```text
复杂问题上下文过大
章节目标模糊
Citation 粒度过粗
```

---

### 4. Grounding 层

```text
V2：
全文 Citation

V3：
Workspace Identity
→ Section Evidence Allowlist
→ Claim semantics
→ deterministic grounding
```

Grounding 更细。

---

### 5. Review 层

```text
V2：
Reviewer 可以修改整篇

V3：
Reviewer 定位问题
→ 只重写错误 Section
```

质量控制更稳定。

## 最核心的结论

V2 已经解决了：

> **“不要让模型脱离项目证据随便回答。”**

而 V3 进一步解决：

> **“即使证据正确，也不能只是把源码事实堆给用户；系统需要主动建立心智模型、选择解释顺序、区分事实与推导、按章节隔离证据，并对教学效果做质量控制。”**

所以 V3 本质不是简单的 **Answer V2 + 更多 Prompt**，而是把回答阶段从：

```text
Grounded Text Generation
```

升级成：

```text
Grounded Explanation Pipeline
```

。
