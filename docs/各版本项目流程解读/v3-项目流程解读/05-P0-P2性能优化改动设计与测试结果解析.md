# V3 P0–P2 性能优化：改动设计与测试结果解析

本文解释 V3 回答链路在 P0、P1、P2 三个阶段做了什么、为什么这样设计、代码怎样保证正确性，以及真实性能和质量测试最终说明了什么。

它不是单纯的测试数字汇总，而是要回答下面几个更重要的问题：

1. 为什么性能优化不能直接从“开线程并发写章节”开始？
2. 为什么章节数量必须由程序约束，不能继续交给 Prompt 自由决定？
3. 为什么 Locate 问题只能绑定“定位 Requirement”的证据？
4. 为什么 `TeachingWriter.last_client` 在串行模式可用，在并发模式却会成为竞态源？
5. 为什么并发后 `LLM work` 可以大于真实 wall-clock，而且这反而是正确结果？
6. 为什么验收报告最初没有切默认值，而当前实现又决定默认启用新策略？

先给最终判断：

> **P0–P2 已经把回答链路从“难以准确测量、章节数量不稳定、Section 串行生成”推进到了“Trace 可解释、章节数有程序约束、Section 与 Revision 可安全并行”的状态。**
>
> 但这次优化不是“所有门禁都通过”。`locate-02` 仍高于 20 秒，L2 小样本的 teach 胜或平率只有 50%。验收结束时因此没有自动提升默认值；随后根据明确的发布决定，当前实现已默认启用 `deterministic / concurrency 3`，同时保留 `legacy / concurrency 1` 作为回归和调试退路。

# 一、优化前的问题不是一个慢函数，而是一条被放大的串行链路

原始性能基线已经证明，用户感觉到的 3～5 分钟并不是偶发网络抖动，而是回答架构本身造成的。

旧链路可以简化成：

```text
用户问题
  ↓
EvidencePlanner
  ↓
SearchActionPlanner
  ↓
Retrieval
  ↓
CoverageChecker
  ↓
ExplanationPlanner
  ↓
Section 1 Writer
  ↓
Section 2 Writer
  ↓
Section 3 Writer
  ↓
……
  ↓
Composer
  ↓
Reviewer
  ↓
Revision 1
  ↓
Revision 2
```

这里有三个相互放大的问题。

第一，ExplanationPlanner 生成的 Section 数不稳定。同一道题可能出现 3、8、11 节。Section 一多，后面的 Writer、Composer、Reviewer 和 Revision 都一起变重。

第二，所有 Section 顺序执行。即使五个章节彼此没有依赖，也要等待前一个章节写完才能开始下一个。

第三，原 Trace 更适合串行流程。它习惯在调用结束后 append 记录，或者通过“最后一个 client / 最后一条调用”读取 usage。并发后，后完成的调用不一定是后开始的调用，这些假设会立刻失效。

所以正确的优化顺序不是：

```text
先开线程池 → 再看是否变快
```

而是：

```text
P0：先让测量系统支持并发
  ↓
P1：再把任务规模变成确定性约束
  ↓
P2：最后并行真正相互独立的 Section / Revision
```

这也是本轮设计最核心的工程顺序。

# 二、P0 先解决“并发以后还能不能相信 Trace”

## 1. 为什么旧的 append-after-call 模式不够

串行模式下，可以在 LLM 返回后追加一条记录：

```text
调用 A 完成 → append A
调用 B 完成 → append B
```

这时列表顺序大致等于请求顺序。

并发模式下可能变成：

```text
0ms   A 开始
2ms   B 开始
5ms   C 开始
20ms  B 完成
35ms  C 完成
60ms  A 完成
```

如果 call ID 通过 `len(calls) + 1` 在完成时生成，那么 ID 表示的是完成顺序，不是请求身份。更严重的是，如果 Planner A 被业务校验丢弃，而 B 恰好最后完成，`mark_last_call_wasted()` 可能把 wasted 标到 B 上。

P0 因此把调用生命周期改成：

```text
begin_llm_call()
  ├── 在锁内原子分配 call_id
  ├── 记录 started_offset_ms
  └── 把 call_id 放入当前 Context

Provider request

finish_llm_call(call_id)
  ├── 更新同一条记录
  ├── 写 ended_offset_ms
  ├── 写 usage / finish_reason / error
  └── 保留开始时的 stage / group / attempt
```

call ID 从“列表位置”变成了“请求身份”。

## 2. Recorder 为什么必须加锁

Section Worker 会共享同一个请求级 `PerfRecorder`。共享本身没有问题，问题是写操作必须原子化。

因此下列操作全部进入锁保护：

- 分配 call ID；
- 更新指定 LLM call；
- 标记指定 call wasted；
- 追加 SectionExecution；
- 追加 Embedding 与 Retrieval action；
- 读取需要一致视图的统计集合。

自动化测试用 100 个并发伪调用验证：

```text
call_id = 1...100
重复 ID = 0
丢失记录 = 0
覆盖记录 = 0
```

## 3. 为什么使用 ContextVar

仅有锁还不够。锁解决“同时写”的问题，ContextVar 解决“这条记录属于谁”的问题。

每个 task 需要自己的：

```text
current recorder
current stage
current call id
parallel group id
attempt index
```

提交线程任务时使用：

```python
ctx = contextvars.copy_context()
executor.submit(ctx.run, task, ...)
```

而且必须每个任务单独 `copy_context()`。

原因是同一个 Context 实例不能同时被多个线程进入。如果只在 fan-out 前复制一次，然后让所有 Future 复用它，不仅会串状态，还可能直接触发运行时错误。

## 4. wasted 必须精确绑定 call ID

本轮废弃了并发路径中的“标记最后调用”语义，改为：

```python
mark_call_wasted(call_id, reason)
```

典型场景是 Planner：

```text
Planner LLM 调用成功返回
  ↓
JSON / section count / evidence binding 验证失败
  ↓
这次调用虽然 Provider 成功，但业务上没有产出
  ↓
精确标记 Planner call wasted
  ↓
走确定性 fallback，不再调用一次 Planner
```

这让“调用失败”和“调用成功但结果被丢弃”成为两个不同概念。

前者用于分析 Provider 稳定性，后者用于分析架构浪费。

# 三、reasoning token 为什么必须是 optional

不同 Provider、不同模型版本，甚至同一个 Provider 的不同响应，都不保证一定返回：

```json
completion_tokens_details.reasoning_tokens
```

如果代码假设这个字段必然存在，那么观测功能反而会让正常回答失败。

本轮固定了如下兼容语义：

```text
detail 存在
+ reasoning_tokens 是非负整数
+ reasoning_tokens <= completion_tokens
    ↓
reasoning_tokens = Provider 真值
visible_output_tokens = completion_tokens - reasoning_tokens
token_detail_available = true

否则
    ↓
reasoning_tokens = null
visible_output_tokens = completion_tokens
token_detail_available = false
```

这里最重要的是两个“不改变”。

第一，`output_tokens` 仍表示 Provider 返回的 completion total。旧字段语义没有被偷偷改成 visible tokens。

第二，token 安全预算继续使用 completion total。visible tokens 只用于解释“正文与推理分别消耗了多少”，不能拿它替代 Provider 真正的输出上限。

测试覆盖了：

- detail 正常返回；
- 整个 `completion_tokens_details` 缺失；
- detail 为 null；
- reasoning 字段缺失；
- reasoning 类型错误；
- reasoning 大于 completion total；
- 失败调用没有 usage。

这些情况都不会让原本成功的正文请求失败。

真实结果也验证了这套兼容设计：

| 数据集 | detail 可用 | detail 不可用 |
|---|---:|---:|
| 旧 27 样本 | 0 | 315 |
| 本轮 P0–P2 样本 | 224 | 0 |

旧数据没有被补算或伪造；新数据则可以开始真正区分 reasoning 与 visible output。

# 四、P1 的核心不是改 Prompt，而是把回答规模变成程序决策

## 1. DepthPolicy 先决定问题需要多深

确定性策略的优先级是：

```text
显式 --depth
  > Locate 提示
  > 详细提示
  > 默认 standard
```

其中：

```text
“在哪、哪个类、哪个文件、哪里、入口、位置”
    → brief

“详细、深入、完整、全面、逐步、底层、源码、调用链、原理、设计取舍”
    → detailed

其他普通解释问题
    → standard
```

`deep` 不会被关键词自动选中，只允许用户显式指定。这样可以避免模型或规则在没有用户授权时进入最昂贵的 7～8 节路径。

Depth 对应的章节预算是固定的：

| Depth | preferred | hard max |
|---|---:|---:|
| brief | 1 | 2 |
| standard | 3 | 4 |
| detailed | 5 | 6 |
| deep | 7 | 8 |

`preferred` 是证据足够时应该输出的数量，`hard max` 是任何情况下都不能越过的上限。

## 2. 为什么 preferred 不能只写进 Prompt

如果只是告诉模型“最好生成 5 节”，模型仍可能输出：

```text
3 节：它觉得已经讲完
8 节：它觉得还可以继续展开
11 节：它把 Requirement、失败情形和总结继续拆分
```

这会让 Section 数继续成为随机变量。

P1 改成先由程序计算 `SectionBudgetDecision`：

```text
遍历 EvidencePlan.requirements
  ↓
Coverage 是 SATISFIED 或 PARTIAL？
  ↓
这个 Requirement 至少有一个 Evidence？
  ↓
Evidence 有合法 citation label？
  ↓
是 → evidence-backed Requirement
否 → unsupported Requirement
```

然后计算：

```text
evidence_capacity = 有证据 Requirement 数量

evidence_capacity == 0
    → target_sections = 0

evidence_capacity > 0
    → target_sections = min(preferred, hard_max, evidence_capacity)
```

例如，一个 detailed 问题期望 5 节，但只有 4 个 Requirement 真正有证据：

```text
preferred = 5
hard_max = 6
evidence_capacity = 4
target_sections = 4

gap_code = INSUFFICIENT_EVIDENCE_REQUIREMENTS
gap_reason = 只有 4 个 Requirement 有可用证据，低于 detailed 期望的 5 节
```

这个 gap reason 是程序根据 EvidencePackage 生成的，不信任模型自己解释“为什么少写了一节”。

## 3. 为什么不能为了满足数量制造空章节

“恰好输出 target 数量”如果没有配套验证，很容易变成另一种问题：模型通过同义标题、空 Summary、重复 key points 来凑数量。

所以每个 Section 还要经过以下验证：

- title、teaching_goal、key_points 非空；
- title 唯一；
- normalized teaching_goal 唯一；
- key_points 集合不能与另一节完全相同；
- 至少绑定一个真实 citation；
- citation 必须反向解析到 evidence-backed Requirement；
- 全部 Section 合计至少覆盖 target 个不同 Requirement；
- `(section_type, requirement_ids, normalized key_points)` fingerprint 不能重复；
- `PROJECT_FACT` 只能引用该 Section 自己绑定的 citation 子集。

这形成了一个双重约束：

```text
数量必须达到 target
        +
每个章节必须有独立、可证据支撑的教学意图
```

## 4. Planner 不合格时为什么不重试

Planner 一次调用可能消耗十几到几十秒。如果输出数量错误，再调用一次相同 Planner，不仅增加串行深度，也不保证第二次一定正确。

本轮策略是：

```text
Planner 输出
  ↓
严格验证
  ├── 通过 → 使用模型计划
  └── 失败 → 标记原 call wasted
              ↓
              使用确定性 fallback
```

fallback 仍然必须满足同一个 target 和 hard max，并且每一节绑定不同的 evidence-backed Requirement。

它不是“随便生成一个保底回答”，而是“用确定性算法实现模型本应满足的约束”。

## 5. 零证据为什么直接短路

如果 `evidence_capacity == 0`，系统不会调用 ExplanationPlanner，也不会调用 Writer。

原因很简单：

```text
没有 Evidence
  ↓
没有任何项目事实可以安全写
  ↓
生成一个“无证据章节”没有业务价值
```

因此它直接沿用无证据回答语义，而不是为了流程完整制造占位章节。

# 五、Locate Fast Path 为什么必须在 Requirement 级别选证据

Locate 问题的目标通常非常窄：

```text
“用户注册入口在哪个类？”
“订单关闭的消费者在哪里？”
```

一个完整 EvidencePackage 可能同时包含：

```text
ER1：入口类和方法
ER2：为什么这样设计
ER3：异常补偿流程
ER4：历史文档中的替代方案
```

如果 Locate fast path 直接使用 `workspace.all()`，一个只有一节的定位回答会拿到整个 EvidencePackage。这样虽然 Citation 可能仍合法，但回答会开始讲设计原因、异常流程甚至历史方案，失去 fast path 的意义。

P1 因此先选择定位 Requirement：

```text
1. target / success criteria 命中定位词
2. CORE 优先于 SUPPORTING
3. CODE 优先于 ANY
4. SATISFIED 优先于 PARTIAL
5. EvidencePlan 原顺序作为最终 tie-break
```

没有直接命中时，才尝试：

```text
CORE
+ CODE / ANY
+ 与原 query 共享类名、方法名、英文标识符或连续中文关键词
```

仍然找不到，就禁用 deterministic Locate fast path，回到普通 Planner。

注意这里的原则：

> **宁可不用 fast path，也不能拿一个无关 CORE Requirement 充当定位证据。**

最终绑定是：

```text
workspace.for_requirements(selected_location_requirement_ids)
```

而不是：

```text
workspace.all()
```

自动化测试专门构造了“定位 + 设计原因 + 异常流程”同时存在的 EvidencePackage，并证明 Locate Section 最终只获得定位 Requirement 的 Evidence。

# 六、Planner schema slimming 为什么既减时延，也提高稳定性

旧 Planner 不只是决定教学结构，还要让模型重复输出很多程序已经知道的信息：

```text
claim type
confidence
depends_on
teaching devices
evidence state
gap
conflict
```

这些字段越多，模型需要生成的 token 越多，JSON 出错面也越大。

新的 slim schema 只让模型决定真正需要语义判断的内容：

```json
{
  "answer_goal": "...",
  "direct_answer": "...",
  "core_mental_model": "...",
  "primary_strategy": "...",
  "sections": [{
    "id": "S1",
    "title": "...",
    "section_type": "...",
    "teaching_goal": "...",
    "key_points": ["..."],
    "evidence_labels": ["E1"],
    "target_tokens": 400
  }],
  "answer_depth": "detailed"
}
```

其余字段由程序从 EvidencePackage 派生：

```text
Citation → Requirement
Requirement Coverage → confidence / evidence_state
Section 顺序 → depends_on
项目证据存在 → PROJECT_FACT
EvidencePackage unresolved → unresolved_gaps
```

旧完整 schema 仍然可以解析，因此这是兼容式收缩，不是一次破坏性切换。

真实测试结果：

| 版本 | Planner 三次 | 平均 | fallback |
|---|---:|---:|---:|
| slimming 前 | 17.13 / 28.42 / 29.77s | 25.11s | 1/3 |
| slimming 后 | 9.39 / 12.59 / 7.58s | 9.85s | 0/3 |

平均耗时下降 60.8%，同时 fallback 从 1 次降为 0。

这说明 schema slimming 的收益不只是“少输出一些 token”，还包括：

- 更少的字段组合错误；
- 更少的 enum 错误；
- 更少的 JSON 验证失败；
- 更低的 fallback 概率；
- 更稳定的 Section 数。

# 七、Writer Output Budget 为什么要区分 reasoning 和 visible output

模型的 completion total 由两部分组成：

```text
completion_tokens
  = reasoning_tokens
  + visible_output_tokens
```

如果只按“希望正文 500 token”设置 `max_tokens=500`，高 reasoning 模型可能还没有输出完整正文就达到 Provider 上限。

本轮预算公式是：

```text
section_max_tokens = round_up_to_256(
    max(4096, visible_target × 1.5 + reasoning_reserve)
)
```

其中：

```text
visible_target = section.target_tokens
              or depth 默认 section tokens
```

第一轮真实测试暴露出一个很有价值的问题：原先 4,096 的 reasoning reserve 略低，出现了 5 次 draft length 和 1 次 revision length。

从 64 个真实 high-effort Writer 调用中计算：

```text
reasoning-token nearest-rank p95 = 4,135
向上取 256 整数倍 = 4,352
```

修正后：

- reserve 改为 4,352；
- `target_tokens` 真正传入 Writer Prompt；
- Prompt 明确 target 是不含 reasoning 的可见正文软目标；
- 实际 Provider `max_tokens` 被 Trace 记录。

复测 17 个 section/revision Writer 调用：

```text
normal stop = 17
length = 0
failed section = 0
```

这说明预算不再只存在于配置或计算结果里，而是真正传到了 Provider。

# 八、P2 并发前最关键的改动：Writer 不能再通过 last_client 发请求

## 1. 旧写法为什么并发不安全

旧式写法相当于：

```python
self.last_client = factory()
self.last_client.generate(...)
```

两个线程交叉时可能发生：

```text
Thread A：self.last_client = client_A
Thread B：self.last_client = client_B
Thread A：self.last_client.generate(...)
```

Thread A 最终可能使用 `client_B` 发请求。

即使 generate 本身没有串，后续通过：

```text
writer.last_client.last_usage
```

读取 usage，也可能读到另一个 Section 的结果。

## 2. 新写法如何隔离

现在 `write()` 和 `write_section()` 都使用局部变量：

```python
client = self._client(max_output_tokens)
response = client.generate(...)
```

并发 Worker 固定：

```python
remember_last_client=False
```

这意味着：

- Worker 不写 `writer.last_client`；
- Worker 不读 `writer.last_client`；
- usage 从当前 task 的精确 LLM call trace 获取；
- call ID 从当前 Context 获取；
- finish reason 和错误属于当前 task；
- `last_client` 只为旧串行测试和调试保留。

自动化测试甚至把 `writer.last_client` 人为设置成一个调用就抛异常的 sentinel client。并发流程仍然正常完成，证明实际请求没有经过它。

这是 C1 的真正含义：

> **并发安全不是给共享字段加锁，而是让共享字段退出请求与结果传递路径。**

# 九、Section Generation 怎样实现有界并行

新的 Multi-pass 流程分成三个阶段。

## 1. 主线程先准备任务

主线程按 ExplanationPlan 顺序：

```text
S1 → 构建 Section Context
S2 → 构建 Section Context
S3 → 构建 Section Context
S4 → 构建 Section Context
S5 → 构建 Section Context
```

如果某一节没有 Evidence，它会在提交前被标记为 `SECTION_WITHOUT_EVIDENCE`，不会创建一个必然失败的 LLM task。

## 2. Worker 并行生成

```text
ThreadPoolExecutor(max_workers=N)

Wave 1：S1、S2、S3
Wave 2：S4、S5
```

每个 Worker：

```text
独立 Context 副本
独立 LLM client
独立 call ID
独立 attempt index
共享但加锁的 Recorder
```

Worker 不直接 append 到 `drafts`、`issues`、`section_traces`、`view_sizes`。它只返回 `_SectionTaskResult`。

## 3. 主线程有序 fan-in

Future 可能按：

```text
S2 → S1 → S3 → S5 → S4
```

完成，但主线程最终按 `section_index` 排序：

```text
S1 → S2 → S3 → S4 → S5
```

所以并发只影响完成时间，不影响文章顺序。

这也是为什么 `_SectionTaskResult` 必须包含 `section_index`，不能只靠 Future 返回顺序。

# 十、Retry、partial answer 与 Revision 的失败语义

## 1. 哪些错误可以重试

只对短暂基础设施问题重试一次：

- timeout；
- HTTP 429；
- HTTP 5xx；
- curl / 连接中断。

以下错误不重试：

- Section 没有 Evidence；
- Citation 验证失败；
- 响应结构或业务验证错误；
- 配置错误；
- Section Budget / hard max 错误。

原因是这些错误不会因为“再请求一次”自动消失。盲目重试只会增加 wasted latency。

## 2. 一个 Section 失败时为什么不取消全部

五节中一节失败，不代表另外四节没有价值。

因此：

```text
至少一节成功
  ↓
保留成功 Draft
  ↓
确定性拼接 partial answer
  ↓
记录 partial_answer=true
  ↓
记录 failed_section_ids
  ↓
跳过 Reviewer / Revision
```

跳过 Reviewer 的原因是：当前回答已经不完整，再让 Reviewer 扩大调用量不能恢复缺失的原始 Draft，反而会继续增加成本。

如果全部 Section 都失败，才进入无可用 Draft 的 fallback。

## 3. Revision 为什么也可以并行

Reviewer 返回的是：

```text
revision_required = [S2, S4]
```

S2 与 S4 的 Revision Context 彼此独立，因此可以使用同一个有界执行器并行执行。

Revision 失败时不会删除原 Draft，而是：

```text
S2 revision 成功 → 替换 S2
S4 revision 失败 → 保留原 S4
```

而且 Revision 的 LLM stage 明确记录为：

```text
teaching_revision
```

不再错误地落到 `teaching_draft`。

# 十一、并发后应该怎样理解新的性能指标

## 1. work 与 wall 不是一回事

假设三个 Section 各运行 20 秒，并行执行：

```text
Section work = 20 + 20 + 20 = 60s
Section wall ≈ 20s
```

所以并发情况下：

```text
llm_work_ms > request wall-clock
```

完全合法。

新的报告区分：

- `llm_work_ms`：所有 LLM duration 之和；
- `llm_active_wall_ms`：所有 LLM 区间并集；
- `llm_wall_span_ms`：第一次开始到最后一次结束的跨度；
- `parallelism_ratio`：work / active wall；
- `peak_llm_concurrency`：同时活跃的最大 LLM 数；
- `section_work_ms`：Section 耗时总和；
- `section_wall_ms`：Section 区间并集；
- `logical_sequential_llm_depth`：逻辑依赖深度；
- `scheduled_llm_waves`：受并发上限影响的实际波次。

同一时间点既有结束又有开始时，统计先处理结束事件，避免把瞬时交接误算成更高并发峰值。

## 2. 为什么还要区分 logical depth 和 waves

假设五个 Section 并发度为 3：

```text
逻辑上：五个 Section 属于同一个 fan-out 依赖层
调度上：需要两波才能执行完
```

因此：

```text
logical depth = 1 个并行层
scheduled waves = 2
```

如果其中一个 Section retry，一条分支多了一层逻辑依赖。把这两个指标分开，才能区分：

- 架构本身还有多少串行依赖；
- 当前 concurrency 配置造成了多少调度波次。

# 十四、为什么验收时没有自动切换，而当前实现选择默认启用

默认切换不是只看“变快了多少”，还要同时通过稳定性和质量门禁。

当前没有通过的门禁有两个。

## 1. Locate 还没有全部达到 20 秒

`locate-02` p50 为 24.9 秒。虽然比旧值明显改善，但门禁是 20 秒，不是“比过去快”。

## 2. L2 盲评没有达到 90%

两个有效小样本：

```text
why-02  → teach 胜
flow-01 → explain 胜
```

teach 胜或平率：

```text
1 / 2 = 50%
```

低于目标 90%。

值得注意的是，质量失败不是 Citation 错误：

```text
新增 invalid citation = 0
zero-valid-citation = 0
未发现新增 must-not-claim 违规
```

`flow-01` 的教学评分甚至达到 4.714/5，但盲评仍选择 explain，原因是：

- teach 正文偏长；
- 历史材料占比过多，削弱当前实现主线；
- 对“已有测试能证明什么”回答不够直接；
- 结构完整，但没有在题目最关心的边界上快速收束。

这说明：

> **教学维度高，不等于最终回答一定更优。**

回答还必须控制材料选择、篇幅和问题贴合度。

按照原门禁，这些结果不足以“自动”提升默认值；这也是验收报告最初保留旧配置的原因。

在验收完成并明确接受上述残余风险后，当前发布决定将默认值切换为：

```text
EXPLANATION_DEPTH_POLICY=deterministic
TEACHING_SECTION_CONCURRENCY=3
```

旧串行路径没有删除。需要回归、调试或隔离并发问题时，可以显式回退：

```text
EXPLANATION_DEPTH_POLICY=legacy
TEACHING_SECTION_CONCURRENCY=1
```

因此要区分两个结论：

```text
测试结论：Locate 与 L2 仍有残余风险
发布结论：在风险已知且可回退的前提下，默认启用 P0–P2
```

默认启用不等于把失败门禁改写成通过；它只是一次显式的发布取舍。

# 十五、P2 以后新的瓶颈已经发生转移

优化前，最明显的瓶颈是 Section Writer 串行执行。

优化后，corrected detailed 样本中：

```text
Teaching draft：36.2～44.2s
Teaching review：34.8～71.1s
Teaching revision：触发时约 40～41s
```

Reviewer 已经能够超过 Draft，Revision 也可能再增加一整个 40 秒阶段。

所以新的主要矛盾变成：

```text
P2 之前：Section Writer 串行放大
P2 之后：Reviewer / Revision 成为主要尾延迟
```

另一个剩余问题是 Retrieval/Coverage 额外 round。它对复杂问题不是第一优先级，但会直接影响 Locate 的最低交互延迟。

下一阶段如果继续优化，合理顺序是：

```text
1. 收敛正文长度与历史材料选择
2. 优化 Reviewer / Revision 成本
3. 重新运行完整 L2
4. 获得授权后再处理 Locate 的 Retrieval Round 1
```

本轮没有越界修改 Composer 默认策略、Reviewer effort/token/timeout、Retrieval Round 1、pgvector、BM25、Fusion、Embedding cache 或默认模型。

# 十六、从工程设计角度，这次改动最值得记住什么

## 1. 并发优化的第一步是让状态不再共享

真正的并发安全不是“给 `last_client` 加锁”，而是让请求和结果根本不通过 `last_client`。

局部 client、任务级 Context、精确 call ID 和主线程 fan-in，四者共同构成并发边界。

## 2. 模型可以负责语义选择，但不能负责系统不变量

模型适合决定：

- 什么教学顺序更自然；
- 什么标题更易理解；
- 哪些 key points 应放在同一节。

程序必须决定：

- 允许几节；
- 最多几节；
- 证据不足时为什么少写；
- Citation 是否真实；
- Section 是否重复；
- PROJECT_FACT 是否越界引用。

这就是 Planner slim schema 和 Section Budget 的边界。

## 3. Fast Path 的关键是减少问题范围，不只是少调用一个模型

Locate 不调用 ExplanationPlanner 只是第一步。

如果仍然把整个 EvidencePackage 交给 Writer，回答范围并没有真正缩小。

Requirement 级证据选择才让 Fast Path 同时具备：

- 更少证据；
- 更短上下文；
- 更少章节；
- 更低幻觉面；
- 更明确的 Citation 责任。

## 4. 性能门禁和质量门禁必须独立

本轮性能目标多数通过，但质量门禁失败，所以没有切默认值。

这避免了一个常见错误：

```text
回答快了
  ≠
回答已经适合默认启用
```

# 十八、可以用一句面试级结论总结这次优化

> 我们没有直接把串行 Writer 改成线程池，而是先重构 Trace，使 call ID、usage、wasted 标记和并发区间都能被精确追踪；再把回答深度和 Section 数从 Prompt 建议升级为基于 Evidence Coverage 的程序约束；最后通过局部 LLM client、任务级 ContextVar、有界线程池和有序 fan-in 并行生成 Section 与 Revision。结果是 Planner 平均降到 9.85 秒，Detailed Draft p50 下降 69%～78%，总延迟下降 40%～72%，最大逻辑串行深度从 23 降到 11。验收时一个 Locate case 和 L2 盲评仍未达标；在明确记录这些风险并保留 `legacy / 1` 回退路径后，当前发布决定默认启用 `deterministic / 3`。

最重要的不是“加了并发”，而是：

```text
先让测量可信
再让任务规模确定
最后让独立任务并行
并且用质量门禁决定是否默认启用
```

这才是这次 P0–P2 改动的完整设计逻辑。
