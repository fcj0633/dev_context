好，这一步只讲：

> **第二轮补查：`PARTIAL/MISSING CORE → discovered_terms → follow-up SearchAction → 再检索`**

这是你当前检索链里最关键、也最值得优化的一段。

---

# 1. 第二轮从哪里开始？

上一阶段 CoverageChecker 已经得到类似：

```text
ER1 事务边界       → SATISFIED
ER2 并发控制       → SATISFIED
ER3 失败补偿       → PARTIAL
ER4 设计背景       → MISSING（SUPPORTING）
```

当前代码只挑：

```python
priority == "CORE"
and
state in {"PARTIAL", "MISSING"}
```

所以这里：

```text
ER3 → 进入第二轮

ER4 → 不进入
```

源码逻辑就是：

```python
followup_requirements = tuple(
    item
    for item in plan.requirements
    if item.priority == "CORE"
    and coverage_by_id[item.id].state
       in {"PARTIAL", "MISSING"}
)
```

所以第二轮不是：

> 把所有问题重新搜一次。

而是：

> **只补没有满足的核心证据。**

---

# 2. 第二轮和第一轮最大的区别是什么？

第一轮时系统只有：

```text
原始问题
+
EvidenceRequirement
```

例如：

```text
“购票失败如何补偿”
```

系统不知道项目里具体叫什么。

---

但是经过第一轮后，Context 中可能已经出现：

```text
PurchaseTicketServiceImpl
compensateTicketIfOrderFailed
createTicketOrder
PurchaseTicketTxService
```

所以第二轮多了一类非常重要的信息：

> **真实项目术语 / Symbol。**

当前系统会把这些内容提取出来，叫：

```python
discovered_terms
```

---

# 3. `discovered_terms` 从哪里来？

代码：

```python
_discovered_terms(
    bundle,
    followup_requirements
)
```

它遍历当前 `ContextBundle` 中的每个 `ContextItem`。

然后提取：

```python
item.citation.class_name
item.citation.symbol_name
item.citation.signature
" > ".join(item.citation.heading_path)
item.citation.file_path
```

所以对 CODE 来说主要可能得到：

```text
class_name
symbol_name
signature
file_path
```

对文档来说可能得到：

```text
heading_path
file_path
```

---

# 4. 举个实际例子

假设第一轮针对：

```text
ER3：
确认订单创建失败后的补偿机制
```

检索结果里出现：

```java
class PurchaseTicketServiceImpl
```

以及：

```java
private void compensateTicketIfOrderFailed(...)
```

那么 `_discovered_terms()` 可能得到：

```text
ER3:
[
    "PurchaseTicketServiceImpl",
    "compensateTicketIfOrderFailed",
    "compensateTicketIfOrderFailed(...)",
    "xxx/PurchaseTicketServiceImpl.java"
]
```

这里非常关键：

> **这些不是 LLM 猜出来的 Symbol。**

而是：

```text
第一轮真实检索结果
↓
Context citation metadata
↓
提取出来
```

所以可信度比模型自己编类名高得多。

---

# 5. 为什么只提取“属于这个 ER”的 Symbol？

ContextItem 上之前有：

```text
Supports: ER1, ER3
```

代码会检查：

```python
for requirement_id in item.sub_question_ids:
```

所以：

```text
ER3
```

只能拿支持 ER3 的 ContextItem 中发现的 Symbol。

不会出现：

```text
ER1 找到的完全无关类
↓
偷偷塞给 ER3
```

这样可以减少第二轮搜索漂移。

---

# 6. 然后再次调用 SearchActionPlanner

第一轮是：

```python
plan_actions(
    original_query,
    requirements,
    round_index=0
)
```

第二轮则变成：

```python
plan_actions(
    original_query,
    followup_requirements,
    round_index=1,
    history=tuple(history),
    coverage=coverage_by_id,
    discovered_terms=...
)
```

这时候 Planner 的输入丰富了很多。

它现在知道四类信息：

```text
1. 原始用户问题

2. EvidenceRequirement

3. 第一轮为什么还不够
   → missing_criteria

4. 第一轮已经发现了哪些项目真实术语
   → discovered_terms
```

还有：

```text
5. 第一轮已经搜过什么
   → history
```

---

# 7. `history` 的作用是什么？

假设第一轮已经搜了：

```text
SA1:
"购票订单失败补偿"
```

第二轮不允许简单重复：

```text
"购票订单失败补偿"
```

代码会收集：

```python
previous_queries
```

然后检查新 Query 是否重复。

如果完全相同：

```python
raise SearchActionPlanError(
    "search action repeats a previous query"
)
```

所以第二轮至少形式上必须变化。

---

# 8. `missing_criteria` 是第二轮的另一个关键输入

上一阶段 CoverageChecker 可能输出：

```text
ER3:
PARTIAL

missing_criteria:
- 缺少订单创建失败后恢复已创建车票状态的直接实现
```

现在 SearchActionPlanner 会看到这个缺口。

所以它不应该再泛泛搜：

```text
购票流程
```

而应该围绕：

```text
订单失败
恢复车票
补偿
```

来生成新的 Query。

---

# 9. 理想情况下第二轮应该怎么工作？

例如第一轮：

```text
用户问题：
订单创建失败怎么办？

第一轮 Query：
购票 订单失败 补偿
```

第一轮发现：

```text
PurchaseTicketServiceImpl
compensateTicketIfOrderFailed
```

Coverage 说：

```text
缺少该补偿方法的具体实现证据
```

理想第二轮应该生成：

```text
compensateTicketIfOrderFailed
PurchaseTicketServiceImpl
```

甚至更精确：

```text
PurchaseTicketServiceImpl
compensateTicketIfOrderFailed
ticket rollback
```

也就是说：

```text
第一轮：
自然语言 Discovery

第二轮：
真实 Symbol 定位
```

---

# 10. 当前代码确实强制第二轮“利用第一轮发现”

这是一个不错的设计。

如果 `discovered_terms` 不为空：

```python
if round_index > 0:
```

代码会验证：

```python
terms = discovered_terms[requirement.id]
```

然后要求：

```text
新的 Query
至少包含一个 discovered term
```

否则：

```python
raise SearchActionPlanError(
    "follow-up action does not use a discovered project term"
)
```

所以如果第一轮已经发现：

```text
doPurchaseInTransaction
```

LLM 第二轮却输出：

```text
购票事务一致性如何实现
```

而完全没出现：

```text
doPurchaseInTransaction
```

这个输出会被判非法。

这是当前系统已经做得比较好的地方。

---

# 11. 如果没有 discovered term 呢？

比如第一轮只是找到一些普通内容：

```text
没有 class_name
没有 symbol_name
没有 signature
```

但 Coverage 有：

```text
missing_criteria
```

那么程序要求第二轮 Query 至少针对这个缺口。

也就是：

```text
有 Symbol
→ 必须利用 Symbol

没有 Symbol
→ 至少利用 missing criteria
```

所以第二轮理论上一定比第一轮更有针对性。

---

# 12. 如果 LLM 第二轮规划失败怎么办？

还是有 fallback。

Fallback 会拼：

```text
original_query
+
requirement.target
+
missing_criteria
+
discovered_terms
```

例如：

```text
订单失败如何补偿
+
确认失败补偿机制
+
缺少恢复车票状态实现
+
PurchaseTicketServiceImpl
compensateTicketIfOrderFailed
```

最后组成一个 Query。

所以即使 LLM 输出有问题，第二轮还是可以继续。

---

# 13. 到这里看起来很好，那为什么 Rescue 只有 40%？

关键来了。

因为：

> **虽然第二轮 Query 变聪明了，但“搜索动作本身”没有变。**

当前 `SearchAction` 仍然只有：

```python
SearchAction(
    query,
    source_scope,
    ...
)
```

然后执行时依然：

```python
self.retrieval_policy.search_scope_with_trace(
    action.query,
    action.source_scope,
    per_action_top_k
)
```

也就是说：

```text
Round 1:
自然语言 Query
→ RetrievalPolicy

Round 2:
带 Symbol 的 Query
→ 还是 RetrievalPolicy
```

---

# 14. 当前并没有真正的 `symbol_search`

例如已经知道：

```text
compensateTicketIfOrderFailed
```

当前第二轮并不是：

```sql
WHERE symbol_name =
'compensateTicketIfOrderFailed'
```

而是：

```text
把 compensateTicketIfOrderFailed
放到一个搜索 Query 里

↓
继续走 keyword/vector/hybrid 策略
```

这两个差别非常大。

---

# 15. 当前第二轮本质上还是“Query Rewrite”

虽然已经比普通 Query Rewrite 强一些，因为它利用：

```text
missing_criteria
+
discovered_terms
```

但本质仍然是：

```text
第一轮 Query
↓
观察结果
↓
生成一个更好的 Query
↓
同一套 Retriever 再搜
```

而不是：

```text
第一轮：
semantic_search

↓
发现 Symbol

第二轮：
symbol_search
```

这就是我们前面一直讨论的架构缺口。

---

# 16. 举一个很直观的例子

第一轮找到了：

```text
class:
PurchaseTicketTxService

method:
doPurchaseInTransaction
```

Coverage：

```text
PARTIAL

缺少具体事务方法实现
```

当前第二轮可能：

```text
Query =
"doPurchaseInTransaction
PurchaseTicketTxService
购票事务实现"
```

然后：

```text
Hybrid Search
```

返回：

```text
1. PurchaseTicketServiceImpl
2. 购票流程文档
3. PurchaseTicketTxService 类 Chunk
4. 某事务说明文档
5. doPurchaseInTransaction 方法 Chunk
```

方法本身可能刚好：

```text
Rank 5
```

甚至：

```text
Rank 8
```

---

如果有真正的 Tool：

```text
symbol_search(
    class_name="PurchaseTicketTxService",
    symbol_name="doPurchaseInTransaction"
)
```

理论上：

```text
Rank 1
```

直接定位。

这就是区别。

# 17. 第二轮搜回来的结果不是另建一个新 EvidencePool

这一点也值得注意。

第一轮建立：

```python
pool = EvidencePool()
```

第二轮还是往**同一个 pool** 里加：

```python
history.extend(
    self._execute(
        followup_actions,
        plan,
        pool
    )
)
```

所以逻辑是：

```text
第一轮候选
        +
第二轮新候选
        ↓
同一个 EvidencePool
```

不是：

```text
第二轮把第一轮覆盖掉
```

---

# 18. 第二轮结束后会重新筛一次

因为 Pool 更新了，所以再次：

```python
bundle = self._build_context(
    request,
    plan,
    pool,
    top_k
)
```

也就是重新执行：

```text
EvidencePool.select()
↓
ContextBuilder
↓
新的 ContextBundle
```

所以第一轮可能：

```text
C1 A
C2 B
C3 C
```

第二轮新找到：

```text
D
E
```

重新选择后可能变成：

```text
C1 A
C2 D
C3 B
C4 E
```

不是简单：

```text
C1 A
C2 B
C3 C
C4 D
C5 E
```

---

# 19. 为什么要重新全局筛选？

因为第二轮可能找到更权威的证据。

例如第一轮：

```text
ER3
找到一个历史文档
```

第二轮：

```text
找到真实 CODE 实现
```

那重新 `EvidencePool.select()` 后：

```text
真实 CODE
```

应该优先进入 Context。

如果只是把第二轮结果简单 append：

```text
旧低质量证据
```

可能继续占据前面的字符预算。

---

# 20. 然后 CoverageChecker 再判断一次

第二轮新 Context：

```python
coverage = self.coverage_checker.check(
    plan.requirements,
    bundle
)
```

所以：

```text
Round 0:

ER3
PARTIAL
```

经过补查：

```text
Round 1:

ER3
SATISFIED
```

这就算：

> **成功 Rescue。**

# 21. 系统会保存两轮 Coverage 历史

不是只保留最后状态。

有：

```python
coverage_rounds.append(
    CoverageRound(0, coverage)
)
```

第二轮：

```python
coverage_rounds.append(
    CoverageRound(1, coverage)
)
```

因此以后可以看到：

```text

Round1 → SATISFIED
```

这也是为什么评测能够算：

```text
Second-round Rescue
```

# 22. 第二轮之后不会有第三轮

当前代码只明确执行：

```text
Round 0
Round 1
```

没有：

```text
while not satisfied:
    search again
```

所以不是无限 Agent Loop。

最多：

```text
第一轮
+
第二轮
```

这样做主要是控制：

```text
成本
延迟
搜索次数
```

# 23. 还有总 Action 数限制

当前：

```python
MAX_SEARCH_ACTIONS = 12
```

也就是说整次 Retrieval 最多：

```text
12 个 SearchAction
```

假设第一轮已经用了：

```text
8 个
```

第二轮最多再：

```text
4 个
```

系统会算：

```python
remaining_budget =
    MAX_SEARCH_ACTIONS - len(history)
```

防止复杂问题产生太多检索动作。

# 25. 这一步目前的优点

当前设计其实已经比普通 RAG 强很多。

因为它不是：

```text
Query
↓
TopK
↓
Answer
```

而是：

```text
Query
↓
搜
↓
判断缺什么
↓
观察发现了哪些真实 Symbol
↓
针对性再搜
```

已经有了很明显的：

```text
Observe → Replan
```

思想。

# 26. 但它还不是真正的 Tool Agent

因为现在：

```text
Replan
```

只能改变：

```text
Query 文本
```

不能改变：

```text
Action 类型
```

当前相当于：

```text
Action 永远是：

SEARCH(query)
```

只是 query 每轮不同。

---

真正 Tool Agent 应该允许：

```text
第一轮：
semantic_search(query)

第二轮：
symbol_search(symbol)

或者：
keyword_search(term)

或者未来：
find_references(symbol)

或者：
read_source(file, lines)
```

这就是未来演进方向。

## 这一阶段最值得记住的一句话

当前 DevContext 的第二轮不是：

> **换一种工具重新调查。**

而是：

> **根据第一轮发现的信息，生成一个更有针对性的 Query，再用原来的 RetrievalPolicy 搜一次。**

所以它已经有：

```text
反馈
+
补查
```

但还没有真正做到：

```text
semantic search
→ symbol search
→ read source
→ find references
```

这就是当前架构从 **Evidence-driven RAG** 向 **Tool-based Project Agent** 之间还差的那一层。

下一步如果继续按流程讲，就是最后的检索收尾：**第二轮结束后，如何根据 Coverage 生成 `READY / PARTIAL / EMPTY` 的 `EvidencePackage`，然后把检索结果冻结并交给 Answer Planner。**
