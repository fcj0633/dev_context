> **阅读说明**：本文是转向期的原始分析记录，其中的流程图描述的是**职责划分**（谁负责理解问题、谁负责决定要什么证据），不是某一版的模块边界。文中作为独立阶段出现的 "Evidence Planner"，其职责**仍然存在**，只是在 `07-规划合并为一次调用设计与实现方案.md` 中被并入了问题规划那一次调用，不再是独立环节。

当前系统问题：1.我最终想要实现的效果是，像chatgpt一样，能够将用户的问题详细拆解并形成清晰的回答 2.当前系统将输入切分为代码和文档或者混合，出发点有问题。一个用户很可能不了解项目，基本上不可能问出具体的代码问题，大概率只能问出语义问题，这样规划本身就不合理。除非后续将用户问题，转换为具体的代码，再使用关键词搜索。3.当前系统是否有必要做成向量检索，直接使用工具，查询代码和文档不是更为方便吗--详细分析解释这三个问题，避免后续陷入方向错误

先给整体判断：

> **现有工作没有走废。Chunk、Metadata、Vector/Keyword、Context Builder、Citation、Evaluation 都可以保留。真正需要调整的是上层抽象：不要再把“CODE / DOC / MIXED”当成用户问题类型，而应该把它降级为 Agent 内部的“证据来源类型”。**

最终 DevContext 更合理的定位应该从：

```text
用户问题
→ CODE / DOC / MIXED
→ 检索
→ 回答
```

调整为：

```text
用户问题
→ 理解用户到底想知道什么
→ 拆成若干子问题
→ 判断每个子问题需要什么证据
→ 自主选择搜索工具
→ 获取代码 / 文档 / 配置等证据
→ 判断证据是否充分
→ 继续搜索
→ 组织成清晰完整的回答
```

这两种架构差别非常大。

# 一、问题 1：想做到像 ChatGPT 一样详细拆解并回答，当前架构够吗？

**不够。**

但原因不是你的 Retriever 不够强。

而是当前系统的核心仍然是：

```text
Query
→ Retrieval
→ Context
→ Answer
```

这更像：

> “根据检索结果回答问题。”

而你真正想做的是：

> **“理解用户的问题，然后决定要调查什么，再组织成一个用户能够理解的答案。”**

这是两个不同层级。

---

## 1. ChatGPT 风格的回答，关键不是“检索更多 Chunk”

假设用户问：

> 订单超时关闭机制是怎么实现的？为什么要这么设计？

好的回答通常不是直接贴几段代码，而会自然拆成：

```text
1. 先给结论
2. 这个机制要解决什么问题
3. 整体执行流程
4. 正常路径是什么
5. 超时后发生什么
6. 哪些类 / 方法负责
7. 为什么采用这种设计
8. 有什么工程取舍
```

这里其实隐含了一个：

```text
Answer Plan
```

或者更准确地说：

```text
Question Understanding
+
Question Decomposition
+
Evidence Planning
+
Answer Planning
```

而不是简单：

```text
拿 Top5 Chunk
→ 塞给 LLM
→ 让 LLM 自己发挥
```

---

# 二、所以你真正缺的是 Question Planner

这是我认为 DevContext 后面最应该调整的地方。

例如用户问：

> 订单超时以后系统是怎么处理的？

用户完全没有说：

```text
代码
文档
类名
方法名
```

但系统应该自己理解：

这个问题想知道的是：

```text
① 整体机制是什么
② 执行流程是什么
③ 具体在哪里实现
④ 为什么这么设计
```

然后内部形成：

```text
QuestionPlan

SubQuestion 1:
订单超时处理整体流程是什么？

SubQuestion 2:
什么组件负责检测超时？

SubQuestion 3:
实际关闭订单的方法在哪里？

SubQuestion 4:
为什么采用这种设计？
```

再进一步决定：

```text
SubQuestion 1
→ DOCUMENT + CODE

SubQuestion 2
→ CODE

SubQuestion 3
→ CODE

SubQuestion 4
→ DOCUMENT
```

注意：

> **CODE / DOCUMENT 仍然存在。**

但是它已经从：

```text
“用户问题是什么类型”
```

变成：

```text
“回答某个子问题需要什么类型的证据”
```

这才是合理的层级。

# 三、你对当前 CODE / DOC / MIXED Router 的质疑是对的

你现在的 Router 相当于：

```text
用户说“代码在哪里”
→ CODE

用户说“为什么”
→ DOC

用户两种都说
→ MIXED
```

这对于做 Retrieval 实验是合理的。

但如果把它当最终产品入口，就有明显问题。

因为真实用户不会这样问。

# 四、真实用户大概率问的是“业务语义问题”

例如第一次接触 12306 项目的人可能问：

> 用户注册怎么防止缓存穿透？

而不会问：

> `userRegisterCachePenetrationBloomFilter` 在哪里定义？

他可能问：

> 车票查询为什么这么快？

而不会问：

> `pageListTicketQuery` 方法在哪里实现？

他可能问：

> 支付回调失败怎么办？

而不会问：

> `PayNotifyCompensateJob` 是怎么执行的？

所以真实情况往往是：

```text
用户语言
    ↓
业务概念 / 自然语言
```

而项目代码是：

```text
Java Symbol
Class
Method
Annotation
Configuration
```

中间天然存在一个：

> **Semantic → Code Symbol Gap**

这其实应该成为 DevContext 的一个核心问题。

# 五、因此你提到的这个方向反而非常重要

你说：

> “除非后续将用户问题转换为具体的代码，再使用关键词搜索。”

这个思路是对的，但可以再精确一点：

> **不是一开始就把自然语言直接“翻译成某个方法名”，而是先通过语义搜索获得线索，再从线索中发现 Symbol，然后进入精确代码搜索。**

也就是：

```text
用户：
“支付回调失败以后系统怎么办？”

↓ Semantic Discovery

找到文档：
“支付回调与下游通知”
“通知补偿任务”

↓ Extract Entities / Symbols

发现：
PayNotifyCompensateJob
payCallback
notifyPayResult

↓ Exact Code Search

symbol_search("PayNotifyCompensateJob")

grep("notifyPayResult")

↓ Read Code

读取具体类和方法

↓ Synthesis

解释：
为什么需要补偿
→ 正常路径
→ 异常路径
→ 对应代码
→ 工程取舍
```

这套流程就比：

```text
Query → MIXED → Vector Search
```

强很多。

---

# 六、这其实可以叫“Semantic-to-Symbol Bridge”

这个概念很适合成为你项目的一个核心设计点。

因为 Java 项目理解最大的一个困难就是：

```text
用户说业务语言
↓
源码使用工程语言
```

例如：

```text
用户：
“登录凭证在哪里校验？”

源码：

TokenValidateGatewayFilter
Authorization
JWT
Gateway
```

用户根本不知道：

```text
TokenValidateGatewayFilter
```

所以直接 Keyword Search 很难。

但是：

```text
Semantic Search
```

可能先找到：

```text
网关鉴权
登录 Token 校验
Gateway Filter
```

然后再发现：

```text
TokenValidateGatewayFilter
```

之后：

```text
Keyword / Symbol Search
```

就非常强。

因此最合理的是：

```text
Semantic Search
    ↓
Discover Symbols
    ↓
Exact Search
    ↓
Read Code
```

而不是在：

```text
Vector
vs
Keyword
```

里面二选一。

# 七、这就引出了你的第三个问题：到底还有没有必要做向量检索？

答案是：

> **有必要，但它不应该再是系统的“中心”。**

我甚至建议你以后把 Vector Retrieval 从：

> “核心检索架构”

降级为：

> **Agent 可调用的一种 Search Tool。**

这是一个非常重要的架构变化。

# 八、把 Vector Search 看成 Tool，而不是系统本身

以后 Agent 可以拥有这些工具：

```text
semantic_search(query)
keyword_search(query)
symbol_search(symbol)
grep(pattern)
read_file(path, lines)
```

甚至以后：

```text
find_references(symbol)
find_implementations(interface)
```

这时候：

```text
Vector Search
```

只是：

```text
semantic_search()
```

这个工具的具体实现。

就像 ChatGPT 使用 Web Search 一样：

> ChatGPT 不是“搜索引擎”。

搜索只是它解决问题的一种能力。

同样：

> DevContext 不应该是“向量数据库前面的聊天框”。

向量检索只是 DevContext 理解项目的一种手段。

# 九、那为什么不干脆完全不要 Vector，直接让 Agent 查代码？

这个问题就很值得分析了。

假设完全去掉 Vector。

用户问：

> 为什么订单创建过程中要把 Feign 调用移出事务？

Agent 只有：

```text
grep
symbol search
read_file
```

问题来了：

它搜什么？

它必须先猜：

```text
Feign
Transaction
OrderService
createTicketOrder
```

如果用户的问题和源码命名差距很大：

```text
用户：
“为什么远程调用不能放在数据库事务里面？”
```

源码可能写的是：

```text
executeDistributedLock()
remoteUserService
afterCommit
```

纯关键词工具可能需要很多轮猜测。

# 十、Vector Search 最大价值就在“你不知道关键词是什么”的时候

Vector Search 擅长：

```text
用户不知道项目术语
用户不知道类名
用户不知道方法名
甚至不知道相关文件
```

但他大概知道：

```text
“我想了解什么”
```

这时候：

```text
自然语言
↓
Embedding
↓
相关 Chunk
```

非常适合做：

> **第一阶段 Discovery。**

所以它不是没用。

它特别适合你现在这个产品定位：

> “用户不了解项目。”

# 十一、而精确 Code Tool 最大价值是在“已经知道线索以后”

一旦发现：

```text
OrderServiceImpl
createTicketOrder
PayNotifyCompensateJob
```

就没有必要再：

```text
vector_search("PayNotifyCompensateJob")
```

这时候最合理的是：

```text
symbol_search("PayNotifyCompensateJob")
```

或者：

```text
grep
AST index
JavaParser
```

因为这些方法：

```text
精准
确定性强
可解释
不会把同义代码排在前面
```

所以比较合理的分工是：

| 场景 | 更适合 |
|---|---|
| 用户完全不知道项目术语 | Vector |
| 自然语言找设计概念 | Vector |
| 找具体 Class | Symbol / Keyword |
| 找具体 Method | Symbol / AST |
| 搜字符串/注解/配置 | grep / Keyword |
| 读实现细节 | read_file |
| 找调用关系 | References / AST |

# 十二、所以正确问题不是“Vector 还是 Tool”

而是：

> **Agent 什么时候应该用什么 Tool？**

这才是 Agentic Retrieval 真正应该研究的东西。

未来架构应该变成：

```text
                 User Query
                     ↓
              Question Planner
                     ↓
              Evidence Planner
                     ↓
            ┌────────┼────────┐
            ↓        ↓        ↓
      Semantic    Symbol    Keyword
       Search      Search     Search
            ↓        ↓        ↓
              Evidence Pool
                     ↓
                Read Files
                     ↓
             Sufficiency Judge
              ↙             ↘
          Enough          Missing
            ↓                ↓
      Answer Planner    New Search Plan
            ↓                ↓
         Answer          Tool Calls
```

这已经比：

```text
CODE / DOC / MIXED
↓
Retrieval
```

高一个层级了。

# 十三、那现有 CODE / DOC / MIXED 要不要删？

**不建议删。**

而是降级。

现在：

```text
CODE / DOC / MIXED
=
Query Type
```

未来应该变成：

```text
CODE / DOCUMENT
=
Evidence Source Type
```

例如：

```text
EvidenceRequirement {
    purpose: "explain design rationale",
    preferred_source: DOCUMENT
}
```

另一个：

```text
EvidenceRequirement {
    purpose: "verify actual implementation",
    preferred_source: CODE
}
```

如果一个问题需要两个：

```text
EvidencePlan:
- rationale → DOCUMENT
- implementation → CODE
```

自然就是原来的：

```text
MIXED
```

但是已经不需要把整个用户 Query 粗暴标成：

```text
MIXED
```

了。

# 十四、所以当前 Router 更像“Retrieval Router”，不应该叫“Question Router”

这是一个很值得修改认知的地方。

它现在其实回答的是：

> “这次检索主要应该去哪种数据源？”

而不是：

> “用户到底想知道什么？”

真正的 Question Router / Planner 应该回答：

```text
用户想：
解释？
定位？
追踪流程？
比较？
理解设计原因？
排查问题？
```

例如：

```text
Explain
Locate
Trace
Compare
Diagnose
Summarize
```

这些才更接近：

```text
User Intent
```

而：

```text
CODE / DOC
```

只是：

```text
Evidence Modality
```


或者：

```text

```

# 最终结论

你的三个疑问，结论分别是：

**1. 想做到 ChatGPT 式详细回答：**

单纯提升 Retrieval 不够。

最需要增加的是：

```text
Question Decomposition
Evidence Planning
Answer Planning
```

---

**2. CODE / DOC / MIXED 作为用户 Query 分类：**

你的质疑成立。

它不应该继续作为最高层 User Intent。

更合理的是：

```text
用户意图
→ 子问题
→ Evidence Requirement
→ CODE / DOCUMENT
```

**CODE/DOC 应该是证据类型，不是用户问题类型。**

---

**3. Vector Search 有没有必要：**

有，但角色应该改变。

不是：

```text
DevContext = Vector RAG
```

而应该是：

```text
DevContext Agent
拥有：
Semantic Search
Symbol Search
Keyword Search
Read File
...
```

Vector Search 只是其中的：

```text
semantic_search()
```

它负责：

> **用户不知道项目术语时，帮助发现方向。**

然后：

```text
Semantic
→ Symbol
→ Exact Tool Search
```

才是更合理的代码理解路径。
