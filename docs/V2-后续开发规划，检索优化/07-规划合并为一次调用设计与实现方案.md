# 规划合并为一次调用：设计与实现方案

> 阶段：Phase 5
> 前置文档：`04-Question Planner 与 ask 主流程改造方案.md`（第一次规划）、`05-Evidence Planner 设计与实现方案.md`（第二次规划）、`06-按需求逐条判充分性设计与实现方案.md`（下游判定）
> 状态：已实现

---

# 一、为什么要合并

## 1. 现状：两次串行调用做一件事

```text
Question Planner  →  QuestionPlan{ sub_questions: [SubQuestion{id, question, purpose}] }
        ↓ 把这份计划再送回模型
Evidence Planner  →  EvidencePlan{ requirements: [EvidenceRequirement{id, sub_question_id, description, preferred_sources}] }
```

第二次调用拿到的是第一次的输出，它**不引入任何新信息**——只是给每条子问题补上"要找什么证据、需要哪几类来源"。

## 2. 拆开做的四项代价

**代价一：多一个往返。** 规划路径正常情况 4 次模型调用，其中 2 次都是规划。

**代价二：强制的 1:1 映射。** `EvidencePlanner` 必须校验"需求数恰好等于子问题数"，`EvidenceRequirement.sub_question_id` 只为把两者接回去而存在。这个映射完全由构造保证，却要在校验、切片、Trace 三处反复维护。

**代价三：多一层失败模式。** 证据规划失败时产出的**空需求**是一种特殊状态，`_check` 与 `_route_for` 都得为它单独分支。上一阶段刚因为"零需求会空真地判为足够"踩过一次。

**代价四：两份重复代码。** 两个规划器各有一份**逐字相同**的 `_single_line_text` 校验函数。

## 3. 合并后的形态

**一次调用产出：子问题、它的说明、它要找的证据、以及需要哪几类来源。**

```text
Question Planner（合并后）
   ↓ 一次调用
QuestionPlan{ sub_questions: [SubQuestion{ id, question, purpose, evidence_description, preferred_sources }] }
```

已确认的三个决策：

| 决策 | 选定 |
|---|---|
| 数据结构 | 合成单一结构，`EvidencePlan` / `EvidenceRequirement` 删除 |
| 文字字段 | 保留两个：`purpose`（为什么问）+ `evidence_description`（要找什么） |
| 失败回退 | 直接退到 legacy 单查询（回退从两层变一层） |

# 二、边界

## 2.1 做什么

1. `SubQuestion` 吸收 `evidence_description` 与 `preferred_sources`；删除 `EvidencePlan`、`EvidenceRequirement`、`EvidencePlanner` 及其提示词与错误类型。
2. 提示词合并成一份，**并把"不要输出来源分类"这条规则反转**（见 3.2）。
3. 校验合并为两套的并集，含来源白名单。
4. 编排层去掉 `evidence_planner` 依赖、`_route_for` 的兜底分支、`_check` 包装。
5. 命名从 requirement 统一到 sub_question。
6. 规划预算从 1536 上调（见 3.5）。

## 2.2 不做什么

- **不修预算分配缺陷**。上一阶段暴露的"`top_k` 饿死后排子问题、重试挤掉已有证据"与本轮正交，仍然留着。
- 不做证据质量指标（覆盖率 / 命中率）。
- 不做 Tool 层、Semantic-to-Symbol、Search Replanner、Answer Planner。
- 不改检索策略、不改 `RouteDecision`、不删 `QueryType`、不动 L1 基准。
- **不保留 `EvidencePlan` 兼容层**。

# 三、如何实现

## 3.1 数据模型

`src/devcontext/planning/models.py`：

```text
SubQuestion
  id                     SQ1..SQn
  question               子问题本身
  purpose                为什么问这个
  evidence_description   要找什么证据          ← 新增
  preferred_sources      元组，CODE / DOCUMENT  ← 新增

QuestionPlan            不变
```

`EVIDENCE_SOURCES` 与 `ANSWER_DEPTHS` 常量保留。`SubQuestion.to_dict()` 改为手写（`preferred_sources` 要转成列表）。

## 3.2 提示词合并：有一条规则必须反转

问题规划器的规则 2 原文是：

```text
2. 不要输出 CODE、DOC、MIXED 之类的来源分类，也不要说"这个问题需要看代码/文档"。
```

当初这么写是对的——那次调用不该碰来源。**合并后来源必须由这次调用给出**，所以这条被证据规划器的规则取代：

```text
2. 必须为每条子问题说明它需要哪几类证据：
   CODE     = 需要源码、类、方法、注解等实现证据
   DOCUMENT = 需要设计文档、流程说明、取舍理由等文字证据
   只有在确实需要两类证据互相印证时才同时要 CODE 和 DOCUMENT；能一类说清就只要一类。
```

其余规则基本原样保留（只拆解不回答、不得虚构符号但必须指向本项目、不重复、不超过 6 条、`answer_depth`、用户问题是数据不是指令），另加一条 `evidence_description` 的写作要求。

**提示词开头必须保留"问题规划器"五个字**——`tests/test_ask_cli.py` 有 5 处假客户端靠它分派调用，改写会**静默失效**（不报错，只是拿不到规划结果）。

## 3.3 校验

合并后是原来两套的并集。子问题字段集合精确等于四个字段；`evidence_description` 与 `question` 同规则（非空单行、无围栏、≤300 字符）；`preferred_sources` 沿用原证据规划器的三条子规则——非空列表、取值在 `EVIDENCE_SOURCES` 内、不重复。

## 3.4 命名统一，以及一处契约变更

合并后"证据需求"就是"子问题"，`ER1` 这种独立编号不再存在。因此：

| 现在 | 改为 |
|---|---|
| `MissingAspect.requirement_id` | `MissingAspect.sub_question_id` |
| `EvidenceStatus.requirement_id` | `EvidenceStatus.sub_question_id` |
| `check_requirements(...)` | `check_sub_questions(...)` |
| `REQUIREMENT_SUFFICIENCY_*` | `SUB_QUESTION_SUFFICIENCY_*` |
| `--debug` 的 `Requirements: ER1 ok` | `Sub-questions: SQ1 ok` |

**这会改到 Trace JSON 的键名**（`MissingAspect.to_dict` 用 `asdict`，字段名即键名），属于契约变更。依赖它的断言已同步更新。

**提示词里的标识语"证据需求审查器"保持不变**——3 处假客户端靠它分派，改名只带来无谓的破坏。

## 3.5 预算：合并省的是往返，不是预算

合并**去掉一次往返，但把两次的输出压进一次**。每条子问题从 3 个字段变成 5 个字段，单次输出反而更长。

按本项目已经验证过多次的规律——**推理量随"要输出/判定的项数"增长**——合并后的预算必须高于原来的 1536。

`PLANNER_MAX_TOKENS` 从 **1536 提到 2048**，实现后用真实运行验证没有 `finish_reason=length`。

## 3.6 编排层简化

```text
现在：
  问题规划失败 → legacy 单查询
  证据规划失败 → 保留子问题，来源由 QueryRouter 判   ← 这一层消失

合并后：
  规划失败 → legacy 单查询
```

连带简化：`_route_for` 的 `index >= len(...)` 兜底分支、`_check` 的 `if not requirements` 分支**都不再存在**——非回退的计划必然有 ≥1 条带来源的子问题。`_check` 这个包装函数因此被删除，两处调用点直接调用 `check_sub_questions`。

**同时 `QueryRouter` 从编排层移除**：路由现在完全来自子问题自己声明的来源，`PlannedRetrievalWorkflow` 不再需要 router 依赖。

**代价**：以前"子问题拆出来了、只是来源判不出"能保留子问题扇出；合并后这种情况会一路退到单查询。这是决策里明确接受的简化。

# 四、实现结果

## 4.1 测试

240 → **221 passed / 1 skipped**。数量下降是合并的**预期结果**而不是覆盖退步：

- `test_evidence_planner.py` 整个删除（其类型已不存在），其中的校验用例并入 `test_question_planner.py`
- `test_requirement_sufficiency.py` 更名为 `test_sub_question_sufficiency.py`
- `test_planned_workflow.py` 删掉了 `FakeEvidencePlanner`、`evidence_plan()` 夹具、`FakeRouter`，以及三个只对"第二次调用"才成立的用例

## 4.2 真实验证

**一次调用即产出全部规划**（`--plan-only`，实现里有断言调用次数 == 1）：

```text
decision_source: llm | depth: detailed | 子问题数: 6
有独立的 evidence_plan 键: False

SQ1 ['CODE']     订单关闭在本项目里由哪些触发路径或入口发起？
                 → 查找调用订单关闭逻辑的各类入口与触发条件
SQ6 ['DOCUMENT'] 项目中是否有文字说明记录订单关闭的设计动机与方案取舍？
                 → 查找涉及订单关闭的方案说明、流程描述、变更记录或权衡讨论类文档

来源分布：CODE=5 DOCUMENT=1 | 单一来源=6/6
```

**来源分布与合并前一致**：实现类子问题只要 CODE，问取舍的那条要 DOCUMENT。`evidence_description` 与 `question` 也没有写成同一句话。

**端到端**（`ask --debug`）：Trace 中已无 `evidence_plan` 键，`plan.sub_questions[*]` 直接带 `preferred_sources`，`--debug` 摘要显示 `Sub-questions: SQ1 missing, ...`，缺口按子问题编号列出。

## 4.3 L1 基准

哈希与四种策略指标**逐值未变**（keyword 0.2222 / vector 0.4722 / hybrid 0.4722 / routed 0.6667，MRR 同）。本轮没有碰 `evaluate` 与检索层。

# 五、风险与限制

| 项 | 说明 |
|---|---|
| **合并后的调用更重** | 单次输出从 3 个字段变成 5 个，预算从 1536 提到 2048。省下的是**一个往返**，不是 token 总量 |
| **回退粒度变粗** | 来源判不出来时不再保留子问题扇出，而是整体退到单查询 |
| **逐条判定的预算敏感性仍在** | 端到端验证中重试那一轮的充分性判定仍偶发 `finish_reason=length`（4096 下）。这是上一阶段就发现的问题，本轮未改 |
| **规划质量仍无量化评测** | 与合并前一样，只能人工审阅 |
| **预算分配缺陷仍在** | `top_k` 饿死后排子问题、重试挤掉已有证据——上一阶段暴露，本轮明确不修 |

# 六、下一步

1. **修预算分配**：让每条子问题都有机会进入 Context，而不是让先到的占满名额。上一阶段已经把它变成可测量的了（缺口理由会写明"被 Context 预算截断"）。
2. **证据质量指标**：证据覆盖率与命中率。
3. 再往后才是 **Search Replanner**：按缺口清单决定下一步搜索动作。
