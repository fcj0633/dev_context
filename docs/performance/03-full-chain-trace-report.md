# 03 · 三问题全链路耗时跟踪报告

> 本轮是**逐问题逐环节的耗时跟踪**，不是统计基线（那是 `01-current-latency-baseline.md`），
> 也不是优化方案（那是 `02-latency-optimization-p0-p2.md`）。
>
> **⚠ 口径：每个问题只跑 1 次，全部为单次观测。**
> 上一轮 27 样本实测过：同一问题、同样参数，仅因 Planner 决定的节数不同，耗时可从 113.7s 到 471.1s，
> 相差 **4.1 倍**。因此本报告的每个数字都是「这一次」的值，不是该问题的特征值。
> 横向比较的是**结构与比例**（哪一环占大头、第二轮值不值），不是绝对秒数。

### 6.1 三条结构性的观察

**1. 证据链路比回答生成更贵。** 三题分别是 56% / 63% / 65%——**为了决定「用哪些证据」而花掉的时间，
超过了写出答案本身**。这不是某一题的异常，是三题一致的结构。

**2. 第二轮检索的收益极不稳定。** Q2 是「修好一条、弄坏一条」，Q3 是「一条都没动」。
两次都花了 7–30s，且 Q3 的第二轮覆盖检查（20.4s）比第一轮（13.5s）还慢。
三题里唯一没有第二轮的 Q1，反而用时最短。

**3. 嵌入便宜且没有重复。** 2.0–2.6s，占总耗时仅 3.7%–4.4%；但它是**检索阶段内部的一半以上**（59%–63%），
远超 SQL 与融合（后者基本是 0）。这次 17 个 action 各嵌入一次，**没有出现重复 embedding**
（那个问题只在混合作用域下偶发）。所以「优化嵌入」对端到端几乎没有意义，
「优化检索」本身也不值得——它只占总耗时的 3%–5%。

**4. 覆盖检查是被低估的环节。** Q2 27.4s、Q3 33.9s，**都超过了写作**（21.3s / 24.8s）。
而它做的事情只是判定证据够不够。

**5. reasoning token 占输出 69%–77%。** 三题都是如此。也就是说模型产出的绝大部分 token
不是答案，而是内部推理——这解释了为什么「覆盖检查」这种看似简单的判定要花 10–20 秒。

### 6.2 与前一版基线的差异（不是同一批题，仅供参考）

`01` 报告的样本多在 100–470s，本批 3 题是 54–93s。差异来自**路径不同**而非优化效果：
`01` 那批多为 5–11 节的多章节路径，本批被新的确定性深度策略统一判为 `standard`（3 节），
走单次写作，省掉了逐节生成、Composer、Reviewer 与 Revision。
`peak_llm_concurrency` 三题都是 **1**，因为单次写作路径没有可并行的章节，
P0–P2 的并发能力在本批完全没有被用到。

1. **本批三题的耗时结构一致：证据链路 56%–65% > 回答生成 35%–44%。**
   若要缩短端到端，优先级应放在覆盖检查与证据计划，而不是写作。
2. **第二轮检索需要收紧触发条件或改进判定。** 两次触发里一次无变化、一次发生回退。

## 附录 A · Q1 完整回答（2299 字符）

**问题**：项目为何使用责任链校验

用户真正要问的是：**为什么这里不写一段 if-else，而要为校验单独搭一套责任链？** 一句话答案：因为该项目的校验不是一次性代码，而是一组「持续追加、顺序自带语义、在多个入口反复出现」的规则；责任链把「顺序」和「扩展点」从方法体里搬出来，变成能声明的结构。

## 一、校验规则只会变多，而 if-else 的代价随规则数增长

设计文档记录的问题形状很具体：注册校验项会持续增加（参数非空 → 用户名可用 → 证件黑名单 → 未来实名核验/风控），而 if-else 堆叠带来三项代价——顺序难以控制与复用、新增校验要改 Service 方法体（违反开闭原则）、校验逻辑与业务逻辑耦合导致难单测 [E6]。这是历史设计文档中的问题陈述，不是当前运行时的行为记录，但它解释了后来代码为何长成那个样子。

关键在于这个形状不是注册独有的。车票查询的组合类接口流程被写成「责任链校验 → 四层组装 → 返回」[E11]；同一条链路的设计文档明确预期校验还会演进（预售期、城市兼容、风控），并点出「顺序即优先级」：先保证参数齐全，再做业务规则判断，最后做重一点的依赖查询（存在性）[E9]。购票前有 4 道校验，教学目标是能说清「分别拦什么、按什么顺序执行」，以及**新增一条校验要改哪里** [E12]。查询链路则是「责任链(3环) → 站码转城市 → 城市对取车次列表 → …」[E13]。

把这几处叠起来看，问题的形状是「多段、有序、可增」。顺序本身就是语义：先查库再报空参，既浪费查询又让错误提示不准 [E9]。所以需要的是**一种结构**，而不是一段写得更长的代码。

## 二、mark 分组、order 排序、Handler 承载规则

这套责任链的最小机制，用三个方法就能说完整。`AbstractChainHandler<T>` 只声明三件事：`mark()` 表明属于哪条链，`order()` 表明在链中的位置，`handler(param)` 表明做什么 [E1][E2]。规则内容与规则位置因此被写在同一处。

容器 `AbstractChainContext` 实现 `ApplicationContextAware` 与 `CommandLineRunner`，内部持有 `Map<String, List<AbstractChainHandler>> container`：启动后按 `mark` 收集全部 Handler、按 `order` 排序，业务侧只需调用 `handler(mark, param)` 顺序执行 [E4][E5]。值得注意它为什么用 `CommandLineRunner` + `ApplicationContext` 收集，而不是构造注入——文档注释给出的理由是这样可以避免 Handler 反向依赖 Service 造成的构造循环 [E4]。这说明「扩展点独立」与「依赖方向」在这一个设计里被一并处理了。

于是「新增一条校验」在代码上就是「新增一个类」：`UserRegisterParamNotNullChainHandler` 实现注册链过滤器，`order=0` 表示它最先执行 [E3]。

从 E1/E2 与 E4/E5 的文件路径看，user-services 与 ticket-services 各有一份同形态实现——**因此**这两条链共享的是同一套设计形态，而不是同一个类实例。这一点也解释了为什么车票侧的设计文档会写「用户模块已经实现并验证过同一套责任链容器，直接复用其设计形态」[E9]。

有一处细节现有证据无法对齐：注册链的环数，[E3] 的注释写「注册责任链 1/3」，而 [E10] 的链路概览写「注册：责任链（4 环）」；两者不一致，且各链的具体规则条数与最终顺序无法从现有证据确认。

## 三、收益与代价：什么时候这套结构是赚的

收益在文档里被表述得很干脆：把每一步校验拆成独立 Handler，按 mark 分组、按 order 排序、顺序执行，结果就是**新增规则 = 新增一个 Handler，不动既有代码** [E6]。扩展成本从「修改既有方法体」变成了「新增文件」。

反过来，什么情况下不赚？规则少且稳定时，集中式校验或条件分支更直观、调用链路更短、读一遍就懂；责任链的价值只在规则持续增长、且这套顺序需要在多处复用时才体现出来 [E6]。这是判断标准，不是无条件正确的架构原则。

代价有三层。第一，规则分散到多个类之后，链的全貌只有把 `mark` 与 `order` 聚合起来才读得出，理解容器的收集与排序时机是调试前提 [E4][E5]。第二，顺序从隐式变成显式约束，也就变成了可能配错的约束——教学材料直接要求回答「库存校验（order 20）为什么必须排在参数校验（order 0）之后」[E8]，顺序配置错误正是这类结构的主要失效点。第三，校验阶段的职责边界：它只做拦截、不产生需要补偿的中间态，这是它可以被放进事务内的前提；[E7] 提出的对照问题（把「订单失败后的手工补偿」作为方案是否比回滚更危险）正是从这一点切入——**如果**校验阶段真的只做拦截不做写入，那么它与补偿方案的风险差异就来自「是否需要人工介入」，而这一结论需要以该前提成立为准。

最后是边界：责任链解决的是「加规则、定顺序」，不解决规则本身怎么写，也不解决跨服务一致性；组合类接口在责任链之后仍有四层组装 [E11]。把它当成校验编排的容器，而不是校验逻辑的替代品，才是它在这个项目里的定位。

## 附录 B · Q2 完整回答（3170 字符）

**问题**：项目购票流程中，是如何保证数据一致性的，避免超卖问题

项目避免超卖靠的是一套分层的组合，而不是某一把锁：先用 Redis 令牌桶对待售余票做一次全局原子预占 [E2]，再用 Redisson 把同一用户、同一车次、同一席别的并发请求串行化 [E6]，然后让真正改票库的动作落在一个只操作 ticket 库的本地事务里 [E8]，最后用提交后回调、幂等补偿和定时兜底把令牌与票状态拉回一致 [E1]。

## 超卖为什么会在购票链路里出现

想象同一趟车、同一天、同一个席别，在开售瞬间涌入几百个请求。每个请求都要回答两个问题："还有票吗？"和"把票占住"。如果这两步之间没有任何互斥——比如先查库存读到"剩 1 张"，再各自去扣减——那么所有请求都能顺利通过查询，最后把余量扣成负数。问题的本质不是数据库慢，而是**判断与扣减不在同一个原子边界内**。

项目的应对是第一道闸门放在最前面：`tokenBucket.takeToken` 用 Redis Lua 脚本执行，按 `(trainId, departure, arrival)` 维度对席别余票令牌做原子扣减 [E2]。一旦返回 false，`purchaseTickets` 直接抛出"列车站点已无余票"，请求根本不会走到后面 [E7]。这说明令牌桶承担的是"全局准入"职责：把绝大多数注定失败的并发请求拦在数据库之外，而不是只做一次查询优化。

但令牌桶本身不解决另一类冲突——同一用户、同一席别下的并发重入。于是需要第二层：分布式锁把临界区收窄。

还有一层结构性约束必须认清：订单服务与票务服务是分离的 [E15]，而票务侧的本地事务被明确设计成只操作 ticket 数据库，远程调用留在编排层，目的是避免网络等待延长行锁持有时间 [E8]。这意味着"扣票 + 建单"无法用一个数据库事务包住，必须靠提交后事件与补偿来衔接。所以防超卖在这个项目里天然是一个**跨进程、跨存储的最终一致问题**，而不是单机事务问题——这也是为什么后面的主链路里，锁、事务、令牌归还的时序必须一丝不乱。

## 从购票入口到本地事务的并发控制链路

按时序复述一遍，每一步都解释它为什么必须在那个位置发生。

**1. 入口与基础校验。** Controller 的 `purchaseTickets` 调用服务层，"代理服务正常返回意味着事务已提交，此时才计为一次成功购票" [E13]——这句话本身就是主链路成功边界的定义。服务层先跑过滤链，再校验 `userId`/`username` 非空、单笔乘车人不超过 5 位 [E7]。这些是极廉价的前置判断，必须全部排在占用任何昂贵资源之前。

**2. 令牌原子预占。** 由请求构建出 `seatTypeCounts` 后调用 `takeToken`；返回 false 就抛"列车站点已无余票" [E2][E7]。这一步是全局准入，也是整个链路里唯一一次对"售出总量"做原子裁决的地方。

**3. 乘车人归属校验。** `loadPassengers` 在加锁之前执行，代码注释特意写明：要在请求占用任何一把分布式锁之前拒绝非法的乘车人归属 [E7]。为什么不放在锁里？因为它是远程调用，一旦进入临界区，网络抖动就会直接转化为锁持有时长。

**4. 加锁并进入本地事务。** `reserveLocally` 先取用户锁（`username + trainId`），再按席别逐个取席别锁，最后才调用 `purchaseTicketTxService.doPurchaseInTransaction` [E6]。注意加锁顺序是固定的：先用户、后席别，席别按遍历顺序 —— 顺序一致是避免互相等待死锁的前提。而这一层事务的定位非常明确："调用方已经完成乘车人校验并持有用户锁和全部席别锁，本事务只操作 ticket 数据库" [E8]。换句话说，锁的临界区**恰好等于**本地事务的范围，不多不少。

**5. 释放锁之后才做外部动作。** 方法返回后进入 `finally` 逆序释放席别锁和用户锁 [E6]；接着才安全地清余票缓存、调订单服务建单 [E7]。订单侧按 `orderSn` 做幂等创建：先 `selectByOrderSn` 命中就直接返回，并发场景靠唯一键 + `DuplicateKeyException` 兜底，并且只允许"内容完全相同的重试"复用已提交订单 [E9]。把建单放在锁外，是因为这个远程调用不具备并发正确性风险（幂等），却会显著拉长锁持有时间。

**6. 令牌归还的责任归属。** 这是最容易写错的一段。本地事务提交后，`cancelCallback` 是唯一的令牌归还者 [E7]；`returnTokensAfterCommit` 会注册 `afterCommit` 回调，只有事务真正提交才执行归还 [E1]。如果没有未提交，`finally` 里直接归还 [E7]。事务提交之后，令牌就归属到"这笔预订"的生命周期，只能由真正的座位释放来归还 [E15]。这条规则把"未提交就放票"这种典型超卖来源直接堵死了。

## 失败恢复、补偿幂等与当前证据边界

正常状态下，上面这条链路会一路走到成功计数。故障则出现在几个不同的位置，每处的状态变化和恢复方式都不同。

**建单明确失败。** `createOrder` 返回空或非成功码时，调用 `compensateKnownFailure`，内部走 `cancelCallback`，成功则计 `compensation.success`，失败则计 `compensation.fail` 并留日志等待恢复任务 [E11]。这一步把已占用的票务状态和令牌释放回可用状态。

**补偿自身的幂等性。** 这里有个反直觉的点：补偿不能是"失败就再调一次"。可能第一次补偿其实已经成功，只是调用方超时以为失败 [E10]。如果第二次继续无条件地 `LOCKED → AVAILABLE` 或 `+1 库存`，被重新放出来的可能是已经卖掉的座位 —— 那不是修复，而是制造超卖 [E10]。所以正确写法是"期望状态 + 条件 UPDATE"，只有符合预期状态的数据才允许变化 [E10]。文档里把这件事总结得更完整：最终一致 = 同步补偿 + 补偿幂等 + 定时兜底 + 按真实状态恢复 [E12]，四者缺一不可。

**辅助设施故障的降级。** 令牌归还抛异常时，`returnToken` 只是记一条降级指标，保留偏松降级并等待 TTL 自愈 [E3]；余票缓存删除失败时同样只记日志、等缓存过期，不阻塞主流程 [E5]。这两处取舍是一致的：宁可短暂少卖，也不因为缓存或计数器问题把已经提交的购票流程回滚掉。

**两个必须说清的边界。** 其一，`TrainPurchaseTicketRepeatChainFilter` 目前是保留占位、未实现 [E4]，所以"防重复购买"不是当前证据支持的强保证。其二，也是更重要的：现有证据里的"扣减"只覆盖到令牌桶预占这一层 [E2]，**没有**直接展示更新库存字段或座位余量的代码片段。因此可以说清的是这套组合——令牌原子预占 [E2]、用户锁与席别锁串行化 [E6]、只操作 ticket 库的本地事务 [E8]、提交后才归还令牌 [E1]、失败后幂等补偿 [E11] ——共同构成防超卖机制；而真实座位库存字段在事务内部如何被条件扣减，无法从当前证据确认。如果 `doPurchaseInTransaction` 内部同样采用"期望状态 + 条件 UPDATE"的语义，那么它与令牌层是闭合的；但这只是基于现有证据的条件判断，不是已证实的事实。

## 附录 C · Q3 完整回答（3646 字符）

**问题**：用户模块，用户表分库分表键为何要使用用户名

用户模块把 `t_user` 的分片键定为 username，直接原因是"分片键必须与查询键一致"这条硬约束在用户模块恰好落在用户名上：登录、注册查重、查资料、查乘车人这些关键路径都以用户名为入口，分片键与它对齐才能单分片命中；换成 id，这些路径会退化成广播查询 [E11][E13][E14]。

## 分片路由的硬约束：查询条件决定能不能定位到某张表

一句话核心模型：**分片算法只吃分片键的值，查询条件里没有这个值，路由就从"定位一张表"退化成"问所有表"。**

把它拆成三个概念来看。

**精确定位是怎么算出来的。** `CustomDbHashModShardingAlgorithm#doSharding` 接收 `PreciseShardingValue`，用 `suffix = |hash| % shardingCount / tableShardingCount` 算出目标后缀，再从可用目标里挑出以该后缀结尾的那一个 [E20]；按类注释的说法，就是 sharding-count 先分库、table-sharding-count 再分表 [E2]。整条计算链的输入只有 `shardingValue` 携带的那个分片键值——没有它，suffix 无从算起。

**哈希本身也只对键值做功。** `hashShardingValue` 把入参的 `hashCode` 取绝对值 [E5]。项目里按 username 做哈希取模并不只出现在分片算法里：`UserReuseUtil.hashShardingIdx` 就是 `Math.abs(username.hashCode() % USER_REGISTER_REUSE_SHARDING_COUNT)`，用来算"已注销用户名复用集合"的分片位置 [E1]，和常量定义 `user-reuse:{hash(username)%1024}` 的写法一致 [E3]。

**拿不到键值时发生什么。** 同一个算法类的 `RangeShardingValue` 分支直接 `return availableTargetNames`，把全部可用目标原样交出去 [E4]。这正是"无法裁剪"的实现形态：算不出唯一的 suffix，就只能承认自己覆盖所有分片。文档把这条机制概括成"分片规则是按分片键路由到具体表，否则 ShardingSphere 无法定位，只能广播" [E12][E16]。

所以选分片键不是挑一个唯一性最好的列（id 显然更"像主键"），而是挑一个**查询条件里一定出现的列**。这是硬约束，不是偏好。

## 用户模块的查询入口为什么收敛在用户名

先看访问模式。`t_user` 的表设计说明把 username 直接标为分片键，理由是"登录、注册、查询都从 username 出发，保证关键路径单分片命中" [E13]；查询清单也给出同样的结论——`t_user` 的主要查询方式是按 username 查，id 只在查详情时用，且不是热点 [E11]。

但真正让 username 站得住的，是它在整个模块里不只是 `t_user` 的查询键，而是**整个用户模块的操作坐标**：

- 注册分布式锁前缀是 `lock:user-register:{username}`，注销锁是 `user-deletion:{username}`，乘车人列表缓存是 `user-passenger-list:{username}`，乘车人写操作锁是 `lock:user-passenger:{username}` [E3]；
- 用户服务对外的远程接口签名也是 `listPassengerQueryByIds(username, ids)`——票务服务按"当前登录用户名 + 乘车人 ID"取实名信息 [E6]；
- 连用户名复用的分片工具，方法签名都是 `hashShardingIdx(String username)` [E7][E1]。

因此可以这样推导：缓存键、锁键、远程调用参数、复用集合的分片位置全都锚在 username 上 [E3][E6][E7]，那么把 `t_user` 的分片键也设成 username，分片路由就和业务路由同构——一个登录请求带进来的 username，既能定位它的缓存和锁，也能定位它的数据落在哪个库、哪张表。反过来，如果分片键换成 id，这些已经带着 username 的路径就必须先想办法把 username 换成 id，再多吃一次查询或者一次广播 [E14]。

`t_passenger` 同样按 username 分片，理由是一致性覆盖："乘车人总是跟着某个会员查询，与用户同分片可避免跨库查询" [E14]；对外接口也是按当前用户名发起的 [E6]。这是同一个坐标在相邻表上的延伸。

还有一层是物理可行性：`UNIQUE (username, deletion_time)` 保证未注销时用户名唯一 [E13]，配合哈希取模可以把数据均匀打散 [E2]；文档也把"按用户名哈希天然均匀"列为用户表分片的理由之一 [E12]。

至于代价——按 id 查用户会广播——项目里确实存在这类查询（`queryUserByUserId` 只能扫全部分片），但它不是热点 [E11]。这笔账放到下一节算。

## 换成 id 分片会怎样，以及手机号/邮箱路径如何补偿

把三个候选放在一起比较，差异立刻显出来。

**按 username 分片**：登录、查资料、查乘车人都是单分片命中 [E11][E13][E14]。这是当前方案。

**按 id 分片**：问题不在数据分布，而在入口。登录这个入口只有 username / phone / mail 三种输入，没有 id [E14]；按 id 分片会让登录时的读请求扩散到全部分片 [E14]，历史文档也把这类"按非分片键查询"的后果称为读扩散，并把它列为登录难题的来源 [E18]。文档给出的具体代价形态是 `queryUserByUserId` 只能扫全部分片 [E11]，而广播的规模在分片表清单里是可以数出来的——文档描述为广播到 32 张表查一遍 [E16]。

**手机号 / 邮箱登录路径**：项目没有把 `t_user` 改成多键分片，而是给每条入口单独建一张按各自字段分片的映射表。`t_user_phone` 按 phone 分片，职责是 `phone → username` 以及手机号唯一性；手机号登录时先路由到该手机号所在分片拿到 username，再按 username 路由主表，两次单分片查询、无读扩散 [E15][E12]。`t_user_mail` 同理按 mail 分片 [E12][E16]，查询清单里也把这两张表的存在目的写成"它存在的唯一目的就是按手机号/邮箱查" [E11]。

为什么这是更好的选择，而不是把主表做成复合键？文档显示复合分片键在本项目并非不可行——`t_order` 用了 `user_id + order_sn`、`t_pay` 用了 `order_sn + pay_sn`，前提是"两个维度都是热查询" [E11]。用户模块的形态不同：每条登录路径各自只需要一个键就能唯一命中，把三个入口拆成三张单入口表，换来的是每条路径都保持单分片；代价是表数量增加、注册与改绑手机号/邮箱时要额外维护映射行（这一条是从映射表的职责反推的，不是文档原文）。文档在教学上也建议把"按 id 分片""按 id_card 分片"当反例对比，用来理解分片键由查询入口决定，而不是由主键决定 [E10]。

**关于一份历史文档**：`12306学习开发文档` 里写的是"用户按用户 ID 分片"，并把映射表/广播描述为应对读扩散的手段 [E18]。这与当前设计文档明确写出的"`t_user` 按 username 分片" [E11][E16]、以及表设计说明中 username 标注为分片键 [E13] 是冲突的。回答时应以当前设计为准；那份历史文档的价值在于它把"读扩散"这个代价讲清楚了。

**证据缺口集中说明**：现有材料里没有直接检索到 `shardingsphere-config.yaml` 中 `t_user` 绑定 username 分片键的配置片段，因此"`t_user` 按 username 分片"这一事实主要来自当前设计文档 [E11][E16] 与表设计说明 [E13]；实现层能确认的是分片算法按分片键值计算路由 [E2][E20][E5]，以及项目里存在按 username 哈希取模的工具实现 [E1]。另外历史文档与当前设计在"按 ID 分片"上存在上述冲突 [E18]，如果以历史文档为准，结论会不同。
