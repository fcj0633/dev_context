### 4.2 ⚠ 本次现场捕获了一次规划器 fallback

**步骤 5 的 `search_action_planning r1` 标记为 `src=fallback`，且 `discarded_llm_latency_ms = 11.7s`。**

拆开看就是：

| | |
|---|---|
| LLM #4 实际发出并成功返回 | 11.7s，in=1121 / out=2650 tokens，`success=True` |
| 但它的输出未通过解析/校验 | 于是走 `_fallback_actions`，`decision_source` 记为 fallback |
| 该次调用被标记为 wasted | `discarded_llm_latency_ms` 恰好 11.7s，与该调用耗时一字不差 |

**第二轮的三条查询因此是 fallback 拼接式查询**，而不是规划出来的精准查询：

```
r1 SA6 CODE 两个请求同时购买同一张票时，系统如何避免重复售卖 系统在并发购买同一张票时避免重复售卖的具体
r1 SA7 CODE 两个请求同时购买同一张票时，系统如何避免重复售卖 购买流程中检查票可售状态与标记票已售或扣减票…
r1 SA8 CODE 两个请求同时购买同一张票时，系统如何避免重复售卖 数据存储层对票的唯一性约束或版本控制字段 …
```

（形态是 `_fallback_actions` 的 `原问题 + target + 缺失条件` 拼接，`search_actions.py:229-231`。）

**这正是先前诊断出的那个间歇性缺陷，这次被完整记录下来。** 与之前那次不同的是：
上一回是**证据计划器** fallback，代价是整条请求退化成 1 条泛化需求并最终返回「没有上下文」；
这一次是**第二轮检索动作规划器** fallback，因为 fallback 动作仍然可用，请求照常完成了 —— 但白烧了 11.7s。

**由此可以确认缺陷的两个特征**：一是发生在**两个没有重试的 planner 上**（`EvidencePlanner` 与
`SearchActionPlanner`，见 `evidence_planner.py:72-78`、`search_actions.py:104-108`，
而 `CoverageChecker` 有 `max_attempts=2`、Writer 也有重试）；二是**爆炸半径取决于发生在哪一环**——
在证据计划器上会让整题失败，在第二轮动作规划器上只是浪费十几秒。

### 6.1 四条观察

**1. 并行章节确实生效，且压缩比接近线性。**
Q1 五节 work 45.7s → wall 18.8s（2.43×），Q3 五节 work 40.8s → wall 16.2s（2.51×）。
并发度设 3，两波跑完 5 节，压缩比 2.4–2.5× 与「5 节分 2 波」的理论值一致（5/2 = 2.5）。
**上一批（`03`）三题的 peak 并发都是 1，P0–P2 的并发能力完全没被用到；这一批才真正验证了它。**

**2. 多章节路径的时间重心整个后移了。**
证据链路从 `03` 的 56–65% 降到 11–16%，而 **评审+修订升到 50% 以上**。
换句话说：**多章节路径的代价几乎全部发生在正文写完之后**（评审、修订、二次合成），
而不在「找证据」或「写正文」上。

**3. Composer 被严重低估。**
Q1 的 Composer 两次共 49.4s（33%），Q3 共 52.4s（26%）。
**单看每一个 Composer 调用，都比它编辑的全部章节加起来更贵**（Q1：22.8s vs 18.8s；Q3：33.2s vs 16.2s）。

## 附录 A · Q1 完整回答（5870 字符）

**问题**：详细解释当前购票占座的数据一致性是如何保证的

## 一句话结论：一致性由一条写链路串起四份数据

**结论先给**：当前购票占座的一致性不是靠某个单点机制（一把锁、一个事务）撑起来的，而是靠一条被串行化的写链路，加上一条不变量——“有占用必然对应一笔订单，本次请求没成功就必须不留下任何占用” [E17]。

需要同时对上的其实是四份数据：座位状态、余票数量、车票记录、订单结果，设计文档把它们画成一条互相牵连的关系链 [E16]。但这四者里只有一个锚点：余票不是独立数据源，它是“可售座位”的计数派生出来的展示口径 [E17]；支付结果与取消结果反过来作用于座位状态，再由座位状态决定可售性和余票展示 [E18]。因此真正必须对齐的是座位状态与车票记录、订单结果之间的一致，余票只是它的投影。

保证手段分三层 [E2]：入口先用令牌桶拦掉无票请求，取不到令牌直接失败；接着在占用任一把分布式锁之前完成登录与乘客归属校验，把非法请求挡在锁外；核心段落在锁内执行 `reserveLocally` 完成占座与车票记录写入，提交后才把 `reservationCommitted` 置为真，然后才做缓存失效、远程创建订单这些周边动作。

失败路径同样是这条链路的一部分：订单被拒绝时走 `compensateKnownFailure` 释放座位，而令牌只有在本地事务未提交时才在 `finally` 中归还，避免成功归还与失败归还各做一次 [E2]。释放侧则靠“只把已锁定改成可售”这一条件堵死超卖 [E18]。

## 为什么占座是个一致性问题：四条关系与三道裂缝

上面这条结论之所以成立，前提是占座本身不是单条 SQL 的原子性问题。假设占座就是一句 `UPDATE seat SET status='已锁定' WHERE ...`，看起来它天然原子，写完了不就一致了吗？要看清问题在哪，得先看这一次请求到底牵扯了多少份数据。项目的设计文档把这归结成四条互相牵制的关系：座位状态 ↔ 余票、座位占用 ↔ 购票结果、购票结果 ↔ 订单结果，以及支付/取消结果反过来决定座位状态 [E17][E18]。关系一旦成网，单条 SQL 的原子性就不再等于业务的一致性——它只锁住了网里的一个节点。

第一道裂缝出现在写集合本身。[E16] 的故障表把“座位分配成功但订单创建失败”列为需要原子性的操作，即“占座 + 写车票记录 + 订单创建”三者的结果一致 [E16]。在 ticket 库内部，座位状态与车票记录由同一个本地事务承担：`PurchaseTicketTxService` 的类注释写明“本事务只操作 ticket 数据库” [E10]，因此这两者在同一事务里同生同死。但订单创建并不在这条事务里——这就是第二道裂缝。

第二道裂缝是事务边界管不到的地方。同一处注释紧接着说“远程调用留在编排层，避免网络等待延长行锁持有时间” [E10]。这句话说明取舍的来由：订单创建、通知下游是远程调用，本地数据库事务覆盖不到它们；若为了表面的“一起成功”把它们塞进事务，行锁就要跨越网络等待被持有，占座链路的吞吐会被下游抖动直接拖住。于是“一致性”必须拆成“本地事务保证什么”和“事务提交后靠什么补偿”两件事。

第三道裂缝在余票。余票不是独立事实，它是可售座位计数的派生量 [E17]，派生量可以被缓存，缓存就可能落后于数据库。E5 里占座提交后删除余票缓存，删除抛出异常时只记 warn、等 key 自然过期 [E5]——这恰恰说明这类不一致是被有意容忍的，因为它的后果只是少卖。真正不能容忍的是另一头：[E18] 的对照表把错误从“余票缓存未失效（少卖）”一路排到“座位被错误改成可售（超卖）”，并强调设计重点就是把这最后一行彻底堵死 [E18]。所以三道裂缝的处置并不对称：前两道要靠锁序与事务边界收窄，第三道则必须分成“可容忍的少卖”和“绝不能发生的超卖”来分别设防。

## 从请求到落库：占座写链路的执行顺序

理解了三道裂缝之后，再看一次请求实际如何穿过这条写链路。把这条链路在脑内走一遍，最省力的方式是把它看成一条“漏斗 + 临界区 + 事务”三段式：并发先被挡在门外，再穿过两把分布式锁，再进入一层本地事务，最后才处理那些即便失败也无伤大雅的周边动作。入口是 [E1] 声明的 `PurchaseTicketService.purchaseTickets`，实现落在 [E2]。

进入方法后第一件事不是查数据，而是跑责任链 `TRAIN_PURCHASE_TICKET_FILTER` 做前置过滤，随后才校验 `UserContext` 里的登录态，并限制单笔订单乘车人不超过 5 位，再按席别聚合出 `seatTypeCounts` [E2]。**限流紧跟在参数准备之后**：以 `trainId + departure + arrival + seatTypeCounts` 为键做令牌桶 `takeToken`，拿不到令牌直接抛“列车站点已无余票”，根本进不了后面的锁与事务 [E2]。这一步的职责很明确——把并发量削到写链路能承受的规模之前，不让请求白白去争锁。

真正的临界区在 `reserveLocally` [E4]。注意加锁顺序：先按 `username + trainId` 拿用户锁，锁住“同一个人对同一车次”的并发；再遍历 `seatTypeCounts.keySet()`，对本次涉及的每个席别逐把获取席别锁 [E4]。两把锁都覆盖了整个占座写过程，释放时席别锁逆序、用户锁最后，都在 `finally` 里兜底 [E4]。顺带一提，`loadPassengers` 的乘车人归属校验发生在拿锁**之前** [E2]，这说明设计上刻意不让远程校验的耗时空转在分布式锁里面。

锁内调用 `purchaseTicketTxService.doPurchaseInTransaction`，方法体带 `@Transactional(rollbackFor = Exception.class)` [E3]，这就是事务真正的起点。事务内依次是：加载车次、按出发到达查区间关系、把乘客按席别分组、由 `SeatAllocator` 选座；随后对选中的座位执行条件更新，只把 `AVAILABLE` 改成 `LOCKED`，并用 `affectedRows != seats.size()` 判定是否被别人抢先 [E3]；最后逐条插入 `TicketDO`，组装订单创建请求与补偿请求返回。因此事务提交的那一刻，落库的只有“座位被占 + 车票已写”这两件本地事实，订单还没创建。[E10] 的类注释把这条边界说得很直白：本事务只操作 ticket 库，远程调用留在编排层，避免网络等待延长行锁持有时间。

事务返回后，控制权回到编排层，剩下的动作都在事务之外：[E5] 的余票缓存失效发生在提交之后，而且删除失败只记 warn、靠缓存过期兜底，不会被反灌成占座失败；接着才远程 `createOrder`，失败则走 `compensateKnownFailure` [E2]。`finally` 里还有一处所有权约定：只有本地占座未提交时才归还令牌，提交之后令牌的归还由回调独占 [E2]。

把这串顺序连起来看，锁边界与事务边界并不重合——锁包住了事务和提交，事务只包住本地写；越是可失败、可重试的动作，越被推到临界区之外。

## 原子性与时序：事务边界、锁粒度和提交后动作

执行顺序给出的是动作先后，但一致性还取决于边界画在哪里。原子性由 ticket 库的本地事务提供，而不是分布式事务，而且这个事务边界是被刻意收窄的。

先看锁是怎么进来的。[E4] 的 `reserveLocally` 先取用户锁（用户名 × 车次），再按 `seatTypeCounts` 的 key 逐个取席别锁（车次 × 席别），全部拿到后才进入临界区，`finally` 里按相反顺序先释放席别锁、再释放用户锁。这里要把两层职责分开：锁解决的是「并发进入」——同一用户同一车次串行、同一席别串行，不同席别之间可以并行；事务解决的是「写入原子」。而 [E10] 的类注释把边界写得很直白：调用方已经完成校验并持有用户锁和全部席别锁，本事务只操作 ticket 数据库，远程调用留在编排层，避免网络等待延长行锁持有时间。原因在于事务存活期里被持有的是数据库行锁，一次慢 RPC 的几秒钟会被放大成同一席别上所有请求的等待。所以把远程调用挤出事务，不是代码整洁问题，而是把「锁 + 事务」的临界区压到最短。

临界区内部的动作可以概括成一次状态机推进。[E11] 中 `seatStatus` 取值为 0 可售、1 已锁定、2 已出售，占座就是把 0 改成 1。关键在于更新的前置条件：回滚时只允许把 1 改回 0，绝不允许把 2 改回 0。[E18] 的一致性对照表把这一条单独标出——座位被错误改成可售，对外影响是超卖，修法是「靠只把已锁定改成可售的条件杜绝」。这说明防超卖靠的是更新语句里带原状态的条件，而不是某段 if 判断；只要 WHERE 带上原状态，并发或重试都无法把已售座位释放回可售。这条条件更新正是「有占用必有订单、没成功必无占用」这个不变量在写入侧的落点。

再看提交之后的动作，它们必须发生在事务成功提交之后，否则回滚会把副作用留在外面。[E12] 的延迟关单消息在 `send` 里先判断是否处于事务同步中，是则注册 `afterCommit` 再发，否则直接发；[E8] 的令牌归还走同样路数：先判断 `TransactionSynchronizationManager.isSynchronizationActive()`，有同步就注册 `afterCommit`，没有才立即执行。为什么必须这样切？如果关单消息在提交前发出而事务随后回滚，订单并不存在，消费者却会去关一张不存在的单；如果令牌提前归还而座位占用没落库，令牌就在描述一个并不存在的可售能力，后续请求会按错误余量放行。

跨服务这一段没有分布式事务。[E18] 给出的修法是补偿重推、重试回滚、删除缓存 key、用条件更新堵住超卖——也就是本地事务保证 ticket 库内部原子，跨服务一致性交给幂等 + 补偿 + 延迟消息。这是有意的取舍：边界之内能拿到强一致，边界之外只能做到最终一致。至于补偿重试的具体次数与幂等键如何设计，从现有证据无法确认。

## 失败、超时与取消：兜底路径和它的边界

正常路径之外，失败、超时与取消才是这条写链路一致性的压力测试。正常状态下，占座链路在本地事务提交时落库的是“座位被占 + 车票已写”，订单此刻还不存在；E12 的 afterCommit 语义侧面印证了这一点——延迟关单消息只在事务同步激活时才注册到提交之后发送，无事务则直接发 [E12]。所以“有占用必有订单”不是由那次本地提交兑现的，而是靠提交之后的建单动作加上失败时的补偿共同维持的最终效果。故障，就是从提交之后的这段链路上某一环断掉开始的。

第一类故障：本地占座事务已提交，但远程建单明确失败。此时状态是座位被占、车票已写、订单不存在，业务上正确的结局是整单失败、座位回到可售。系统做的是同步兜底：compensateKnownFailure 调用 ticketCallbackService.cancelCallback(...) 释放座位，成功则 my12306.purchase.compensation.success 计数加一；一旦抛错，计数打到 my12306.purchase.compensation.fail，日志写明“等待恢复任务” [E14]。这说明补偿本身是一次尽力而为的尝试而非保证——它把“没补成功”这件事转成显式的待恢复信号，由外部恢复任务接手。还要注意，cancelCallback 在这里只是接口声明 [E13]，它是否幂等、被重复调用会不会二次释放，从现有证据看不出来。

第二类故障：建单成功但用户不付款或主动取消。这条路径不靠同步补偿，而靠延迟消息推进。关单消息在事务提交时才真正投递（afterCommit 里执行 doSend，若当前没有事务同步则直接发）[E12]，这避免了“订单还没落库就先去关单”的时序倒置。超时触发关单后，订单侧先按 orderSn 查订单明细，若明细为空则只打日志告警、不发起远程调用 [E15]；有明细才把车厢号、座位号、席别组装成 OrderCancelSeatRemoteDTO，远程调 ticketRemoteService.cancelCallback 回滚座位，返回码非成功或抛异常都统一转成 ServiceException 并记录“等待重投” [E15]。因此超时回滚同样依赖重投：一次失败不会让座位永久丢失，但也不会当场回滚。

第三类故障最轻：主流程已提交，只是余票缓存删不掉。evictRemainingTicketCacheSafely 捕获 RuntimeException，只 warn 并注明“等待缓存过期”，不向上抛 [E5]。也就是说余票这个展示口径允许短暂偏旧，靠 TTL 收敛——这和“余票由座位状态派生”的定位是自洽的，缓存不属于一致性义务的承担者。

边界必须说清。以上证据能证明的是三条兜底动作存在及其语义：同步补偿加计数、提交后延迟关单加远程回滚加重投、缓存删除失败降级。证明不了的是更难的重复性问题：历史文档把“服务调用超时但订单实际已创建”和“用户重复提交导致部分数据重复”统一归到幂等键/唯一键与防重提交之下，并标注为“后续技术问题” [E16]——这是计划口径，不是已实现事实。所以只能给条件判断：如果幂等键与唯一约束尚未落地，那么超时重试路径上就存在重复占座的空间，补偿与关单也可能被重复触发，这属于需要进一步确认的区域。换言之，当前兜底保证的是“占用最终会被释放”，而不是“绝不重复占用”。

总体来看，当前购票占座的数据一致性靠的是一条被锁串行化的写链路：它守住“有占用必有订单、没成功必无占用”的不变量，把强一致收在 ticket 库本地事务之内，把跨服务一致性交给提交后动作、补偿、延迟消息与重投，并明确容忍余票缓存的短暂偏旧。

## 附录 B · Q2 完整回答（3608 字符）

**问题**：两个请求同时购买同一张票时，系统如何避免重复售卖

## 为什么"查到了票"不等于"提交时还能买到"

假设两个用户在同一秒点了同一趟车、同一个席别，而余票只剩一张，并且这两次点击之前查询接口都返回过"有票"。如果他们各自拿着这次查询结果去下单，会发生什么？历史链路分析文档已经把这个问题定义清楚了：查询有票只是参考信息，不代表提交时一定有票，购票必须以提交时刻的实际可售状态为准；业务上必须保证绝不因为"用户看到过有票"而超卖，也绝不出现"提示成功但没有座位" [E19]。

这个时间差窗口没法靠"下单前再查一次"消掉，因为查询与占用之间总要花一段时间，两个请求的这两段时间可以重叠。项目的分层结构还让窗口更明显：购票不是一步把座位变成"售出"。设计文档描述的过程是座位先 AVAILABLE → LOCKED 并生成 t_ticket 记录，此时用户尚未付款，所以不能直接 LOCKED → SOLD，需要一个 Order 来记录"已发起购买、等待付款" [E17][E18]。也就是说"座位被占用"和"订单成立"是两个不同时刻，中间还夹着一次跨服务调用。并发重复售卖因此不止一个需要防的点。

当前代码确实把"提交时刻还有没有量"作为硬门槛：purchaseTickets 先取令牌桶令牌，取不到直接抛"列车站点已无余票" [E20]。但这一步只挡住"没量还放进来"，挡不住"两个请求都拿到令牌、都去占同一张座位"。

这里要打断一个常见误解：TrainPurchaseTicketRepeatChainFilter.handler 目前是空实现，注释写明重复购买校验规则未定 [E8]。所以"同一用户重复下单会被拦"在当前代码里并不成立，不能把它算作防重手段。

## 入口准入与座位锁：两个请求怎样被排成先后

核心模型可以压成一句：并发购票不是"先查后改"，而是把同一购票资源的占座操作串行化——入口令牌控制放行量，用户锁与席别锁保证同一车次同一席别的本地占座一次只有一个请求在临界区内。

按数据流拆开看。purchaseTickets 的第一行就是购票责任链 `purchaseTicketAbstractChainContext.handler(TicketChainMarkEnum.TRAIN_PURCHASE_TICKET_FILTER, ...)` [E20]，这个 mark 由 TrainPurchaseTicketChainFilter 提供，它是一个 `AbstractChainHandler<PurchaseTicketReqDTO>` 扩展点 [E2][E21]。所以参数校验、车次校验这类便宜判断可以先于昂贵资源发生，形成快速拒绝的位置。

第二步才是准入：`tokenBucket.takeToken(trainId, departure, arrival, seatTypeCounts)` 返回 false 就抛"列车站点已无余票" [E20]。它按乘车区间和席别数量取令牌，作用是把进入后续逻辑的请求量压到与可售量同量级。

第三步是锁前校验：`loadPassengers(requestParam, username)` 完成乘车人归属检查 [E20]，类注释也明确 admission 和 passenger ownership 检查发生在加锁之前 [E5]。这样无效请求不会占着锁。

第四步才进临界区。reserveLocally 先 `userLock.lock()`，key 由 username 与 trainId 拼出；再对 seatTypeCounts 中每个席别依次取席别锁，key 由 trainId 与 seatType 拼出；然后在锁内调用 `purchaseTicketTxService.doPurchaseInTransaction(...)` 完成本地票事务；释放时席别锁倒序释放，用户锁最后释放 [E3]。

为什么这样就能成立：两个请求若命中同一车次同一席别，第二个会阻塞在席别锁上，直到第一个把本地票事务做完并释放；于是它在临界区内读到的余量，就是它真正用来扣减的那份状态，"检查"与"占用"落在同一个临界区里 [E3]。用户锁再叠一层，让同一用户对同一车次的并发（例如连点两次）也串行 [E3]。

锁的边界同样是设计的一部分：类注释写明座位锁只覆盖本地票事务，订单创建发生在所有锁释放之后 [E5]。把跨服务调用留在锁外，锁持有时间短，吞吐不会随订单服务延迟下坠。粒度上，席别锁按 (trainId, seatType) 划分，不同席别之间不互相阻塞 [E3]，对并发友好。需要说明的是，E3 用的是 `lock()` 即阻塞等待，不是 tryLock；公平性与等待超时在给出的代码中看不到。

## 锁释放之后：订单、补偿与恢复如何兜底

起点状态是：reserveLocally 返回，本地票事务已提交，座位进入 LOCKED 类状态 [E17]，随后 `reservationCommitted = true` [E20]。

第一步是令牌归属转移。finally 块只在 `!reservationCommitted` 时才 returnToken [E20]，也就是说一旦本地占座提交，令牌不再随请求结束归还，而是绑到 reservation 生命周期上，类注释写明它只能由真实的座位释放归还 [E5]。这一步是防超卖的枢纽：如果订单创建失败时顺手还令牌，座位还锁着、令牌却已回到池里，新请求就可能拿令牌去抢一张实际不可售的座位。

第二步清缓存：`evictRemainingTicketCacheSafely(requestParam)` 在创建订单前清掉余票缓存 [E20]，避免后续请求读到过期的"有票"。

第三步创建订单，`createOrder` 调用 `orderRemoteService.createTicketOrder(reservation.orderCreateRequest())` [E1]，刻意在锁外执行，结果分三类。正常返回且 code 成功、data 等于本地 orderSn：计 order.success 并返回 orderSn 与订单明细 [E20]，Controller 也只在代理服务正常返回时计一次成功购票 [E15]。明确失败：走 compensateKnownFailure，通过 `ticketCallbackService.cancelCallback` 释放本地占座，再抛"订单服务拒绝创建订单，座位已释放" [E20][E7]；补偿本身也可能失败，此时计 compensation.fail 并记日志，等恢复任务 [E7]。结果未知：createOrder 捕获 Throwable 后计 `my12306.purchase.order.ambiguous`，明确不释放座位，按 orderSn 等待恢复 [E1]；返回的 orderSn 与本地不一致时同样计 ambiguous 并抛"订单创建结果未知" [E20]。未知时不释放的理由很直接——订单可能已经建好，释放座位等于把一张可能已售的票放回可售池。

第四步是订单侧的幂等核对。`assertSameCreateRequest` 在同一 orderSn 已存在时，比对 userId/username/trainId/departure/arrival 以及每一张票的 carriageNumber/seatNumber/seatType/idCard/amount，不一致就抛"订单号已被其他购票请求占用" [E14]。要注意它拦的是"同一订单号被不同内容复用"，而不是"两个不同订单号卖出同一座位"；后者依赖订座环节自身的唯一性，E14 不提供这个保证。

第五步是恢复线索。`selectRecoverableOrderSns` 按 ticket_status 与 create_time < before 过滤，再按 order_sn 分组取回可恢复的订单号 [E13]。这说明结果不确定的订单最终是靠 t_ticket 的状态与 order_sn 做对账收敛，而不是当场重试。仓库中可见的全局异常处理器把未捕获异常转成 500 "系统异常" [E16]，但它位于 user-services，不能据此断言 ticket-services 的异常响应格式。

仍有几处无法由现有证据确认：重复购买规则最终形态未定 [E8]；恢复任务如何把座位与订单逐条对齐、可疑订单最终如何判定成功或释放，属未解决缺口，只能写成条件判断——如果恢复任务以 orderSn 为线索核对 t_ticket 状态，那么它就能补上跨服务那一段的不确定性。

## 附录 C · Q3 完整回答（5864 字符）

**问题**：详细解释当前订单和支付链路是如何保证幂等的

当前订单与支付链路的幂等，不是靠入口去重，而是靠同一套机制贯穿始终：每一次状态推进都把状态前置条件写进 WHERE 做条件更新，再用影响行数判断“本次是否取得推进权”。拿到推进权的请求才继续改下游数据，拿不到 0 行的请求被当作“已经处理过”，重复请求因此被吸收成“已处理”而不会产生二次副作用；跨服务重试也可以整条链重跑。下面从重复来源、统一手法到具体链路和边界依次展开。

## 链路上的重复从哪来：为什么订单和支付必须先谈幂等

先设想一个没有防护的场景：同一条订单被处理两次会怎样？关单逻辑可能关两次支付单、回滚两次座位，支付回调可能把同一笔订单推进两次。而在这条链路上，"被处理两次"不是小概率意外，几乎一定会发生——重复有四个来源，且都不在订单服务手里。

第一，延迟关单任务本身有两条投递路径。正常路径把 orderSn 放进延迟队列 [E3]；但投递被 try/catch 包住，失败时只记日志，注释写明"投递失败不能影响下单：兜底扫表会覆盖这种情况" [E3]。因此同一条 orderSn 既可能由延迟队列送达，也可能再由兜底扫表补送一次，两条路径叠加就产生重复。

第二，关单任务自身就把重复写进了预期。入口查不到订单时直接返回，注释给出的理由是"延迟消息被重复投递、订单已被清理" [E5]。这说明重复执行属于设计内的正常分支，而不是异常兜底。

第三，支付回调是重推语义。订单侧遇到"订单已支付"时直接返回 true，注释解释为"重复回调：状态已是已支付，直接返回已处理，让支付服务停止重推" [E10]。既然实现者要主动让支付服务"停止重推"，就说明在此之前重推已经发生过，订单侧必须能识别并消化它。

第四，回调入口由 ticket-service 以 HTTP 接口对外暴露 [E9]。外部调用方的超时重试、上游投递的重复语义，都不受订单服务控制。

四点合起来指向同一个判断：重复无法在入口处被消除。因此防护不能押在"调用方只调一次"这个假设上，而必须押在每一次状态推进的那一步——重复请求到来时，由状态前置条件判断它是否已经处理过，把它吸收成"已处理"。这正是整条链路选择条件更新、用影响行数决定"本次是否取得推进权"的原因，也是后面各节展开的基础。

## 统一手法：把判断条件写进 WHERE，用影响行数说话

整条链路的幂等其实只有一个原语：**把状态前置条件写进 WHERE 做条件更新，再用影响行数判断"本次是否取得推进权"**。订单侧、支付侧、票务侧用的是同一套写法 [E11][E17][E20]，围绕它拆开看是四件事。

第一，判断和修改不能分家。票务回调的类注释直接点破了"先查再改"的病灶：查询与修改之间存在并发窗口，两个请求可能都查到"已锁定"，然后先后都去改，把状态改错；把判断条件写进 WHERE，判断与修改就在数据库里原子完成 [E11]。这不是风格偏好，而是把并发控制下沉给数据库的比较语义。

第二，影响行数是"推进权"的凭证，而不是顺带返回的结果。`markOrderPaid` 更新订单时带上 `.eq(OrderDO::getStatus, PENDING_PAYMENT)`，`affectedRows == 0` 就返回 false [E13]；再看它的顺序——只有订单行被改到了，才会继续去改订单明细 [E13]。这说明拿到行数的人才配继续动下游数据，拿不到的人应当原地退场，否则同一笔业务会被两条路径各推一半。

第三，0 行不是错误，是"已经处理过"。`payCallbackOrder` 在 `markOrderPaid` 返回 false 时只打一条 info 日志"订单状态推进未生效，视为已处理"，然后照旧 `return true` [E10]；票务侧的注释也写明影响行数为 0 不抛异常，因为跨服务重试中它就是"已经处理过"的正常语义 [E11]。把 0 行当异常抛出，重试方就会误判为失败而无限重推。

第四，终态本身就是收敛点。状态已是 `ALREADY_PAID` 时直接返回 true 让支付服务停止重推 [E10]；文档里描述的第二次回调同样只是"发现已经处理过 → return true"，不产生任何副作用，因此整条链可以放心重跑 [E18]。重复执行不会把状态推得更远，只会重新落到同一个终态。

这套写法还有一个容易忽略的收益：它不依赖 Redis 之类的中间件，静态可读、离线也能测 [E17]。复习框架把"能说清条件更新 + 影响行数"列为过关标准，同时也提醒它的边界——没有状态可判断的副作用，比如发短信、调外部接口，这套机制管不了 [E20]。记住这条边界，才能判断一段重试逻辑能不能直接套用这个原语。

## 下单与发起支付：订单号作为幂等键的第一道闸门

整条链的前半段并不急着做条件更新，它先解决一个更前置的问题：**同一个请求被重复送达时，能不能在还没产生任何副作用之前就把它识别出来**。因此从下单到发起支付，动作都被安排成"先按订单号找一次，再决定是否写入"。

时序从 `createTicketOrder` 开始。请求进来第一件事是完整性校验：`orderSn`、`userId`、订单明细任一为空就直接抛"订单参数不完整"，避免落下一张没有明细的半成品订单；整个方法带 `@Transactional`，约束的是订单主记录与明细记录的写入 [E4]。校验之后不是立刻插入，而是先 `selectByOrderSn(orderSn)`：若已存在，就走 `assertSameCreateRequest` 判断这是不是同一个创建请求，是则直接返回该 `orderSn`，不再产生第二张订单 [E4]。这一步就是"订单号即幂等键"的第一道闸门——重复请求在这里被吸收成"已处理"，而不是变成第二次写入。

为什么查过之后还要兜一层？因为查询与插入之间存在竞态：两个请求可能同时查到"不存在"。代码对这种情况的处理方式是让唯一约束来串行化，捕获 `DuplicateKeyException` 后再查一次，查到且内容一致就返回同一个 `orderSn`，查不到才把异常抛出去 [E4]。从这段异常分支可以推断，`orderSn` 在存储层承担了唯一键的角色（具体约束定义不在这些片段中，无法确认）。插入主记录之后依次写明细，再投递"20 分钟后检查是否已支付"的延迟任务 [E4]。这里要留意边界：代码注释说明投递会等到事务提交后才真正发出，所以事务的原子性覆盖的是订单与明细的插入，不覆盖这次投递——回滚不会撤回已发出的任务，投递失败也不会回滚订单。

链路进入支付侧时，闸门的形态从"订单号唯一"扩展为"订单号 + 前置状态"。`createPay` 先要求登录态存在，再要求 `orderSn` 非空；随后 `loadOrderDetail` 加载订单并校验归属，不属于当前用户直接拒绝 [E15]。紧接着 `checkOrderCanPay` 做状态前置校验：待支付才放行，已支付抛"订单已支付，无需重复支付"，其余（已取消）抛"订单已取消，无法支付" [E14]。金额由 `sumAmount` 按订单明细在服务端汇总，前端传值一律不采信 [E15][E17]。此时才去按 `orderSn` 找已有支付单：若已存在，已支付的抛异常、已关闭的抛异常，其余复用并返回，绝不新建第二笔；不存在才构造 `PayDO`，用雪花 `paySn` 标识、`orderSn` 绑定、状态置为待支付 [E15]。最后 `buildCashierUrl` 只接收 `PayDO` 生成收银台地址，使支付请求与订单号保持一对一绑定 [E16]。

把这半段放回核心模型看：入口处用的是"订单号作幂等键 + 读后判断 + 唯一约束兜底"，它负责把重复请求挡在副作用之前；正因为第一道闸门已经把重复收敛掉，后续的状态推进才有条件退化为"条件更新 + 影响行数"这一种判断方式。需要说明的是，幂等键是否稳定取决于上游是否为同一笔订单复用同一个 `orderSn`——生成方不在这批证据里，无法确认。

## 回调与关单：状态推进如何做到重复执行不产生副作用

这条支线里每一步的落脚点都是同一个动作：把"当前必须是某状态"写进 WHERE，再看影响行数决定这次要不要继续往下做。按时间顺序走一遍。

支付回调从支付侧进来：`payCallback` [E8] 接渠道回调，`notifyPayResult` [E7] 把结果推给订单侧，订单侧入口是 `payCallbackOrder` [E6]，实现在 [E10]。它先按 orderSn 查订单，查不到直接抛异常——这不是重复，是数据异常；查到后第一件事是看状态：已是"已支付"就 `return true`。这一步的职责不是更新，而是让支付服务停止重推——返回 true 对上游意味着"已处理"，重推循环在此收敛。若状态是"已关闭"却收到支付成功，[E10] 同样返回 true，但打 error 日志留人工核对（真实场景要退款，此处标注为 P3）。

只有既非已支付、也非已关闭，即处于待支付时，才轮到 `markOrderPaid` [E13]。它的更新条件带 orderSn 与 status=待支付，影响行数为 0 就返回 false。注意 false 不是失败：调用点把它记为"状态推进未生效，视为已处理" [E10]。为什么可以这样理解？因为影响行数为 0 只可能意味着别人已经推进过——条件更新把判断与修改压进同一条 SQL，不存在两个线程都读到待支付再都去改的窗口。也正因如此，订单明细的更新被放在拿到推进权之后才执行 [E13]，重复的那一次根本走不到那里。

票务回调的时序同形：`payCallback` 先以 orderSn 把车票从"未支付"推进，只有取得推进权的回调才继续改座位；座位的推进条件是"已锁定"，推不动就回滚本次车票状态变更 [E11]。它把"影响行数为 0 不抛异常"写成公开语义——在跨服务重试里这就是"已经处理过"。

关单时序更长。`closeTimeoutOrder` 先判空，再查订单：订单不存在（延迟消息重投、订单已清理）直接 return [E5]。查到后先看是否已支付——已支付就返回，绝不关单、也绝不回滚座位 [E5]，这是整条支线里最不能退让的一步。只有待支付才调用 `closePendingOrder` 推进本地状态 [E5]。

关键在最后两步：无论本次是否真的推进了状态，`closePayOrder`（最终落到支付侧 `closePayByOrderSn` [E2]）与 `rollbackTicketSeats` 都会执行 [E5]，对应订单侧关单接口 `closeTicketOrder` [E1]。为什么不做成"只有推进成功才执行"？因为下游可能已经成功、只是确认丢了；这两个动作本身幂等，重做不产生二次伤害，却能保证最终一致。重复执行在这条链上的统一表现就是：前面各步的影响行数先变成 0，后面的补偿步骤照走一遍，然后再无变化。

## 边界、失败情形与取舍：这套机制管不了什么

这套幂等机制的能力，完全取决于一件事：**状态里能不能看出"这一步已经做过"**。条件更新之所以成立，是因为有待支付、已支付、已关闭这样的前置状态可以写进 WHERE；一旦某个副作用在数据库里找不到对应的状态字段可以判断，它就不在这套机制的覆盖范围内——发短信、调外部接口这类动作，重复执行不会因为影响行数为 0 而被吸收，机制管不了它们。这是它的适用边界，也是复习框架里把"没有状态可判断的副作用它管不了"列为过关标准的原因 [E20]。

正因为边界清楚，链路里那些看起来"反常"的顺序才是有意为之。`OrderStateService` 类注释直接写明：**本地状态必须比跨服务通知先提交**，并把"改本地状态"抽成独立事务方法，重试时靠"条件更新 + 影响行数"判断是否已经推进过 [E12]。代价是失败时本地与下游会短暂不一致；收益是避免两个更糟的后果：关单链路的后两步（关支付单、回滚座位）是跨服务调用，若与本地关单放进同一事务，下游一失败本地关单就被回滚，重试要从头再来；更严重的是座位一旦释放而订单状态还没落定，就会出现"座位已释放、订单仍可支付"的超卖窗口 [E12]。

同样的取舍出现在支付侧：支付成功后的下游通知失败不回滚支付单，只把通知状态置为未完成，交给补偿任务重推 [E17]。支撑这种"敢重推"的，正是核心模型里那条把重复请求吸收成"已处理"的逻辑——文档把它总结为：幂等的价值之一，就是让失败重试不必精确记录"上一次执行到了第几步"，因此可以整条链重跑 [E18][E19]。可以想象一种没有这层保护的写法：补偿任务必须维护一张"执行进度表"，每一步的推进都要精确落盘，进度与真实状态一旦错位就再也对不齐。

但重跑能对齐的是"可判断的状态"，不是"所有异常"。订单已关闭却收到支付成功回调时，代码只能记一条 error 日志并返回 true，注释明确写着这属于需要人工介入的异常（真实场景要退款），退款处理属后续范围 [E10]。这里要特别澄清 return true 的语义：它不是"支付已被受理"，而是"我收到了，别再重推"；已支付状态下重复回调返回 true 也是同一含义——让支付服务停止重推 [E10]。也就是说，这套机制保证的是**不重复产生副作用**，不保证**异常终态被自动纠正**，后者仍需人工介入或后续补偿方案。

至于为什么最终没有抽一个统一的 `@Idempotent` 组件，复习框架只把这个问题列为待填充的取舍项 [E20]，现有证据无法确认其结论。能确认的相邻取舍是：支付侧的状态推进不依赖 Redis，用条件更新加影响行数实现，因此离线也能测 [E17]——这本身也划出了边界，它换来的简单性，代价是把幂等责任分散在每一个写状态的方法上。

整条链路的答案可以收束为一句话：重复无法在入口被消灭，只能在每一次状态推进处被识别；只要状态可判断，条件更新与影响行数就能把重复请求收敛到同一终态，而无法判断的副作用仍要交给人工或补偿。
