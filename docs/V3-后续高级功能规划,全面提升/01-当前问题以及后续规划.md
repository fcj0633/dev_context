# 四、ExplanationPlan 应该是什么

例如用户问：

```text
详细解释项目的余票桶是如何设计的
```

EvidencePlanner 负责回答：

```text
需要确认哪些事实？
```

例如：

```text
ER1 余票桶是什么
ER2 Redis 数据结构
ER3 初始化
ER4 扣减
ER5 归还
ER6 一致性
```

这些没有问题。

但 ExplanationPlanner 应该输出完全不同的东西：

```json
{
  "user_goal": "理解为什么需要余票桶，以及它如何在不成为真实库存的情况下削峰",
  "core_mental_model": "Redis 是准入凭证，MySQL 才是真实库存",
  "reader_assumption": "知道 Redis 和事务基础，但不熟悉高并发库存设计",

  "confusions": [
    "为什么 Redis 有余票还不能代表真的有票",
    "为什么不能直接 Redis 扣库存",
    "为什么失败后需要归还",
    "为什么宁可偏松不能偏紧"
  ],

  "narrative": [
    {
      "type": "problem_setup",
      "goal": "先说明没有令牌桶会发生什么"
    },
    {
      "type": "mental_model",
      "goal": "区分准入库存与真实库存"
    },
    {
      "type": "mechanism",
      "goal": "解释 Hash + Lua + 懒初始化"
    },
    {
      "type": "failure_scenario",
      "goal": "解释扣令牌后 DB 失败"
    },
    {
      "type": "tradeoff",
      "goal": "解释偏松优于偏紧"
    }
  ]
}
```

注意：

**这和 EvidencePlan 是两回事。**

EvidencePlan 是：

> 我要查什么。

ExplanationPlan 是：

> 我应该按什么认知顺序讲。

这是当前系统缺的关键抽象。

# 五、建议正式把系统拆成“两张图”

这是我认为 DevContext 后面最值得讲的设计。

## 1. Evidence Graph

> **事实是什么？**

节点：

```text

文档
方法
类
配置
SQL
测试
设计说明
```

关系：

```text
CALLS
IMPLEMENTS
EXTENDS

```

并附带：

```text

```

---

## 2. Explanation Graph

解决：

> **这些事实应该怎么解释？**

节点不是代码，而是：

```text
Problem
Concept
Mechanism
Reason
Example
CounterExample
FailureCase
Tradeoff
Boundary
Summary
```

例如：

```text
高并发导致无效请求进入 DB
            ↓
为什么需要准入层
            ↓
Redis Token Bucket
            ↓
为什么 Redis 不是最终库存
            ↓
MySQL 条件更新
        ↙          ↘
 DB失败          Redis失效
   ↓                ↓
归还token         降级放行
```

最后 Writer 遍历 Explanation Graph 写答案。

这会形成非常漂亮的面试设计：

> **DevContext 不直接把检索结果喂给模型，而是先构造 Evidence Model，再根据用户认知目标生成 Explanation Plan，最后在事实约束下生成答案。**

这比：

> “我用了 Hybrid Search + Query Rewrite”

强很多。

# 十六、回答质量方面还有一个很重要的设计：Fact 与 Teaching 必须分层

这能解决你“想达到 ChatGPT 解释能力”与“RAG 必须严格有依据”之间的冲突。

ChatGPT 回答里用了大量假设案例：

```text
10 张票
50 个用户
```

这些不是项目代码中的真实数据。

但它们非常有助于理解。:chatgpt-content-reference{index="6"}

DevContext 现在过于害怕“没有证据”，所以容易变成：

> 类注释是什么  
> 方法是什么  
> Key 是什么  
> 配置是什么

解决方法不是解除 Grounding。

而是把内容分三类：

```text
PROJECT_FACT

DERIVED_EXPLANATION

ILLUSTRATIVE_EXAMPLE
```

例如：

```text
[PROJECT_FACT]
takeToken 在获取分布式锁前调用。

[DERIVED_EXPLANATION]
因此它承担的是前置准入，而不是最终库存校验。

[ILLUSTRATIVE_EXAMPLE]
假设还有 10 张票但有 50 个请求，
它可以让大量无意义请求在进入锁竞争前快速失败。
```

第三部分不需要声称：

```text
项目真实发生了 50 个请求。
```

只要明确：

> “假设”。

这样既能有 ChatGPT 的教学能力，又不会破坏项目事实约束。

# 二十五、关于 RAGFlow、Continue、Aider、OpenHands，真正值得抄的是什么

不是抄代码，而是抄设计思想。

**Continue：Tool-first codebase awareness。**  
当前推荐让 Agent 通过文件探索、代码搜索、Git 等工具主动理解代码，而不是所有问题都依赖静态 Codebase RAG。:chatgpt-content-reference{index="10"}

**Aider：Repo Map。**  
利用 Symbol + Dependency Graph，从整个 Repository 中压缩出最重要的结构信息，在 token budget 内给模型全局认识。:chatgpt-content-reference{index="11"}

**RAGFlow：Retrieval 是 Agent Tool，不是 Agent 本身。**  
它的 Agent workflow 可以把 Retrieval 与条件分支、HTTP、数据库、MCP、循环等能力组合。:chatgpt-content-reference{index="12"}

**OpenHands：Reasoning-Action + Tool + Context Management。**  
它把 Agent 核心职责明确拆成 reasoning-action loop、tool orchestration、context management 等，并强调状态和组件边界。:chatgpt-content-reference{index="13"}

DevContext 不需要做到它们的规模。

应该抽出：

```text
Continue     → Tools
Aider        → Repo Map / Graph
RAGFlow      → Workflow
OpenHands    → Agent Runtime 思想
DevContext   → Grounded Explanation
```

最后形成你自己的组合。

# 二十六、这五天之后项目的定位应该重新写

现在 README 第一印象是：

> Structure-aware hybrid retrieval for Java source and Markdown documentation.

这已经不够了。

我建议未来定位为：

> **DevContext is an evidence-driven code intelligence agent for understanding large Java projects. It combines structured code indexing, hybrid retrieval, symbol/call graphs, tool-driven investigation, grounded explanation, multi-turn sessions, and evaluation to answer not only “where the code is”, but also “how it works, why it is designed this way, and what will be affected by a change.”**

中文可以讲成：

> **DevContext 是一个面向 Java 工程的证据驱动代码理解 Agent。系统通过 JavaParser 建立结构化代码索引和 Symbol Graph，结合关键词、向量和图检索，由 Agent 根据问题动态调用代码搜索、Symbol 查询、引用分析和调用链工具，形成 EvidencePackage；随后通过 Explanation Planner 将项目事实转化为适合开发者理解的心智模型、因果链和失败场景，并输出可追溯回答。同时支持多轮项目问答、调用链追踪、影响分析、增量索引和分层自动评测。**

这和现在的：

> RAG + 几层检索控制

已经是完全不同的项目叙事。

# 二十七、面试时真正能讲的 6 个核心技术问题

最终应该确保自己能完整回答：

```text
1. 为什么普通向量 RAG 不足以理解大型代码仓库？

2. 为什么需要 Symbol Graph？
   它和 Vector Retrieval 分别解决什么问题？

3. Agent 如何决定 search / symbol / reference / graph 工具？

4. 如何防止 Agent 无限搜索？
   Coverage、MAX_TOOL_STEPS、EvidencePackage 如何控制？

5. 如何同时做到：
   回答像 ChatGPT 一样容易理解
   +
   不对项目事实产生幻觉？

6. 当代码变化时，
   如何保证 Chunk、Embedding、Symbol Graph 一致更新？
```

如果这六个问题能讲清楚，DevContext 的面试价值会明显高于继续把 Recall@5 从某个数字调高几个百分点。

## 最后给你的开发优先级

如果五天时间非常严格，我会按这个优先级执行：

**第一优先级：Explanation Planner + 教学型回答。**  
这是目前最明显、用户实际能感知到的问题。

**第二优先级：Symbol Graph + Repo Map。**  
这是项目从“RAG”升级成“Code Intelligence”的关键。

**第三优先级：Tool-driven LangGraph Agent + Trace/Impact。**  
这是项目从“复杂检索流程”升级成“真正 Agent”的关键。

**第四优先级：Multi-turn + Web Trace。**  
让能力真正可展示。

**第五优先级：Incremental Index + L3 Evaluation。**  
把 Demo 提升为一个工程化项目。

我不建议下一步继续把主要开发时间投入到“第三轮 Retrieval、更多 Query Rewrite、Top-K 微调、再加一个 Sufficiency Checker”。**当前 Retrieval 已经足够成为基础设施了，接下来应该让它服务于更高级的 Code Intelligence 和 Agent 能力。**
