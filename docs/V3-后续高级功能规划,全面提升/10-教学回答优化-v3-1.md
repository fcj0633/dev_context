# 一、先冻结这次重构的目标

这次不是修改 `MicroExplanationPlanner` 的几个 Prompt，而是重新设计回答模块的主链路。

目标架构固定为：

```text
Frozen EvidencePackage
        │
        ▼
┌────────────────────────┐
│  Teaching Planner V3   │
│  1 次 LLM              │
│  决定“怎样让用户理解”   │
└───────────┬────────────┘
            │
      Teaching Blueprint
            │
            ▼
┌────────────────────────┐
│ Evidence Organization  │
│ 0 次 LLM               │
│ 为 Writer 整理证据      │
└───────────┬────────────┘
            │
      Writer Evidence Pack
            │
            ▼
┌────────────────────────┐
│ Teaching Writer V3     │
│ 1 次 LLM               │
│ 执行教学计划            │
└───────────┬────────────┘
            │
            ▼
┌────────────────────────┐
│ Deterministic Validate │
│ 0 次 LLM               │
└───────────┬────────────┘
            │
            ▼
        Final Answer
```

第一版严格限制：

```text
支持：
WHY
HOW

暂不支持：
WHAT / COMPARE / DEBUG / LOCATE 的专门优化

默认：
1 个 Worked Scenario

正常：
2 次 LLM

禁止：
Section Writer × N
Composer
在线 Reviewer
全文 Revision
Mechanism Agent
Learner Model
Planner ↔ Retrieval 循环
```

性能目标：

```text
目标：< 120 秒
硬上限：< 180 秒
```

# 二、这套设计真正依赖哪些研究

不是所有研究都要照搬，真正和项目有直接关系的主要是六条。

| 研究 | 得出的设计原则 |
|---|---|
| LearnLM | 不要假定通用模型天然会“教学”，要明确规定 pedagogical behavior |
| STORM | 正文生成前先完成知识组织和写作规划 |
| Self-explanation | 重点解释原因、条件、步骤之间关系，而不是复述事实 |
| Cognitive Load / Worked Example | 降低无关搜索，让学习者沿完整步骤形成 schema |
| RAGChecker | 检索到证据不够，还要控制 Context Precision / Utilization |
| Lost in the Middle | 不能把全部 Evidence 堆给 Writer，位置和组织会影响使用效果 |

LearnLM 的研究尤其重要：研究者明确指出，通用生成模型默认倾向于“present information”，而不是像导师一样围绕学习目标教学，因此他们把问题重新定义成 **pedagogical instruction following**。这直接支持我们用严格 Teaching Blueprint 约束 Writer，而不是只写一句“请详细解释”。:chatgpt-content-reference{index="1"}

STORM 则说明复杂长回答的 pre-writing 本身应该成为独立阶段：先整理信息、形成 outline，再进入正文生成；其文章组织性相较 baseline 有明显提升。:chatgpt-content-reference{index="2"}

Self-explanation 研究表明，学习效果更好的学习者会主动解释“为什么步骤成立”“成立需要什么条件”，并把具体步骤连接到一般原理。:chatgpt-content-reference{index="3"}

Cognitive Load 研究强调复杂任务的困难来自大量**相互作用的信息元素**同时占用工作记忆；part-whole、worked examples 等方法的价值，就是逐步增加关系并减少无效搜索。:chatgpt-content-reference{index="4"}

所以：

> **新回答模块不能继续把“章节短、术语少、字数受限”当作主要教学优化。真正应该控制的是用户每一步需要建立的关系。**

# 三、当前实现中什么应该保留，什么必须重构

我重新看了当前 `codex/teaching-answer-v2`。

目前 `micro.py` 的核心规划结构仍然倾向于：

```text
direct_answer
core_mental_model
question_kind
likely_misconceptions
sections
    ├── reader_takeaway
    ├── new_terms
    ├── key_points
    ├── evidence_labels
    └── target_chars
```

并且存在：

```text
每节 100～250 字
1～3 key_points
0～2 new_terms
detailed 6～9 sections
```

这些规则能够改善格式，但无法保证：

```text
A 为什么存在
A 解决什么
A 为什么还不够
为什么需要 B
B 与 A 的职责区别是什么
```

所以它更接近：

> **Content Outline**

而不是我们现在需要的：

> **Learning Path。**

---

当前 `stream_writer.py` 反而有不少东西值得继续保留：

```text
SectionParser
严格 section marker
严格顺序
Citation allowlist
引用合法性检查
streaming 输出
首段产生后不整篇 replay
```

这些都是成熟的工程基础。

所以不要把整个现有模块推倒。

真正需要重构的是：

```text
旧 MicroPlanner
        ↓
新的 Teaching Planner V3

旧 Writer Contract
        ↓
新的 Controlled Teaching Writer V3
```

而：

```text
SectionParser
Citation Validator
EvidenceWorkspace
E1/E2稳定证据编号
streaming machinery
performance trace
```

应该继续复用。

# 四、整个回答模块真实执行流程

最终一次请求进入回答模块以后，应该发生这些事情：

```text
Frozen EvidencePackage
        ↓
STEP 1  准备 Planner Evidence
        ↓
STEP 2  Teaching Planner
        ↓
STEP 3  Plan Validation
        ↓
STEP 4  Evidence Organization
        ↓
STEP 5  Build Writer Prompt
        ↓
STEP 6  Single Streaming Writer
        ↓
STEP 7  Section Validation
        ↓
STEP 8  Finalize Answer
```

下面逐个研究。

---

# 五、STEP 1：Planner 输入准备

## 目标

不要直接把整个 Workspace 原封不动地丢给 Planner。

Planner 真正需要的是：

```text
Question

Answer Options

Evidence Plan

Coverage

Current / Historical / Conflict

Evidence 内容
```

Planner 必须知道：

```text
有什么事实

哪些事实确认了

哪些只是部分确认

哪些地方仍然未知
```

否则后面很容易为了得到漂亮的教学结构，自己填补 Evidence 缺口。

---

## 实现思想

目前 `_payload()` 已经提供：

```text
question
answer_options
evidence_plan
requirement_coverage
retrieval_state
available_citations
evidence
```

这个基础其实很好。

第一版可以继续使用。

不要在这里进行新的智能化。

---

## 需要改变的一点

Planner 不应该把：

```text
EvidenceRequirement
```

直接当作：

```text
Teaching Section
```

例如检索规划：

```text
ER1 并发控制
ER2 数据更新
ER3 补偿
```

只是：

> “为了回答问题，需要查什么。”

它绝对不代表：

> “用户应该按什么顺序理解。”

这两层必须彻底分开。

---

# 六、STEP 2：Teaching Planner V3

这是整个重构最重要的模块。

Planner 不应该直接从：

```text
Evidence
→ Sections
```

而应该走内部逻辑：

```text
Evidence
   ↓
Question Type
   ↓
Learning Goal
   ↓
Minimal Mental Model
   ↓
Cognitive Spine
   ↓
Critical Distinctions
   ↓
Worked Scenario
   ↓
Knowledge Boundaries
   ↓
Answer Structure
```

注意：

> 这些是一次 LLM 调用里的逻辑步骤，不是八次模型调用。

---

# 七、Planner 第一步：只判断 WHY / HOW

第一版明确不要为了“通用性”支持六种 question kind。

只支持：

```text
WHY
HOW
```

对于这两个测试问题：

### WHY

> 为什么订单关闭使用延迟队列，而不是只使用定时轮询？

### HOW

> 当前购票占座的数据一致性是如何保证的？

---

## WHY 与 HOW 本质不同

WHY 的核心问题是：

```text
为什么这个设计存在？
```

所以它应该建立：

```text
Goal / Constraint
        ↓
Alternative
        ↓
Problem with Alternative
        ↓
Chosen Design
        ↓
Why It Solves the Gap
        ↓
Tradeoff / Boundary
```

HOW 的核心是：

```text
系统如何从状态A走到状态B并保持正确？
```

所以：

```text
Initial State
        ↓
Mechanism A
        ↓
State Change / Guarantee
        ↓
Remaining Gap
        ↓
Mechanism B
        ↓
Failure Path
        ↓
Final Invariant
```

如果两个问题使用完全同一个 Template，第一版就已经设计错了。

---

# 八、Planner 第二步：Learning Goal

这是最容易被低估、但非常重要的阶段。

模型不能只被要求：

> “生成学习目标。”

因为很容易生成：

```text
了解延迟队列的设计和实现。
```

这种目标几乎没有价值。

---

## Learning Goal 的正式定义

应该是：

> **回答结束以后，用户应该能够解释、区分或重建什么？**

### WHY

必须回答：

```text
用户最后能否解释：

1. 当前设计解决什么问题？
2. 一个直觉方案为什么不够？
3. 当前方案为什么有效？
4. 当前方案牺牲了什么？
```

例如：

```text
让用户理解订单超时关闭同时面对
“触发及时性”和“持续扫描成本”两个约束，

理解只使用定时轮询为什么难以同时优化二者，

以及延迟消息为什么能够改变这一问题，
同时理解定时扫描为什么仍可能作为兜底存在。
```

---

### HOW

必须让用户最终能：

```text
重建：
系统从初始状态到最终状态的主要过程

并解释：
每一个核心机制具体保证什么，
为什么上一机制不足以代替下一机制。
```

Q1 可以变成：

```text
让用户理解购票一致性不是由一个机制完成，

而是：
串行化
→ 状态裁决
→ 本地原子性
→ 跨服务收敛

分别解决不同层级的问题。
```

---

## 为什么研究支持这样做

LearnLM 的一个核心思想就是：

> 教学行为需要围绕明确 pedagogical goal 被显式指定，而不能期待模型自己从普通 QA Prompt 中推导出来。:chatgpt-content-reference{index="5"}

所以 Learning Goal 不是装饰字段。

它应该成为整个 Planner 的：

# Optimization Target。

---

# 九、Planner 第三步：Minimal Mental Model

这里应该做一次非常重要的压缩：

```text
大量项目事实
        ↓
少数真正重要的关系
```

例如：

```text
Redisson
PurchaseTicketServiceImpl
SeatMapper
@Transactional
TicketCallback
Redis TokenBucket
OrderClient
...
```

不能成为用户的 mental model。

Q1 应该提炼成：

```text
Admission
Serialization
State Validation
Local Atomicity
Cross-service Convergence
```

其中甚至：

```text
Admission
```

还应该被标记成：

```text
performance / protection
```

而不是 correctness 核心。

---

## 这里的质量标准

一个好的 mental model：

### 1. 可以脱离具体代码理解

删掉 Java 类名后仍然成立。

### 2. 足够少

通常：

```text
3～5 个核心关系
```

而不是 10 个组件。

### 3. 可以用于推理

用户可以用它回答：

> “如果把 Transaction 去掉，会失去哪种保证？”

这才说明形成了 model。

---

# 十、Planner 第四步：构造 Cognitive Spine

这是整篇回答的“内部因果骨架”。

## WHY Spine

第一版固定为：

```text
目标 / 约束
      ↓
最直觉的方案
      ↓
为什么不够
      ↓
当前设计
      ↓
设计改变了什么
      ↓
为什么因此有效
      ↓
仍然有什么代价 / 边界
```

---

## HOW Spine

第一版固定为：

```text
初始问题 / 状态
      ↓
Mechanism A
      ↓
A 改变了什么
      ↓
A 保证什么
      ↓
A 还没保证什么
      ↓
Mechanism B
      ↓
...
      ↓
Failure Handling
      ↓
Final Invariant
```

---

# 十一、为什么 Spine 必须这么设计

Self-explanation 的经典研究表明，真正促进深层学习的行为并不是复述操作，而是解释操作与原理的关系、条件和原因。:chatgpt-content-reference{index="6"}

所以：

```text
Lock
Transaction
Compensation
```

不是一个好的骨架。

而：

```text
Lock
解决并发执行

但是：
不保证数据库状态合法

所以：
Conditional Update
```

才是。

---

# 十二、Spine 的四条强校验规则

第一版应该把以下规则写进 Planner Prompt，并部分做程序校验。

### 规则 1：禁止纯名词步骤

差：

```text
Redis
Lock
Transaction
RocketMQ
```

好：

```text
先把竞争请求串行化
真正写库时验证状态
让多个本地写共同提交
处理事务外失败
```

---

### 规则 2：相邻步骤必须有关系

应该存在：

```text
前一步解决什么
↓
还缺什么
↓
下一步为什么存在
```

不能只是主题切换。

---

### 规则 3：每一步必须产生 Learning Delta

例如：

```text
Before:
有锁就不会超卖

After:
锁只负责串行化，
数据库仍需做状态验证
```

如果没有这种理解变化，这一步不是核心教学步骤。

---

### 规则 4：Evidence 不支持时必须停止

不能为了构造完整：

```text
A → B → C
```

自动发明 C。

---

# 十三、Planner 第五步：Critical Distinctions

第一版只允许非常少：

```text
最多 2～4 个
```

Q1：

```text
Lock ≠ Idempotency

Serialization ≠ State Validation

Conditional Update ≠ Transaction

Token Bucket ≠ Final Inventory Truth
```

不是让 Writer单独写四个章节。

而是让 Writer 写到相关位置时：

> 不能把两者混成一个概念。

---

# 十四、Planner 第六步：Worked Scenario

第一版按照你的要求：

> **默认使用。**

但 WHY 和 HOW 使用方式不同。

---

## WHY Scenario

应该是：

# Counterfactual Scenario

例如：

```text
一个订单 10:00 创建，
10:30 超时。

如果只用定时轮询：

扫描间隔很大
→ 关闭不及时

扫描间隔很小
→ DB持续承担扫描成本
```

然后：

```text
Delay Message
```

出现。

Scenario 的作用是：

> 把设计选择变成可以观察的 tradeoff。

---

## HOW Scenario

应该是：

# State Trace

例如：

```text
只剩最后一个座位

A 和 B 同时购买
```

然后一路跑：

```text
A/B进入
↓
Lock
↓
DB条件更新
↓
Seat + Ticket transaction
↓
Remote Order
↓
Compensation
```

---

## 为什么默认 Scenario 有研究依据

worked-example 研究认为，完整示范能减少学习者在“自己寻找解决路径”上的额外负担，让工作记忆更多地用于理解步骤和构建 schema；对于复杂认知任务尤其明显。:chatgpt-content-reference{index="7"}

但研究同样提醒：

> example 本身也必须被良好组织，否则一样可能造成 cognitive overload。:chatgpt-content-reference{index="8"}

所以 Scenario 必须：

```text
简单
一个
贯穿全文
不引入额外项目事实
```

---

# 十五、Planner 第七步：Knowledge Boundary

这个步骤是 Teaching 和 Grounding 的交界。

Planner 必须明确：

```text
哪些结论：
CONFIRMED

哪些：
可以基于 Evidence 推断

哪些：
当前 Evidence 不能确认
```

例如：

```text
确认：
存在补偿路径

不能确认：
补偿是否拥有完整业务幂等键
```

后面 Writer 不能越界说：

> “该补偿可以保证任意重试安全。”

---

# 十六、Planner 第八步：Answer Structure

这是目前最容易“看起来优化了，但实际没有”的地方。

不能：

```text
Spine Step 1 → Section 1
Step 2 → Section 2
...
```

机械映射。

因为：

> Cognitive Spine 是内部理解结构。

> Answer Structure 是用户阅读结构。

---

# 十七、WHY 最终回答结构

第一版建议固定：

```text
1. 直接给核心原因

2. 这个设计真正面对什么问题

3. 如果不用它，会怎样

4. 当前机制为什么有效

5. 为什么它还不是完整答案

6. 项目代码如何落实这个设计

7. 一句话抽象设计思想
```

注意：

章节标题不要变成：

```text
延迟队列
定时任务
消费者
```

应该：

```text
为什么单靠定时扫描不够？

延迟消息究竟改变了什么？

既然有延迟消息，为什么还需要兜底？
```

标题本身成为理解线索。

---

# 十八、HOW 最终回答结构

第一版：

```text
1. 先给整体 Mental Model

2. 建立初始问题 / 状态

3. 顺着 Cognitive Spine 展开核心机制

4. Scenario 与每一步同步推进

5. 正常路径理解后再进入 failure path

6. 抽象出 1～2 个通用设计原则

7. 最小总结
```

不要：

```text
Lock一章
Transaction一章
Cache一章
Callback一章
```

---

# 十九、为什么不能让 Answer Structure 流于表面

真正应该控制的是：

> 每个 Section 有一个唯一的 **Learning Delta**。

例如：

### Section

> 有锁以后，为什么数据库还要判断一次？

用户读之前：

```text
Lock = 不超卖
```

读之后：

```text
Lock = Serialization
DB Conditional Update = State Arbitration
```

这个 section 就有价值。

而：

> “分布式锁”

只描述 Topic。

---

# 二十、Planner Prompt 的实际设计

不要写成 100 条平铺规则。

建议分 6 层。

```text
[1] ROLE

你是 Teaching Planner。
你不写最终答案。
你的任务是构造用户的学习路径。


[2] GLOBAL OBJECTIVE

最终计划必须让 Writer 能够解释：
为什么？
如何？
以及各机制之间的关系。


[3] WHY CONTRACT

固定 WHY planning 方法。


[4] HOW CONTRACT

固定 HOW planning 方法。


[5] GROUNDING CONTRACT

不得超越 Evidence。


[6] OUTPUT + DEMONSTRATIONS

严格结构
+
WHY example
+
HOW example
```

---

# 二十一、为什么必须加入 Few-shot Examples

这里不是为了教模型项目知识。

而是为了：

> **限制模型行为分布。**

Min 等人在 EMNLP 2022 的研究发现，demonstration 的作用不只来自“正确答案”，它还给模型提供了 label space、输入分布和输出格式信息。:chatgpt-content-reference{index="9"}

所以对于 Planner，我们应该给：

```text
WHY 好计划示例
HOW 好计划示例
```

并且同时给很短的：

```text
bad → good
```

对比。

例如：

### BAD HOW

```text
1. 分布式锁
2. MySQL更新
3. Transaction
4. 补偿
```

### GOOD HOW

```text
并发竞争
↓
先串行化

但是状态仍需由数据库裁决
↓
Expected-state update

但是多个本地写仍可能部分成功
↓
Transaction

但是远程调用不在事务内
↓
Compensation
```

这比继续增加 20 条 Prompt Rule 更容易固定模型行为。

---

# 二十二、STEP 3：Plan Validation

正常：

```text
0 LLM
```

只检查硬问题。

包括：

```text
Question Type 是否 WHY/HOW

有没有 Learning Goal

Mental Model 是否为空

Spine 是否为空

Evidence Label 是否存在

Boundary Evidence 是否存在

Answer Structure 是否覆盖核心 Spine

Scenario 是否存在

是否出现明显纯组件列表结构
```

---

## 不做什么

程序不要试图判断：

> “这条 Cognitive Spine 教学质量是不是 9/10。”

这种留给 offline evaluation。

否则又要引入 Reviewer。

# 二十三、STEP 4：Evidence Organization

RAGChecker 的研究说明，Retriever 的 Recall 高并不足够；Context Precision、Generator 对 context 的利用同样影响最终 RAG 质量。:chatgpt-content-reference{index="10"}

而 `Lost in the Middle` 表明，即使模型拥有足够长的上下文，重要信息的位置仍然会显著影响利用效果。:chatgpt-content-reference{index="11"}

所以不能：

```text
Planner用了 E1-E12
↓
把 E1-E12 按检索顺序全部塞给 Writer
```

---

# 二十四、Evidence Organization 应该做四件事

## 1. 根据 Spine 重新绑定 Evidence

从：

```text
Retrieval Requirement → Evidence
```

转换成：

```text
Teaching Step → Evidence
```

---

## 2. 核心 / 辅助 / Boundary 分层

例如：

```text
CORE
支持当前核心机制

SUPPORT
提供额外实现细节

BOUNDARY
防止 Writer 说过头
```

---

## 3. 去除低教学价值 Evidence

例如：

```text
Mapper extends BaseMapper
DTO字段
配置常量
日志
```

如果不帮助理解 Spine：

> 不进入 Writer Prompt。

---

## 4. 按 Cognitive Spine 顺序排列

不是 retrieval rank。

# 二十五、Evidence Organization 第一版不能加 LLM

因为 Planner 已经花了一次 reasoning。

再问一个模型：

> “哪些 Evidence 更重要？”

很可能是在重复推理。

第一版：

```text

```

依靠：

```text

source authority
retrieval rank
```

完成。

目标耗时：

```text
< 1 秒
```

# 二十六、STEP 5：Teaching Writer V3

这是第二个核心 LLM。

它的定位：

> **Controlled Realizer**

而不是：

> 第二个 Planner。

它已经没有资格重新决定：

```text
讲哪些机制
什么顺序
要不要Scenario
哪些是核心
```

这些已经确定。

# 二十七、Writer 输入

```text
User Question

Teaching Blueprint

Writer Evidence Pack

Reader Assumption

Answer Depth
```

不要把整个 Workspace 重新给 Writer。

否则 Evidence Organization 完全失去意义。

---

# 二十八、Writer 的第一条强约束：不允许重新规划

禁止：

```text
新增核心章节

改变 Spine 顺序

增加 Blueprint 没有的核心机制

因为 Evidence 里有 Cache 就突然讲 Cache

重新定义 Mental Model
```

---

# 二十九、WHY Writer 的写作算法

Writer 内部按照：

```text
① 核心答案

② Problem / Constraint

③ Alternative

④ Counterfactual Scenario

⑤ Alternative 为什么失败

⑥ Current Mechanism 怎么改变问题

⑦ 为什么因此有效

⑧ Boundary / Tradeoff

⑨ Code Anchor

⑩ 收束
```

关键是：

> “为什么”至少要出现两层。

不是：

```text
为什么用延迟队列？

因为延迟队列能延迟消息。
```

而：

```text
问题是什么？
↓
简单方案为什么不够？
↓
当前机制具体改变哪一个约束？
↓
所以为什么更适合？
```

---

# 三十、HOW Writer 的写作算法

每一个核心 Spine Step：

```text
进入这一步前系统是什么状态？

↓

当前仍有什么问题？

↓

这一机制做了什么？

↓

哪个状态/约束发生变化？

↓

现在保证了什么？

↓

仍然没有保证什么？

↓

为什么继续进入下一机制？
```

这就是防止：

```text
调用 A
调用 B
调用 C
```

的核心手段。

---

# 三十一、Writer 的语言设计

你特别要求：

> 生成语言要让用户更容易理解。

第一版我建议强制四个规则。

---

## 规则 1：先人话，再术语

不要：

> “使用 expected-state transition 实现幂等状态推进。”

应该：

> “只有当前状态仍然是系统预期的旧状态，这次更新才允许成功。这个模式可以抽象成 expected-state transition。”

---

## 规则 2：一句话主要表达一个关系

不要：

> “Redis 令牌桶通过 Lua 配合 Redisson 和事务完成一致性……”

这种把五个概念堆在一起。

---

## 规则 3：概念先于源码

```text
WHY / mechanism
↓
Project evidence
↓
Code anchor
```

---

## 规则 4：不要暴露内部审计语言

不要：

> “这里属于 PROJECT_INFERENCE。”

改成：

> “从当前调用顺序可以进一步判断……”

---

# 三十二、Writer 的 Code Policy

代码细节只有满足以下之一才能进入：

```text
证明核心事实

帮助理解机制

用户明确问具体代码

是重要入口 / anchor
```

否则：

```text
DTO
Mapper继承
日志
配置项
辅助工具类
```

默认不出现。

---

# 三十三、Claim Ownership

这是解决当前重复问题的一个非常重要的设计。

Planner 要决定：

```text
哪个 Section 是某个核心 Claim 的主要解释位置。
```

例如：

```text
Lock → Section 2 owner

Conditional Update → Section 2/3 owner

Transaction → Section 3 owner
```

其他 section 可以：

> “前面已经解决了请求串行化……”

但不能再解释一遍。

这样比：

```text
target_chars=150
```

更有效地解决重复。

---

# 三十四、Scenario 在 Writer 中如何执行

Scenario 不是独立一章完整重放。

应该成为：

# Shared Narrative State

HOW：

```text
Section 1:
A/B同时买最后一个座位

Section 2:
继续这个场景，A先获得锁

Section 3:
A的UPDATE成功，B之后怎样

Section 4:
A座位更新成功但Ticket insert失败

Section 5:
A本地提交后Remote Order失败
```

WHY：

同一个 counterfactual 前后比较：

```text
只有轮询时怎样

↓

使用Delay Message后改变什么
```

---

# 三十五、Writer Prompt 同样需要 Few-shot

只写规则仍然给模型很大的解释自由。

所以：

```text
WHY Writer 示例
HOW Writer 示例
```

各一个。

示例不要使用真实项目。

避免模型把 example 中具体机制迁入当前项目。

使用通用假设系统。

---

# 三十六、STEP 6：Streaming

继续复用现有：

```text
SectionParser
<<<SECTION:S1>>>
...
<<<END_SECTION:S1>>>
```

这部分没有必要重写。

当前实现已经能够：

```text

```

是应该保留的成熟能力。

保持：


检查：

```text

标题是否匹配

是否超过输出预算

是否漏掉 required section
```

# 三十八、不要在线检查这些

第一版不要试图实时判：

```text
为什么讲得够不够深入

Cognitive Spine 是否优美

用户是否一定理解

例子是否完美
```

这些属于：

# Offline Evaluation

不是 runtime。

# 三十九、失败处理

正常：

```text
Planner
→ Writer
```

2 次 LLM。

### Planner hard failure

允许：

```text
最多 1 次 retry
```

只有：

```text
JSON非法
Evidence label非法
结构完全缺失
```

---

### Writer hard failure

如果：

```text
尚未输出 section
```

可以 retry 一次。

如果：

```text
已经输出部分 section
```

不要整篇重放。

继续沿用当前 single-stream 的安全策略。

# 五十、最终项目设计原则

整个回答模块 V3 可以压缩成五条。

### 1. Planner 决定理解，不决定漂亮文字

```text
Evidence → Learning Path
```

---

### 2. Writer 执行计划，不重新做 reasoning architecture

```text
Blueprint → Natural Explanation
```

---

### 3. WHY 和 HOW 使用不同的认知骨架

```text
WHY = design causality

HOW = mechanism / state progression
```

---

### 4. Worked Scenario 是认知模型的“运行实例”

不是装饰。

---

### 5. 质量不靠更多 Agent 保证

而靠：

```text
更好的 Planning Contract
+
更好的 Evidence Context
+
更受控的 Writer
+
确定性校验
+
离线评测
```

## 最后的目标形态

如果这次重构成功，用户问：

> “当前购票一致性是如何保证的？”

系统内部不会再思考：

```text
“我要写8个章节介绍8个组件。”
```

而是：

```text
用户最终需要理解：

一致性由不同责任层共同完成。

先建立：
Serialization
≠ State Validation
≠ Local Atomicity
≠ Distributed Convergence

然后：

并发问题
→ Lock

Lock不够
→ DB State Validation

State Validation不够
→ Transaction

Transaction不够
→ Compensation

用 A/B 抢最后一个座位
贯穿整条链

最后才落到项目代码。
```

然后 Writer 只负责把这条路径**自然、清楚、有证据地讲出来**。

这就是这次回答模块重构最核心的目标，也是目前学习科学、RAG 研究和你当前真实性能数据能够共同支持的一条相对稳健的路线。
