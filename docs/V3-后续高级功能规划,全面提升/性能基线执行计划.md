## 0. 前置条件（不满足则整轮基线作废）

### 0.1 嵌入模型必须绕开本地 hiddify 代理

本机 `HTTP_PROXY` / `HTTPS_PROXY` = `http://127.0.0.1:12334`（hiddify 客户端），
`NO_PROXY` 当前只有 `localhost,127.0.0.1,::1,.local`，**不含 `aliyuncs.com`**。

2026-10-01 实测（C6：两个 endpoint 都要核对，不能只测一个）：

| endpoint | 走代理 | 绕过代理 | 结论 |
|---|---|---|---|
| `https://api.deepseek.com/chat/completions` | `401` | `401` | **不受影响**，两种都通 |
| `https://dashscope.aliyuncs.com/compatible-mode/v1/embeddings` | `000`（握手失败） | `400`（可达，未带 body） | **受影响，必须绕过** |

即：**代理只打断 embedding，不打断 LLM**。这解释了为什么故障表现为「检索全空但 LLM 阶段看着正常」。
设置 `NO_PROXY` 对 deepseek 无害，所以统一加上即可。

**不只是 embedding。** LLM 客户端也是 curl 子进程（`llm/deepseek.py:50-98`），
curl 同样吃 `HTTPS_PROXY`。因此**每一次**真实运行都必须带：

```bash
NO_PROXY="localhost,127.0.0.1,::1,.local,.aliyuncs.com" uv run devcontext ask ...
```

不带的后果不是报错，而是**静默降级**：retrieval 全部失败（错误只记类型名，
`agentic/retrieval_controller.py:241` 做 `replace(action, error=type(exception).__name__)`），
用户侧输出变成「当前没有检索到足够的项目上下文」，
看起来像「知识库没证据」而不是「嵌入端点不通」。这样采到的 §5/§6 数据全是废的。

`§25.2 测试环境` 必须把 `NO_PROXY`、`EMBEDDING_TRANSPORT`、是否绕过代理一起记录，
因为它直接影响延迟数值。

**实现层面的两处偏离（相对本文原始设计，均已生效）：**

1. **stage 标签用环境上下文，不改 `LLMClient` 协议。** 原计划给 `generate()` 加 `stage=` 参数；实测发现仓库里有 **24 个测试替身**只实现 `generate(self, messages)`，改签名会全部打破。改为 `observability.llm_stage(...)` 上下文管理器 + `generate()` 内部读取，协议签名保持不变。

## 4. 改动清单

### A. 数据模型 — 新增 `src/devcontext/observability/trace.py`

四个 dataclass，各自带 `to_dict()`，**只依赖 stdlib**（见 §2.5 偏离 2）：

- `LLMCallTrace`: `call_id, stage, latency_ms, substage, model, reasoning_effort, max_tokens, json_mode, input_tokens, output_tokens, finish_reason, success, error, wasted, wasted_reason`
- `EmbeddingCallTrace`: `call_id, query, latency_ms, batch_size, model, dimensions, transport, success, error`
- `RetrievalActionTrace`: `action_id, requirement_id, round_index, query, source_scope, top_k, total_ms, result_count, query_embedding_ms, keyword_sql_ms, vector_sql_ms, fusion_ms, error`
- `SectionExecutionTrace`: `section_id, title, section_type, latency_ms, evidence_count, context_chars, target_tokens, revision, revision_notes_count, input_tokens, output_tokens, success, error`

外加 `PerfRecorder`（四个 list + `repeated_embeddings()` / `llm_totals()`）。

**C3：`StageUsage` 一个字段都没加。** 轮次信息走 `LLMCallTrace.substage`（`round_0`/`round_1`），
Section 数据全部进 `SectionExecutionTrace`。`AgenticTrace.to_dict()` 也未改动 ——
Section 数据经由既有的 `stats["trace"]` → `AgenticTrace.teaching` 通道呈现（见 C 段）。
因此 `evaluation/answer_quality_runner.py:120` 读到的形状不变，无需兼容处理。

### B. 调用级 trace 注入 — `src/devcontext/observability/recorder.py`

- `ContextVar` 持有 recorder + stage；`capture()` / `llm_stage()` 两个上下文管理器；
  `record_llm_call / record_embedding_call / record_retrieval_action / record_section_execution /
  mark_last_call_wasted`。
- **为什么用 ContextVar 而不是给 client 挂 list**：client 由 `cli.py:328-474` 的 14 个 factory 逐个构造，
  没有统一注册点；且同一 client 会跨多个 section 调用（`writer.py:137` 与 `:194`），
  挂 `last_call` 会丢数据。ContextVar 只影响 profiling 路径，非 profiling 时为 `None`，零开销。
- **stage 标签是环境上下文，不是 `generate()` 参数**（§2.5 偏离 1）：`llm/client.py:17-19` 的 protocol
  与 `deepseek.py:47` 的签名**保持原样**。24 个只实现 `generate(self, messages)` 的测试替身因此一行都不用改。
- `deepseek.py` 拆成 `generate()`（计时 + 记录 + 委托）与 `_generate()`（原实现）；
  新增 `last_finish_reason`，供 §23.4 判定 `length` —— 原实现取到该值后直接丢弃。
- recorder 为 `None` 时全部 hook 空转，`generate` 行为与改动前完全一致。

**teach 链路已埋点的 8 处（全部用 `llm_stage(...)` 包裹）：**

| 文件:行 | stage 标签 | substage |
|---|---|---|
| `planning/evidence_planner.py:75` | `evidence_planning` | — |
| `agentic/search_actions.py:86` | `search_action_planning` | `round_{round_index}` |
| `agentic/coverage.py:130` | `coverage_check` | `round_{view.round_index}` |
| `explanation/planner.py:82` | `explanation_planning` | — |
| `explanation/writer.py:137` | `teaching_draft` | `single_pass`（fast path） |

| `explanation/composer.py:68` | `composer` | `call_{n}`（revision 后会第二次） |
| `explanation/reviewer.py:121` | `teaching_review` | — |

stage 名与顶层 `StageUsage.stage` 对齐，报告才能把「LLM 调用耗时」与「阶段耗时」对上。
`mark_last_call_wasted` 埋在 6 处丢弃点：evidence/search-action/explanation 三个 planner 的 fallback、

> 注意：`l2`/`l1.5` 的 case 没有 perf 标签，**不要修改这些文件**去加标签——

### 6.2 时间预算（spec 完全没提，这里必须承认）

一个 detailed 问题 3–5 分钟。12 case × 3 次 = **36 次真实请求 ≈ 2–4 小时**（不含冷启动）。

因此采集分两轮：

1. **先跑 4 条（每类 1 条）× 3 次** ≈ 30–45 分钟，验证数据可信、`unattributed` 达标。
2. 确认后再补齐到 8–12 条。**不要一次挂 36 次**。

**冷/热的定义（C4）。** 当前 `uv run devcontext ask` **每次都是独立 Python 进程**，
所以第 2、3 次运行并不共享导入、客户端初始化或连接池 —— **不得称为 warm**。

- 首选：P5 给 `ask` 增加单进程 `--repeat N`，一次进程内连跑 N 次；
  此时第 1 次标 `first_sample`，其余标 `repeat_sample`，两者差异才真正代表稳态。
- 若本轮不做 `--repeat`：**禁用 cold/warm 措辞**，一律用 `first_sample` / `repeat_sample`，
  并在报告里写明「每次 ask 为独立进程，样本间不共享进程内状态」。

## 7. 验证方法

1. **回归**：`uv run pytest`（42 个测试文件）。只有 `tests/test_storage_integration.py:11-16`
   需要 DB 且被 `DEVCONTEXT_RUN_INTEGRATION=1` 守卫，其余不打网络/DB，不受影响。
2. **行为不变性（最关键的一条，按 C2 改为 mock）**：
   - **主体**：`tests/test_perf_trace.py::TestInstrumentationChangesNothing` —— 同一组
     ScriptedClient 输入，跑「开 tracing」与「不开 tracing」两次，断言答案文本、used/invalid
     citations、`stats["path"]`、`invalid_citation_count` 完全一致，且 `stats["trace"]` 中
     **除新增的 `section_execution` 键外逐键相等**。这比真实 LLM diff 更强：真实运行有
     采样抖动，逐字比对会把抖动误判成回归。
   - **补充**：真实 LLM 只跑 1 个 standard 问题，核对执行路径、`coverage_rounds` 的
     round 数、citation 集合、depth、fallback/error 字段**未出现异常变化**，不做逐字比对。
3. **计时完整性（C1 收紧后的口径）**：

   ```
   unattributed = wall_clock
                - Σ(顶层 stage 的 latency_ms)
   ```

   顶层 stage 是**互斥**的、划分整个请求的那些：`evidence_planning`、
   `search_action_planning`(×2)、`evidence_retrieval`(×2)、`coverage_check`(×2)、
   `explanation_planning`、`teaching_draft`、`teaching_review`、`teaching_revision`。

   `LLMCallTrace` / `SectionExecutionTrace` / `EmbeddingCallTrace` / `RetrievalActionTrace`
   **一律不得进入这个求和** —— 它们是被上面某个 stage 包住的子级诊断，加进来就是重复计数
   （例如 `teaching_draft` 已经覆盖了全部 N 节，再加 Σ section 就把同一段时间算了两遍）。

   目标仍是 `< 5%`。已知的合法缺口：`_build_context`（`retrieval_controller.py:133` 与 `:191`）
   发生在 `evidence_retrieval` 结束之后、`coverage_check` 开始之前，两轮各有一段未被任何 stage 覆盖，
   会落进 `unattributed`。若冒烟时该项偏大，先查这里再查别处。
4. **数据自洽**：`llm_calls` 条数 == 实际发生次数；`embedding_calls` 中同一 query 出现 2 次
   （混合作用域时）应能被观测到。
5. **代理前置**：任何一次采集前先跑 §0.1 的 curl 对照，确认 `http=401` 而非 `000`。
