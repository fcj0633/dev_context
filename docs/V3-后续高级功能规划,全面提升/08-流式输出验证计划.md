下面这份可以直接发给 Agent 执行。目标不是立刻替换现有回答链路，而是做一个**可切换、可 A/B、可回退**的 `single_stream` 实验实现。

# DevContext Single-Stream Teaching 实验实施计划

## 0. 背景与目标

当前 `detailed` 多章节回答链路较重：

```text
Evidence
→ ExplanationPlanner
→ Section Writer × N
→ Composer
→ Reviewer
→ Revision
→ Composer
→ Final Answer
```

最新全链路测试中：

- Q1：151.5s，5 节，13 次 LLM；
- Q3：202.1s，5 节，13 次 LLM；
- 五节并行本身已经压缩到 18.8s / 16.2s；
- 真正的新瓶颈是 Composer、Reviewer、Revision；
- Q1 评审+修订占总耗时 50.4%，Q3 占 52.8%。:chatgpt-content-reference{index="1"} :chatgpt-content-reference{index="2"}
- 当前章节并发已经获得约 2.43× / 2.51× 压缩，因此本轮**不要继续优化 Section 并发**。:chatgpt-content-reference{index="3"}

本实验目标是验证：

```text
Evidence
→ ExplanationPlanner
→ Micro Section Plan
→ One Streaming Teaching Writer
→ Deterministic Validation
→ Final Answer
```

能否替代大部分 `detailed` 请求当前的重型生成链路。

# 3. Phase 1：增加 Generation Mode

新增运行配置：

```text
TEACHING_GENERATION_MODE=
    multi_pass
    single_stream
```

默认必须保持：

```text
multi_pass
```

不要影响当前用户。

建议形成不可变运行配置，例如：

```python
TeachingRuntimeOptions(
    depth_policy=...,
    section_concurrency=...,
    generation_mode="multi_pass",
)
```

运行流程：

```python
if generation_mode == "single_stream":
    return _run_single_stream(...)
else:
    return _run_existing_pipeline(...)
```

要求：

> 现有 multi-pass 行为、测试和输出不能因本阶段发生变化。

---

# 4. Phase 2：Micro Section Plan

## 4.1 不再使用“5 个大章节”

`single_stream` 下增加一种：

```text
section_granularity = micro
```

暂时不要修改旧 multi-pass 的章节规则。

建议初始范围：

```text
brief      2～4
standard   4～7
detailed   7～12
deep       10～16
```

注意：

> Section 数只控制阅读颗粒度，不控制总回答长度。

---

## 4.2 每个 Micro Section 只回答一个小问题

例如原来：

```text
## 原子性与时序：事务边界、锁粒度和提交后动作
```

可能包含几百字、多种机制。

改成：

```text
## 锁负责什么
## 事务负责什么
## 为什么 RPC 放在事务外
## 条件更新为什么能防止超卖
## 提交以后还有哪些动作
```

每节：

```text
1 个核心问题
1～3 个 key points
1 组 allowed evidence
约 100～250 中文字
```

---

## 4.3 Planner Schema 保持轻量

每节只需：

```json
{
  "id": "S4",
  "title": "为什么 RPC 放在事务外",
  "teaching_goal": "解释事务边界设计原因",
  "key_points": [
    "本地事务只覆盖 ticket DB",
    "订单创建属于 RPC",
    "RPC 会延长锁持有时间"
  ],
  "evidence_labels": ["E10", "E16"],
  "target_tokens": 180
}
```

全局保留：

```text
direct_answer
core_mental_model
answer_depth
```

不要恢复旧的超大 Planner Schema。

---

# 5. Phase 3：实现 Streaming LLM Client

当前 LLM 调用为非流式。

新增能力，不破坏原接口：

```python
generate(...)
generate_stream(...)
```

建议 `generate_stream()` 返回统一事件，而不是直接暴露 provider 原始 SSE：

```python
StreamEvent(
    type="content",
    text="..."
)
```

必要事件至少支持：

```text
content
usage
finish
error
```

如果 Provider 同时返回：

```text
reasoning_content
content
```

必须：

```text
reasoning_content
→ 只进入性能统计

content
→ 才进入最终答案
```

禁止把 reasoning 内容输出给用户。

---

# 6. Phase 4：SingleStreamingTeachingWriter

新增独立组件，不直接改坏现有 `TeachingWriter`：

```text
SingleStreamingTeachingWriter
```

输入：

```text
Question
Direct Answer
Core Mental Model
Micro Section Plan
Section → Evidence 映射
Evidence Text
Total Answer Budget
```

只进行：

```text
1 次 LLM 请求
```

要求模型按固定 Section 顺序生成。

---

# 7. 输出协议不要完全自由 Markdown

建议内部采用明确边界，例如：

```text
<<<SECTION:S1>>>
## 一句话结论

正文...
<<<END_SECTION:S1>>>

<<<SECTION:S2>>>
## 一致性需要保护什么

正文...
<<<END_SECTION:S2>>>
```

最终返回用户时再移除内部 marker。

这样 Streaming Parser 可以知道：

```text
S1 什么时候完整生成
S2 什么时候开始
```

不要依赖模型“碰巧输出 ## 标题”判断边界。

---

# 8. Phase 5：章节级缓冲，而不是裸 Token Streaming

第一版不要：

```text
Provider token
→ 立即发给用户
```

采用：

```text
Provider stream
      ↓
当前 Section Buffer
      ↓
END_SECTION
      ↓
Deterministic Validator
      ↓
PASS
      ↓
emit section
```

例如：

```text
S1 生成中
↓
暂存在 Buffer
↓
S1 完成
↓
校验
↓
用户看到 S1

S2 继续……
```

这样既有流式体验，又保留 Grounding 控制。

---

# 9. Phase 6：Deterministic Section Validator

不要第一版重新引入 LLM Reviewer。

程序验证：

```text
Section ID 是否合法
Section 是否缺失
Section 是否重复
Section 是否为空
Citation 是否存在
Citation 是否属于当前 Section allowlist
Citation 是否真实存在 EvidenceWorkspace
是否 zero-valid-citation
输出 Section 数是否与 Plan 一致
```

特别是：

```python
used_citations ⊆ section.evidence_labels
```

必须成立。

如果不成立：

```text
section validation failed
```

不要直接展示该 Section。

---

# 10. 第一版失败策略

保持简单。

### Section 尚未向用户输出

如果模型生成：

```text
invalid citation
malformed section
```

允许：

```text
整次 single_stream retry once
```

前提：

```text
尚未 emit 任何 section
```

### 已经输出 S1/S2 后失败

第一版不要偷偷从头重播。

记录：

```text
partial_stream = true
failed_section = S3
```

然后正常结束为不完整状态。

后续版本再研究：

```text
从指定 Section 恢复生成
```

不要把 resume protocol 放进第一版。

---

# 11. Phase 7：总长度控制

Micro Section 增加后，不能让答案无限增长。

必须把两个概念分离：

```text
answer_depth
→ 控制总信息量

section_granularity
→ 控制如何切分信息
```

建议第一轮使用现有回答实际长度作为参考。

目前 Q1/Q3 最终约：

```text
5.8k 字符
```

:chatgpt-content-reference{index="5"}

实验阶段建议：

```text
detailed:
目标最终正文约 3000～5000 中文字符
```

不要因为：

```text
5 大节 → 10 小节
```

让总字数翻倍。

## 最终执行原则

Agent 本轮最重要的是验证这一条假设：

> **对于 DevContext 的 standard/detailed 教学回答，只要前置 Evidence 和 Explanation Plan 足够可靠，就可能没有必要再使用“N 个独立 Writer + Composer + Reviewer + Revision + Composer”；一个受 Evidence 约束、按 Micro Sections 连续生成的 Streaming Writer，可能以更短链路获得相近甚至更好的整体连贯性与阅读体验。**

先把这个假设实验清楚，再决定是否改变 DevContext 的正式回答架构。
