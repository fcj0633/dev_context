可以。下面直接把**最值得做好的几个功能点**收敛成可执行实现方案。重点不是再解释“为什么要做”，而是回答：

> **具体应该怎样实现，Prompt 怎么限制，运行时怎么走，怎么验收，怎样避免再次出现当前回答的问题。**

我建议第一版只实现 6 个核心能力：

1. Learning Goal Contract  
2. WHY / HOW Cognitive Spine  
3. Learning Delta + Claim Ownership  
4. Worked Scenario Simulator  
5. Writer Evidence Pack  
6. Few-shot + Controlled Writer  

这 6 个功能组合起来，才构成真正的 V3。

# 1. Learning Goal Contract：先把“教什么”锁死

这是 Planner 第一步，而且必须比当前 `direct_answer + core_mental_model` 更严格。

## 推荐实现

不要让模型自由回答：

> “这个问题的学习目标是什么？”

而是明确给它一个**能力型目标模板**。

WHY 必须规划成：

```text
回答结束后，读者应该能够：

1. 说出当前设计真正想解决的约束/矛盾；
2. 解释一个更直觉的替代方案为什么不足；
3. 解释当前方案究竟改变了什么；
4. 解释为什么这个变化解决了问题；
5. 说明当前方案仍然存在什么边界或代价。
```

HOW 必须规划成：

```text
回答结束后，读者应该能够：

1. 重建系统从初始状态到最终状态的关键过程；
2. 说明每个核心机制改变了什么；
3. 说明每层机制提供什么保证；
4. 解释为什么前一层保证不足以替代后一层；
5. 对一个关键失败场景预测系统接下来会怎样处理。
```

这不是 Writer Prompt，而是 **Planner 的内部成功标准**。

LearnLM 的研究非常支持这一点：通用模型默认更偏向“呈现信息”，而不是主动围绕学习目标教学；显式的 pedagogical instruction 能让教学行为更稳定。:chatgpt-content-reference{index="0"}

## Prompt 怎么写

Planner Prompt 里直接加入：

```text
Learning Goal 的定义：

它不是用户问题的改写，也不是技术名词列表。

它必须描述：
“回答结束后，读者应该能够解释、区分、重建或预测什么。”

禁止生成：
- “了解 XXX”
- “掌握 XXX 的实现”
- “理解 A、B、C”
- 章节目录
- 类名/方法名列表
```

再分别给 WHY / HOW 的模板。

## 最好再生成一个“理解检查”

不是在线询问用户，而是 Planner 内部生成 2～3 个检查问题。

HOW Q1 可以是：

```text
为什么只有 Lock 还不能保证最终座位状态正确？

Conditional Update 已经是原子的，
为什么 Seat + Ticket 仍需要 Transaction？

为什么本地 Transaction 无法直接回滚 Remote Order？
```

这个小功能非常有价值。

因为它可以反向检验 Learning Goal：

> 如果 Planner 自己连“理解以后应该能回答什么”都构造不出来，Goal 很可能过浅。

第一版不用把这些问题展示给用户，只记录在 trace。

# 2. Cognitive Spine：不要让模型“列步骤”，让它构造因果链

这是整个 V3 最重要的实现。

Self-explanation 研究发现，学习效果好的学习者会解释步骤成立的条件，并把具体操作和更一般的原则建立联系，而不是单纯复述步骤。:chatgpt-content-reference{index="1"}

所以 Spine 的最小单位不能是：

```text
Redis
Lock
Transaction
MQ
```

而必须是：

```text
问题
→ 当前机制
→ 它提供什么保证
→ 它为什么仍然不够
→ 下一机制为什么因此出现
```

---

## 2.1 WHY Spine 最佳实现

WHY 不应该围绕：

```text
技术 → 优点
```

而应该围绕：

# Constraint → Alternative → Failure Mechanism → Design Effect

第一版直接固定推理顺序：

```text
A. Goal / Constraint
系统真正需要满足什么？

B. Naive Alternative
不用当前方案，最直接会怎么做？

C. Failure Mechanism
这个方案具体为什么失败？
不是说“不好”，而是具体失败机制。

D. Chosen Design
项目当前用了什么设计？

E. Design Effect
这个设计改变了哪个条件？

F. Causal Explanation
为什么改变这个条件以后，
刚才的 Failure Mechanism 被缓解？

G. Tradeoff / Boundary
新方案又没有解决什么？
付出了什么代价？
```

### 例子

问题：

> 为什么订单关闭使用延迟队列，而不是只定时轮询？

差 Plan：

```text
定时轮询
→ 延迟队列
→ 延迟消费者
→ 定时任务
```

V3 Plan：

```text
目标：
订单到期后应该比较及时地关闭，
又不能持续高频扫描整个未支付订单集合。

直接方案：
定时扫描数据库。

Failure mechanism：
扫描间隔长
→ 关闭不及时；

扫描间隔短
→ DB 持续承担扫描成本。

核心矛盾：
及时性 ↔ 持续扫描成本。

当前设计：
订单创建时就安排一个接近其超时时刻的延迟触发。

Design effect：
从“周期扫描整个集合”
变为
“针对某个订单的定向触发”。

Boundary：
消息可能延迟/丢失等，
所以仍需要兜底扫描。
```

这才是真正回答“为什么”。

### 在线校验

不用 LLM Reviewer。

Planner Parser 只检查结构上必须存在：

```text
constraint
alternative
failure mechanism
design effect
boundary
```

语义是否优秀留给 benchmark。

# 2.2 HOW Spine 最佳实现

HOW 不应该围绕：

```text
Controller → Service → Mapper → RPC
```

而应该围绕：

# System Condition + Guarantee

我建议 HOW 的每一步都内部考虑这五件事：

```text
进入这一步前：
系统现在是什么情况？

当前问题：
还有什么可能出错？

Mechanism：
系统做了什么？

Effect / Guarantee：
这一步新增了什么保证？

Remaining Gap：
还有哪个保证没有建立？
```

然后：

```text
Remaining Gap(N)
→
Problem(N+1)
```

必须逻辑连起来。

---

## Q1 具体应该生成什么

```text
初始：
两个请求可能竞争同一个座位。

Step 1：
Lock

Effect：
竞争请求在关键区域内串行执行。

Guarantee：
不会同时执行同一临界操作。

Remaining Gap：
串行执行不等于数据库状态仍然合法。


Step 2：
Conditional Update

Effect：
只有 seat_status=AVAILABLE 才允许更新。

Guarantee：
数据库成为状态转换的最终裁决者。

Remaining Gap：
一次 Seat 更新成功，
不保证后面的 Ticket 插入也成功。


Step 3：
Local Transaction

Effect：
Seat update 和 Ticket insert 绑定。

Guarantee：
本地多写一起提交/回滚。

Remaining Gap：
Remote Order 不属于这个本地事务。


Step 4：
Compensation / Idempotent State Transition

Effect：
事务外失败通过补偿或状态推进处理。

Guarantee：
跨服务失败后能够重新向一致状态收敛。

Boundary：
具体幂等能力只能说到 Evidence 能证明的程度。
```

这就是 HOW Planner 的主体。

# 3. Minimal Mental Model：从 Spine 再压缩一层

Spine 是详细推理结构。

Mental Model 是用户开头需要得到的“地图”。

推荐只允许：

```text
3～5 个关系
```

不要允许类名、方法名。

例如 Q1：

```text
并发串行化
≠
数据库状态裁决
≠
本地原子性
≠
跨服务收敛
```

或者：

```text
Lock
解决执行竞争

条件更新
解决状态合法性

事务
解决本地多写原子性

补偿/幂等
解决事务边界外的收敛
```

## 一个非常实用的程序检查

Mental Model 中如果出现大量：

```text
PurchaseTicketServiceImpl
doPurchaseInTransaction
SeatMapper
```

直接给 warning。

现有 `TeachingStyleInspector` 已经有 identifier 检测代码，可以复用。

Mental Model 应该是：

> **抽象层。**

代码应该后面再出现。

# 4. Learning Delta：用它真正决定章节

这是我最建议加入的新概念。

当前 `MicroSection` 有：

```text
reader_takeaway
key_points
new_terms
```

但这些都没有直接表示：

> “用户的理解从什么变成什么。”

推荐让每个核心 Section 都明确拥有一个：

# Learning Delta

概念上就是：

```text
Before:
用户当前可能怎样理解？

After:
读完这一节以后，
应该新增/修正什么关系？
```

---

## Q1 示例

### Section 2

标题：

> 有锁以后，为什么数据库还要再判断一次？

Learning Delta：

```text
Before:
“锁住以后就不会超卖。”

After:
“锁只负责请求之间的执行顺序，
真正的座位状态合法性仍由数据库条件更新裁决。”
```

### Section 3

标题：

> 条件更新已经原子了，为什么还需要事务？

Learning Delta：

```text
Before:
“只要 Seat 更新安全就够了。”

After:
“一个状态更新正确，
不代表 Seat 与 Ticket 两个业务写能共同成功。”
```

### Section 4

标题：

> 有了本地事务，为什么还需要补偿？

Learning Delta：

```text
Before:
“@Transactional 能覆盖整个购票过程。”

After:
“本地事务只能约束本地数据库，
Remote Order 已经越过本地事务边界。”
```

这会比 `reader_takeaway` 强很多。

因为它直接要求：

> **这一节必须改变一个认知模型。**

# 5. Claim Ownership：专门解决重复问题

这是 Learning Delta 的配套功能。

Planner 在形成所有核心结论后，为每个核心 Claim 指定：

> **主要在哪一个 Section 被完整解释。**

例如：

```text
C1:
Lock = serialization
Owner → S2

C2:
Conditional Update = state validation
Owner → S2

C3:
Transaction = local atomicity
Owner → S3

C4:
Compensation = cross-service recovery
Owner → S4
```

Writer Contract：

```text
Owner Section:
允许完整解释 Claim。

Non-owner Section:
最多引用/承接 Claim，
不得再次完整解释。
```

例如 S4 可以写：

> 前面本地事务已经保证了 Seat 和 Ticket 的共同提交。

但不能再花一段重新解释：

> 什么是事务、为什么事务有原子性……

---

## 为什么这比 target_chars 好

当前：

```text
100～250 字
```

只是压长度。

Claim Ownership 直接控制：

> **内容应该在哪解释一次。**

这是解决：

```text
开头讲一遍
正文讲一遍
总结再讲一遍
```

最有效的结构性办法之一。

Coherence 相关研究也支持减少冗余和不服务学习目标的信息处理。重复材料不一定增强理解，反而可能增加额外认知加工。:chatgpt-content-reference{index="2"}

# 6. Answer Structure：不要 Spine Step = Section

这是非常关键的实现细节。

错误做法：

```text
Spine 7 steps
→
7 sections
```

最终还是很机械。

正确做法：

```text
Spine
↓
根据共同 Learning Delta 合并
↓
Reader-facing Sections
```

例如：

```text
Lock
→ remaining gap
→ Conditional Update
```

共同完成：

> “Serialization ≠ State Validation”

所以可以合并成一节：

> **有锁以后，为什么数据库还要判断一次？**

而：

```text
Conditional Update
→ remaining gap
→ Transaction
```

完成另一个理解变化：

> “State Validation ≠ Local Atomicity”

所以另起一节。

# 7. 第一版章节数量不要固定 6～9

当前：

```text
detailed = 6～9
```

我建议取消这种硬范围。

第一版 WHY：

```text
大约 4～6 节
```

HOW：

```text
大约 5～7 节
```

只是 soft guidance。

真正决定章节数量的是：

```text

```

而不是：

```text
用户选择了 detailed
所以必须 8 节
```

# 8. Worked Scenario Simulator：做成“运行模型”，不是“举例模块”

第一版你已经决定默认使用 Scenario，我建议具体这样实现。

---

## 8.1 HOW Scenario

Planner 生成：

```text
Initial Scenario State

Actor / Resource

每个 Spine Step 对应的 Scenario Checkpoint

一个关键 Failure Branch
```

例如：

```text
初始：
只剩最后一个二等座；
A 和 B 同时购买。

S2：
A/B 都进入请求，
A 先获得临界区执行资格。

S2 后半：
A UPDATE AVAILABLE→LOCKED 成功，
B 随后条件更新失败。

S3：
假设 A 的 Seat update 成功，
但 Ticket insert 抛异常，
事务回滚。

S4：
假设本地事务已提交，
但 Remote Order 明确失败，
进入补偿。
```

重点：

> Scenario 的 checkpoint 必须映射到 Cognitive Spine。

---

## 8.2 WHY Scenario

WHY 不做 state trace。

做：

# Counterfactual Pair

相同起点，两种方案。

例如：

```text
订单 10:00 创建，
10:30 过期。

世界 A：
只定时扫描。

世界 B：
创建时安排延迟消息。
```

比较：

```text
什么时候发现过期？
扫描了多少无关订单？
如果消息异常怎么办？
```

这样 Scenario 直接服务 WHY 的 design comparison。

---

# 9. Scenario 不独立成一大节

Writer 不要：

```text
正文全部讲完
↓
“下面举一个完整案例”
↓
再讲一次
```

应该：

```text
S2 推进 scenario 一步
S3 再推进一步
S4 再推进一步
```

Scenario 是：

> **Shared Narrative State。**

这样减少重复。

---

# 10. Scenario 必须防止“编造项目事实”

Planner Prompt 明确区分：

```text
Hypothetical setup
vs
Project fact
```

可以：

> “假设只剩一个座位。”

不能：

> “项目每 30 秒扫描一次订单。”

除非 Evidence 明确有这个事实。

所有假设数字/场景必须被 Writer 表达成：

```text
“假设……”
```

而不能变成：

> “系统会……”

# 11. Writer Evidence Pack：不要再给一个大 bundle

这是工程实现上非常值得改的一点。

当前 single-stream 大致是：

```text
plan.evidence_labels
↓
union
↓
一个 ContextBundle
↓
Writer
```

推荐改成：

```text
WriterEvidencePack

GLOBAL_MODEL_EVIDENCE

  CORE
  SUPPORT
  BOUNDARY

SECTION S2
  CORE
  SUPPORT
  BOUNDARY

...

CONFLICTS
```

仍然：

> **只调用一次 Writer。**

# 12. Evidence 怎么分类

第一版不要加 LLM。

Planner 本身已经给每个 Delta / Claim 绑定 Evidence。

Organizer 只做确定性处理。

优先级：

```text
CORE
直接证明这一节的核心 Project Fact

BOUNDARY
限制 Writer 不能说得更强

SUPPORT
额外背景/设计解释
```

预算不够时：

```text
先删 SUPPORT
再删重复 Evidence

CORE 和关键 BOUNDARY 最后删
```

# 13. Evidence 不要重复全文

如果 E4 同时支持 S2、S3：

不要：

```text
S2 中复制 E4 body

S3 中再复制一遍 E4 body
```

建议只保留一次完整 Evidence body，并让 section contract 指向：

```text
S2 allowed: E2 E4
S3 allowed: E4 E6
```

Evidence Catalog 按首次使用 Section 的顺序排列。

这样同时兼顾：

```text
Context locality
+
Prompt token size
```

# 14. Context Budget 最好按 Section 公平分配

当前 `ContextBuilder` 是：

```text
不断放 chunk
遇到第一个放不下
→ stop
```

对于 Writer Pack，我不建议继续完全依赖这个逻辑。

第一版最好：

```text
Pass 1:
保证每个核心 Section 至少拥有一个 CORE Evidence。

Pass 2:
保证关键 Boundary Evidence。

Pass 3:
再加入 SUPPORT Evidence。

Pass 4:
仍有预算才加入额外 Core detail。
```

这样可以避免：

> S1/S2 把 Context 吃完，S5 没 Evidence。

RAGChecker 的工作也说明，RAG 不仅需要 retrieval recall，还需要 context precision 和 generation utilization。:chatgpt-content-reference{index="3"}

---

# 15. 为什么 Evidence 顺序很重要

`Lost in the Middle` 发现，即使是 long-context 模型，关键信息放在上下文不同位置时性能也会明显变化，尤其处于长上下文中间时使用效果可能下降。:chatgpt-content-reference{index="4"}

所以 Writer Pack 推荐：

```text
Question
Teaching Blueprint

S1 Contract
S1 Core Evidence refs

S2 Contract
S2 Core Evidence refs

...

Evidence Catalog
```

或者把实际 Evidence body 按：

```text
S1 → S2 → S3
```

顺序排列。

不要继续完全按 retrieval rank。

# 16. Few-shot：Planner 必须有两个高质量示例

这是我最推荐投入时间做好的 Prompt 功能。

Min 等人的研究显示，few-shot demonstrations 会向模型提供任务空间、输入分布和输出格式等重要信号，而不仅仅是“正确答案”。:chatgpt-content-reference{index="5"}

因此 V3 Planner 不应该只靠规则。

---

## Planner Prompt 放三个 demonstration block

### Demo 1：WHY

用一个和项目无关的假设系统：

> 为什么任务到期使用事件触发，而不是每秒扫描全部任务？

完整示范：

```text
Learning Goal
Mental Model
Constraint
Alternative
Failure Mechanism
Design Effect
Boundary
Scenario
Learning Delta
```

---

### Demo 2：HOW

例如：

> 文件上传如何保证元数据和对象存储状态协调？

示范：

```text
Initial condition
Guarantee
Remaining gap
Next mechanism
Failure handling
```

---

### Demo 3：短 Anti-pattern

```text
BAD:

1. Redis
2. Lock
3. Transaction
4. MQ

为什么错误：
只是组件列表，
没有解释每个机制解决什么，
也没有说明前一个为什么不够。
```

只需要非常短。

# 17. 为什么示例不能用 my12306

否则 Planner 很容易形成：

```text
HOW
=
Lock → Transaction → Compensation
```

这种领域模式依赖。

我们真正想让模型学习：

```text
Guarantee → Remaining Gap → Next Mechanism
```

因此 demo 要跨领域。

# 18. Writer 的 Few-shot 应该更短

Writer 不需要两篇完整示例答案。

只需要几个：

# Micro-demonstration

例如 HOW：

### BAD

```text
系统首先获取分布式锁，
然后执行条件更新，
最后开启事务。
```

### GOOD

```text
锁先解决多个请求同时进入临界区的问题，但它并不能证明真正写库时状态仍然合法。因此数据库更新本身还要检查旧状态，只有满足预期条件时才允许推进。
```

模型学到的是：

```text
previous guarantee
→ remaining gap
→ next mechanism
```

# 19. Writer 最佳实现：One Writer + Section-local Contract

这是我最推荐的 Writer V3 实现。

不要：

```text
一个巨大的全局 Blueprint
+
让模型自由写全文
```

也不要：

```text
N 个 Writer
```

而是：

```text
一次 Writer 调用

但每一个 Section 都有自己的 local contract
```

例如 S3：

```text
SECTION GOAL:
让用户理解 Conditional Update 为什么不能代替 Transaction。

LEARNING DELTA:
Before → 单次更新安全就够。
After → 单次写安全 ≠ 多个本地写共同成功。

OWNED CLAIMS:
C3, C4

MAY REFERENCE:
C1, C2
但不能重新展开。

SCENARIO CHECKPOINT:

E4 E6

BOUNDARY:
...
```

这会大幅降低 Writer 自由度。

# 21. Writer 语言约束具体怎么做

# 22. 现有 `new_terms` 和硬 `target_chars` 怎么处理

## `new_terms`

从 Planner 的硬约束中删除。

```text
NEW_TERM_LOAD warning
```

但不要：

> 每节必须声明最多两个新术语。

因为认知负担不是这样机械测量的。

## `target_chars`

改成：

```text

250～450 字左右
```

# 23. 需要新增哪些确定性 Validation

第一版不用 LLM Reviewer，但可以增加几个很有用的程序校验。

### Planner Validation

检查：

```text
WHY 是否存在：
constraint
alternative
failure mechanism
design effect

HOW 是否存在：
initial condition
guarantee
remaining gap
final invariant

每个 Spine Step 是否有 Evidence

所有核心 Spine 都被某 Section 覆盖

Scenario 是否映射至少一个核心 Section

Boundary Evidence label 是否合法

Mental Model 中代码 identifier 是否过多
```

### Writer Validation

继续复用：

```text

heading
citation

```

新增可以非常简单：

```text
所有计划 Section 都出现

Owner Claim Section 没有被跳过

Scenario required 的 Section 已生成
```

语义是否真的写出了 Claim 暂时不要硬校验。

否则很容易做出脆弱规则。

# 25. 两个测试题的 Gold Contract 要提前人工写好

不要写 Gold Answer。

写：

# Gold Teaching Contract

---

## WHY Gold Contract

问题：

> 为什么订单关闭使用延迟队列，而不是只使用定时轮询？

必须包含：

```text
Goal:
订单过期及时处理，同时避免持续高频扫描。

Alternative:
定时轮询。

Failure Mechanism:
轮询间隔和及时性/扫描成本存在权衡。

Design Effect:
延迟消息把全局周期扫描变成针对单个订单的定向到期触发。

Boundary:
消息机制不是绝对可靠，存在扫描兜底的意义。
```

具体以真实 Evidence 能证明的内容为准。

---

## HOW Gold Contract

问题：

> 当前购票占座的数据一致性如何保证？

至少检查：

```text
Lock
= serialization

Conditional Update
= state validation

Transaction
= local atomicity

Remote Order outside transaction
= distributed boundary

Compensation / callback
= convergence mechanism

并且存在：
Lock → gap → Conditional Update
Conditional Update → gap → Transaction
Transaction → gap → Compensation
```

这比写一个标准答案更适合验证 Planner。


正常整个 Answer Module：


加 Retrieval Control 后：


比较符合你的目标。

# 28. 最终我最推荐的 V3 核心结构

不是：

```text
Question
→ 8个Sections
→ Writer
```

而是：

```text
Question
        ↓
Learning Goal
        ↓
Minimal Mental Model
        ↓
WHY / HOW Cognitive Spine
        ↓
Learning Deltas
        ↓
Claim Ownership
        ↓
Worked Scenario Checkpoints
        ↓
Reader-facing Answer Structure
        ↓
Section-aligned Evidence Pack
        ↓
ONE Controlled Writer
        ↓
Deterministic Validation
```

这里真正高价值的新功能不是“更多字段”，而是三个约束：

> **`Remaining Gap` 强制建立因果链。**

> **`Learning Delta` 强制每节真的改变用户理解。**

> **`Claim Ownership` 强制核心知识只在一个地方完整展开。**

再配合一个与 Spine 映射的 **Worked Scenario**，就能同时解决当前版本最明显的四个问题：组件堆叠、关系断裂、正文重复、例子装饰化。

Few-shot 则负责让模型稳定学会这套行为，而不是继续用几十条 Prompt rule 去“祈祷模型理解我们的意图”。这也符合 in-context learning 研究中 demonstrations 对任务空间和输出结构的塑造作用。:chatgpt-content-reference{index="6"}

**如果马上开始开发，我建议第一批代码只做：`Learning Goal + WHY/HOW Spine + Learning Delta/Claim Ownership + Scenario + Planner Few-shot`，然后先看两个问题的 Plan-only 输出。这个关口通过以后，再接 Evidence Pack 和 Writer。**
