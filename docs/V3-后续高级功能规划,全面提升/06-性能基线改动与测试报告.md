## 1. 本轮范围

只做 **性能可观测性（Performance Profiling / Latency Baseline）**，
目标是让「一次 ask 每个阶段、每次 LLM 调用、每轮检索、每节生成各花多少时间」变成可测量的事实。

**本轮不包含任何优化。** 依据 spec §27：profiling 与优化同轮进行会失去可靠基线。

## 3. 改动清单

### 3.1 新增 `src/devcontext/observability/`（4 个文件，仅依赖 stdlib）

| 文件 | 内容 |
|---|---|
| `trace.py` | `LLMCallTrace` / `EmbeddingCallTrace` / `RetrievalActionTrace` / `SectionExecutionTrace` / `PerfRecorder` |
| `recorder.py` | `capture()` / `llm_stage()` 两个上下文管理器；`record_*` 与 `mark_last_call_wasted()` |
| `report.py` | `TOP_LEVEL_STAGES`、`build_perf_report()`、`render_summary()` |
| `__init__.py` | 再导出 |

**为什么单独建包而不放进 `agentic/models.py`**：后者 `import devcontext.answer.generator`，
而 `llm/deepseek.py` 需要记录调用 —— 放在一起会构成
`llm → agentic.models → answer.generator → llm` 的循环导入。
本包只依赖标准库，任何层都能安全引用。

### 3.2 修改的源码（13 个文件）

| 文件 | 改动 | 为什么 |
|---|---|---|
| `llm/deepseek.py` | `generate()` 拆为「计时+记录」外壳与 `_generate()`；新增 `last_finish_reason` | `finish_reason` 原先取到后即被丢弃（非 `stop` 直接 raise），导致 §23.4 的 `length` 情形**无法被观测**。实测确实出现过 |
| `planning/evidence_planner.py` | `llm_stage("evidence_planning")`；fallback 时 `mark_last_call_wasted` | 该 planner 会跑满一次完整 LLM 调用后因校验失败被丢弃，这段耗时原先完全不可见 |
| `agentic/search_actions.py` | `llm_stage("search_action_planning", round_N)` | spec §4.2 要求两轮分开记录 |
| `agentic/coverage.py` | 同上；`_semantic_check` 增加 `round_index` 参数；重试分支标记 wasted | coverage 有重试循环（`max_attempts=2`），重试是纯浪费，需要单独可见 |
| `explanation/planner.py` | `llm_stage("explanation_planning")` | 实测它是全场第 2 大开销，此前没有独立调用级数据 |
| `explanation/writer.py` | `write()` → `single_pass`；`write_section()` → `section.id` | fast 与 multi-pass 是两条不同路径，必须能区分 |
| `explanation/composer.py` | `llm_stage("composer", call_N)`；两条丢弃分支标记 wasted；新增 `compose_count` | **Composer 没有自己的顶层 stage**（被包在 `teaching_draft` / `teaching_revision` 内），此前它的成本完全不可见。实测单次 32.9s，比任何单节写作都贵 |
| `explanation/reviewer.py` | `llm_stage("teaching_review")`；fallback 标记 wasted | 实测单次 53.8s，全场最贵；且出现过 120s 超时全废 |
| `explanation/workflow.py` | 逐节 `SectionExecutionTrace`；`TeachingAnswerResult.section_traces`；`_trace_block` 增加 `section_execution` | spec §9 要求逐节耗时。原先 N 节被聚合成**一个** `teaching_draft` stage，节级数据不存在 |
| `agentic/retrieval_controller.py` | `_execute` 逐 action 记 `RetrievalActionTrace`；round 0/1 的 stage 加 `round_index` | spec §5 要求拆出 embedding / SQL / fusion；spec §4.2 要求两轮可分 |
| `agentic/models.py` | `StageUsage` 增加 `round_index: int \| None = None` | 见 §5 的 C3 说明 |
| `embedding/client.py` | `embed_query` 计时并记录；新增 `effective_transport` | spec §6 要求量化 embedding，含实际生效的传输方式（curl fallback 后要用真实值） |
| `cli.py` | `ask --perf / --perf-json / --repeat N`；`_run_ask()` / `_emit_perf()` | spec §20 要求机器可读 JSON；C4 要求单进程批量 |

### 3.3 新增 `tests/test_perf_trace.py`（24 条）

覆盖四类：

1. **recorder 惰性**：无 `capture()` 时 `generate()` 行为与改动前一致。
2. **调用级记录**：stage / substage / actual token / `finish_reason` / 失败与超时。
3. **`unattributed` 口径（C1）**：5 次 LLM 子级调用 + 一个非顶层 stage **不得**减少 attributed 时间。
4. **行为不变性（C2）**：开/关 tracing 各跑一次，断言答案文本、citations、`stats["path"]`、
   `stats["trace"]`（除新增 `section_execution` 外）逐键相等。

## 4. 三条设计决定（与 spec 原文不同，均已生效）

### 4.1 stage 标签走环境上下文，不改 `LLMClient` 协议

spec §14 建议「每次 `generate()` 产生 trace」，隐含给签名加 `stage` 参数。
**实施前先数了一遍：仓库里有 24 个测试替身只实现 `generate(self, messages)`**，
改签名会全部抛 `TypeError`。

改为 `observability.llm_stage(...)` 上下文管理器 + `generate()` 内部读取环境。
`llm/client.py:18` 的 protocol 与 `deepseek.py` 的签名**一行未动**，24 个替身零改动。

### 4.2 trace 数据类放 `observability/`，不放 `agentic/models.py`

理由见 §3.1（循环导入）。`deepseek.py` 里对 `error_detail` 的引用沿用仓库既有的
**函数内延迟导入**写法（`evidence_workflow.py:111` 等处本来就这么做）。

### 4.3 `unattributed` 只由互斥的顶层 stage 计算（C1）

`report.py:TOP_LEVEL_STAGES` 定义白名单：
`evidence_planning` / `search_action_planning` / `evidence_retrieval` / `coverage_check` /
`explanation_planning` / `teaching_draft` / `teaching_review` / `teaching_revision`。

`LLMCallTrace` / `SectionExecutionTrace` / `EmbeddingCallTrace` / `RetrievalActionTrace`
**一律不参与求和** —— 它们各自被上面某个 stage 包住，相加即重复计数。
（例：`teaching_draft` 已覆盖全部 N 节，再加 Σ section 就把同一段时间算两遍。）

## 5. 用户 7 条补充修正的落地

| # | 修正 | 落地位置 | 验证 |
|---|---|---|---|
| C1 | `unattributed` 只用互斥顶层 stage | `report.py:TOP_LEVEL_STAGES` | `test_child_records_do_not_enter_the_sum`、`test_section_traces_are_reported_but_not_summed` |
| C2 | 用 Mock 而非真实 LLM 验行为不变 | `TestInstrumentationChangesNothing`（3 条） | 通过；真实 LLM 另核对了 citation / 路径无异常 |
| C3 | 新增 `SectionExecutionTrace`，不扩张 `StageUsage` | `trace.py`；Section 字段全在新类 | `StageUsage` **只加了 `round_index`**，理由见下 |
| C4 | 明确 cold/warm，优先单进程批量 | `cli.py --repeat N`；文档统一用 `first_sample` / `repeat_sample` | `test_repeat_marks_the_first_sample_apart` |
| C5 | D 类须由 trace 确认进入 round 1 | 采集后用 `round_index=1` 核对 | `edge-03` / `flow-05` 各 3 次**全部确认** |
| C6 | 采集前核对两个 endpoint | 实测记入基线文档 §2.1 | `api.deepseek.com` 走代理仍 401；`dashscope` 走代理 `000` |
| C7 | token 区分 actual / estimated | `input_tokens` / `output_tokens` = actual；估算值字段名带 `_estimated` | 315 次调用 313 次有 actual token（缺的 2 次是**失败**调用，本就没有 usage） |

### 关于 C3 的一处必要偏离

**`StageUsage` 还是加了一个字段：`round_index: int | None = None`。**

C3 的原文是「不要继续扩张 `StageUsage` 来承载 `section_type` / `evidence_count` /
`context_chars` / `target_tokens` 等 **Section 专属数据**」。
`round_index` 不是 Section 数据，是检索状态机的通用维度，且**不加就无法满足 spec §4.2 与 §7**：
两轮的 `search_action_planning` / `evidence_retrieval` / `coverage_check` 记录名字完全相同，
只能靠**列表位置**区分，那是推断而不是数据。

Section 数据（`section_type` / `evidence_count` / `context_chars` / `target_tokens` /
`revision` / `revision_notes_count`）**全部**在新类 `SectionExecutionTrace` 里，
`StageUsage` 一个都没接。C3 的意图成立。

## 7. 本轮明确不做的事（spec §1 / §27）

每条都给了理由，不是「来不及」：

| 不做 | 理由 |
|---|---|
| 任何性能优化 | spec §27：与 profiling 同轮会失去可靠基线 |
| 改 asyncio / Section 并行 | spec §1 明列。且并行会改变 wall clock 语义，使本轮基线不可复现 |
| 删除或确定性化 Composer | 会改变答案文本，污染基线 |
| 改 Reviewer 门控 | 同上；且实测 11 次评审带来 7 次修订，命中率不低，不能简单关掉 |
| 改检索策略 / 修重复 embedding | spec §6 明确「本轮只记录，不优化」 |
| 换默认模型 / 大规模调 max_tokens | spec §1 明列 |
| 为性能改 Prompt | 会改变答案质量与文本，基线即失效 |
| 改 Benchmark 语义 | spec §1 明列 |
| 改默认 `teach` 模式 | spec §1 明列 |
| 实现 `docs/.../05-代码图检索实现规划.md` | 与本轮无关；该文件是一个空占位 |

## 8. 已知缺口（如实记录）

1. **perf JSON 未记录 Planner 实际选择的 `answer_depth`**，只有 `planned_section_count`。
   基线文档 §4.1 因此改用「实测路径 + sections」分类。补此字段需改代码，
   而采集期间修改会让 27 个样本前后不一致，故留到下一轮。
2. **每 case 只有 3 个样本、单机单次会话**。n=3 的 p50 只能说明量级。
   实测方差很大（同一问题不同样本可差 4.1 倍），结论应按「路径 + 节数」理解，而不是稳定分布。
3. **`artifacts/` 被 `.gitignore` 忽略**（`.gitignore:8` 的 `artifacts/*`），
   因此 27 个原始样本**未入库**，仅保留在本机 `artifacts/perf/`。
   若需要跨机器复现，应单独归档。基线文档 §8 已注明该路径。
4. **四个提交按关注点切分，但只有最终树跑过测试**。中间提交是最终树的严格子集，
   已逐个核对过符号依赖（每个提交只引用本提交或更早提交引入的名字），
   但未在中间提交上单独执行 pytest。
5. `unattributed` 里含 `_build_context`（`retrieval_controller.py:133` / `:191`）
   两段未被任何 stage 覆盖的时段。实测占比 0.0100%，可忽略，但它是已知的结构性缺口。
