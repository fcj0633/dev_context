# DevContext 回答性能全链路测试计划

## 0. 任务背景


当前 DevContext 默认回答模式已经切换为：

```text
--answer-mode teach
```

目前一次较复杂问题的完整回答耗时大约：

```text
3～5 分钟
```

这个响应速度对于实际交互使用是不可接受的。

当前阶段**不要直接进行性能优化**。

本轮任务的唯一核心目标是：

> 建立 DevContext 当前完整回答链路的性能基线，准确测量一次请求中每个阶段、每次模型调用、每轮检索和每个章节生成分别耗费多少时间，从真实数据中定位性能瓶颈和关键路径。

不得仅通过静态代码推测“哪里可能比较慢”。

必须：

```text
代码分析
+
真实运行
+
阶段级计时
+
LLM 调用级计时
+
Token 统计
+
最终性能报告
```

共同得出结论。

```text
Performance Profiling / Latency Baseline
```

暂时不要：

- 重构整个 Workflow

- 修改 Benchmark 语义

可以为了测试加入：

```text
计时

统计工具

```

但这些修改必须：

> 尽量只增加可观测性，不改变原来的业务执行行为。

# 14. LLM Client 层必须增加统一调用级 Trace

除了业务 Stage，还需要建立统一的：

```text
LLM Call Trace
```

因为一个 Stage 可能对应多个 LLM 调用。

建议每次 `DeepSeekLLMClient.generate()` 产生类似：

```json
{
  "call_id": 8,
  "stage": "section_generation",
  "substage": "S3",
  "model": "deepseek-flash",
  "reasoning_effort": "high",
  "max_tokens": 32768,
  "json_mode": false,

  "input_tokens": 5200,
  "output_tokens": 1350,

  "latency_ms": 13420,

  "finish_reason": "stop",
  "success": true
}
```

如果失败：

```json
{
  "success": false,
  "error": "...",
  "latency_ms": 14020
}
```

需要最终计算：

```text
LLM call count

LLM latency sum

LLM output tokens sum

LLM input tokens sum
```

还要区分：

```text
successful_latency

wasted_latency
```

例如：

- Planner 最终 parse 失败
- Composer 输出被丢弃
- Reviewer 请求失败后 fallback
- LLM 输出超长导致 finish_reason=length

这些都是非常重要的性能浪费。

# 15. 注意：Stage Latency 不能简单相加当 Total Latency

如果当前全部串行，大部分情况下接近成立。

但性能系统设计时不要假设未来永远串行。

因此报告中至少区分：

```text
wall_clock_latency
```

和：

```text
component_latency_sum
```

本轮当前代码主要还是同步链路，所以两者可以用来检查计时是否完整。

例如：

```text
total wall clock = 182000 ms

已统计各阶段总和 = 176000 ms

unattributed = 6000 ms
```

如果 unattributed 很大，需要继续定位。

目标：

```text
unattributed latency < 5%
```

# 17. Benchmark 测试问题设计

至少准备 8～12 个代表性问题。

不要只测试一个黄金问题。

建议分四类。

---

## A. Locate / Brief

至少 2 个。

特点：

```text
答案短
Section 少
理论上应该很快
```

例如：

```text
TicketAvailabilityTokenBucket 在哪个类中实现？
```

```text
项目中的订单取消入口在哪里？
```

目标：

测试系统是否对一个简单问题仍然执行过多 LLM 阶段。

---

## B. Standard Explanation

至少 3 个。

例如：

```text
解释 TicketAvailabilityTokenBucket 的作用和基本工作流程。
```

```text
解释项目是如何实现购票流程的。
```

```text
解释订单支付超时后项目如何处理。
```

---

## C. Detailed / Multi-pass

至少 3 个。

例如：

```text
详细解释余票令牌桶为什么这样设计，包括完整流程、并发控制、失败场景和设计取舍。
```

```text
详细解释从用户提交购票请求到订单最终创建完成的完整调用链和关键实现。
```

目标：

稳定触发：

```text
ExplanationPlanner
+
多个 Section Writer
+
Composer
+
Reviewer
```

---

## D. Evidence Insufficient / Second Round

至少 2 个。

尽量选择现有 Benchmark 中会触发：

```text
PARTIAL
MISSING
follow-up retrieval
```

的问题。

用于测量：

```text
Round 0
+
Round 1
```

到底增加多少耗时。

优先复用：

```text
benchmark/
```

中已经存在的真实案例，而不是为了性能测试凭空编问题。

# 23. 需要额外计算的几个核心指标

最终报告至少给出：

## 23.1 LLM Amplification

```text
一次用户问题
→
最终产生多少次 LLM API 调用
```

例如：

```text
LLM Amplification = 14 calls / user query
```

---

## 23.2 Sequential LLM Depth

区别于总调用次数。

例如有：

```text
14 LLM calls
```

但真正需要关注的是：

```text
有多少层必须前一个完成才能运行下一个。
```

当前同步系统可能：

```text
Sequential LLM Depth = 12
```

这个指标是后续并行优化最重要的依据之一。

---

## 23.3 Token Amplification

计算：

```text
所有 LLM 输入 token 总和
/
用户输入 token
```

虽然这个比例会非常大，但可以直观说明 Agent Pipeline 的放大成本。

另外记录：

```text
总 input tokens
总 output tokens
最终 answer tokens
```

比较：

```text
内部为了生成 3000 token 答案，
到底消耗了多少中间 token。
```

---

## 23.4 Wasted LLM Time

统计所有：

```text
已经花费模型调用时间
但结果最后没有进入最终结果
```

的调用。

包括但不限于：

```text
Planner → validation fail → fallback

Composer → invalid citation → deterministic join

Reviewer → malformed JSON → fallback accepted

Generation → finish_reason=length
```
