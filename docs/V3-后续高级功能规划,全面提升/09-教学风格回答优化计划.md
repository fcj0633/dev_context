# 1. 改 Teaching Planner：从“拆章节”变成“规划怎么教”

主要修改：

```text
src/devcontext/explanation/micro.py
```

保留现有 Evidence 绑定逻辑，但调整 Plan Schema。

### 全局增加

```python
direct_answer
core_mental_model
likely_misconceptions
```

### Section 改成

```python
id
title
reader_takeaway
new_terms
key_points
evidence_labels
target_chars
```

其中最重要的是：

```text
reader_takeaway
```

表示：

> 用户读完这一节，只需要真正记住什么。

例如：

```json
{
  "title": "为什么有锁了还要检查数据库？",
  "reader_takeaway": "锁负责减少并发竞争，数据库条件更新才负责最后防止座位被重复卖出。",
  "new_terms": ["条件更新"],
  "target_chars": 180
}
```

### 约束

```text
每节 new_terms <= 2
target_chars = 100～250
detailed 默认 6～9 节
```

不要继续使用大 `target_tokens` 作为小节长度提示。

# 2. 重写 Streaming Writer Prompt

主要修改：

```text
src/devcontext/explanation/stream_writer.py
```

保留：

```text
SectionParser
Section marker
Citation allowlist
partial 状态
streaming transport
```

这些都不要改。

只重写 Writer 的教学规则。

核心要求：

```text
1. 先解释现象，再给专业术语。
2. 先说为什么，再说项目用了什么技术。
3. 每节只完成 reader_takeaway 这一件事。
4. 每节最多引入 new_terms 中的 1～2 个新概念。
5. 第一次出现专业术语时，必须先用普通中文解释。
6. 不允许连续堆类名、方法名、状态名。
7. 能用一个简单场景解释时，优先举例。
8. 代码用于证明解释，不是解释本身。
9. 句子尽量短，一个句子只表达一个主要关系。
10. 不要为了“完整”扩展计划之外的内容。
```

最重要的语言顺序：

```text
现象
↓
为什么是问题
↓
怎么解决
↓
这个技术叫什么
↓
代码如何实现
```

而不是：

```text
术语
↓
源码
↓
让用户自己理解
```

# 3. 调整 Section 的组织方式

Planner 不要按组件机械拆：

```text
令牌桶
锁
事务
订单
补偿
```

而要按用户理解过程拆。

以购票一致性为例，目标结构类似：

```text
S1 到底是谁最后决定一张票还能不能卖？

S2 Redis 令牌桶到底是干什么的？

S3 为什么需要让购票请求排队？

S4 有锁了为什么还要数据库再检查一次？

S5 为什么占座和写车票必须一起成功？

S6 为什么订单创建不能放进这个事务？

S7 如果订单创建失败，刚占的座位怎么办？

S8 最后把整条流程串起来
```

也就是说：

> 标题优先写成“用户会问的问题”，而不是技术名词。

# 7. 真实 A/B 测试

不要一开始跑很多题。

先用同一个：

> 详细解释当前购票占座的数据一致性是如何保证的

比较：

```text
A：当前 single-stream V1

B：Teaching Answer V2
```

重点不要先看速度。

先人工比较：

```text
① 第一次读能不能懂
② 是否需要反复读一句话
③ 主线是否清楚
④ 是否一次塞太多术语
⑤ 是否知道“为什么”
⑥ 是否能读完后自己复述
```

尤其看是否从当前这种：

> “段内用锁和条件更新做成原子，段间用提交后副作用、幂等状态推进和失败补偿收敛到最终一致。”

变成类似：

> “座位先在 ticket 服务里安全占住。如果后面的订单创建失败，就把刚才占的座位释放回来。所以这里不是一个跨服务的大事务，而是前面先成功，后面失败时再补回来。”
