开始优化时以：

```text

LLM calls:

```

顶层耗时：

| Stage | 占总耗时 |
|---|---:|
| teaching_draft | 37.7% |
| explanation_planning | 20.1% |
| coverage_check | 11.4% |

| teaching_revision | 8.1% |

重要实测结果：


也就是说：

> 当前主要问题不是 Retrieval，而是 LLM orchestration 的调用放大和串行 Critical Path。

本轮优化目标不是降低回答质量，而是：

> 用更少、更稳定、更短的 Sequential LLM Critical Path，获得接近当前质量的回答。

# 1. 本轮原则

本轮可以进行性能优化，但必须遵守以下原则。

## 1.1 不优先优化 Retrieval

已经实测：

```text
整个 Retrieval = 2.0%
```

因此本轮不得把主要时间花在：

- pgvector
- BM25
- SQL
- Fusion
- Embedding cache
- Embedding batch

这些可以最后处理。

---

## 1.2 不一次性把所有优化混成一个提交

必须分阶段：

```text
P0 Observability V2
↓
P1 Explanation Planner
↓
P2 Section 并行
↓
P3 Composer
↓
P4 Reviewer / Revision
↓
P5 Retrieval Workflow
↓
P6 Transport / Streaming（如仍有必要）
```

每一个阶段都必须：

```text
改代码
→ 测试
→ 性能小样本
→ 质量回归
→ 记录结果
→ 再进入下一阶段
```

否则最终无法知道：

> 到底是哪项优化真正带来了收益。

# 3. P0：先升级 Profiling，使其支持并发优化

这一步必须在 Section 并发之前完成。

原因：

当前 Trace 假设：

```text
所有 LLM 串行
```

并行以后：

```text
Σ LLM latency
```

会大于：

```text
wall-clock latency
```

这是正常现象。

如果仍按当前统计方式分析，会误判。

---

## 3.1 修改 LLMCallTrace

当前：

```text
LLMCallTrace
```

增加：

```text
started_offset_ms
ended_offset_ms
```

相对于当前 request 的：

```text
PerfRecorder.request_started_at
```

记录。

SectionExecutionTrace 同样增加：

```text
started_offset_ms
ended_offset_ms
```

---

## 3.2 PerfRecorder 增加并发安全

当前 `recorder.py`：

```python
call_id = len(recorder.llm_calls) + 1
recorder.llm_calls.append(...)
```

一旦 Section Writer 并行，这种实现存在竞争风险。

改造：

```text
PerfRecorder
 ├── lock
 ├── next_llm_call_id()
 ├── append_llm_call()
 ├── append_section()
 └── ...
```

使用：

```python
threading.Lock
```

保护：

```text
ID 分配
list append
mark wasted
```

不要依赖：

```text
GIL 恰好没出问题
```

---

## 3.3 mark_last_call_wasted 不再依赖全局最后一次调用

并发情况下：

```python
recorder.llm_calls[-1]
```

不能代表当前线程刚刚执行的调用。

修改为：

```text
LLM call_id
```

或者 context 内保存当前调用 ID。

推荐：

```text
_llm_call ContextVar
```

调用返回后：

```text
mark_call_wasted(call_id, reason)
```

保证不会误标其他线程的调用。

---

## 3.4 ContextVar 必须支持 ThreadPool

P2 使用 `ThreadPoolExecutor` 后，ContextVar 默认不能简单假设自动传播。

每个 Section task 使用：

```python
contextvars.copy_context()
```

例如：

```python
ctx = copy_context()
executor.submit(ctx.run, function, ...)
```

每个 task 必须独立 copy context。

---

## 3.5 增加并发指标

Performance Report 新增：

```text
llm_call_count
llm_work_ms
llm_wall_span_ms
peak_llm_concurrency
parallelism_ratio
```

其中：

```text
llm_work_ms
=
所有 LLM latency 求和
```

而：

```text
llm_wall_span_ms
=
真实时间轴覆盖范围
```

并行后允许：

```text
llm_work_ms > wall clock
```

这是正常的。

---

## 3.6 修正 Revision 的 Trace Stage

目前 `TeachingWriter.write_section()` 内部固定：

```python
llm_stage("teaching_draft", section.id)
```

但 `_revise()` 调它时实际属于：

```text
teaching_revision
```

导致调用级统计会把 Revision Writer 算进：

```text
teaching_draft
```

本轮修正。

建议：

```python
write_section(
    ...,
    trace_stage="teaching_draft"
)
```

Revision：

```python
trace_stage="teaching_revision"
```

注意：

不要改 `LLMClient.generate()` 协议。

# 20. P2 错误行为必须保持可控

当前串行实现中：

某 Section generation 失败可能终止 Multi-pass。

并行以后必须定义明确行为。

建议：

```text
某 section 失败
→ 保留成功 section
→ 对失败 section 记录 trace
→ 允许一次单独 retry
→ retry 仍失败才走原 fallback/error 语义
```

不要因为一个 Section：

```text
网络短暂失败
```

把其他已经成功的 Section 全部浪费掉。

但是：

```text
retry <= 1
```

禁止无限重试。

## 最核心的执行判断

这轮不要把任务理解成：

> “把几个 API 调快一点。”

应该把它理解成：

```text
当前：
User Query
→ 11～23 次串行 LLM

目标：
User Query
→ 少量必要串行阶段
→ 可并行的生成阶段 fan-out
→ 确定性后处理
→ 只在确实有价值时 Review
```

这才是本轮优化的核心。
