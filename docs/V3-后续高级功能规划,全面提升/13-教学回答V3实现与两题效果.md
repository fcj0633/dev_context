# 教学回答 V3：实现、实测与质量判断

## 交付范围

已实现独立 V3 模型、解析器、Planner、Evidence Organizer、Controlled Writer 和工作流，并接通配置、CLI、结果与诊断。默认仍为 multi_pass；显式开启 V3。详细设计的 P1–P15 和全部核心教学能力保留，未增加在线 Reviewer、自动重规划、LearnerModel 或 benchmark。

正常成功是一次 Planner 和一次流式 Writer；检索阶段仍有既有的规划、搜索行动与覆盖检查模型调用。不能将“两次教学调用”说成整个请求只有两次模型调用。

## 系统契约如何落实

- Planner 在一次调用内给出目标、读者起点、互斥 WHY/HOW 骨架、单一 Claims、地图、场景、教学增量和展开位置。解析器检查类型、状态、引用、目标覆盖及分支结构。
- PROJECT_FACT 只能 CONFIRMED，PROJECT_INFERENCE 可以 INFERENCE/UNKNOWN。HOW 终态分别存储已建立保证和未知边界，UNKNOWN 有原因且不能当成已建立保证。
- Organizer 汇总 owner、may_reference、Spine、checkpoint、地图、相关区别及前文已建立认识的 Claims，必要证据保留完整，正文全局去重。首节与收束节都绑定全局地图。前文知识可简短承接，主要展开位置不变。
- Writer 收到逐节完整契约及实际证据，按类型使用一套完整正文示范。协议校验通过一节就发布；部分发布后错误不重播，明确返回 partial；失败不伪装完整答案。
- 共享 180 秒 deadline 从请求入口覆盖检索、嵌入、数据库与模型调用。重试消耗剩余预算；阶段不会重置请求计时。必要材料缺失或超真实模型窗口明确失败。
- 支持类型的 question_form 从主任务派生；重复 owner 引用和单一一致类型包装可无损归一化并记录 warning。未知引用、互斥骨架冲突、错误分支和未知保证仍拒绝。

| 收束和承接引用真实材料却缺章节绑定 | 补充地图依赖与前文认识依赖 | 不允许引入未知材料或重新完整展开前文 |
| 场景停留在蓝图、正文泛述职责 | Writer 强制落实具体 setup 与 checkpoint 状态，正常路径后回到分叉点 | 仍需阅读判断场景是否有助理解 |
| 将租约兜底或失败分类扩大为保证 | Planner/Writer 同时区分策略、协议前提、外部事实；HOW 复跑保留这些条件 | 不证明真实业务最终收敛 |
| 方法签名被当成固定返回值的强约束 | 同时明确接口声明、默认实现、注释与执行保证的区别，WHY 再次验证 | 格式合法不是语义正确的证明 |

## 主观质量判断与局限

**我认为这次相对旧回答有明显的结构与理解路径改善，HOW 最明显；但还不能认定已经稳定达到优质教学回答。**

WHY 能公平承认集中分支的可行性，并把采用责任链的原因落实为“改动位置、装配与顺序声明”。最后复跑把接口签名误当固定返回值的问题修正了：它明确说明 `mark()` 值由实现给出，注释是约定而非编译器强制。贯穿例子能解释新增规则如何进入执行集合。仍有重复：第一、二、四节反复解释改动位置；第四、五节的证据止点占比偏大。机制先后较清楚，但术语仍偏早，源码名称与历史材料语言较密集。失败路径可进一步把“节点抛异常且容器不捕获”这一条件讲透，而不是只留下无法确认的笼统止点。

HOW 使用同一次请求解释准入→锁内本地事务→条件更新和写票→提交后远程订单→失败分叉→回调状态推进。读者较容易重建正常过程，能区分令牌不裁决座位、锁不覆盖远程订单、数据库条件更新作最终裁决、本地事务不等于跨服务共同事务。明确失败与结果未知从已提交状态分叉；当前答案也明确区分了代码的失败分类与远程事实，未再宣称所有兜底一定收敛。仍需改善：第一段的组件和引用密度高，每节重复“边界”句式，基础读者对事务、条件更新与锁的关系还可得到更自然的铺垫。

**现阶段适合以显式 V3 模式继续试用，默认 multi_pass 保留。** 不是因为功能删减，而是因为证据覆盖、模型的语义判断和语言执行仍决定最终效果。检索两轮与 Planner high 推理是主要时间压力，不能只靠缩正文提速。下一步应优先处理同义 Claim、将条件嵌入因果解释、关键执行体证据覆盖及这些问题的阶段归属，不以增加一层泛化 Reviewer 代替具体修正。


研究支撑目标明确、条件解释、示例学习与上下文组织，但不直接证明这套两次调用架构必然提升学习效果。本次没有学习者复述实验，也没有广泛题集验收，判断是基于真实正文阅读的工程判断。
