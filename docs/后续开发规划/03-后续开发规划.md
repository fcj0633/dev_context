
重构为：

# 一、先重新冻结最终目标

当前系统最大的抽象问题已经可以从源码直接确认：`QueryRouter` 的最高层状态只有 `CODE / DOC / MIXED`，甚至 LLM Router 的唯一任务就是三分类。

随后 `ContextSufficiencyChecker` 又根据这个分类硬编码“CODE 必须有代码、DOC 必须有文档、MIXED 必须两者都有”。 

这对于 Retrieval 实验是合理的，但不应该继续作为最终 Agent 的思考模型。

因此新的 P0 应冻结为：

```text
用户自然语言问题
        ↓
Question Understanding
        ↓
Question Planner
        ↓
SubQuestions
        ↓
Evidence Planner
        ↓
选择搜索工具
        ↓
Semantic Discovery
        ↓
发现 Symbol / 项目术语
        ↓
Symbol / Keyword / Source 精确查找
        ↓
Evidence Pool
        ↓
Evidence Sufficiency
      ↙          ↘
不足              足够
↓                  ↓
Search Replan   Answer Planner
↓                  ↓
Tools          Grounded Answer
                   ↓
                Citation
```

项目边界继续保持：

```text
Search
Understand
Explain
Trace
```

**不扩展到 Coding Agent：**

```text
Edit
Run
Fix
Commit
PR
```

这样仍然符合最初“Context Engineering + Retrieval + Evaluation”的学习目标，而不会变成一个缩小版 Cursor。

# 二、现有代码怎么处理

这是这次重构最重要的一点：**大约 70%～80% 的现有能力都应该保留。**

| 当前模块 | 处理 | 新角色 |
|---|---|---|
| `ingestion/` | 保留 | 项目知识解析 |
| `embedding/` | 保留 | Semantic Search 基础 |
| `storage.py` | 保留并小扩展 | Search Tool 数据层 |
| `retrieval/hybrid.py` | 保留 | 一种检索实现 |
| `retrieval/service.py` | 保留 | 搜索底座 |
| `context/builder.py` | 保留 | Evidence → LLM Context |
| `answer/generator.py` | 保留并调整 | Grounded 最终生成 |
| `llm/` | 保留 | 模型调用抽象 |
| `evaluation/runner.py` | 保留 | **Retrieval Benchmark** |
| `routing/router.py` | 降级 | 不再作为主 Agent 入口 |
| `retrieval/policy.py` | 重构 | 从 QueryType Policy → Tool 层 |
| `agentic/sufficiency.py` | 重构 | Source Sufficiency → Evidence Sufficiency |
| `agentic/rewrite.py` | 替换/演进 | Query Rewrite → Search Replanner |
| `agentic/workflow.py` | 重构 | 从 Retry Loop → Planning/Search Loop |

当前 `Chunk` 本身已经保留了 `class_name / symbol_name / signature / heading_path / content` 等足够丰富的信息，因此完全没必要重新做解析层。

`SearchResult` 同样已经包含 Symbol、路径、源码行号等信息，很适合下一阶段做 **Semantic → Symbol Discovery**。

所以千万不要重新折腾 Chunk、Embedding 模型、pgvector。

# Phase 1：Question Planner V1

这是**下一步真正应该开发的功能**。

不要先做 LangGraph。

新增：

```text
src/devcontext/planning/
├── __init__.py
├── models.py
└── question_planner.py
```

核心数据结构可以控制得非常简单：

```python
@dataclass
class SubQuestion:
    id: str
    question: str
    purpose: str

@dataclass
class QuestionPlan:
    original_query: str
    intent_summary: str
    sub_questions: list[SubQuestion]
    answer_depth: str
```

例如：

```text
用户：
为什么 Redis 余票桶不直接作为真实库存，
然后通过 MQ 异步落库？
```

Planner 输出：

```text
SQ1 当前 Redis 余票桶的职责是什么？
SQ2 项目真正扣减座位库存在哪里完成？
SQ3 为什么 Redis 不作为库存真相源？
SQ4 当前 MQ 在购票/支付链路承担什么职责？
SQ5 Redis 原子扣减 + MQ 方案与当前设计有什么差异？
```

注意，这里**完全不要出现 CODE/DOC/MIXED 分类**。

Question Planner 只回答：

> 用户到底想知道哪些事情？

### Phase 1 验收

最重要的不是“Planner Prompt 很高级”，而是用 10～15 个自然语言问题人工检查：

```text
是否漏掉关键子问题？
是否拆得过碎？
是否出现重复问题？
是否偷偷回答问题而不是规划？
```

你那个：

```text
详细解释用户注册的整个业务流程
```

应该被规划成：

```text
入口
→ 参数校验
→ 唯一性校验
→ 核心注册流程
→ 数据库写入
→ 缓存/布隆过滤器
→ 事务与异常
→ 返回结果
```

这本身就能开始解决现在 `finish_reason=length` 时回答结构失控的问题。

# Phase 2：Evidence Planner V1

Question Planner 解决：

```text
要回答什么？
```

Evidence Planner 解决：

```text
每个问题需要查什么？
```

增加：

```python
class EvidenceType:
    CODE
    DOCUMENT

@dataclass
class EvidenceRequirement:
    id: str
    sub_question_id: str
    description: str
    preferred_sources: list[str]
```

这里才重新使用：

```text
CODE
DOCUMENT
```

例如：

```text
SQ2：
项目真正扣库存在哪里完成？

Evidence:
- CODE：实际扣减方法
- CODE：条件更新/锁/事务
- DOCUMENT：如果存在，相关设计说明
```

而：

```text
SQ3：
为什么 Redis 不作为真相源？

Evidence:
- DOCUMENT：库存模型设计
- CODE：Redis token 与 DB seat 的实际职责边界
```

所以从此以后：

```text
CODE / DOCUMENT
```

代表：

> **Evidence Type**

而不是：

> User Query Type。

这一步完成后，旧的 `QueryType.CODE/DOC/MIXED` 就应该逐渐退出主 Workflow。

# Phase 3：Tool-based Retrieval + Semantic-to-Symbol

这是整个重构中**最值得做成项目亮点**的一步。

第一版只做四个 Tool：

```text
semantic_search(query)
keyword_search(query)
symbol_search(symbol)
read_source(...)
```

不要一口气搞十几个工具。

其中：

### `semantic_search`

直接复用：

```text
Embedding
+
Vector Search
```

它的职责变成：

> 用户不知道项目术语时，先发现方向。

### `keyword_search`

复用现有 Keyword Search。

负责：

```text
字符串
配置
类名
方法名
业务术语
```

### `symbol_search`

这个建议新增。

例如：

```text
symbol_search("UserRegisterParamNotNullChainHandler")
```

优先查：

```text
class_name
symbol_name
signature
```

而不是再跑全文本 Hybrid。

### `read_source`

第一版不用真的访问文件系统。

完全可以：

```text
chunk_id
file_path
symbol
→ 从 knowledge_chunk 找对应代码正文
```

以后如果确实需要完整文件上下文，再扩展读取真实源码。

---

## 最关键的 Demo：Semantic → Symbol

例如：

```text
用户：
用户注册时哪些地方会校验参数？
```

系统首先：

```text
semantic_search("用户注册 参数校验")
```

发现：

```text
UserRegisterReqDTO
UserInfoController
UserRegisterParamNotNullChainHandler
```

然后：

```text
symbol_search("UserRegisterParamNotNullChainHandler")
symbol_search("UserRegisterReqDTO")
```

最终精确定位源码。

这个故事比：

> “我的项目用了 pgvector”

强很多。

它真正说明你理解：

```text
自然语言
≠
源码 Symbol
```

以及如何搭桥。

# Phase 4：Evidence Pool + 新 Sufficiency

现在 `ContextSufficiencyChecker` 的逻辑本质仍然依赖：

```text
RouteDecision
→ Required Source
```



重构后不要判断：

```text
CODE 有没有？
DOC 有没有？
```

而是判断：

```text
ER1 是否满足？
ER2 是否满足？
ER3 是否满足？
```

建议新增：

```python
@dataclass
class EvidenceItem:
    requirement_id: str
    search_result: SearchResult
    why_relevant: str

@dataclass
class EvidenceStatus:
    requirement_id: str
    satisfied: bool
    reason: str
```

例如：

```text
Requirement:
找到真实库存扣减位置

Evidence:
PurchaseTicketTxService.doPurchaseInTransaction
SeatService...
UPDATE ... WHERE seat_status = AVAILABLE

Status:
SATISFIED
```

而：

```text
Requirement:
项目是否明确评估过 Redis + MQ 库存方案

Status:
UNSATISFIED
```

这时候 Sufficiency 才是真正意义上的：

> Evidence Completeness。

# Phase 5：把 Query Rewrite 升级成 Search Replanner

当前 Workflow 已经有一个很好的基础：会累积旧结果、检查 Sufficiency、最多进行两次 Retry。

但不足时目前只能：

```text
rewrite query
→ search again
```



下一阶段应该让 Replanner 输出：

```python
SearchAction
```

例如：

```text
missing:
“未找到 MQ 当前业务用途”

next actions:

1. semantic_search("RocketMQ 支付通知")
2. keyword_search("RocketMQ")
3. semantic_search("支付成功 下游通知")
```

如果发现：

```text
PayNotifyCompensateJob
```

下一轮：

```text
symbol_search("PayNotifyCompensateJob")
```

这就出现了真正的：

```text
Observation
→ 新 Symbol
→ 下一步 Action
```

而不是：

```text
同一句话换个说法再搜一次
```

### Retry 限制仍然保留

不要做无限 Agent。

建议：

```text
MAX_ROUNDS = 4
MAX_TOOL_CALLS = 8~10
```

明确预算比“让 Agent 自己一直跑”更适合这个项目。

# Phase 6：Answer Planner

这是我认为第二重要的新功能。

你已经真实遇到：

```text
详细解释用户注册的整个业务流程
→ finish_reason=length
```

现在 `AnswerResult` 只保存：

```text
answer
used_citations
```



缺少真正的回答结构。

新增：

```text
answer/planner.py
```

输出类似：

```python
AnswerPlan:
  summary
  sections:
    - 注册入口
    - 参数校验
    - 唯一性保证
    - 核心事务
    - Redis / Bloom Filter
    - 异常与回滚
    - 总结
```

每个 Section 可以绑定：

```text
EvidenceRequirement IDs
```

于是最终 Generator 不再面对：

```text
一大坨 Context
```

而是面对：

```text
这一节回答什么
+
这一节允许使用哪些证据
```

第一版不用分多次 LLM 请求。

只要先产生：

```text
AnswerPlan
```

再一次生成完整答案就行。

如果之后仍然容易超长，再做：

```text
section-by-section generation
```

这是 P1，不要现在做。

```text
├── collected_evidence
├── discovered_symbols
├── tool_history
```

流程：

```text
Plan
 ↓
Evidence Plan
 ↓
Select Tool
 ↓
Execute
 ↓
Observe
 ↓
Update Evidence
 ↓
Sufficiency
 ├── insufficient → Replan → Select Tool
```

这时候你有：

```text
State
Node
Conditional Edge
Cycle
Retry
```

LangGraph 才是在解决真实问题。

而不是简单把：

```text

```

换成 Graph API。

# 九、最终面试故事也会因此发生变化

旧版本可以讲：

> 我实现了 Java/Markdown Structure-aware Chunk，使用 Keyword + Vector + RRF 做 Hybrid Retrieval，并建立严格 Benchmark，通过 Router 和来源感知策略优化 MIXED Retrieval。

这个故事应该保留，它是你的**第一阶段工程演进**。

新版本则可以继续讲：

> 后来通过真实用户问题发现，CODE/DOC/MIXED 只是检索层分类，并不适合作为用户意图。我把它降级为 Evidence Type，引入 Question/Evidence Planning，并把向量检索从系统中心变成 `semantic_search` 工具，用 Semantic Search 发现项目术语，再通过 Symbol Search 精确定位代码。当证据不足时，系统不是简单改写 Query，而是根据 Missing Evidence 重新规划搜索动作，最后由 Answer Planner 基于证据组织完整回答。

这个演进逻辑非常完整：

```text
能检索
↓
能评测
↓
能 Grounded Answer
↓
发现 Router 抽象不足
↓
重构为 Project Understanding Agent
```

这比一开始直接声称：

```text
我做了一个 LangGraph Agent
```

更有技术含量。

## 最终优先级

如果只记住接下来最重要的六步，就是：

```text
Question Planner
      ↓
Evidence Planner
      ↓
Tool-based Retrieval
      ↓
Semantic → Symbol
      ↓
Evidence Sufficiency + Search Replan
      ↓
Answer Planner
```

**LangGraph 放最后。**

而你下一次实际编码，建议就从 **`Question Planner V1`** 开始。它是这次架构转型的第一个真正分界点：从“根据 Query 检索”进入“先理解问题，再决定如何调查”。
