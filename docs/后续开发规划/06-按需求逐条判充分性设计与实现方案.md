> 阶段：Phase 4
> 前置文档：`03-后续开发规划.md`（Phase 4 定义）、`05-Evidence Planner 设计与实现方案.md`（上游）

# 一、为什么要实现这个功能

## 1. 现状：判定还停在"来源类型"粒度

Evidence Planner 已经把证据需求逐条化了：`EvidencePlan` 产出 ER1…ERn，每条声明它需要哪些来源。但**下游的充分性判定没有跟着细下来**：

```text
现在做的事：
  required_sources = _required_sources(union_route(decisions).query_type)
                   = {"CODE", "DOCUMENT"}
  然后看最终 Context 里这两类"有没有"
```

也就是说，上游辛辛苦苦逐条声明了需求，下游却把它们**并回成一个二元素集合**再判。

## 2. 这处不匹配的具体后果

对"订单关闭为何这样设计"，证据规划产出 6 条需求，其中 ER6 要的是设计取舍说明。

假设 ER6 一无所获——检索回来的东西跟设计取舍无关。但 ER1–ER5 的代码证据都在，最终 Context 里 CODE 和 DOCUMENT 两类**都存在**。

于是：

```text
来源检查：需要 {CODE, DOCUMENT}，实际 {CODE, DOCUMENT} 都有 → 通过
语义检查：模型看整体证据，大体支持这个问题 → 判定足够
结果：系统认为证据充分，照常回答
```

**ER6 完全没找到证据这件事，从头到尾没有被任何人发现。** 更糟的是，答案里那一节本来应该说明"设计取舍"的部分，会在没有证据的情况下被模型自由发挥。

## 3. 目标

把判定改成逐条：

```text
ER1 满足吗？ → 是
ER2 满足吗？ → 是
...
ER6 满足吗？ → 否，没找到设计取舍的说明
→ 证据不足，缺口是 ER6
```

价值有两层：**一是准确**（一条需求没找到就被指出，而不是被同类需求的证据掩饰）；**二是可定位**（缺口从"缺少文档证据"这种笼统描述，变成"ER6：设计取舍说明"这种能直接去查的清单）。

缺口清单还会顺着现有链路进入答案的 `Known Evidence Gaps`，因此"哪一条没找到"会自动出现在部分回答里。

## 4. 与整体路线的关系

这是 `01-项目开发方向转型.md` 那条主线上的第四步：

```text
用户意图 → 子问题 → 证据需求 → 逐条判定是否满足 → 重新规划搜索
  ✅        ✅         ✅              ← 本轮          ↑ 下一阶段
```

也就是说，本轮完成后，"缺哪条需求"才第一次成为一个**结构化的事实**，而这正是下一阶段 Search Replanner 的输入。没有它，Replanner 无从知道该去补什么。

# 二、边界

## 2.1 做什么

1. 新增数据结构 `EvidenceStatus`（需求标识 + 是否满足 + 理由），并让 `MissingAspect` 携带需求标识、`SufficiencyResult` 携带逐条状态。
2. 在扇出阶段**记录每条需求各自检索到了什么**，作为归属表；不额外调用模型来判断归属。
3. 新增逐条判定方法：先按"该需求自己的证据有没有进最终 Context"做确定性检查，再由**一次**模型调用逐条判语义是否真的支持。
4. `enough` 的定义改为**全部需求都满足**。
5. 未满足的需求派生成缺口，带需求标识，继续流向部分回答的缺口说明。
6. 逐条状态写入 Trace，`--debug` 下额外给一行可读摘要。

## 2.2 不做什么

- **不做质量指标**（证据需求覆盖率、证据命中率）。那是**度量**，本轮做的是**机制**；混在一轮里，一旦数字不好看就无法判断是机制错还是度量错。留到下一步。
- **不做 `EvidenceItem` 存储结构**。内部只需要"哪条需求有哪些 chunk"这一个映射，存全量 `SearchResult` 对象既重又与只读的 Context 重复。
- **不做 Search Replanner**。本轮只判定"缺哪条"，不做"根据缺口重新规划搜索动作"。
- **不做 Tool 层、Semantic-to-Symbol、Answer Planner 模块**。
- **不做"一条子问题拆多条需求"**。当前是一对一，本轮不动这个粒度。
- **不改检索策略、不改 `RouteDecision`、不删 `QueryType`**。L1 基准仍依赖它们。
- **不改旧的 `check()` 方法及其提示词与 JSON 契约**。回退路径必须逐字节不变。

# 三、具体如何实现

## 3.1 数据模型

新增与扩展都在 `src/devcontext/agentic/models.py`：

```text
EvidenceStatus（新增）
  requirement_id   ER1..ERn        由程序赋值
  satisfied        bool            模型填
  reason           非空字符串       模型填

MissingAspect（加一个字段）
  requirement_id   str = ""        "" 表示旧路径，没有需求身份

SufficiencyResult（加一个字段）
  statuses         tuple[EvidenceStatus, ...] = ()
```

两个字段都**带默认值**。原因不是图省事，而是这三处约束：

- `MissingAspect` 与 `SufficiencyResult` 都是 `frozen=True, slots=True`，且在 5 个测试文件里用**位置参数**构造。加必填字段会让这些构造点一起报错。
- `requirement_id` 取空串是**有意义的取值**——旧工作流没有需求概念，空串正表示"这条缺口不属于任何需求"，不是占位符。
- `statuses` 挂在 `SufficiencyResult` 上，会顺着 `AgenticRoundTrace.to_dict` → `AgenticTrace.to_dict` 自动进入 `--debug` 的 Trace，不需要额外接线。

**注意 `to_dict` 是契约面。** `MissingAspect.to_dict` 用的是 `asdict`，`SufficiencyResult.to_dict` 是手写的——两者加字段后，所有序列化输出都会多一个键，需要复查依赖 trace JSON 的断言。

## 3.2 证据归属：按构造归属，并保证切片对齐

### 归属从哪来

扇出循环里**本来就知道**答案：每个子问题用了哪条需求（`requirements[index]`），那次检索返回了什么。所以归属不需要模型判断，只需要**别把它丢掉**。

现在的问题是丢得太彻底：`_merge_results` 把各子问题的结果拍平成一个按 id 去重的列表，`ContextBuilder` 还会重新去重并把条目标号全部重排为 `C1..Cn`。归属信息在两处都被丢掉。

做法是让扇出**多返回一份平行视图**：

```text
_fan_out(plan, evidence_plan)
  → (decisions, merged, sub_question_traces, evidence_index)

evidence_index: dict[requirement_id, list[chunk_id]]
```

`merged` 与 `sub_question_traces` 的语义都不变：前者继续供给 `ContextBuilder`，后者继续进 Trace。`evidence_index` 是给充分性判定用的。

**连接键是 `chunk_id`。** 已核实 `ContextItem.chunk_id` 就是 `SearchResult.id`，而 `ContextBuilder` 重排的只是条目标号、不动 `chunk_id`，所以这条连接成立。

### 一个必须修的切片错位

扇出循环里用的是 `plan.sub_questions[:max_sub_questions]`——只截断了子问题，**没有截断 `requirements`**。

当配置的子问题上限小于实际数量时（规划器上限 6，工作流上限可配），`requirements[index]` 会与子问题错位，尾部的需求永远拿不到检索，于是它们在阶段一里必然判失败——而失败理由是假的。

**修法**：子问题与需求取**同一段切片**，再进入循环。

## 3.3 两阶段判定

新增方法挂在 `ContextSufficiencyChecker` 上，**旧 `check()` 一行不动**：

```text
check_requirements(query, requirements, evidence_index, bundle) -> SufficiencyResult
```

### 阶段一：确定性检查（不调模型）

对**每条需求**，看它自己的证据里有没有 chunk 进了最终 bundle，且来源属于该需求的 `preferred_sources`。

判定范围是"这条需求检索到、且最终确实进了 Context"的交集——被截断或去重掉的证据支撑不了回答，不能算数。

**关键点：三条互相独立的失败原因必须分开报。**

| 情况 | 含义 |
|---|---|
| 该需求从未检索到任何东西 | 检索本身没命中 |
| 检索到了，但全被 `top_k` 预算截掉 | 证据存在，但没进最终 Context |
| 进了 Context，但来源类型不符合需求 | 找到了材料，但不是要的那类 |

第三种是"找到了但不是要的"，前两种是"没找到"。三者混成一个"缺少代码证据"会误导排查方向——**尤其第二种**：`PLANNED_TOP_K` 默认 12，6 条需求各召回 3 条就是 18 条，尾部需求被截掉是常态。如果报成"缺少代码证据"，会让人去怀疑检索质量，而真正的问题是预算。

因此 `evidence_index` 除了"哪些 chunk 进了 Bundle"，还要能区分"哪些根本没检索到"。

任一需求未通过阶段一 → 立即返回不足（`decision_source="rules"`），为每条未通过的需求生成一个带 `requirement_id` 的 `MissingAspect`，**不调用模型**。这与现有的"缺来源就直接返回"完全同构。

**通过的需求也要给状态。** 否则规则路径下的 `statuses` 只包含失败项，读起来像"只有这几条被判过"。为通过项合成 `satisfied=True` 与一句规则理由，让 `statuses` 始终覆盖全部需求。

### 阶段二：逐条语义判定（一次模型调用）

所有需求都过了阶段一才调用。把每条需求（描述 + 来源 + 它归属的证据）一并交给模型，要求**逐条**给结论。

一次调用而不是每条一次：需求之间是并列关系，没有相互依赖，拆成多次只是把一次上下文重复 N 遍。

结果合成：

- `enough` = **全部** `satisfied`
- `missing_aspects` 由未满足的需求派生（带 `requirement_id` 与需求描述）
- `statuses` 原样挂到 `SufficiencyResult`
- `reason` 综合生成（该字段在 `src/` 里从没被读过，只进 Trace）

## 3.4 LLM 契约

模型**按给定顺序**返回一串状态，程序按序赋 `requirement_id`——沿用项目一贯的"标识由程序定、模型只填措辞"：

```json
{"statuses": [{"satisfied": true, "reason": "非空理由"}, ...]}
```

严格校验（任一条不满足即整体回退）：

| # | 规则 |
|---|---|
| 1 | 响应非空、能被 JSON 解析 |
| 2 | 顶层字段集合精确等于 `{"statuses"}` |
| 3 | 数组长度**恰好等于**需求数 |
| 4 | 每项字段集合精确等于 `{satisfied, reason}` |
| 5 | `satisfied` 必须是布尔 |
| 6 | `reason` 非空单行 |

**不做局部容忍**：出现多余或缺失的键就整体拒绝，而不是忽略那一项继续。逐条判定的价值就在于"每条都有明确结论"，容忍缺项会让"某条没被判过"和"某条判为满足"变得无法区分。

**新提示词用「证据需求审查器」作标识语**，与旧提示词的「证据充分性审查器」区分开——测试的假客户端靠这句话分派调用，两者必须不同，否则新调用会被旧的假响应喂进旧 schema。

## 3.5 接入与回退

`src/devcontext/agentic/planned_workflow.py`：

```text
decisions, merged, traces, evidence_index = self._fan_out(plan, evidence_plan)

if evidence_plan.requirements:          ← 有需求才走逐条判定
    sufficiency = checker.check_requirements(...)
else:                                   ← Evidence Planner 失败，退回旧行为
    sufficiency = checker.check(query, union_route(decisions), bundle)
```

**分流条件必须是"有没有需求"，不能是"证据规划成不成功"。** Evidence Planner 失败时产出的是**空需求**；如果拿空需求去走逐条判定，"零条需求全部满足"会**空真地判为足够**——这是最容易漏掉的一处错误。

**两处调用点都要同一条件**：初次判定与重试后的判定。只改一处会让重试路径走进空真分支。

## 3.6 重试归属

改写之后新增的结果必须归到某条需求，否则一次重试永远补不上缺口——归属表里没有新证据，阶段一照旧失败。

**归属规则：按 `RewriteResult.targeted_aspects` 里的需求标识。**

这条链是天然存在的：改写器本来就是拿 `missing_aspects` 去生成新查询的，而它把这个元组原样复制进了 `targeted_aspects`。只要 `MissingAspect` 带上了 `requirement_id`，这条链就自动携带了"这次重写是为哪几条需求做的"。

**不要按来源类型去匹配未满足的需求。** 改写器只看来源类型、只产出一个查询，说明这次重试本就是"为这一批缺口发的单查询"；按来源类型去套未满足需求会把结果张冠李戴到同源的其他需求上。

还有一个连带要求：**未满足的需求必须映射成非空的 `missing_aspects`**，否则改写器会以"没有缺口"为由拒绝改写，重试根本不会发生。

## 3.7 可观测性

- `--debug` 的 Trace 自动带上逐条 `statuses`。
- `--debug` 下**额外加一行**可读摘要，形如 `Requirements: ER1 ok, ER3 missing`。本轮的全部价值就是"缺哪条"，不该逼着人读 JSON。
- **普通输出一行不加**：现有测试断言了 `Sufficiency: enough` 这一行的存在，新增内容只能进 `--debug`。
- 未满足需求的描述继续流向部分回答的 `Known Evidence Gaps`（链路不变），所以"缺什么"会自动出现在答案里。

# 五、风险

| 风险 | 说明 | 应对 |
|---|---|---|
| **零需求空真判足够** | 空需求走逐条判定会全票通过 | 分流条件用"有无需求"，两处调用点一致 |
| **截断导致后段需求常年失败** | `top_k` 预算有限，尾部需求容易被切掉 | 阶段一区分"从未检索到"与"被预算截掉"，理由分别写明 |
| **切片错位** | 只截断子问题不截断需求 | 两者取同一段切片 |
| **重试归属错挂** | 按来源类型匹配会把结果挂到同源的其他需求上 | 改按 `targeted_aspects` 的需求标识 |
| **判定变严导致重试变多** | "全部满足才算足够"比原来的并集判定严格 | 这是本轮**有意**的行为改变；对证据不足的问题如实报告正是目标。重试有硬上限，不会失控 |
| **逐条判定的模型调用变贵** | 上下文里多了需求描述与归属信息 | 只增加一次调用；不再增加别的调用 |

# 六、实现结果

测试从 211 增至 **240 passed / 1 skipped**；L1 基准的哈希与四种策略指标**逐值未变**（keyword 0.2222 / vector 0.4722 / hybrid 0.4722 / routed 0.6667，MRR 同）。

## 6.1 它确实做到了"缺哪条"

对"订单关闭为何这样设计"的真实运行，逐条结论是：

```text
ER5 ok   C2、C7、C8 为文档材料，描述了取消订单与超时关单的业务目标…取舍
ER1 MISS 仅有 closeTicketOrder、closePayByOrderSn 的方法签名，未出现触发条件判断…
ER2 MISS 证据只展示零散方法片段和入口声明，未体现阶段划分与调用链路
ER3 MISS 证据仅包含入参非空/订单查询等局部校验和 setStatus(CLOSE)，未出现状态流转规则
ER4 MISS 证据只有方法签名和关单方法开头片段，未出现对关联业务数据的清理、释放
ER6 MISS 只对比取消与超时关单目标，均未记录订单关闭方案选型理由、可选做法对比及代价
```

**这正是本轮要的东西**：不是笼统的"缺少代码证据"，而是"哪一条、缺的是什么、现有证据差在哪"。而且**重试真的起了作用**——缺口从 6 条降到 3 条。

## 6.2 三个预算发现：推理量随"被判定项数"增长

实现与验证中连撞三次同一类问题，每次表现都是 `finish_reason=length` 被静默转成回退：

| 调用 | 原预算 | 调整后 | 触发场景 |
|---|---|---|---|
| 问题规划 | 1024 | 1536 | 否定式问题（"为什么**没有**用 MQ"）推理更长 |
| **逐条充分性** | 1024 | **4096** | 一次要输出 N 个状态对象，推理随需求条数增长 |
| 定向改写 | 1024 | 2048 | 缺口列表变长，输入变大 |

**可以推广的一条规律**：这类调用的预算应当与**被判定/被输出的项数**挂钩，而不是按"输出很短"来估。逐条充分性在 2048 下第 0 轮能过、第 1 轮仍截断，到 4096 才稳定。

## 6.3 一个必须单独说的改进：让失败可见

前三次预算问题都表现为**完全相同的**一句 "semantic sufficiency could not be verified"，耗时两轮排查才定位到 `finish_reason=length`。

因此两处回退消息改为**带上异常类型**（`RuntimeError` / `ValueError`），但**不回显异常文本**——项目既有约定是异常消息不进入结果（有一条测试专门断言密钥不泄漏）。

这一条本身价值很高：它把"静默回退"从不可诊断变成一眼可分类。**这是项目文档第三次记录这个问题**（前两次分别在问题规划器与整体失败闭合处）。

# 七、本轮暴露的问题（未修，属下一阶段）

逐条判定**第一次让下面这个缺陷变得可见**。它一直存在，只是旧的并集判定看不见。

## 7.1 `top_k` 预算会饿死后面的需求

对"为什么购票没有使用 MQ 作为异步中间件提高性能"的真实运行：

```text
round 0：ER1 ok、ER2 ok、ER4 ok
         ER3 / ER5 / ER6 → 检索到了证据，但都被 Context 预算截断
```

机制：6 个子问题各召回 3 条 = 18 条，合并后按子问题顺序排列，再被 `merged[:top_k]`（默认 12）截断。**排在后面的子问题的证据被整段切掉**，于是它们的需求必然判失败。

旧的并集判定看不到这件事——它只问"CODE 有没有、DOCUMENT 有没有"，而这两类始终都有。

## 7.2 重试会把已有证据挤出去

同一题的第 1 轮：

```text
round 1：ER3 ok、ER5 ok、ER6 ok
         ER1 / ER2 / ER4 → 检索到了证据，但都被 Context 预算截断
```

缺失集合**整体翻转**。原因是重试结果被前置（`_merge_results(新, 旧)`），而重试那次检索本身就取回 `top_k` 条，足以占满整个窗口，把原有证据全部挤出。

也就是说：**一次重试可以解决它针对的缺口，同时制造出新的缺口**。

## 7.3 这两条属于下一阶段

它们不是判定逻辑的问题，而是**预算分配**的问题——如何在不同需求之间分配 Context 的名额。修它要么改 `top_k` 的分配方式，要么在合并时保证已有证据不被驱逐，两者都动到检索与 Context 构建，超出本轮边界（本轮明确"不改检索策略"）。

**但它们现在是可测量的了**：逐条状态直接告诉你"哪几条被预算截断了"。因此下一步做预算分配时，有了明确的验收指标——目标是让"被预算截断"这一条理由从常态变为罕见。

# 八、下一步

2. **证据质量指标**（证据需求覆盖率、证据命中率）。逐条状态已经是结构化事实，把它变成可统计的数字。
3. 再往后才是 **Search Replanner**：按缺口清单决定下一步搜索动作。
