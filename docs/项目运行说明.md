可以，现在已经能直接使用。

它目前能做三件主要事情：

1. 搜索项目代码和文档。
2. 把搜索结果整理成带引用的 Context。
3. 使用 DeepSeek 根据项目证据回答问题，并给出真实的文件、方法、行号或文档标题来源。

## 使用前确认

确保以下三项正常：

- Docker Desktop 已启动。
- PostgreSQL 容器正在运行。
- 用户环境变量中已经有：
  - `DASHSCOPE_API_KEY`
  - `DEEPSEEK_API_KEY`
  - `DEEPSEEK_BASE_URL=https://api.deepseek.com`

进入项目目录：

```powershell
cd D:\Java-learning\DevContext
```

启动数据库：

```powershell
docker compose up -d
```

如果源码或项目文档发生了变化，重新建立索引：

```powershell
uv run devcontext ingest
```

平时没有修改源码或文档，不需要每次都执行 `ingest`。

## 最常用：直接提问

执行：

```powershell
uv run devcontext ask "OrderServiceImpl.createTicketOrder 如何保证事务和幂等？"
```

系统会自动完成：

```text
搜索代码和文档
→ 整理 Context
→ 调用 DeepSeek
→ 检查引用是否合法
→ 输出回答和真实 Sources
```

输出大致如下：

```text
Question:
OrderServiceImpl.createTicketOrder 如何保证事务和幂等？

Answer:
createTicketOrder 使用 @Transactional 保证订单和订单项写入处于同一事务中 [C1]。
它通过 orderSn 查询、内容一致性检查和唯一键冲突处理保证幂等 [C1][C2]。

Sources:
[C1] services/order-services/.../OrderServiceImpl.java:81-155 — OrderServiceImpl#createTicketOrder
[C2] 7-模块设计文档/订单与支付模块.md > 六、四条跨模块完整流程 > 6.1 流程一：下单
```

`[C1]`、`[C2]` 是回答中的证据编号。下面的 `Sources` 是程序从数据库中的真实检索结果生成的，不是模型自己编造的路径。

## 常用提问示例

询问代码实现：

```powershell
uv run devcontext ask "购票事务在哪个类和方法中实现？"
```

询问设计原因：

```powershell
uv run devcontext ask "为什么订单延迟任务要在事务提交后投递？"
```

同时询问代码和设计：

```powershell
uv run devcontext ask "createTicketOrder 的事务实现和提交后投递设计是什么？" --top-k 10 --max-chars 8000
```

询问流程：

```powershell
uv run devcontext ask "订单超时关闭的完整流程是什么？"
```

定位异常处理：

```powershell
uv run devcontext ask "订单创建时 DuplicateKeyException 是如何处理的？"
```

## 两个可调参数

默认命令：

```powershell
uv run devcontext ask "你的问题"
```

等价于：

```powershell
uv run devcontext ask "你的问题" --top-k 5 --max-chars 6000
```

参数含义：

- `--top-k`：最多从检索结果中取多少条候选。
- `--max-chars`：提供给模型的项目 Context 最大字符数。

简单问题使用默认值即可。

如果问题需要同时参考代码和设计文档，可以使用：

```powershell
uv run devcontext ask "你的问题" --top-k 10 --max-chars 8000
```

不建议一开始把数值设得特别大，否则模型输入更长、调用成本更高，而且可能混入更多低相关内容。

## 只查看原始搜索结果

如果不想调用 DeepSeek，只想看系统检索到了什么：

```powershell
uv run devcontext search --strategy hybrid --query "购票事务" --top-k 10
```

这适合检查检索质量。

也可以分别查看关键词或向量检索：

```powershell
uv run devcontext search --strategy keyword --query "createTicketOrder" --top-k 10
```

```powershell
uv run devcontext search --strategy vector --query "订单事务和幂等设计" --top-k 10
```

## 只查看整理后的 Context

如果想检查“系统准备交给模型的证据是什么”，但不调用模型：

```powershell
uv run devcontext context "购票事务是如何实现的？" --top-k 5
```

它会输出：

```text
[C1] CODE
File: ...
Symbol: ...
Lines: ...
Score: ...

代码正文……

[C2] DOCUMENT
File: ...
Heading: ...
Score: ...

文档正文……
```

这个命令很适合排查回答不理想的原因：

- 如果 Context 本身不相关，问题主要在检索阶段。
- 如果 Context 很准确，但回答不理想，问题主要在模型生成阶段。
- 如果只检索到文档，没有代码，系统不会伪造代码来源。

## 推荐的日常使用方式

通常直接使用：

```powershell
uv run devcontext ask "你的问题"
```

回答不理想时，先检查 Context：

```powershell
uv run devcontext context "你的问题" --top-k 10 --max-chars 8000
```

如果发现默认 5 条证据不够，再增加参数：

```powershell
uv run devcontext ask "你的问题" --top-k 10 --max-chars 8000
```

如果你修改了 `my12306` 源码或项目文档，重新入库：

```powershell
uv run devcontext ingest
```

然后再提问。

## 当前需要注意

系统已经可以使用，但目前还是 V1：

- 回答只能基于检索到的 Context。
- 检索不到的内容，模型应当说明证据不足。
- 系统会检查 `[C1]` 是否真实存在，但暂时不会判断该证据是否真的完全支持对应语句。
- 某些问题默认 Top 5 可能只有文档或只有代码，这时可以尝试 `--top-k 10`。
- 如果出现 `finish_reason=length`，说明问题和证据过于复杂，当前系统会拒绝输出半截回答；可以尝试缩小问题范围或降低 `--max-chars`。
- 当前没有网页界面，需要在 PowerShell 中使用。

最简单的开始方式就是：

```powershell
cd D:\Java-learning\DevContext
docker compose up -d
uv run devcontext ask "购票事务是如何实现的？"
```
