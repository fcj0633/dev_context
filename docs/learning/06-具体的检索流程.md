当前正常 `ask` 流程中的检索，不是“拿用户原问题直接查一次数据库”，而是一套有状态、最多两轮的证据检索流程。

它的核心目标不是简单返回相似度最高的若干 Chunk，而是：

> 围绕每条 EvidenceRequirement 搜集候选证据，保证核心需求尽量都有证据进入最终 Context，再逐条判断证据是否真的够用，必要时进行一次定向补查，最后输出冻结的 EvidencePackage。

完整流程是：

```text
EvidencePlan
  ↓
第一轮 SearchAction 规划
  ↓
按来源要求选择检索策略
  ↓
关键词 / 向量 / Hybrid 检索
  ↓
SourcePolicy 标记证据身份和时间状态
  ↓
EvidencePool 汇总、去重、公平选取
  ↓
ContextBuilder 构建最终 Context
  ↓
CoverageChecker 检查每条需求
  ├─ 已满足：停止
  ├─ SUPPORTING 未满足：停止，不补查
  ├─ CORE PARTIAL/MISSING：进入第二轮
  └─ UNVERIFIED：停止，避免盲目补查
  ↓
第二轮定向 SearchAction
  ↓
追加候选并重新构建 Context
  ↓
第二轮 Coverage
  ↓
冻结 EvidencePackage
```

主控制逻辑位于 [retrieval_controller.py](D:/Java-learning/DevContext/src/devcontext/agentic/retrieval_controller.py:39)。

# 一、检索从什么数据开始

检索阶段的直接输入不是原始字符串，而是：

```text
UserRequest
EvidencePlan
```

其中，EvidencePlan 已经把用户问题转换成若干证据需求。

例如用户问：

```text
详细解释当前购票占座的数据一致性是如何保证的
```

可能形成如下证据需求。以下只是结构示例，不代表一次真实在线输出：

```text
ER1
target:
确认当前占座成功过程中的状态变化和执行顺序

success_criteria:
证据能够指出主要入口、关键状态写入和成功路径顺序

priority:
CORE

temporal_scope:
CURRENT

source_requirement:
CODE
```

```text
ER2
target:
确认并发占座请求使用的协调机制及其保护范围

success_criteria:
证据能够区分请求准入、并发协调和最终数据库写入的职责

priority:
CORE

temporal_scope:
CURRENT

source_requirement:
CODE
```

```text
ER3
target:
确认跨服务失败后的恢复或补偿机制

success_criteria:
证据能够指出失败状态、补偿触发条件和恢复路径

priority:
SUPPORTING

temporal_scope:
CURRENT

source_requirement:
BOTH
```

这时，检索控制器已经知道：

- 要找哪几类事实；
- 哪些是核心事实；
- 哪些只是辅助事实；
- 需要当前、历史还是未来证据；
- 需要代码、文档还是两者。

但它还没有实际的搜索文本。

这是当前设计的重要特点：

```text
EvidenceRequirement 决定“要找什么”
SearchAction 决定“这一轮具体怎么搜”
```

# 二、第一步：生成 SearchAction

SearchAction 的实现位于 [search_actions.py](D:/Java-learning/DevContext/src/devcontext/agentic/search_actions.py)。

每个 SearchAction 的结构是：

```text
SearchAction
  action_id
  requirement_id
  round_index
  query
  source_scope
  reason
  decision_source
  error
```

例如：

```json
{
  "action_id": "SA1",
  "requirement_id": "ER1",
  "round_index": 0,
  "query": "购票占座成功状态变更 执行入口 状态写入 调用顺序",
  "source_scope": "CODE",
  "reason": "查找当前占座成功路径中的入口和状态写入",
  "decision_source": "llm",
  "error": null
}
```

这里的 `query` 才是真正送给底层检索器的文本。

## 1. 第一轮 Query 如何产生

第一轮 SearchActionPlanner 接收：

```text
original_query
requirement.target
requirement.success_criteria
requirement.source_requirement
```

例如：

```json
{
  "original_query": "详细解释当前购票占座的数据一致性是如何保证的",
  "round_index": 0,
  "requirements": [
    {
      "requirement_id": "ER1",
      "target": "确认当前占座成功过程中的状态变化和执行顺序",
      "success_criteria": "证据能够指出主要入口、关键状态写入和成功路径顺序",
      "source_requirement": "CODE",
      "missing_criteria": [],
      "discovered_terms": [],
      "previous_queries": []
    }
  ]
}
```

SearchActionPlanner 使用一个受限提示词，要求模型：

- 只生成查询文本；
- 不回答原问题；
- 不增加证据需求；
- 不改变 Requirement 的来源要求；
- 不生成多个候选 Query；
- 不虚构类名、方法名或文件名；
- 不重复历史 Query；
- 只输出严格 JSON。

模型输出形状必须是：

```json
{
  "actions": [
    {
      "requirement_id": "ER1",
      "query": "搜索文本",
      "reason": "为什么执行这次搜索"
    }
  ]
}
```

程序会严格检查：

- 根对象只能有 `actions`；
- Action 数量必须与传入 Requirement 数量相同；
- 顺序和 `requirement_id` 必须对应；
- 每条只能包含 `requirement_id`、`query`、`reason`；
- Query 不能为空；
- Query 最长 500 字符；
- reason 最长 160 字符；
- 不能包含 Markdown 代码围栏或换行；
- Query 不能与历史 Query 重复。

只要模型调用失败、JSON 非法或者结构不合格，就使用确定性 Query。

确定性 Query 的基本形式是：

```text
original_query
+ requirement.target
+ missing_criteria
+ discovered_terms
```

因此，SearchActionPlanner 失败不会导致检索停止。

---

## 2. CORE 和 SUPPORTING 的执行顺序

RetrievalController 会先排序 Requirement：

```text
CORE 在前
SUPPORTING 在后
同一优先级按 ER 编号排序
```

例如原顺序是：

```text
ER1 SUPPORTING
ER2 CORE
ER3 CORE
```

实际第一轮执行顺序会变成：

```text
ER2
ER3
ER1
```

这样做主要是为了：

- 优先消耗检索预算在核心问题上；
- 让核心证据更早进入 EvidencePool；
- 避免辅助需求抢占前面的 Context 名额。

每条 Requirement 第一轮最多生成一个逻辑 SearchAction。

# 三、第二步：来源要求映射为真实检索策略

LLM 不直接决定使用 keyword、vector 还是 hybrid。

LLM 只负责输出：

```text
source_scope
```

实际检索策略由程序中的 RetrievalPolicy 确定，代码位于 [policy.py](D:/Java-learning/DevContext/src/devcontext/retrieval/policy.py:10)。

当前映射关系是：

| `source_scope` | 实际行为 |
|---|---|
| `CODE` | 只检索 CODE，使用 Hybrid |
| `DOCUMENT` | 只检索 DOCUMENT，使用 Vector |
| `BOTH` | 分别检索 CODE 和 DOCUMENT，然后交错组合 |
| `ANY` | 不限制来源，使用 Hybrid |

这样做的目的是防止 LLM自由选择尚不存在或未经评测的检索工具。

模型不能输出：

```text
symbol_search
AST_search
read_source
call_graph
```

当前系统只有：

```text
keyword
vector
hybrid
```

以及：

```text
CODE
DOCUMENT
不限制来源
```

---

## 1. CODE 检索

当 EvidenceRequirement 要求：

```text
source_requirement = CODE
```

系统执行：

```text
strategy = hybrid
source_type = CODE
```

也就是：

```text
只在代码 Chunk 中
同时进行关键词检索和向量检索
最后通过 RRF 融合
```

CORE 默认每次取：

```text
top_k = 5
```

SUPPORTING 默认每次取：

```text
top_k = 3
```

---

## 2. DOCUMENT 检索

当要求：

```text
source_requirement = DOCUMENT
```

系统执行：

```text
strategy = vector
source_type = DOCUMENT
```

即：

- 先把 SearchAction.query 转换成向量；
- 只在文档 Chunk 中进行向量相似度检索；
- 不执行关键词与向量 RRF。

当前 DOCUMENT 路径选择 Vector，是现有 RetrievalPolicy 的固定策略，并不是 LLM 每次临时决定的。

---

## 3. BOTH 检索

当要求：

```text
source_requirement = BOTH
```

系统把它映射为 MIXED 路径。

当前具体行为是：

```text
CODE:
  Vector Search
  候选数 = top_k

DOCUMENT:
  Vector Search
  候选池 = max(20, top_k)
```

然后：

1. 对文档候选进行一次“文档锚点提升”；
2. 从 CODE 开始，将 CODE 和 DOCUMENT 稳定交错；
3. 最终截断到本次 Action 的 `top_k`。

例如 CODE 排名为：

```text
Code1
Code2
Code3
```

DOCUMENT 排名为：

```text
Doc1
Doc2
Doc3
```

最终组合可能是：

```text
Code1
Doc1
Code2
Doc2
Code3
```

BOTH 的最终结果数仍然是整个 Action 的 `top_k`，不是 CODE 取 5 条、DOCUMENT 再取 5 条后返回 10 条。

---

## 4. ANY 检索

当要求：

```text
source_requirement = ANY
```

系统执行：

```text
strategy = hybrid
source_type = None
```

也就是：

- 关键词检索不限制 CODE/DOCUMENT；
- 向量检索不限制 CODE/DOCUMENT；
- 通过 RRF 融合；
- 最终哪种来源排名靠前就返回哪种来源。

CoverageChecker 对 ANY 的满足条件是：

```text
CODE 或 DOCUMENT 中至少有一种直接证据即可
```

它并不要求两种来源都存在。

不过当前 EvidencePool 选择逻辑有一个值得注意的实现细节：

> ANY 和 BOTH 在“允许哪些来源”上都被转换为 CODE + DOCUMENT，因此 CORE + ANY 在两类候选都存在时，也可能尝试各保留一条。

这不会让 CoverageChecker 错误地要求 BOTH，但可能比 ANY 的语义更保守，多占用一个最终 Context 名额。严格来说，后续可以将“允许两种来源”和“必须优先保留两种来源”拆成两个判断，确保只有 BOTH 才预留双来源。

# 四、底层关键词检索怎么实现

底层检索服务位于 [service.py](D:/Java-learning/DevContext/src/devcontext/retrieval/service.py:11)，数据库查询位于 [storage.py](D:/Java-learning/DevContext/src/devcontext/storage.py:95)。

关键词检索不是简单的全文 `LIKE`。

它会先从 Query 中提取类似 Java 标识符的英文词：

```text
[A-Za-z_$][A-Za-z0-9_$]{2,}
```

例如 Query：

```text
OrderServiceImpl createTicketOrder 占座状态更新
```

会提取：

```text
OrderServiceImpl
createTicketOrder
```

然后对不同命中类型赋予不同权重：

| 命中方式 | 加分 |
|---|---:|
| `symbol_name` 精确匹配 | 12 |
| `class_name` 精确匹配 | 10 |
| `signature` 包含标识符 | 6 |
| `keyword_text` 包含完整 Query | 2 |
| `keyword_text` 文本相似度 | `similarity()` 分数 |

因此，Query 中如果已经有真实类名或方法名，关键词检索能够明显提升对应代码 Chunk。

候选条件是满足以下任一条件：

- `keyword_text` 包含完整 Query；
- `similarity(keyword_text, query) > 0.03`；
- `keyword_text` 包含至少一个提取出的标识符。

排序方式：

```text
score DESC
id ASC
```

同分时通过 ID 保持稳定结果。

这里依赖 PostgreSQL 的字符串相似度能力，并不是由 LLM 对结果重新打分。

# 五、底层向量检索怎么实现

向量检索分为两步。

## 1. Query Embedding

系统使用 Bailian Embedding 客户端，将 SearchAction.query 转换成向量：

```text
query
  ↓
BailianEmbeddingClient.embed_query()
  ↓
query_vector
```

这一步的时间记录在：

```text
query_embedding_ms
```

## 2. PostgreSQL pgvector 检索

数据库使用：

```sql
embedding <=> query_vector
```

计算向量距离。

排序：

```sql
ORDER BY embedding <=> query_vector, id ASC
```

返回分数：

```text
score = 1 - distance
```

也就是说：

- 距离越小越相似；
- 转换后的 score 越大越好；
- 同距离通过 ID 保持稳定顺序。

向量检索可以通过 `source_type` 限定：

```text
CODE
DOCUMENT
None
```

# 六、Hybrid 检索怎么实现

Hybrid 会同时运行：

```text
关键词检索
向量检索
```

候选池大小为：

```text
pool_size = max(20, top_k)
```

例如最终只要 5 条，仍会分别先取：

```text
关键词候选 20 条
向量候选 20 条
```

然后通过 Reciprocal Rank Fusion，也就是 RRF 融合，实现在 [hybrid.py](D:/Java-learning/DevContext/src/devcontext/retrieval/hybrid.py:9)。

计算方式是：

```text
RRF 分数 = Σ 1 / (60 + 当前排名)
```

例如一个 Chunk：

- 在关键词结果中排名第 1；
- 在向量结果中排名第 4；

它的分数为：

```text
1 / (60 + 1) + 1 / (60 + 4)
```

RRF 的特点是：

- 不直接比较关键词分数和向量相似度；
- 只使用两套排名；
- 同时在两套排名中靠前的结果更容易排到前面；
- 只在某一套结果中出现的 Chunk 也可以保留。

融合后按：

```text
RRF score DESC
chunk id ASC
```

排序并截断到 `top_k`。

# 七、BOTH 路径的文档锚点提升

MIXED/BOTH 路径在文档向量检索后，会进行一次轻量级锚点提升。

系统从 Query 中提取：

- 英文标识符；
- 连续中文文本的双字词。

例如：

```text
支付回调通知推进
```

会产生类似：

```text
支付
付回
回调
调通
通知
知推
推进
```

然后与文档元数据比较：

```text
file_path
title
heading_path
```

系统计算 Query 词项与文档元数据的重合比例。

如果某一条文档的元数据重合度明显高于当前第一条文档，就把它提升到文档候选第一位。

需要注意：

- 只调整文档候选顺序；
- 不修改原始向量分数；
- 只提升一个最明确的文档锚点；
- 相同重合度保持原顺序；
- 最终仍与 CODE 结果交错。

这主要用于解决：

```text
正文语义相似度一般
但文件名、标题或章节名明显与用户问题对应
```

的场景。

# 八、检索结果如何进入 EvidencePool

每个 SearchAction 返回的是若干原始 `SearchResult`。

但这些结果不会直接进入最终 Context，而是先经过：

```text
SourcePolicy
EvidencePool
```

实现位于 [evidence.py](D:/Java-learning/DevContext/src/devcontext/evidence.py:1)。

## 1. 每条结果先绑定 Requirement

假设 ER1 执行检索得到 Chunk 101：

```text
Chunk 101
  source_type = CODE
  requirement_id = ER1
```

ER2 也检索到同一个 Chunk 101：

```text
Chunk 101
  source_type = CODE
  requirement_id = ER2
```

EvidencePool 会保留它对两个 Requirement 的归属关系。

最终 Context 中不会重复放两次 Chunk 101，但它的 Annotation 会包含：

```text
supports = ER1, ER2
```

这样 CoverageChecker 可以知道：

```text
这一条证据同时可能支持 ER1 和 ER2
```

但 CoverageChecker 仍然会分别判断是否真的满足两个 Requirement，不会自动认为同一个 Chunk 一定满足全部需求。

---

## 2. SourcePolicy 给证据加身份

代码证据固定标记为：

```text
source_role = IMPLEMENTATION
temporal_status = CURRENT
authority_priority = 100
```

文档证据根据 [source-policy.json](D:/Java-learning/DevContext/config/source-policy.json) 的路径规则标记。

当前主要规则是：

| 文件特征 | source_role | temporal_status | priority |
|---|---|---|---:|
| 包含“验证报告” | VERIFICATION | CURRENT | 95 |
| 包含“实验报告” | VERIFICATION | CURRENT | 90 |
| 包含“历史” | HISTORICAL_PLAN | HISTORICAL | 35 |
| 包含“后续…规划” | HISTORICAL_PLAN | FUTURE | 30 |
| 包含“设计” | CURRENT_DESIGN | UNKNOWN | 70 |
| 其他 Markdown | GENERAL_DOCUMENT | UNKNOWN | 55 |
| 未命中规则 | UNKNOWN | UNKNOWN | 50 |

第一条匹配规则生效。

这个标记不会改变底层数据库检索分数，而是在 EvidencePool 选择最终证据时影响优先级。

---

## 3. 同一 Requirement 内去重

EvidencePool 按 Requirement 保存候选：

```text
candidates_by_requirement
```

当前代码中的字段名仍然保留兼容名称：

```text
candidates_by_sub_question
sub_question_id
```

但在新流程中实际承载的是：

```text
requirement_id
```

同一 Requirement 内，如果同一个 Chunk ID 被多次检索到，只保留一次。

不同 Requirement 可以同时持有同一个 Chunk，以保留证据归属。

# 九、EvidencePool 如何公平选择最终候选

原始检索可能得到很多候选，但最终 Context 有：

- `top_k` 限制；
- 字符预算限制。

如果直接把所有候选混在一起按排名截断，会出现：

```text
ER1 的五条结果全部排在前面
ER2、ER3 一条都进不了 Context
```

因此 EvidencePool 按以下顺序选择。

## 第一步：每个 CORE 先保留一条

例如：

```text
ER1 CORE
ER2 CORE
ER3 SUPPORTING
```

会先尝试：

```text
ER1 选一条
ER2 选一条
```

避免 ER1 的多个候选挤掉 ER2。

---

## 第二步：双来源 CORE 尽量各保留一条

如果 CORE Requirement 允许或要求 CODE + DOCUMENT，EvidencePool 会尝试：

```text
一条 CODE
一条 DOCUMENT
```

设计意图主要是保证 `BOTH` 的两个来源都能进入最终 Context。

如前面所述，当前实现对 CORE + ANY 也可能进行同样的双来源保留，这是一个偏保守的实现细节。

---

## 第三步：每个 SUPPORTING 保留一条

核心需求完成基本占位后，再给每个 SUPPORTING 尝试保留一条。

---

## 第四步：剩余预算按权威性和检索顺序填充

剩余候选按以下优先级填充：

```text
有效权威优先级
  ↓
原检索顺序
```

有效优先级不只是配置中的 `authority_priority`，还会考虑 Requirement 的时间范围。

例如：

```text
Requirement.temporal_scope = CURRENT
```

如果候选也是：

```text
temporal_status = CURRENT
```

则增加：

```text
+25
```

如果当前问题遇到：

```text
HISTORICAL
FUTURE
```

则减少：

```text
-25
```

所以对于“当前如何实现”的问题：

- 当前代码优先；
- 当前验证报告其次；
- 普通设计文档再后；
- 历史计划和未来规划会被降低优先级。

但这里需要区分：

> EvidencePool 的优先级只是影响“谁更先进入 Context”，并不等于程序已经证明某条证据内容正确。

真正的语义满足仍由 CoverageChecker 判断。

---

# 十、ContextBuilder 如何生成最终检索上下文

EvidencePool 选择结果后，交给 [builder.py](D:/Java-learning/DevContext/src/devcontext/context/builder.py:18)。

ContextBuilder 负责把 `SearchResult` 转换成最终给 CoverageChecker 和回答系统使用的 `ContextBundle`。

## 1. 再次按 Chunk ID 去重

ContextBuilder 会再次按数据库 Chunk ID 去重。

这样即使上游意外重复传入，也不会重复渲染相同 Chunk。

---

## 2. 双来源锚点

如果结果同时存在 CODE 和 DOCUMENT，并且第一条 CODE 和第一条 DOCUMENT 的完整内容可以同时放进字符预算，ContextBuilder 会把这两条放在前面。

例如原顺序：

```text
Code1
Code2
Doc1
Code3
```

可能调整为：

```text
Code1
Doc1
Code2
Code3
```

这一步是最终 Context 层面的来源保护。

EvidencePool 是按 Requirement 做公平选择；ContextBuilder 则是按来源保证 CODE 和 DOCUMENT 都不容易被字符预算裁掉。

---

## 3. 生成 Citation

每条进入 Context 的证据被编号为：

```text
C1
C2
C3
```

代码证据的 Header 包括：

```text
[C1] CODE
File: ...
Symbol: ClassName#methodName
Signature: ...
Lines: 100-130
Score: ...
Evidence: role=IMPLEMENTATION; time=CURRENT; priority=100
Supports: ER1, ER2
```

文档证据包括：

```text
[C2] DOCUMENT
File: ...
Heading: 一级标题 > 二级标题
Score: ...
Evidence: role=CURRENT_DESIGN; time=UNKNOWN; priority=70
Supports: ER3
```

然后附上 Chunk 正文。

---

## 4. 字符预算如何确定

如果用户显式传入：

```text
--max-chars
```

就使用该值。

否则，根据 EvidencePlan 复杂度决定。

### 8000 字符

条件：

```text
只有一条 Requirement
并且是 CORE
并且不是 BOTH
```

### 16000 字符

通常用于：

```text
2–3 条 Requirement
不存在多条 CURRENT CORE
不存在多条 BOTH
```

### 28000 字符

满足任一条件：

```text
Requirement 数量 >= 4
BOTH 数量 >= 2
CURRENT CORE 数量 >= 2
```

这里与回答深度无关。

也就是说：

```text
--depth brief
--depth detailed
```

不会改变检索 Context 预算。

---

## 5. 超出字符预算怎样处理

ContextBuilder 按顺序加入证据。

如果某条完整 Chunk 放不下：

1. 计算剩余字符；
2. 保留 Header；
3. 截断正文；
4. 追加：

```text
… [truncated]
```

5. 将该 ContextItem 标记为：

```text
truncated = true
```

6. 停止继续加入后面的结果。

被截断的 Chunk 可以出现在最终 Context 中供回答参考，但：

> CoverageChecker 不会把它计入“证据需求已满足”。

这是为了避免只看到半个方法、半段文档，就判断完整的 success criteria 已经满足。

# 十一、第一轮 Coverage 如何判断证据够不够

Context 构建完成后，进入 [coverage.py](D:/Java-learning/DevContext/src/devcontext/agentic/coverage.py:27)。

CoverageChecker 的输入是：

```text
所有 EvidenceRequirement
最终 ContextBundle
```

这里非常关键：

> Coverage 检查的是最终真正进入 Context 的证据，而不是数据库检索出来但后来被 Top-K 或字符预算裁掉的候选。

因此，不会出现：

```text
检索器曾经找到过某条证据
所以认为回答器一定看得到
```

如果证据没有进入最终 Context，就不能算满足。

---

## 1. 先做确定性来源检查

对于每条 Requirement，只收集：

```text
属于该 Requirement
并且 truncated = false
```

的 ContextItem。

然后检查来源。

### CODE

必须存在：

```text
source_type = CODE
```

### DOCUMENT

必须存在：

```text
source_type = DOCUMENT
```

### BOTH

必须同时存在：

```text
CODE
DOCUMENT
```

### ANY

至少存在一种：

```text
CODE 或 DOCUMENT
```

来源不齐时不调用 LLM，直接得到：

```text
PARTIAL
```

或者：

```text
MISSING
```

区别是：

- 已有部分直接证据但来源不完整：PARTIAL；
- 一条直接证据都没有：MISSING。

---

## 2. 来源齐全后做语义检查

来源满足后，才把 Requirement 和属于它的证据交给 Coverage LLM。

模型接收到：

```text
requirement_id
target
success_criteria
evidence[]
```

每条 evidence 包括：

```text
chunk_id
source_type
file_path
identity
content
```

Coverage LLM 只能判断：

```text
SATISFIED
PARTIAL
MISSING
```

要求：

- 只能使用当前 Requirement 名下的证据；
- 不能借用其他 Requirement 的证据；
- 不能使用模型记忆；
- 相关但不充分只能判 PARTIAL；
- SATISFIED 必须给出真实 evidence ID；
- 非 SATISFIED 必须给出 missing criteria；
- missing criteria 最多三条；
- reason 和每条缺口最长 160 字符。

程序会校验模型给出的 `evidence_ids` 是否真的属于当前 Requirement。

例如模型不能说：

```json
{
  "requirement_id": "ER1",
  "state": "SATISFIED",
  "evidence_ids": [999]
}
```

如果 Chunk 999 不在 ER1 的最终证据集合中，整个 Coverage 输出无效。

---

## 3. Coverage Checker 自己失败怎么办

Coverage LLM 或解析失败时最多再尝试一次。

两次都失败后，不会标记成：

```text
MISSING
```

而是：

```text
UNVERIFIED
```

含义是：

```text
已经有候选证据
但系统没有完成语义确认
```

这样可以区分：

```text
真的没找到证据
```

和：

```text
Checker 自己出错了
```

异常只记录类型，例如：

```text
RuntimeError
CoverageCheckError
```

不记录可能包含敏感内容的完整异常原文。

---

# 十二、哪些 Requirement 会进入第二轮

第一轮 Coverage 后，RetrievalController 只选择：

```text
priority = CORE
并且 state = PARTIAL 或 MISSING
```

的 Requirement 进入第二轮。

不会进入第二轮的情况：

| Requirement 状态 | 是否补查 |
|---|---|
| CORE + SATISFIED | 否 |
| CORE + PARTIAL | 是 |
| CORE + MISSING | 是 |
| CORE + UNVERIFIED | 否 |
| SUPPORTING + PARTIAL | 否 |
| SUPPORTING + MISSING | 否 |
| SUPPORTING + UNVERIFIED | 否 |

SUPPORTING 不补查，是为了控制成本。

UNVERIFIED 不自动补查，是因为它可能不是检索问题，而是 Coverage Checker 自己失败。如果盲目补查，会浪费检索预算。

---

# 十三、第二轮 Query 如何利用第一轮结果

第二轮不是把第一轮 Query 再执行一次。

系统会从第一轮最终 Context 中，提取每条待补查 Requirement 已发现的真实术语：

```text
class_name
symbol_name
signature
heading_path
file_path
```

每条 Requirement 最多保留八个 discovered terms。

例如第一轮发现：

```text
SeatService
lockSeat
boolean lockSeat(...)
TicketServiceImpl.java
```

Coverage 又指出：

```text
尚缺数据库影响行数检查
```

第二轮 SearchAction 输入类似：

```json
{
  "requirement_id": "ER2",
  "target": "确认数据库写入承担的最终一致性条件",
  "success_criteria": "找到状态条件和影响行数检查",
  "missing_criteria": [
    "尚缺数据库影响行数检查"
  ],
  "discovered_terms": [
    "SeatService",
    "lockSeat",
    "boolean lockSeat(...)",
    "TicketServiceImpl.java"
  ],
  "previous_queries": [
    "购票占座 数据库状态条件 更新结果检查"
  ]
}
```

第二轮 LLM Query 必须满足：

- 与第一轮 Query 不同；
- 如果有 discovered terms，至少使用一个真实术语；
- 如果没有 discovered terms，至少明确包含某个 missing criterion；
- 不能改变 Requirement；
- 不能改变来源要求；
- 不能虚构新的类名或方法名。

不满足这些条件就退回确定性 Query。

这使第二轮从：

```text
泛化搜索“占座一致性”
```

变成：

```text
围绕第一轮真实发现的 SeatService、lockSeat，
定向寻找数据库更新结果检查
```

---

# 十四、第二轮结果怎样合并

第二轮检索不会清空第一轮 EvidencePool。

流程是：

```text
第一轮候选
  +
第二轮候选
  ↓
EvidencePool 去重、重新排序
  ↓
重新选择最终 Top-K
  ↓
重新构建整个 Context
```

因此，第二轮后最终 Context 可能发生变化。

例如第一轮：

```text
C1 ER1 主流程
C2 ER2 锁逻辑
C3 ER3 设计文档
```

第二轮找到更权威的数据库条件更新代码后，重新选取可能变成：

```text
C1 ER1 主流程
C2 ER2 数据库条件更新
C3 ER2 影响行数检查
C4 ER3 设计文档
```

Citation 会按照第二轮最终 Context 重新编号。

Coverage 也会对所有 Requirement 再检查一次，不只是检查补查的 CORE。

---

# 十五、检索预算如何限制

当前限制是：

```text
Requirement 最多 6 条
CORE 最多 4 条
CORE 最多两个 SearchAction
SUPPORTING 最多一个 SearchAction
Coverage 最多两轮
SearchAction 全局上限 12
```

在当前 EvidencePlanner 的约束下，实际通常最多是：

```text
第一轮最多 6 个 Action
第二轮最多 4 个 CORE Action
合计通常最多 10 个
```

代码仍保留 `MAX_SEARCH_ACTIONS = 12` 作为总上限。

每个 Action 的候选数量：

```text
CORE：5
SUPPORTING：3
```

注意，这些是每个 Requirement 的候选数量，不是最终 Context 的结果数。

最终结果还会受：

```text
ask --top-k
Context 字符预算
去重
来源保留
Requirement 公平分配
```

共同限制。

当前正常规划路径默认最终 `top_k` 是 12。

# 十六、单次检索失败如何处理

如果某个 SearchAction 执行时出现异常，例如：

- Embedding 调用失败；
- PostgreSQL 查询失败；
- 网络异常；
- 数据格式错误；

RetrievalController 不会让整个循环立即崩溃。

它会把异常类型写入该 SearchAction：

```json
{
  "action_id": "SA2",
  "requirement_id": "ER2",
  "error": "RuntimeError"
}
```

然后继续处理其他 Action。

最终：

- 如果其他 Requirement 找到证据，Package 可能是 PARTIAL；
- 如果没有任何证据进入 Context，Package 是 EMPTY；
- 具体错误可以在 Debug Trace 中查看；
- 不会把完整敏感异常内容暴露给普通回答。

---

# 十七、最终检索结果不是普通 List，而是 EvidencePackage

传统检索的输出可能只是：

```text
List<SearchResult>
```

当前证据检索流程的最终输出是：

```text
RetrievalOutcome
  package
  stage_usage
```

其中 `package` 是 [EvidencePackage](D:/Java-learning/DevContext/src/devcontext/agentic/evidence_models.py:88)。

它包含：

```text
EvidencePackage
  original_query
  evidence_plan
  context_bundle
  requirement_coverage
  unresolved_requirements
  retrieval_state
  search_history
  coverage_rounds
```

## 1. `context_bundle`

这是最终真正交给回答阶段的检索结果。

它包含：

```text
query
items
rendered_text
total_chars
max_chars
truncated
```

每个 item 包含：

```text
Citation
Chunk 内容
Chunk ID
Chunk 类型
检索分数
原检索排名
是否被截断
source_role
temporal_status
authority_priority
支持哪些 Requirement
```

---

## 2. `requirement_coverage`

表示每条证据需求最终是否满足：

```json
{
  "requirement_id": "ER2",
  "state": "SATISFIED",
  "evidence_ids": [101, 106],
  "missing_criteria": [],
  "reason": "代码证据包含状态条件和更新结果检查",
  "decision_source": "llm",
  "check_error": null
}
```

---

## 3. `unresolved_requirements`

保存所有未满足 Requirement 的 ID。

包括：

```text
PARTIAL
MISSING
UNVERIFIED
```

即使是 SUPPORTING 未满足，也会进入该列表。

但是 SUPPORTING 未满足不一定阻止 Package 成为 READY。

---

## 4. `search_history`

保存全部 SearchAction：

```text
第一轮搜索了什么
第二轮搜索了什么
为什么搜索
来源范围是什么
是 LLM 生成还是 fallback
执行是否失败
```

它只用于 Trace 和调试，不直接暴露给普通回答。

---

## 5. `coverage_rounds`

保存每一轮 Coverage：

```text
round 0
round 1
```

这样可以判断：

```text
第一轮缺什么
第二轮是否补齐
哪条 Requirement 一直未满足
```

---

## 6. `retrieval_state`

最终状态通过 CORE Requirement 决定。

### READY

```text
Context 不为空
并且所有 CORE 都是 SATISFIED
```

SUPPORTING 可以仍然未满足。

### PARTIAL

```text
Context 中至少有可用证据
但至少一个 CORE 为 PARTIAL、MISSING 或 UNVERIFIED
```

### EMPTY

```text
最终 Context 没有任何证据项
```

这里不是根据“数据库是否曾返回过结果”判断，而是根据“最终 Context 是否真的有结果”判断。

例如数据库返回了结果，但全部因为：

- 去重；
- Top-K；
- 来源限制；
- 字符预算；

没有进入最终 Context，那么回答阶段仍然不能使用它们。

检索流程同时记录每个阶段的运行信息：

每个阶段可以包含：

# 十九、用一个简化例子串起来

假设用户问题是：

```text
当前占座流程如何避免同一个座位被两个请求同时占用？
```

EvidencePlan 产生：

```text
ER1 CORE CODE
确认并发占座请求的协调机制

ER2 CORE CODE
确认数据库最终状态更新条件
```

## 第一轮 SearchAction

```text
SA1 / ER1:
占座并发锁 用户锁 席别锁 保护范围

SA2 / ER2:
占座状态更新 条件更新 影响行数检查
```

## 第一轮检索

ER1 使用 CODE Hybrid：

```text
关键词结果：
LockSeatService#lockSeat
SeatLockManager#acquire

向量结果：
TicketServiceImpl 占座方法
SeatService 座位更新方法

RRF 后：
Chunk 11
Chunk 18
Chunk 23
...
```

ER2 使用 CODE Hybrid：

```text
Chunk 23
Chunk 31
Chunk 45
...
```

Chunk 23 同时归属于 ER1 和 ER2。

## EvidencePool 选择

先保证：

```text
ER1 至少一条
ER2 至少一条
```

再按当前代码优先级和原检索排名填充。

最终 Context：

```text
C1 Chunk 11 supports ER1
C2 Chunk 23 supports ER1, ER2
C3 Chunk 31 supports ER2
```

## 第一轮 Coverage

ER1：

```text
SATISFIED
已经找到锁机制和保护范围
```

ER2：

```text
PARTIAL
找到了条件更新，但缺少影响行数检查
```

## 第二轮

只补查 ER2。

提取第一轮术语：

```text
SeatService
updateSeatStatus
SeatMapper.xml
```

生成新 Query：

```text
SeatService updateSeatStatus SeatMapper 影响行数 条件更新失败
```

得到新 Chunk：

```text
Chunk 52
```

重新构建 Context：

```text
C1 Chunk 11 supports ER1
C2 Chunk 23 supports ER1, ER2
C3 Chunk 52 supports ER2
```

第二轮 Coverage：

```text
ER1 SATISFIED
ER2 SATISFIED
```

最终：

```text
retrieval_state = READY
```

回答阶段只能使用这个最终 EvidencePackage。

# 二十、当前实现的优点

当前检索链路相对于“原问题直接检索一次”的主要改进是：

1. **检索目标显式化**

   每次搜索都对应一条 EvidenceRequirement。

2. **Query 可以动态调整**

   第一轮发现的真实类名、方法名可以进入第二轮。

3. **核心需求不会轻易被前面结果挤掉**

   EvidencePool 会先为每个 CORE 保留证据。

4. **来源要求可验证**

   BOTH 必须同时有 CODE 和 DOCUMENT。

5. **检查最终可用证据，而不是检查曾经检索到的候选**

   被 Top-K 或字符预算裁掉的证据不计入 Coverage。

6. **检索失败不是单点故障**

   单个 Action 失败可以继续其他 Requirement。

7. **Coverage 错误与没有证据分开**

   `UNVERIFIED` 不冒充 `MISSING`。

8. **回答阶段不能偷偷重新检索**

   EvidencePackage 形成后检索结束。

# 二十一、当前实现仍有的限制

## 1. 没有真正的源码符号检索

虽然第二轮可以使用：

```text
类名
方法名
文件名
```

但底层仍然只是：

```text
keyword
vector
hybrid
```

没有：

```text
精确 Symbol Index
按文件读取完整源码
调用图
定义跳转
引用查找
AST 关系检索
```

因此“发现方法名后精确读取完整方法”目前还做不到。

---

## 2. Coverage 是对 Chunk 的判断

系统判断的是：

```text
当前 Chunk 是否满足 success criteria
```

不是对完整文件、完整调用链或数据库事务执行进行形式化验证。

所以 Coverage 仍然是证据充分性的模型判断，不是静态分析证明。

---

## 3. 第二轮只有一次

CORE 即使第二轮后仍然缺证据，也不会继续循环。

这是有意设置的成本边界，但意味着复杂问题可能以 PARTIAL 结束。

---

## 4. SUPPORTING 不补查

辅助证据第一轮没找到就停止。

这样节省成本，但可能使设计背景、验证报告等辅助信息不完整。

---

## 5. ANY 的 Context 分配目前偏保守

ANY 语义上只需要任一来源，但 EvidencePool 当前可能为 CORE + ANY 同时保留 CODE 和 DOCUMENT。

这不会导致错误的 Coverage 状态，但可能占用额外 Context 名额。

---

## 6. 没有独立语义 Reranker

当前重排主要依赖：

- 关键词 SQL 分数；
- Vector 相似度；
- RRF；
- 文档标题锚点；
- SourcePolicy 权威性；
- 时间状态；
- Requirement 公平分配。

没有单独的 Cross-Encoder 或 LLM Reranker 对所有候选重新打相关性分数。

CoverageChecker 只判断证据够不够，不负责重新排序所有检索结果。

---

# 总结

当前检索实现可以概括为：

```text
证据需求
  ↓
动态生成一次具体 SearchAction
  ↓
按来源要求映射到现有 keyword/vector/hybrid
  ↓
从 PostgreSQL + pgvector 取得候选
  ↓
用 SourcePolicy 标记证据身份
  ↓
EvidencePool 按 Requirement 公平选择
  ↓
ContextBuilder 在 Top-K 和字符预算内形成最终证据
  ↓
CoverageChecker 判断每条需求是否满足
  ↓
只对未满足的 CORE 进行一次定向补查
  ↓
重新构建并冻结 EvidencePackage
```

最重要的设计变化是：

> “数据库返回了哪些相似结果”不再直接等于“最终检索结果”。

当前真正的最终检索结果是 EvidencePackage，它同时回答了五个问题：

- 找到了哪些证据；
- 每条证据支持哪个 Requirement；
- 哪些核心事实已经得到满足；
- 哪些内容仍然缺失或无法验证；
- 检索过程执行过哪些 Query，以及为什么停止。
