## 先给骨架：三层机制叠出来的占座一致性

购票占座的一致性不是一个开关，而是三层机制叠出来的：**锁在事务外负责"不许同时抢"，本地事务负责"要么都成要么都不成"，跨服务的部分交给状态机、幂等与补偿去追"最终都成"** [E4][E15]。把这三层记住，后面每一节讲的细节都可以往其中一层上挂。

第一层是串行化。购票链路上有两把锁——用户锁防同一用户重复提交，席别锁把同一车次同一席别的占座串行化，而且两把锁都加在事务外面 [E4]。为什么要在事务外，这不是风格偏好：如果事务的快照建立得比锁早，锁内的读读到的会是锁外的旧世界 [E4]，那样锁就没能保护它本该保护的那段读。从 `PurchaseTicketTxService` 的类注释也能反推出这个分层——它明确写着"调用方已经完成乘车人校验并持有用户锁和全部席别锁"，本事务只操作 ticket 数据库 [E10]。这说明加锁的职责不在事务方法内部，而在它的上游编排层。（至于是哪一种锁实现，这些证据里没有说明，无法确认。）

第二层是原子性。真正的占座动作和写票动作，落在同一个带 `@Transactional(rollbackFor = Exception.class)` 的方法里 [E9]。在 `doPurchaseInTransaction` 内部可以看到座位的写法是带条件的更新——把 `seatStatus` 从 `AVAILABLE` 改成 `LOCKED`，并且用受影响行数与申请座位数比对，不一致就抛"站点余票不足" [E9]；紧接着在同一方法里 `ticketMapper.insert(ticketDO)` 为每位乘客写入车票 [E9]。两者同处一个事务边界内，任何一步抛出 `ServiceException`，整个方法整体回滚 [E9]——所以不会出现"座位被锁了但票没写"或"票写了但座位没锁"的中间态。这里还有一条值得注意的约束：该类注释强调本事务只操作 ticket 数据库，远程调用留在编排层，理由是避免网络等待延长行锁持有时间 [E10]。这正好解释了为什么跨服务的部分必须被推出事务，交给第三层。

第三层是最终一致。跨出本地库之后的订单、支付、座位状态同步，不能靠一个数据库事务兜住，设计上明确走【状态机 + 幂等 + 补偿】 [E15]。这类设计的取向不是"闪避失败"，而是承认失败必然发生、然后选择失败后更安全的落脚点：文档里给出的判断是，即便订单已支付而座位仍停在 `LOCKED`，对可售库存而言它同样不会被别人买走，因此这个组合可以安全地等待补偿收敛 [E13]。这就是为什么源码注释按这个理由把顺序固定成"先订单、后票务" [E13]。换句话说，第三层不保证某一瞬间全局一致，它保证的是——没有哪一步的中间状态会把库存放跑。

三层合起来看，一致性是被"分工"出来的：锁把并发收敛掉，本地事务把单库内的原子性兜住，剩下的跨服务不确定性由补偿慢慢追平。后面几节会分别把这三层展开——先讲锁为什么必须在事务外，再讲事务边界内具体原子了什么，最后讲补偿链路如何把中间状态收敛到终态。

## 难在哪：几组状态必须在并发下同时自洽

先看清问题的形状，再谈解法。

一次"确认购票"的请求，在数据层留下的不是一行记录，而是一条链。支付侧的阅读材料把它写成：座位状态 «——» 余票 «——» 车票 «——» 订单 «——» 支付单 [E14]；购票侧文档给的是同一件事的简化版：座位状态 ↔ 余票 ↔ 购票结果 ↔ 订单结果 [E2]。这两处都是设计期口径，未必逐条对应当前代码；如果当前实现仍沿用这个模型，那么链条的含义是——链条上任取一环，它的正确性都要靠相邻环来定义。座位被标记为已占用而余票没减，余票就是错的；订单明细里写着一个座位而座位状态仍是可售，订单就是错的；支付成功了而订单被超时关掉、座位被放回可售，那这笔钱就买了一个已经不存在的资源 [E14]。所以这里说的"一致性"，不是"某张表没写坏"，而是"这几组状态互相指向同一个事实"。

麻烦的是，这个事实很容易被撕开，而撕开的位置是有限的、可枚举的。购票侧文档成体系地列了五类故障情形，并逐条给出业务上正确的结果和必须对齐的数据 [E2]：

| 故障情形 | 业务上正确结果 | 必须一致的数据 | 文档标出的后续技术问题 |
| --- | --- | --- | --- |
| 座位分配成功，订单创建失败 | 本次购票整体失败，座位回到可售 | 座位状态、车票记录、订单（不应存在） | 事务边界、远程调用失败处理、补偿 |
| 订单创建成功，座位未正确占用 | 不允许出现，订单明细的座位必须真被占用 | 订单明细、座位状态 | 跨服务一致性、对账/补偿 |
| 余票减少，但购票失败 | 余票恢复（余票由座位状态派生） | 余票口径与座位状态 | 缓存与数据库口径一致性 |
| 服务调用超时，订单实际已创建 | 用户最终只得到一笔订单、一组座位 | 订单、座位、车票记录 | 幂等、结果查询确认 |
| 用户重复提交导致数据重复 | 只产生一笔订单、一组座位 | 订单、座位、车票记录 | 幂等与防重提交 |

把这张表竖着读一遍会发现，撕开的关口几乎都落在"两次写之间"，而不是某一次写内部：占座与建单之间、建单与写座位之间、减余票与落座位之间、请求超时与订单真正落库之间、用户第二次点击与第一次结果之间。文档在最后一列给出的定性也正是这几类——"事务边界、远程调用失败处理、补偿""跨服务一致性、对账/补偿""缓存与数据库口径一致性""幂等" [E2]。换句话说，问题不是"某个操作写错了"，而是"两个各自正确的操作之间存在一个会失败的缝隙"。

支付侧还要多一层。它列出的四条必须成立的关系覆盖了另一组撕裂：支付成功而票务回调失败（不能超卖，订单也不能被超时关闭）、关单成功而回滚座位失败（座位最终必须回到可售）、用户重复提交支付（只能有一笔有效支付）、回调重复投递（状态不回退）[E14]。对照两组场景可以看出一个差异：购票侧的多数场景要求"要么整体成、要么整体败"，支付侧的这几条要求的是"即使中途断了，最终也要走到正确的那一边"。

为什么这些缝隙关不上？因为这些状态并不都在同一个库、同一个事务里——场景描述中出现的是票务回调、订单、支付单这类跨服务动作 [E14]，而项目自身的结论说得更直接：跨服务的操作不能靠一个数据库事务，必须靠状态机 + 幂等 + 补偿达到最终一致 [E15]。这说明缝隙不是实现粗糙造成的，而是事务的覆盖范围天然小于状态的分布范围。一个本地事务能保证的只是"同一个库里的几行要么都写、要么都不写"；它既管不了"座位库写了、订单库没写"这种断口，也管不了"请求发出去了但没等到响应"这种结果不确定的状态。

于是问题被压成三层，每层要解决的根本不是同一个问题：有争抢存在时，需要一层在事务之外先保证"同一时刻只有一个人能碰这个座位"；同库内的那几步写，需要一层保证"要么都成要么都不成"；而跨服务、跨库的断口既没有共同事务、也没有确定的调用结果，只能靠记录状态、让重复执行不产生副作用、再把没走完的状态推向终态，追求"最终都成"。这三层各自挡什么、接缝留在哪里，是接下来要展开的内容。

## 贯穿全文的模型：一致性被拆到三个层次上

购票占座的一致性不是一个开关，而是被打散到三个层次上的三件事：Redis 锁负责"不许同时抢"，本地数据库事务负责"要么都成要么都不成"，跨服务之间只能靠状态机、幂等与补偿走向"最终都成"。

先把这张能自己画出来的分层图记住，后面所有细节都往上挂：

```text
[层1 串行化]  用户锁 → 席别锁              ← 事务之外
        ↓
[层2 原子]    @Transactional               ← 只碰 ticket 库
              SELECT 车次 / 站间关系
              UPDATE seat  AVAILABLE→LOCKED（带状态条件）
              INSERT ticket UNPAID
        ↘ commit
[层3 最终一致] 返回结果 → 编排层发起远程下单 → 补偿 / 回调 → 状态机收敛
```

第一层是串行化层。从 `reserveLocally` 的调用顺序看，它先 `userLock.lock()`，再按 `seatTypeCounts` 逐个加席别锁，全都拿到之后才调用 `doPurchaseInTransaction`，`finally` 里按相反顺序释放席别锁、最后释放用户锁 [E6]。这一段解决的正是"两个请求同时抢同一个座位"：席别锁把并发改成排队。用户锁处理的是另一个维度——同一个用户重复提交 [E4]。

第二层是原子层，也就是 `doPurchaseInTransaction` 的方法体。它带 `@Transactional` [E9]，在同一个事务里做三件事：读取车次与站间关系、把选中的座位从 `AVAILABLE` 更新为 `LOCKED`、为每位乘车人插入一条 `UNPAID` 的 ticket 记录 [E9]。这里最值得盯住的是那次 update 带着 `.eq(SeatDO::getSeatStatus, AVAILABLE)`，并且把 `affectedRows` 与座位数比对，不相等就抛异常 [E9]。这说明占座不是"读了再写"的松散写法，而是一次带状态前提的条件更新：即使锁没兜住、或座位状态已被别处改动，事务也不会把已被占用的座位再占一遍。座位状态与车票记录必须在同一个事务里一起落地——这是"要么都成要么都不成"在代码里的落点。

第三层是最终一致层。`doPurchaseInTransaction` 全程没有发起跨服务调用，它只在本库里写数据，然后把 `orderCreateReqDTO`、`ticketOrderDetails` 和一份 `compensationRequest` 打包成 `PurchaseReservationResult` 返回 [E9]。类注释把这条边界写得很直白：本事务只操作 ticket 数据库，远程调用留在编排层，避免网络等待延长行锁持有时间 [E10]。订单服务、支付服务不可能和 ticket 库共用一个数据库事务，所以一旦跨过去，原子性就不存在了，只能用状态机 + 幂等 + 补偿去逼近最终一致 [E15]。而这条路径需要一个"失败后更安全"的中间态：座位停在 `LOCKED`，对可售库存而言同样不会被别人买走，因此"订单已支付 + 座位仍锁定"是可以安全等待补偿的组合，这也是源码注释固定为"先订单、后票务"的理由 [E13]。

把三层连起来，分层原则是：能在同一层里原子解决的，绝不跨层去做；一旦跨层，就只能接受最终一致 [E15]。第一层与第二层的关系恰好印证这一点——文档给出的结构是 `lock { transaction { select update insert } commit } unlock` [E3]，锁包在事务外面，事务只包住它该包住的数据库读写。E4 给出这么排的理由：如果事务的快照建立得比锁早，锁内的读会读到锁外的旧世界 [E4]。所以顺序不能颠倒：锁先把并发挡在门外，事务再在这个已被串行化的窗口里做原子提交。

也要说清这套模型的边界：层 1 和层 2 里拿到的是严格串行与严格原子，层 3 的"最终一致"并不是"立刻一致"，它依赖状态机、幂等和补偿把中间态收敛回来 [E15]。至于缓存失效被安排在哪一步、由谁触发，本轮证据只能看到 `PurchaseTicketTxService` 持有 `RedisCacheHelper` 依赖 [E10]，具体时机无法从这些片段确认；如果后面要讲补偿的完整闭环，需要另找证据。

## 一次占座从加锁到释放锁的实际顺序

一次占座请求的完整时序可以压缩成一句话：**先在事务外把所有锁拿齐，再进事务做本地读写，等事务提交返回之后才按相反顺序放锁。** 这正是核心模型的第一层与第二层在时间轴上的咬合点——锁负责"不许同时抢"，事务负责"要么都成要么都不成"，两者的先后顺序不能颠倒。

```
reserveLocally（编排层 PurchaseTicketServiceImpl）
 ├─ lock(userLock)                    ← 事务外
 ├─ lock(seatTypeLock) × N            ← 事务外
 ├─ Timer.start("seat-lock.hold")
 └─ doPurchaseInTransaction(@Transactional)
      校验车次 → 校验站关系 → 按席别分组 → 选座
      → 条件 UPDATE AVAILABLE→LOCKED → INSERT ticket → 组装订单请求
    // 方法返回 = COMMIT
 finally: 逆序 unlock 席别锁 → unlock 用户锁
（事务外，编排层后续执行）远程创建订单
```

**第一步：编排层先拿用户锁。** 入口在 `reserveLocally`，它先通过 Redisson 取一个以"用户名 + 车次"为键的 `RLock` 并 `lock()`，同时把 `userLockAcquired` 置为 true [E6]。这一步落在编排层而不是事务层，是因为它的职责只是并发闸门，和数据库无关。用户锁粒度最大，先拿它可以把同一个用户对同一车次的重复请求挡在门外；代码紧接着 `userLockAcquired = true` 而不是在 `lock()` 之前置位，也说明这一层的写法考虑了"加锁本身失败"的情况。

**第二步：按席别逐个拿席别锁。** 拿到用户锁后，循环 `seatTypeCounts.keySet()`，为每个席别取一把以"车次 + 席别"为键的锁并 `lock()`，每成功一把就加进 `seatTypeLocks` 列表 [E6]。锁的集合来自入参 `seatTypeCounts`，而不是在事务里算出来的。为什么要分成两级而不是一把锁：用户锁隔绝"同一用户重复提交"，席别锁隔绝"不同用户抢同一席别的同一批座位"，后者才是真正的资源竞争面。

**第三步：进入事务方法。** 两把锁都到手之后，先 `Timer.start` 开始给"席别锁临界区持有时间"计时，然后 `return purchaseTicketTxService.doPurchaseInTransaction(...)` [E6]。注意调用点是 try 块内的直接 return——这说明**加锁代码在事务方法之外**，不是事务的切面行为。

**第四步：事务内的固定顺序。** `doPurchaseInTransaction` 标注了 `@Transactional(rollbackFor = Exception.class)`，它按"校验 → 分组 → 选座 → 占座 → 写车票 → 组装参数"展开 [E9]：先 `loadTrain` 与查 `TrainStationRelationDO` 确认车次和出发/到达站关系成立，不成立就抛异常；再把乘客按 `seatType` 用 `LinkedHashMap` 分组；对每个席别调用 `seatAllocator.allocate` 选座，座位数不够直接抛 `SEAT_NOT_ENOUGH_MESSAGE`；接着是并发正确性的关键一步——用 `update seat set seatStatus = LOCKED where id in (...) and seatStatus = AVAILABLE` 做条件更新，并要求 `affectedRows == seats.size()`，否则同样抛异常 [E9]。条件里的 `seatStatus = AVAILABLE` 是乐观校验，`affectedRows` 的对账是它的验收条件。之后逐条 `insert` 车票记录，同时累积 `orderItems` 和返回给上层的 `ticketOrderDetails`，最后组装出 `TicketOrderCreateRemoteReqDTO` 和一个 `TicketCallbackReqDTO` 补偿请求一起返回 [E9]。

**第五步：事务内不做远程调用。** 这一点是显式设计：`PurchaseTicketTxService` 的类注释写明"本事务只操作 ticket 数据库；远程调用留在编排层，避免网络等待延长行锁持有时间"[E10]。所以事务方法返回的是"准备好但还没发出去"的请求对象，真正的跨服务调用由编排层在事务之外做。从核心模型看，这是把本地事务这一层和跨服务最终一致那一层在时间上拆开——本地事务只承诺座位变 LOCKED、车票落库这两件事同时成立。

**第六步：提交之后再放锁。** 事务方法 return 意味着事务提交完成，控制权回到 `reserveLocally` 的 finally 块：先停掉计时（用 try/catch 包住，注释说明可观测性不允许改变预约或令牌语义）[E6]，然后**倒序**遍历 `seatTypeLocks` 逐个 `unlockSafely`，最后才释放用户锁 [E6]。文档把修正后的顺序明确总结为"拿锁 → 事务开始 → 选座 → 占座 → 提交 → 释放锁"，并强调先 commit 再 unlock，这样后一个线程拿到锁时前一个事务已经提交 [E1]；结构图上对应的就是 `lock { transaction { select; update; insert } //commit } //unlock` [E3]。

**第七步：finally 保证对称释放。** 释放逻辑放在 finally 里，意味着事务内任何异常导致回滚，锁同样会被释放；而由于 `userLockAcquired` 与 `seatTypeLocks.add` 都发生在加锁成功之后，中途失败时只会释放真正持有过的那几把锁 [E6]。倒序释放（先席别锁、后用户锁）与获取顺序相反，读者可以据此把整条链路记成"由外向内进、由内向外出"。

由此可以说，一次占座请求在各组件中的落点是：并发控制落在编排层的 Redisson 锁上，数据正确性落在 `PurchaseTicketTxService` 的本地事务与条件 UPDATE 上，而跨服务的订单创建被推到事务之后，留给状态机、幂等与补偿那第三层去收敛 [E10]。你在复述这条链路时只要记住三件事的顺序——锁、事务、解锁——就能推出其余细节为什么必须这么排。

## 为什么锁必须在事务外面

锁在事务外面，决定的不是代码好不好看，而是**锁里面那次 SELECT 读的到底是哪一份世界**。[E4] 项目里购票链路有两把锁——用户锁负责防同一用户重复提交，席别锁负责串行化占座——最要紧的一条是两把锁都放在事务外面，给出的理由也正是这一点：事务的快照若建立得比锁早，锁内的读读到的就是锁外的旧世界。[E4]

项目给出的正确嵌套结构是这样的 [E3]：

```text
lock
{
    transaction
    {
        select
        update
        insert
    } // commit
} // unlock
```

展开成时序就是"拿锁 → 事务开始 → 选座 → 占座 → 提交 → 释放锁"，注意 commit 明确落在 unlock 之前 [E1]；这样安排的直接后果是：后一个线程拿到业务锁时，前一个事务已经提交。[E1]

把两个请求放进来走一遍，这个顺序的价值才看得清。以下是一条用于说明机制的假设轨迹（不是项目运行日志）：A、B 两个请求想占同一个席别。在正确顺序下，A 先拿到席别锁，然后才开启事务，走 select → update → insert ticket，提交，最后释放锁；B 全程只能在锁上排队。等 B 拿到锁时，A 的事务已经提交 [E1]，B 这才开始自己的事务，于是 B 锁内的 select 看到的是 A 落库之后的状态，条件校验（"这个座位还能不能占"）是在新鲜数据上做的——B 被正确拦下。整个链路的串行化之所以成立，是因为"放行"这个动作发生在"别人已经提交"之后。

再看反过来写会怎样：先开事务，再去取锁。仍然假设 A、B 几乎同时到达，两个事务在各自拿到锁之前就已经开启，读取视图也就在那个时刻定下来了（这是 MVCC 数据库的一般语义，不是本项目证据里能确认的配置——本项目实际隔离级别未在证据中出现，所以这里只能作条件判断：**如果**隔离语义是"事务开始时固定读视图"这一路，**那么**）A 抢先做完并提交、释放锁之后，B 才拿到锁，但 B 的读视图还停在它自己事务开始的那一刻，即 A 提交之前。于是 B 锁内的 select 读到的仍是旧世界：条件校验看到的座位还是可占的，B 照样去 update / insert。结果是——锁确实把两个临界区严格串行化了，可串行执行的两次读却读到了同一个旧状态。锁解决了"同时"，没有解决"看得见"，这就是两者的分工边界：锁负责互斥进入，事务语义负责可见性，只有把事务整个包进锁的临界区里，前者的串行化才能传导到后者的读上。

由此还能反推出一个不可交换的细节。E1 说"后一个线程拿到业务锁时前一个事务已经提交"，这条保证依赖的是 commit 在 unlock 之前 [E1]；如果释放锁被提到提交之前，那么后一个线程拿到锁时前一个事务可能还没提交，这条保证就不成立了，锁内读到的又会是未提交状态。也就是说，"锁 → 事务 → 提交 → 解锁"里，锁在事务外和提交在解锁前是两个必须同时满足的约束，缺一个，锁内读的可信度就掉回旧世界 [E1][E3]。这条规则对用户锁同样适用，因为两把锁都在事务外面 [E4]。

要划清的边界是：这套机制只回答"同一席别的并发占座，锁内的读是否可信"，它不改变事务自身的原子性（那仍由事务保证），也没有说明项目选了哪种隔离级别——证据里没有这一项，因此任何关于"用的是什么隔离级别"的推断都超出了当前证据。

## 事务内部：占座是怎么做到“要么成功要么不占”的

原子性在这个项目里不是一行注解的事，而是落在几道闸门上：几道是显式抛出的异常，最后一道是数据库自己回报的"我到底改到了几行"。

把 [E9] 的方法体压成伪代码，闸门的位置就清楚了：

```java
@Transactional(rollbackFor = Exception.class)
doPurchaseInTransaction(...) {
    TrainDO train = loadTrain(trainId);            // 车次不存在 -> 抛
    TrainStationRelationDO relation = ...;         // 区间数据不对 -> 抛
    Map<Integer, List<...>> seatTypeMap = 乘客按席别分组;
    List<SeatAssignResult> assignResults = new ArrayList<>();
    for (每个席别 : seatTypeMap) {
        List<SeatDO> seats = seatAllocator.allocate(trainId, dep, arr, seatType, 人数);
        if (seats.size() < 人数) throw 余票不足;
        int affectedRows = seatMapper.update(
                set seat_status = LOCKED,
                where id IN seatIds AND seat_status = AVAILABLE);
        if (affectedRows != seats.size()) throw 余票不足;   // 最终防线
        assignResults += 乘客与座位一一配对;
    }
    for (每个 assignResult) {
        ticketMapper.insert(ticketDO);              // 与上面的 UPDATE 同一事务
        组装 orderItems / ticketOrderDetails;
    }
    return new PurchaseReservationResult(...);
}
```

前半段的两个检查是"数据前提"性质的：车次、区间关系读不出来就抛，跟并发无关。真正的拉锯从 `seatAllocator.allocate` 开始。它返回的 `seats` 是从之前查到的 AVAILABLE 座位里挑出来的**候选**集合，而读取和写入之间必然存在时间窗口，候选并不等于到手。

所以关键的一步是那条条件更新：`UPDATE seat SET seat_status = LOCKED WHERE id IN (...) AND seat_status = AVAILABLE` [E9]。它把"判断这个座位还空着"和"把它置为 LOCKED"合并成同一条 SQL，判据从应用层看到的旧快照，换成了数据库执行这一刻的真实状态；受影响行数就是"我实际抢到的座位数"。因此当 `affectedRows != seats.size()` 成立，说明在读取与更新之间，有别的请求先把其中一部分座位改成了非 AVAILABLE，此时抛余票不足 [E9] 是对的。这就是防超卖的最终防线——它不是应用层的一次 if 判断，而是数据库对写入的定序结果。

值得留意的是，`affectedRows` 不足时，代码里并没有任何一行去把已经改成功的那几个座位改回 AVAILABLE。这不是遗漏：抛出的异常由 `@Transactional(rollbackFor = Exception.class)` [E9] 兜住，本次事务内已经执行的 UPDATE 会一起撤销。这也解释了为什么这些检查全都写成 `throw` 而不是返回一个失败结果——返回值不会触发回滚。从同一处还能看出，当席别多、循环到第二轮才失败时，第一轮已经锁掉的座位也不需要手工清理，它们和当前这一轮一起被回滚，这正是"整批要么都成、要么都不成"在代码里的落点。

车票记录与座位状态的同生共死也是靠同一件事：`ticketMapper.insert(ticketDO)` 就写在 `doPurchaseInTransaction` 内部 [E9]，和座位条件是同一个事务边界，[E10] 的类注释也把这一层限定为"只操作 ticket 数据库"。因此不会出现座位 LOCKED 而车票没落库、或车票落库而座位仍是 AVAILABLE 的中间态。

这个边界是刻意收窄的：远程调用被留在编排层，理由是避免网络等待延长行锁持有时间 [E10]。也就是说，这一层事务只对本地库负责，它既不管"不许同时抢"——那由调用方已经持有的用户锁和全部席别锁保证 [E10]——也不管跨服务的订单创建。三层职责里，它恰好就是中间那一层。

提交之后的动作则被有意推到事务外。[E7] 的 `returnTokensAfterCommit` 先看 `TransactionSynchronizationManager.isSynchronizationActive()`：没有活跃同步就直接执行，有就注册一个 `afterCommit` 回调把令牌回补放到提交之后 [E7]。之所以不能放在事务体内，是因为令牌是 Redis 侧的独立状态，数据库回滚撤不回它；如果先回补再回滚，就会出现"座位没占成、令牌却已经还回去"的错配。这一点 [E7] 位于 `TicketCallbackServiceImpl`，并不在 [E9] 的事务方法里，但两者遵循同一条纪律：凡是提交之后才应该发生的副作用，都必须挂在提交确定之后，而不是写在事务里面。

## 为什么把远程调用留在事务外，而不是上分布式事务

这段设计要先看它被什么约束住。`PurchaseTicketTxService` 的类注释交代得很直接：调用方已经完成乘车人校验并持有用户锁和全部席别锁，而"本事务只操作 ticket 数据库；远程调用留在编排层，避免网络等待延长行锁持有时间" [E10]。也就是说，事务窗口里握着的是席别级别的行锁，窗口的长度直接等于这些锁被占住的时间。把远程调用放进窗口，锁持有时间就从"几条本地 SQL"变成"几条本地 SQL 加上一次网络往返加上下游处理时间"；热点车次上，这段时间里所有想买同席别的请求都得排队。所以第一个选择不是审美问题，而是锁成本问题：事务边界刻意收缩到只覆盖 ticket 库的操作。

第二个选择是跨服务不用一个数据库事务。项目文档把这条写成核心约束：跨服务的操作不能靠一个数据库事务，必须靠状态机 + 幂等 + 补偿达到最终一致 [E15]。这是项目自己的定位，而不是对某种实现细节的描述。通用地看，分布式事务要把参与者的资源锁一直持有到全局提交决定作出为止，锁窗口等于协作过程本身；在本项目这种"锁本来就是稀缺资源、且要先尽量避免长时间持锁"的前提下 [E10]，这个方向与第一层约束是冲突的。所以这里不是"分布式事务做不到"，而是它与已经付出的锁代价不相容——注意这是从锁约束推出的判断，不是源码里写明的对比结论。

真正让这个拆分站得住的是中间状态的选择。文档明确把顺序固定为"先 Order、再 Ticket 座位"，并且给出理由：座位处于 LOCKED 时，"对可售库存而言同样不会被别人购买"，因此"Order 已支付 + Seat 仍锁定"可以安全等待补偿 [E13]。这句话的关键在于 LOCKED 的语义——它虽然不等于 SOLD，但在可售性上已经排他，别人抢不走。于是拆开执行造成的中间态不再是"钱付了票被别人买走"这种不可逆的坏状态，而是一个可以被后续动作收敛的状态，这正是"无法一步原子完成时，要选择失败后更安全的中间状态"这条原则的落地 [E13]。反过来推：如果顺序相反，先让票务把座位推到 SOLD、再建订单，那么中途失败就会落到"票已定死、订单不存在"的位置，缺少一个自然的状态载体去驱动重试和补偿——这是一条设计上的条件推理，文档并没有给出反向实现的证据。

代价也必须说清楚：既然 LOCKED 只是"暂时排他"，就必然要有一条把 LOCKED 继续推到 SOLD 的补偿/重推路径，否则已支付订单对应的座位会一直停在锁定态。文档在订单支付链路层面给出的对应问题是"用户不付款怎么办 → 座位不能被永久占用 → 超时关单" [E15]，这与前一条互相呼应：LOCKED 需要一个出口，无论出口是推向 SOLD 还是释放。

回到整体：锁被放在事务外，是为了让"不许同时抢"这件事尽早发生；本地事务只碰 ticket 库，是为了让"要么都成要么都不成"的范围尽量窄 [E10]；而跨服务这一段放弃了原子性，换取的是短锁窗口，代价是必须靠状态机驱动的幂等与补偿把中间态收敛掉 [E15]。先前那种"订单成功、座位仍 LOCKED"的中间态之所以可接受，正是因为 LOCKED 在可售语义上已经等价于"别人买不走" [E13]。

## 跨服务那一半：状态机、幂等与补偿

本地事务的原子性止步于单个数据库连接；支付单在支付库、订单在订单库、座位在票务库，任何一次回调都要跨库落地。所以这一段一致性不是靠"一次事务"实现的，而是把状态推进拆成若干个单库内、可重复执行的动作，再用幂等和补偿把没走完的部分补上——状态机负责"知道走到哪了"，幂等负责"重跑不坏事"，补偿负责"最终走到头"。

数据流的方向是固定的：先推进订单，再推进座位。E13 记录了当前源码注释就是按这个理由固定为"先订单、后票务"，因为 LOCKED 与 SOLD 对可售库存而言同样不可售，所以"订单已支付 + 座位仍锁定"是可以安全等待补偿的中间态 [E13]。E12 从另一侧说明了同一个道理：座位状态决定可售性、支付与取消结果推进订单状态，余票展示和订单展示分别从这两者派生——只要中间态对"可售性"是安全的，对外就不会产生错误 [E12]。

把这条链上会出的岔子列全，就能看清每种机制各自堵的是哪个口子：

| 不一致场景 | 业务上必须成立什么 | 收敛机制 |
| --- | --- | --- |
| 回调重复投递 | 状态不回退、不报错 | 条件更新 + 影响行数判断 [E14] |
| 用户重复提交支付 | 只产生一笔有效支付 | `uk_order_sn` 唯一 + 复用已有支付单 [E14] |
| 关单成功、回滚座位失败 | 座位最终回到可售 | 消费者重投 / 兜底扫表重跑，方法幂等 [E14] |
| 支付成功、票务回调失败 | 不能超卖，订单不能超时被关 | 先通知订单（订单已支付），座位停在已锁定，补偿重推 [E14][E13] |
| 座位被错误改成可售 | 不能超卖 | 靠"只把已锁定改成可售"的条件杜绝 [E12] |

逐条看为什么只能这么做。

幂等靠"条件更新 + 影响行数"实现。写操作被组织成"当前状态等于期望的前置状态时才改成目标状态"，重复投递时第二次更新命中的行数是零 [E14]。这里的关键约定不是那条 SQL，而是对结果的解释：零行要读成"这件事已经做过了"，而不是失败——否则要么报错（重复投递变成故障），要么静默（真正的前置状态不符也被吞掉）。这是通用做法上的推导，历史文档只记录了"条件更新 + 影响行数"这一做法本身 [E14]，没有写调用方如何区分这两种零行。

订单侧防重复提交靠唯一键加复用。`uk_order_sn` 让并发的重复插入里只有一笔能成功，落败的那笔不新建记录，而是复用已存在的支付单 [E14]。这比"先查再插"稳，因为查询与插入之间的窗口正是并发钻进来的地方。

补偿路径在关单回滚座位失败时启动：消费者重投，或者兜底扫表重跑，而被重跑的方法本身幂等 [E14]。两条路并存说明设计不假设消息一定送达；同时它也反过来说明幂等是补偿的前提——不幂等的方法越重投越坏。

防超卖是唯一不能靠补偿挽回的一条。E12 明确把这张表按严重度排序：从下往上错误越来越严重，设计的重点就是把"座位被错误改成可售"这一行彻底堵死 [E12]。无差别的"置为可售"在重投、并发关单、状态错乱时都可能把一张已经卖掉的座位放回池子，而超卖没有重推能修回来；限定为"只允许已锁定→可售"的条件回滚后，重复执行也只是空操作 [E12]。

支付成功而票务回调失败时，处理方式是先让订单侧生效，座位停在 LOCKED 等补偿重推 [E14][E13]。这样做的代价是:在补偿完成前，座位既不是"已售"也没回到可售，系统对外靠"已锁定同样不可售"来维持不超卖 [E13]。E12 的对照表还给出了这一行的影响判断——订单已支付、座位未变已售，对外影响是"无" [E12]，因为两种状态对可售库存等价。同一张表里"余票缓存未失效"这一行的影响是少卖，修法是删除缓存 key [E12]，属于同一严重度量级里的次一级问题。

需要说明证据强度：E12 与 E14 是历史设计/阅读指导文档，时间标记为 HISTORICAL，因此上面这些具体做法在当前代码中的逐条一致性无法确认；如果历史口径在当前实现中仍然成立，那么跨服务这一半的收敛方式就是上述条件更新、唯一键复用与幂等补偿的组合。E13 属于当前设计文档，但其时间标记为 UNKNOWN，同样只能作为设计口径而非代码事实来读。

## 把失败路径逐条走一遍

正常路径先摆出来，否则失败路径无从谈起：reserveLocally 在事务外先拿用户锁、再按席别逐个加锁 [E6]；进 doPurchaseInTransaction 后在同一个事务里把座位条件更新成 LOCKED、写入车票记录，并把远程订单创建请求和一份 TicketCallbackReqDTO 补偿请求一起组装好返回 [E9]；事务提交之后，调用方才在事务外发起订单创建，最后删余票缓存 [E8]。三层机制的接缝就沿着这条线分布，下面每一条撕裂都能落到某个接缝上。

第一条，并发抢到同一座位。两个请求同时走到座位更新这步，条件更新带的谓词是 seatStatus = AVAILABLE，同一批座位只有一个请求能把影响行数改满；另一个拿到的 affectedRows 小于 seats.size()，直接抛 SEAT_NOT_ENOUGH_MESSAGE [E9]。异常抛出点还在事务内部，@Transactional(rollbackFor = Exception.class) 让占座和写车票一起回滚 [E9]；异常继续向上冒泡穿过 reserveLocally 的 try，finally 逆序释放席别锁、再释放用户锁 [E6]。这条路径值得注意的是它根本没走到跨服务那一层——锁负责"不许同时抢"，影响行数负责"抢了也得改得动"，事务负责"改不动就全退"，前两层就把问题关掉了。也就是说，影响行数校验在这里不是防御性编程，它是乐观并发的判定点；少了它，两个请求都会认为自己占到了同一个座位。

第二条，占座事务已提交，但订单创建失败。这条开始越过提交点：座位已经 LOCKED、车票已经写进去，而订单在另一个服务里没建起来 [E9]。本地事务已经结束，没有任何机制会回头纠正它——回滚只在异常穿过事务边界的那一刻发生，此时边界早已关闭。按历史设计文档的分类，这种情形业务上正确的结果是"本次购票整体失败，座位必须回到可售"，必须一致的是座位状态、车票记录和"订单不应存在"，后续技术问题正是事务边界、远程调用失败处理和补偿 [E2]；同源材料给出的修法是重试回滚 [E12]。这里要打个折扣：这些结论来自历史设计文档，当前实现的补偿由谁触发、触发条件是什么，证据里并未确认 [E2]。不过有一条当前代码的线索值得留意：补偿用的 TicketCallbackReqDTO 是在 doPurchaseInTransaction 内部、提交之前就组装好并随返回值带出来的 [E9]，这说明设计上预留了"这条事务一旦提交、后续任何一步失败，都有一份能拿来回滚座位的凭据"——凭据准备好了，谁按按钮仍不清楚。

第三条，余票缓存删除失败。它的定位和前两条不同，发生在派生数据而不是权威数据上。evictRemainingTicketCacheSafely 把 delete 包在 try 里，捕获 RuntimeException 后只打一行 warn，日志自己就写着"本地占座已提交，但余票缓存删除失败，等待缓存过期" [E8]。它没有重试、没有抛异常、没有进补偿队列——这是刻意的降级。理由是层次问题：座位状态是权威，余票是从座位状态派生出来的展示口径 [E2]，删缓存失败只是让展示层短时间看到偏小的余票；对照历史文档的修法表，"余票缓存未失效"的对外影响是少卖，修法是删除缓存 key，而它下面一行"座位被错误改成可售"才对应超卖 [E12]。所以这里的取舍是拿少卖换不超卖，缓存过期是兜底时钟。代价也真实存在：过期窗口内用户看到的余票少于实际，属于可用性上的让步；证据里没说明过期时长，也没说明是否有主动对账去提前纠正。

第四条，占座成功但下游回调失败。典型形态是支付已经成功，票务这边的座位还停在 LOCKED [E13]。这看着像不一致，其实是被刻意选中的安全中间态：LOCKED 对可售库存而言同样不会被别人购买 [E13]，所以"Order 已支付 + Seat 仍锁定"可以安全等待补偿 [E13]。历史材料把它写成"支付成功，票务回调失败 → 不能超卖；订单不能超时被关 → 先通知订单（订单已支付），座位停在已锁定，补偿重推" [E14]，对照表里对应行的对外影响记为"无（已锁定与已售都不可售）"，修法是补偿重推 [E12]。从这条能读出那个设计原则：无法一步原子完成时，要选"失败后更安全"的那一侧中间状态 [E13]。真正危险的方向是反过来——先改座位再通知订单，一旦订单侧失败，座位已经 SOLD 而订单还是待支付，要动的是可售性。

第五条，也是唯一没有答案的一条：补偿本身失败之后怎么办。现有证据里只有一份标记为【待填充】的追问清单，列着"扣了库存但订单创建失败，座位会不会一直占着""补偿失败了怎么办""为什么不用分布式事务""支付成功了但票务没改状态，用户怎么办""延迟消息丢了怎么办" [E11]。这些恰好就是上面第二到第四条路径的兜底问题，而清单本身是空的 [E11]。所以对第五条只能明确写成无法确认：补偿的重试上限、补偿失败后的告警与人工介入、延迟消息丢失后的对账扫表，在当前证据中都没有可引用的实现或设计。

把五条并排看，就能看清"对号入座"的边界落在哪：

| 故障场景 | 撕裂落在哪一层 | 收敛机制 | 证据状态 |
| --- | --- | --- | --- |
| 并发抢到同一座位 | 本地事务内的条件更新 | 影响行数不足 → 抛异常 → 回滚 → finally 释放锁 [E9][E6] | 当前实现已确认 |
| 占座已提交、订单创建失败 | 跨服务 | 回滚/补偿把座位放回可售 [E2][E12] | 部分：分类来自历史文档，触发方式未确认 |
| 余票缓存删除失败 | 派生数据 | 只记 warn，等缓存自然过期 [E8] | 当前实现已确认，属刻意降级 |
| 支付已成功、座位仍 LOCKED | 跨服务 | 补偿重推 [E13][E14][E12] | 设计文档有说明，实现细节仅部分 |
| 补偿本身失败 | 兜底 | 无 | 文档标注【待填充】，无可引用答案 [E11] |

表格的行序其实对应一条分界：前三条里，只要撕裂没越过本地事务的提交点，或者只伤到派生数据，三层机制都能自行闭合；一旦越过提交点，收敛就完全依赖状态机、幂等和补偿，第二条和第四条都属于这一类；而第五条提醒你，这条链的最后一段——补偿的补偿——在现有证据里是断的。

## 这套机制保证到哪一步，代价是什么

这套机制换来的不是一种一致性，而是三种强度不同的一致性叠在一起，代价也就落在三个不同的位置上。

最里面一层是真的强原子。`reserveLocally` 拿到锁之后调用的 `doPurchaseInTransaction` 属于 `PurchaseTicketTxService`，它的类注释把边界写得很死：本事务只操作 ticket 数据库，远程调用留在编排层 [E10]。这意味着 ticket 库内的一批写要么全提交、要么全回滚，不存在半成品——这一层没有窗口期。往外一层立刻换了性质：订单、支付、票务不是一个库，文档给出的路线是状态机 + 幂等 + 补偿 [E15]，目标是最终一致而不是强一致，而且这是有意选择的结果 [E15]。再往外还有缓存这一层，它连"最终一致"都是靠事后删 key 去追的。

先说被牺牲的吞吐。`reserveLocally` 里席别锁的 key 由车次和席别拼成 [E6]，因此同一车次同一席别的占座请求会被排成一队；从调用顺序看，这个 key 里没有用户、也没有乘车站点，所以不同乘客买同一车次同一席别时同样要互相等待 [E6]。这就是用并发度换正确性：宁可让本来可以并行的请求串起来，也不允许两份请求在同一时刻各自判定同一份余票。两把锁还都被放在事务之外 [E4]，锁的持有范围比事务更长，代价是在锁里等待的线程持有锁本身的时间也被拉长——换来的是锁内的读不会读到锁外的旧快照 [E4]。

再说窗口期，它是最终一致必然附带的。中间态是真实存在的：座位已经锁定但还没变成已售，或者订单状态与座位状态在某一瞬间不同步。E13 解释了这个中间态为什么可以安全停留：LOCKED 对可售库存而言同样不会被别人购买，所以"订单已支付 + 座位仍锁定"可以安心等补偿 [E13]。真正的代价出现在缓存上——历史设计文档的对照表把"余票缓存未失效"归类为少卖 [E12]。它的后果不是算错库存，而是该卖的时候卖不出去，用户看到的是虚假的紧张。

这套设计里被当成重点防线的是最严重的一档。同一份历史对照表明确说了排序：从下往上错误越来越严重，最后一行是"座位被错误改成可售"，后果是超卖，修法是靠"只把已锁定改成可售"这个条件来杜绝 [E12]。这其实是把回滚写成了条件回滚：不是无条件把座位恢复成可售，而是先确认它确实处于本次占用留下的状态，才允许改回去。这一行的性质和其他几行不同——其他行的共同后果是少卖或用户多等一会儿，只有这一行会让同一个座位被卖出两次，所以设计的优先序是把这一行彻底堵死 [E12]。需要说明的是，这个排序原则出自历史支付模块的设计文档 [E12]，如果它在现行实现中仍然被遵守，那么"条件回滚"就是这套机制里最不能省的一步。

为什么选这条路而不是更强的即时一致？E13 给了判断标准：无法一步原子完成时，要选择失败后更安全的中间状态。往反方向走——比如用一个跨服务的分布式事务把订单、票务、支付圈进同一个原子操作（这是通用做法，本项目文档未讨论）——能消掉窗口期，但代价是让事务跨过网络、长时间持有各方资源。而 E10 的注释恰好把远程调用从本地事务里挪了出去，理由是不让网络等待延长行锁持有时间，方向与前者相反。所以这套机制宁可让中间态存在一段时间，也不愿意让事务边界越过服务边界。

边界要划清。ticket 库之外的订单与支付状态，不会因为那个本地事务而自动对齐，它们完全依赖补偿重推与幂等 [E15]；余票缓存可能短暂不失效 [E12]；最终一致也没有在给定证据里出现时间上界——如果补偿路径自身一直失败会怎样，从这份材料无法确认。所以准确的说法是：本地库内强原子，跨服务最终一致，重点防线是防超卖而不是防延迟。

## 三句话复述一遍

合上答案时，手里应该只剩三句话。

第一句：**抢座位的“不许同时抢”，是锁在事务外面挡住的。** 同一个人同一车次先过用户锁，再按席别逐个加席别锁，把整段占座过程串起来；两把锁都放在事务外面，事务先提交、锁后释放——因为如果事务快照建立得比锁早，锁内的读读到的就是锁外的旧世界 [E4]。代码顺序也是这么排的：先 `userLock.lock()`，拿齐所有席别锁之后才进入带事务的 `doPurchaseInTransaction`，`finally` 里倒序释放席别锁、最后才放用户锁 [E6]。

第二句：**“要么都成要么都不成”，是本地事务里的带条件更新加影响行数校验兜住的。** 座位从 `AVAILABLE` 改成 `LOCKED` 的这条 update 自带 `seatStatus=AVAILABLE` 条件，影响行数只要不等于申请座位数就抛“余票不足”，整个事务回滚 [E9]。这是防超卖的最后一道防线：锁解决的是“别人别在同一时刻抢”，事务解决的是“就算情况变了也不许少卖一张或多占一张”。所以这个事务只操作 ticket 库，远程调用被刻意留在编排层，不让网络等待拉长行锁持有时间 [E10]。

第三句：**跨服务那一段没得选，只能靠状态机 + 幂等 + 补偿走到“最终都成”。** 跨服务操作不能靠一个数据库事务，这是前提约束，于是每一步都要设计成可重放：幂等的条件更新让重推不会重复扣减，补偿把中途失败的那半截推完 [E15]。而在无法一步原子完成的接缝上，选择的是“失败后更安全”的中间状态——座位处于 `LOCKED` 时，对可售库存而言同样不会被别人买走，所以“订单已支付 + 座位仍锁定”这种状态可以安全地等着补偿 [E13]。

这三句分别回答三个不同的问题：谁不许同时抢、谁不许半途而废、谁保证迟早完成。复习提纲里并排摆着的那些关键词 [E5]，其实就是这三层各自的展开；能把三句话完整说出来，等于把整条链路的一致性骨架握在手里了。
