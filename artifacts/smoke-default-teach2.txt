Answer:
余票桶由 `TicketAvailabilityTokenBucket` 这个类承载，位于 ticket-services 的 tokenbucket 包下：

`services/ticket-services/src/main/java/edu/swu/fcj/my12306/biz/ticketservice/service/handler/ticket/tokenbucket/TicketAvailabilityTokenBucket.java` [E5]

需要留意的是，这个类里并没有一个"余票桶"类型的 Java 字段。从证据看，桶的实体存放在 Redis 中，类只是它的读写入口：

- 桶的键由 `buildBucketKey(trainId, departure, arrival)` 生成，即"车次 + 出发站 + 到达站"这一区间坐标决定一个桶 [E3]；
- 桶内按席别组织：`loadBucket` 会把车型支持的全部席别作为字段写进去，值为该席别的可售数量，并按 `expireMinutes` 设置 TTL [E4]；
- 取用与归还分别走 `takeToken` / `returnToken`，两者都基于同一个 `bucketKey` 执行 Lua 脚本 [E3][E2]。

因此，如果你是在找"余票桶的数据结构定义"，答案是它不体现为某个实体类的字段，而是 Redis 上的一个哈希结构，由 `TicketAvailabilityTokenBucket` 用 `RedisCacheHelper` 装载和操作 [E4][E5]。这一点也写在类的注释里：它"只负责购票准入，不是库存事实源" [E5]。

另外，`TicketDO` 虽然名字接近，但它不是余票桶——它是 `t_ticket` 表的车票实体，记录的是购票事实（订单号、乘客、车厢座位、席别、状态等） [E1]。

无法从现有证据确认的部分：桶内字段的具体命名规则、`buildBucketKey` 的字符串拼接格式，以及 `RedisCacheHelper` 的实现细节，这些在给出的证据片段中没有展开 [E2][E3][E4]。
