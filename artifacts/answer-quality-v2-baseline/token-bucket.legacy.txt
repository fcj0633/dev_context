Answer:
根据当前 Context，可以确认余票桶的设计要点如下；但其中 Lua 脚本内部、桶 key 具体格式、查询余票桶路径等无法确认。

**1. 定位与配置**

余票桶由 `TicketAvailabilityTokenBucket` 实现，注释明确说明：Redis 余票令牌桶只负责购票准入，不是库存事实源；异常时始终降级放行，最终是否能占座仍由 MySQL 条件更新决定。 
它通过配置开关控制：`my12306.availability.token-bucket.enabled` 默认 `true`，`my12306.availability.token-bucket.expire-minutes` 默认 `10` 分钟。 
桶的取令牌和归还分别使用 Lua 脚本 `lua/take_token_from_bucket.lua`、`lua/return_token_to_bucket.lua`。取令牌结果常量包括 `TAKE_SUCCESS=1`、`TAKE_REJECTED=0`、`BUCKET_MISSING=-1`。

**2. 桶的维度与内容**

桶 key 通过 `buildBucketKey(trainId, departure, arrival)` 构造，说明其设计维度是“车次 + 出发站 + 到达站”。 
装载时构造 `Map<Object, Object> bucket`，字段为席别字符串，值为对应可售数量字符串；对于车型支持但当前可售数为 0 的席别，会补 `0`。从 `hMultiGet`、`hPutAllWithTtl` 调用看，桶按 Redis Hash 结构进行批量读写并设置 TTL。

**3. 取令牌流程**

购票入口会调用 `tokenBucket.takeToken(trainId, departure, arrival, seatTypeCounts)`，若取令牌返回 `false`，则抛出“列车站点已无余票”。 
`takeToken` 的具体逻辑是：未启用、参数为空或请求席别为空时直接返回 `true`；否则对席别数量做 `normalize`，构造 bucketKey，并执行 `TAKE_TOKEN_SCRIPT`。 
如果脚本返回 `BUCKET_MISSING`，会调用 `loadBucket` 装载桶，然后再次执行取令牌脚本。 
若返回 `TAKE_SUCCESS`，增加 `my12306.token.pass` 指标并返回 `true`；若返回 `TAKE_REJECTED`，增加 `my12306.token.reject` 指标并返回 `false`。 
若装载后仍缺少席别，或取令牌过程抛异常，则记录 warn，增加 `my12306.token.degrade` 指标，并降级放行返回 `true`。

**4. 桶的装载流程**

`loadBucket` 会以 `LOCK_TRAIN_STATION_TOKEN_BUCKET` 加锁，并通过 `redisCacheHelper.executeWithLock` 执行装载逻辑。 
装载前先检查本次请求涉及的席别字段是否都已存在；注释指出“Key 存在不代表字段完整”，只要任一请求席别缺失，就重新装载完整桶。 
装载时执行一次聚合查询，从 `SeatDO` 按 `train_id`、`start_station`、`end_station`、`seat_status=AVAILABLE`、`del_flag=0` 统计各席别可售数，并 `group by seat_type`。 
随后查询 `TrainDO`，通过 `VehicleTypeEnum.findSeatTypesByCode(train.getTrainType())` 获取车型支持的全部席别；如果车次不存在或车型没有席别，会抛出 `IllegalStateException`。 
最后按车型支持的全部席别构造桶，缺失席别补 `0`，并用 `hPutAllWithTtl(bucketKey, bucket, expireMinutes, TimeUnit.MINUTES)` 写入 Redis，同时增加 `my12306.token.load` 指标。补 0 的目的是避免售完席别永久触发“field 缺失”重装。

**5. 归还令牌流程**

归还入口是 `returnToken(trainId, departure, arrival, seatTypeCountMap)`。未启用或席别数量为空时直接返回；否则 `normalize` 后构造 bucketKey，执行 `RETURN_TOKEN_SCRIPT`。 
如果归还异常，会记录 warn，注释说明“保留偏松降级并等待 TTL 自愈”，并增加 `my12306.token.degrade` 指标。

归还触发点主要有两类：

- 购票流程中，若本地预约未成功提交，`finally` 会调用 `returnToken`；注释同时说明“本地事务提交后，cancelCallback 是唯一的 token 归还者”。
- 取消流程中，`cancelCallback` 会将座位更新为 `AVAILABLE`，并按席别统计 `releasedBySeatType`；非空时调用 `returnTokensAfterCommit`。`returnTokensAfterCommit` 会在事务同步活跃时注册 `afterCommit` 执行归还，否则立即执行。

取消后还会调用 `evictRemainingTicketCache`，删除 `TRAIN_STATION_REMAINING_TICKET + trainId + departure + arrival` 组成的余票缓存 key，底层通过 `redisCacheHelper.delete` 删除。

**6. 降级与一致性设计**

整体设计是“Redis 桶做准入、MySQL 做最终占座事实”。取令牌异常或非预期结果时降级放行，避免 Redis 故障阻断购票；但最终是否能占座仍由 MySQL 条件更新决定。归还异常时也不强一致补偿，而是依赖 TTL 自愈，TTL 默认 10 分钟。同时通过 `pass`、`reject`、`degrade`、`load` 等指标观测运行状态。

**7. 当前无法确认的部分**

Context 未包含 `take_token_from_bucket.lua` 和 `return_token_to_bucket.lua` 的具体脚本内容，因此无法确认 Lua 内部如何原子扣减、归还多席别、返回值细节。 
未包含 `buildBucketKey` 的具体 key 格式、`normalize` 的具体实现、`execute` 如何序列化参数并调用 Redis 脚本。 
未包含 `RedisCacheHelper.executeWithLock`、`hPutAllWithTtl` 的内部实现，也未包含 `VehicleTypeEnum.findSeatTypesByCode` 的席别映射细节。 
尤其缺少“查询余票桶”的具体代码路径、调用关系及结果判定；现有 Context 只有 `TicketService#pageListTicketQuery` 接口声明，没有其实现或与令牌桶的调用关系，因此无法确认查询余票时是否读桶、如何读桶以及结果如何判定。
