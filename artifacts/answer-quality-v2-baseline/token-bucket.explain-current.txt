Answer:
项目的余票桶本质上是一层“购票准入令牌桶”，不是库存事实源：用 Redis Hash 保存每个“车次 + 发售区间 + 席别”的可售令牌数，购票前取令、业务撤销后按实际释放量归还；桶不预建而是懒加载，异常降级放行，最终能否占座由 MySQL 条件更新裁决。以下按定位、结构、装载、操作、并发、存储同步展开。

## 一、定位：购票准入拦截层，不是库存事实源

类注释明确：Redis 余票令牌桶只负责购票准入，不是库存事实源；异常时始终降级放行，最终是否能占座仍由 MySQL 条件更新决定。purchaseTickets 中只有 takeToken 返回 false 才抛出“列车站点已无余票”，即在进入占座处理前完成快速拒绝。令牌桶与展示余票必须使用不同 Key：展示余票走“写时删除 → 读时重算”，令牌桶走增量维护；若合并，购票成功后删除展示缓存会把令牌桶一并删除，下次装载将令牌重置为数据库值，已扣令牌被“还”回来造成虚高。实验报告从外部观察到首次购票自动创建桶、Hash 保留车型全部席别、TTL 600 秒，与“懒加载 + TTL 自愈”的定位一致。

## 二、数据结构：Redis Hash、三维复合键与席别字段

从实现看，桶结构落在 Redis Hash 上：键由 buildBucketKey(trainId, departure, arrival) 构建，实验报告中的形如 my12306-ticket-service:train_station_token_bucket:1_北京南_宁波 可对应为 trainId_出发站_到达站。Hash 的 field 是席别 seatType 的字符串形式，value 是该席别在“该车次 + 该发售区间”内的令牌余量；实验报告确认 Hash 包含车型全部席别（如 0/1/2），没有库存的席别也保留为 0。业务坐标上，车次 + 发售区间 + 席别唯一确定一条余票桶记录；支付/取消回调中的座位坐标还要再叠加车厢号与座号，五项合起来才能唯一定位一行座位。TicketDO 使用 trainId、startStation、endStation、seatType，与座位、票价保持同一坐标。

## 三、创建与初始化：懒加载装载、车型席别补 0 与 TTL

桶不预建。取令脚本返回 BUCKET_MISSING（-1）时调用 loadBucket，装载后再执行一次取令；实验报告从外部观察到的现象也是“首次购票自动创建”。字段缺失同样触发装载：代码注释指出“Key 存在不代表字段完整”，只要本次请求涉及的任一席别在 Hash 中缺失，就重新装载完整桶。装载在分布式锁内进行，锁键由 LOCK_TRAIN_STATION_TOKEN_BUCKET 模板套上由 trainId、departure、arrival 构建的 keySuffix，避免并发重复装载。初值来自一次聚合查询：对 t_seat 按 seat_type 分组统计 seat_status=AVAILABLE 且 del_flag=0 的记录数；随后查车次，取车型支持的全部席别，对聚合结果中不存在的席别补 0，再整体 hPutAllWithTtl 写入。补 0 的意图是避免售完席别永久触发“field 缺失”重装；车型无席别或车次不存在时抛 IllegalStateException，视为装载失败。TTL 与开关方面，默认 my12306.availability.token-bucket.expire-minutes=10、enabled=true，装载以 expireMinutes 为 TTL 写入，实验报告实测 TTL 为 600 秒。

## 四、操作链路：取令、拒绝、归还与取消回滚的归还责任划分

取令 takeToken 先 normalize 入参，再执行 take_token_from_bucket.lua；返回 1（TAKE_SUCCESS）计 my12306.token.pass 并放行，返回 0（TAKE_REJECTED）计 my12306.token.reject 并返回 false，返回 -1 则装载后重试；若装载后仍缺席别或脚本抛异常，记录 my12306.token.degrade 并降级放行。购票链路上的使用点是：purchaseTickets 先构建 seatTypeCounts，调用 takeToken，失败直接抛“列车站点已无余票”，从而在 reserveLocally 等占座处理前完成准入拦截。归还 returnToken 执行 return_token_to_bucket.lua，异常时记录 warn 与 my12306.token.degrade，保留“偏松降级并等待 TTL 自愈”的处理。归还责任划分是：购票侧本地事务若未提交（reservationCommitted=false），在 finally 中归还令牌；一旦提交，归还责任交给 cancelCallback，成为唯一归还方，避免重复归还。取消回调侧，cancelCallback 逐座位把车票状态置为 CANCELED，仅在把座位从 LOCKED 更新为 AVAILABLE 成功时才按席别 merge 释放数，随后用 returnTokensAfterCommit 在事务 afterCommit 阶段归还；若座位回滚失败，则恢复车票状态并只记警告，不归还令牌。

## 五、并发与一致性：Lua 原子脚本、装载锁与降级自愈

取令与归还都是 DefaultRedisScript 加载的 Lua 脚本，扣减/归还的“读—判断—写”在 Redis 单次原子执行内完成，不依赖应用层多步操作。装载互斥由 redisCacheHelper.executeWithLock 提供，锁内再做二次校验（hMultiGet + allNonNull），保证同一桶不会被并发重复装载。失败方向明确：取令异常、装载后仍缺席别、归还异常都走降级——取令侧放行，归还侧等待 TTL 自愈，最终由 MySQL 条件更新兜底，符合“准入层宁可偏松”的意图。收敛与幂等手段包括：字段缺失即重装整桶、按车型席别补 0 以终止重复重装、TTL 到期后再次触发懒加载时会以数据库当前可售数重新装载。

## 六、存储与同步：Redis Hash 的持久化安排，以及与展示余票缓存的边界

存储介质为 Redis Hash，写入使用 hPutAllWithTtl 带 TTL，默认 10 分钟、实测 600 秒；桶的生命周期由“懒加载创建 + TTL 到期重建”驱动，而不是长期驻留。同步策略是增量维护：购票扣减、取消归还都由业务事件驱动，只有 TTL 过期或字段缺失时才回到数据库做一次区间席别聚合重装。与展示余票缓存的分工：展示余票是写时删除、读时重算，令牌桶是增量维护，两者必须使用不同 Key，否则购票成功删除展示缓存时会把令牌桶一并删除，下次装载把令牌重置为数据库值，导致令牌虚高。令牌桶只是准入拦截层，即使数据因 TTL 或异常暂时偏松，最终占座仍由 MySQL 条件更新决定，因此它不承担库存事实源的持久化职责。

## 七、证据缺口与一处口径差异

有两个 Lua 脚本（take_token_from_bucket.lua / return_token_to_bucket.lua）的脚本体未出现在证据中，无法确认脚本内部比较方式、返回值分支与是否包含防负数等额外保护。RedisCacheHelper 中 executeWithLock、hPutAllWithTtl、hMultiGet、allNonNull 的实现细节未给出，锁的具体实现以及装载写入是否会刷新已有 TTL 只能从调用点推断。VehicleTypeEnum.findSeatTypesByCode 所用的车型—席别全集也未出现，无法列出所有参与补 0 的席别编码。除实验报告记录的懒加载与 600 秒 TTL 实测外，缺少针对 takeToken/returnToken 并发行为、降级路径与归还幂等的专项验证数据。另有一处口径差异：复习文档把令牌桶描述为“增量维护（只减不增）”，但当前实现中明确存在归还路径，returnToken 会执行 return_token_to_bucket.lua 把令牌加回，取消回滚成功后也在事务 afterCommit 阶段调用归还。因此“只减不增”应理解为“不像展示余票那样通过删 Key 后从数据库重算覆盖桶内容、只在业务撤销时按实际释放量归还”，而非字面意义上的绝对不增，以当前实现为准。

整体来看，项目的余票桶是一层 Redis Hash 准入桶：以“车次 + 区间”为 Key、席别为 field，懒加载装载、车型席别补 0、Lua 原子取还、异常降级并靠 TTL 自愈，最终正确性由 MySQL 条件更新兜底。
