Answer:
## 先给结论：项目里的余票桶是什么

项目里的"余票桶"不是数据库表，也不是库存账本，而是 `TicketAvailabilityTokenBucket` 这个 Spring 组件承载的一池 Redis 令牌：对外只暴露 `takeToken` 与 `returnToken` 两个公开方法，内部还有 `loadBucket`、`execute`、`buildBucketKey`、`normalize` 等私有方法 [E4]。桶的 Key 由"车次 + 出发站 + 到达站"决定，桶内 Hash 的 field 是席别、value 是该席别剩余的令牌数 [E4][E3]。

它的身份在类注释里写得非常直白：**"Redis 余票令牌桶只负责购票准入，不是库存事实源。异常时始终降级放行，最终是否能占座仍由 MySQL 条件更新决定"** [E4]。所以它不回答"还剩几张票"，只回答"这个请求值不值得放进数据库去抢"。取令失败/异常时放行，归还异常时只记日志等 TTL 自愈 [E7][E1]，判断口径全部朝"宁可多发令牌，不可少发"倾斜。

## 先把三种"余票"分开：真实可售、展示余票、令牌余量

后文所有取舍都建立在同一个前提上：项目里有三个东西都被叫"余票"，但载体、权威性和用途完全不同。把它们混成一回事，令牌桶就一定会做错——这也是设计文档反复强调的第一件事 [E17]。

| 名字 | 存在哪 | 权威性 | 用途 |
|---|---|---|---|
| 真实可售 | `t_seat` 中 `seat_status = AVAILABLE` 且 `del_flag = 0` 的行数 | 唯一权威 | 最终能不能买到由它决定 [E3][E17] |
| 展示余票 | Redis Hash，Key 形如余票前缀 + `trainId` + 出发站 + 到达站，field 是席别 | 近似值 | 查询接口给用户看 [E15][E17] |
| 令牌余量 | Redis 令牌桶 Hash（本项目由 `TicketAvailabilityTokenBucket` 维护） | 近似值，允许偏差 | 只做购票准入拦截 [E7][E17] |

三者的关系是"上游参考、下游裁决"：令牌桶的初始值懒加载自 `t_seat` 的可售聚合计数值 [E3]，所以它确实"看着像"库存；但它随后的增减只跟随取令与归还，不再回读数据库，允许短期偏离真实可售。真正的裁决权始终留在数据库那一条条件更新上 [E4][E17]。

这里要说明证据状态：`E17` 的时效标记为 FUTURE（开发计划文档），它描述的"三种余票"框架与当前代码的 `TicketAvailabilityTokenBucket`、`train_station_remaining_ticket` 缓存结构互相吻合 [E7][E15]，因此可以说**设计意图被实现沿用**，但不能反过来把该文档的每一句都当成当前运行时的实测结论。

## 桶的代码实体与 Redis 结构

`TicketAvailabilityTokenBucket` 的依赖很能说明它的定位：`StringRedisTemplate`（真正存桶的地方）、`SeatMapper`（装载时回源聚合）、`TrainMapper`（查车型以确定席别全集）、`RedisCacheHelper`（分布式锁与带 TTL 的 Hash 写入）、`MeterRegistry`（打点）[E4]。它没有持任何订单或库存服务，说明它根本不参与扣减。

```
takeToken(trainId, dep, arr, seatTypeCountMap) --> Lua 扣减 --> 1 放行 / 0 拒绝 / -1 桶缺
returnToken(trainId, dep, arr, seatTypeCountMap) --> Lua 加回 --> 异常只告警
                    ↓ 桶缺时
loadBucket(...) --> 分布式锁 --> 聚合 t_seat --> hPutAllWithTtl(桶, TTL)
```

关键字面语义：

- **返回码常量**：`TAKE_SUCCESS = 1L`、`TAKE_REJECTED = 0L`、`BUCKET_MISSING = -1L` [E4]。取令结果用三个值区分"成功 / 明确不足 / 桶或字段不存在"，第三种是触发装载的信号，而不是拒绝理由 [E7]。
- **两个 Lua 脚本**：`lua/take_token_from_bucket.lua` 与 `lua/return_token_to_bucket.lua`，以 `DefaultRedisScript<Long>` 静态加载 [E4]。扣减与归还不是"读—算—写"的 Java 组合命令。
- **配置项**：`my12306.availability.token-bucket.enabled` 默认 `true`，`expire-minutes` 默认 `10`（分钟）[E4]。
- **监控计数**：`my12306.token.pass` / `my12306.token.reject` / `my12306.token.degrade` / `my12306.token.load` [E7][E1][E3]。
- **开关与空参数短路**：`!enabled` 或席别数量为空时，`takeToken` 直接返回 `true`，`returnToken` 直接返回 [E7][E1]——这本身就是"准入组件缺位时不阻购"的态度。

## 分桶粒度：车次 × 区间，席别是桶内字段

桶的粒度不是"一列车一个桶"，也不是"一个车厢一个桶"，而是**一个车次的一个上下站区间对应一个 Hash 桶**：`buildBucketKey(trainId, departure, arrival)` 的入参就决定了 Key [E4]；`loadBucket` 里拼锁 Key 时同样用 `CacheUtil.buildKey(trainId, departure, arrival)` 作为后缀 [E3]；装载 SQL 的过滤条件也是 `train_id` + `start_station` + `end_station` [E3]。

同一个桶内部，**席别才是 field**：装载时构造的 `Map<Object,Object> bucket` 以 `String.valueOf(seatType)` 为键、可售数为值 [E3]。这带来两个具体后果：

1. **一次取令可以带多个席别**。`takeToken` 接收 `Map<Integer,Integer>`，先经 `normalize` 归并，再整体交给同一个 Key 的 Lua 脚本 [E7][E4]。所以"同一区间下二等座和一等座"共享一个桶、一次原子判定。
2. **售完的席别不会被遗漏**。装载时会按车型支持的全部席别遍历，用 `availableBySeatType.getOrDefault(seatType, 0L)` 补 0，代码注释写明目的是"避免售完席别永久触发 field 缺失重装" [E3]。若只写非空席别，`-1` 会不断把请求拖进装载路径。

这一粒度与项目"余票必须按区间算"的区间票额模型一致：余票口径是"车次 × 区间 × 席别"，`t_seat` 每行带 `start_station` / `end_station` [E8]。**因此**可以推断，令牌桶的分桶维度是刻意对齐余票口径的，而不是巧合——否则桶的粒度会与购票时的区间过滤条件错位。（`E8` 属说明性材料、时效 UNKNOWN，此条按推导理解。）

## 桶怎么被装满：懒加载、聚合 SQL 与 TTL 自愈

装载不是启动时预热，而是**按需触发**。跟着一次请求看：

1. `takeToken` 先 `normalize` 请求席别数量，构造 bucketKey，执行 `TAKE_TOKEN_SCRIPT` [E7]。
2. 若返回 `BUCKET_MISSING`（-1），调用 `loadBucket(bucketKey, trainId, departure, arrival, requested.keySet())`，然后**再执行一次同样的脚本** [E7]。注意这里传的是本次请求涉及的席别列表，不是全部席别。
3. `loadBucket` 在 `RedisCacheHelper.executeWithLock` 的分布式锁内执行 [E3]——多个并发请求同时发现桶缺失时，只有一个真正装载。
4. 锁内先做一次"够不够用"的检查：把请求席别逐个 `hMultiGet`，若全部非空就直接返回；代码注释点明"Key 存在不代表字段完整；只要本次请求涉及的任一席别缺失，就重新装载完整桶" [E3]。
5. 真正装载时执行一次聚合查询：从 `SeatDO` 按 `train_id`、`start_station`、`end_station`、`seat_status = AVAILABLE`、`del_flag = 0` 分组统计 `seat_type` 与 `COUNT(*)`，注释说明这是为了"减少装载阶段的 SQL 往返" [E3]。
6. 再 `trainMapper.selectById(trainId)` 拿车型，用 `VehicleTypeEnum.findSeatTypesByCode` 得到该车型支持的席别全集 [E3]。车次不存在、或车型席别为空，直接抛 `IllegalStateException` [E3]。
7. 最终 `redisCacheHelper.hPutAllWithTtl(bucketKey, bucket, expireMinutes, TimeUnit.MINUTES)` 写入并设置过期时间，同时 `my12306.token.load` 计数 +1 [E3]。

**TTL 自愈是推导出来的，不是注释写出来的**：桶 Key 写入时带 `expireMinutes` 过期，而过期后下一次取令只会拿到 `-1`，于是重新走装载路径，把桶重置为当次的数据库聚合值 [E3][E7]。**因此**这个设计不需要任何主动刷新任务——它把"刷新"外包给了过期。装载失败也没有补偿逻辑，因为下一次请求自然会再试。

顺带解释一个容易疑惑的细节：为什么装载后还要"重试一次脚本"？因为第一次 `-1` 只说明**桶或请求席别字段缺失**，`loadBucket` 完成后桶里是否真的出现了这些字段，只能由第二次取令来验证；如果第二次仍不是 0/1，就落到降级放行分支 [E7]。

## 取令与归还：Lua 脚本里的原子扣加

`takeToken` 的分支是完整的四路 [E7]：

- `1` → `my12306.token.pass` +1，返回 `true`（放行）；
- `0` → `my12306.token.reject` +1，返回 `false`（业务层据此抛"列车站点已无余票"，见 `PurchaseTicketServiceImpl` [E20]）；
- `-1` → 装载后重试；
- 其他值或抛异常 → `log.warn` + `my12306.token.degrade` +1，返回 `true`（降级放行）[E7]。

```pseudo
takeToken(trainId, dep, arr, counts):
    if not enabled or counts empty: return true
    requested = normalize(counts)
    if requested empty: return true
    try:
        r = eval(TAKE_SCRIPT, key(trainId,dep,arr), requested)
        if r == -1:
            loadBucket(...); r = eval(TAKE_SCRIPT, ...)
        return per(r)   # 1 -> pass, 0 -> reject, else degrade-pass
    catch: degrade++; return true
```

`returnToken` 则短得多：短路检查 → `normalize` → 执行 `RETURN_TOKEN_SCRIPT` → 异常只 `log.warn("余票令牌归还异常，保留偏松降级并等待 TTL 自愈")` 并 `my12306.token.degrade` +1，**不向调用方抛出** [E1]。这保证"归还"这件事永远不会把已经成功的业务打回。

并发正确性从哪来？装载阶段靠 `RedisCacheHelper.executeWithLock` 的分布式锁，取令与归还阶段靠 Redis 单线程执行 Lua 脚本带来的原子性 [E3][E7]。说明一下：Redis 以原子方式执行 Lua、脚本内不会被其他命令插入，属于通用机制，不是本项目特有的实现；本项目的证据只到"用了 Lua 脚本 + 分布式锁"这一层 [E4][E3]。

一个仍需保留的条件判断：测试文档记录"多席别时一个席别不足 → 两个都不被扣"，即整笔请求被拒绝 [E18]。**如果** `take_token_from_bucket.lua` 确实是"先整体校验、再统一扣减"，**那么**这个结果是脚本语义的自然结论；但脚本源码不在证据中，此条按带前提的推断接受，而不是确定结论。

## 为什么这样设计：宁可多发令牌，不可少发

核心取舍一句话：**令牌桶的作用是减少无效请求，不是保证不超卖；不超卖的保证始终来自 `UPDATE ... WHERE seat_status = AVAILABLE` 那条条件更新，所以令牌宁可比真实值多，不能比真实值少** [E17][E4]。多发只是让更多请求打到数据库、由条件更新兜底；少发则会直接制造"有票却买不到" [E17]。这条原则解释了前面所有看起来"不够严谨"的细节：

- **异常一律放行**：Redis 挂了、脚本报错、装载后仍缺字段，都走 `degrade` 放行 [E7]；
- **归还宽松**：归还异常不重试、不抛出，交给 TTL [E1]；
- **懒加载而非强一致预热**：桶缺就现装，装不上就放行 [E7]；
- **补 0 而非省略 field**：减少无谓的重装，让"售完"表现为 `reject` 而不是反复装载 [E3]。

反过来看一个反面情形：**假设**把展示余票缓存和令牌桶合并成同一个 Key，那么"购票成功后删除展示缓存以刷新"这个动作会连带删掉令牌桶，下次装载又把令牌重置为数据库值，等于把已扣的令牌"还"了回去，令牌虚高 [E19]。两个缓存的失效口径（展示侧删除重算、令牌侧增量维护）根本不同，**因此**必须分 Key——这不是风格问题，是正确性问题 [E19]。

## 失败与降级：桶缺、Redis 挂、归还失败、重复归还

| 失败情形 | 项目行为 | 证据 |
|---|---|---|
| 桶 Key 不存在 / 请求席别字段缺失 | 触发 `loadBucket`，装载后重试一次 | [E7][E3] |
| 装载后仍拿不到结果 | `degrade` +1，放行 | [E7] |
| Redis 抛异常（连接、序列化等） | `catch` 后 `degrade` +1，放行 | [E7] |
| 归还时异常 | 只 `warn` + `degrade`，等 TTL 自愈 | [E1] |
| 桶已被删除或过期后归还 | 归还脚本不重建 Key（测试文档记录 `returnAbsentDoesNotCreate`） | [E18]（条件性） |
| 重复取消 | 只归还一次（测试记录第二次仍为 810） | [E18]（条件性） |
| 支付成功 | 令牌**不**归还 | [E18]（条件性） |

事务边界这一层很关键，它是"不泄漏也不多还"的支点：

- 在回滚/取消链路中，`returnTokensAfterCommit` 会把归还动作注册为事务同步：如果当前没有活动事务就直接执行，否则注册 `afterCommit` 回调再执行 [E12]。**因此**只有本地事务真正提交后才会归还，避免事务回滚了却把令牌放回去。
- 在购票主流程中，先用 `takeToken` 准入，失败即抛"列车站点已无余票"；随后 `finally` 里检查 `reservationCommitted`，**未提交才归还**，代码注释写明"本地事务提交后，cancelCallback 是唯一的令牌归还方" [E20]。

这两处合起来形成一条分工：**乐观路径（提交成功）不归还，失败路径（未提交、取消回调）负责归还**。不过要注意证据边界——支付成功、关单等路径的完整调用链在给定证据里并未全量覆盖，所以这里只断言"这两条已看到的路径是这样分工"，不能说"所有路径都已被证明覆盖"。

还有两处测试文档承认的空白：**Redis 不可用时的降级放行**与**Feign 失败时的归还**被标为 ⚠️ 未覆盖，`tokenDegrade` 在测试中始终为 0，说明异常分支从未被主动触发过 [E18]。`E18` 属 FUTURE 计划材料，其结论对应当次测试范围。

## 边界：余票桶不解决哪些问题

- **不对外展示余票**。查询接口读的是另一个 Key：`TRAIN_STATION_REMAINING_TICKET + CacheUtil.buildKey(trainId, departure, arrival)`，field 取 `seatType`，未命中则走 `seatMarginCacheLoader.load(...)` 回源 [E15]。令牌桶没有任何路径向查询接口提供数值。
- **购票流程会清理展示缓存**。`PurchaseTicketServiceImpl` 在本地预约成功后调用展示余票缓存的清理 [E20]，对应的 `evictRemainingTicketCache` 正是删除 `TRAIN_STATION_REMAINING_TICKET + buildKey(trainId, departure, arrival)` [E16]。这与历史文档记录的"购票成功后没有任何代码去更新或删除这个 hash"不一致 [E13]——**如果** `E13` 描述的是更早版本，**那么**该缺口在当前代码中已经被补上；这是带前提的判断，不能直接宣布"文档过时"。
- **不保证与 `t_seat` 精确一致**。桶的值是懒加载快照 + 增量维护 + 异常放行的组合产物，允许偏高；偏高由数据库条件更新兜底 [E4][E17]。
- **不与展示缓存共用失效口径**。两者必须分 Key，否则删展示缓存会重置令牌 [E19]。

**无法从现有证据确认的部分**（集中说明，避免每节重复免责）：

- 两个 Lua 脚本的具体源码未在证据中，多席别是否"整体校验后统一扣减"、归还是否封顶、重复归还是否幂等，只能由测试文档间接推断 [E18]。
- `buildBucketKey` 生成的实际 Key 前缀未在证据中给出，**因此**令牌桶 Key 与展示余票 Key 之间是否存在前缀层面的关联或碰撞风险，无法确认（只能确认二者由不同代码路径构造 [E4][E15]）。
- 当前部署是否覆盖 `enabled` / `expire-minutes` 默认值未确认 [E4]。
- 支付成功与关单路径与归还动作的完整调用关系未完整覆盖 [E12][E20]。
- 监控指标是否有容量或告警阈值配置，证据未涉及 [E7][E1][E3]。
- `E8`、`E13`、`E17`、`E18`、`E19` 多为说明性或计划类材料，时效标记包含 HISTORICAL / FUTURE / UNKNOWN，其描述与当前实现可能存在落差；正文中凡引用它们之处，均已按"设计意图"或"条件性判断"处理。

## 一页复述：余票桶设计要点

**一句话**：余票桶是一个**区间级 Redis Hash 令牌桶**——Key = 车次 + 出发站 + 到达站，field = 席别，value = 令牌数；懒加载自 `t_seat` 可售聚合、带 TTL 自愈、用 Lua 原子取还、异常一律降级放行，只做购票准入，不做库存扣减 [E4][E3][E7][E1]。

| 维度 | 设计 |
|---|---|
| 承载类 | `TicketAvailabilityTokenBucket`，对外 `takeToken` / `returnToken` [E4] |
| Key | 车次 × 出发站 × 到达站 [E4][E3] |
| field / value | 席别 → 令牌数；车型全部席别补 0 [E3] |
| 初始来源 | `t_seat` 按区间 + 席别、`AVAILABLE`、`del_flag=0` 聚合计数 [E3] |
| 装载时机 | 取令返回 `-1` 才装载，锁内执行，装载后再试一次 [E7][E3] |
| 原子性 | Redis 执行 Lua 脚本；装载用分布式锁 [E7][E3] |
