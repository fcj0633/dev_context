Answer:
项目中的“余票桶”指的是 `TicketAvailabilityTokenBucket`，它的设计目标不是保存最终库存，而是在请求进入用户锁、席别锁和数据库事务之前，先用 Redis 做一道廉价的购票准入判断：如果桶里明显没有对应区间、对应席别的余票，就提前拒绝，避免无效请求穿透到锁和 MySQL；如果桶缺失，先尝试懒加载并重试；装载后仍缺席别或 Redis 异常，则降级放行，让后续链路继续处理。因此它本质上是一份“更近似的余票副本”，不是库存事实源，最终能不能占座仍由 MySQL 条件更新决定。

## 一、设计目标与领域模型

余票桶最重要的设计前提是“余票按区间算”，而不是按整列车算。项目设计文档明确指出：一个座位可以按不重叠区间重复售卖，余票口径是“车次 × 区间 × 席别”，`t_seat` 的每一行带 `start_station` / `end_station`，购票时也必须按区间过滤。这解释了为什么桶不是简单按 `trainId` 存一个总余票数，而是要把出发站、到达站纳入定位维度。当前代码中取令牌和还令牌都传入 `trainId`、`departure`、`arrival`，并通过 `buildBucketKey(trainId, departure, arrival)` 构建桶键；装载桶时的聚合查询也明确以 `train_id`、`start_station = departure`、`end_station = arrival`、`seat_status = AVAILABLE`、`del_flag = 0` 为条件，再按 `seat_type` 分组统计。也就是说，桶的一个键对应一个“车次 + 区间”，这个键下的 Hash 字段对应不同席别。

## 二、数据结构、装载与 TTL

从实现证据看，桶使用 Redis Hash：`takeToken` 和 `returnToken` 都先对传入的 `seatTypeCountMap` 做 `normalize`，再构建 `bucketKey`，然后执行 Lua 脚本。`loadBucket` 中把席别转成字符串作为 Hash field，把可售数量转成字符串作为 value，最后通过 `hPutAllWithTtl` 写入并设置 TTL。验证报告记录了一个具体现象：首次购票会自动创建类似 `my12306-ticket-service:train_station_token_bucket:1_北京南_宁波` 的键，Hash 包含车型全部席别 `0/1/2`，没有库存的席别也保留为 `0`，实测 TTL 为 600 秒。代码中 TTL 由 `my12306.availability.token-bucket.expire-minutes` 控制，默认 10 分钟，启停由 `my12306.availability.token-bucket.enabled` 控制且默认开启；600 秒与默认 10 分钟一致。

装载策略是“懒加载 + 加锁 + 补零”。取令牌时先执行 `TAKE_TOKEN_SCRIPT`，如果返回 `BUCKET_MISSING`，就调用 `loadBucket` 装载，然后重试一次取令牌。`loadBucket` 会先对 `LOCK_TRAIN_STATION_TOKEN_BUCKET` 加锁，检查本次请求涉及的席别字段是否都已存在；只要任一席别缺失，就重新装载完整桶。装载时先做一次聚合查询取得该区间各席别的真实可售数，再查车次车型支持的全部席别，并按车型席别集合补 `0`，避免售完席别永久触发“字段缺失”重装。这个设计在验证报告中被描述为：没有库存的席别也保留为 `0`。写完后打点 `my12306.token.load`。

这里需要指出一个证据口径差异：一般设计文档 `S2C-2` 把令牌桶描述为 `TICKET_AVAILABILITY_TOKEN_BUCKET + trainId`，Field 为 `出发_到达_席别`；但当前代码调用 `buildBucketKey(trainId, departure, arrival)`，`loadBucket` 把席别作为 Hash field 写入，验证报告给出的键示例也包含区间信息。由于 `buildBucketKey` 的具体实现和 Lua 脚本内容未在证据中展开，无法仅凭现有 Context 裁决精确拼装方式，只能确认桶键由车次和区间共同决定、席别通常作为 Hash field 参与定位。

## 三、取令牌、还令牌与降级策略

取令牌流程体现了“准入过滤、异常放行”的取舍。`takeToken` 在桶未启用、入参为空或规范化后为空时直接返回 `true`，不拦截。真正执行 Lua 后，返回 `1` 表示取令牌成功，打点 `my12306.token.pass` 并返回 `true`；返回 `0` 表示拒绝，打点 `my12306.token.reject` 并返回 `false`；如果装载后仍缺少席别，或者执行脚本抛异常，就记录告警、打点 `my12306.token.degrade`，然后降级放行返回 `true`。这说明桶的设计原则是“宁可偏松，不可误杀”：Redis 或桶状态异常时不能阻塞正常购票，最终由下游锁和 MySQL 条件更新兜底。

还令牌流程与之对称。`returnToken` 在未启用或 `seatTypeCountMap` 为空时直接返回；否则规范化后执行 `RETURN_TOKEN_SCRIPT`。如果归还异常，会记录“余票令牌归还异常，保留偏松降级并等待 TTL 自愈”，并打点 `my12306.token.degrade`。归还时机不是随意调用，而是在回调链路中通过 `returnTokensAfterCommit` 处理：如果当前存在事务同步，就注册 `afterCommit`，在事务提交后归还；如果不存在事务同步，则立即执行。这可以避免事务回滚后错误地把令牌加回去，说明令牌归还与事务边界被有意绑定。

## 四、并发协调与最终正确性

令牌桶本身不是锁，也不是最终库存。真正本地占座由 `reserveLocally` 完成：先获取用户级 Redisson 锁，再按席别获取席别锁，然后在事务服务 `doPurchaseInTransaction` 中执行占座。释放时逆序释放席别锁，再释放用户锁，并对计时上报异常做了保护，注释明确“Observability must never change reservation or token ownership semantics”。因此整体结构是：令牌桶在前置阶段做快速准入，锁和事务在后置阶段保证占座互斥与一致性。

最终事实源是 MySQL。类注释明确写道：Redis 余票令牌桶只负责购票准入，不是库存事实源；异常时始终降级放行，最终是否能占座仍由 MySQL 条件更新决定。设计文档进一步把购票链路里的余票分成三份：MySQL `t_seat` 真实库存、Redis 站点余票缓存、Redis 令牌桶；三者载体、写入方、精度不同，因此天然会漂移。站点余票缓存的加载逻辑在 `SeatMarginCacheLoader#load` 中：它使用 `TRAIN_STATION_REMAINING_TICKET + trainId_出发_到达` 作为 Hash 键，按路线批量写入各区间各席别余票，并有锁与回填逻辑。购票成功或回调时会删除该站点余票缓存，删除失败则记录告警并等待缓存过期。这些证据说明令牌桶之外还存在一份近似余票缓存，令牌桶是更前置、更近似的一层副本。

## 五、证据边界

当前证据可以确认余票桶的核心设计：Redis Hash、按车次与区间定位、席别为字段、懒加载完整装载、车型席别补零、TTL 自愈、Lua 脚本取还、异常降级放行、不是最终库存事实源、最终由 MySQL 条件更新和锁事务兜底。但仍有关键细节无法从现有 Context 可靠确认：`buildBucketKey` 的具体拼装实现未展示；`take_token_from_bucket.lua` 与 `return_token_to_bucket.lua` 的脚本内容未提供；`SeatMapper` 最终条件更新的 SQL 未出现；令牌桶与站点余票缓存之间是否存在同步、回写或对账机制，证据中没有实现级说明。设计文档提到的“10 秒自愈机制”只出现在一般文档中，且被引用的第 8 节细节未进入证据，不能据此证明当前代码已经落地。C2 和 C12 属于设计意图层面的文档，C6 是验证报告，只能证明其中明确记录的创建键、席别补零和 600 秒 TTL 测试结果，不能单独证明全部代码路径。

总体上，项目的余票桶是一个“区间化、席别化、懒加载、带 TTL、Lua 脚本取还、异常降级”的 Redis 准入桶。它的价值在于用近似快照挡住明显无票的请求，而不是替代 MySQL 库存；一旦桶缺失、过期或异常，系统优先保证可购票，再由锁、事务和 MySQL 条件更新承担最终正确性。
